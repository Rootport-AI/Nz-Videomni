# 第1部 決まったこと

## 1. 利用者から見た動き

**音声フォルダを空欄にして画像フォルダだけを指定すると、画像1枚につき動画1本を作るバッチになります。** これまでの「音声フォルダを丸ごと指定して、就寝中などにA2Vを連続生成する」機能（a2v）と同じパネル・同じ操作感で、画像だけを渡したときの新しい動き（i2v）が使えるようになりました。

1. **どちらのモードになるかは、スキャンボタンを押した瞬間に決まります。** 音声フォルダを指定していれば（画像フォルダの有無に関わらず）従来どおりのa2v、音声フォルダが空で画像フォルダだけ指定していればi2v、両方とも空ならスキャンボタン自体が押せません。**一度スキャンしたら、そのバッチが終わるまでモードは固定されます**——スキャン後に設定パネルの値を変えても、走行中に音声フォルダや画像フォルダを触っても、選んだモードが黙って入れ替わることはありません。
2. **i2vモードの表**は次のようになります。
   - 番号列: 1始まりの連番（ファイル名の自然順——`img2.png`が`img10.png`より前）。
   - 音声列: すべての行が固定のラベル「i2vモード」になります（音声ファイルが無いため）。
   - 長さ列: Create画面のDURATION（尺）を秒表示にしたもの。すべての行が同じ値です。
   - 画像列: 初期値は各行が指すファイル自身の名前です。ドロップダウンから他の画像や「Shared」へ変更できます。
3. **出力フォルダとファイル名**: 出力先を自分で選んでいなければ、**画像フォルダの兄弟フォルダ**（`{画像フォルダ名}_i2v_out`）が自動で入ります（音声フォルダを使うa2vでは`_a2v_out`）。出力ファイル名は、各行が元にした**画像ファイルの語幹**に`.mp4`を付けたものです（例: `cat01.png` → `cat01.mp4`）。同名の出力が既にある場合は上書きせず、番号を付けて保存します。
4. **行画像の生成強度**は、a2v・i2vのどちらのモードでも同じ規則になりました。**Create画面冒頭のキーフレームカード**（「Shared」を選んだ行が参照するのと同じカード）にスライダー値があればその値を、無ければ既定の0.8を使います。**この規則は今回、バッチa2vの行画像にも及びました**——これまでバッチa2vの行画像は強度1.0で固定でしたが、今回からSharedと同じ値を使うように変わっています（詳しくは§2.5）。
5. **「Shared」の意味は変わりません。** 画像ドロップダウンの先頭は常に「Shared」で、これを選んだ行はCreate画面のKEYFRAMESカードをそのまま使います。KEYFRAMESが空の状態でSharedの行がある場合、開始できずに既存の警告が出るのも従来どおりです。
6. **`chunked_upsample`（省メモリの時間分割アップサンプル）チェックボックスは、i2vモードでは灰色になります。** i2vの1行は単発の`POST /generate`で、そもそも時間分割アップサンプルの工程を持たないためです。
7. **バッチパネルは、仕組みのうえでは両方のベースモデルで動きます（D10）。** パネルが灰色になるかどうかは、読み込んでいるエンジンの`unsupported_features`（`GET /models`）に`chain`または`a2v`が含まれるかどうかだけで決まります（`featureScope.ts`の`batchA2vDisabledFor`）。LTX 2.5アダプタは台帳[`PENDING_TASKS_CLOSED.md`](../../../Docs/PENDING_TASKS_CLOSED.md) §3-102（2026-09-01クローズ）以降どちらの語も宣言していないため、**バッチa2vは既にLTX 2.5でも動作し、今回追加したi2vモードも同じゲートに乗るぶん理屈のうえでは動作します。** ただし**今回の実機ゲートG1〜G12はLTX 2.3だけで実施しました**——LTX 2.5での実機確認は2026-09-15にオーナーが実施しクローズ済みです（正本はバックエンド[`VERIFICATION_LOG.md`](../../../Docs/VERIFICATION_LOG.md) §108.7、台帳は[`PENDING_TASKS_CLOSED.md`](../../../Docs/PENDING_TASKS_CLOSED.md) §3-151）。

## 2. 決まったこと

**以下、各節の見出しに、対応するオーナー裁定の番号（D1〜D13。D1〜D12は2026-09-15、D13は2026-09-16）を添えます。**

### 2.1 モードの決定とスナップショットへの凍結（D1）

**モードはスキャン時に一度だけ決まり、以後は走行スナップショットに凍結されます。** 判定は次の1つの純関数だけが行い、「スキャンボタンが押せるかどうか」と「実際に何をスキャンするか」が同じ関数を通るため、両者が食い違うことはありません。

```
scanModeFor(音声フォルダ, 画像フォルダ):
    音声フォルダが指定されている → a2v
    音声フォルダが無く、画像フォルダが指定されている → i2v
    どちらも無い → 決定不可（スキャンボタンを無効化）
```

決まったモードは、走行開始（`start()`）の瞬間にランナーへ渡す設定一式（`mode`）として固定されます。**`mode`は省略できない必須の値です**——「省略したらa2vとして扱う」という暗黙の既定は作っていません。これは、i2v用に用意したはずの行が誤ってa2vとして扱われ、存在しない音声ファイルを探しに行く事故を防ぐためです。

### 2.2 i2v行の中身（D2）

行の形そのもの（列の集合）は変えていません。**スキャン元の画像ファイル名は、音声ファイル名を保持する既存の列にそのまま入ります。** この列は出力ファイル名の元にもなっているため、画像列を利用者が「Shared」へ切り替えても、行がどの画像から生まれたか・出力名が何になるかは変わりません。

| 列 | i2v行の値 |
|---|---|
| 番号 | 1始まり（ファイル名の自然順） |
| （音声名の列） | スキャン元の画像ファイル名。表には出さず、出力ファイル名の元にする |
| 長さ | Create画面のDURATIONを秒表示にしたもの |
| 画像 | 同じ画像ファイル名（初期値。Sharedへ変更可） |
| プロンプト・状態・出力・スキップ理由・エラー | 空／「待機中」／空／空／空 |

**「Shared」の意味そのものは変えていません（D6）。** 画像ドロップダウンの先頭は常に「Shared」のままで、i2vモードでは各行の初期値が自分のファイル名になるだけです。Sharedを選んだ行にKEYFRAMESが1枚も無い場合に開始をブロックする既存のゲートと警告も、a2v・i2v共通でそのまま効きます。

### 2.3 スキャンの手順（D4・D8）

1. 音声フォルダが指定されていれば、そのフォルダを列挙して従来どおりの行を作ります（a2vモード）。
2. 画像フォルダが指定されていれば、そのフォルダを**1回だけ**列挙します。この列挙結果は、行ごと画像ドロップダウンの選択肢と、i2vモードの行そのものの**両方**に使われるため、2つが食い違うことはありません。
3. i2vモードなら、その列挙結果からファイル名の自然順で行を作ります。
4. 決まったモードを記録し、あわせてスキャン時点のFPSとDURATION上限も記録します（あとからCreate画面の値が変わったことを検知するため）。

**画像の拡張子は、a2v・i2vのどちらも`/config`が配る`upload.allowed_image_extensions`（アップロードAPIが実際に受け付ける拡張子）を正典にします。** これまでバッチパネルはこの一覧をフロントエンド側にハードコードしていましたが、今回`/config`由来の一覧へ一本化しました。**この結果、a2vの行ごと画像ドロップダウンから`.bmp`・`.gif`が消えます**——もともとアップロードAPI側が受け付けていなかった拡張子なので、実害のある変化ではありません。

**画像フォルダの大きすぎるファイルを、スキャン時点で事前に弾くことはしません。** 上限を超えたファイルは、実行時にアップロードがエラーを返した時点でその行だけが失敗になります（§3参照）。

### 2.4 走行開始時の再判定

DURATIONやFPSは、スキャンしたあとでもCreate画面側でいつでも変更できます。開始ボタンを押した瞬間、行は**開始時点の現在値**へ必ず作り直されます。

- a2vモードは、音声の長さから求めたフレーム数を現在のFPSで引き直します（従来どおり）。
- i2vモードは、そもそも音声由来の長さを持たないため、単純に**現在のDURATIONとFPSをそのまま**すべての行へ上書きします。すでに完了・失敗・スキップ済みの行には触れません。

### 2.5 行画像の生成強度（両モード共通の新しい規則、D5）

**行が自分の画像を使うとき（Sharedではないとき）、その強度はCreate画面冒頭のキーフレームカードのスライダー値を使います。** readyなカードが無ければ既定の0.8を使います。これは「Sharedを選んだ行が参照する値」とまったく同じ値で、走行開始時点で凍結されます（開始後にカードの値を動かしても、走行中のバッチには影響しません）。**Chained画面のバッチi2v-longは対象外で、その行画像は従来どおり1.0固定です（`buildI2vLongPayload.ts`）。**

**この規則は、バッチa2vの行画像にも初めて適用されました。** これまでバッチa2vの行画像は強度1.0で固定でした。今回、i2vモードのために「行画像の強度」という概念を整理し直した際、a2vとi2vで別々の規則を持たせる理由が無いと判断し、**a2vの行画像もこの規則へ揃えました**。**バックエンド同梱のGradio版バッチも、いまは同じ規則で送ります**——共有キーフレームのうち`frame_idx`がいちばん小さいものの強度を使い、共有キーフレームが1枚も無ければ既定の0.8を使います（以前は1.0固定でした）。

### 2.6 入力フォルダを変えたときの規則

**音声フォルダ・画像フォルダのどちらを変えても、行・スキャンエラー・記録済みのFPSとDURATION上限・確定したモードが、まとめて消えます。** 画像フォルダも行の生成元になった以上、「片方のフォルダだけ特別扱いする」規則を増やさない判断です。これにより、**a2vの挙動もこれまでよりわずかに変わりました**——以前は画像フォルダだけを変えても音声由来の行は残っていましたが、今回からは画像フォルダを変えただけで音声側の行も消えます。

### 2.7 出力フォルダの自動導出（D3）

出力先を自分で選んでいない間、次の1つの規則で自動的に決まります。

```
音声フォルダが指定されている → 音声フォルダの兄弟 `{フォルダ名}_a2v_out`
音声フォルダが無く、画像フォルダが指定されている → 画像フォルダの兄弟 `{フォルダ名}_i2v_out`
どちらも無い → 未定
```

音声フォルダ・画像フォルダのどちらを変えても、この式で出力先が再計算されます（自分で出力先を選んだ後は、その手動指定を上書きしません）。

### 2.8 開始できるかどうかの判定

**フォルダの条件**（モードごとに、行の生成元になっているフォルダが指定されているか）:

- a2v: 音声フォルダが必要。
- i2v: 画像フォルダが必要。
- まだスキャンしていない: 開始不可。

**フレーム数の条件**（新設）: i2vの`num_frames`はCreate画面のDURATIONの生値をそのまま使いますが、この欄は手入力で8の倍数+1のグリッドを外れた値を受け付けてしまいます。外れたまま夜間バッチを走らせると、全行がサーバーの検証エラーで失敗するため、**i2vモードのときだけ**、DURATIONがグリッド上にあることを開始条件へ加えました。a2vは音声の長さから求めるフレーム数が常にグリッド上に乗るため、この条件は関係しません。

このほかの条件（出力先が決まっていること、他のバッチ・他のジョブが走行中でないこと、KEYFRAMESアップロード中でないこと、Sharedを選んだ行があるのにKEYFRAMESが空でないこと、NAG設定が不正でないこと、解像度がグリッド上にあること、実行対象の行が1行以上あること）は、a2v・i2v共通のまま変わっていません。

**`chunked_upsample`（省メモリの時間分割アップサンプル）チェックボックスは、開始条件ではなく画面上の操作そのものをi2vモードで無効化しています（D9）。** i2vの1行は単発生成で、そもそも時間分割アップサンプルの工程を経由しないため、送っても意味を持ちません。

### 2.9 i2v行が送るペイロード（D11）

i2v行は`POST /api/v1/generate`（単発生成と同じエンドポイント）へ、次のフィールドを送ります。並び順はCreate画面の単発生成が組み立てる内容とバイト単位で同じになるよう、テストで固定してあります。

- `prompt`（プロンプトと追加プロンプトを合成したもの）。合成した文字列は、Create画面と同じ解析器に1回だけ通して`<lora:名前:強度>`タグを取り除いたものを送ります。取り出したタグが下の`loras`になります（合成と解析の規則の正本はバックエンド[`BATCH_A2V_CSV_SPEC.md`](../../../Docs/BATCH_A2V_CSV_SPEC.md) §8で、a2v行も同じ経路です）
- `width`／`height`（Create画面の設定値）
- `num_frames`（行のフレーム数。トップレベルの欄で、a2vのような`clips`配列は使いません）
- `frame_rate`／`seed`
- NAG（ネガティブプロンプト）の設定一式（有効なときだけ）
- Accelerationの設定一式（既定から動かしたぶんだけ）
- `loras`（1件以上あるときだけ）
- `conditioning_images`（行の画像またはSharedの画像。無ければ省略）

**送らないフィールド**: `source_audio`、`stage2_window`、`pipeline`、`num_inference_steps`、`guidance_scale`、`overlap_frames`、`overlap_strength`、`chunked_upsample`、`clips`。これらはいずれもチェーン生成専用か、非蒸留モデル専用のフィールドで、i2v行には存在しません。`crop_output` は Create画面の設定を継承して、ONのときだけ送ります（§2.11）。

### 2.10 共用している部品（D12）

409（サーバー混雑）時の再試行、完了までのポーリング、`noClobber`（上書きしないダウンロード）、画像アップロードのキャッシュは、a2v・i2vの両モードで同じ部品を使い回しています。i2v専用に新設したのは、ペイロードの組み立て（§2.9）と、送信先を`/api/v1/generate`へ切り替える分岐だけです。

### 2.11 出力クロップ設定の継承（D13）

**ここで言うクロップは、完成した動画を指定サイズへ切り出す「出力をクロップ」（Create画面の欄）のことです。** §3にある「バッチ側でのクロップ・リサイズ」（入力画像を生成サイズに合わせて中央で切り出す話）とは別物です。

- **バッチパネルにクロップの欄はありません。** Create画面の「出力をクロップ」の設定（チェックと幅・高さ）を、NAGやAccelerationと同じように黙って継承します。走行開始（`start()`）の瞬間に他の設定と一緒に凍結され、開始後にCreate画面の欄を触っても走行中のバッチには影響しません。
- **a2v・i2vのどちらのモードにも効きます。** a2v（`POST /generate/chain`）はクロップがOFFのときも従来どおり`crop_output: null`を明示して送り、i2v（`POST /generate`）はONのときだけ`crop_output`を`height`の直後に載せ、OFFならキーごと省略します。サーバーにとってこの2つは等価です（`crop_output`の既定は「無し」）。見え方が違うのは、i2vの送信本文がCreate画面の単発生成（`toGenerateRequest`）とバイト単位で一致することをテストで固定しているためです。
- **Create画面のクロップが不正（生成サイズ超・空欄・32未満など）だと、バッチは開始できません。** 判定はCreate・Chainと同じ`isCropOutputValid`で、文言もCreate画面の「クロップサイズが生成サイズよりも大きいか、もしくは空欄です。」を借ります。2026-09-16からクロップ欄は自由入力なので、範囲外や空欄を直接打った場合も、クロップを設定したあとに生成サイズを縮めた場合も、同じゲートに掛かります。
- **Chain画面のバッチi2v-longは対象外です。** こちらはChain画面の送信本文をテンプレートとして丸ごと継承する作りで、クロップも、開始ゲート（Chain画面の`validityReasons`をそのまま`chainBlockReasons`として出す）も、以前から効いています。

## 3. 意図的に入れなかったもの

- **画像サイズの事前チェック**: 大きすぎる画像をスキャン時点で弾く仕組みは入れていません。上限超過はアップロード時にサーバーがエラーを返し、その行だけが失敗になります。
- **行ごとの解像度・尺の指定**: すべての行はCreate画面の設定（幅・高さ・DURATION・FPSなど）を共有します。行ごとに違うサイズや尺を指定する仕組みはありません。
- **バッチ側でのクロップ・リサイズ**: フロントエンド（webui・ネイティブブリッジ・アップロードストア）は、画像に対して一切のリサイズ・クロップを行いません。生成サイズと縦横比が違う画像は、**単発生成・チェーン生成と同じように**、バックエンド側（LTX 2.3・LTX 2.5どちらの`ltx_pipelines`も同じ関数）が「覆うように拡縮してから中央で切り出す」処理に委ねます。この事実は今回のために新しく調べて確定したものではなく、既存の挙動を本書で初めて文書に書き起こしたものです。
- **LTX 2.5での実機確認**: バッチパネルは仕組みのうえでは既にLTX 2.5でも動作します（上記§1の7）。今回の実機ゲートG1〜G12はLTX 2.3だけで実施しましたが、**LTX 2.5側の実機確認は2026-09-15にオーナーが実施し、クローズ済みです**（正本はバックエンド[`VERIFICATION_LOG.md`](../../../Docs/VERIFICATION_LOG.md) §108.7、台帳は[`PENDING_TASKS_CLOSED.md`](../../../Docs/PENDING_TASKS_CLOSED.md) §3-151）。

# 第2部 なぜそう決めたか

## 4. なぜ`/generate/chain`ではなく`/generate`なのか

**i2v行を、既存のa2vビルダー（チェーン生成用）に相乗りさせる案を否決しました。**

バックエンドのバリデータには、次の2つの制約があります。

1. `source_video`／`source_audio`／`reference_video_id`／`retake`／`end_source`のいずれも指定しないチェーンは、`clips`が2本未満だとエラーになります（「チェーンには最低2クリップが必要」）。
2. `stage2_window: "full_length"`は`source_audio`が無いとエラーになります。既存のa2vビルダーは、このフィールドを常に送る作りです。

i2v行は音声を持たない1クリップの生成なので、この2つのどちらの経路からも`/generate/chain`には乗れません。単発生成と同じ`POST /generate`へ送るのが、バックエンドを一切変えずに済む唯一の経路でした。バックエンド（`api/`・`engine/`・`engine25/`）は今回1行も触っていません。

## 5. なぜCreate画面の`toGenerateRequest`を再利用せず、並行ビルダーを新設したのか

**単発生成のペイロード組み立て関数をそのまま呼び出す案を否決しました。**

Create画面の`toGenerateRequest`は、画面の「今その瞬間」の状態（クロップ設定・参照動画・制御LoRAなど）を直接読み取る関数です。これをバッチへ流用すると、3つの問題が生まれます。

1. バッチは「開始した瞬間の設定を凍結し、以後の画面操作に影響されない」という前提で動いています。生きた画面状態を読む関数を呼ぶと、この前提が壊れます。
2. i2v行は参照動画関連のフィールドを送ってはいけません。生きた画面の状態をそのまま読むのも禁止です（送るべきでないフィールドを巻き込むため）。`crop_output` は `start()` で凍結した値を引数で受け取って載せます（§2.11）。
3. バッチのランナーは画面のコンポーネントの外側（シングルトン）で動くため、Create画面がアンマウントされたあとに画面のフックへ依存した関数を呼び出す形になりかねません。

既存のa2vビルダー（`buildA2vChainPayload`）が「引数を渡すだけの純粋な組み立て関数」という前提で先に実装されていたため、i2v用にも同じ作りの並行ビルダーを新設し、両者で足並みを揃えました。共通するフィールド（`prompt`・`width`・`height`・`frame_rate`・`seed`・NAG・Acceleration・`loras`）は、Create画面の単発生成が組み立てる内容とバイト単位で同じになるようテストで固定してあります。

## 6. なぜ行画像の強度をこの規則にしたのか

**a2vの行画像だけ従来どおり1.0固定で残す案と、i2v専用に新しい設定欄を作る案の両方を否決しました。**

i2vの実装にあたって「行画像の強度」という概念を整理し直す必要が生まれた際、a2vとi2vで別々の規則を持たせる理由が見当たりませんでした。そこで、**両モードとも「Sharedを選んだ行が参照するのと同じ値」を使う**という1つの規則に統一しました。これにより新しい設定欄を1つも増やさずに済み、「Sharedの行と自分の画像を使う行とで、強度の意味が違う」という利用者にとって説明しづらい非対称も解消されます。

代償は、**バッチa2vの行画像がこれまでの1.0固定ではなくなる**ことと、決めた時点ではバックエンド同梱のGradio版バッチが1.0固定のままで、フロントエンドのバッチパネルとのあいだに差分が生まれたことです（この差分はその後、Gradio版バッチが同じ規則へ揃って解消しました。§2.5）。この代償が実用上問題ないかどうか（行画像を使ったa2v出力で、顔などの追従が変わって見えないか）は、実機ゲートG11でオーナーが確認し、2026-09-15に合格しました（結果は[`VERIFICATION_LOG.md`](../../../Docs/VERIFICATION_LOG.md) §108）。

## 7. なぜD7（i2v行は`crop_output`を送らない）を撤回したのか（D13）

D7は、a2vの行が`crop_output`を常に`null`で送っていた実態に横並びで揃えた判断で、「チェーン専用の欄だから」という理由づけは事実と合っていませんでした——`crop_output`は単発生成の要求にも正規に存在します。一方、a2vが`null`を送っていたのは設計ではなく、設定を組み立てる箇所にクロップの行が無かっただけでした。オーナーは「欄は作らず、Create画面の値をそのまま継承する」と裁定し、両モードを同じ規則に揃えました（§2.11）。
