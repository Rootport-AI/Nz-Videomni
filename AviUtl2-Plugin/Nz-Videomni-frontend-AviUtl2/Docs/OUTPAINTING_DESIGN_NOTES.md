## 1. 機能概要と目標

Outpainting（アウトペインティング）とは、既存の動画の上下左右にキャンバスを拡張し、画面外にあたる領域をAIに描き足させる機能である。画像編集ソフトの「生成拡張」の動画版にあたる。たとえば横長 16:9 の動画の上下を描き足して縦長 9:16 に作り変える、といった用途に使う。

配置場所は、フロントエンドの Edit タブ（2026-08-08 時点ではモックのみのプレースホルダー）配下に新設するサブタブ。Edit タブには将来的に Retake・Outpainting・Inpainting（マスク指定した領域の描き直し）のサブタブを並べる構想である。

**北極星（プロジェクト方針）**: Nz-Videomni で「できること」は、可能な限り Lightricks 公式の実装に準拠させる。第三者製の学習済み重みで代替するのは、公式版を諦めた場合の次善策とする。

## 3. 決定の根拠と調査結果

### 3-1. D1: なぜ公式実装準拠か。「公式」の実像はどれか

公式デスクトップアプリ LTX Desktop（v1.0.0〜v1.1.0 の全リリースノートを確認）には、**空間方向の Outpainting / Inpainting は存在しない**。v1.1.0 の "Video extend" は時間方向（尺の延長）であり別物。公式の空間 Outpainting は次の 3 形態に分かれている。

1. **Reframe**: 有料ホスト API（Fal / LTX Studio 経由）。アスペクト比変換、60 秒上限。Desktop 非搭載。自前再現の対象にならない。
2. **公式 OSS ワークフロー**: `Lightricks/ComfyUI-LTXVideo` リポジトリが配布する ComfyUI ワークフロー＋公式 In-Outpainting IC-LoRA（`Lightricks/LTX-2.3-22b-IC-LoRA-In-Outpainting`）。**再現可能な公式一次資料はこれであり、本機能が準拠する対象**。
3. **Desktop 内部実装**（非公開）: GitHub Issue #424 によれば潜在表現の直接置換＋専用 sigma スケジュールを使い、OSS 版より品質が良いという報告がある。参考情報として頭に置く。

つまり Outpainting を実装すると「LTX Desktop でできること」を超える。準拠先は上記 2 の公式 OSS ワークフローで確定した。

コミュニティ版 LoRA（`oumoumad/LTX-2.3-22b-IC-LoRA-Outpaint`、黒塗り領域を生成対象とするセンチネル方式、マスク入力不要）は、実装が最も軽い代替案として存在する。公式版がうちの環境（蒸留＋GGUF量子化。GGUF はモデル重みの量子化フォーマット）で動かなかった場合の次善策として記録しておく。なお暗いシーンで黒バーと本物の暗部を混同する既知の弱点があり、ガンマ補正の往復（2.0→生成→0.5）で回避するトリックが案内されている。

### 3-2. 公式 OSS ワークフローの機構（2026-08-08 精読結果）

公式サンプル `LTX-2.3_ICLoRA_Outpaint_Two_Stage_Distilled.json`（および Inpaint 版）をパースして裏取りした内容。実装時の仕様書はこの節を出発点に再確認すること。

処理は 3 段からなる。

1. **前処理（ピクセル空間）**: 元動画を拡張後キャンバスに配置し、生成対象領域（Outpainting では外周のパディング帯）を**緑色 RGB(102,255,0) で塗りつぶす**（`LTXVInpaintPreprocess`。黒ではなく緑がセンチネル）。マスクは「白=生成、黒=保持」の二値。Inpainting ではさらにマスクを max-pool で空間・時間方向に膨張させる工程（`LTXVDilateVideoMask`、既定 spatial_radius=32、ぼかしなし）が入るが、**Outpainting ではパディング帯の形状が既知のため膨張工程は不要**。
2. **条件付け（トークン空間）**: 緑塗り済み動画を VAE（変分オートエンコーダ。動画を潜在表現に圧縮する部品）でエンコードし、参照トークンとして条件付けに追加（`LTXAddVideoICLoRAGuideAdvanced`）。attention_strength は既定 1.0。マスクはピクセル空間からトークン空間に正規化されて注意強度に乗算される。
3. **後処理（ピクセル空間）**: 生成結果と元映像を**ラプラシアンピラミッドブレンド**（最大 7 段の多重解像度合成）で合成する（`LTXVLaplacianPyramidBlend`）。マスクを 64px 長辺まで縮小→膨張（既定 dilation=5、範囲 0-15）→元解像度へ補間で戻す処理が実質的なフェザリング（境界のぼかし）として機能し、継ぎ目・色ズレを消す。ワークフロー注記いわく「このdilationが最重要パラメータ」。**保持領域も一度 denoise（ノイズ除去生成）を通ってからブレンドで原画に寄せる設計であり、ピクセル完全一致の保持ではない**点は仕様として認識しておく。

パラメータの実測値（サンプルワークフローの widgets_values より）:

- LoRA 構成: 蒸留 LoRA `ltx-2.3-22b-distilled-lora-384-1.1.safetensors` strength=0.5 ＋ In-Outpainting IC-LoRA `ltx-2.3-22b-ic-lora-in-outpainting-0.9.safetensors` strength=1.0
- sigma スケジュール: stage-1 は 9 値の固定列（1.0, 0.99375, …, 0.0）、stage-2 は 3 値（0.725, 0.4219, 0.0）。CFG=1
- ブレンドの dilation: Outpaint は stage-1=5 / stage-2=2（公式ドキュメントの一般推奨は 6 で、サンプル既定値と食い違う。実装時に要検証）
- キャンバス例: 1920×1088

### 3-3. Inpainting とのマスク機構の共通性（将来展望）

公式の Inpaint 用・Outpaint 用サンプルワークフローを突き合わせた結果、**LoRA ファイル・マスク意味論（白=生成、黒=保持）・緑塗り前処理・条件付けパラメータ・sigma スケジュールまで完全に共通**であることを確認した。違いは 3 点のみ。

| 項目 | Outpaint | Inpaint |
|---|---|---|
| マスクの生成元 | パディング矩形を機械的に算出 | ユーザーが白黒マスク動画を用意（red チャンネルから抽出） |
| 膨張（dilate）工程 | 不要 | 必要（対象物サイズに合わせてユーザー調整） |
| ブレンド dilation 値 | 5 / 2 | 5 / 6 |

Inpaint 側はフレームごとに変化する動画マスク（時変マスク）に対応しており、将来の Inpainting 構想（物体追尾AIで作った白黒マスク動画を元動画と一緒にサーバーへ送る）とそのまま噛み合う。**したがって本機能で作るマスク経路は、Outpainting 専用ではなく、将来の Inpainting と共通の基盤として設計する。** Outpainting はマスクが静的な矩形帯になるだけの特殊ケースである。

### 3-4. D2: なぜ wheel 据え置きの自前実装か

実行時 venv の `ltx_core`（git commit `00dc53d` にピン止め）には、空間マスク条件付けクラス `VideoConditionByMask` が**存在しない**（新しい vendor ツリーにのみ存在。`Docs/V2V_CONTINUATION_DESIGN.md` の記述どおり）。選択肢は 3 案あった。

- **(a) wheel のピンを更新して `VideoConditionByMask` を使う** → 新 wheel では `DistilledPipeline` がブロック構成へ全面書き換えされており、エンジンが依存するモジュールグローバル 5 つ（sigma 値・denoise 関数・条件付け関数等）が消滅・改名・シグネチャ変更される。NAG・VSF・SageAttention・res2s 等の全モンキーパッチの移植と全機能リグレッションが必要で、**総合難易度 L**。マスク機能自体より周辺の互換性崩壊コストが支配的。
- **(b) wheel 据え置きで自前実装** → 決定的な発見として、`latent_tools.patchifier.patchify(mask)` は現行ピンでも動く公開 API であり、新 wheel の `VideoConditionByMask` の実体はこれを使った十数行のクラスにすぎない。`ConditioningItem` は Protocol（継承不要）なので、**エンジン側に同等クラスを自前で書いて差し込める**。差し込み口も既存: Single 系は `fast_video_pipeline.py` の `_hybrid_image_conditionings`（IC-LoRA 参照条件付けが現に使っている条件付け追加フック、stage-1/stage-2 の判別も可能）、Chain 系は `_denoise_av_with_carry` の denoise_mask 直書き（時間方向凍結の実績あるパターンを空間へ一般化するだけ）。マスク動画の受け口もアップロードストアは無改修で対応可能（API フィールド追加程度）。**総合難易度 S〜M**。
- **(c) マスクなし（黒レターボックス＋LoRA のみ）** → 実装最軽量だが「保持の保証」が注意強度の変調止まりで効果が不確実。足がかり実験用。

**(b) を採用**。3 案中もっとも低リスクで、公式方式の機構を過不足なく再現でき、将来の Inpainting にもそのまま使える。

### 3-5. D3: なぜ境界処理を独立部品にするか

ラプラシアンピラミッドブレンドは純粋なピクセル空間の後処理であり、生成パイプライン本体と分離できる（公式実装も独立ノードになっている）。独立部品にしておけば、(1) Outpainting と将来の Inpainting で共用できる、(2) 生成品質のチューニング（dilation 値など）を生成本体と切り離して検証できる、(3) 万一品質が不足した場合の差し替え・省略の判断が局所化できる。公式の `pyramid_blending.py` のソースは取得済みで、torch への移植は素直な見通し。

### 3-6. 蒸留＋GGUF 環境での適合性（見込みと検証項目）

- 公式ドキュメントは「IC-LoRA は蒸留モデル・FP8 量子化に対応」と明記している。
- 公式サンプル自体が蒸留向け（Two_Stage_Distilled、蒸留 LoRA 0.5 併用＋固定 sigma）である。
- GGUF＋蒸留 LoRA＋Outpaint IC-LoRA の三重併用は Civitai に実配布ワークフローがある（コミュニティ実績。GGUF への公式保証はない）。
- うち自身が IC-LoRA Depth/Deblur を蒸留＋GGUF＋実行時 LoRA 適用で動かし実機ゲートに合格済み（2026-08-03）。IC-LoRA という仕組み自体の適合性は自前環境で実証済みで、残る検証は In-Outpainting LoRA 固有の挙動のみ。
- 未解決の懸念: GitHub Issue #243（蒸留の sigma スケジュールと IC-LoRA 学習時サンプラーの不整合疑い。公式未回答）。継続ウォッチ。

### 3-7. 解像度制約 — 128 の倍数を継承する

参照動画（reference_video_id）付きリクエストは、既存 API が**アダプタ種別を見ずに一律で幅・高さ 128 の倍数**を要求する（`api/generate.py` / `api/generate_chain.py`。理論上 downscale 係数 1 なら 64 で足りるとコードコメント自身が認めているが、保守的に 128 で統一されている）。**Outpainting もこの 128 制約をそのまま継承する**（オーナー決定。検証コードの条件分岐を増やさない）。

### 3-8. 総フレーム数と参照動画の関係 — フレーム数の事前取得は不要

既存の IC-LoRA 参照動画は、フレーム数の事前検証も fps（フレームレート）整合も一切なく、リクエストの num_frames を上限に**先頭から読んで打ち切るだけ**（長ければ切り捨て、短ければ短いまま。エラーなし）。これが許されるのは、参照が生成潜在に「位置合わせして上書き」されるのではなく**独立したトークン列として追加される**構造だからである。この仕様を Outpainting に当てはめると:

- ユーザーは Single タブと同じ num_frames スライダー（8n+1 制約。8 の倍数＋1 のフレーム数のみ有効）と fps を指定する。**元動画のフレーム数が 8n+1 かどうかは無関係**（生成尺は常にユーザー指定で、参照はそこに合わせて切られる）。
- タイムラインのリボン（AviUtl2 のオブジェクト表示帯）によるトリムは既存機構が**秒ベース**（`trim_start_sec` / `trim_duration_sec`）で完結しており、`num_frames ÷ fps = 秒数` はフロントで計算できる。**bridge（ネイティブ連携 API）の拡張もバックエンド API の拡張も不要**。

## 4. UI/UX 方針

### 4-1. 入力導線

Chained タブの v2v（動画から動画を生成する機能）と同じ二導線を流用する。

- ドラッグ＆ドロップ（`useFileDrop` / `SourceInputPanel` のパターン）
- タイムライン右クリックメニュー（`menuRouting.ts` の静的テーブルに 1 行追加＋ネイティブ側メニュー 1 項目。§1-6 で実装済みの**リボントリム**（リボンの再生範囲で入力動画を秒指定トリムする機構）をそのまま利用）

### 4-2. 生成サイズ指定 — アライメント方式（D4）

> **⚠ 本節のアライメント方式は 2026-08-11 に撤回された。現行仕様は §5-B を読むこと。** 以下は当時の記録として残してある。

上下左右の追加ピクセル数をスライダー 4 本で指定する。その上に「Input Video Aligned／入力動画調整」として「上詰め・中央・下詰め」「左詰め・中央・右詰め」の 2 系統のラジオボタンを置く。

- 128px の倍数でない動画が入力された場合、ラジオボタンの設定に従って**不足分がスライダーへ自動セット**され、スライダーはその値未満（ゼロ）に戻せなくなる。例: 1265×720 の動画で「上詰め・左詰め」なら、入力時点で右 15px・下 48px が追加された状態から始まる（幅 1265→1280 の不足 15px は左右へ、高さ 720→768 の不足 48px は上下へ割り当てる）。「中央・中央」なら左 7px・右 8px・上 24px・下 24px（割り切れない端数は上詰め・左詰め側へ丸める）。
- 以後、各スライダーは「アライメント初期値＋128×k」の目盛りを動く。これで総寸法が常に 128 の倍数から外れない。
- スライダーの下に「動画の縦横は 128px の倍数でなければなりません」という説明文を付ける。
- **採用しなかった案**: 自由入力値を最寄りの合法値へ自動スナップする案は不採用。「720px と指定したのに 768px の動画が出てくる」というユーザー体験は、最初から 720px を指定できない UI より劣る（オーナー判断）。

### 4-3. プレビュー

動画サムネイルは表示しない。動画が入力されたら、元動画の縦横比の塗り長方形を表示し、スライダーに連動して拡張後キャンバスの縦横比の長方形を線のみで重ね描きする。~~アライメントによる自動追加分も視覚的に伝わる。~~（**2026-08-11 撤回**: 自動追加分そのものが無くなった。プレビューは利用者が入れた値だけを描く。§5-B）React＋SVG（または素の div）で実装でき、外部ライブラリは不要。業界的にも「拡張エリアを枠線でオーバーレイ」は Runway 等が採る標準的な表現である。

### 4-4. 総フレーム数スライダー（D5）

- num_frames（8n+1）と fps は Single タブと同じ形式で指定する。数分〜数時間になり得るタイムライン素材に対し、受け入れる長さの上限をパネル側で決める装置として必須。
- **スライダーの上限を元動画の長さに合わせて動的に短縮**し、元動画より長い生成は指定できなくする（ガイドなし生成の防止）。上限は `probeMediaInfo`（bridge 経由のメディア情報取得。尺・幅・高さのみ返す）の durationSec × fps を**切り捨てで 8n+1 に丸めて**算出する（durationSec は概算のため安全側に倒す）。fps を変更したら上限を再計算する。
- 「裏側で送信値だけ短縮する」案は不採用。UI 表示値と送信値の乖離はズレたまま動くタイプのバグの温床になる（オーナー判断）。
- 上限クランプは state に保存せず、**現在の入力ソースから描画時に毎回導出する**（単一ソース化）。入力の差し替え・取り外し後にクランプだけ残る典型バグを構造的に防ぐ（§prefillSeed 単一ソース化と同じ教訓）。

### 4-5. 快適上限の警告

拡張後解像度で計算する。既存の経験則「約 40,000 トークン（32px 四方マス数×潜在フレーム数）で VRAM スピル開始」を流用し、`(拡張後幅/32)×(拡張後高さ/32)×潜在フレーム数` で警告を出す。エラー表示は `generateReasonMessages.ts` の理由コード辞書に追加する既存パターンに統合する。

## 5-A. 実装時に判明した訂正と確定事項（2026-08-09、W2 実装）

本節は §2〜§4 の方針を実装した際に、**設計時の想定と食い違っていた点**の記録である。上の各節はあえて当時のまま残してあるので、矛盾する場合は本節が優先する。

### 訂正1: D2 の「マスク条件付け自前クラス」は**不要だった**

§3-4 で「`patchifier.patchify(mask)` を使った自前の `VideoConditionByMask` 相当クラスを書き、stage-1/stage-2 へ配線する」と決めていたが、**公式ワークフローの実配線を精読した結果、公式はマスク条件付けを使っていないことが判明した**。

- 公式の `LTXAddVideoICLoRAGuideAdvanced`（ノード 5114）は `attention_mask` 入力が**未接続**で、`attention_strength` は既定の 1.0 のままである。
- 「マスクはピクセル空間からトークン空間へ正規化されて注意強度に乗算される」（§3-2 の 2 番）という当時の読みは誤りだった。
- ノードの widget に見えた `'disabled'` は**マスクの設定ではなく crop の設定**である。ここを混同しないこと。

つまり公式におけるマスクの役割は、(a) 前処理で緑を塗る範囲を決めること、(b) 後処理のブレンドの重みになること、の 2 つだけである。条件付けの経路にマスクは一切入らない。したがって wheel 据え置きの自前実装（案 b）は採用したが、その中身は「マスク条件付けクラス」ではなく「緑塗り＋ブレンド」になった。**難易度は S〜M よりさらに軽い。**

将来の Inpainting（§3-55）も、時変マスクを緑塗りとブレンドに渡すだけで同じ骨格に乗る。この見立て自体は変わらない。

### 訂正2: 緑参照が効くのは stage-1 だけ（`LTXVCropGuides` の実装で確定）

公式グラフの `LTXVCropGuides`（ノード 5013）は ComfyUI 本体の組み込みノードで、実装は `latent[:, :, :-num_keyframes]` によりガイド用の潜在フレームを**末尾から物理的に削除**し、conditioning からも `keyframe_idxs` / `guide_attention_entries` を消す。挿入位置は stage-1 のサンプリング直後・VAE デコードの直前である。

当方の既存実装にはこれと等価な機構がすでにある。

- 参照条件付けを組み立てる `_reference_conditioning_for_stage` は、渡された解像度が半分でなければ空リストを返す（stage-1 限定）。
- 潜在に追加された余分なトークンは、denoise 後に `LatentTools.clear_conditioning` が末尾から切り落とす。

したがって**専用のガード引数を足す必要はない**（`override_stage_check` のような引数を新設しないこと）。

### 訂正3: キャンバスの寸法は「元動画＋パディング」ではなく**リクエストの width/height が正本**

§4-2 は「パディング量を指定するとキャンバス寸法が決まる」と書いているが、実装では逆向きにした。`width` / `height` が最終キャンバスであり、保持領域はそこからパディングを引いた残りである。理由は 2 つ。

1. 128 の倍数という既存ルールは `width` / `height` に掛かるので、そこを正本にすれば検証が 1 か所で済む。
2. 元動画の寸法から逆算すると、サーバー側の実測値とリクエストの値という**2 つの情報源**ができてしまう。両者がずれたとき、参照動画の読み込み処理が黙って拡大縮小と中央切り抜きを行い、「元の画素はそのまま残る」という Outpainting 唯一の約束が静かに壊れる。

実装では元動画の寸法を ffprobe で実測し、保持領域と一致しなければ 422（`OUTPAINT_SOURCE_MISMATCH`）で弾く。フロントエンドの見た目は §4-2 のまま（パディングのスライダー 4 本）で、送信時にキャンバス寸法へ畳んでいる。

### 確定4: ブレンドは境目から内側へ**約 150 画素**まで効く

ラプラシアンピラミッドブレンドのマスク膨張は「マスクを長辺 64 画素まで縮小してから半径 r で膨らませ、元の解像度へ戻す」処理である。つまり実効的な膨張幅は `r × キャンバス長辺 ÷ 64` になり、キャンバス長辺 1920・公式既定の r=5 なら **full 解像度で約 150 画素**に相当する。

膨張は「生成する側」を広げる向きなので、**保持領域の外周 150 画素は元の映像と生成映像の混合になる**。§3-2 が「保持領域もピクセル完全一致ではない」と書いていたのは正しいが、その幅がこれほど大きいことは設計時には認識していなかった。

対応として次の 2 つを実装した。

- 保持領域が縦横とも **256 画素以上**であることを API とエンジンの両方で検証する（それ未満だと保持領域が丸ごと生成画素に置き換わる）。
- パネルに「境目から内側へおよそ 150 画素は混ぜ合わされる（元のままではない）」という説明文を出す。

### 確定5: 緑は可逆 RGB で書き出さないと保てない

緑（102, 255, 0）は ffmpeg のフィルタ内で一度でも YUV を経由すると **(101, 253, 0)** までずれる（実測）。公式 LoRA はその色ちょうどを描き替えるよう学習されているため、キャンバス動画は次の 3 点を守って生成している。

1. `pad` フィルタの**前**に `format=rgb24` を入れ、緑を塗る時点で RGB にしておく。
2. `libx264rgb -pix_fmt rgb24 -crf 0`（使えない ffmpeg ビルド向けに `ffv1` へ退避）。
3. 音声は載せない（`-an`）。音声は元のアップロードから別途読む。任意のコーデックを mp4 へ `-c:a copy` するとコンテナが受け付けない場合があり、再エンコードすれば音が劣化するため。

### 確定6: stage-2 のノイズ量は公式に合わせた

ライブラリ既定の stage-2 は 0.909375 から始まるが、公式ワークフローは 1 段低い **0.725** から始める（`[0.725, 0.421875, 0.0]`）。stage-2 の出発点はブレンド済みのピクセルを符号化し直したものなので、ノイズ量が高いとブレンドで直した継ぎ目を作り直してしまう。公式に合わせた。

### 確定7: 公式との意図的な差分（実装後の確定版）

| 項目 | 公式 | 当方 | 理由 |
|---|---|---|---|
| サンプラー | euler_ancestral_cfg_pp / euler_cfg_pp | 素の euler | wheel に cfg++ 系が無い。CFG=1.0 なので影響は限定的 |
| 蒸留 LoRA 0.5 の併用 | あり | なし | 公式は非蒸留モデルに足している。当方は蒸留済みベース |
| 2 倍拡大の補間 | lanczos | bicubic | torch に lanczos カーネルが無い |
| 参照動画の VAE 符号化 | タイル分割しない | タイル分割する | 16GB での OOM 回避（既存 IC-LoRA 全体の方針） |
| stage-2 の音声参照 | stage-1 の出力音声 | 元動画の音声 | stage-1 で完全固定しているので内容は同じ。既存 A2V と同じ流儀 |
| ブレンドマスク | 全解像度版を 0.5 倍縮小・全フレーム分保持 | 各解像度で直接生成・1 フレームのみ保持 | 後段の縮小＋膨張が半画素差を消すので等価。全フレーム保持は full 解像度で 2.0GB になる |

ラプラシアンピラミッドの計算そのものは、本物の kornia 0.8.3 と**誤差 0.0（完全一致）**であることを 3 ケースの固定データで検証済み（`tests/fixtures/outpaint_pyramid_golden.npz`）。

### 確定8: stage-2 は時間方向に分割しない

Clip Chain は stage-2 を 22 潜在フレームの固定窓で分割するが、Outpainting は単発生成と同じく**分割しない**。公式ワークフローも 121 フレームを 1 回のサンプラーで通している。VAE の符号化・復号は従来どおりタイル分割する（こちらは VRAM のための分割で、別の話）。

## 5-B. パッドの 1 ピクセル刻み化（2026-08-11 オーナー決定）

本節は §4-2（D4 アライメント方式）と §4-3 のプレビュー記述を**撤回**する改訂である。§5-A と同じく、上の各節は当時のまま残してあるので、矛盾する場合は本節が優先する。

### 撤回の理由

128 ピクセル刻みでは「縦 738 ピクセルの動画に上 10 ピクセル・下 20 ピクセルを足して 768 ピクセルにする」という実用的な使い方が表現できない。アライメント方式は「キャンバスが 128 の格子から外れることは構造的に起こらない」という美点と引き換えに、**利用者が足したい量を足せない**という代償を払っていた。オーナー判断でこの取引を解消した。

### 現行仕様

1. **スライダーは 0 起点・1 ピクセル刻み**（`min=0`・`step=1`・初期値 0）。初期配置（詰め方向）のラジオ 2 系統と自動フロアは完全に削除した。
2. **各スライダーに数値入力ボックスを併設**する。打った値はそのまま採用し、スナップしない。範囲外・非数のときだけ端で止める（`outpaintGeometry.clampPad`）。~~上限は対辺の現在値を引いた残り（`maxPad`）で、余地が 0 の素材では両方の操作部を無効化する。~~（**2026-08-11 第2弾で撤回**: 対辺連動と、余地 0 での操作部無効化はどちらも廃止した。上限はスライダー 220・ボックス 4096 の定数 2 本になった。§5-C）
3. **128 の倍数はブロック理由で担保する**。拡張後キャンバスの幅・高さを個別に検査し、`canvasWidthOffGrid`（「幅は128の倍数でなければなりません。」）／`canvasHeightOffGrid`（「高さは128の倍数でなければなりません。」）を出す。**1 行にまとめないこと**が仕様である —— 生成理由の note は解決済みの文言で重複を除くため、共通の 1 文にすると幅だけ直した段階でも行が残り、「次はどちらを動かすのか」が分からなくなる。スライダーを動かしながら行が 1 本ずつ消えるのを見て調整できることが、この分割の目的である。
4. ~~**4096 ピクセルを超える元動画は `sourceTooLarge` でブロック**する。パッドは `maxPad` で頭打ちになるので 4096 超のキャンバスは元動画自体が大きいときにしか起きないが、5120×2816 のような「4096 超かつ 128 の倍数」の素材は格子検査を素通りしてサーバーの 422 に至るため、専用の理由コードで塞いだ。~~（**2026-08-11 第2弾で撤回**: `sourceTooLarge` は廃止し、幅・高さ個別の `canvasWidthTooLarge` / `canvasHeightTooLarge` へ置き換えた。対辺連動の廃止でパッド由来の 4096 超も到達可能になったため、根拠の前提ごと変わっている。§5-C）
5. **素材を差し替えたらパッドは 0 に戻す**。ただし「判明している寸法が前回と変わったとき」だけである。同一ファイルの再添付やメディア情報取得の一時失敗では消さない（1 ピクセル刻みでは入力に手間がかかるため、消してよい場面を狭く限った）。
6. 値の自動スナップを持たせない方針（§4-2 の「採用しなかった案」）は**そのまま生きている**。撤回したのは「自動で足す下限」であって、「指定した値と違う値が出てくる UI にはしない」という原則ではない。
7. stage-1 の ±1 ピクセルの丸めは許容する（オーナー確認済み）。

### バックエンドは無改修

パッド 4 値に倍数の制約は元から無い（`api/models.py` は 0〜4096 の整数のみを見る）。1 ピクセル粒度・奇数パッドをそのまま処理できることは API・エンジン・本書 §5 の 3 番の 3 層で確認済みである。フロントエンドが守る不変条件は「キャンバスの幅・高さが 128 の倍数」「保持領域＝元動画の実寸」「保持領域は各辺 256 以上」「パッド合計が 0 より大きい」「キャンバス各辺 4096 以下」の 5 つになった。

## 5-C. パッド入力の役割分担リファイン（2026-08-11 オーナー決定・第2弾）

§5-B（1 ピクセル刻み化）は実装・デプロイのうえ実機ゲート 8 項目に合格したが、オーナーの実機テストで操作性の問題が 2 点挙がった。本節はその手当てであり、§5-B の現行仕様 2 と 4 を**撤回して置き換える**。

### 直した 2 点

1. **スライダーの可動域が広すぎた。** 上限が「4096 − 元動画の辺 − 対辺のパッド」だったため最大で約 2800 に達し、トラック幅およそ 220 ピクセルに対してマウス 1 ピクセルの移動が値 13 相当になっていた。**マウスでは決して指定できない値**が生まれるのは入力装置として破綻している。
2. **対辺連動が不要だった。** 片方のスライダーの値でもう一方の上限が動く仕組みは、「値を自動調整せず、メッセージで案内する」という本機能の設計思想そのものと矛盾していた。

### 現行仕様（§5-B の 2・4 を置き換える）

1. **スライダーは入力補助**。上限は定数 `PAD_SLIDER_MAX = 220` で、元動画の寸法にも対辺の値にも依存しない。`min=0`・`step=1` は据え置き。220 という値はパッド欄のグリッド列の最小幅（`EditScreen.css` の `.outpaint-pads` は `minmax(220px, 1fr)`）を根拠とする、「マウス 1 ピクセルが値 1 を超えない」実用範囲である。実トラックはつまみの分だけ短く、列は広い画面では伸びるので、厳密な 1 対 1 対応ではなく**選んだ作業範囲**である。
2. **数値入力ボックスが正確な値の入り口**。上限は定数 `MAX_PAD = 4096`（API の `pad_* le=4096` に対応）で固定。対辺連動は完全に廃止した。（2026-08-12追記: 対辺の**値**を揃えるオプトイン「センタリング」を §5-D で追加した。ここで廃止した「対辺が**上限**を動かす・常時働く」仕組みとは別物であり、上限の定数2本は不変のままである）
3. **220 を超える値を入れるとスライダーのつまみは右端に貼りつく。** `value > max` の range 入力を表示上 max へ丸める HTML 本来の挙動をそのまま使っており、state の値は変わらず、ボックスは実値を出し続ける。
4. **貼りつき中にスライダーを操作すると、値は 220 以下へ落ちる。これは仕様である**（ドラッグ、トラック上のクリック、矢印キー左、フォーカス中のホイール操作）。厳密には「つまみが今いる右端ちょうど」を狙ったクリックのように、スライダーの表示値が 220 のまま変わらない操作では値も動かない（変化が無いので `change` が起きない）。それ以外はどこを触っても落ちると考えてよい。「スライダーを操作した＝スライダーの範囲で指定し直す意思」とみなす。`max(220, 現在値)` のような動的上限は**入れない**（上限が値によって動く仕組みを追放したばかりなので、別の形で呼び戻さない）。
   - 既知の副作用: 貼りつき中はスクリーンリーダーが同じパッドについてスライダー「220」・数値ボックス「500」と**別々の値**を読み上げる。2 つの入力部品に別々の上限を持たせ、超過分をボックス側だけで表現するという承認済み仕様の内在的な帰結であり、対処はしない（読み上げを揃えるには、追放したばかりの動的上限か、値を丸める処理のどちらかが必要になる）。
5. **4096 の上限もメッセージで担保する**。`sourceTooLarge` を廃止し、拡張後キャンバスを測る `canvasWidthTooLarge`（「幅の上限は4096ピクセルです。」）／`canvasHeightTooLarge`（「高さの上限は4096ピクセルです。」）の 2 本へ置き換えた。これで 128 の格子と 4096 の上限が同じ方式に揃い、キャンバス側の制約はすべて理由コードが担う。
   - 拡張後キャンバスで測るので、**パッドを盛りすぎた場合**（対辺連動の廃止で新たに到達可能になった経路）と**元動画自体が 4096 超の場合**の両方を 1 つの機構で拾える。
   - ちょうど 4096 は合法（`>` で判定）。4096 は 128 の倍数でもあるため、境界で格子の行が道連れに出ることもない。
   - 4096 超かつ 128 非倍数のとき、同じ軸で TooLarge と OffGrid の 2 行が出るのは抑制しない。
   - 元動画自体が 4096 超のとき（例: 5120×2816）は `padsZero` と `canvasWidthTooLarge` が併存し、後者はパッドを動かしても消えず、原因（元動画が大きい）も述べない。**このままでよい**（オーナー決定: 例外ルールを増やさずシンプルを優先。キャンバス寸法の表示と合わせて読めば原因は読み取れる）。
6. 常設説明文（`gridNote`）への案内一文の追加は**しない**（オーナー決定: 画面の文字を増やさない。ボックスはスライダーの隣にあるので気づける）。
7. §5-B の他の項（0 起点・1 ピクセル刻み・スナップ禁止・幅と高さの個別メッセージ・素材差し替え時のリセット・stage-1 の ±1 ピクセル丸め許容）は**すべてそのまま有効**である。とくに `applyMediaInfo` の「既知サイズが変わったときだけ 0 に戻す」規則は無改修で維持した（対辺連動とは無関係の話であり、実機ゲート⑦で合格済みの挙動を動かす理由がない）。

### バックエンドは無改修

§5-B の「バックエンドは無改修」の記述は**そのまま真**である。パッド 0〜4096・キャンバスは 128 の倍数かつ 4096 以下・保持領域＝元動画の実寸・保持領域は各辺 256 以上、という契約は何も変わっていない。変わったのは、その契約をフロントエンドの**どの層で守るか**（入力部品の上限か、生成ブロックのメッセージか）だけである。

### 関連コード

- 定数と理由コード: `webui/src/modes/edit/outpaintGeometry.ts`（`PAD_SLIDER_MAX` / `MAX_PAD` / `clampPad` / `canvasWidthTooLarge`・`canvasHeightTooLarge`。`maxPad` 関数は削除）
- 画面: `webui/src/modes/edit/OutpaintingPanel.tsx`（`PadSlider` が 2 つの上限を持ち分ける。貼りつき挙動の説明もここ）
- 状態モデル: `webui/src/modes/edit/useOutpaintForm.ts`（`maxPads` の導出を削除。`setPad` は `clampPad` 1 本）

## 5-D. センタリング（2026-08-12 オーナー決定）

パッドのスライダー 4 本にはガイドが無く、「元動画を中心にして上下左右を同じだけ広げる」という最も素直な使い方が、毎回 4 つの数字を自分で合わせる作業になっていた。本節はそのための入力補助を 1 つ足す改訂であり、§5-B・§5-C の仕様は**何も撤回しない**。

### §5-C で廃止した「対辺連動」とは別物である

紛らわしいので先に線を引く。§5-C の 2 で廃止したのは、**片辺の値が対辺の「上限」を動かす**仕組み（`maxPad`）であった。あれには 3 つの性質があった —— 常時働く（切れない）、動くのは上限であって値ではない、そして「値を自動調整せず、メッセージで案内する」という本機能の設計思想と矛盾する。

本節が足すのは、そのどれとも重ならない。

1. **明示的なオプトイン**。チェックボックスで入にしたときだけ働き、既定は切。切のあいだの挙動は §5-C までと 1 ビットも変わらない。
2. **動くのは上限ではなく値**。`PAD_SLIDER_MAX = 220` と `MAX_PAD = 4096` の定数 2 本は不変で、入力部品の上限は元動画の寸法にも対辺の値にも依然として依存しない。
3. **思想と矛盾しない**。「指定した値と違う値が出てくる UI にはしない」が禁じているのは、利用者の意図と無関係に値が書き換わることである。センタリングは利用者が自分で入にした結果として対辺が動くのであり、入にした時点でそれが意図そのものである。

### 現行仕様

1. **位置はパッドのスライダー 4 本の「上」**、見出し「描き足す量」の直下。当初案は「下」だったが、常設説明文（`gridNote`）の直上に来て「128 の倍数」の話と地続きに読めてしまう。上に置けばその誤読が構造的に消え、「下のスライダー群の書き込まれ方を変えるスイッチ」という関係も自然に伝わる（オーナー提案）。
2. **既定は切**。ラベルは日本語「センタリング」／英語 "Keep centered"。
3. **入のあいだは上下・左右が連動する**。片辺を動かすと対辺に同じ値が入る。スライダーからでも数値入力ボックスからでもミラーする（どちらも同じ `setPad` を通るため）。
4. **切→入の瞬間に各軸を等分する**。合計 ÷ 2 の**切り捨て**を両辺へ入れる（左 10・右 20 なら 15/15、左 10・右 21 でも 15/15）。切り捨てなのでキャンバスが指定より大きくなることはない。奇数合計で 1 ピクセル消えるのは**許容**する。
5. **入→切では値をリセットしない**。揃えるのを手伝う機能であって、揃った値を取り消す機能ではない。
6. **片軸の合計が 1（上 1・下 0 など）は 0/0 になる**。四辺すべてが 0 になれば既存の `padsZero` が生成を止める。これも**許容**であり、特例は設けない（オーナー確認済み。例外ルールを増やさないという §5-C の判断と同じ線）。
7. **素材を差し替えてもチェック状態は維持する**。パッドが 0 に戻るのは §5-B の 5 のままだが、`ZERO_PADS` は対称なのでチェックとの不整合が生じない。
8. **生成リクエストには一切入らない**。チェック状態は純粋な UI の入力補助で、送られるのはミラーの結果であるパッド 4 値だけである。サーバーにも API にも対応するフィールドは無い（バックエンドは当然ながら無改修）。
9. 既知の帰結: **幅（または高さ）が奇数の元動画は、入のままでは 128 の格子に絶対に乗らない**。入のあいだ 1 軸の増分は必ず偶数なので、キャンバスの偶奇は元動画のそれから動かないためである。1265×720 のような素材では、幅だけは切にして片辺ずつ合わせることになる。ブロック理由（`canvasWidthOffGrid`）が出続けるので気づけるため、専用の案内は足さない。
10. 右クリックから Edit 系のルートへ入り直すと `remountTokens.edit` で画面ごと作り直され、チェックは既定の切に戻る（メインタブの切り替えでは維持される）。既存の再マウント規則そのままであり、ここに例外は設けない。
11. 既知の帰結: **入のあいだに数値ボックスを空にすると、対辺も 0 になる**。空欄は `Number("") === 0` として `setPad` に渡る既存挙動（§5-B）そのままで、センタリング固有の分岐は無い。ミラーは「打った値をそのまま対辺へ写す」だけなので、0 が渡ればミラー結果も 0 になるという自然な帰結であり、**許容**する。

### §5-C-6「画面の文字を増やさない」との線引き

§5-C の 6 でオーナーが退けたのは、常設説明文（`gridNote`）に**案内の一文を足す**ことであった。本節が足すのは**操作部**（チェックボックス 1 個）であり、説明文（hint）は付けない。読む文字は増やさず、押せるものが 1 つ増えるだけなので、あの決定の趣旨は維持されている。

### 関連コード

- 純関数コア: `webui/src/modes/edit/outpaintGeometry.ts`（`centerPads` —— 切→入の等分。冪等かつ入力非破壊。対辺ミラーは入力の操作規則なのでここには置かない）
- 状態モデル: `webui/src/modes/edit/useOutpaintForm.ts`（`centering` / `setCentering`。`setPad` は入のとき 1 回の updater で対辺 2 値を同時に書くので、非対称な中間状態は存在せず、`useEffect` による相互監視も要らない）

## 5-E. 高解像度での継ぎ目の余裕は小さい（観察の物差し・2026-09-03 追記）

**キャンバスを大きくするほど、継ぎ目の機械判定には余裕が無くなる。** 実 GPU ゲートの 8 腕のうち、最大幾何の腕（1920×1152 のキャンバスに左 384 画素だけパディングした構成）だけが、**境界勾配比が合格の上限 2.0 に近い**。境界勾配比とは「継ぎ目の位置での画素の変化の急さが、その周りと比べて何倍か」という指標で、線や段差が出ていれば大きくなる。他の腕には余裕があり、保持領域の一致度・緑残存・VRAM はいずれも合格の範囲にある。

**現時点で不具合ではない。** 2 倍に拡大した継ぎ目の画像を見ても稜線は見当たらず、判定線 2.0 そのものを動かす話でもない（上限 2.0 は画角拡張のゲートで一貫して使っている値である）。**本節を置く理由はただ 1 つで、より大きなキャンバスを許すときや、継ぎ目の見え方に指摘が出たときに、まずこの数値から見ればよいと分かるようにするためである。**

- **数値の正本**: バックエンド[`VERIFICATION_LOG.md`](../../../Docs/VERIFICATION_LOG.md) **§79.10(5)(6)(7)**（**本書には写さない**。脱緑ブレンドの前後で値が動いた経緯も同節にある）。腕ごとの一覧は `outputs/ltx25-outpaint-gate/summary.json` の `arms.O8.measurements.boundary_gradient_ratio_worst`。
- **観察の道具**: 判定器 `outputs/ltx25-outpaint-gate/analyze_w2.py` が出す `ratio.json` に、辺ごとの内訳が載る。
- **近い話題との線引き**: 上限 2.0 を**超えた**事例（オーナー目視用の街路素材）は別件として決着済みである——[`PENDING_TASKS_CLOSED.md`](../../../Docs/PENDING_TASKS_CLOSED.md) §3-123（目視では極端な不自然さが無く、建物のふちや石畳の線が継ぎ目に重なって機械判定を誤作動させたという見立て）。本節が扱うのは、判定を通しているゲートの腕そのものの数値である。
- **出自**: 台帳の観察項目として起票していたものを、オーナー裁定（2026-09-03）で本節へ移した——行動も完了条件も無い観察は、「次に何をすべきか」を読む台帳ではなく設計資料の側が持つ、という判断である。クローズ記録は[`PENDING_TASKS_CLOSED.md`](../../../Docs/PENDING_TASKS_CLOSED.md) §3-120。
