# タイムライン生成AI α版 要件定義（技術的な唯一の正）

この文書は、AviUtl2 プラグイン「Nz-Videomni」のタイムライン生成AI機能について、α版で実装する内容の技術的な拠り所（唯一の正）をまとめた開発者向け資料です。ここに書かれた技術的事実・制約・確認事項が、実装判断の基準になります。実機確認リスト（第6節）は本文書にのみ置き、他の資料には重複させません。

**改訂（2026/7/7）**：これまで「実機で確認する」としていた論点の大半を、事前調査（beta52 同梱ファイルの精査・SDK 更新履歴の Web 調査・実在する参考実装プラグインの解析）で高い蓋然性まで詰めました。詰めた結論と、そこから定めた実装方針を新設の第0節にまとめ、(3) と (6) にも織り込んでいます。実機がないと最終確認できない残件は、正直に「実機のみ」として第6節に分離してあります。

**注記（後日追記）**：本書は2026/7/7時点の要件です。実機対象はその後 **v2.0.54ポータブル**（`D:\For_Videos\AviUtl2\aviutl2_v2.0.54\`）へ移行しました（Cドライブ容量都合のポータブル固定運用）。本書中の「beta52」を前提とした可否判定ルール（第0節A・第3節・第6節）や実機確認リストは、その移行前に書かれたものであり、右クリック生成系SDK APIの実機再検証はv2.0.54では未実施です。調査内容（API追加日の裏取り等）自体は史料として保持します。

読み物としての概要・背景・オーナー向けの説明は、姉妹資料 `TIMELINE_FEATURE_CANDIDATES.md`（第2版）を参照してください。本文書は実装の拠り所に徹し、なぜそれが嬉しいかといった説明は最小限にとどめます。

生成の種類を表す言葉は、姉妹資料と同じく「略語＋短い解説」で表記します。

- txt2vid（Text-to-Video：テキストから動画を生成する）
- img2vid（Image-to-Video：画像から動画を生成する）
- vid2vid（Video-to-Video：動画の続きを生成する）
- Aud2Vid（Audio-to-Video：音声から動画を生成する）
- IC-LoRA（動きや輪郭を参照して生成する）

## (0) 調査で裏付けた実装方針サマリ

実機がない状態で、beta52 同梱ファイル・SDK 更新履歴・実在する参考実装プラグインを調べ、実機確認の論点の大半を高い蓋然性で結論づけました。以降の各節はこの結論を前提に書かれています。要点は次の4つです。

### A. beta52 での API 利用可否を判定するルール（今後も使う基準）

- **beta52 のリリース日は 2026/6/28**（同梱の `aviutl2.txt` と公式サイトで確認）。
- **判定ルール**：AviUtl2 作者は beta 公開と同日にプラグイン SDK も更新しており、SDK の CHANGELOG に記された各 API の「追加日」は、その API が本体で有効になった beta の公開日と一致します（調べた4件が4件とも beta 公開日と厳密一致）。**したがって、SDK コメントの追加日が 2026/6/28 以前の API は、beta52 で使えると判断してよい**、というルールを本文書の基準として採用します。今後ほかの API の可否も、このルールで判断します。
- 当てはめ結果（右クリックメニュー系）：

| API | 追加日（相当 beta） | beta52 での可否 |
|---|---|---|
| `register_object_menu` / `register_layer_menu` | 2025/11/8（beta19 相当・33世代前） | 蓋然性：高 |
| `register_object_item_menu` | 2026/5/4（beta44 相当） | 蓋然性：高 |
| `register_event_listener` | 2026/6/14（beta50 相当・2世代前） | 蓋然性：中〜高（最も新しく確度はやや控えめ） |

- ただしこれは「SDK 更新履歴と beta 公開日が一致する」という状況証拠に基づく推論であり、beta52 実機で実際に呼び出した動作実績（コミュニティ実例）は見つかっていません。最終的な動作確認は帰宅後の実機で行う前提です。
- 情報源：公式 <https://spring-fragrance.mints.ne.jp/aviutl/>、SDK 非公式ミラー CHANGELOG <https://github.com/aviutl2/aviutl2_sdk_mirror>、更新履歴まとめ <https://docs.aviutl2.jp/changelog>。

### B. エイリアス書式と effect名／item名（ほぼ判明）

- エイリアスは INI 風の UTF-8 テキスト。`[Object]` の下に `[Object.0]`・`[Object.1]`… と連番セクションが並び、各セクション先頭が `effect.name=<エフェクト名>`、以降が `項目名=値` の形です（SDK 公式サンプル `WindowClient.cpp` のリテラルで確認）。旧 AviUtl1系の `_name=` から `effect.name=` に変わった点が非互換ポイントです。
- 判明した effect名／item名（beta52 同梱 `effect.conf` の OldScript 互換表＋実在プラグインのソースで確認）：

| オブジェクト | effect名 | 主な item名 |
|---|---|---|
| 動画ファイル | `動画ファイル` | ファイルパスは `ファイル`（英語UIは `File`）。再生は別セクション `映像再生`（`透明度`・`音量`）、`音声付き` 項目あり |
| 画像ファイル | `画像ファイル` | `ファイル` |
| 音声ファイル | `音声ファイル` | `ファイル` |
| 図形 | `図形` | `図形の種類`・`色`・`ライン幅` 等（種類は円/四角形/三角形/星/ハート/背景/カスタムSVG） |
| テキスト | `テキスト`＋`標準描画`＋`縁取り` | ― |

> **訂正注記（2026-09-01追記）**：上表の `動画ファイル` の行にある「**`音声付き` 項目あり**」は**誤りです**。2026-09-01 の調査で、`音声付き` という項目名は**現在の AviUtl2 本体には存在しない**ことを確認しました——本体の実行時抽出によるエフェクト項目表にも、UI 文字列テーブル（beta2〜beta27）にも、1度も出現しません。この名前は、起草時に参照した beta52 同梱 `effect.conf` の**旧 AviUtl1 系 OldScript 互換表**から拾ったものです。
>
> **`動画ファイル` エフェクトの実際の項目は `ファイル`・`再生位置`・`再生速度`・`ループ再生`・`トラック` で、音声の制御は出力側の `映像再生` にある `音量`・`左右` が担います**（`再生位置` の実測結果は [`V2V_RIBBON_TRIM_WORKORDER.md`](V2V_RIBBON_TRIM_WORKORDER.md) §4 が正本）。出典：本体実行時抽出のエフェクト項目表 <https://github.com/aviutl2/aviutl2_community_translation>（`extract/effects.json`）、UI 対訳表 <https://github.com/nagotown/aviutl2-EN>。**上表そのものは 2026/7/7 時点の調査の史料として原文のまま残します。**

- 含意：A5「差し替え」のインプレース書換えは `set_object_item_value(obj, L"動画ファイル", L"ファイル", パス)` で可能な見込みです（item名 `ファイル` はパーサ探索キーからの高確度な推測。実機ダンプで最終確認）。仮オブジェクトのテキスト生成に必要な書式はこれで揃いました。

### C. 参考実装プラグイン（設計の裏付け・最重要）

- **`clean262/sam3_bb_gb_generator`**（MIT ライセンス、2026/4 公開、CGWORLD 掲載）が、本設計とほぼ同型の実在プラグインです。外部 AI 処理（Python 側）の結果を `create_object_from_alias` でタイムラインに挿入し、ジョブファイルをポーリングして `call_edit_section` のコールバック内で反映しています。URL: <https://github.com/clean262/sam3_bb_gb_generator>（`cpp/sam3_aux2.cpp`）。
- ここから裏付けられた実装パターン（本文書では該当箇所に「実在プラグインで実証済み」と明記します）：
  - **OBJECT_HANDLE はキャッシュせず、エイリアス文字列の完全一致＋フレーム位置で毎回オブジェクトを再検索する**（同プラグインの `FindObjectCoveringFrameByExactAlias`）。これは本設計の「ジョブID で仮オブジェクトを再発見する」方式そのもので、実証済みの安全パターンと位置づけます。→ 第5節「完了時」の再発見を、ジョブID をエイリアス内のテキスト/名前に埋め込み、完全一致で探す方式に寄せます。
  - **`find_object` は「指定フレーム以降で最初の1個」しか返さない**ため、範囲検索・空きレイヤー探索・重複防止は呼び出し側で自前ロジックを組みます（同プラグインが `IsLayerRangeFree` / `FindObjectCoveringFrame` を自作）。
  - `create_object_from_alias` / `get_object_alias` / `get_object_layer_frame` / `set_object_item_value` / `set_object_name` / `set`・`get_focus_object` / `call_edit_section` / `set_cursor_layer_frame` の実利用が確認できました＝これらは実在プラグインで動く実績があります。

### D. 依然として実機でしか詰められない残件（正直に「未解決」）

- **対象オブジェクトだけの音の抽出**（`rendering_scene_audio` ＋ `set_layer_enable`）：コミュニティ実例ゼロ。論理的には導けるが未実証。実装は慎重に、帰宅後の実機検証を必須とします。
- **アンドゥ挙動**：DeepWiki は「`call_edit_section` 内の操作はアトミックな1トランザクション」と述べるが、ヘッダには記載なし＝未確認。実機検証項目に残します。ただし本設計の仮オブジェクトは「消えても正しい場所に出る」ため、アンドゥで多少ずれても実害は小さい見込みです。
- **図形オブジェクトの正確なエイリアス実書式**：同梱プリセットが空で未取得。ただし仮オブジェクトはテキストで作る方針なので図形書式は必須ではありません（テキストのエイリアス書式は確認済み）。

## (1) α版スコープと優先順位

### 実装する機能

| 記号 | 機能 |
|---|---|
| A1 | 続き生成（vid2vid＋join） |
| A2 | img2vid |
| A3 | IC-LoRA |
| A4 | 再生成＋履歴 |
| A5 | 差し替え |
| A6 | 生成画面へ送る |
| B1 | 位置指定 txt2vid |
| B2 | すき間埋め（img2vid で前後フレーム条件） |
| B3 | 現在フレームから img2vid |

加えて、次の三つをα版の正式スコープに含めます。

- **Aud2Vid**：音声オブジェクト選択／動画から音声抽出の2入口。
- **範囲選択切り抜き（先行実装）**：タイムラインの見えている状態を短い mp4／音声に書き出して入力にする土台。
- **仮オブジェクト方式の生成待ち**：生成尺と同じ長さのテキストオブジェクトを予約位置に置き、完了時に本物へ置換する。（※ここでの「予約」はタイムライン上の位置予約という別概念で、DEVLOG §13.3で廃止されたWebUI側の生成キュー予約機構〔`useGenerationQueue`〕とは無関係です）

### 優先度

土台を先に、を明示します。範囲選択切り抜きは複数機能（A1・A3・Aud2Vid・B2 など）の前提になるため、最初に固めます。

```
範囲選択切り抜き（土台）
  → A1
  → A2・B3
  → Aud2Vid
  → A4・A5
  → B1・B2
  → A3・A6
```

この順序はオーナー承認の優先度を尊重したものです。範囲切り抜きが複数機能の前提である点を踏まえ、土台を先行させています。

### 優先順位の階層

将来の拡張は次の階層とします。**「将来の改修項目」＞「将来の研究課題」**。

- 将来の改修項目（優先度：高）：仮オブジェクトのキャンセル、失敗仮オブジェクトの自動片付け、孤児仮オブジェクトの自動掃除。
- 将来の研究課題（優先度：低）：部分再生成（Retake）、領域塗り替え（Inpaint）。

**追記（2026-07-27）**: この5項目の追跡は[`PENDING_TASKS.md`](PENDING_TASKS.md)へ一本化しました。**以後の管理は同書で行います**（改修項目の3件＝[`PENDING_TASKS_CLOSED.md`](PENDING_TASKS_CLOSED.md) §3-27・§3-28・§3-29〔2026-09-02にオーナー裁定「実用上不要」でクローズ済み〕、Retake・Inpaint＝[`PENDING_TASKS.md`](PENDING_TASKS.md) §4-12）。本書は設計記録として残します。

## (2) バックエンド制約（凍結・変更不可）

以下はすべて別途の調査で確定した事実です。バックエンド（β版）は凍結済みで変更しません。フロント側はこの制約を前提に設計します。

### Aud2Vid（`/generate/chain` の `source_audio`）

- トリム指定パラメータは**無い**（v1仕様）。音声はタイムライン尺に合わせて切り詰められるのみ。
- 不足時のみ `422 SOURCE_AUDIO_TOO_SHORT` で拒否。
- 「長すぎ」は黙って切り詰め（**警告なし**）。
- 音声ストリーム無しの場合も同じ `SOURCE_AUDIO_TOO_SHORT` で弾かれる。
- `source_audio` は clips ちょうど1本のみ。`source_video` と**排他**。

含意：フロント側で「音声が短すぎないこと」「音声ストリームが存在すること」を切り抜き段階で保証する。長さの上振れは切り詰めで吸収されるが、下振れは 422 になるため事前チェックが必須。

### `/upload/audio`

- 最大 50MB。
- 対応拡張子：`.wav` / `.mp3` / `.m4a` / `.aac` / `.flac` / `.ogg`。
- コーデック妥当性の検査は、保存後の ffprobe preflight まで先送り（アップロード時点では通る）。

### IC-LoRA（`reference_video_id`）

- **`reference_video_id`（IC-LoRA 参照動画、M6）と `loras`（スタイル LoRA、M5）は別機能だがいずれも `/generate` 専用**。`/generate/chain` には存在しない（続き生成に IC-LoRA を混ぜられない）。※これは 2026/7/7 執筆時点の制約です。**2026-07-11 に `/generate/chain` へ解禁済み**（`reference_video_id`／`conditioning_attention_strength`／`reference_video_strength`）。詳細は `Docs/API_REFERENCE.md` §12.4、実装は `webui/src/modes/chain/useChainForm.ts` の `subMode==="clips"` 時合流を参照。以下の「含意」および第7節7-3-Aの不整合記録は、解禁前の制約を前提に書かれた記述であることに留意してください。
  - **追補（2026-07-16のUIリデザインで`subMode`は廃止）**: `useChainForm.ts`の`subMode`（`"clips"`／`"v2v"`の切り替え）はサブタブ廃止に伴い削除され、現在はソース動画の有無で自動判別する方式になっている。参照動画（IC-LoRA）を添付するUIはChain画面から削除され、現在はCreate画面のみに存在する。ここで解禁された「`/generate/chain`への`reference_video_id`等の送信能力」自体はバックエンド契約として維持されており、`webui/src/modes/chain/chainUtils.ts`の`buildChainRequest`に送信ロジックのみが残存している（Chain側UIから参照動画を設定する手段は無い）。
- IC-LoRA 使用時の生成 width/height は **128 の倍数が必須**（違反は `422 REFERENCE_RESOLUTION_INVALID`）。一般モードの÷64より制約が厳しい。
- **長さ・fps・解像度の preflight が無い**。
- エンジンは参照動画を先頭から `num_frames` だけ機械的にデコードして使う。
  - 長い → 先頭のみ使い、残りは無視。
  - 短い → エラーにならず、想定より短いテンソルで**下流クラッシュの恐れ**（未検証・要実機確認）。
- fps リサンプルはされない。
- トリム指定パラメータは無い。`reference_video_strength` 等は強度調整であり、長さとは無関係。

含意：フロント側で「参照動画の長さ ≒ 生成予定 `num_frames`」を保証してから渡すのが安全。fps も生成側に合わせて切り抜く。ここが範囲切り抜き土台を先行実装する最大の技術的理由。

### 入力素材の解像度（3モード共通）

- i2v（`conditioning_images`）・v2v（`source_video`）・IC-LoRA（`reference_video`）とも、入力素材の元解像度は問われず、生成 width/height へ **`resize_and_center_crop`（覆うようにスケール＋中央クロップ）で強制変換**される。レターボックス／パディングではない。
- 入力≠出力でも**エラーにならず黙って合わせる**。ただしアスペクト比が違うと、端が中央クロップで切れる。
- 含意：α「自動リサイズしない・入力前提」は破綻しない（mismatch でもクラッシュしない）。ただし端クロップを避けるため、**出力解像度は入力の解像度・アスペクト比に合わせて決める**のが安全（設計方針は第7節 7-5）。

### フレーム数上限とVRAM（事前予測が弱い）

- `num_frames` の形状上限（481・8n+1）は静的に決まるが、**解像度に応じた実効的な最大フレーム数を機械取得する手段は無い**。`limits.spill_free_frames` は解像度ごとの静的値のみで、補間式が無い。
  > **【2026-08-31 追記】括弧内に書いていた3組の数値（1280×768→257／1920×1088→153／2560×1472→81）は当時の値なので削除した。** 現在の値はバックエンド`config.yaml`の`limits.spill_free_frames`（説明の正本は[`COMFORT_LIMIT_TABLE.md`](../../../Docs/COMFORT_LIMIT_TABLE.md) §付記）を参照すること。**なお「補間式が無い」という本文の指摘は、その後`limits.comfort_budgets`（エンジン系統ごとの予算の表からフレーム数を逆算する仕組み）で部分的に解消している**——ただし表に一致する行が無い構成では、いまも`spill_free_frames`の静的値へ落ちる（同 §1.1）。
- 超過しても即 OOM ではなく 2〜4倍の低速化にとどまる。VRAM 枯渇時のみ**実行中に** `503 GPU_OOM`（detail は torch の生メッセージ）を返す。
- 含意：任意解像度の最大フレーム数は事前確定できない。事前チェックは既知3解像度の警告どまりで、それ以外は実行時エラー文字列の提示に頼る（設計方針は第7節 7-5）。

### 生成尺の算出

単発 `/generate`：

- `num_frames` は 9〜481、**8n+1 必須**。
- `frame_rate` 指定。尺 = `num_frames / frame_rate`。
- 上限 20 秒（481f）@24fps。

latent 変換：

- `v_latent_frames(P) = (P - 1) // 8 + 1`
- 逆変換：`px = (N - 1) * 8 + 1`

chain：

- `f_total = Σ v_latent(clip) - (n - 1) * overlap`
- `total_px = px_from_v_latent(f_total)`
- `overlap_frames` を大きくすると最終尺は縮む。
- overlap 実効上限 = 各 clip の latent 数**未満**。
- 総尺上限 = `8 * 481 = 3848` px フレーム。
- V2V ありのときは配信尺 = `total_px - source_context_px`（混同注意）。

join（続き生成の結合）：

- 元動画＋新規を ffmpeg でオーディオクロスフェード結合。
- `handle_crossfade_ms` 既定 300ms（範囲 0〜2000ms）。

換算：

- プロジェクト fps と生成 fps（既定 24）の換算を仕様に含める必要がある。仮オブジェクトの長さ・切り抜き尺・挿入位置はすべてプロジェクト fps 基準で扱い、生成尺の算出は生成 fps 基準で行うため、両者の換算を一箇所に集約する。

## (3) AviUtl2 SDK 能力（`plugin2.h`）

対象：beta52 本体。ただし参照している SDK ヘッダは beta53a 世代。この世代差が実機確認を要する要因だったが、第0節Aの判定ルール（SDK 追加日 ≦ 2026/6/28 なら beta52 で使える）により、各 API の可否は事前に高い蓋然性で判定できるようになった。以下、各項に判明した事実を織り込む。

### 右クリックメニュー

- **`register_object_menu` / `register_layer_menu`（ともに 2025/11/8 追加）が A系統／B系統の本命 API。**
- `register_object_item_menu`（2026/5/4、設定項目単位）とは**別物**。混同しないこと。
- **beta52 で使える蓋然性：高**（第0節Aの判定ルールによる。追加日 2025/11/8 は beta52 の約7か月・33世代前で、追加日 ≦ 2026/6/28 を満たす）。`register_object_item_menu`（2026/5/4）も同様に蓋然性：高。
- ⚠️ `SDK_REFERENCE.md` の本体整合表に、この2つ（`register_object_menu` / `register_layer_menu`）が漏れている。整合表の漏れは残るため、最終的な呼び出し実績は帰宅後の実機で確認する（第6節）。

### 選択・列挙

- `get_selected_object(_num)` は選択中のみ取得。
- 全件列挙 API は**無い**。
- `find_object(layer, frame)` で「指定フレーム以降の**最初の1個**」を取れる。範囲検索・空きレイヤー探索・重複防止は呼び出し側で自前ロジックを組む必要がある。→ **参考プラグイン `sam3_bb_gb_generator` が `IsLayerRangeFree` / `FindObjectCoveringFrame` を自作して同じ問題を解いており、実証済みのパターン**（第0節C）。レイヤーごとにフレームを進めて走査すれば、全件スキャンはブルートフォースで可能。
- 名前 → ハンドルの逆引き API は無い。
- `OBJECT_HANDLE` の寿命に関するコメントはヘッダに無い。→ **参考プラグインは OBJECT_HANDLE をキャッシュせず、エイリアス文字列の完全一致＋フレーム位置で毎回オブジェクトを再検索する方式（`FindObjectCoveringFrameByExactAlias`）を採っており、これが実証済みの安全策**。本設計もハンドル保持に依存せず、この再検索方式を採用する（第5節）。

### 選択範囲

- `EDIT_INFO.select_range_start` / `select_range_end` はフレーム範囲のみ（レイヤー情報は含まない）。
- 未選択時は `-1`。

含意：範囲選択切り抜きの「明示範囲」はフレーム範囲としてのみ取得できる。対象レイヤー／オブジェクトは選択オブジェクト側から別途特定する。

### 図形／テキスト生成

- `create_object_from_alias` でメディアなしオブジェクト生成が可能。→ **参考プラグイン `sam3_bb_gb_generator` が実利用しており動作実績あり**（第0節C）。
- **エイリアスは INI 風の UTF-8 テキスト**。`[Object]` 直下に `[Object.0]`・`[Object.1]`… と連番セクションが並び、各セクション先頭が `effect.name=<エフェクト名>`、以降が `項目名=値`（SDK 公式サンプル `WindowClient.cpp` のリテラルで確認。第0節B）。旧 AviUtl1系の `_name=` からの変更が非互換ポイント。
- サンプル `WindowClient.cpp` にテキストオブジェクトの実例あり。テキストの effect名は `テキスト`（＋`標準描画`＋`縁取り`）。→ **仮オブジェクトはテキストで確実に作れる**。
- 図形の effect名は `図形`（項目 `図形の種類`・`色`・`ライン幅` 等）と判明したが、正確なエイリアス実書式は同梱プリセットが空で未取得（要実機ダンプ）。ただし仮オブジェクトはテキストで作る方針のため、図形書式は必須ではない。
- `length` は作成時のみ指定。**後から長さを変える／ロックする API は無い**（レイヤー単位ロックはあるが、オブジェクト単位は無い）。

含意：仮オブジェクトの「長さ固定」は不可能。長さ変更不可は諦め、「消えても正しい場所に出る」設計で担保する（第5節）。

### 置き換え

- 確実な方式は `delete_object` ＋ `create_object_from_media_file`。
- `set_object_item_value` でファイルパス書換えは形式上可能。動画ファイルオブジェクトの effect名は `動画ファイル`、ファイルパスの item名は `ファイル`（英語UIは `File`）と判明（第0節B）。→ **インプレース書換えは `set_object_item_value(obj, L"動画ファイル", L"ファイル", パス)` で可能な見込み**。item名 `ファイル` はパーサ探索キーからの高確度な推測のため、実機ダンプで最終確認する。`set_object_item_value` 自体は参考プラグインで実利用が確認済み（第0節C）。

含意：A5 差し替えは、まず確実な delete＋create で実装。インプレース書換えは effect/item 名がほぼ判明したため、実機で item名 `ファイル` を最終確認できてから任意最適化として検討する。

### 音声取得

- `rendering_scene_audio`：指定フレームの PCM float32 を L/R 別に返す非同期 API（`rendering_scene_video` と対）。
- ただし返るのは**シーン全体のミックス音**。
- 特定オブジェクトだけの音は、他レイヤーを `set_layer_enable` 等で一時無効化してレンダリングする間接手段が要る。
- オブジェクト単位の音声取得 API は無い。

含意：Aud2Vid の抽出方式2通り（ミックス／対象のみ）は、この API 特性がそのまま根拠。「対象のみ」は他レイヤー一時無効化 → レンダリング → 復元、の手順で実装。

## (4) 切り出し（レンダリング → ファイル化）の実装方針＝エンコーダ決定

### 調査結論：本体のエンコード機能は借りられない

- `HOST_APP_TABLE` / `EDIT_HANDLE` に、出力・エクスポートを起動する API は無い。
- `register_export_menu` は自前コールバックを呼ぶだけ。
- `output2.h` の出力プラグインは、本体からフレーム／PCM を pull して自前エンコードする設計。同梱サンプル `AviSaver.cpp` も無圧縮 AVI 止まり。
- 本体標準の mp4/H.264（auo2）の有無は要実機確認だが、いずれにせよプログラムから無人起動する API が無いため、自前実装は不可避。

### 採用方針：Windows 標準の Media Foundation Sink Writer

**`IMFSinkWriter` ＋ OS 内蔵 H.264 エンコーダ MFT** を採用します。`rendering_scene_video` / `rendering_scene_audio` で選択範囲分のフレーム（`PIXEL_RGBA`）と PCM を集めて mp4 化します。

追加コストは小さい：

- 新規ヘッダ取得は不要（Windows SDK 標準の `mfapi` / `mfidl` / `mfreadwrite` / `mferror`）。
- リンクに `mfplat.lib` / `mfreadwrite.lib` / `mfuuid.lib` の3つを追加。
- `MFStartup` / `MFShutdown` と `CoInitializeEx`（`ole32` は既存リンク）を足すだけ。
- `CMakeLists.txt` の変更は数行規模。
- `PIXEL_RGBA` は MF の RGB32/ARGB32 入力に低コストで乗る。

### ffmpeg 同梱は不採用

配布・ライセンス・サイズの都合で不採用。H.264/mp4 程度なら Media Foundation で足ります。

### 既存資産の流用

- 既存の `captureFrame`（`native/src/bridge.cpp`）が `rendering_scene_video` を次の設計で実装済み：
  - ワーカーからタスク投入 → 専用スレッドのコールバックで即コピー → condvar で受け渡し（10秒タイムアウト＋abandoned 安全策）→ WIC で PNG 化。
- **この設計を `rendering_scene_audio` と映像フレーム列収集にそのまま流用できる。**
- 現状、`rendering_scene_audio` の呼び出しと、PCM → WAV/mp4 エンコーダは未実装。ここが新規実装ポイント。

## (5) 生成待ち（仮オブジェクト）ライフサイクルの技術仕様

**注記（後日追記・2026-07-19）**：本節の仮オブジェクト・ライフサイクル仕様は起草時点の設計です。第1段階の実装では、状況表示を**4段階テキスト**（⏳生成予約〔未Generate〕→⏳生成中→完了時に**手動🎞置換**／❌失敗）に、予約を**予約席1件の追跡**に、完了時反映を**手動🎞挿入による位置連動置換**（新設RPC `insertMediaForJob`）に具体化しました。付け替えは新設RPC `updateProvisionalReservation` が1編集セクション（アンドゥ1件）で担います。現行の唯一の正は [`RIGHTCLICK_REDESIGN_SPEC.md`](RIGHTCLICK_REDESIGN_SPEC.md) §5（第8版）を参照してください。

### 投入時

1. 生成尺を第2節の式で事前算出する（プロジェクト fps ⇄ 生成 fps 換算に注意）。
2. その尺のテキストオブジェクトを `create_object_from_alias` で予約位置に作成する。
3. オブジェクトにジョブID を持たせる（名前 or テキスト内容に埋め込み）。表示は `⏳生成中：（指示文の先頭）…`。

### 完了時

1. ジョブID でレイヤー走査（`find_object` ベースのスキャン）して仮オブジェクトを探す。**OBJECT_HANDLE はキャッシュせず、ジョブID を埋め込んだエイリアス文字列の完全一致＋フレーム位置で毎回再検索する**（参考プラグイン `sam3_bb_gb_generator` の `FindObjectCoveringFrameByExactAlias` と同方式。実証済みの安全パターン。第0節C）。ジョブID は仮オブジェクトのテキスト内容／名前に埋め込んでおく。
2. 見つかれば `delete_object` ＋ `create_object_from_media_file` で置換。
3. 見つからなければ、予約時に控えた layer/frame へ挿入。→ 仮オブジェクトが動かされた・消されても結果は正しい場所に出る。

### 失敗時

- 仮オブジェクトは**残す**。テキストを `❌失敗：理由` に更新する（例：`いま別の生成中です` / `音声が短すぎます`）。
- 自動削除は**α版スコープ外**（将来の改修項目）。

### 孤児（セッションまたぎ）

- プロジェクト読み込みハンドラで、宙に浮いた仮オブジェクトを検出する。
- 「再生成しますか？」と提案する。
- 自動掃除は**スコープ外**（将来の改修項目）。

### スレッド規約

- 右クリックのコールバック内では**選択情報の取得だけ**行い、即 return。
- 重い処理（HTTP・レンダリング・エンコード）は**別スレッド**へ。
- 編集操作（作成・削除・置換）は `call_edit_section` の更新ロック下で行う。

### 7-5. 入力解像度の扱い（α版方針とβ版送り）

右クリック生成で「選択した入力素材の解像度をどう生成パラメータへ反映するか」の方針です。次の担当が最初に迷う論点なので、α版の確定方針とβ版送りの線引きを明示します。

#### α版方針（確定）

入力の**自動リサイズ**（VRAM／モデル最適解像度への自動調整。例：1920×1080 を 768p へレターボックス変換）は、それ単体でセッション一つ分の複雑さがあるため**β版送り**とします。α版は「ユーザーが適切なサイズで入力する前提」で配線し、次の2点だけを土台として入れます。

1. **出力解像度を入力に合わせる**：右クリック生成では、選択した入力素材の解像度・アスペクト比から生成 width/height を決め、**÷64（IC-LoRA 使用時は÷128）に丸める**。理由は、合わせないとバックエンドの中央クロップ（`resize_and_center_crop`）で端が切れるためです（第2節「入力素材の解像度」）。既存の「AviUtl2からサイズ取得」ボタン（`getEditInfo` の width/height を反映するロジック。7-2）を、**選択オブジェクトに向ける形で流用**できます。
2. **制約エラーを明示**：形状系の制約（÷64／÷128／`crop_output` 超過／8n+1）は、受理前に `422` の明確なコードが付くため、**事前に人間語でUIに提示**します。一方フレーム過多・VRAM 由来のエラーは事前予測が弱く（第2節「フレーム数上限とVRAM」）、**既知3解像度の事前警告＋実行時 `GPU_OOM`／`GENERATION_FAILED` の文字列提示にとどまる**旨を、正直にUIへ書きます（「解像度が原因」等の構造化した因果はバックエンドから得られません）。

#### なぜα版で見送れるか（安全性の根拠）

バックエンドは3モード（i2v／v2v／IC-LoRA）とも**入力解像度を問わず生成 width/height へ強制リサイズし、入力≠出力でもクラッシュしません**（第2節）。したがって「入力前提」で配線しても実害は**端の中央クロップ程度**で、α「自動リサイズしない」は安全に成立します。自動リサイズが無いこと自体はバグではなく、意図した割り切りです。

#### β版でやること

**最適解像度の算出＋レターボックス＋出力の切り戻し**を行います。バックエンドには未使用フック `resize_and_reflect_pad`／`REFLECT_PAD`／`align_resolution` が定義済みで（将来のレターボックス実装の予約と見られる。第2節の後処理 `crop_output` は最終 mp4 の中央クロップで入力解像度とは無関係なので混同しないこと）、これがβ版レターボックスの受け皿になり得ます。

土台方針：α版で**解像度決定を一箇所の seam（接ぎ目）にまとめておけば、β版はそこへ差し込むだけ**で済みます。上記1（出力解像度の決定）と2（制約丸め・エラー提示）を、7-3-B の解像度決定と同じ一箇所に集約しておくことを、次セッションの設計上の指針とします。

**実装状況（本セッションで対応済み）**：上記の指針どおり、解像度決定は `deriveGenerationParams`（`webui/src/timeline/deriveGenerationParams.ts`）という一つの seam に一元化して実装しました（7-3-B の実装状況注記と同一箇所）。出力解像度の決定（選択素材の実解像度優先、無ければプロジェクト既定）と、制約丸め（÷64／IC-LoRA時は÷128、上限は128の倍数へ切り下げ）・調整理由の `notes` 提示を、この一箇所にまとめてあります。β版のレターボックス実装は、このseamへの差し込みで対応できる見込みです。詳細は [DEVLOG.md](DEVLOG.md) §7.2 を参照してください。
