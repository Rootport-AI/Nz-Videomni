## 0. このデザインで作るもの（一言で）

**パソコン1台（家庭用のグラフィックボード搭載機）の中だけで動く「AIによる動画生成ツール」の操作画面**をデザインしてください。生成の中身（AIの計算）は別のプログラム（バックエンド）が担当します。あなたにデザインしてほしいのは、そのバックエンドに「こういう動画を作って」と頼み、出来上がった動画を受け取って、動画編集ソフト **AviUtl2** のタイムラインに渡すための **フロントエンド（操作画面）** です。

- **役割分担**: 動画を生成するのはバックエンド。動画の切り貼り・タイムライン編集は AviUtl2 本体。あなたがデザインする拡張機能は、その間に立つ **「生成を頼んで、結果を受け取って渡すだけの薄い仲介役」** です。動画のエンコードや編集機能を自前で持つ必要はありません。
- **ゴール**: AviUtl2 で動画を編集している人が、編集の流れを止めずに「AIで素材の動画クリップを作る」ことができる操作画面。

## 1. 用語集（この文書で使う言葉）

| 用語 | 意味 |
|---|---|
| **バックエンド** | 動画を実際に生成する裏方プログラム。パソコン内で別プロセスとして動く。操作画面からは通信（HTTP）で命令を送る。 |
| **T2V（文章→動画）** | 文章（プロンプト）だけを入力して動画を生成すること。 |
| **I2V（画像→動画）** | 静止画を起点にして動画を生成すること（例: 1枚目の絵を指定してそこから動かす）。 |
| **プロンプト** | 「どんな映像がほしいか」を書いた文章による指示。英語でも日本語でも書ける。 |
| **シード** | 生成の乱数の種。同じ設定＋同じシードなら毎回同じ動画になる。数字を変えると別パターンが出る。「-1」でランダム。 |
| **クリップ** | 生成される1本の短い動画。これを何本もつないで長いシーンにする。 |
| **フレーム** | 動画のコマ。1秒あたり24コマ（24fps）が既定。 |
| **LoRA（ローラ）** | AIに画風やキャラクターを追加で覚えさせた小さな追加ファイル。適用すると絵柄が変わる。 |
| **制御LoRA** | 別の動画の「輪郭線」や「人の骨格（ポーズ）」を手本にして、動きだけをまねさせる仕組み。手本になる参照動画が必要。 |
| **ジョブ** | 1回の生成依頼。時間がかかるので、依頼するとすぐ受付番号（ジョブID）が返り、裏で処理が進む。 |

## 2. ターゲットユーザー像

- **AviUtl2 のユーザー**。日本の趣味〜セミプロの動画編集者。ニコニコ動画・YouTube 文化圏。
- **無料・軽量・キーボード操作を好む** 層。重厚な有料ソフトより、身軽で自分好みにいじれるツールを選ぶ人たち。
- 動画編集の作業中に、AI生成を **「素材づくりの一手段」** として使う。目的は「編集する素材（短いクリップ）を手早く得る」ことであって、AIそのものをいじり倒すことではない。専門用語より、編集者の言葉（「クリップ」「尺」「つなぐ」など）で語られるほうが馴染む。
- **待ち時間に慣れていない前提で設計する**。動画生成は数分かかる（後述）。編集のテンポを崩さない見せ方が重要。

## 3. できること一覧（＝デザインすべき機能）

現在バックエンドが提供している機能です。AviUtl2 ユーザーの言葉で並べます。**これらが画面に必要な機能の全体像**です（画面の並べ方・まとめ方は自由）。

### 3-1. 文章から動画を作る（T2V）
- プロンプト（文章）を書いて生成する。
- **サイズ**（幅×高さ）、**尺**（コマ数／秒数）、**シード**を指定できる。
- 出来上がりは1本の短い動画クリップ（音声つき。発話・効果音・音楽はプロンプト次第のベストエフォート）。

### 3-2. 画像を起点に動かす（I2V／キーフレーム指定）
- 静止画を「この位置のコマはこの絵」と指定して、そこから動く動画を生成する。
- **最大10枚**まで画像を置ける（例: 先頭の絵と終わりの絵を指定して、その間をAIが補間する）。各画像に「どのくらい絵に忠実にするか（強さ）」を持てる。

### 3-3. クリップ連結で長いシーンを作る
- 短いクリップを何本もつなげて長尺（長いシーン）にする。**前のクリップの終わり＝次のクリップの始まり** が自然につながるように生成される（つなぎ目のブレンド幅を調整可能）。
- **クリップごとに別々のプロンプト** を書ける（全体共通のプロンプト＋クリップ個別の上書き、という考え方）。
- 現状は最大8本のクリップ枠。
  - **追補（2026-07-14・24本へ拡張）**: 現webuiでは`MAX_CLIPS`が24本まで拡張されている（フロントエンド`Docs/PENDING_TASKS.md`・`Nz-LTX23-backend/Docs/FRONTEND_CATCHUP_WORKORDER.md`参照）。8本は初期実装時点の値。
  - **追補（2026-08-11・棲み分け原則）**: 「1本だけ作る」（Single）と「つなげて長くする」（Chained）は**相互補完の関係で、どちらか一方が上位互換ではない**。Singleは解像度が柔軟でフレーム数によってメモリ消費を調整し、Chainedは長さが柔軟で解像度等によって調整する。設計方針の正本は`Nz-LTX23-backend/Docs/CHAIN_STAGE2_RESEARCH_NOTES.md` §7。
- **【重要・v3追記】現行バックエンドの仕様では、クリップ連結モードのときは画風LoRA（3-6）が適用されない**。UI上プロンプトを一本化したため、Chainモードではプロンプト内のLoRAタグは無視される（この矛盾はUIで明示し、実装時に回避策を検討する）。
  - **追補（2026-07-11・グループ1で解消）**: バックエンド側でchainリクエストへの`loras`が受理されるようになり（`/generate/chain`拡張）、フロントエンド実装もこれに追随してChainのLoRAタグを送信するようになった。この「Chainでは無視される」という警告UIは撤去済みであり、**復元しないこと**。詳細はフロントエンド`Docs/WEBVIEW2_PARITY_BACKLOG.md`§8、`Docs/DEVLOG.md`§8参照。

### 3-4. 既存の動画の続きを生成する（動画→動画）
- 手持ちの動画をアップロードし、その **続き** をAIに作らせる。元動画の末尾何コマ分を手本にするかを指定できる。
- 生成後、元動画と続きを1本につなぎ合わせた版も作れる（つなぎ目の音声クロスフェード付き）。

### 3-5. 音声に合わせて動画を作る（音声→動画）
- 音声ファイルをアップロードし、その音声に沿った動画を生成する（口の動きの一致は、寄りの単一話者・動き控えめのときに得意という性質がある）。

### 3-6. 画風・キャラクターの LoRA を当てる
- 決められたフォルダ（`models/loras/`）に LoRA ファイルを置くと、一覧に **サムネイル** で並ぶ。
- サムネイルをクリックすると、プロンプトの中に `<lora:名前:強さ>` という短いタグが挿入される。これで絵柄が切り替わる。
- **強さは 0〜2.0 の範囲で、1.0 が標準**（＝そのLoRAが想定どおりに効く）。手書きで直接タグを書き込むこともできる。
- **【v3追記】UI上は、挿入されたLoRAをタグではなく「チップ」で見せ、強さは −／＋ボタン（0.1刻み）＋数値の直接入力で調整できるようにした。**
- 一覧は「再読み込み」ボタンで最新化できる（フォルダにファイルを足したあとに押す）。

### 3-7. 動きを別動画から借りる（制御LoRA）
- 別の動画の **輪郭線** や **人の骨格（ポーズ）** を手本にして、その動き方だけを生成に反映させる。**手本になる参照動画が必須**（無いとエラー）。
- 「どのくらい厳密に手本に従わせるか」を調整できる。
- ※ これは 3-6 の画風LoRA とは別物です。画風は「絵柄」、制御LoRAは「動き」を借りる機能。
- **追補（2026-07-17・IC-LoRA UI再設計、第5波）**: 実装では、この制御LoRAの選択を3-6の画風LoRAと同じプロンプトタグ／チップ機構には乗せず、Create画面の参照動画欄に専用の入口（「なし」を含む選択保持ドロップダウン＋LoRA重みスライダー）を用意する形に確定しました。選択してもプロンプト文字列にはタグが出ません（内部的には送信時に画風LoRAと同じ`loras`配列へ合流しますが、UI上の入口は分離しています）。また、「輪郭線と骨格を同じ参照動画から同時に制御したい（SDXLのControlNet的な重ねがけ）」という需要を調査した結果、**現行バックエンドの仕組み上は重ねがけができない**ことが判明しました。異なる前処理（輪郭線用・骨格用など）の制御LoRAは、実は同一のUnion-Control LoRAファイルを前処理違いで登録しているだけの別名であり、バックエンドは異種の制御LoRA併用を明示的に拒否します。複数の手がかりを同時に使いたい場合の正道は、LoRAの重ねがけではなく「1本の参照動画へ複数の手がかりを合成する前処理モード」の追加であり、これは将来の研究課題として起票済みです。詳細は[`DEVLOG.md`](../Docs/DEVLOG.md) §15、[`PENDING_TASKS.md`](../Docs/PENDING_TASKS.md) §3-7を参照。

### 3-8. ジョブの進捗確認・管理
- 生成は時間がかかるので、依頼するとすぐ受付番号（ジョブID）が返り、裏で処理が進む。
- **今どこまで進んだか**（受付中／生成中◯％／どのクリップまで進んだか／完成）を確認できる。
- 過去のジョブ一覧を見て、完成動画を取り出したり、実行中のものを止めたり、不要なものを消したりできる。

## 4. 性能の現実（UXの前提として最重要）

**生成は非同期ジョブ＝押してすぐには出ない。** ここを踏まえないと使えない画面になります。以下はすべて実測値です（グラフィックボードのメモリ16GBの機種での計測）。

### 4-1. 解像度ごとの目安（一次資料 `RESOLUTION_DURATION_CAPABILITY.md` より）

| 表示解像度 | 5秒の生成時間 | 快適に作れる最長 | その最長での生成時間 |
|---|---|---|---|
| 720p（1280×768） | 約2.8分 | **約10.7秒**（257コマ） | 約4.5分 |
| 1080p（1920×1088） | 約4.3分 | **約6.3秒**（153コマ） | 約5.7分 |
| 1440p（2560×1472） | 約11分 | **約3.3秒**（81コマ） | 約5.6分 |
| 4K（3840×2176） | （2秒で約8.7分） | **約2秒** | 約8.7分 |

- **高解像度・長尺ほど遅くなる**。しかも「快適に作れる最長」を超えると、メモリが溢れて **さらに大幅に遅くなる**（例: 1080p は 5秒=約4.3分 → 9秒=約9分 → 11秒=約15分と急激に伸びる）。止まる（クラッシュする）わけではなく「ひたすら遅くなる」。
- **実用の推奨は「720p で作って、必要なら外部ツールで拡大」**。1080p 以上の長尺は現実的な待ち時間を超える。

### 4-2. デザインへの含意（この節が UX の肝）
- **待ち時間があるので、進捗・ジョブ一覧・完了通知のデザインが決定的に重要。** 押して固まる画面はダメ。
- ユーザーが生成前に「これは何分かかりそうか」を把握できると親切（上表の内蔵）。
- 「快適に作れる最長」を超える設定をしたら、**警告を出す**（例:「この設定は生成が大幅に遅くなります」）。禁止ではなく注意喚起。

## 5. 変えてはいけない制約（デザインの外枠）

自由に発想してよい部分（§8）と区別してください。以下は **技術的に決まっていて動かせない** 制約です。

1. **バックエンドの機能しか出せない**。バックエンドとの通信の口（API）は凍結されています。**API が提供していない機能は画面に出さないでください**。特に次は **現状バックエンドに繋がっていないので出さないこと**:
   - **品質モード切替**（「高品質モード」など）→ 出さない。
   - **生成ステップ数の変更**（8ステップ固定）→ 出さない。
   - **CFG／ガイダンス強度** と **ネガティブプロンプト** → **【v3で方針変更】**。現行は蒸留モデルのため機能しない（CFGは実質1固定・ネガティブは無視）が、**将来の非蒸留モデル対応を見越して、無効化した状態（グレーアウト・操作不可）でUI上の場所だけ確保する**ことにした（CFGは「1.0」固定表示、ネガティブ欄は入力不可のプレースホルダ）。完全に隠すのではなく「今は使えない／将来用」と明示する。
     - **→ 2026-07-28にNAG（Normalized Attention Guidance。CFGを使わずにネガティブプロンプトを効かせる手法）で条件付き解禁（経緯は`Docs/DEVLOG.md`の該当節）。CFGは引き続きこの制約のとおり無効のまま。**

   （※開発用の仮画面にもこれらの名残があり機能しません。品質モード・ステップ数は引き続き画面に出しません。）
2. **サイズは64の倍数で生成し、希望サイズへ中央クロップ**（LTX 2.3の制約で幅・高さは64px刻みでしか指定できない）。**【v3で方針変更】** プリセット選択ではなく、**幅・高さを64px刻みのスライダーで直接指定**する形にした（内部の64倍数事情を隠すのではなく、刻みそのものをUIに反映）。加えて **AviUtl2で編集中の動画サイズを取得するボタン** を用意し、取得値は自動で64グリッドへ切り上げる（例: AviUtl2側 1280×720 → 生成 1280×768、1920×1080 → 1920×1088）。希望表示サイズへの中央クロップはバックエンドが担当。
3. **尺はコマ数が「8の倍数＋1」**（9, 17, 25 … 121 …）。秒数で見せてよいが、内部的にこの刻みになる。上限は481コマ（24fpsで約20秒）。**【v3追記】fpsを数値で指定可能**にしたため、**尺（秒）および「快適に作れる最長（秒）」はfpsから換算して表示する**（コマ数の刻み・上限481は不変。例: 121コマ＝24fpsで約5.0秒／30fpsで約4.0秒）。
4. **日英2言語対応**（既定＝英語、日本語に切替可能）。これは現行GUIの流儀。※ ただしターゲットは日本人なので、日本語を第一級に扱う配慮はしてよい。
5. **バックエンドは同じパソコン内で別プロセスとして起動している**。操作画面は `localhost`（自分のパソコン）の決まったポートに通信する。したがって:
   - **接続先の設定**（アドレス・ポート）を持てる必要がある。
   - **「バックエンドがまだ起動していない／落ちている」状態** を、ちゃんと扱う（エラーで固まらず「サーバー未起動です」と伝える）デザインが必要。
6. **同時に処理できるのは1ジョブだけ**。生成中に次を頼むと断られる（混雑中）。この状態の見せ方が要る。

## 6. 既存GUI（参考・これが「お題」の出発点）

現在は開発検証用に **Gradio 製の仮の操作画面** があります。これは **開発者が機能を確認するための仮GUI** であって、デザインのお手本ではありません。**これを AviUtl2 の文脈・UI慣習に合わせて作り直すのが、あなたへのお題**です。機能の全体像を掴むための参考として、その構成を文章で描写します（スクリーンショットはありません）。

現状は上部の共通バー＋5つのタブで構成されています。

- **上部の共通バー**（常時表示）: サーバーの状態表示（GPU・メモリ・混雑状況）／「更新」「モデル読込」「モデル解放」ボタン。
- **タブ1「生成（Generate）」**: 左に入力欄（プロンプト、サイズ、コマ数、fps、シード、プリセット選択、最大10枚のキーフレーム画像欄、制御LoRA用の参照動画欄）、右に操作パネル（生成ボタン→進捗表示→ジョブID→出来上がり動画のプレビュー）という左右2カラム。
- **タブ2「クリップ連結（Clip Chain）」**: 全体共通の設定＋つなぎ目の設定＋クリップ8枠（各枠にプロンプトとコマ数、先頭枠だけ開始画像）。ここに「既存動画の続き（動画→動画）」のモード切替が同居。（注: 単発の「音声→動画」はDesignv3でCreate画面の音声添付欄に移設されました。詳しくは§11を参照。）
- **タブ3「ジョブ（Jobs）」**: ジョブ一覧の表。行を選ぶと詳細・完成動画・エラーが出て、キャンセル／削除ボタン。
- **タブ4「設定（Settings）」**: 言語・テーマ（ダーク/ライト）切替、接続先アドレス表示、ポーリング間隔、サーバー設定の閲覧、モデル選択、危険操作（アンロード/一括削除）。
- **タブ5「画風LoRA（Style LoRA）」**: 画風・キャラLoRAのサムネイル一覧＋「再読み込み」ボタン。クリックでタブ1のプロンプトにタグが挿入される。

この5タブ構成は「機能を漏れなく並べた」だけの検証用レイアウトです。**タブの再編・統合・並べ替えは自由**（§8参照）。

## 7. AviUtl2 側の UI 形態（実装方針・確定）

**AviUtl2** は日本製の定番無料動画編集ソフト（旧「AviUtl」の後継。2025年7月に6年ぶりの後継として ExEdit2 が登場、64bit化・UI刷新。以降ほぼ毎週ベータ更新中で、2026年7月時点でbeta53a）。拡張機能（プラグイン）で機能を足せます。

**旧版ではこの節を「要調査」としていましたが、AviUtl2公式の更新履歴（docs.aviutl2.jp/changelog）を確認し、方針を確定しました。**

- beta1（2025/7/7）時点のSDKは入力・出力プラグインのみ対応で、フィルタプラグインや独自UIウィンドウは未対応でした（当時の外部記事はこの状態を正しく報告していたものです）。
- その後 **beta25（2025/12/20）で「プラグインのウィンドウを分離できる」機能が追加**され、**beta41（2026/4/12）・beta50（2026/6/14）ではフィルタプラグイン（.auf2）自体のバグ修正**が入っています。SDKミラー（GitHub: aviutl2/aviutl2_sdk_mirror）にも、現在は入力・出力・フィルタ・スクリプトモジュールの4種のプラグインタイプが揃っています。
- 以上から、**プラグインが自分の子ウィンドウを持ち、それが本体パネル（オブジェクトリスト等）と同様にドッキング／独立ウィンドウ化できる**という前提で設計を進めます（※厳密なSDK登録手順の裏取りは実装フェーズで別途行いますが、デザイン方針としてはこの前提で確定とします）。

**実装方針（確定）**: プラグインが持つそのウィンドウの中身は、**WebView2（Chromiumベースのネイティブ埋め込みブラウザコンポーネント）でホストするWeb UI**とします。バックエンドとの非同期通信、ジョブポーリング、サムネイル一覧といった今回の要件と相性が良いためです。AviUtl2本体との連携（選択中クリップの取得、生成結果のタイムライン挿入）が必要な箇所だけ、薄いネイティブブリッジを挟みます。**Win32/GDIによるネイティブ描画は禁止ではなく、フレーム単位の低遅延描画が本当に必要になった場合の逃げ道として残しますが**、現時点で想定している画面（フォーム、ジョブ一覧、LoRAブラウザ等）はいずれもWeb UIで十分にカバーできる想定です。

**デザインAIへの指示**: 「特定のUI形態に依存しない設計」はもう気にする必要はありません。素直に、**レスポンシブなWebアプリ／ダッシュボードとして**設計してください。ホバー、トランジション、モーダル、トースト通知、タブ切り替えアニメーションなど、通常のWeb UIで使える表現は遠慮なく使って構いません。ネイティブWindowsダイアログの制約に合わせる必要はありません。ただし、ホストされるウィンドウは横長の別窓にも縦長の細いドッキングパネルにもなり得るため、**極端な横幅・縦幅でも破綻しないレスポンシブなレイアウト**は引き続き重要です。

## 8. 自由に発想してよい領域（デザインの腕の見せどころ）

§5の制約を守る限り、以下は自由です。むしろ積極的に提案してください。

- **レイアウト・タブ構成の再編**。5タブをそのまま踏襲する必要はない。編集者の作業導線（「クリップを1本作る」「つなげて長くする」「絵柄を当てる」）に沿って再設計してよい。
- **プリセット／履歴のアイデア**。よく使うサイズ・尺・プロンプトの保存、過去に作ったクリップの再利用など。
- **生成待ち時間のUX**。数分の待ちを退屈・不安にさせない見せ方（進捗の可視化、完了通知、待ち時間の見積り表示、待つ間に次の設定を仕込める導線など）。
- **サムネイル／プレビューの見せ方**。画風LoRA一覧、キーフレーム画像、生成結果の並べ方・比較のしかた。
- **「素材づくり」としての位置づけを強めるアイデア**。作ったクリップをどうタイムラインへ渡すか（の見せ方。実際の受け渡しはバックエンド外の連携だが、UI上の導線として提案してよい）。
- **Web的なインタラクション表現**。§7の通り実装はWebView2ベースのWeb UIです。ホバー、トランジション、モーダル、トースト通知、スケルトンローディングなど、通常のWebダッシュボードで使う表現を制約なく使ってください。

## 9. デザインに期待する成果物

1. **画面構成案**。まずワイヤーフレームで検証し、その後High Fidelityへ進める2段階を推奨します。§7の実装方針（レスポンシブなWeb UI）に沿った、単一の情報設計で構いません。
2. **主要ワークフローの画面遷移**。最低限この3つの流れを:
   - **A: 「文章から1クリップ作って、タイムラインへ渡す」**（T2V の基本フロー。プロンプト入力→生成→待ち→完成→受け渡し）。
   - **B: 「クリップ連結で30秒のシーンを作る」**（複数クリップにそれぞれプロンプトを与えてつなぐフロー）。
   - **C: 「画風LoRAを当てて絵柄を変える」**（LoRA一覧から選ぶ→プロンプトにタグが入る→生成）。
3. **情報設計の提案**。待ち時間・混雑・サーバー未起動といった「状態」をどう伝えるか。

## 11. 確定したデザイン（v3・叩き台の要約）

ワイヤーフレーム→High Fidelityの検証を経て、以下の情報設計に決定した（成果物のモック: `AviUtl2-AI動画生成-モック.html`）。

- **5タブ→3モード＋常設ジョブレーンに再編**。編集者の導線に沿って「作る（Create）」「つなげる（Chain）」「素材棚（Library：画風LoRA＋履歴）」の3モードとし、ジョブ管理（§3-8）はタブにせず**画面右に常設のジョブレーン**として置く。「投げたら編集に戻る／状態は常に見えている」を軸にする。
- **単発A2V（音声→動画）はCreate画面の音声添付欄に配置**。音声ファイルを添付すると自動的にA2Vモード（distilled で生成）として実行される。**ChainはClips（クリップ連結）とV2V（既存動画の続き）の2つのサブモードのみに確定**。
  - **追補（2026-07-17・UIリデザイン）**: ChainのClips／V2Vは**サブタブ（切り替えボタン）を廃止**し、ソース動画（V2Vの元動画）を添付したかどうかで自動的にモードを判別する方式へ変更しました（添付あり=V2V継続、添付なし=ゼロから連結）。どちらのモードかはモードバッジで表示します。またCreate画面のIC-LoRA（参照動画）とA2V（音声添付）は、キーフレーム欄の下の折りたたみ（アコーディオン・初期は閉）へ常設化し、両者は相互排他です。生成プリセットは、タグボタンの列から**ドロップダウン（Create／Chain共用）**へ変更しました。詳細は[`DEVLOG.md`](../Docs/DEVLOG.md) §13。
  - **追補（2026-07-17・IC-LoRA UI再設計、第5波）**: 上記アコーディオン内のIC-LoRA入口を、単なる参照動画アップロード欄からさらに一歩進め、**制御LoRAの選択自体も専用の状態持ちドロップダウン（「なし」付き・選択保持）＋重みスライダーへ分離**しました。従来は制御LoRAの選択も画風LoRAと同じプロンプトタグ機構を経由しており、選択後にドロップダウン表示がplaceholderへ戻って選択に気づきにくい、異なる制御LoRAを選び直すとタグが積み上がりバックエンドの422エラーを誘発する、という問題があったためです。プロンプトに制御LoRAタグを手打ちした場合は自動でパネル選択へ移行し、Chain画面では（自動移行はせず）警告バナー＋Generate無効化で対応します。詳細は[`DEVLOG.md`](../Docs/DEVLOG.md) §15。
- **プロンプト欄はタブの外・上部に一本化**し、CreateとChainで共有する（ただしChainではLoRAタグは無視される点を明示、§3-3）。
  - **追補（2026-07-11・グループ1で解消）**: §3-3の追補と同じく、Chainでのプロンプト内LoRAタグは現在受理・送信される。「Chainでは無視される」の明示UIは撤去済みで、**復元しないこと**。
- **待ち時間UX（§4が最重要）**: 生成ボタンに所要時間の見積りを常時表示／尺スライダーに「快適に作れる最長」の目盛りを置き、超過時は黄色＋警告（禁止はしない）／完了はトースト＋ジョブレーンのサムネイル点灯で通知。
- **同時1ジョブ制約（§5-6）は「予約」で吸収**：生成中に次を頼むと断るのではなく「予約中（現在のジョブ完了後に自動送信）」として受ける。
  - **追補（2026-07-17・予約機構は廃止）**: 実機での使用感を踏まえ、この「予約」方式はやめました。同時1ジョブという制約はそのままに、生成中は生成ボタンをビジー状態で無効化して弾く（シンプルに「今は押せない」と分かる）方式へ変更しています。あわせて画面右に常設していたジョブレーン（ジョブ一覧の縦長パネル）も廃止し、ジョブ一覧は生成ボタンと同じパネルの中に台帳（ledger：全ジョブの一覧表）として置き直しました。これは「生成ボタンのあるパネルを画面の最も右上に置き、その右には何も表示しない」というオーナー要望に合わせるための再構成です。
- **状態表示（§5-5）**: サーバーの待機／混雑／未起動をヘッダで色分け。未起動時はエラーで固めず「サーバー未起動」バナー＋再接続導線。
- **解像度・fps・シード・CFG（無効）・ネガティブ（無効）の数値UIはCreate/Chain両方に配置**。Chainはこれに加えクリップ枠エディタ（各枠のプロンプト上書き・尺の±調整）とSeam blend（秒＋コマ数を併記するスライダー）を持つ。
  - **→ 2026-07-28にネガティブはNAGで条件付き解禁（経緯は`Docs/DEVLOG.md`の該当節）。CFGは引き続き無効のまま。**
- **日英2言語（§5-4）**: 既定＝英語、ヘッダのトグルで全画面を日本語に切替。
- **実装**: §7の通りWebView2上のレスポンシブWeb UI。横長ウィンドウでも縦長ドッキングパネルでも破綻しないよう、パネルは折り返しで縦積みに再構成される。

> 注: このモックは操作感を伝えるためのプロトタイプで、サーバーの状態やジョブ進捗はデモ用のダミー挙動（ヘッダのステータスはクリックで待機／混雑／未起動を手動切替）。実装では実サーバー状態に自動追従させる。
