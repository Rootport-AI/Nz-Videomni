# AviUtl2 拡張機能 UI/UX デザインブリーフ

> **この文書の読み手はデザインAI（Claude Design）です。** あなたはこのアプリのコードも実物のテストGUI画面も見られません。AviUtl2のデフォルトUIのみ、画像を共有します。これらだけを読んで、後述する「AviUtl2 拡張機能」の画面デザイン案（叩き台）を作ってください。設計に必要な情報はすべてこの文書に入っています。専門的な略語には最初に用語集を用意しました。

---

## 0. このデザインで作るもの（一言で）

**パソコン1台（家庭用のグラフィックボード搭載機）の中だけで動く「AIによる動画生成ツール」の操作画面**をデザインしてください。生成の中身（AIの計算）は別のプログラム（バックエンド）が担当します。あなたにデザインしてほしいのは、そのバックエンドに「こういう動画を作って」と頼み、出来上がった動画を受け取って、動画編集ソフト **AviUtl2** のタイムラインに渡すための **フロントエンド（操作画面）** です。

- **役割分担**: 動画を生成するのはバックエンド。動画の切り貼り・タイムライン編集は AviUtl2 本体。あなたがデザインする拡張機能は、その間に立つ **「生成を頼んで、結果を受け取って渡すだけの薄い仲介役」** です。動画のエンコードや編集機能を自前で持つ必要はありません。
- **ゴール**: AviUtl2 で動画を編集している人が、編集の流れを止めずに「AIで素材の動画クリップを作る」ことができる操作画面。

## 1. 用語集（この文書で使う言葉）

| 用語 | 意味 |
|---|---|
| **バックエンド** | 動画を実際に生成する裏方プログラム。パソコン内で別プロセスとして動く。操作画面からは通信（HTTP）で命令を送る。 |
| **T2V（文章→動画）** | 文章（プロンプト）だけを入力して動画を生成すること。 |
| **I2V（画像→動画）** | 静止画を起点にして動画を生成すること（例: 1枚目の絵を指定してそこから動かす）。 |
| **プロンプト** | 「どんな映像がほしいか」を書いた文章による指示。英語でも日本語でも書ける。 |
| **シード** | 生成の乱数の種。同じ設定＋同じシードなら毎回同じ動画になる。数字を変えると別パターンが出る。「-1」でランダム。 |
| **クリップ** | 生成される1本の短い動画。これを何本もつないで長いシーンにする。 |
| **フレーム** | 動画のコマ。1秒あたり24コマ（24fps）が既定。 |
| **LoRA（ローラ）** | AIに画風やキャラクターを追加で覚えさせた小さな追加ファイル。適用すると絵柄が変わる。 |
| **制御LoRA** | 別の動画の「輪郭線」や「人の骨格（ポーズ）」を手本にして、動きだけをまねさせる仕組み。手本になる参照動画が必要。 |
| **ジョブ** | 1回の生成依頼。時間がかかるので、依頼するとすぐ受付番号（ジョブID）が返り、裏で処理が進む。 |

## 2. ターゲットユーザー像

- **AviUtl2 のユーザー**。日本の趣味〜セミプロの動画編集者。ニコニコ動画・YouTube 文化圏。
- **無料・軽量・キーボード操作を好む** 層。重厚な有料ソフトより、身軽で自分好みにいじれるツールを選ぶ人たち。
- 動画編集の作業中に、AI生成を **「素材づくりの一手段」** として使う。目的は「編集する素材（短いクリップ）を手早く得る」ことであって、AIそのものをいじり倒すことではない。専門用語より、編集者の言葉（「クリップ」「尺」「つなぐ」など）で語られるほうが馴染む。
- **待ち時間に慣れていない前提で設計する**。動画生成は数分かかる（後述）。編集のテンポを崩さない見せ方が重要。

## 3. できること一覧（＝デザインすべき機能）

現在バックエンドが提供している機能です。AviUtl2 ユーザーの言葉で並べます。**これらが画面に必要な機能の全体像**です（画面の並べ方・まとめ方は自由）。

### 3-1. 文章から動画を作る（T2V）
- プロンプト（文章）を書いて生成する。
- **サイズ**（幅×高さ）、**尺**（コマ数／秒数）、**シード**を指定できる。
- 出来上がりは1本の短い動画クリップ（音声つき。発話・効果音・音楽はプロンプト次第のベストエフォート）。

### 3-2. 画像を起点に動かす（I2V／キーフレーム指定）
- 静止画を「この位置のコマはこの絵」と指定して、そこから動く動画を生成する。
- **最大5枚**まで画像を置ける（例: 先頭の絵と終わりの絵を指定して、その間をAIが補間する）。各画像に「どのくらい絵に忠実にするか（強さ）」を持てる。

### 3-3. クリップ連結で長いシーンを作る
- 短いクリップを何本もつなげて長尺（長いシーン）にする。**前のクリップの終わり＝次のクリップの始まり** が自然につながるように生成される（つなぎ目のブレンド幅を調整可能）。
- **クリップごとに別々のプロンプト** を書ける（全体共通のプロンプト＋クリップ個別の上書き、という考え方）。
- 現状は最大8本のクリップ枠。

### 3-4. 既存の動画の続きを生成する（動画→動画）
- 手持ちの動画をアップロードし、その **続き** をAIに作らせる。元動画の末尾何コマ分を手本にするかを指定できる。
- 生成後、元動画と続きを1本につなぎ合わせた版も作れる（つなぎ目の音声クロスフェード付き）。

### 3-5. 音声に合わせて動画を作る（音声→動画）
- 音声ファイルをアップロードし、その音声に沿った動画を生成する（口の動きの一致は、寄りの単一話者・動き控えめのときに得意という性質がある）。

### 3-6. 画風・キャラクターの LoRA を当てる
- 決められたフォルダ（`models/loras/`）に LoRA ファイルを置くと、一覧に **サムネイル** で並ぶ。
- サムネイルをクリックすると、プロンプトの中に `<lora:名前:強さ>` という短いタグが挿入される。これで絵柄が切り替わる。
- **強さは 0〜2.0 の範囲で、1.0 が標準**（＝そのLoRAが想定どおりに効く）。手書きで直接タグを書き込むこともできる。
- 一覧は「再読み込み」ボタンで最新化できる（フォルダにファイルを足したあとに押す）。

### 3-7. 動きを別動画から借りる（制御LoRA）
- 別の動画の **輪郭線** や **人の骨格（ポーズ）** を手本にして、その動き方だけを生成に反映させる。**手本になる参照動画が必須**（無いとエラー）。
- 「どのくらい厳密に手本に従わせるか」を調整できる。
- ※ これは 3-6 の画風LoRA とは別物です。画風は「絵柄」、制御LoRAは「動き」を借りる機能。

### 3-8. ジョブの進捗確認・管理
- 生成は時間がかかるので、依頼するとすぐ受付番号（ジョブID）が返り、裏で処理が進む。
- **今どこまで進んだか**（受付中／生成中◯％／どのクリップまで進んだか／完成）を確認できる。
- 過去のジョブ一覧を見て、完成動画を取り出したり、実行中のものを止めたり、不要なものを消したりできる。

## 4. 性能の現実（UXの前提として最重要）

**生成は非同期ジョブ＝押してすぐには出ない。** ここを踏まえないと使えない画面になります。以下はすべて実測値です（グラフィックボードのメモリ16GBの機種での計測）。

### 4-1. 解像度ごとの目安（一次資料 `RESOLUTION_DURATION_CAPABILITY.md` より）

| 表示解像度 | 5秒の生成時間 | 快適に作れる最長 | その最長での生成時間 |
|---|---|---|---|
| 720p（1280×768） | 約2.8分 | **約10.7秒**（257コマ） | 約4.5分 |
| 1080p（1920×1088） | 約4.3分 | **約6.3秒**（153コマ） | 約5.7分 |
| 1440p（2560×1472） | 約11分 | **約3.3秒**（81コマ） | 約5.6分 |
| 4K（3840×2176） | （2秒で約8.7分） | **約2秒** | 約8.7分 |

- **高解像度・長尺ほど遅くなる**。しかも「快適に作れる最長」を超えると、メモリが溢れて **さらに大幅に遅くなる**（例: 1080p は 5秒=約4.3分 → 9秒=約9分 → 11秒=約15分と急激に伸びる）。止まる（クラッシュする）わけではなく「ひたすら遅くなる」。
- **実用の推奨は「720p で作って、必要なら外部ツールで拡大」**。1080p 以上の長尺は現実的な待ち時間を超える。

### 4-2. デザインへの含意（この節が UX の肝）
- **待ち時間があるので、進捗・ジョブ一覧・完了通知のデザインが決定的に重要。** 押して固まる画面はダメ。
- ユーザーが生成前に「これは何分かかりそうか」を把握できると親切（上表の内蔵）。
- 「快適に作れる最長」を超える設定をしたら、**警告を出す**（例:「この設定は生成が大幅に遅くなります」）。禁止ではなく注意喚起。

## 5. 変えてはいけない制約（デザインの外枠）

自由に発想してよい部分（§8）と区別してください。以下は **技術的に決まっていて動かせない** 制約です。

1. **バックエンドの機能しか出せない**。バックエンドとの通信の口（API）は凍結されています。**API が提供していない機能は画面に出さないでください**。特に次は **現状バックエンドに繋がっていないので出さないこと**:
   - **ネガティブプロンプト**（「これは出さないで」という否定指示欄）
   - **CFG／ガイダンス強度のスライダー**
   - **品質モード切替**（「高品質モード」など）
   - **生成ステップ数の変更**（8ステップ固定）

   （※開発用の仮画面にはこれらの欄が名残で置いてありますが、機能しません。デザイン案では出さないでください。）
2. **サイズは64の倍数で生成し、希望サイズへ中央クロップ**。ユーザーが 1280×720 を望んでも、内部では 1280×768 で生成してから中央を切り抜いて 720 にする、という仕組み。この差はUIが吸収する（ユーザーには「720p」等の分かりやすい選択肢を見せ、64倍数の内部事情は隠してよい）。
3. **尺はコマ数が「8の倍数＋1」**（9, 17, 25 … 121 …）。秒数で見せてよいが、内部的にこの刻みになる。上限は 24fps で 20秒（481コマ）。
4. **日英2言語対応**（既定＝英語、日本語に切替可能）。これは現行GUIの流儀。※ ただしターゲットは日本人なので、日本語を第一級に扱う配慮はしてよい。
5. **バックエンドは同じパソコン内で別プロセスとして起動している**。操作画面は `localhost`（自分のパソコン）の決まったポートに通信する。したがって:
   - **接続先の設定**（アドレス・ポート）を持てる必要がある。
   - **「バックエンドがまだ起動していない／落ちている」状態** を、ちゃんと扱う（エラーで固まらず「サーバー未起動です」と伝える）デザインが必要。
6. **同時に処理できるのは1ジョブだけ**。生成中に次を頼むと断られる（混雑中）。この状態の見せ方が要る。

## 6. 既存GUI（参考・これが「お題」の出発点）

現在は開発検証用に **Gradio 製の仮の操作画面** があります。これは **開発者が機能を確認するための仮GUI** であって、デザインのお手本ではありません。**これを AviUtl2 の文脈・UI慣習に合わせて作り直すのが、あなたへのお題**です。機能の全体像を掴むための参考として、その構成を文章で描写します（スクリーンショットはありません）。

現状は上部の共通バー＋5つのタブで構成されています。

- **上部の共通バー**（常時表示）: サーバーの状態表示（GPU・メモリ・混雑状況）／「更新」「モデル読込」「モデル解放」ボタン。
- **タブ1「生成（Generate）」**: 左に入力欄（プロンプト、サイズ、コマ数、fps、シード、プリセット選択、最大5枚のキーフレーム画像欄、制御LoRA用の参照動画欄）、右に操作パネル（生成ボタン→進捗表示→ジョブID→出来上がり動画のプレビュー）という左右2カラム。
- **タブ2「クリップ連結（Clip Chain）」**: 全体共通の設定＋つなぎ目の設定＋クリップ8枠（各枠にプロンプトとコマ数、先頭枠だけ開始画像）。ここに「既存動画の続き（動画→動画）」「音声→動画」のモード切替も同居。
- **タブ3「ジョブ（Jobs）」**: ジョブ一覧の表。行を選ぶと詳細・完成動画・エラーが出て、キャンセル／削除ボタン。
- **タブ4「設定（Settings）」**: 言語・テーマ（ダーク/ライト）切替、接続先アドレス表示、ポーリング間隔、サーバー設定の閲覧、モデル選択、危険操作（アンロード/一括削除）。
- **タブ5「画風LoRA（Style LoRA）」**: 画風・キャラLoRAのサムネイル一覧＋「再読み込み」ボタン。クリックでタブ1のプロンプトにタグが挿入される。

この5タブ構成は「機能を漏れなく並べた」だけの検証用レイアウトです。**タブの再編・統合・並べ替えは自由**（§8参照）。

## 7. AviUtl2 側の UI 形態（重要・不確実性あり）

**AviUtl2** は日本製の定番無料動画編集ソフト（旧「AviUtl」の後継。2025年に6年ぶりの後継として ExEdit2 が登場、64bit化・UI刷新）。拡張機能（プラグイン）で機能を足せます。

**⚠️ ここは正直に「要調査」を含みます。** WEB調査時点（2026年）で分かった範囲:

- AviUtl2 のプラグインSDKは、公式には **入力プラグイン（.aui2）と出力プラグイン（.auo2）** を主対象としており、**フィルタプラグイン（.auf2）や独自UIウィンドウ／ドッキングパネルの公式サポートは、まだ整備途上** と報告されています（旧AviUtlにあった自由なプラグインUIが、AviUtl2 ではまだ揃っていない）。
- **したがって「拡張機能が本体内にどんな形のUI（ドッキングパネル／独自ウィンドウ／設定ダイアログ）を出せるか」は現時点で確定していません（要調査：公式SDKの最新確認が必要）。**

**デザインAIへの指示**: この不確実性を踏まえ、**特定のUI形態（本体内ドッキング前提など）に強く依存しない、移植しやすい設計** にしてください。現実的にあり得る受け皿として、次のいずれでも成立するようレイアウトを考えると安全です:

- **(A) 独立したウィンドウ**（AviUtl2 とは別窓のコンパネ的ウィンドウ。最も確実に実現可能な想定）。
- **(B) 本体に組み込まれるドッキングパネル**（実現できれば理想。ただし現状SDKで可能か要調査）。
- 実装言語の候補は C++（.aux2 DLL）または C#（HTTP通信が容易）。どちらでも、画面は上記いずれかの器に載る前提。

つまり **「幅の広い横長パネルでも、縦長の別窓でも破綻しないレスポンシブな情報設計」** を優先してください。

## 8. 自由に発想してよい領域（デザインの腕の見せどころ）

§5の制約を守る限り、以下は自由です。むしろ積極的に提案してください。

- **レイアウト・タブ構成の再編**。5タブをそのまま踏襲する必要はない。編集者の作業導線（「クリップを1本作る」「つなげて長くする」「絵柄を当てる」）に沿って再設計してよい。
- **プリセット／履歴のアイデア**。よく使うサイズ・尺・プロンプトの保存、過去に作ったクリップの再利用など。
- **生成待ち時間のUX**。数分の待ちを退屈・不安にさせない見せ方（進捗の可視化、完了通知、待ち時間の見積り表示、待つ間に次の設定を仕込める導線など）。
- **サムネイル／プレビューの見せ方**。画風LoRA一覧、キーフレーム画像、生成結果の並べ方・比較のしかた。
- **「素材づくり」としての位置づけを強めるアイデア**。作ったクリップをどうタイムラインへ渡すか（の見せ方。実際の受け渡しはバックエンド外の連携だが、UI上の導線として提案してよい）。

## 9. デザインに期待する成果物

1. **画面構成案**（ワイヤーフレーム〜ビジュアルモック）。§7の不確実性を踏まえ、独立ウィンドウでも組み込みパネルでも成立する構成が望ましい。
2. **主要ワークフローの画面遷移**。最低限この3つの流れを:
   - **A: 「文章から1クリップ作って、タイムラインへ渡す」**（T2V の基本フロー。プロンプト入力→生成→待ち→完成→受け渡し）。
   - **B: 「クリップ連結で30秒のシーンを作る」**（複数クリップにそれぞれプロンプトを与えてつなぐフロー）。
   - **C: 「画風LoRAを当てて絵柄を変える」**（LoRA一覧から選ぶ→プロンプトにタグが入る→生成）。
3. **情報設計の提案**。待ち時間・混雑・サーバー未起動といった「状態」をどう伝えるか。
