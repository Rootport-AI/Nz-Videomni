## 1. 背景と動機

想定ユーザーは、ゆっくり実況・VOICEROID実況（音声合成ソフトによるキャラクター実況動画）の制作者。20分の動画1本に対して音声素材が100〜200個あり、そのすべてに i2v（画像から動画を生成する機能）による立ち絵の口パクアニメーションが必要になる。

i2v 生成は1本あたり4〜5分かかる（RTX 4070 Ti SUPER 実測）。100〜200本を1件ずつ手動で生成していては到底終わらないため、就寝中に一括投入して朝までに全件仕上げる「バッチA2V」機能が必須になる。

## 2. 確定済みのUX設計（オーナー合意・2026-07-11〜12）

### 2.1 表（マニフェスト）が正典

ファイル名から音声・画像・プロンプトを自動的に結びつける機能は**採用しない**。理由は次の2点:

- ユーザーにファイルのリネームという余計な手間を負わせたくない。
- 音声ファイル名は VOICEROID が吐き出したままの形（連番＋台詞の一部など）で使う前提であり、命名規則に依存した自動結びつけは事故りやすい。

同様の理由で、**表情プリセット機能（喜怒哀楽などを定型ボタンで選ぶ方式）も不採用**。オーナーの判断は「演技は主観的な表現であり、LTX 2.3 は自然言語プロンプトがよく効くモデルなので、表情を定型化するとむしろ表現の幅を狭める」というもの。プロンプトは自由記述のテキスト欄に任せる。

### 2.2 操作フロー

1. wav フォルダのパスを入力する。
2. 画像フォルダのパスを入力する。
3. 「Set audios」ボタンを押すと、wav フォルダをスキャンして表（マニフェスト）を生成・表示する。
4. 表の上で、必要な行だけ手動編集する（画像の割り当て・プロンプトの上書きなど）。
5. 「Generate」ボタンでバッチ生成を開始する。

### 2.3 表の列構成

| 列 | 内容 |
|---|---|
| queue# | 実行順を表す通し番号 |
| wav名 | 音声ファイル名（VOICEROIDが吐いたままの表記） |
| Duration | 音声の長さ |
| image | ドロップダウン選択。既定値は "Shared"（Generate タブで設定する共通のi2vキーフレーム画像を指す） |
| Prompt | テキスト入力（行ごとの個別プロンプト） |
| Stat | Waiting / Generating / Done / Failed / Skip のいずれか |

### 2.4 プロンプト合成モード（Add / Replace）

行ごとの個別切り替えは**α版では見送り**（要望が多ければ次段で検討）。**グローバルなラジオボタン**で全行に一括適用する:

- **Add**: 共通プロンプト（Generate タブの共通欄）の末尾に、行のテキストを追記する。
- **Replace**: 行のテキストが共通プロンプトを丸ごと置換する。

### 2.5 共通画像未設定時のガード

共通のi2vキーフレーム画像が未設定の状態で、image列が "Shared" のまま（＝行ごとの個別画像指定が無い）行が1つでもあると、生成開始時にエラーで停止する。

### 2.6 尺の上限表示とSkip

パス入力欄の近くに「max duration: ***f(**s)」（フレーム数・秒数）を表示する。上限を超える音声はバッチから除外し、表上でグレー表示＋理由表示の **Skip** 扱いとする。算出は既存の算術（481フレーム上限・解像度別の快適上限）をそのまま流用する（[`RESOLUTION_DURATION_CAPABILITY.md`](RESOLUTION_DURATION_CAPABILITY.md)・`chain_math.py`）。

### 2.7 行の並び順

既定は**ファイル更新日時順**。VOICEROIDは台本の順番どおりにファイルを保存するため、更新日時順にしないと台本の並びと一致しない（ファイル名の五十音順ソートだと台本の順番からズレる）。

### 2.8 出力ファイル名

音声ファイルと同名にする（例: `こんにちは.wav` → `こんにちは.mp4`）。AviUtl2（動画編集ソフト）のタイムラインへ生成結果を戻す際、音声と動画の対応付けをファイル名で行えるようにするため。

### 2.9 CSVマニフェストの永続化

表はCSVとして音声フォルダの隣に自動保存し、再スキャン時に読み戻す。これにより、やり直しや追加生成（既に生成済みの行をスキップして続きだけ回す、など）に耐える設計にする。

**CSV形式はWebView2フロントエンド（AviUtl2拡張・Reactベース）と共通仕様にし、Gradio GUIとWebView2フロントエンドの両方で相互運用できるようにする。** 列定義・文字コードなど具体的な形式は未確定（§4.5参照）。

### 2.10 バッチ実行の逐次投入・耐障害性

バックエンドは同時1ジョブ制（2件目以降は409で拒否される仕様）のため、GUI側が表の上から1件ずつ逐次投入するキューを持つ。

- **1件失敗しても全体を止めず、次の行へ進む。**
- 完了時に成功／失敗の一覧を表示する。
- **途中再開（既に生成済みの行はスキップする）が必須**。就寝中に実行し、翌朝に結果を確認する運用が前提のため、電源断・アプリ再起動などがあっても再実行で続きから拾えるようにする。

## 3. 技術的裏取り済み事項（Gradio 6.19.0 実ソース確認済み）

表の実装方式を検討する上で、Gradio（Python製のGUIフレームワーク。本バックエンドのWebGUIはこれで構築されている）の `gr.Dataframe` コンポーネントの実際の機能を現物のソースで確認した。

- **`gr.Dataframe` にセル内ドロップダウンは存在しない**（`choices` に相当するパラメータが無い）。列ごとに選択式のセルを持たせる機能は無い。
- 使える機能は次のとおり:
  - `interactive=True` によるセル編集。
  - `static_columns`（特定の列だけ読み取り専用にする。ただし `col_count` を固定する副作用がある）。
  - `.select` イベント（`evt.index=(row, col)`・`evt.row_value` でクリックされたセルの位置と行データを取得できる）。
  - **`.edit` イベント**（セル単位の差分を取得できる。`index`・`previous_value`・`value`）。
  - `max_height`（スクロール可能な高さ指定。ページネーション機能は無い）。
- **推奨構成**: 表と `.select` イベントを組み合わせ、選択した行を下部の編集パネル（`gr.Dropdown` ＋ `gr.Textbox`）へロードする方式。これは**既存の Jobs タブの `jobs_table` / `on_job_select`（`gradio_ui/ui.py`・`gradio_ui/handlers.py`）と同型**であり、実装パターンを流用できる。
- **折衷案**: Prompt 列だけ `interactive=True` にして `.edit` の差分検知でセル直接編集を許し、image 列（ドロップダウンが必要）は下部パネル経由にする、という組み合わせも有力。
- **Stat 列の更新**は `gr.Timer` の `.tick` によるポーリングで実現する（既存の `config_retry_timer` に前例がある・`gradio_ui/ui.py`）。
- **WebView2側（React・AviUtl2拡張フロントエンド）は、セル内に `<select>` や `<textarea>` を自由に組み込めるため**、モック通りのドロップダウン付き表がそのまま作れる。想定行数（200行程度）であれば仮想化（画面外の行を描画しない最適化）は不要と見積もる。

## 4. 未決の設計論点（次セッション冒頭でオーナーに確認すること）

以下5点は本セッションでは決着していない。実装着手前に必ずオーナーへ確認する。

### 4.1 Replace切替時の挙動

- **オーナー原案**: Add⇔Replace の切替時に、共通プロンプトの内容を全行のテキスト欄へ転記する。この場合、誤操作で個別プロンプトが上書き消失するリスクがあるため、**Undo（元に戻す）機能が必須**になる。
- **対案（非破壊方式）**: 行のテキストは常に「個別テキストのみ」を保持し、送信時にモード（Add/Replace）に応じてサーバー側・GUI側で合成する。この方式ならモード切替でデータが壊れないため Undo は不要。個別テキストが空の行を「共通プロンプトで下敷き編集したい」というニーズには、「共通をこの行にコピー」ボタンを別途用意して対応する。

どちらを採るかは実装コストと事故りやすさのトレードオフであり、次セッション冒頭でオーナーに確認する。

### 4.2 Prompt列の編集方式

- セル直接編集（`.edit` イベントで差分検知）か、下部パネル経由か、両者の折衷か（§3参照）。UXの手触りに関わるため、実装前に方向性を決める。

### 4.3 Skipの閾値

- 481フレーム（API上限）基準か、解像度別の快適上限基準かで迷いがある。**現時点で有力なのは「快適上限は警告のみで表示し、Skip自体は481フレーム基準にする」案**だが、確定はしていない。

### 4.4 バッチAPIの実装層

- **第一候補**: GUI側のループで、既存の `POST /generate/chain` を1件ずつ叩く（API側は無改修）。凍結API契約を壊さない点で望ましい。
- サーバー側にバッチ専用エンドポイントを新設する案は、当面は不要と思われるが、要件を詰める過程で必要性が出てくる可能性もあるため要確認。

### 4.5 CSVマニフェストの形式

- 列定義・文字コード（UTF-8 with BOM か否かなど、Excelでの開きやすさも考慮）・配置場所（音声フォルダ直下か、隣接する別フォルダか）が未確定。**WebView2フロントエンド側との共通仕様にする**という方針だけは決まっているため、フロントエンド側の実装状況・都合も踏まえて次セッションで確定する。
