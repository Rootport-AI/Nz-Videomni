## 1. 背景と動機

Clip Chainタブ（クリップ＝連結される動画の1区間を複数つなげて1本の長い動画にする機能）は現在、クリップ入力欄が8枠すべて常時縦に並んでおり、縦に長く見栄えが悪い。実際に使う本数は毎回2〜3枠程度であることが多く、残りの空欄が画面を圧迫している。

Generateタブの Keyframe images（i2v＝画像から動画を生成する機能のキーフレーム指定欄。5スロット）も同じ問題を抱えている。

デフォルトでは少数の枠だけを表示し、＋ボタンを押すごとに次の枠を開いていくUIに変更したい。あわせて、クリップ連結の上限を「ユーザーが上限をほとんど意識しなくて済む数」へ引き上げたい。

## 2. オーナー確定事項（2026-07-13）

1. **クリップ連結の上限は24に引き上げる。** 当初案の120（1クリップ約240秒×120＝8時間）は、チェーンが不可分の単一ジョブであるリスク（後述§4参照）の指摘を受けて撤回した。
2. **＋ボタンと−ボタンの両方を設ける。** ＋で次の枠を開き、−で最後に開いた枠を閉じる（Clip 2までは閉じない＝最低2枠は常に表示する）。デフォルト表示はClip 2まで。
3. **キーフレームは5枚固定を維持する（上限は変えない）。** UIのみ折りたたみ式にする: デフォルトは1枚目のみ表示し、＋で2〜5枚目を開いていく。
4. **VAEデコード（latent＝VAEでピクセルに戻す前の圧縮データ。それを実際のピクセル映像へ戻す処理）のメモリ挙動の調査を、着手前の必須ステップとする。** オーナー自身のログ観察でも「全クリップぶんのlatentを貯めてから最後にまとめてVAEデコードしている」ように見え（実機ログで `chain VAE decode started` がチェーン全体で1回のみ出ることと整合する）、クリップ数を増やすとVRAM（GPUのメモリ）溢れのリスクがあるとの認識で一致している。

## 3. 技術的裏取り済みの事実（2026-07-13、コード確認済み）

- **クリップ数上限はUIの8枠だけでなく、サーバー側にも存在する。** `GenerateChainRequest.clips` は `min_length=1, max_length=8`（`api/models.py:323`）。チェーン総尺の上限は `MAX_CHAIN_TOTAL_PIXEL_FRAMES = 8 * 481 = 3848`（`api/models.py:201`）。同ファイルのコメント（`api/models.py:196-201`）には、この上限は「安全上限（sanity ceiling）」であり、「8クリップ×481フレーム（最大クリップ数×クリップ単体の凍結上限）」という積で決めた数値であって、UIが無制限の尺を要求できないようにするための天井だと明記されている。**これはLTX 2.3本体の仕様値ではなく、本バックエンド独自の上限**である（LTX側にそもそも「チェーン」という概念は無く、LTX由来の凍結上限は1クリップあたり481フレームのみ）。`config.yaml` には総尺の設定項目は無く、コード内定数（`api/models.py`）のみで管理されている。
- **同コメントには「stage-2（全体の高解像度化・仕上げ段階）は常にタイル処理〔always-tiled〕でデコードするため、単一クリップの481フレーム上限には縛られず、タイル化によってどんな長さでもVRAM使用量はほぼ一定に保たれる」という趣旨の記述がある。** これは§4の調査対象そのものに関わる手がかりであり、着手前調査で実装（`engine/pipeline/chain_pipeline.py`等）の実際の挙動と照らし合わせて確認すること。コメントの記述と、オーナーが観察した「全クリップぶんのlatentを貯めてから最後にまとめてデコードしている」ように見えるログ挙動が両立するのか（＝1回でまとめてデコードするが内部はタイル分割されているためVRAMは一定、という可能性）、それとも記述と実態がずれているのかは、まだ確認できていない。
- **GUIは8枠のうちUseチェックがオンの枠だけを抽出して `clips` 配列（単純なJSON配列。配列長＝クリップ数）を組み立てて送信する**（`gradio_ui/handlers.py:804-814`）。クリップ数に依存する特殊な通信仕様は無く、動的UI化（枠数の可変表示）はサーバーAPI無改修で実現できる。
- **動的UIの実装方式は「全枠をあらかじめ生成して `visible=False` で隠しておき、＋ボタンで `gr.update(visible=True)` にする」可視性切り替え方式を推奨する。** 既存の前例として、Clip ChainタブのV2Vパネル（`v2v_group`）が同じ手法で実装されている（`gradio_ui/ui.py:659` で `gr.Group(visible=False)` として定義し、`gradio_ui/ui.py:1552-1558` の `on_chain_mode_change` で `gr.update(visible=is_v2v)` により切り替える）。Gradio 6.19には `gr.render`（要素を動的に再生成する仕組み）も存在するが、再生成のたびにイベント配線（`.click` や `.change` の紐付け）もやり直しになるため、本UIのような固定枠数の開閉には不向きと判断する。
- **−ボタンの実装上の罠**: 送信対象はUseチェックボックスの状態で決まるため（上記のとおり）、枠を非表示にするだけでは、Useチェックがオンのまま画面上は見えなくなったクリップの内容が送信されてしまう。−ボタンは「枠の非表示化」と「そのスロットのUseチェックをオフにする」を必ずセットで行うこと。入力済みのテキストや画像は消さない非破壊方式にする（＋で再度開けば内容がそのまま残っている）。
- **キーフレーム上限5の定義箇所**: `config.yaml` の `limits.max_conditioning_images: 5` と、APIバリデーション側の `api/models.py:146-147`（単発 `GenerateRequest`）・`api/models.py:444-447`（チェーンの各クリップ）。**いずれも `5` のリテラル直書きであり、`config.yaml` の値は実際には参照されていない**（コード上の数値が正）。仮に上限を変更するならAPI側2箇所の修正が必要になるが、今回のスコープでは上限自体は変えない。
- **GUIのジョブ監視（ポーリング）タイムアウトの既定値は3600秒。** 24クリップ（総尺次第では生成に数時間かかりうる）を回す場合、このタイムアウト値が実運用に十分かは要確認事項として残る。

## 4. リスクと着手手順（合意済み）

### リスク

- チェーンは**不可分の単一ジョブ**であり、実行中に安全に中断する手段が無い（Phase 1からの既知の制約）。電源断が起きれば実行中のジョブは全ロストする。
- GUIのジョブ監視タイムアウトの既定値は3600秒（上記§3参照）。24クリップの長尺チェーンでこの値が妥当かは未検証。
- VAEデコード時にメモリ蓄積がチェーンの総尺に比例して増える可能性がある（現行の `MAX_CHAIN_TOTAL_PIXEL_FRAMES = 3848` という上限自体が、実はこのメモリ制約を暗黙に反映した数値である可能性も否定できない）。

### 着手手順

1. **手順1**: エンジン側のデコード処理をコード読解で確定する。具体的には、全クリップぶんのlatentをまとめて一括デコードしているのか、時間方向に分割して逐次デコードしているのか。また、デコード後のピクセルフレームはRAM上に全量蓄積されるのか、それとも都度ディスクへ書き出されるのか。§3で触れた「stage-2は常にタイル処理」というコメントの実態を、この読解で裏取りする。
2. **手順2**: 手順1の結果をもとに総尺上限を決定する。24クリップ×481フレーム＝11544まで引き上げて安全か、それとも24クリップは許すが総尺は控えめに抑えるべきか、を判断する。変更が必要になる箇所は `MAX_CHAIN_TOTAL_PIXEL_FRAMES`（`api/models.py:201`）と `max_length=8`（`api/models.py:323`）の両方、および対応するUI側の枠数上限。
3. **手順3**: 実測が必要な場合、「短いクリップ×24本」を1回通しで実行すれば、最悪ケースのVRAM/RAM使用量を安価に確認できる。
4. **手順4**: UI実装に着手する（可視性切り替え方式による±ボタン、キーフレームの折りたたみ表示）。

### 遠い将来の構想（今回のスコープ外）

120クリップ級の長尺チェーンをやるとすれば、固定枠の拡張という方式ではなく、バッチA2V機能（[`BATCH_A2V_WORKORDER.md`](BATCH_A2V_WORKORDER.md)）と同様の「表＋State方式のUI＋区間分割生成して繋ぐ再開可能な仕組み」として、別途の設計課題で扱うべきものと位置付ける。
