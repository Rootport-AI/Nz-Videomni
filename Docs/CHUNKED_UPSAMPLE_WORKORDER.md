## 実装完了の要約（2026-07-14）

### 1. 手順1（裏取り）の結果 — 2026-07-14完了

- アップサンプラーの内部は3次元畳み込み（カーネル3）18層＋GroupNorm（グループ正規化＝数値のばらつきを整える層）17箇所＋フレーム独立の空間2倍部で、時間方向の受容野（1つの出力を計算するのに参照する入力の範囲）は片側18フレームと確定した。
- ワークオーダー原案の「stage-2タイル方式（オーバーラップ4＋ブレンド）の流用」は棄却した。代わりに「halo（のりしろ＝チャンクの前後に付ける余分なフレーム）18フレーム＋切り捨て」方式を採用した。理由は、halo18なら畳み込み部分が一括処理と数学的に厳密一致するためである（GPU実験でfp32の差ゼロを実測。halo17では境界が破綻した）。
- チャンク化で結果が変わる唯一の要素はGroupNormの統計量（テンソル全体の平均・分散）である。GPU実験の結果、チャンクごとの統計のままでも境界の段差は出ないと確認した（シーンの切り替わりをチャンク境界に一致させた最悪ケースを本番解像度で実測し、境界の跳ねはチャンク内部の自然な揺らぎ以下だった）。統計を全体で共有する強化案（B+）は、実機の目視で万一継ぎ目が見えた場合の予備として設計のみ保持する。

### 2. 小実験の主要な発見 — 2026-07-14

- 現行の一括アップサンプルのメモリ爆発の主因は、チャンク化以前の問題として、Conv3d（3次元畳み込み）が既定のメモリ配置（NCDHW）でim2col方式の27倍作業バッファを確保する経路に落ちていたことだった。channels_last_3d（テンソルのメモリ配置をチャネル最後に並べ替える最適化）化でメモリ約7.6分の1・速度約6倍（実測）を達成した。ただし配置変更だけでは24クリップ級は収まらず、チャンク化との併用が必須である。
- チャンクごとの torch.cuda.empty_cache()（GPUメモリのキャッシュ解放）が必須である。怠るとメモリ断片化で予約量が19GBに膨れ、共有メモリへのスピルで約4倍低速化し、最悪ネイティブクラッシュする（実験中に実際に発生した）。
- 確定レシピは、チャンク幅32＋halo18＋channels_last_3d＋チャンク毎empty_cache＋入出力のCPU退避である。実測でピークVRAMは総尺に依存せず（F=192/384/768で9.3〜9.8GB）、24クリップ級（約1395 latentフレーム）への外挿はピーク約10.4GB・アップサンプル工程約7分となった。
- 却下した代替案として、時間間引き入力で統計を先取りする方式（sub8）は畳み込みの文脈が壊れて精度が悪化するため不採用とした。

## 1. 背景と動機

Clip Chain拡張（クリップ連結の上限を8→24へ引き上げ・[`CHAIN_UI_EXPANSION_WORKORDER.md`](CHAIN_UI_EXPANSION_WORKORDER.md)）の実機ゲート（2026-07-14）で、768p（1280x768）の長尺チェーンが、GPU専用メモリ（VRAM）から共有GPUメモリ（メインメモリ側）へデータが溢れるスピルを起こし、大幅に低速化することが実測で確定した。24クリップ相当まで直線で外挿すると、専用＋共有の合計需要が約98GBに達し、測定機体の総上限（約48GB）を大幅に超えてハードOOM（メモリ不足でジョブが落ちる）が確実になる。詳しい実測値は [`CHAIN_UI_EXPANSION_WORKORDER.md`](CHAIN_UI_EXPANSION_WORKORDER.md) の「実機ゲート結果（2026-07-14）」節を参照。

その実測でスピルの発生箇所が一箇所に特定された。すなわち、**stage-1（各クリップの下書き生成）が全クリップぶん完了した直後に、連結したタイムライン全体を一括で高解像度化する「アップサンプル処理」**（`engine/pipeline/chain_pipeline.py:728-733` の `upsample_video` 呼び出し）である。この一括アップサンプルは、総尺（動画全体の長さ）に比例して増えるVRAM消費の項のうち最大のものであり、これがスピル・OOMの主因である。

一方、その後の stage-2（全体の仕上げデノイズ＝ノイズ除去による最終的な画質の作り込み）は既に時間タイル（時間方向に分割した処理単位。1タイル22latent）ごとに逐次処理されており、専用VRAMは頭打ちになってスピルが起きていない。**つまり、アップサンプル本体も stage-2 と同じように時間方向へチャンク化（分割して少しずつ処理）できれば、この最大のVRAMピークを削れる見込みがある。** これが本課題である。

なお、320p帯は24クリップでも9.5GBで安全に収まっており、本課題が対象とするのは主に768pの長尺である。安全性は「総尺 × 解像度」の積で決まるという実測の結論を踏まえ、解像度が高く総尺が長いケースを救うことを狙う。

## 3. 技術的な手がかり（次セッションで裏取りすべき点）

以下は着手前調査で実装と照らして裏取りすべき仮説・見込みであり、確定事項ではない。

- **アップサンプラーは空間方向を2倍にし、時間方向は拡大しない。** ただし内部が3D畳み込み（縦・横・時間の3方向にまたがるフィルタ処理）であるため、時間方向にも受容野（1つの出力を計算するのに参照する入力の範囲）を持つ。したがって単純に時間で切って独立に処理すると、チャンクの境界で不連続（シーム＝継ぎ目）が生じる見込みである。**チャンク境界にはオーバーラップ（隣接チャンクを一部重ねて処理する）とブレンド（重なり部分を混ぜて滑らかにつなぐ）が必要になる**と予想する。
- **流用候補**: stage-2 仕上げの既存の時間タイル分割（1タイル22latent、`chain_pipeline.py` のstage-2ループ）は、まさに時間方向の分割＋境界処理を既に行っている実装である。アップサンプルのチャンク化にこの仕組み・パラメータを流用できないか検討すること。
- **配線の見込み**: 新ルートを有効化するには、フラグを API から順に流す配線が必要になる見込みである。具体的には、`GenerateChainRequest`（API入力モデル）へフラグを追加 → サービス層（`services/`）→ エンジン（`engine/pipeline/chain_pipeline.py`）へと渡す経路を通す。**UIはサーバーAPIの無改修では済まない**（従来のClip Chain拡張はAPI無改修で実現できたが、本課題はチェックボックスの状態＝フラグをサーバーへ渡す必要があるため、この点が異なる）。ここは着手前に確認しておくこと。
- **実機ゲートに含めること**: チャンク境界のシーム（継ぎ目）が映像に見えないかの画質検証を、必ずGPU実機の目視ゲートに含めること。数値上メモリが収まっても、継ぎ目が見えては使い物にならない。

## 4. リスクと着手手順

### リスク

- **時間チャンク化による画質劣化（境界シーム）の可能性。** オーバーラップとブレンドで抑える設計にするが、完全に消せる保証はない。実機目視で継ぎ目の有無を必ず確認する。
- **既存経路との出力一致性は、オンオフで厳密には一致しない。** チャンク化ルートは別経路（分割＋ブレンド）であるため、チェックオフ（従来一括）とチェックオン（チャンク化）の出力はバイト単位では一致しない。これは仕様として受容し、両者の等価性テストは行わない（従来経路の非退行のみを担保する）。

### 着手手順

1. **手順1**: §3の技術的な手がかりをコード読解で裏取りする。アップサンプラーの時間方向の受容野の有無、stage-2タイル分割の仕組みの流用可否、API→サービス層→エンジンのフラグ配線経路を確定する。
2. **手順2**: チャンク化ルートを実装する。既存の一括 `upsample_video` 経路（`chain_pipeline.py:728-733`）は温存し、フラグがオンのときだけ分岐する新ルートを追加する。境界のオーバーラップ・ブレンドは stage-2 の時間タイル方式を流用する方針で設計する。
3. **手順3**: UIに「Chunked upsample mode (for VRAM 16GB)」チェックボックスを「Clip list」見出しの上に新設し、その状態をフラグとしてAPIへ配線する（既定オフ）。
4. **手順4**: GPU実機の目視ゲート。768p長尺でスピル・OOMが回避できることの実測（専用/共有GPUメモリのサンプリング）と、チャンク境界のシーム有無の画質確認を行う。既定オフでの従来経路の非退行も確認する。
