## 1. 結論を先に

### 1.1 快適上限の線 — ベースモデル×重みの種別×加速設定の表

**快適上限の線は、ベースモデル（エンジン系統）・transformer の重みの種別・加速設定の組で決まる。** 下の表をベースモデルごとに上から順に見て、条件をすべて満たした最初の行の予算を採る。**どの行にも当てはまらないときは線を引かず、単発生成はレガシー表`spill_free_frames`（解像度ごとの快適上限フレーム数。§付記）へ、連結生成は互換値 40,000（`limits.chain_comfort_token_budget`）へ落ちる**——これは異常ではなく、設計どおりの正常な経路である。

| :--- | :--- | :--- | ---: | ---: | ---: |
| LTX 2.3（`ltx`） | 4bit | 下記5項目がすべてon（「全on構成」） | 42,840 | 345 | 42,240 |
| LTX 2.3（`ltx`） | 8bit | 条件なし | 32,640 | 265 | 32,384 |
| LTX 2.3（`ltx`） | Q6_K | 全on構成 | 43,200 | 353 | 40,832 |
| LTX 2.5（`ltx25`） | 4bit | 条件なし | 46,920 | 377 | 46,376 |
| LTX 2.5（`ltx25`） | 8bit | 条件なし | 38,760 | 313 | 39,424 |

- **正本はマニフェストの `comfort`**（`scripts/manifests/10-ltx23.json`・`20-ltx25.json`。行の種別は `requires.weight_class` に `"4bit"`・`"8bit"`・`"q6k"` で書く）。サーバーは起動時にこれを読み、`GET /config` の `limits.comfort_budgets` として配る。**`config.yaml` では上書きできない**——`limits.comfort_budgets` を書いても無視され、起動時に WARNING が出る。値を動かすときはマニフェストを直し、この表も直す。
- 「1280×768 換算のコマ数」は、単発の予算に収まる最大のコマ数（第1.3節の式）。プリセットの 345／161／81 は LTX 2.3 4bit の線 42,840 に収まる値である（§付記の追記）。
- 画角拡張（Outpainting）の予算は種別で分けない別軸の線で、第9節（`ltx`＝42,240・`ltx25`＝46,080）。

「全on構成」の5項目は次のとおりである。

1. sage attention（`attentionBackend: "sage"`）
2. block_swap_prefetch（`blockSwapPrefetch: true`）
3. keep_resident（`keepResident: true`）
4. fused_gguf_dequant_kernel（`fusedGgufDequantKernel: true`）
5. vae_mode = prune_vaed（`vaeMode: "prune_vaed"`）

**LTX 2.3 の 4bit の既定構成には、意図的に行を置いていない。** 既定構成は素のVAEデコーダ（PrunaVAEDを使わない復元処理）で動くため、復元（デコード）の段で共有GPUメモリへの退避が起き、**快適と非快適の境界がトークン数に対して単調にならない**。境界は復元のかたまり（チャンク）の数がちょうど1段増える点（7→8・4→5・2→3）と一致しており、しかも境界付近の判定は同じ条件で走らせても実行のたびに変わる（非決定的）。**ただし3つの段のうち1080pの4→5（161→169フレーム）だけは、段差の点そのもの（169フレーム）が2回の実行で快適・非快適に割れたため、720p（273→289）・1440p（81→89）のように段差と境界がぴったり重なるとは言い切れない**（第4.8節）。**1本の線では表せないので、この構成では`spill_free_frames`へ落とすのが正しい。** ここへ「加速設定の条件が無い 4bit の行」を足してはならない——足せば、退避が起きる領域まで快適と表示してしまう。現象そのものの解明は研究課題として第8節に残した。LTX 2.3 の Q6_K の既定構成も行を持たず、同じく`spill_free_frames`へ落ちる（第1.4節の留保）。LTX 2.3 の 8bit は全on構成と既定構成が同じ段だった（第16.5節）ので、条件なしの行にしてある。

### 1.2 使っている式

生成1本が扱う注意（アテンション）のトークン数は、次の1本の式で決まる。

```
トークン数 N = (幅 ÷ 32) × (高さ ÷ 32) × 潜在フレーム数
潜在フレーム数 = (フレーム数 − 1) ÷ 8 + 1
```

幅と高さの割り算は切り捨てである。映像のVAE（映像を圧縮・伸長する仕組み）が空間方向を32分の1に、時間方向を8分の1に圧縮するため、32×32ピクセルの1区画が1つの潜在位置になり、その潜在位置1つが注意のトークン1つになる。この式自体は全on構成でも既定構成でも変わらない。変わるのは「何トークンまでが快適か」という線の位置だけである。

### 1.3 逆算式（実装で使う向き）

Singleタブのフレーム数スライダーが必要としているのは、表の向きとは逆の「今の解像度なら快適上限は何フレームか」である。式は次の1行で書ける。

```
潜在フレーム数の上限 N_latent_max = floor(その行の単発の予算 ÷ ((幅÷32) × (高さ÷32)))
フレーム数の上限 = 8 × (N_latent_max − 1) + 1     ※8n+1グリッドへ丸め、[9, 481] へ収める
```

**この式は表を持たずに実装できる。** 60行の表をコードへ焼き込む必要はなく、第1.1節で一致した行の単発の予算と現在の幅・高さから毎回計算すればよい。表は人が確かめるための資料であって、実装の入力ではない。

### 1.5 種別の判定

**サーバーが、選択中の transformer のファイルのヘッダを読んで種別を判定し、`GET /models` の `base_models[].transformer_weight_class`（`"4bit"`・`"8bit"`・`"q6k"`・null）で名乗る。** 値が入るのは有効なベースモデルだけで、ほかのベースモデルは null である。クライアント（操作パネル・Gradio）は、種別が分かればそれを照合の材料 `weight_class` に加え、分からなければ加えない。

- **safetensors**: `sft_quant_format.inspect` が読む量子化方式の層数の多数派。8bit の方式（fp8・fp8_scaled・int8・int8_convrot）の層数と w4a8 の層数を比べ、多いほうを採る。**同数なら 8bit**。REDGraft LTX 2.5（int8_convrot 831 層＋w4a8 513 層）は 8bit になる。
- **GGUF**: `transformer_blocks.<n>.` の 2 次元の `.weight` テンソルの型の多数派。Q4_K なら 4bit、Q6_K なら Q6_K。公式 Q4_K_M は Q6_K・Q5_K の層を含むが、Q4_K が多数なので 4bit になる。
- **判定できないもの**: Q8_0・F16・bf16 の GGUF、量子化を含まない safetensors、読めないファイルは null。null のときは種別つきの行が一致しないので、単発は `spill_free_frames`、連結は 40,000 へ落ちる。落ち先の値そのものは以前と変わらない（Q8_0・bf16 は 4bit より重いので、これは安全側を保証するものではない）。種別を知らない古いクライアントも同じ落ち先へ落ちる。
- **GGUF の `general.file_type` は使えない**——手元の GGUF はどれも同じ値（15）で、種別を見分けられないため、テンソルの型を数えている。

## 2. 表の読み方

> **旧配信値 44,880 での計算表（記録）。現在の値は第1.1節。** 第2〜3節は 2026-10-05 までの線 44,880 で計算した表と、その読み方である（第4節以降の割合の根拠として残す）。

- **フレーム数**: 生成できるフレーム数は8n+1（9・17・25…481）に限られる。下限9は`webui/src/modes/single/defaultConfig.ts`の`MIN_NUM_FRAMES`、上限481は`config.yaml`の`limits.max_num_frames`である。
- **潜在フレーム数**: `(フレーム数 − 1) ÷ 8 + 1`。
- **空間マス目の上限**: `44,880 ÷ 潜在フレーム数`の切り捨て。32ピクセル四方の区画が何個まで許されるかである。
- **総ピクセル数の上限**: 空間マス目の上限 × 1,024（＝32×32）。これは幅×高さの積の上限であって、幅と高さそれぞれの上限ではない。片方を下げればもう片方はこの表の目安解像度より大きくできる。
- **16:9に近い目安の解像度**: 総ピクセル数の上限を16対9の比で分け、幅・高さともに64の倍数へ切り捨てた組である（生成サイズは必ず64の倍数という契約による）。切り捨てのぶん、実トークン数は44,880をやや下回ることが多い。
- **その解像度の実トークン数／予算に対する割合**: 64の倍数へ切り捨てる都合で90〜100パーセントの範囲でばらつく。
- 幅・高さの本体上限は4,096である（`config.yaml`の`limits.max_width` / `max_height`）。フレーム数が少ない側の数行は、トークンの予算より先にこの4,096が効く。該当行には注記を入れた。

**表の性格について**: 各行は「トークン数 ≤ 44,880」という1本の式から機械的に生成した計算値であり、前版のような「40,000という数値が正しいと仮定した推定」ではない。44,880そのものが実測アンカー（1920×1088・169フレーム）であり、下の第4節のとおり周辺の実測点との整合も確認済みである。ただし60行すべてを個別に実機検証したわけではない点は変わらない——検証されているのは「線の位置」であって「表の全行」ではない。

**行数について**: 9から481まで8刻みで数えると60パターンである（`(481 − 9) ÷ 8 + 1 = 60`）。

## 4. 実測アンカー一覧と検証の経緯

### 4.1 実測条件

すべて全on構成（sage attention・block_swap_prefetch・keep_resident・fused_gguf_dequant_kernel・vae_mode=prune_vaed の5項目すべてon）・シード12345・車のプロンプト・24fpsで統一して測定した。

### 4.2 快適の判定規則

#### 判定規則 v3（2026-08-31・現行）

**快適とは、同じ解像度の基準点と比べて、stage-2（仕上げのノイズ除去）の窓でも復元（デコード）の窓でも、共有GPUメモリの中央値が持続的に +300MB 以上は上がらないことである。** どちらかの窓でこれを超えたら非快適とする。速度低下（トークン当たりの所要時間）とPCIe転送量は、何が起きているかを説明する証拠として「有害／オーガニック」の分類には記録するが、**線の決定には使わない**。

**速度とPCIeを線から外した理由**: 同じだけ共有メモリへ退避していても、その先で実際にスラッシング（本体メモリとGPUの間でのデータの奪い合い）が起きるかどうかは確率的で、走らせるたびには再現しない。2026-08-31 の較正では、復元窓の共有メモリが同程度に高止まりした3点のうち2点だけがPCIe受信の張り付きを示し、残る1点は無症状のままだった。**線は、再現する指標だけで引く。** 詳細は一次記録 `outputs/comfort-calib-2026-08-31/RESULTS.md` 第2節（複写: [`Docs/Outputs-archive/comfort-calib-2026-08-31/RESULTS.md`](Outputs-archive/comfort-calib-2026-08-31/RESULTS.md)）。

#### 判定規則 v2（2026-08-18 時点。第4.3節のアンカーはこの規則で判定した）

「有害」と判定する基準は次の3軸すべてが同時に成立することである。1軸だけでは有害と判定しない。

1. **共有GPUメモリの持続的プラトー**（+0.8〜3GBの範囲で高止まりする）
2. **PCIe持続転送**（`nvidia-smi dmon`のサンプルの過半数が5MB/sを超え、帯域上限27,000MB/s付近まで飽和する挙動が見える）
3. **トークン当たりの所要時間が+20%を超える**

この3軸を分ける理由は、共有メモリへの確保だけなら速度低下を伴わない「オーガニックな溢れ」（後述4.5）と区別する必要があるためである。

#### v2 の出力と v3 の再判定を混同しないこと

**2026-08-31 の較正台が書き出した `manifest.jsonl` と `runs/<ラベル>/run.json` のうち、`verdict` は v1、`verdict_v2` は v2 の出力である。どちらも v3 ではない。** v3 で引き直した判定は `outputs/comfort-calib-2026-08-31/RESULTS.md` の結果表の「v3快適」列が正本で、**両者が食い違う点が実際にある**（同 第3節・第4節）。数値を引くときは必ずどちらの規則の値かを確かめること。

### 4.4 検証の経緯（段階1〜4の要約）

各段階のラベルの並びから読み取れる設計意図は次のとおりである。

- **段階1（初期アンカー確認・A1'/A2'）**: 既定構成時代の実測から引かれていた40,000前後の帯（39,360・40,800）が、全on構成でも変わらず快適であることをまず確かめた段階。ここで「全on構成でも既存の帯の下限は崩れない」ことが分かった。
- **段階2（本探索・境界の追い込み・M1〜M5）**: 1280×768と1920×1088の2解像度でフレーム数を刻みながら、快適→境界域→有害の遷移を追い込んだ段階。M2（1920×1088・169f・44,880）が快適の最上点、M5（1280×768・377f・46,080）が境界域、M3・M4が明確な有害という並びから、快適の上限が44,880付近にあることが確定した。
- **段階3（縦横比・解像度依存性の検証・AR1〜AR4）**: 線がトークン数だけで説明できるか、それとも解像度の形状（横長か縦長か、絶対解像度の高低）に依存するかを確かめた段階。AR1（横長）とAR4（縦長）が同一トークン数・同一判定（快適）になったことで「線の内側では縦横の別なく快適」が支持された一方、AR2（横長・有害）とAR3（縦長・境界域）の比較から「境界近傍では縦長のほうが余裕が薄い」という非対称性も同時に見つかった。
- **段階4（有害判定の確定・U1/U3）**: 3軸の有害判定基準（共有メモリのプラトー・PCIe持続転送・所要時間+20%超）を、複数解像度（1280×768と1920×1088）で明確に有害な条件に対して当てはめ、判定基準そのものが解像度をまたいで一貫することを確認した段階。

### 4.5 オーガニックな溢れ（有害とは別物）

速度低下もPCIe転送も伴わない、共有メモリへの容量予約だけの現象を「オーガニックな溢れ」と呼ぶ。既定構成の720p・321フレームでは約1GBのオーガニックな溢れが観測されている。**全on構成では、この容量予約はPrunaVAED（`vae_mode=prune_vaed`）が確保済みVRAMに残す余裕（reserved−2.6GB）によって吸収され、消滅する。** つまり全on構成のほうが既定構成よりオーガニックな溢れに強いという副次効果があり、これも快適上限が既定構成の40,000から全on構成の44,880へ引き上がった一因である。

### 4.6 既定構成では説明できない逆転が全on構成では起きない

既定構成（全onでない構成）では、トークン数だけで順序が説明できない逆転（39,360トークンで溢れ、40,800トークンで快適）が過去に観測されていた。全on構成のアンカー（4.3節）ではこの種の逆転は再現しておらず、快適・境界域・有害の並びはトークン数の順序どおりに素直に並んでいる。**線44,880が「全on構成限定」で成立するのは、この逆転が起きない条件だからでもある。**

### 4.7 段階1（既定構成時代）のデータ — 歴史的経緯として

全on構成の検証に先立つ既定構成時代の測定（ラベルB・B'・S1・S2・S3）では、共有GPUメモリの使用量がフレーム数・解像度の増加につれて天井へ緩やかに近づいていく勾配が観測されていた。この発見が「共有メモリへのはみ出しは急激な崖ではなく連続的な現象である」という前提を作り、後の40,000という運用上の線の考え方につながっている。

これと並行して、`keep_resident`によるRAMコミット圧（システムメモリの占有率）も全計測を通じて確認されているが、いずれの計測でも95%に達しておらず、ページアウトによる速度低下は顕在化していない。この点は全on構成の検証でも変わっていない。

したがって 44,880 は「ここを1トークンでも超えたら不快になる崖」ではなく、**兆しが出る手前で止めた安全側の線**である。

### 4.9 参照動画つき単発生成の境界（2026-09-04 実測）

**結論は「単発の線をそのまま当ててよい」である。** 参照動画（IC-LoRAの制御アダプタ）を添えた単発生成にも、参照を添えないときと同じ 44,880 トークンの線を引く——**LTX 2.3・LTX 2.5 のどちらでも別の線は要らない。** **一次記録は `outputs/comfort-calib-2026-09-04/RESULTS_comfort-calib-2026-09-04.md`** で、全31計測点の表・参照の符号化が確保するGPUメモリの法則・再走との対比はそちらが正本である（ここには写さない。複写: [`Docs/Outputs-archive/comfort-calib-2026-09-04/`](Outputs-archive/comfort-calib-2026-09-04/)）。較正そのものの記録は[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §94。

**根拠は3つある。**

- **LTX 2.3（全on構成）の境界は [44,160, 47,040) トークンの区間にあり、線 44,880 はその内側である。** 下端 44,160 は 1280×768・361フレームと 1920×1024・177フレームという別々の2つの幾何で一致し、上端 47,040 は再走でも非快適の側に落ちた（判定は第4.2節のv3——同じ幾何の基準点と比べた共有GPUメモリの中央値）。
- **LTX 2.5（サーバー既定）は掃引の上端 47,040 トークンまで一度も反転しなかった。** 線 44,880 はこの系統では保守的に安全な側にある。**ただし「境界が無い」という意味ではない**——上端の点で専有GPUメモリのピークが物理の97パーセントに達しており、掃引を上へ伸ばせば反転する見込みが高い（一次読み）。
- **参照を添えたことによる上乗せは、v3の2つの窓をほとんど動かさない。** 同一の幾何・同一のフレーム数で参照あり／なしを対にして直接引き算すると、差は最大でも +80.3MB（LTX 2.3・1280×768・361フレーム・stage-2の窓）で、判定の閾値 +300MB には遠く及ばない。

**この線を当ててよい範囲（適用条件）**

1. **幅・高さがどちらも128の倍数であること。** 参照動画つきの生成は`api/generate.py`がこれを必須にしており（制御アダプタの倍率2では参照が出力の半分の解像度で扱われるため）、64の倍数でしかない幾何はそもそも422で断られる。上の実測もすべて128倍数の幾何である。
2. **測ったのは倍率2の制御アダプタ（`canny-control`）で、参照の符号化を一括で行う帯である。** 倍率2でも、参照自身の潜在トークン数がしきい値を超えると符号化は自動でタイル化へ切り替わる（正本は[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §101）が、**上の実測点はすべてその内側にあるので、この線はタイル化しない側の振る舞いを写している。** 倍率1のアダプタ（deblur系や、画角拡張が使う`in-outpainting`）は参照の符号化の経路そのものが違い、確保するGPUメモリが参照トークン数に比例しない——**この線の根拠には含まれていない**（振る舞いの違いは `RESULTS_comfort-calib-2026-09-04.md` 第4節）。
3. **画角拡張（Outpainting）はこの線の対象外である。** 別のワークロードであり、予算も別軸で扱う——**第9節（とくに第9.4節）を見よ。**

**判定の物差しについて申し送りが1つある。** v3に参照の符号化の窓を足したv3′でも併せて判定したが、**LTX 2.3 の参照つき単発では符号化の窓が0.41〜3.41秒しかなく、1秒間隔の採取では標本数が足りずに全点で判定不能になった**（LTX 2.5 の同じ窓はさらに短い）。**実際に境界を捉えたのはv3のstage-2の窓のほうである。** 参照の符号化が確保するGPUメモリそのものは、ワーカーの記録が出す区間ピーク（予約）で読める。

**前提条件**: 上の実測は**sysmem fallback（GPUメモリが足りないときにシステムメモリへ自動で退避するNVIDIAの機能）が有効な機体**でのものである。「Prefer No Sysmem Fallback」に設定した機体では退避ではなくメモリ不足で落ちるため、線の意味そのものが変わる（同じ前提は長尺IC-LoRAの較正にも付いている——[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §57.6のG4、[`PENDING_TASKS_CLOSED.md`](PENDING_TASKS_CLOSED.md) §3-77）。

## 5. 縦長の注意

**線の内側（44,880トークン未満で十分な余裕がある領域）では、縦横の別なく快適である。** AR1（横長・2560×1472・89f）とAR4（縦長・768×1280・361f）が同一トークン数（44,160）・同一判定（快適）になったことがその根拠である。

**一方、境界近傍（線のすぐ外側、44,880〜47,000トークン程度の帯）では、縦長のほうが横長より余裕が薄い。** 同じトークン数帯（45,120前後）で比べると、横長のM1は快適、縦長のAR3は境界域（s/tok +19.96%・共有メモリ+330〜390MB）だった。実装上のマーカーは横縦比を区別しない1本の線（44,880）を引く設計になるが、**縦長の解像度をこの線ぎりぎりまで攻めるユーザーには、横長より早めに境界域へ入る可能性がある**ことを踏まえておく必要がある。線そのものを縦横比別に分ける必要はない（線の内側では問題が出ていない）が、境界域の警告文言や余裕の持たせ方を検討する際にはこの非対称性を考慮すべきである。

## 6. 実装への引き渡し事項

1. **マーカーの実装は逆算式1行で足りる。** 第1.3節の式（`N_latent_max = floor(その行の単発の予算 ÷ ((幅÷32)×(高さ÷32)))`、フレーム数へ変換して8n+1グリッドへ丸め）をそのままコードへ落とす。60行の表はここでは不要で、あくまで人が検算するための資料である。
2. **行の選択は「実効の高速化設定をサーバー語彙へ写してから照合する」。** フロントエンド`webui/src/shell/accelerationSettings.ts`の`effectiveAccelerationFields()`が、`effectiveAcceleration()`（keep_residentをblock_swap_prefetchの実効状態で畳み込んだ後の値）を通した設定を、リクエストのフィールド名と同じ語彙（`attention_backend`・`block_swap_prefetch`・`keep_resident`・`fused_gguf_dequant_kernel`・`vae_mode`）へ写す。照合の材料にはもう 1 つ、サーバーが`GET /models`の`base_models[].transformer_weight_class`で名乗る重みの種別が`weight_class`として加わる（分からないときは加えない。第1.5節）。`webui/src/shell/comfortTable.ts`の`resolveComfortRow()`が、その写した値で第1.1節の表を上から順に照合し、全鍵が一致した最初の行を返す。**生の（畳み込み前の）設定値で照合してはならない**——prefetch不可のときに自動offされたkeep_residentを見誤る。**5条件を直接数え上げる判定関数は置かない**（条件はコードではなく表の側にある）。
3. **一致する行が無いときはレガシー表`spill_free_frames`へ落ちる**（連結生成は互換値 40,000 へ）。LTX 2.3 の 4bit と Q6_K で5項目のどれか1つでもoffのとき（＝既定構成を含む）と、重みの種別が分からないときがこれにあたる。LTX 2.3 の 8bit と LTX 2.5 の行は加速設定を条件に持たないので、種別が分かれば必ず一致する。`config.yaml`の`spill_free_frames`（解像度ごとの実測快適上限フレーム数の表、`webui/src/modes/single/spillUtils.ts`の`resolveSpillFreeFrames`が読む）を従来どおり使う。**一致行が無いのは異常ではなく設計どおりの正常系である**（第1.1節）。
4. **予算はエンジン系統ごとの表として配信する（2026-08-31〜）。** バックエンドは`GET /config`の`limits.comfort_budgets`で、第1.1節の表そのもの（エンジン系統ごとの係数と行の並び）を配信する。**表の正本はマニフェスト（`scripts/manifests/*.json`の`comfort`）で、`config.yaml`では上書きできない（2026-10-06〜）。** 行の`requires`はリクエストのフィールド名と同じ語彙に重みの種別`weight_class`を加えて書かれており、フロントエンドは上から順に全鍵一致した最初の行を採る。**将来モデルや高速化トグル、重みの種別が増えても、行を1本足すだけで済む形にしてある。** 旧来の2鍵（`chain_comfort_token_budget`＝40,000／`single_comfort_token_budget`＝44,880）は**互換値として残置**している。単発の 44,880 は表が配信されていないとき（古いサーバー）とエンジン系統が未確定の間だけ使われ、連結の 40,000 は一致する行が無いときの落ち先でもある。

**決着（2026-08-18）＝現在は上記4の表方式へ移行済み**: 当時は別鍵の新設で決着した。`config.py`の`LimitsConfig`へ`single_comfort_token_budget: int = 44880`を独立フィールドとして追加し、`chain_comfort_token_budget`（40,000）とは値も鍵も完全に分離している。`GET /config`の`limits`ブロックへ`model_dump()`経由でそのまま載るため、配信経路の追加配線は不要だった。フロントエンドは`webui/src/modes/single/spillUtils.ts`の`resolveSingleComfortBudget`を通してのみこの値を読み、欠落・不正値のときは同ファイルのミラー定数`SINGLE_COMFORT_TOKEN_BUDGET = 44880`へ落ちる。実装・機械検証の正本はバックエンド`Docs/VERIFICATION_LOG.md`の該当節。**2026-08-31 に配信形が`comfort_budgets`（上記4）へ移り、この2鍵は互換値として残置する扱いになった**——較正と再判定の記録は同 §84。

**1280×768の式値361とM1（369f）の関係**: 逆算式に幅1280・高さ768をそのまま代入すると、`cells = floor(1280/32)*floor(768/32) = 40*24 = 960`、`N_latent_max = floor(44880/960) = 46`、`frames = 8*(46-1)+1 = 361`となる（第3節の表で1280×768が目安解像度として対応する行と一致）。一方、第4節の実測アンカーM1は**同じ1280×768で369フレーム**（潜在47・総トークン`960*47=45,120`）を快適と判定している——**式の出力（361）より1段外側（369）まで実測では快適だった**、という関係にある。これは式が誤っているのではなく、式が**切り捨て（floor）による安全側の丸め**を含むために起きる差である。式は「44,880 ÷ 空間マス目」を潜在フレーム数へ切り捨ててから8n+1グリッドへ変換するため、実際のトークン数が予算をわずかに下回る解像度・フレーム数の組み合わせでは、線ぎりぎりの1段が式の出力から漏れる。M1の実トークン数45,120は44,880をわずかに超えているにもかかわらず実測では快適と判定されており、この点は44,880という線そのものに数百トークン程度の実測誤差・個体差が伴うことを示している——線を「ここを1トークンでも超えたら不快になる崖」ではなく「この付近から先は注意が要る」という目安として扱うべき根拠でもある（第5節「縦長の注意」の非対称性とあわせて、線の位置は常に安全側に引いてある）。マーカーの実装は式の出力（361）をそのまま使い、369まで攻める調整はしない。

2. **復元済みフレームの保持量を数える**（かたまりを書き出すまでに何フレーム分をメモリ上に抱えるか）。
3. **メモリ確保器（アロケータ）の環境変数を変える**（断片化の状態が実行ごとに変わることが非決定性の原因なら、確保器の設定で境界が動きうる）。

### 9.1 採用の根拠（2026-09-05 の再較正）

採る規則は前回と同じである——**反転を観測できたら、境界区間の下端（＝快適側で実測できた最大の値）を線にする**（較正側の呼び名は規則 **R-A**）。**今回は両系統ともこの規則が当たった。**

- **LTX 2.3 ＝ 42,240（据え置き）。** 境界区間は [42,240, 44,160) で、**両端とも2回ずつ走らせ、2回とも同じ側に落ちた。** これは前回の区間 [42,240, 46,080) の部分集合であり、**不確かさが狭まっただけで答えは動いていない**（前回は 44,160 を測っていないので、矛盾ではない）。
- **LTX 2.5 ＝ 46,080。** 境界区間は [46,080, 48,000) で、こちらも**両端2回ずつで判定は割れなかった。** 前回は掃引の上端まで一度も反転せず、境界そのものを掴めていなかったため保守的に 44,880 を据え置いていた。**今回はその1段上で反転を捉えたので、掴めた境界の下端をそのまま採れる。**
- **この境界は画角拡張に固有である。** LTX 2.3 が反転した点と**同じキャンバス・同じコマ数で、画角拡張だけを外した対照**を1本走らせたところ、stage-2 の窓の共有GPUメモリはその対照自身の基準点と変わらなかった（**−17.2MB**。同じ点に画角拡張を付けると **+769.9MB／再走 +847.4MB**）。**したがってこの反転は、キャンバスの大きさの副作用でも、高解像度側の復号の天井（台帳[`PENDING_TASKS.md`](PENDING_TASKS.md) §4-34）でもない。** 画角拡張の予算を単発生成の予算と混ぜてはならないという第9.4節の原則を、実測で裏づけた形である。
- **判定はトークン数に対して単調である。** 両系統とも、反転より下の点はすべて快適側、上の点はすべて退避側に落ちた（LTX 2.5 では退避の深さも基準比 442 → 889 → 1,586MB と単調に悪化する）。**復元のかたまり（チャンク）の段差で説明する仮説は 2026-09-04 の較正で棄却されており**（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §95.4）、今回の実測もそれを覆さない。第1.1節が LTX 2.3 の既定構成の単発生成について書いている非単調性は、このワークロードでは現れていない。

### 9.2 前提（変わったら測り直す）

**上の実測は、Settingsの加速設定を全てonにした構成で測ったものである**（「全on」の中身は系統で違う。定義の正本は本書末尾の付記の1項目目）。

**Edit画面（画角拡張・撮り直し）は、2026-09-05 から生成要求に加速設定を載せる。** それまではこの画面から出たジョブだけが、利用者がSettingsで何を選んでいても常にサーバー既定の構成で走っていた（改修と再較正・画面目視の記録は台帳[`PENDING_TASKS_CLOSED.md`](PENDING_TASKS_CLOSED.md) §3-143）。**いまは利用者が選んだ構成がそのままこの画面のジョブに効くので、線も全on構成で測り直した。**

**したがってこの線は「全on構成の実測値」であって、構成が1つでも違えば線の値は保証されない。** 第1.1節が LTX 2.3 の線を「全on構成」とそれ以外で分けているとおり、この系統の線は構成で動く。

**そのうえで、本節の線には「構成が合わないときに別の線へ落ちる」仕組みが無い。** 単発生成・連結生成のマーカーは、実効の加速設定が第1.1節の表の行と一致しなければレガシー表`spill_free_frames`へ落ちる（第6節の2〜3）。**画角拡張の線はエンジン系統だけで決まる固定線なので、加速を切っている利用者にも全on構成の線がそのまま当たる——つまり楽観側に出る。**

**この帰結は、2026-09-05のオーナー裁定で「このままでよい」と決まった。** 両系統とも固定線のままとし、構成に連動して線を切り替える仕組みは入れない——**実害が小さいため**である（LTX 2.3 は線がそもそも動いておらず、LTX 2.5 の新しい線の位置は、サーバー既定の構成で行った2026-09-04の掃引でも快適だった）。

**ただし、この裁定を一般の設計思想として持ち出してはならない。** 裁定は**エンジン系統ごとの個別判断**であって、「全on構成で測った線は、構成を問わず当ててよい」という原則を立てたものではない。**将来ベースモデルが増えたときは、その系統についてあらためて裁定を仰ぐこと**——ここに前例があるからという理由で引き写さない。裁定の記録は[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §98.11、台帳の記録は[`PENDING_TASKS_CLOSED.md`](PENDING_TASKS_CLOSED.md) §3-143 である。

### 13.2 LTX 2.3 fp8 — 全 on は測り切れず、既定構成では線が大きく下がる

測ったファイルは `sulphur_distil_fp8mixed` です。

- **全 on（線を定義している構成）では、境界を決め切れませんでした。** Windows のコミット（仮想メモリの予約）が停止線の上限比 95% を 2 回超えたので、計画どおりそこで打ち切ったためです（この機体の上限は 113.82 GiB。基準点の 1920×1088・89コマでも 91.0%）。それまでに取れた 2 点は、どちらも 1 回で VRAM 溢れでした——1920×1088・161コマ（42,840・単発の線の 95%）と、連結の 1216×704・窓 w46（38,456・連結の線の 96%）です。
- **代わりにサーバーの既定構成（sdpa・keep_resident なし・prune_vaed なし）で 1920×1088 を降りると、境界は 121コマ（32,640）が 2 回とも快適、129コマ（34,680）が溢れでした。** 現行の線 44,880 の 73〜77% です。**これは線の定義（全 on）とは別の構成での診断です。**
- **溢れはコミットの逼迫の巻き添えではなく、fp8 の transformer そのものによるものです。** 既定構成ではコミットは上限の 85.6% にとどまっていましたが、161コマの溢れ方は全 on とほぼ同じで、どちらも専有 VRAM が 16 GB の天井に張り付いていました。
- **全 on の境界は、既定構成の境界と同じか、それより下にあると読んでいます**（推定です。全 on は速いぶん共有 GPU メモリが上がりやすい側だからで、第10.2節の観察と同じ向きです）。

### 13.3 同じプロセスの対照 — GGUF は同じ条件で快適だった

**同じ日・同じサーバープロセス・同じコード・同じシード・同じ加速設定で、変換器だけを GGUF に替えると、fp8 で溢れた点が快適でした。**

- LTX 2.3 の Sulphur-2 Q6_K: 1920×1088 の 161コマ・169コマ（線上）とも快適（各 1 回）。第11節の結果（線上は快適）と一致しています。同じ 161コマの fp8 は、全 on でも既定構成でも溢れ。
- **fp8 は、変換器に付いて回る一定の VRAM を GGUF より多く使います。** 基準点の torch の割当ピークで、LTX 2.3 は Q6_K より約 +1.2 GiB、LTX 2.5 は公式 GGUF より約 +2.1 GiB でした（点が重くなっても差は同じ）。**LTX 2.3 の増え方は、常駐ブロックの重さの差からの見立て（Q6_K 比 +0.5〜0.6 GiB。[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §117.8）の約 2 倍で、ブロックの重さだけでは説明できません。** 何が上乗せされているのかは測っていません（数値は一次記録の表3）。
