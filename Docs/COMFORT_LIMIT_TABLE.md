# 単発生成の快適上限テーブル（フレーム数ごとの総ピクセル数の上限・実測較正版）

作成: 2026-08-18 / 改訂: 2026-08-24（本体の全面改訂＝フェルミ推定版から実測較正版へ、は2026-08-18。以後、表の値そのものに変更は無い）
性格: **Singleタブのフレーム数スライダーに引く「快適上限」の線を、プリセット解像度単位ではなく1フレーム単位で動かすための下ごしらえ**。前版はこの表を「実測から逆算した式を機械的に適用した推定値」として公開していたが、その後の実測検証で線の値そのものが更新され、かつ線が成立する前提条件（後述の「全on構成」）が判明した。本版は更新後の線で表を再計算したものであり、**表の性格は「フェルミ推定」から「実測較正済みの式による計算値」へ変わった**。

## 1. 結論を先に

### 1.1 快適上限の線 — 44,880トークン（全on構成限定）

**快適上限のトークン線は44,880である。** これはオーナー裁定による確定値（案A＝実測で快適と確認できた最大の共通値）で、実測アンカーのひとつ（1920×1088・169フレーム）がちょうどこの値を刻んでおり、かつ快適と判定されている。つまり44,880は「この値まではまだ快適」という実測点そのものである。

**ただしこの線が成立するのは、次の5項目がすべてonになっている「全on構成」に限られる。**（**本書はエンジン系統 `ltx`＝ベースモデル LTX 2.3 を前提とする。** LTX 2.5 では下記のうち sage attention・`keep_resident`・PrunaVAED が 422 で断られ、残る2項目も無視されるため「全on構成」が成立せず、本書の線は適用されない。**なお 2026-08-23 に LTX 2.5 でもクリップ連結（Chained）・V2V 継続・A2V〔長尺 A2V を含む〕が動くようになったが、連結側の快適上限の線（`chain_comfort_token_budget`＝40,000。§6 の4項目め）は LTX 2.3 での実測に由来するもので、LTX 2.5 では測り直していない。** 連結生成は「LTX 2.3 と同じことが一通りできる」ことを優先して 2.3 の窓の値をそのまま持ち込んでおり、画面に出る線も 2.3 のままである。LTX 2.5 単体の窓の快適上限は約 47,000 トークンという別の実測があるが（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §71）、これはまだ製品の線には反映していない。）

1. sage attention（`attentionBackend: "sage"`）
2. block_swap_prefetch（`blockSwapPrefetch: true`）
3. keep_resident（`keepResident: true`）
4. fused_gguf_dequant_kernel（`fusedGgufDequantKernel: true`）
5. vae_mode = prune_vaed（`vaeMode: "prune_vaed"`）

**この5項目のうち1つでもoffの場合、本表は適用外である。** その場合は既存の`spill_free_frames`テーブル（`config.yaml`の`spill_free_frames`、既定構成時代の実測に基づく解像度別の快適上限フレーム数）が引き続き正である。全on構成と既定構成は別の物理条件であり、線をひとつに混ぜてはならない。

### 1.2 使っている式

生成1本が扱う注意（アテンション）のトークン数は、次の1本の式で決まる。

```
トークン数 N = (幅 ÷ 32) × (高さ ÷ 32) × 潜在フレーム数
潜在フレーム数 = (フレーム数 − 1) ÷ 8 + 1
```

幅と高さの割り算は切り捨てである。映像のVAE（映像を圧縮・伸長する仕組み）が空間方向を32分の1に、時間方向を8分の1に圧縮するため、32×32ピクセルの1区画が1つの潜在位置になり、その潜在位置1つが注意のトークン1つになる。この式自体は全on構成でも既定構成でも変わらない。変わるのは「何トークンまでが快適か」という線の位置だけである。

### 1.3 逆算式（実装で使う向き）

Singleタブのフレーム数スライダーが必要としているのは、表の向きとは逆の「今の解像度なら快適上限は何フレームか」である。式は次の1行で書ける。

```
潜在フレーム数の上限 N_latent_max = floor(44880 ÷ ((幅÷32) × (高さ÷32)))
フレーム数の上限 = 8 × (N_latent_max − 1) + 1     ※8n+1グリッドへ丸め、[9, 481] へ収める
```

**この式は表を持たずに実装できる。** 60行の表をコードへ焼き込む必要はなく、線の値（44,880、全on構成のとき）と現在の幅・高さから毎回計算すればよい。表は人が確かめるための資料であって、実装の入力ではない。

## 2. 表の読み方

- **フレーム数**: 生成できるフレーム数は8n+1（9・17・25…481）に限られる。下限9は`webui/src/modes/single/defaultConfig.ts`の`MIN_NUM_FRAMES`、上限481は`config.yaml`の`limits.max_num_frames`である。
- **潜在フレーム数**: `(フレーム数 − 1) ÷ 8 + 1`。
- **空間マス目の上限**: `44,880 ÷ 潜在フレーム数`の切り捨て。32ピクセル四方の区画が何個まで許されるかである。
- **総ピクセル数の上限**: 空間マス目の上限 × 1,024（＝32×32）。これは幅×高さの積の上限であって、幅と高さそれぞれの上限ではない。片方を下げればもう片方はこの表の目安解像度より大きくできる。
- **16:9に近い目安の解像度**: 総ピクセル数の上限を16対9の比で分け、幅・高さともに64の倍数へ切り捨てた組である（生成サイズは必ず64の倍数という契約による）。切り捨てのぶん、実トークン数は44,880をやや下回ることが多い。
- **その解像度の実トークン数／予算に対する割合**: 64の倍数へ切り捨てる都合で90〜100パーセントの範囲でばらつく。
- 幅・高さの本体上限は4,096である（`config.yaml`の`limits.max_width` / `max_height`）。フレーム数が少ない側の数行は、トークンの予算より先にこの4,096が効く。該当行には注記を入れた。

**表の性格について**: 各行は「トークン数 ≤ 44,880」という1本の式から機械的に生成した計算値であり、前版のような「40,000という数値が正しいと仮定した推定」ではない。44,880そのものが実測アンカー（1920×1088・169フレーム）であり、下の第4節のとおり周辺の実測点との整合も確認済みである。ただし60行すべてを個別に実機検証したわけではない点は変わらない——検証されているのは「線の位置」であって「表の全行」ではない。

**行数について**: 9から481まで8刻みで数えると60パターンである（`(481 − 9) ÷ 8 + 1 = 60`）。

## 4. 実測アンカー一覧と検証の経緯

### 4.1 実測条件

すべて全on構成（sage attention・block_swap_prefetch・keep_resident・fused_gguf_dequant_kernel・vae_mode=prune_vaed の5項目すべてon）・シード12345・車のプロンプト・24fpsで統一して測定した。

### 4.2 有害な溢れの判定基準

「有害」と判定する基準は次の3軸すべてが同時に成立することである。1軸だけでは有害と判定しない。

1. **共有GPUメモリの持続的プラトー**（+0.8〜3GBの範囲で高止まりする）
2. **PCIe持続転送**（`nvidia-smi dmon`のサンプルの過半数が5MB/sを超え、帯域上限27,000MB/s付近まで飽和する挙動が見える）
3. **トークン当たりの所要時間が+20%を超える**

この3軸を分ける理由は、共有メモリへの確保だけなら速度低下を伴わない「オーガニックな溢れ」（後述4.5）と区別する必要があるためである。

### 4.4 検証の経緯（段階1〜4の要約）

各段階のラベルの並びから読み取れる設計意図は次のとおりである。

- **段階1（初期アンカー確認・A1'/A2'）**: 既定構成時代の実測から引かれていた40,000前後の帯（39,360・40,800）が、全on構成でも変わらず快適であることをまず確かめた段階。ここで「全on構成でも既存の帯の下限は崩れない」ことが分かった。
- **段階2（本探索・境界の追い込み・M1〜M5）**: 1280×768と1920×1088の2解像度でフレーム数を刻みながら、快適→境界域→有害の遷移を追い込んだ段階。M2（1920×1088・169f・44,880）が快適の最上点、M5（1280×768・377f・46,080）が境界域、M3・M4が明確な有害という並びから、快適の上限が44,880付近にあることが確定した。
- **段階3（縦横比・解像度依存性の検証・AR1〜AR4）**: 線がトークン数だけで説明できるか、それとも解像度の形状（横長か縦長か、絶対解像度の高低）に依存するかを確かめた段階。AR1（横長）とAR4（縦長）が同一トークン数・同一判定（快適）になったことで「線の内側では縦横の別なく快適」が支持された一方、AR2（横長・有害）とAR3（縦長・境界域）の比較から「境界近傍では縦長のほうが余裕が薄い」という非対称性も同時に見つかった。
- **段階4（有害判定の確定・U1/U3）**: 3軸の有害判定基準（共有メモリのプラトー・PCIe持続転送・所要時間+20%超）を、複数解像度（1280×768と1920×1088）で明確に有害な条件に対して当てはめ、判定基準そのものが解像度をまたいで一貫することを確認した段階。

### 4.5 オーガニックな溢れ（有害とは別物）

速度低下もPCIe転送も伴わない、共有メモリへの容量予約だけの現象を「オーガニックな溢れ」と呼ぶ。既定構成の720p・321フレームでは約1GBのオーガニックな溢れが観測されている。**全on構成では、この容量予約はPrunaVAED（`vae_mode=prune_vaed`）が確保済みVRAMに残す余裕（reserved−2.6GB）によって吸収され、消滅する。** つまり全on構成のほうが既定構成よりオーガニックな溢れに強いという副次効果があり、これも快適上限が既定構成の40,000から全on構成の44,880へ引き上がった一因である。

### 4.6 既定構成では説明できない逆転が全on構成では起きない

既定構成（全onでない構成）では、トークン数だけで順序が説明できない逆転（39,360トークンで溢れ、40,800トークンで快適）が過去に観測されていた。全on構成のアンカー（4.3節）ではこの種の逆転は再現しておらず、快適・境界域・有害の並びはトークン数の順序どおりに素直に並んでいる。**線44,880が「全on構成限定」で成立するのは、この逆転が起きない条件だからでもある。**

### 4.7 段階1（既定構成時代）のデータ — 歴史的経緯として

全on構成の検証に先立つ既定構成時代の測定（ラベルB・B'・S1・S2・S3）では、共有GPUメモリの使用量がフレーム数・解像度の増加につれて天井へ緩やかに近づいていく勾配が観測されていた。この発見が「共有メモリへのはみ出しは急激な崖ではなく連続的な現象である」という前提を作り、後の40,000という運用上の線の考え方につながっている。

これと並行して、`keep_resident`によるRAMコミット圧（システムメモリの占有率）も全計測を通じて確認されているが、いずれの計測でも95%に達しておらず、ページアウトによる速度低下は顕在化していない。この点は全on構成の検証でも変わっていない。

## 5. 縦長の注意

**線の内側（44,880トークン未満で十分な余裕がある領域）では、縦横の別なく快適である。** AR1（横長・2560×1472・89f）とAR4（縦長・768×1280・361f）が同一トークン数（44,160）・同一判定（快適）になったことがその根拠である。

**一方、境界近傍（線のすぐ外側、44,880〜47,000トークン程度の帯）では、縦長のほうが横長より余裕が薄い。** 同じトークン数帯（45,120前後）で比べると、横長のM1は快適、縦長のAR3は境界域（s/tok +19.96%・共有メモリ+330〜390MB）だった。実装上のマーカーは横縦比を区別しない1本の線（44,880）を引く設計になるが、**縦長の解像度をこの線ぎりぎりまで攻めるユーザーには、横長より早めに境界域へ入る可能性がある**ことを踏まえておく必要がある。線そのものを縦横比別に分ける必要はない（線の内側では問題が出ていない）が、境界域の警告文言や余裕の持たせ方を検討する際にはこの非対称性を考慮すべきである。

## 6. 実装への引き渡し事項

1. **マーカーの実装は逆算式1行で足りる。** 第1.3節の式（`N_latent_max = floor(44880 ÷ ((幅÷32)×(高さ÷32)))`、フレーム数へ変換して8n+1グリッドへ丸め）をそのままコードへ落とす。60行の表はここでは不要で、あくまで人が検算するための資料である。
2. **全on判定は`effectiveAcceleration`ベースで行う。** フロントエンド`webui/src/shell/accelerationSettings.ts`の`effectiveAcceleration()`（keep_residentをblock_swap_prefetchの実効状態で畳み込んだ後の値）を経由した設定を見て、`attentionBackend === "sage"` かつ `blockSwapPrefetch === true` かつ（畳み込み後の）`keepResident === true` かつ `fusedGgufDequantKernel === true` かつ `vaeMode === "prune_vaed"` の5条件がすべて真であることを確認する。生の（畳み込み前の）設定値で判定すると、prefetch不可時に自動offされたkeep_residentを見誤る恐れがある。
3. **フォールバックは既存の`spill_free_frames`。** 5条件のいずれか1つでもfalseの場合、本表の線（44,880）は適用外であり、`config.yaml`の`spill_free_frames`（解像度ごとの実測快適上限フレーム数テーブル、`webui/src/modes/single/spillUtils.ts`の`resolveSpillFreeFrames`が読む）を従来どおり使う。
4. **配信する予算値の設計判断が必要。** バックエンドが`GET /config`で配信している`chain_comfort_token_budget`（`config.py`の`LimitsConfig.chain_comfort_token_budget`、既定値40,000）は、クリップ連結の仕上げ工程の窓1枚分に対する予算であり、本書の44,880（単発生成・全on構成限定）とは**別の物理条件から出た別の数値**である。同じ鍵で配信して値を出し分けるか、`single_comfort_token_budget`のような別鍵を新設するかは、この文書の範囲を超える設計判断であり、実装プランの中で扱うべき論点として引き渡す。

**決着（2026-08-18）**: 別鍵の新設で決着した。`config.py`の`LimitsConfig`へ`single_comfort_token_budget: int = 44880`を独立フィールドとして追加し、`chain_comfort_token_budget`（40,000）とは値も鍵も完全に分離している。`GET /config`の`limits`ブロックへ`model_dump()`経由でそのまま載るため、配信経路の追加配線は不要だった。フロントエンドは`webui/src/modes/single/spillUtils.ts`の`resolveSingleComfortBudget`を通してのみこの値を読み、欠落・不正値のときは同ファイルのミラー定数`SINGLE_COMFORT_TOKEN_BUDGET = 44880`へ落ちる。実装・機械検証の正本はバックエンド`Docs/VERIFICATION_LOG.md`の該当節。

**1280×768の式値361とM1（369f）の関係**: 逆算式に幅1280・高さ768をそのまま代入すると、`cells = floor(1280/32)*floor(768/32) = 40*24 = 960`、`N_latent_max = floor(44880/960) = 46`、`frames = 8*(46-1)+1 = 361`となる（第3節の表で1280×768が目安解像度として対応する行と一致）。一方、第4節の実測アンカーM1は**同じ1280×768で369フレーム**（潜在47・総トークン`960*47=45,120`）を快適と判定している——**式の出力（361）より1段外側（369）まで実測では快適だった**、という関係にある。これは式が誤っているのではなく、式が**切り捨て（floor）による安全側の丸め**を含むために起きる差である。式は「44,880 ÷ 空間マス目」を潜在フレーム数へ切り捨ててから8n+1グリッドへ変換するため、実際のトークン数が予算をわずかに下回る解像度・フレーム数の組み合わせでは、線ぎりぎりの1段が式の出力から漏れる。M1の実トークン数45,120は44,880をわずかに超えているにもかかわらず実測では快適と判定されており、この点は44,880という線そのものに数百トークン程度の実測誤差・個体差が伴うことを示している——線を「ここを1トークンでも超えたら不快になる崖」ではなく「この付近から先は注意が要る」という目安として扱うべき根拠でもある（第5節「縦長の注意」の非対称性とあわせて、線の位置は常に安全側に引いてある）。マーカーの実装は式の出力（361）をそのまま使い、369まで攻める調整はしない。

## 付記（前提と限界）

- 本書の実測アンカーはすべて全on構成（sage attention・block_swap_prefetch・keep_resident・fused_gguf_dequant_kernel・vae_mode=prune_vaed の5項目すべてon）・シード12345・車のプロンプト・24fpsで統一して測定されたものである。構成が1つでも異なれば線の値は保証されない。
- 表の計算では、幅と高さの割り算の切り捨てを厳密に再現している。実際に選べる解像度は64の倍数なので、目安解像度の実トークン数は44,880をやや下回ることが多い。
- 旧40,000トークン線は既定構成時代の較正であり、全on構成の実測線44,880に置き換わる。ただし既定構成向けのフォールバックとしては`spill_free_frames`が引き続き正であり、40,000という数値そのものが誤りだったわけではない。
- 本表は60行すべてを実機検証したものではない。検証済みなのは第4節のアンカー（線の位置とその周辺の判定）であり、表はその線を式に代入して機械的に生成した計算値である。
