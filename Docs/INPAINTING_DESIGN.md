# 第1部 決まったこと

## 1. 利用者から見た操作の流れ

**マスクはAviUtl2に描かせます。** 利用者はマスクを作る操作も、マスクを見る操作もしません。部分フィルタの枠を合わせるだけです。

1. 描き替えたい区間に**部分フィルタ**を置き、プレビューを見ながら枠を対象に合わせます。動く対象なら、物体追尾（[`OBJECT_TRACKING_DESIGN.md`](OBJECT_TRACKING_DESIGN.md)）で枠を追わせておくこともできますし、中間点（値の時間変化を指定する点）を手で打っても構いません。**追尾したかどうかを本機能は問いません。**
2. タイムラインでその部分フィルタを右クリックし、「🖌 Inpainting: この部分フィルタをマスクに使う」を選びます。操作パネルがEditタブの「Inpainting」サブタブに切り替わります。
3. 描き替えたい動画のリボンを右クリックし、「🎬 Video: この動画をInpaintingする」を選びます。**順序はどちらが先でも構いません。** 2回目の右クリックで1回目の内容が消えることもありません。
4. 画面にカードが2枚揃います。上が**対象動画**、下が**部分フィルタ**です。フレーム数欄には、部分フィルタの長さを生成できる長さへ切り上げた値が入っています（§4）。
5. プロンプト（生成の指示文）を書きます。**空欄でも構いません**——その場合は「まわりに合わせて埋める」動きになります。
6. Generateを押します。**この1回の押下で、マスク動画の描画・アップロード・生成の投入が続けて行われます。** マスクを作るための別のボタンはありません。
7. 窓の位置に**仮オブジェクト**（生成中の場所取り）が置かれます。完成すると仮オブジェクトの文言が「完成」に変わり、ジョブ一覧の🎞（挿入）ボタンか右クリックの挿入で、出来上がった動画に差し替えます（撮り直しと同じ流れ）。**完成動画は対象動画の上の段に重ね置きされます**（元の動画は消えません）。
8. 部分フィルタはタイムラインに残ります。効果を付けたままにしてあれば、その効果はAviUtl2の合成として完成動画にも掛かります——これはAviUtl2の想定どおりの挙動です。

**描き替わるのはマスクの白い領域だけです。** 外側は元の映像が画素単位でそのまま戻ります（§7）。音声も元のままです。

## 2. 責務の分担

**どの層が何を持つかを固定します。** これを崩さないかぎり、画面の項目が増えてもサーバーとの契約は変わりません。

| 層 | 持つもの |
|---|---|
| AviUtl2本体 | 合成結果の描画、オブジェクトの生成と削除、レイヤーの表示制御、元に戻す操作 |
| プラグイン | 右クリック項目2つ、一時オブジェクトの作成と削除、ソロ表示、窓の各フレームの描画、mp4への書き出し、進捗の通知、中止の合図 |
| 操作パネル | カード2枚の表示、フレーム数欄、窓の計算、Generateを止める判断とその文言、マスクのアップロード、席の予約、生成要求の組み立て |
| バックエンドAPI | 要求の検証、窓の切り出し、マスクを使った緑塗り、エンジンへの受け渡し、保存物の記録 |
| エンジン | 二段の生成、フレームごとのマスクによるブレンド、外側の復元、余白の切り落とし、音声の付け直し |

それぞれが**持たないもの**も同じくらい重要です。

- プラグインは**マスクの意味を知りません。** 白黒の絵を作って渡すだけで、どう使われるかには関与しません。アップロードもしません。
- 操作パネルは**マスクを見せません。** 画素にも触れません。
- バックエンドは**マスクを引き伸ばしません。** 解像度が合わなければ断ります（§6）。
- エンジンは**窓を切りません。** 受け取るのは既に窓で切られ、緑で塗られたキャンバスです。

## 3. 操作パネル（Editタブ「Inpainting」サブタブ）

これまで常時無効のモックだったEditタブの「Inpainting」サブタブを、実際に使えるサブタブに昇格させます。

### 3.1 カードは2枚

- **対象動画カード** — サムネイル枠、`幅×高さ · N.N秒` の1行、外す操作（❌）を持ちます。**ファイル選択は置きません**——ディスクから選んだファイルにはリボンもレイヤーもトリムの起点も無く、窓を決められないためです（対象は右クリックからだけ入ります）。それ以外は既存の撮り直し（Retake）の対象動画カードと同じ骨格です。
- **部分フィルタカード** — **レイヤー番号・フレーム範囲・中間点の枚数の3つだけ**を出します。フレーム番号は利用者の見ている1始まりで表示します。**マスクの絵は出しません**（§13）。

右クリックで届いた内容は、画面の外にある保管庫に置きます。**Editタブが作り直されても消えません。** 対象動画を別の動画へ差し替えたときは、アップロードをやり直します。

### 3.2 フレーム数欄と快適上限マーカー

**単発生成（Single）と同じ部品を使います。** スライダーと数値欄の対で、範囲は9〜481フレーム、刻みは「8の倍数＋1」です。

- 部分フィルタが届いた時点で、**その長さを「8の倍数＋1」へ切り上げた値**を初期値に入れます（481を超える場合は481で止めます）。
- **快適上限マーカー**（そのあたりから生成が重くなる、という目安の線）は、画角拡張（Outpainting）と同じ配信値を、いまのキャンバス寸で引き直して出します。**これは助言であって、Generateを止めません**（§22）。

### 3.3 Generateを止める理由

**止める理由は次のとおりです。** 文言は理由の符号ごとに用意し、画面のボタンの近くに出します。

| 理由 | いつ |
|---|---|
| 部分フィルタが無い | 右クリックで部分フィルタがまだ届いていない、または生成の直前に探し直して見つからない |
| 対象動画が無い | 動画の右クリックで対象がまだ入っていない |
| 対象動画を送っている最中 | アップロードが終わっていない |
| 対象動画を送れなかった | アップロードの失敗、またはリボン範囲の切り出しの失敗 |
| 対象動画の寸法が読めない | 素材の解像度が分からないと、一致検査も余白の計算もできない |
| **解像度が一致しない** | 下記の専用文言を出す |
| 窓が置けない | フレーム数の窓がリボンに収まらない（§4） |
| マスクを描いている最中 | 二重に押させない |
| サーバーが他のジョブで塞がっている | 既存の同時1ジョブの規律をそのまま適用する |

**解像度が一致しないときの文言は次のとおりです**（数字は実測値を差し込みます）。

> 部分フィルタの解像度（＝プロジェクトの解像度）と対象動画の解像度を一致させてください。（※部分フィルタ＝1920*1088px、対象動画＝1280*768pxで不一致）

**幅・高さのスライダーは置きません。** 出力の解像度は対象動画の解像度で決まります（§14）。

**窓が部分フィルタより短いときは止めません。** 代わりに「窓の外にはみ出した部分のマスクは描き替えられません」という注意文を出します（§4）。

### 3.4 注意文は4行

カードの下に、常に次の4行を置きます。上の2行は段0のスパイクで実測した性質から来ています（§15）。

- **部分フィルタは被写体の全体（脚や足の先まで）を、影・反射・接地面も含めて広めに覆ってください。** 一部が枠の外に残ると、その文脈に引きずられて「同じ種類のもの」が描き替わります。
- **消したいときは「空の芝生」のように、代わりに描くものを肯定形で書いてください。** 「人はいない」のような否定の指示は効きません。まわりの文脈が求める「何か」が必ず描かれます。
- **マスクの外に既にあるものをプロンプトに書くと、マスクの中にも同じものが描かれて複製になることがあります。**
- **部分フィルタの「ぼかし」は効きません**（境界のなじみはサーバー側が付けます。§23）。

### 3.5 のりしろのモック

**時間軸の「のりしろ」は第1弾では動きません**（§17）。ただし、後から足す場所を画面に見せておくため、**操作できない灰色の見本**として次を置きます。文面は原文どおりです。

```
### 時間軸の「のりしろ」の有無

〇あり ◎なし
のりしろのフレーム数 [ ]

物体除去などの用途では「なし」、物体の色変えなどの用途では「あり」を推奨します。のりしろ「あり」の場合、Inpaintする区間よりも前の動画と自然に繋がります（その代わり、物体が消えづらくなります）
```

ラジオボタンは横並び、既定は「なし」、数値欄を含めて**すべて操作できません。**

### 3.6 進捗

- マスクを描いているあいだは「`123 / 240 フレーム`」の形の1行を出します。通知は200ミリ秒ごとに間引き、**最初と最後は必ず届きます。**
- マスクが送られて生成が始まったあとは、既存のジョブ進捗の仕組みにそのまま乗ります。この区画に専用の表示は足しません。

### 3.7 エラーの文言

| 符号 | 画面に出すこと |
|---|---|
| `MASK_SEED_INVALID` | 「部分フィルタが見つかりません。もう一度右クリックしてください。」 |
| `MASK_BUSY` | 「追尾かマスクの描画が実行中です。」——これは失敗ではなく断りなので、失敗の見出しは付けません |
| `MASK_FAILED` | 「マスクを作れませんでした。もう一度お試しください。」（原文のメッセージはプラグインのログにだけ残ります） |

生成そのものの失敗（422の各符号）は、既存の生成エラーの表示経路に乗せます。

## 4. 窓の規則

**窓とは、対象動画のうち実際に生成へ送る区間のことです。**

- **窓の起点は部分フィルタの開始フレームです。** 長さはフレーム数欄の値そのものです。長さの定義をここ1箇所に置き、二重にしません。
- **窓の尻尾がリボンの外へはみ出すときは、頭側へずらします。** それでも収まらなければ生成できません（§3.3）。
- **窓が部分フィルタより短いときは、注意文を出したうえで進めます。** 窓の外に出た区間のマスクは、そもそも生成の対象になりません。
- **窓が部分フィルタより長いときも進めます。** 部分フィルタの無いフレームのマスクは全面が黒（描き替えなし）になり、その区間は元の映像がそのまま戻ります。
- **長さの上限は481フレーム**です。単発生成のAPI上限と同じ値で、本機能のために新しい上限は作りません（§22）。
- **操作パネルは対象動画のリボンの範囲をそのままアップロードし、窓の切り出しはサーバーが行います。** 窓は「開始秒」と「フレーム数」の2つの値だけで指定します（§7.1。撮り直しと同じ規約）。
- **窓の開始位置は、対象動画の素材の時間軸の秒で渡します。** タイムラインのリボンが素材の途中から始まっている場合は、その切り出し起点を差し引いた値です。

## 5. マスク動画の作り方（プラグイン側）

**マスクはAviUtl2本体に描かせます**（§12）。プラグインは一時的なオブジェクトを2つ置き、その2つだけを表示して窓の各フレームを描き、mp4（動画ファイルの形式）へ焼き、後片付けをします。

### 5.1 呼び出しは1本

**`timeline.renderMaskVideo`**（非同期）です。

| 項目 | 内容 |
|---|---|
| 引数 | `{ layer, frameStart, frameEnd, windowStart, windowEnd }`。すべてAviUtl2の絶対フレーム番号で、両端を含みます。窓は部分フィルタと重なっていればよく、部分フィルタより短くても長くても構いません（§4）。窓の長さは4096フレームが上限です |
| 戻り値 | `{ filePath, width, height, frameCount }` |
| 進捗イベント | `timeline.maskProgress` — `{ frame, index, total }`。200ミリ秒の間引き、最初と最後は必ず送ります |
| エラー | `BAD_REQUEST` / `NO_EDIT_HANDLE` / `MASK_BUSY` / `MASK_SEED_INVALID` / `MASK_FAILED` |

**停止用の呼び出しは作りません**（§18）。AviUtl2を閉じたときの中止の合図だけを内部のフラグで持ちます。

### 5.2 一時オブジェクトは2つ

空いているレイヤーに、**必ず `layer_max+1` → `layer_max+2` の順**で2つ作ります。`layer_max+1` 以降が空いていることは定義上保証され、そこへの作成でレイヤーが自動確保されることは実機で確定しています（[`SDK_REFERENCE.md`](../AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/Docs/SDK_REFERENCE.md) §16(d)）。`+2` は保証の外なので、作成後に実尺を読み直して検証し、片方でも失敗したら同じ編集区間の中で作った側を消して失敗にします。

- **黒い背景** — シーンと同じ寸法の**真っ黒なPNG画像**（画像ファイルの形式）を書き出して置きます（§19）。範囲は窓の全体です。PNGはシーン寸ごとに1枚だけ作り、以後は使い回します。
- **部分フィルタの複製＋白化効果** — 元の部分フィルタのエイリアス（オブジェクトの設定を文字列で表したもの）から**最初の効果ブロックだけを残し**（§20）、その後ろに「枠の内側を白くする効果」のブロックを1つ足したものを置きます。範囲は部分フィルタ自身の範囲で、窓からはみ出す分は窓の長さで切ります。切ったときは、窓の内側に残る中間点をそのまま保ち、末尾には直前の値を繰り返す境界を1つ足します（中間点が疎な手打ちの部分フィルタでは、窓の末尾の区間で枠の動きが止まります。追尾で毎フレームに中間点が打たれていれば影響はありません）。

**どちらを `layer_max+1` に置くかは【実機採取待ち】です。** 部分フィルタは自分より番号の小さいレイヤーの合成結果に掛かるため、**背景は複製より小さい番号に要る**——この上下関係を実機の目視で確かめてから、番号を固定します。

**白化効果の効果名と項目名は【実機採取待ち】です。** 部分フィルタの中に「反転」を足して「輝度反転」をオンにすると、枠の内側が白・外側が黒になる見込みで、これが成り立たない場合は「単色化（白）」で同じことを試します。採取した原文は [`SDK_REFERENCE.md`](../AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/Docs/SDK_REFERENCE.md) §16 へ転記し、**プラグインのバイト定数とテストの期待値の唯一の一次資料**にします。

### 5.3 種の検証・ソロ表示・描画

1. **種の検証** — 指定されたレイヤーと開始フレームのオブジェクトを読み、開始フレームが一致し、かつ先頭の効果名が「部分フィルタ」であることを確かめます。違えば `MASK_SEED_INVALID` で戻します。**生成の直前にここで探し直すので、利用者が部分フィルタを消していれば止まります。**
2. **エイリアスの正規化** — 複製に渡す前に、`frame=` の並びの全値から先頭の値を引いて**0始まりの相対番号へ直します**（§21）。中間点の並びそのものは保ちます。
3. **ソロ表示** — 一時オブジェクト2つ**以外のすべてのレイヤーを一時的に無効**にし、2つが載るレイヤーは明示的に表示にします。走査の上限は `layer_max+2` まで広げます。出口では必ず元へ戻します。
4. **描画** — 窓の各フレームについて合成結果を描き、RGBA（1画素を赤・緑・青・不透明度の4バイトで表す並び）のままmp4へ書き出します。フレームレートはプロジェクトの値です。描画の実寸がシーン寸と違えば `MASK_FAILED` です。
5. **後片付け** — 位置で引き直したうえで、複製はエイリアスの完全一致、背景はPNGの道筋の一致を確かめてから削除し、レイヤーの表示を戻します。順序は**削除が先、ソロ解除が後**です。

**AviUtl2の終了処理中だけは後片付けを諦めます。** 追尾と同じ判断で、代償として**一時オブジェクトがタイムラインに残ることがあります。** この場合は利用者が削除します。

### 5.4 元に戻す操作は2段

**一時オブジェクトの作成と削除は別々の編集区間に入るため、「元に戻す」の履歴が2件増えます。** 押しても利用者のオブジェクトは壊れません——増えた2件は、既に消えている一時オブジェクトの作成と削除だからです。この2段は仕様として受け入れます。

### 5.5 マスク動画の置き場

`%LOCALAPPDATA%\NzVideomni\masks\` に `mask_<開始>_<枚数>_<時刻印>.mp4` として書きます。**誰も消しません**——切り抜き（cutouts）と同じ扱いです。所在は [`BRIDGE_CONTRACT.md`](../AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/Docs/BRIDGE_CONTRACT.md) の一時ファイルの表に載せます。黒いPNGも同じ場所です。

### 5.6 追尾との相互排他

**追尾とマスク描画は同時に走りません。** どちらもタイムラインの見た目を一時的に変えるためです。片方が走っているあいだにもう片方を呼ぶと、追尾なら `TRACK_BUSY`、マスク描画なら `MASK_BUSY` で断ります。既存の追尾側の契約は変わりません。

### 5.7 右クリックの2項目

オブジェクト右クリックに2項目を足し、16項目から18項目にします。通し番号は [`RIGHTCLICK_REDESIGN_SPEC.md`](../AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/Docs/RIGHTCLICK_REDESIGN_SPEC.md) の **#22・#23** です。

| # | 表示名 | 必須種別 |
|---|---|---|
| #22 | 🖌 Inpainting: この部分フィルタをマスクに使う | 部分フィルタ |
| #23 | 🎬 Video: この動画をInpaintingする | 動画 |

**種別が違うときは、既存の種別不一致の案内文でそのまま断ります。** どちらの項目も仮オブジェクトを置きません——席の予約はGenerateのときに行います。

## 6. API契約

### 6.1 入口は単発生成

**`POST /generate` に `inpaint` ブロックを1つ足します。** 画角拡張（`outpaint`）の隣です。**このブロックが無い要求は、これまでと1バイトも変わりません。** クリップ連結の経路には載せません。

```
inpaint:
  mask_video_id        マスク動画のアップロードID（白＝描き替え）
  window_start_sec     対象動画の素材時間軸での窓の開始秒（0以上）
  blend_dilation_stage1  ブレンドの膨張（0〜15）
  blend_dilation_stage2  同上
```

**操作パネルが送るのは上の2つだけです。** 膨張の2つはサーバー側の既定値を使います（§7.4）。

**`width` と `height` は「キャンバス」の寸法**——素材の寸法を128の倍数へ切り上げた値——です。**余白（右と下）はサーバーが素材の実寸から導き出します**（§16）。素材は常に左上（0,0）に置きます。

### 6.2 検証の規則

**要求の形の検査**（他の検証より先に効きます）

1. 対象動画（`reference_video_id`）が必須。
2. 画角拡張（`outpaint`）とは同時に使えない。
3. キーフレーム画像（`conditioning_images`）とは同時に使えない。
4. 出力の切り抜き（`crop_output`）とは同時に使えない。
5. `width` と `height` はどちらも128の倍数。
6. フレーム数は「8の倍数＋1」（既存の規則をそのまま継承）。

**受付時の検査**（エラーの符号は7本）

| 符号 | 状態番号 | いつ |
|---|---|---|
| `INPAINT_PREPROCESS_CONFLICT` | 422 | 前処理を伴う制御アダプタと併用した |
| `INPAINT_SOURCE_MISMATCH` | 422 | 素材の実寸を128の倍数へ切り上げた値が、要求の `width`/`height` と違う。素材の辺が最小値（256画素）未満のときも同じ |
| `INPAINT_MASK_NOT_FOUND` | 404 | マスクのIDが見つからない |
| `INPAINT_MASK_RESOLUTION_MISMATCH` | 422 | マスクの解像度が素材の実寸と違う（**引き伸ばしません**。§14） |
| `INPAINT_MASK_FRAME_MISMATCH` | 422 | マスクの枚数がフレーム数と違う |
| `INPAINT_WINDOW_OUT_OF_RANGE` | 422 | 窓が素材の中に収まらない |
| `INPAINT_LORA_INVALID` | 422 | 制御アダプタの指定が、前処理の要らない制御系1本という条件から外れている |

フレーム数の上限（481）と、参照解像度の128倍数の検査は、**既存の検証がそのまま効きます。** 新しい予算の項目は作りません。

### 6.3 LTX 2.5 での扱い

**LTX 2.5 は本機能を持ちません。** 断り方は [`MULTI_ENGINE_DESIGN.md`](MULTI_ENGINE_DESIGN.md) §5.6 の仕組みにそのまま乗せます——LTX 2.5 のエンジンアダプタの拒否表に `inpaint` を1行足すだけで、次の3つが自動的に成立します。

1. LTX 2.5 で `inpaint` を送ると 422 `FEATURE_UNSUPPORTED` で断られる。
2. `GET /models` の `unsupported_features` に `inpaint` が並ぶ。
3. 操作パネルがそれを読み、**LTX 2.5 を読み込んでいるあいだ Inpainting サブタブを灰色にする。**

**LTX 2.3 側には何も足しません。** 宣言していない系統は「制限なし」として素通りする、という既定の向きのままです。

## 7. バックエンドの仕組み

**画角拡張（Outpainting）の経路をそのまま土台にします**——In-Outpainting LoRA（**LoRA**＝モデルに後から足す小さな追加学習の重み。**IC-LoRA**＝参照動画や参照画像で生成を制御する種類のLoRA）に、描き替えたい領域を緑一色で塗ったキャンバスを参照として渡し、出来上がった絵を元の映像へラプラシアンピラミッド（絵を粗さの階層に分けて混ぜる手法）でブレンドする、という筋です。この設計は段0のスパイクで確定しました——静止矩形のマスクで、外側の画素は完全に元のまま、継ぎ目は統計的に検出できず、マスク内は文脈に合わせて描き替わりました（判定の数値は §105 が正本）。第二の筋（撮り直しの凍結マスクを空間方向へ広げる案）は走らせていません（§15）。

### 7.1 窓の切り出し

対象動画を `window_start_sec` から `num_frames` 枚だけ切り出し、ジョブの置き場へ書きます。フレーム数を厳密に合わせ、フレームレートが違えば作り直します。**切り出しは撮り直しと同じ設定です。**

### 7.2 緑塗り

**マスクの白い領域を緑一色で塗り潰し、外周に余白の帯を足して、128の倍数のキャンバスにします。** ffmpeg（動画を変換する道具）の**1本のフィルタグラフ**で両方を同時に行います。

- 緑は**別入力として作らず**、元の絵を複製して色を置き換えて作ります。別入力の色板を合成すると色空間の変換で値がずれるためです。
- **マスクは合成の前に二値化します**（明るさ128以上を白、それ未満を黒）。合成が線形なので、動画圧縮で生じた境界の中間の明るさが「半端な緑」になり、脱緑の処理をすり抜けるためです。
- 書き出しは**可逆の符号化**で行います。緑の値が厳密に保たれないと、後段で緑を抜けません。
- **書けた枚数を実測して照合します。** マスクが短いとき最終フレームが繰り返されて枚数だけ揃ってしまう事故を防ぐため、合成は短いほうに合わせて止め、枚数が足りなければ失敗にします。

### 7.3 二段の生成

**stage-1（半分の解像度で描く下絵）と stage-2（全解像度で仕上げる工程）**の2段は、画角拡張とまったく同じ形です。

1. プロンプトを符号化する。
2. 音声を凍結する（元の音声をそのまま持ち回る）。
3. In-Outpainting LoRA を装着する。
4. **stage-1** — 緑のキャンバスを参照として渡し、半分の解像度で描く。
5. 復号し、脱緑して、マスクでブレンドする（下記 §7.4）。
6. 2倍に拡大し、タイルに分けて**VAE**（画像を潜在空間へ圧縮・復元する符号化器）で符号化し直す。
7. **stage-2** — 参照なしで全解像度に仕上げる。
8. 復号し、脱緑して、もう一度ブレンドする。
9. 外側を復元し、余白を切り落とし、音声を付け直す。

**音声凍結・音声の初期化・音声の付け直しの3か所だけ**を画角拡張と共有します。それ以外は本機能側に書きます（§15）。

### 7.4 フレームごとのマスクによるブレンド

**マスクは1枚ではなく、フレームごとに違う絵です。** ブレンドの仕組みを、1枚のマスクに加えて「フレーム数と同じ枚数のマスク」も受け取れるように広げます。**1枚のマスクを渡したときの出力は1バイトも変わりません**——画角拡張は LTX 2.3 でも LTX 2.5 でも同じ仕組みを使っているので、ここが変わると両方の既存出力が動いてしまいます（§9のG10）。

マスクは各段の解像度へ落として使います。**半分の解像度へ落とすときは、面積で縮めてから半分以上を白とみなす多数決**にします。最近傍で間引くと、1画素幅の細い部分が確率的に消えるためです。

**膨張（マスクの縁を外へ広げてから混ぜる量）の既定値は画角拡張と同じ5／2です**（段0のスパイクで確定。実測値は§105が正本）。マスクの外側で描き替わる帯の幅は**仕上げ段（stage-2）の膨張だけ**で決まり、「膨張の段数×長辺÷64」にほぼ一定の18画素を足した幅になります（長辺1280画素・既定2段なら約58画素）。下絵段（stage-1）の膨張は最終の帯幅に残りません——仕上げ段のブレンドが下絵段のにじみをキャンバスで上書きするためです。帯を狭めたいときは仕上げ段の膨張を下げるのが効きます。受け付ける範囲（0〜15）は画角拡張と同じです。

### 7.5 外側の復元と余白の切り落とし

- **外側の復元は最後の1回だけ行います。** 膨張したマスクが完全に0の画素を、窓で切り出した元の映像の画素へ戻します。**混ざり具合が中間の帯には触りません**——そこを戻すと帯の縁に新しい継ぎ目ができるためです。これにより「マスクの外は元のまま」が画素単位で保証されます。
- **余白の切り落としは、8ビット整数の段階で行います。** 素材は左上に置いてあるので、右と下の帯を落とすだけです。切り落としは可逆で、**出力の解像度は対象動画の解像度と一致します。**
- **音声は作り直しません。** 窓で切り出した元の音声をそのまま付け直します。

### 7.6 保存物と記録

- 窓で切り出した動画と、緑で塗ったキャンバスは、**そのジョブの置き場に残します。**
- `metadata.json` に `inpaint` ブロックを書きます。中身は、マスクと素材のID・素材の寸法とフレームレート・窓の開始（秒とフレーム）・書き出した枚数・キャンバスの寸法・膨張の値・音声の有無です。
- あわせて **`mask_proof`** を書きます——復号したマスクの枚数、白い画素の割合、膨張後の割合の3つです。**これはモックには書けない値なので、「本当にマスクを読んで使ったか」の証拠になります。**

### 7.7 モック

実際のモデルを動かさないモック（偽の生成）では、**素材の解像度で絵を描き、全周に目印の緑の枠を付けます。** 幾何の誤りを実バックエンドまで素通りさせないための措置で、画角拡張と同じ理由です。**モックは動画ファイルを開かない**という不変条件を守るため、マスクの形そのものは描きません。

## 8. 保存物と他機能との関係

- **`uploads/` に置くもの**: マスク動画と、対象動画。どちらも一時的に預かった入力素材で、消えても成果物には影響しません（[`STORAGE_POLICY.md`](STORAGE_POLICY.md) §0）。
- **`outputs/{ジョブ}/` に残るもの**: 完成動画、`metadata.json`、**窓で切り出した動画**、**緑で塗ったキャンバス**。後ろの2つは「何を入れたらこれが出たか」を後から確かめるための証拠です。
- **AviUtl2側に残るもの**: マスク動画と黒いPNG（§5.5）。**誰も消しません。**
- **追尾とは同時に走りません**（§5.6）。ただし依存はしていません——追尾していない部分フィルタでもマスクは作れます。
- **MCPサーバー**（外部のAIエージェントから操作するための窓口）**の道具にはしません。** AviUtl2のタイムラインの上でしか意味を持たない操作だからです。
- **チェーン（クリップ連結）には載せません。** 入口は単発生成だけです。

# 第2部 なぜそう決めたか

ここから先は、**一度検討して否決した案を再提案しないための記録**です。実装に着手するだけなら第1部で足ります。

## 11. 追尾とInpaintingを切り離した理由

**「追尾した部分フィルタだけをマスクにできる」という案を否決しました。**

マスクの元になるのは部分フィルタの枠であって、その枠がどうやって置かれたかではありません。追尾で動かした枠も、利用者が手で中間点を打った枠も、止まったままの枠も、マスクから見れば同じです。追尾を前提にすると、**「まず追尾しなければInpaintingできない」という、機能の性質から出てこない順序**を利用者に押しつけることになります。

台帳もこの形になっています——[`PENDING_TASKS.md`](PENDING_TASKS.md) §3-55 がマスク受け渡し契約の正本で、追尾はその**入力元の1つに過ぎません**。逆向きの依存（追尾がマスクを作る）を否決した理由は [`OBJECT_TRACKING_DESIGN.md`](OBJECT_TRACKING_DESIGN.md) にあります。

## 12. マスクをAviUtl2に描かせる理由

**部分フィルタの値を読んで、プラグインが自分でマスクの絵を計算する案を否決しました。**

部分フィルタの枠は、位置・大きさ・縦横比・**角の丸め・ぼかし・マスクの種類（矩形か楕円か）・回転**といった複数の項目の組み合わせで決まります。自前で計算するなら、これらの意味をすべてAviUtl2本体と同じに再現しなければなりません。**しかもその再現は、本体の版が上がるたびに合わせ直す必要があります。**

一方、AviUtl2は合成結果を1枚ずつ描き出せます。黒い背景の上に「枠の内側を白くする」効果を付けた部分フィルタを重ねて描かせれば、**本体自身が計算した枠がそのまま白黒の絵として出てきます。** 再現も追従も要りません。中間点で枠が動いていれば、その動きもそのまま絵に現れます。

**代償は、一時オブジェクトを2つ作って消すことと、「元に戻す」の履歴が2件増えること**（§5.4）です。オーナーの裁定でこの代償を受け入れました。自前計算の保守負担と、本体の挙動との食い違いによる見つけにくい不具合に比べれば、軽いという判断です。

## 13. マスクを見せない理由

**マスク動画をタイムラインや操作パネルに出す案を否決しました。**

利用者から見ると、マスクは**部分フィルタの枠そのもの**です。それはAviUtl2のプレビューに既に映っています。同じものをもう一度、白黒の絵として操作パネルに出しても、新しく分かることがありません。

見せると害のほうが大きくなります。画面に出せば「これを直したい」という要求が自然に生まれますが、**直す場所は部分フィルタの枠であって、マスクの絵ではありません。** 編集できないものを見せるのは、操作できるのに効かない項目を置くのと同じ種類の誤りです。

したがって部分フィルタカードは、レイヤー・フレーム範囲・中間点の枚数という**「どのオブジェクトを使うか」が分かる最小限**にとどめました。

## 14. 解像度を一致させる理由

**マスクや素材を引き伸ばして合わせる案と、プロジェクト全体を書き出してから使う案の、両方を否決しました。**

マスクは部分フィルタの枠を**画素単位で**表した絵です。これを引き伸ばすと、境界の位置が半端にずれます。そのずれは「描き替える領域が少し違う」という形で出るので、**利用者からは原因の分からない不具合に見えます。** しかも引き伸ばしを許すと、どの補間方法で、どちら側を基準にするか、という決めごとが増え、その全部が二値化の前後関係と干渉します。

**プロジェクト全体を書き出して、それを対象動画にする案**も否決しました。これは解像度の一致を自動的に満たしますが、代わりに「AviUtl2でいま組んでいる合成」が入力になってしまいます。利用者が描き替えたいのは**特定の1本の動画素材**であって、他のオブジェクトも重なった合成結果ではありません。書き出しの時間と保存物も増えます。

そこで、**プロジェクトの解像度と対象動画の解像度が違うときは、そもそも始めさせない**ことにしました（オーナーの裁定）。画面には不一致の実数を入れた文言を出すので、利用者は**プロジェクトの設定を直すか、別の素材を選ぶか**をすぐ判断できます。サーバー側にも同じ検査を置き、操作パネルを通らない要求も同じところで止めます。

## 15. 画角拡張経路を土台にした理由

**撮り直し（Retake）の凍結マスクを空間方向へ広げる案を、第二の候補に落としました。**

撮り直しの凍結は**潜在空間**（モデルが絵を圧縮して扱う内部の表現）のボクセル単位で効きます。ここを空間方向へ広げれば、モデルの中で直接「この部分だけ描き替える」を指示できる——構造としては素直です。

しかし当方の実装には次の事情があります。

- **凍結マスクを書き込む口は1か所しかなく**、その1か所は時間方向の窓のために書かれています。空間方向の任意形状を通すには、その関数の前提を広げることになります。
- **潜在空間の粒度は段によって違い**、stage-2 では32画素角、stage-1 は納品換算で64画素角です。台帳 §3-55 の設計メモにある「32画素角のブロック精度に丸まる」は、**この潜在マスク方式を採ったときにだけ当てはまる話**です。本設計が採る画角拡張経路は緑塗りとブレンドがどちらも画素単位なので、**この丸めは起きません。**
- 一方、**画角拡張はもう動いています。** In-Outpainting LoRA を装着し、緑で塗った領域を「ここを描き足せ」とモデルに読ませ、出来上がりをピラミッドでブレンドする経路が、LTX 2.3 でも LTX 2.5 でも実績があります。**外周の帯を内側の矩形に変えるだけ**で成立するなら、新しく発明するものがほとんどありません。

したがって**まず画角拡張経路を試し、成立すれば第二の候補は走らせません。** 成立の判定は最初の実験の数値とオーナーの目視で行い、判定の基準と結果は §105 が正本です。

なお**新しいモジュールを1つ足す形**にし、画角拡張の本体を作り替える形は採りませんでした。共通化すると差し替え点が6か所以上に散り、切り替えのための引数だらけの関数になります。**画角拡張への変更を「音声まわり3か所の純粋な切り出し」に限定すれば、既存の出力が1バイトも変わらないことを機械で確かめられます**（§9のG10）。

## 16. 余白を請求に載せない理由

**要求の中に余白の大きさを持たせる案を否決しました。**

余白（キャンバスと素材の差）は、**素材の実寸から一意に決まります**——素材の寸法を128の倍数へ切り上げた差が、右と下の余白です。これを要求にも書くと、**同じ事実の置き場が2つ**になります。2つあれば必ずずれ、ずれたときは「どちらが正しいか」を決める規則がもう1つ要ります。

サーバーは素材ファイルの実寸を読めます（画角拡張が既に同じ読み方をしています）。したがって**正本は素材ファイルそのもの1つ**にし、要求にはキャンバスの寸法だけを載せ、その寸法が素材と辻褄が合うかを検査する形にしました。

## 17. のりしろを第1弾に入れない理由

**時間軸ののりしろは両刃です。**

のりしろとは、描き替える区間の手前にある元の映像を、生成の条件として少し渡すことです。**繋がりは良くなりますが、その分だけ「元の映像にあったもの」がモデルに伝わります。** 物体を消したい用途では、これは消えにくくなる方向に働きます——のりしろの中に消したい物体が映っているからです。

つまり、のりしろの有無は**用途によって望ましい向きが逆になります。** 一律の既定値が無く、利用者に選ばせる項目になるということです。

第1弾では、まず**「なし」の側だけを正しく作り切ります。** 画面には操作できない灰色の見本を先回りして置き（§3.5）、後から足す場所を示しておきます。文面はオーナーの指定どおりで、既定は「なし」です。

## 18. 停止RPCを作らない理由

**マスクの描画を途中で止めるための呼び出し（RPC＝遠隔手続き呼び出し）を作りませんでした。**

**止めても途中結果に意味がないためです。** マスクは窓の全フレームが揃って初めて使えます。半分だけ描けたマスクは、生成にも、見るのにも使えません。したがって「止める」は必ず「失敗にして捨てる」と同義になり、追尾の停止ボタン——**そこまでの結果を書き戻す**——とは性格が違います。

**画面に停止ボタンを置かないなら、呼び出しも要りません。** 残るのは「AviUtl2が閉じられたときに描画ループを畳む」用途だけで、これは内部のフラグ1つで足ります。**呼び出しを作ると、画面に出さないのに契約だけが存在する**という状態になり、後から読む人を迷わせます。

描画は1フレームずつ進むので、窓が長くても待ち時間は進捗の行で見えます。

## 19. 黒い背景を図形ではなくPNG画像にした理由

**AviUtl2の「図形」オブジェクトで黒い全画面を作る案を否決しました。**

図形オブジェクトをエイリアスで作るには、**図形の項目名と既定値を実機から採取して、バイト列の定数として持つ**必要があります。採取が1つ増えるだけでなく、その定数はAviUtl2本体の版に追随する保守対象になります。

一方、**シーンと同じ寸法の真っ黒なPNGを書き出して、画像ファイルとして置く**なら、採取するものは何もありません。プラグインには既にPNGを書き出す仕組みがあり、画像ファイルからオブジェクトを作る呼び出しも既にあります。ファイルはシーン寸ごとに1枚だけ作って使い回すので、書き出しの費用も1回きりです。

**採取が1件減ったこと自体が主な効果です。** 実機でしか採れない一次資料は、採るのも待つのも費用が高く、少ないほど設計が早く固まります。

## 20. 子効果を落とす理由

**部分フィルタの複製から、2つ目以降の効果ブロックをすべて落とします。**

利用者の部分フィルタには、既にモザイクやぼかしなどの効果が付いていることがあります。**それらを付けたまま複製すると、白くするための効果より先にそれらが掛かり、マスクの絵が白と黒でなくなります。** モザイクの掛かった白、というような絵になれば、二値化の結果は予測できません。

**残すのは最初の効果ブロック——部分フィルタ自身——だけです。** そこに「枠の内側を白くする」効果を1つだけ足します。これで、マスクの絵に影響するのは**枠の形と位置だけ**になります。

**元の部分フィルタには手を触れません。** 落とすのは複製の側だけなので、利用者が付けた効果はタイムラインにそのまま残ります。

## 21. `frame=` を相対へ正規化する理由

**エイリアスの `frame=` の行は、中間点の境界をフレーム番号の並びで持っています。** プラグインが書くときは0始まりの相対番号で、末尾は必ず「長さ−1」です（[`SDK_REFERENCE.md`](../AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/Docs/SDK_REFERENCE.md) §16(h)）。

**問題は読み出す側です。** タイムライン上のオブジェクトからエイリアスを読んだとき、この並びが**タイムラインの絶対番号で返るのか、オブジェクト先頭からの相対番号で返るのか、実績がありません。** 絶対で返るものを相対のつもりで渡せば、複製は数百フレーム先から始まる、あるいは作成に失敗します。

そこで、**読んだ並びの全値から先頭の値を引く**という正規化を1つ挟みます。相対で返っていれば先頭は0なので、引いても何も変わりません。絶対で返っていれば、引くことで相対になります。**どちらでも正しくなります。**

**既存の「先頭と末尾の1組へ潰す」正規化は使いません。** あれは中間点を持たないオブジェクト向けで、通すと枠の動きが消えてしまいます。動く枠を動くまま複製することが本機能の要点なので、中間点の並びは保ちます。

## 22. 長さの上限を481にした理由

**Inpainting専用の長さの上限を新しく作る案を否決しました。**

本設計は単発生成の経路に載るので、**単発生成のAPI上限（481フレーム）がそのまま効きます。** ここに本機能だけの別の上限を足すと、上限の置き場が2つになり、片方だけが動いたときに食い違います。

**快適上限マーカーは助言であって、上限ではありません。** これは「このあたりから生成が重くなる」という目安を線で示すもので、**線を越えても止めない**という契約で運用してきました（画角拡張と同じ配信値を使います）。重いかどうかは機械の性能と設定で変わるので、**押させない理由にはなりません。**

したがって、**硬い上限は481の1つだけ、目安の線は1本だけ**という形にしました。なお、第二の候補（潜在マスク方式）へ落ちた場合は潜在クリップの長さが上限を支配するため、その場合は上限の設計をやり直します（§7）。

## 23. ぼかしが効かない理由

**部分フィルタの「ぼかし」は、マスクとしては効きません。**

マスク受け渡し契約 (c)（[`PENDING_TASKS.md`](PENDING_TASKS.md) §3-55）は、**受信側での二値化**を含んでいます。マスク動画はH.264という非可逆の符号化を通るので、白と黒の境界には圧縮由来の中間の明るさが必ず現れます。これを「半分だけ描き替える」と解釈すると、**圧縮の癖がそのまま描き替えの強さのむらになります。** そこで明るさ128を境に白か黒かへ丸める、という契約にしてあります。

**ぼかしが作る灰色の勾配は、この丸めと区別が付きません。** したがってぼかしを上げても、丸めた結果が少し太るか細るかするだけで、境界がなじむ効果は出ません。

**境界のなじみは、サーバー側が付けます。** マスクの縁を少し外へ広げ、その帯の中でラプラシアンピラミッドのブレンドを掛けるので、**利用者がぼかしで作ろうとしたものは、既に別の場所で作られています。** 二重に掛ける意味はありません。

この事実は画面の注意文にも1行で出します（§3.4）——**操作できるのに効かない項目**を黙って置くと、利用者はそこを調整して直そうとするためです。
