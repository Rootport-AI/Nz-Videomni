## 1. 結論（何をするのか）

1. MiniMax H3 を第 3 のエンジン系統（`h3`）として載せている。**専用の仮想環境 `.venv-engine-h3`・専用のワーカー `engine_h3/worker.py`・専用のアダプタ**を持つ（MULTI_ENGINE_DESIGN §3.3 の「同居できない系統」パターン）。
2. 重みは公式系 FL2VA の**枝刈り（AdaLN の枝を表に畳んだ版）int8 ConvRot** の DiT と、**int8 ConvRot のテキストエンコーダ**、Comfy-Org 配布の映像 VAE と音声 VAE である。int8 の行列積は comfy-kitchen の CUDA 拡張に任せ、CPU オフロードは本製品の block swap と先読みに載せる。VRAM 16GB で動かす。
3. 推論は CFG なし・1 ステップ 1 回の前向き計算で、映像と音声を同じ系列の中で同時にノイズ除去する。ステップ数と shift は要求の項目として API と操作パネルから渡し、ワーカーの引数で受け取る（§9）。
4. ノイズ除去の段には「VRAM 16GB mode」（既定 on）がある。活性化をヘッド群と行の塊に分けて VRAM の山を下げ、共有メモリへの退避を防ぐ（§6.5）。
5. 単発の A2V（音声から映像）は、音声の行を元の音声の潜在に寄せる「行ごとの連続値マスク」で行う（§3.1）。

## 2. オーナー裁定

番号は研究ノート [`MINIMAX_H3_RESEARCH_NOTES.md`](MINIMAX_H3_RESEARCH_NOTES.md) §10 の裁定番号をそのまま使う（ただし本書の裁定 62・63 は研究ノートの 62・63 と別物）。**進め方の裁定（作業の順序・了承の取り方・インストーラの名前など）は同ノート §10 に残してあり、本書には移していない。**

- **裁定 3 【オーナー裁定】**: 最初のタスク範囲は、FL2VA 重み 1 本での T2V（文章から動画）と I2V（画像から動画）の両対応とする。Ref2VA（参照素材からの生成）は後回しである。α版の I2V は先頭フレームだけを受け付ける。
  > **更新（2026-10-19）**: 「α版の I2V は先頭フレームだけ」は台帳 §1-97 で広げた。いまの I2V は、最大 10 枚のキーフレームを 0〜F−1 の任意のフレームに置ける（裁定 56・59、§3）。
- **裁定 6 【オーナー裁定】**: 重みの形式は int8 ConvRot とする。利用者が CivitAI などから落としたファイルをフォルダに置くだけで動かせることを理想とする。理由は、ファインチューンが大量に出回っており、コミュニティの主流が int8 ConvRot だからである。
- **裁定 7 【オーナー裁定】**: 配布は公開リポジトリからの直接ダウンロードとし、再ホストはしない（ライセンスに地域条項があるため）。
- **裁定 8 【オーナー裁定】**: テキストエンコーダは int8 ConvRot を使う。nvfp4 や bf16 は将来の拡張とする。
- **裁定 9 【オーナー裁定】**: 動画の尺は「快適上限を測って決める」方針に揃える。外部ガイドの 1344×768・345 フレームは正式目標にしない。
- **裁定 10 【オーナー裁定】**: LoRA は後回しとする。Turbo LoRA（少ないステップで生成するための蒸留 LoRA）への対応は Style LoRA への対応とほぼ同じ仕組みになるので、Style LoRA に対応するときに一緒に進める。（実装した。§6.6・研究ノート §10 の裁定 62〜73）
- **裁定 11 【オーナー裁定】**: H3 の仮想環境は、torch の版を LTX に揃えなくてよい。comfy-kitchen の CUDA 拡張が効く版を選ぶ。利用者側の条件（ドライバ R580 以上・ディスクの増加）は README に書く。
- **裁定 16 【オーナー裁定】**: int8 の実行は comfy-kitchen の CUDA 拡張に任せる。H3 の仮想環境の torch は、MiniMax H3 を動かすことに最も適した版を選ぶ。本製品はモデルごとに仮想環境を持てる設計なので、既存の torch の版にこだわらない。
- **裁定 17 【オーナー裁定】**: 実装の土台は DiffSynth-Studio（Apache-2.0）、diffusers は数値の正解データ源、ComfyUI（GPL-3.0）は仕様書として読むだけとする。次の 4 点を設計に織り込む。(1) int8 の実行は comfy-kitchen に任せる（既存の読み込み〔呼び出しごとに bf16 へ戻す・groupsize 256 のみ〕はヘッダの判定には使えても、H3 の実行経路には向かない）。(2) attention は DiffSynth の区間ごとの Python ループを使わず、diffusers の「1 リクエストを 1 つの系列に詰めてマスクなしで渡す」形を手本にして書き、本製品に導入済みの SageAttention を効かせる。(3) CPU オフロードは DiffSynth の仕組みではなく、本製品の block swap と先読みを接続する。(4) ローダは「揺れを吸収する」作りで書く（DiffSynth の変換表を出発点に、ComfyUI の判定の振る舞いを仕様として自前で書く）。
- **裁定 18 【オーナー裁定】**: ステップ数と shift は定数の既定値を持ち、ワーカーは引数で受け取る（画面に出すのは裁定 22）。
- **裁定 19 【オーナー裁定】**: α版の I2V は先頭フレームのみとする。末尾キーフレームと中間キーフレームは台帳 §1-97 で扱う。
  > **更新（2026-10-19）**: 台帳 §1-97 で末尾と中間のキーフレームを実装した（裁定 56・57・59〜61、§3）。
- **裁定 22 【オーナー裁定】**: ステップ数と shift（映像・音声）の 3 本のスライダーを、操作パネルと Gradio に出す。既存の CFG スライダーのモックを差し替え、項目名・スライダー本体・数値を 1 行に並べる。既定値と範囲は裁定 24 である。背景は、Turbo を融合した低ステップの配布物が多く、LoRA 未対応でも速く生成できる見込みがあることである。
- **裁定 24 【オーナー裁定】**: ステップ数と shift（映像・音声）の 3 本のスライダーの既定値は **20／12／3**（ステップ数／shift〔映像〕／shift〔音声〕）。範囲は、ステップ数が 1〜50 の整数、shift が映像・音声とも 1〜20（刻みは 0.1）である。
- **裁定 26 【オーナー裁定】**: 常駐（生成のあいだに読んだ重みを次の生成まで捨てずに持つこと）は α版から有りである。本製品の推奨スペックは VRAM 16GB・主メモリ 64GB であり、これに足りない機械への対応は後から考える。常駐の on／off は Settings 画面の「Acceleration／生成の高速化」の区画にある既存のトグル（モデル骨格の常駐）をそのまま使う。
- **裁定 28 【オーナー裁定】**: I2V の先頭画像の VAE 符号化は、分布の平均を使う（サンプルしない）。ComfyUI と DiffSynth も平均を取り、diffusers だけが固定の種でサンプルする。
- **裁定 29 【オーナー裁定】**: サンプラは Euler 固定とし、選択肢は出さない。
- **裁定 30 【オーナー裁定】**: 操作パネルの方針。LTX に固有の機能（IC-LoRA、Edit の Alpha Gen、Chained の Stage-2〔upscale pass〕の clip length など）は H3 では非表示にする。動画生成の基本機能（中間キーフレームの指定、Chained、Inpainting、Outpainting など）は H3 でも将来実装する予定なので、グレーアウトして操作できない状態で配置だけ決めておく。H3 には「Ref2V」（参照素材からの生成）という目玉機能があり、LTX とまったく違う UI が要る。その UI／UX は Ref2V の実装時に考える。
  > **更新（2026-10-19）**: 中間キーフレームは実装済み（裁定 56・59、§3）。
- **裁定 32 【オーナー裁定】**: 常駐の方式。テキストエンコーダは層ごとにファイルから GPU へ直接読む（§4）。理由は、DiT と VAE を常駐させたまま、テキストエンコーダを主メモリへ丸ごと読む方式を取ると、主メモリの山が 64GB 機でもページファイルに溢れ、常駐の目的（速くする）と逆になるからである。直接読みにすれば、テキストエンコーダは主メモリをほぼ使わない。
- **裁定 33 【オーナー裁定】**: 映像 VAE は符号化器と復号器に分けて組み、T2V では符号化器を読まない（§8）。
- **裁定 34 【オーナー裁定】**: 操作パネルの Edit タブは、H3 では 4 つのサブタブ（Retake・Outpainting・Inpainting・Alpha Gen）が全部閉じるため、既存の規則によりタブごと灰色になる。裁定 30 の「グレーアウトして配置だけ決めておく」はこの形で満たす。
- **裁定 35 【オーナー裁定】**: NAG のアコーディオンは H3 では非表示でなく灰色にし、要求に NAG の項目を載せない（非表示にすると、有効にしたまま解除できず全ジョブが 422 になるため）。IC-LoRA の参照動画のアコーディオンは非表示にする。Single の A2V カードとバッチ A2V は H3 では `chain` の行で灰色にする（連結要求そのもののため）。
  > **訂正（2026-10-21）**: 2026-10-18 の目視の所感では、A2V カードとバッチ A2V を非表示にするよう求めていた（[`PENDING_TASKS_CLOSED.md`](PENDING_TASKS_CLOSED.md) 3-242 の ②）。オーナーは 2026-10-21 にこれを取り下げた。A2V（台帳 §1-103）とバッチ A2V を近日実装するので、いま隠してもすぐ戻すことになるためである。灰色のままとする。記録は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §171。
  > **更新（2026-10-25）**: Single の A2V カードは、H3 では単発の `/generate` に送る形で開いた（裁定 74・§3.1）。バッチ A2V は `chain` の行で灰色のままである。
- **裁定 36 【オーナー裁定】**: ライセンスは README に明記する（名称・適用除外地域・取得者の自己責任）。インストーラは取得前に注意文とライセンスの URL を表示するだけで、同意の入力は作らない（§10）。
- **裁定 37 【オーナー裁定】**: README で H3 を「α版」と明示し、できること・できないこと・快適上限が未較正で大きな画角では遅くなること・推奨（VRAM 16GB・主メモリ 64GB）を書く（README §7.6）。
  > **訂正（2026-10-19）**: 「大きな画角では遅くなる」の README の文は、VRAM 16GB mode の実装（台帳 CLOSED 3-240）で現行化した。README では快適上限が未較正であることを残している。記録は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §169。
- **裁定 38 【オーナー裁定】**: GPU 世代の文言は正直に書く。「ドライバ R580 以上・RTX 20 以降（GTX 10 以前は動かない）。確かめたのは RTX 40 だけ。RTX 30・50 は未確認。RTX 20 は int8 が遅い経路になり SageAttention も使えず、動作も未確認」。
  > **訂正（2026-10-18）**: 文言は裁定 43 で更新した（RTX 30 でも確認・RTX 50 は未確認・主メモリ 32GB はページファイル前提で短い生成を確認・推奨 64GB）。現在の文言は §10 と README にある。
- **裁定 41 【オーナー裁定】**: インストーラは `MiniMaxAI/MiniMax-H3` の `LICENSE` も取得して `models/MiniMaxH3/LICENSE` に置く。本製品はモデルを再配布しないが、ライセンスは第三者へ渡すときに写しと NOTICE を求めているので、写しを手元に置く安全側の手当てである。NOTICE は作らない（§10）。

- **裁定 44 【オーナー裁定】**: 名称は「VRAM 16GB mode」。Settings の「Acceleration／生成の高速化」のトグルで、**H3 では既定 on**、off も選べる。Gradio と MCP にも出す。値はジョブごとに毎回送る（§6.5）。
- **裁定 45 【オーナー裁定】**: 切り替えは同じワーカーの中で行う。off は現行の経路に一切触れず（基準の指紋 `0da6111c…` の不変で担保する）、on が新しい経路である。ワーカーや仮想環境は複製しない。
- **裁定 46 【オーナー裁定】**: 数値の約束。目標はビット一致である。門で最終桁の差が出たときは、ブロックごとの最大差がゆらぎ級であることと、オーナーの目視で品質差が無いことの 2 つで採否を決める。
- **裁定 47 【オーナー裁定】**: OOM は、ジョブを失敗させて「解像度かフレーム数を下げるか、VRAM 16GB mode を切る」と案内する（「画角」と書かない）。黙って退避を許す経路は作らない。既知の限界: 割り当て器の上限はこのプロセスの割り当てだけを縛るので、ジョブ中に他のプロセスが VRAM を増やした場合の退避は防げない。
- **裁定 51 【オーナー裁定】**: 分割の単位（ヘッド群・行の塊）と常駐数は、形状だけから決める決定的な規則とする。割り当て器の上限だけは、実行時の値から導いてよい。
- **裁定 53 【オーナー裁定】**: VRAM 16GB mode の数値の差を採用する。sage のヘッド数依存の差（50 ブロック中 2 ブロック・相対差 6.6e-3 以下）は、B-G5 のオーナーの目視で合格した。sdpa はビット一致である（§6.5）。
- **裁定 56 【オーナー裁定】**: キーフレームを置ける位置は、系統の規則表 `RequestRules` の項目（`keyframe_step`・`keyframe_offset`）で系統ごとに決める。全系統に共通の設定値や、系統が分かる前に走るスキーマの検査で位置を丸めることはしない。UI の表 FEATURE_UI（機能ごとの表示・非表示の表）は位置の規則に使い回さない（機能の有無の表と数値の規則は別物である）。H3 は任意のフレームに置ける（§3・§9。仕組みは MULTI_ENGINE_DESIGN §4・§5.2）。
- **裁定 57 【オーナー裁定】**: H3 にはキーフレームの強度が無い。操作パネルでは強度の行を非表示にする（灰色ではない）。記録には「強度が効いていない」と分かる形で残す（1.0 にしない）。仕組みは「強度を省略できるようにし、系統の規則表が既定を書き戻す」で、LTX は 0.8 を書き戻し、H3 は書き戻さずに `null` のまま残す。H3 に強度の値を送った要求は 422 で断る（§8）。
- **裁定 59 【オーナー裁定】**: 中間のキーフレームの画像は、画像読み取り部（vision tower）に渡さず、条件行だけに入れる（§3）。品質が足りなければ、「渡す」を比較の腕として後で検討する。
- **裁定 60 【オーナー裁定】**: 公式のプロンプトの指南にある指示文（「Picture 1 は 0.00 秒、Picture 2 は S.SS 秒に合わせる」の趣旨）は、README で紹介するだけで、製品はプロンプトに入れない。
- **裁定 61 【オーナー裁定】**: T2V と先頭だけの I2V の結果は、キーフレームへの対応で変えない。回帰は基準の指紋で確かめる（§3・§8 の「セルフテスト」）。GPU を使う実測の了承の取り方（進め方の分）は研究ノート §10 にある。

## 3. モデルの正体と推論の形

配布ファイルの実測は研究ノート §13.2 にある。ここでは推論の形だけを書く。

- **規模と構成**: DiT は約 33B パラメータ。隠れ幅 5376・50 ブロック・56 ヘッド×128 次元。このうち約 13B は AdaLN（時刻に応じて各層の変調量を決める枝）で、枝刈り版ではこの枝が表に畳まれている。
- **映像と音声を同時に作る**: 映像と音声（32kHz ステレオ）のトークンを 1 本の系列に詰め、同じ DiT で同時にノイズ除去する。
- **CFG なし【設計】**: モデルはガイダンス蒸留済みで、negative prompt も guidance scale も無い。1 ステップにつき前向き計算は 1 回である。
- **Rectified Flow の Euler**: モデルの出力は「データ方向の速度」v で、`x0 = x + σ·v` と読む（一般の flow-match と符号が逆）。更新は `x_next = x + (σ − σ_next)·v`。N ステップは N 回の評価である。
- **shift は 2 本立て**: σ の列は `base = linspace(1, 0, N+1)[:-1]`、`σ = s·base / (1 + (s−1)·base)` で作る。s は映像用と音声用の 2 つで、同じ添字 i について映像は σ_v[i]、音声は σ_a[i] を使い、出力もそれぞれの列で別々に更新する。モデルに渡す時刻は `t = 1 − σ`（1 が無ノイズ）。
- **フレームと解像度の規約**: 24fps 固定。フレーム数は **17n+5**。潜在フレーム数は `T' = 5n + 2`、音声の潜在数は `A = round(F / 24 × 40)`（例: 124 フレームで T'=37、A=207）。縦横は **32 の倍数**（映像 VAE の 16 倍圧縮とパッチ 2 の積）。モデルの学習上の既定は短辺 768 である（本製品の既定の画角ではない）。
- **系列の並び**: `[ text(L) | cond | audio(2A) | video(T'×(H/32)×(W/32)) ]`。cond は条件付けのキーフレーム行で、T2V では空である。attention は系列全体で全結合（区間ごとの制限もマスクも無い）。token_refiner（テキストだけを整える 2 ブロック）はテキスト行の中に閉じ、時刻にも位置にも依存しないので、ループの前に 1 回だけ計算する。
- **AdaLN の添字**: 各行が使う変調の行は `時刻の番号 × 3 + タグ`（タグは 0＝映像、1＝テキスト、2＝音声）。時刻の番号は、映像・テキスト・音声（と条件行）の時刻を `unique` でまとめた番号である。最終層の添字は時刻の番号だけである。
- **枝刈り版の AdaLN（表の補間）**: 時刻はスカラーなので、「時刻の埋め込み→AdaLN 射影」の写像を格子点の表（`adaln_t_table`、格子数 G・ランク R）に先計算してある。表の引き方は次の式で、SiLU は挟まない（float32）。

  ```text
  pos = clamp(t, 0, 1) × (G − 1)
  i0  = min(floor(pos), G − 2)        … 上端 t=1.0 でも範囲外を読まない
  w   = pos − i0
  e   = lerp(table[i0], table[i0+1], w)
  変調 = adaln_proj.linear(e)
  ```

- **RoPE（位置符号化）**: 3 軸（時間・縦・横）。座標は float64 で作り、角度と cos／sin は float32 で計算する。128 次元のうち先頭 96 次元だけを回す。映像の時間は一様でなく、`5/3 × (1,4,4,4,4)` の周期で進む。
- **I2V のキーフレームの条件行**: 系列の cond の位置に、キーフレーム 1 枚につき `grid = (H/32)×(W/32)` 行の塊を入れる。キーフレームは 0〜F−1 の任意のフレームに置ける（裁定 56。枚数の上限は API の検査で、値は仕様書を見よ）。K 枚なら cond は `K·grid` 行になる。
  - **並べる順**: 画像を `frame_idx` の昇順に並べる（同じ値は無い。並べ方は安定ソート）。条件行の塊も、画像読み取り部への入力もこの順である。先頭＋末尾のジョブでは、公式の入力順（先頭→末尾）と同じになる。
  - **値**: 各画像を映像 VAE の符号化器（f32。§8）で 1 枚ずつ符号化し（分布の平均。裁定 28）、パッチに並べたものを昇順につないで `clean`（`[K·grid, 96]`・f32）を作る。符号化器は 1 ジョブで 1 度だけ組む。条件行は `cond = 0.999·clean + (1 − 0.999)·noise` で、すべて f32 で計算する。`0.999` は定数 `KEYFRAME_NOISE_AUG` である。
  - **乱数の引き順**: ジョブの種から作った CPU の生成器から、**映像の初期乱数 → 音声の初期乱数 → 条件行の乱数**の順に引く。条件行の乱数は `[grid, 96]`（f32）を 1 回だけ引き、K 回繰り返して（`repeat(K, 1)`）全部の塊に同じノイズを使う（DiffSynth・ComfyUI と同じ「全部の条件で同じノイズ」）。全ステップで使い回す。T2V は 3 本目を引かないので、T2V の結果はキーフレームの対応で変わらない。1 枚のときは繰り返しが値を変えないので、先頭だけの I2V の結果も変わらない（裁定 61）。
  - **毎ステップ入れ直す**: 条件行はノイズ除去の状態（映像・音声）に入れず、毎ステップ同じ値を `embed_rows` に渡す。DiT の出力は映像と音声の行だけを返すので、条件行は更新されない。
  - **時刻**: 条件行の時刻は、全部の塊で `max(t_video, 0.999)`（Python の float で求めて f32 の行に入れる）。時刻の番号は `unique` でまとめるので、マスク（§3.1）の無いジョブでは番号は最大 3 つになる。A2V の音声のマスクは音声の行の時刻を置き換えるだけで、V1 は値が 1 つなので 3 つを超えない（実測は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §178 の `m_per_step`）。行ごとに違う値のマスクでは 3 を超えうる（§3.1 の「時刻の番号の数」）。
  - **AdaLN のタグ**: 条件行は映像（0）として扱う。
  - **RoPE の座標**: 縦横は映像の格子と同じである。時間はフレーム n ごとに次の式で決める（`engine_h3/rope.py` の `keyframe_t`。座標は float64。`L` は視覚ブロックを含むテキストの全長、`T'` は潜在フレーム数）。位置は画素のフレーム番号で決まり、潜在フレームの境目に縛られない。
    - n = 0: `t = float(L)`
    - n = F−1: `t = (float(L) + span) − 5/3`。span は、float64 の配列 `np.ones(T') × (5/3)` の k 番目の要素に `(1,4,4,4,4)[k mod 5]` を掛けてから `np.sum()` で足した値である（正解データ〔DiffSynth の写し〕の末尾フレームの式と同じ組み方・同じ順序）。
    - それ以外（中間）: `t = float(L) + (5/3)·n`（ComfyUI と同じく掛け算が先）。比べられる正解データは無い。
    - **F−1 だけ別の式にする理由**: 実数の計算では `L + (5/3)·(F−1)` と同じ値だが、float64 では最後の桁が合わない組がある（総当たりのテストは `tests/test_h3_engine.py`、件数は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §170）。正解データと全桁一致させるため、F−1 は正解データと同じ組み方の式を使う。
  - 進捗の数え方（`encode` の総数）は §8 の「ワーカーのメッセージ」にある。
- **I2V の画像読み取り部（vision tower）とプロンプトの書式**: テキストエンコーダは `Qwen3VLModel`（文章側＋画像読み取り部）を使い、T2V でも I2V でも同じ型で組む（T2V は画像読み取り部を読まない）。
  - **渡す画像の規則**: 画像読み取り部に渡すのは、`frame_idx` が 0 か F−1 の画像だけである。昇順に渡し、ラベルは渡す順に `<Picture 1>`、`<Picture 2>` とする（公式の FL2VA と同じ）。末尾だけのジョブでは、末尾の画像が `<Picture 1>` になる。中間の画像は条件行だけに入り、トークン列を増やさない（裁定 59）。中間だけのジョブは画像読み取り部を読まず、トークン列は T2V と同じ形になる。
  - 渡す画像ごとに次の 1・2 を、全部の画像の後に 3 を、それぞれ**別々にトークン化して ID を連結**する（つなげた文字列をまとめてトークン化すると、`": "` の空白が次の語とくっつくため）。2 枚なら「ラベル 1・塊 1・ラベル 2・塊 2・プロンプト」の順になる。チャットテンプレートは使わない。
    1. `"<Picture i>: "`（i は 1 から。AdaLN のタグは文章＝1）
    2. `<|vision_start|>` ＋ `<|image_pad|>` × N ＋ `<|vision_end|>`（タグは映像＝0）
    3. プロンプト（タグは文章＝1）

  `N` は画像ごとの数で、画像プロセッサが返す格子の積を `merge_size²` で割った値である。画像プロセッサは、渡す画像をまとめて 1 回だけ呼ぶ。キャンバスが 32 の倍数で、画素数がプロセッサの上下限の内なら `N = (H/32)×(W/32)` になる。プロセッサの設定は tokenizer のフォルダの `preprocessor_config.json` に従う。HF の `forward` はそのまま使う（DeepStack〔画像読み取り部の中間層の特徴を文章側の先頭の層へ足す処理〕と画像トークンの 3 軸の位置は、層のループの中で起きるため）。前向きには、画像トークンの位置を示す `mm_token_type_ids` が要る。
- **キーフレームの画像のキャンバスへの合わせ方**: 1 枚ずつ、縦横比を保って**覆うように拡縮し、中央で切り抜く**（補間は PIL の LANCZOS。EXIF の向きを直して RGB にする。H.264 の再圧縮はしない）。切り抜き後の画像を映像 VAE の符号化器に渡し、先頭と末尾の画像は画像読み取り部にも渡す（上の規則）。符号化は ImageNet 方式の正規化・空間タイル（256／重なり 64）を常に使い、1 フレームを複製しない。全部の画像の存在と読めることは、テキストエンコーダを読む**前**に確かめる。

## 3.1 行ごとの連続値マスクと A2V（音声から映像）

**結論**: H3 の A2V〔Audio-to-Video。音声から映像を作る機能〕は、単発の生成に音声を 1 本添え、音声の行を元の音声の潜在に寄せたまま映像を作る。仕組みは「行ごとの連続値マスク」で、エンジンは映像と音声の両方のマスクを持つ（裁定 75）。製品が使うのは音声のマスクだけで、値は全部の音声の潜在で 1 つ、`m = 1 − Strength` である。Strength の既定は 0.5（裁定 76）。本節は式と仕組みの正本である。API の形（`source_audio`・422・`constraints.source_audio`・`metadata.json` の `a2v`）の正本は仕様書 [`Videomni_Backend_Specification.md`](../Videomni_Backend_Specification.md) §6.2、実測と門は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §178 にある。

### 記号

- 流れ（映像か音声）ごとに、いまのステップの σ を σ、次のステップの σ を σ' と書く（§3 の shift は 2 本立てなので、映像は σ_v[i]、音声は σ_a[i]）。ステップを評価するときの σ は常に正である。
- 状態 x はノイズ除去の途中の潜在（f32）。マスクがあってもなくても、いつもどおり純ノイズから始める。
- clean は元の潜在（音声なら、元の波形を符号化した潜在）。
- inject は、残す部分として DiT〔拡散の本体の変換器〕に見せる固定の値。音声は clean そのもの、映像は `0.999·clean + 0.001·noise`（下の「映像の inject」）。
- m は行ごとのマスクの値（0〜1）。0 は「元の潜在に固定」、1 は「いつもどおり作る」。
- v は DiT の出力（データ方向の速度。`x0 = x + σ·v` と読む。§3）。

### 1 ステップの式

1. **DiT への入力**: `x̃ = m·x + (1 − m)·inject`
2. **行の時刻**: m < 1 の行は `t = min(1 − m·σ, 上限)`。上限は映像 0.999、音声 1.0。m = 1 の行は流れの時刻のまま。テキストの行は映像の時刻、条件行（キーフレーム）は今までどおり `max(t_video, 0.999)`。
3. **推定した元の潜在**: `x0̂ = x̃ + σ·(m·v)`
4. **元の潜在との混ぜ合わせ**: `x0_b = m·x0̂ + (1 − m)·clean`
5. **状態の更新**: 状態に使う速度 `v_s = (x0_b − x) / σ` を**式のとおりそのまま計算し**、いつもの Euler の 1 ステップ（`scheduler.py` の `euler_step(x, v_s, σ, σ')`）に渡す。

ループの後に、m = 0 の行だけを clean で置き換える（`torch.where(m == 0, clean, x)`）。計算はすべて f32 である。

- **展開した形は実装に使わない**: 5 を展開すると `v_s = m²·v + (1 − m²)·(clean − x)/σ + m(1 − m)·(inject − clean)/σ` になる。映像では inject と clean が違うので最後の項が残る（音声では消える）。整理した形で書くと映像でこの項を落としやすいので、実装は 1〜5 を順に計算する（計画の敵対的レビューの指摘。記録は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §178）。
- 式の意味は ComfyUI の H3 の仕様（値 m の行を「σ が m·σ の行」として扱う）と同じである。ComfyUI は GPL-3.0 なので、仕様として読んだだけで、コードは写していない（裁定 17）。

### 性質

- **m = 1（作り直す）**: `v_s = v` になり、今までと同じ更新である。全部の値が 1 のマスクは組み立ての時点で作らず（None）、None のときは補助関数が受け取った物をそのまま返す。マスクの無いジョブは新しい演算を 1 つも通らないので、結果は変わらない（作りで保証し、GPU の門 G3-0 で mp4 の一致を確かめた。[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §178）。
- **m = 0（固定）**: DiT は毎ステップ inject（音声は clean）を受け取り、時刻は上限（音声 1.0）になる。状態の更新は `clean + (σ'/σ)(x − clean)` で、DiffSynth の Retake〔一部を元のまま残して作り直す機能〕の `return_to_timestep` と同じ式である。最後の置き換えで clean とビット単位で一致する。
- **0 < m < 1（部分的に固定）**: 最終値は `m·x0̂ + (1 − m)·clean` で、clean に戻り切らない。音声のマスクなら、生成された音声は元の音声から少しずれる。
- RoPE〔位置の回転埋め込み〕の座標は変えない。行の数も増えないので、系列の長さ（快適上限の較正の条件。台帳 §1-95）も変わらない。
- **時刻の番号の数**: マスクのある行の時刻が `unique` の集合に加わる（§3 の AdaLN の添字）。DiT の AdaLN の射影と VRAM 16GB mode の経路は番号の数に依存しない。t = 1.0 でも AdaLN の表は範囲外を読まない（§3 の式の `i0 = min(floor(pos), G − 2)`）。

### 上限・映像の inject・乱数の引き順

- **上限 0.999（映像）と 1.0（音声）** は ComfyUI の定数（`VISUAL_COND_TIMESTEP`／`AUDIO_COND_TIMESTEP`）と同じ値である。DiffSynth の Retake は映像も 1.0 にする。
- **映像の inject**: その行の**初期雑音**（ジョブの種から引いた映像の初期乱数。§3 の乱数の引き順の 1 本目）を使い回して `0.999·clean + 0.001·noise` を作り、ジョブの間ずっと同じ値を使う。ComfyUI と同じ形である（毎ステップ同じ雑音で作る）。DiffSynth の映像の Retake は clean そのもの（雑音を足さない）。どちらを採るかは、映像のマスクを製品に出すとき（台帳 §1-106）に目視で決める（§13）。
- **乱数の引き順は変えない**: 新しい乱数を引かないので、§3 の「映像 → 音声 → 条件行」の順はそのままである。マスクの組み立ては、乱数を引いた後に `_denoise` の中で行う。

### 粒度

- 映像は潜在フレームごと（`[T']`。1 フレームの `grid` 行に同じ値）、音声は潜在ごと（`[A]`。左右のチャンネルで共通）。行の並びは系列と同じで、音声は左チャンネルの A 個の後に右チャンネルの A 個、映像は時間→縦→横である。
- もっと細かくする（映像の 2×2 パッチ単位）には、マスクを `[T', 縦, 横]` で持ってパッチごとの最大値に寄せる処理と、トークン単位の時刻が要る。式は同じである（§12）。

### 実装の置き場

- `engine_h3/denoise_mask.py`（torch だけに依存。CPU で試験できる）: マスクの組み立て（`audio_mask`・`video_mask`。全部 1 なら None）、DiT への入力（`dit_input`）、状態の速度（`state_velocity`）、ループ後の置き換え（`finish`）、行の時刻（`masked_row_times`）。
- `engine_h3/pipeline_h3.py`: `time_rows` がマスクのある流れの行の時刻を受ける（無ければ今までのコードそのもの。条件行の時刻は今までどおり最後に入れる）。`_denoise` は「clean と行ごとの値」の組を受け、乱数を引いた後にマスクを組む。

### 音声の符号化器

H3 の音声 VAE〔音声の圧縮器〕のファイル（`minimax_h3_audio_vae_fp32.safetensors`）には符号化器の重みも入っている。DiffSynth-Studio（Apache-2.0）から移植した（`engine_h3/audio_vae.py` の `H3AudioEncoder`）。

- **構成**: 入力は生の波形（32kHz・1 チャンネル。メルスペクトログラムではない）。DAC 系の畳み込み（`encoder.*`。ストライド 2・4・4・5・5、積が 800＝ホップ長）→ 因果注意〔後ろを見ない注意〕の射影ブロック（`pre_block.*`。幅を 2048 から 32 に絞る）→ 1×1 の畳み込み（`mean_proj`）。ステレオは「バッチ 2 のモノラル」として通す。
- **符号化の手順**: 右側を 0 で埋めて 800 の倍数にし、事後分布の平均（mean）をそのまま使い（標本は取らない。`logs_proj` は使わない）、`(z − latents_mean) / latents_std` で正規化する。統計量は復号器と同じく `__metadata__` から読む。計算はすべて f32 である。
- **落とし穴 1（Snake の α）**: 符号化器の活性化 Snake は、α を**指数を取らない生の値**で使う（`x + 1/(α + 1e-9)·sin²(αx)`）。復号器の SnakeBeta は対数空間の値に `exp` を取るので、復号器の活性化を使い回すと値が狂う。符号化器にはアンチエイリアス（折り返し雑音を防ぐ上げ下げ）も無い。
- **落とし穴 2（`zero_k_bias`）**: 因果注意の `zero_k_bias` は**永続の buffer**（`persistent=True`）にする。非永続にすると `load_state_dict(strict=False)` がこの名前を捨て、meta のまま残る。ファイルのテンソル名は、そのまま受ける。
- **読み分け**: 読むのは `encoder.`・`pre_block.`・`mean_proj.` のテンソルで、`logs_proj` と復号器と統計量は読み捨てる（本数の実測は §178 の G0）。復号器の `H3AudioVAE` とその読み分けは変えていない（T2V の読み込みと常駐を変えないため）。2 つの読み分けは 1 つの接頭辞の表から作る。
- **組み方**: キーフレームの画像の符号化器（§4 の段 2）と同じ作法で、そのジョブのためだけに組み、1 回符号化し、DiT を組む前に捨てる。常駐させない。

### 元の波形の読み込み（`engine_h3/source_audio.py`）

- H3 の仮想環境に torchaudio は無い（§10）ので、PyAV〔Python から ffmpeg を使うライブラリ〕で復号し、`AudioResampler(format="fltp", layout=None, rate=32000)` で 32kHz の浮動小数に変換する（チャンネルの並びは変えない）。
- **出し切り**: 読み終えたら必ず `resample(None)` を呼んで、変換器が抱えている末尾の数ミリ秒を出し切る。入力がすでに 32kHz の fltp のときは変換器が素通しになり、出し切りは PyAV 18.1.0 の実物では空のリスト `[]` を返す（`av/audio/resampler.py` 55〜79 行の近道では `[None]` を返す）。どちらでも、`None` の要素は捨てる。途中で形式が変わる入力は、日本語の理由をつけて止める。
- **チャンネル**: 1 チャンネルなら左右に複製し、3 チャンネル以上なら先頭の 2 つを使う（DiffSynth と同じ）。ピーク正規化はしない。
- **読む量**: `A·800 + 32,000` サンプル（映像の音声の潜在 A 個ぶん＋約 1 秒）に達したら読むのをやめる。

### 長さの規則（裁定 78）

- **映像の尺が主**: 音声は映像の長さ `F / fps` 秒以上が要る。長ければ切り詰め、足りなければ断る（水増ししない）。トリムの指定は受けない。
- **アプリの事前検査**: `duration + 0.001 < F / fps` なら 422 で断る（1 ミリ秒の許容。読める音声の流れが無いときも 422。長さが測れないときはエンジンの歯止めに任せる）。形と文言の正本は仕様書 §6.2。
- **エンジンの歯止め**: 映像の長さ `round(F·32000/24)` サンプルに対し、足りないのが 32 サンプル（1 ミリ秒）以内なら 0 で埋め、それ以上なら日本語の理由で止める。事前検査の許容と同じ幅である。
- **符号化する長さ**: 手に入った分のうち `min(長さ, A·800 + 32,000)` サンプルを符号化し、潜在を先頭から A 個に切り詰める。pre_block の注意は因果なので、余裕が効くのは畳み込みの受容野の末尾だけである。長い音源を全部符号化する無駄も避ける。音声が映像以上あれば、潜在は必ず A 個以上できる（`ceil(N/800) ≥ A`）。

### 出力の音声（裁定 77）

- **Strength 1.0**: 音声の行は最後に clean と一致するので、音声 VAE の復号を飛ばし（組まない。常駐している物にも触らない）、**元の波形**を映像の長さで切って mp4 に入れる。記録は `audio_output: "original"`。
- **Strength が 1.0 未満**: 生成された音声の潜在を、いつもの経路で復号して入れる（モデルが解釈し直した音声）。記録は `audio_output: "decoded"`。
- **Strength 0**: マスクの値が全部 1 で効き目が無いので、符号化もしない。音声の無いジョブと同じ計算になり、音声はモデルが作ったものになる。

### V1 で公開するもの・しないもの

- **公開する**: 単発の `POST /generate` の `source_audio`（`audio_id` と `strength`。裁定 74）。音声のマスクだけで、値は全部の潜在で 1 つ。キーフレームとの併用は通す（裁定 79）。
- **エンジンにあるが公開しない**: 映像のマスク（`video_mask`）。V2A〔Video-to-Audio。映像から音声を作る機能〕は映像を固定して音声を作るだけで同じ部品で実現できるが、製品には出さない（裁定 75。§12）。行ごとに違う値・区間の指定・パッチ単位のマスクも出さない。
- 連結生成（`/generate/chain`）とそのスキーマは変えていない。H3 は連結を今までどおり断る。

### Strength の既定 0.5 と目視の所見

- **オーナーの目視（2026-10-25。[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §178 の G4）**: Strength 1.0 では「音が鳴っている間、ずっと口を開けっ放しにして、音が止まったら閉じる」硬い動きになり、実用的でなかった。0.5 では口が言葉に合わせて動き、実用的だった（LTX のリップシンクにはわずかに及ばない）。0.5 で復号した音声には、聞いて分かるほどの劣化はほとんど無かった。先頭画像なしでも 0.5 は 0.75 より自然で、先頭画像ありの 0.75 にはまだ硬さが残った（同 §178 の G3b）。これを受けて既定を 0.5 にした（裁定 76）。
- **オーナーの仮説（推測）**: テンソルの一部を厳密に固定すると、残りの部分の創造性まで引きずり下ろす（画像生成の AI でも見られる現象）。
- **監督の読み（推測）**: Strength 1.0 では、音声の行が最初のステップから時刻 1.0（ノイズ無し）にあり、映像は高いノイズから下りてくる。「片方の流れだけが先に完成している」状態で、映像と音声を一緒にノイズ除去する学習の分布の外にある。0.5 では音声の行の時刻が `1 − 0.5σ` で、映像と並んで下りてくる。
- どちらの仮説も確かめていない。**DiffSynth の Retake と、コミュニティの LipSync のノード（ComfyUI-MiniMax-H3-LongMedia。音声 0・映像 0.35）の既定は、どちらも音声を完全に固定する（本製品の Strength 1.0 にあたる）**ので、本製品の既定はそれらと違う。
- 操作パネルの文言では、1.0 を「実用的でない」とは書かない（主観の判断は利用者に任せる。裁定 80）。

## 4. 推論の段と常駐

推論の本体は条件付け・ノイズ除去・デコードの 3 段で、I2V は前に画像の段が、A2V（§3.1）は音声の段が加わる。一度に GPU に置くのは 1 段ぶんだけである。段が終わるたびに解放する（常駐を求められたときの保持物を除く。下の「常駐」）。

| 段 | 内容 | GPU に置くもの | 解放するもの |
|---|---|---|---|
| 0. 画像の読み込み（I2V のみ） | キーフレームの画像を全部読み、キャンバスに合わせる | なし | — |
| 0b. 元の音声の読み込み（A2V のみ） | 元の波形を 32kHz のステレオで読む（§3.1）。テキストエンコーダより前に読むので、短い・読めない音声はモデルを読む前に止まる | なし | — |
| 1. 条件付け（`encode`） | テキストエンコーダでプロンプトを埋め込みにする | いま計算している 1 層（層ごとにファイルから直接読む）。先頭か末尾の画像があるジョブでは、画像読み取り部も計算の前に読む | テキストエンコーダ全体 |
| 2. 画像の符号化（`image_encode`。I2V のみ） | 映像 VAE の符号化器（1 度だけ組む）で K 枚の画像を 1 枚ずつ符号化する | 符号化器（f32） | 符号化器（保持しない） |
| 2b. 音声の符号化（`audio_encode`。A2V で Strength が 0 より大きいときだけ） | 音声 VAE の符号化器で元の波形を 1 回符号化する（§3.1）。進捗では `encode` の 1 ステップとして数える（`audio_encode` は `done` の `h3.phases` の段の名前だけ。§8） | 符号化器（f32） | 符号化器（保持しない） |
| 3. ノイズ除去（`stage1_denoise`） | DiT をステップ数だけ回す | ブロック以外（埋め込み・最終層など）と、block swap が選んだ一部のブロック（`blocks_on_gpu`） | DiT のブロック以外と全ブロック（常駐しなければ DiT 全体も） |
| 4. デコード（`decode`） | 映像 VAE と音声 VAE で復号し、mp4 に書く。Strength 1.0 の A2V では音声 VAE を組まず、元の波形を入れる（§3.1） | 映像の復号器 → 音声 VAE の順に 1 つずつ | VAE（常駐しなければ） |

- **テキストエンコーダは直接読む（裁定 32）**: プロンプトの前向き計算は 1 ジョブで 1 回しかない（CFG が無い）ので、層を主メモリに置く意味がない。HF の `forward` はそのまま使い、各デコーダ層の前向きの直前にファイルから GPU へその層だけを読み、直後に捨てるフックを掛ける。埋め込み表と画像読み取り部は、計算の前に読んで計算の後に捨てる。主メモリに残るのは骨格（meta）だけである。層数は数えて、全部の層が走ったことを検査する。`te_layers_on_gpu` という設定は無い。
- **主メモリ**: 直接読みにしたので、テキストエンコーダの段で主メモリは増えない。作業セット（実メモリに置いている量）とコミット量（OS が確保を約束した量）の実測は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §166 を見よ。32GB 機の扱いは §13。
- **常駐（`keep_resident`。裁定 26）**: 要求の `keep_resident` が真のジョブだけが、終わりに次の物を **CPU に**保持する。
  - 保持する物: DiT（ブロックもブロック以外も CPU へ戻す）・映像の復号器・音声 VAE。映像の符号化器と音声の符号化器は保持しない（I2V・A2V のジョブごとに組んで捨てる）。テキストエンコーダは直接読みなので保持する物が無い。`BlockSwapService` は元からプロセスに 1 つで、ページ固定の領域と転送用の流れをジョブをまたいで持つ。
  - **GPU には何も残さない**（cuBLAS が持つ作業領域は除く）。同期経路は最後の窓のブロックを GPU に残すので、ジョブの終わりに明示的に CPU へ戻す。
  - block swap の包みは、共有部品の印（元の `forward` を覚えている属性）から元の `forward` を戻して剥がす。ジョブの終わりと DiT を GPU へ置く直前の 2 か所で剥がし、次のジョブで入れ直す。先読みの on／off が常駐中に変わっても包みが二重にならない。共有部品は変更しない。
  - **キーが無い（偽の）ジョブ**は、保持物があれば使い回し（読み込みを飛ばす）、ジョブの終わりに解放する。**失敗したジョブ**は、どの段で止まったか分からないので保持物を丸ごと解放し、次のジョブはファイルから読み直す。検査の失敗や画像が読めない失敗でも同じである。
  - 使い回しの有無は `done` の `h3.phases` の `dit_source`・`vae_source`（`"file"`／`"resident"`）に出る。
- 常駐でないジョブは、毎生成、段 1 から段 4 まで組み直す。
- **VRAM 16GB mode（`vram16_mode`。H3 では既定 on）のノイズ除去の段**は、上の表の段 3 と次の点だけが違う（規則の正本は §6.5）。block swap の常駐ブロック数を `min(blocks_on_gpu, 4)` にする（DiT 全体を GPU に置く設定ならそのまま）。段の頭で割り当て器に上限を課し、段の終わりに外す（上限は実行時の空きから導く）。token_refiner と `condition_proj` は `refine_text` の後に GPU から降ろす（常駐するジョブは CPU へ、しないジョブは meta へ）。
- **ジョブごとの設定**: `attention_backend` と `block_swap_prefetch` は `generate` でもジョブごとに受ける（`load` の値は既定値になる）。SageAttention が使えないときは SDPA へ落とし、使った値を `done` に返す。attention の既定は本製品の現状の既定に従い、H3 専用の既定は作らない（裁定 27）。

## 5. int8 ConvRot の実行方式

- **素の int8 `Parameter` ＋ f32 `[N,1]` のスケール**: 量子化された Linear は `H3Int8Linear` という自前のモジュールにする。重みは素の int8 の `nn.Parameter`（`requires_grad=False`）、スケールはファイルどおりの f32 `[出力次元, 1]` のバッファ、bias は任意である。`forward` は `comfy_kitchen.int8_linear` を呼ぶ。ConvRot（活性化を回転してから量子化する方式）の有無と groupsize は層ごとの記述（`comfy_quant`）から取る。
- **量子化テンソル型を使わない理由**: comfy-kitchen には重みをラッパー型のテンソルとして持つ量子化テンソル型もある。しかし、ラッパー型のテンソルは本製品の block swap と先読み（素のテンソルを前提に重みを出し入れする）に乗らない。関数 API の `int8_linear` は同じ CUDA カーネルに届くので、素のテンソルで足りる。
- **CUDA 経路に固定する**: 起動時に `comfy_kitchen.list_backends()["cuda"]` が使用可能で、能力に `int8_linear` を含むことを確かめ、満たさなければロードを拒否する（理由の文を返す）。そのうえで **triton と eager の両経路を切る**。
  - triton を切る理由: comfy-kitchen の triton 経路の int8 行列積は、トークン数×出力幅が 2³¹ 以上で出力の位置が int32 であふれ、プロセスごと落ちる既知の不具合がある（上流 issue #136）。CUDA 経路は出力の位置を int64 で計算しているので、この限界を持たない。
  - eager を切る理由: eager は制約から外れた呼び出しを黙って受けて遅くなるだけで、速度の低下から区別できない。切っておけば、CUDA 経路に乗らない呼び出しは `NoCapableBackendError` で止まる（**fail loud**）。
- **CUDA 経路に乗る条件**: 重みとスケールが GPU 上にあること。block swap が重みを GPU に載せた状態で呼ぶ限り満たされる。
- groupsize は 256 以外（例: 64）も、そのまま `int8_linear` に渡す。
- **例外（VRAM 16GB mode の qkv だけ。台帳 §1-105 ①・オーナー裁定 2026-10-25）**: VRAM 16GB mode の qkv の射影（§6.5）だけは、関数 API の `int8_linear` に任せず、comfy-kitchen 0.2.37 の**公開されていない内部**を使って、入力の量子化を 1 ブロック 1 回にする。量子化は `backends.cuda.quantize_int8_rowwise_convrot64`（`int8_linear` が中で呼ぶものと同じ核・同じ引数）、行列積は `int8_linear` の量子化より後の部分を写した `_int8_gemm_prequantized`（`engine_h3/quant_linear.py`）で行う。
  - 版 0.2.37・記号・引数の並びを起動時に検査し、外れたらログに残して従来の経路に戻す（ロードは拒否しない。詳細は `quant_linear.py` の冒頭）。
  - **fail loud の保ち方**: この経路は comfy-kitchen の登録の制約を通らない。そのため、重みとスケールが入力と同じデバイスに無い呼び出しは共有せず、従来の `int8_linear` に回して `NoCapableBackendError` で止める。
  - 数値が変わらないことと短縮の実測は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §177。

## 6. 既存部品との接続

- **block swap と先読み**: 既存の `engine/transformer/block_swap_service.py` と `block_swap_prefetch.py` をそのまま使う。`BlockSwapService` はパイプラインに常駐し、ジョブごとには作らない。H3 の本体ブロック列の名前が `blocks` で、block swap が探す候補名に当たる。素の `nn.Module` の列なので、既存の形でそのまま乗る。共有部品は変更しない。
- **テキストエンコーダの読み方**: 層ごとにファイルから GPU へ直接読む（§4）。`GemmaLayerOffloadService` は使わない。
- **推論の囲み【設計】**: `engine_h3` は**全経路 `torch.no_grad()`** で書く（`inference_mode` は 1 箇所も書かない）。規約と理由は MULTI_ENGINE_DESIGN §5.8。CPU テストで `engine_h3` 配下に `inference_mode` が現れないことを固定する。
- **精度の島の dtype**: 読み込みの直後に `H3DiT.normalize_dtypes()` で、精度の島の内外の dtype を揃える（公式ファイルでは AdaLN 射影の F16→F32 だけが変わる）。
- **meta で組んで `assign=True`【設計】**: DiT もテキストエンコーダも `torch.device("meta")` の中で組み、量子化層を `H3Int8Linear`（meta）に差し替え、テンソルを 1 本ずつ読んで `load_state_dict(assign=True)` で入れる。読み込みの後に meta のまま残ったテンソルが無いことを、読んだ部分ごとに検査する（テキストエンコーダは、画像読み取り部を読むジョブ〔先頭か末尾の画像がある I2V〕では画像読み取り部も含め、それ以外〔T2V と中間だけのジョブ〕では文章側だけを調べる。読まない画像読み取り部は meta のまま残すため）。普通に組むと DiT が f32 で約 77GB、テキストエンコーダが bf16 で約 49GB を先に確保して主メモリ（64GB）を超えるので、この作りは必須である。

## 6.5 VRAM 16GB mode（ノイズ除去の活性化を分割して VRAM 16GB に収める）

**結論**: ノイズ除去の段で、1 ブロックの計算を「ヘッド群」と「行の塊」に分けて回し、活性化（計算途中のテンソル）の山を下げる。割り当て器（torch の CUDA メモリの割り当ての仕組み）には上限を課して、返されない空きセグメントが共有メモリへの退避（VRAM から主メモリ側へ溢れること）を起こさないようにする。H3 では**既定で on** で、Settings の「Acceleration／生成の高速化」から切れる（裁定 44）。製品の条件（I2V 896×1152×124 フレーム）で、ノイズ除去の割り当て／予約が 12,807／16,828MiB から 4,411／7,262MiB に下がり、1 ステップが約 203 秒から約 22 秒になる（退避ゼロ。詳しい実測は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §169.3、qkv の量子化の共有の後の値は同 §177）。精度を落とす手段は使わない（裁定 46）。

### 何をするか

on の経路で行うことは次の 8 つである。#1・#7・#8 は VRAM の山そのものではなく、予約と固定費を下げる。

| # | 単位 | 内容 |
|---|---|---|
| 1 | 割り当て器の上限 | ノイズ除去の頭で、このプロセスの割り当て器に上限を課し、終わりに外す。導き方は下の「上限と OOM」 |
| 2 | 早期解放 | q・k・v を重みの行で切って射影し（融合した qkv を作らない）、埋め込み済みのトークンは bf16 にした直後に捨てる。norm 後の入力は量子化の直後に捨てる（共有に乗らないときは最後のヘッド群の後） |
| 3 | ヘッド分割 | 注意計算をヘッド群ごとに回す。呼ぶのは off と同じ `_attention` |
| 4 | FFN の行の塊化 | FFN を行の塊ごとに回し、結果を 1 本の受け皿へ書く |
| 5 | AdaLN の塊化 | 変調とゲートを行の塊ごとに回す |
| 6 | 最終層 | 正規化と変調だけを行の塊ごとに回し、f32 の連続バッファに集めて、出力の行列積は映像と音声それぞれで 1 回行う（行の方向には分けない） |
| 7 | 降ろす | `refine_text` の後で、token_refiner と `condition_proj` を GPU から降ろす（下の「降ろす規則」）。本書で「退避」と書くのは共有メモリへの退避（spill）だけである |
| 8 | 常駐数 | block swap の常駐ブロック数を `min(n_load, 4)` にする（下の「常駐数」） |

- **off の経路は変えない（裁定 45）**。on と off は同じワーカーの中の切り替えで、ワーカーや仮想環境は複製しない。off の保証は、基準の指紋 `0da6111c…` が変わらないことで担保する（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §169.3 の A-G3）。
- 採らないもの: Q だけの流し込み・q と k の strided な渡し・2 分割の MLP・融合した SwiGLU・RMSNorm と RoPE の融合・`smooth_k` の無効化・VAE の fp16 累積・CUTLASS 設定の強制。数値に触れる手段は、精度を落とさない目標（裁定 46）と合わないので使わない。

### 置き方

- **`engine_h3/lowvram.py`**: 新しい計算を書かない。off の経路が呼ぶ既存の関数（`_modulate`・`_gate`・`block.mlp`・`_attention`・`apply_rope`・`_linear_f32`・各 norm）を、**行の範囲・ヘッドの群ごとに呼ぶだけ**で、結果は事前に確保した受け皿へ書く。含むのは `Vram16Plan`（分割の単位）・`row_chunks`・`blocks_on_gpu_for`・`derive_memory_cap`・`block_forward`・`final_rows_chunked`。`_modulate`・`_gate`・`_attention`・`apply_rope`・`_linear_f32` の 5 つは `engine_h3.dit` のモジュールを経由して呼ぶので、テストでの差し替えが効く（`block.mlp` と各 norm はブロックから直接呼ぶ）。
  - **例外（台帳 §1-105 ①・オーナー裁定 2026-10-25）**: qkv の入力は、ヘッド群のループの前に 1 回だけ量子化し（`H3Int8Linear.quantize_input`）、その直後に `h` を捨てる。ループの中の q・k・v は、量子化済みの入力から `forward_rows_q` で切片ごとに計算する（行列積は `_int8_gemm_prequantized`。§5 の例外）。使えるかはブロックごとに `shares_input` が決め、使えないときは従来どおり `forward_rows` で切片ごとに量子化する（分岐はこの 1 か所）。LoRA の行数は `xa` から取る（`forward_rows_q` は `lora.apply` に入力を渡さない）。
- **`engine_h3/dit.py`** は分岐と引数だけ。`H3DiTBlock.vram16`（クラス属性。None なら off）に計画が入っていれば、`forward` の先頭で `lowvram.block_forward` へ渡す。`H3DiT.forward` は `vram16` と `tokens_box`（埋め込み済みトークンを入れた容れ物。取り出した後に呼び出し側の参照が残らないようにするため）を受け、ブロックごとに `block.vram16` を**毎回**代入する（None も。常駐した DiT の後始末になる）。`final_rows` も `vram16` の有無で分岐する。off の経路の行は変えない。
- **`H3Int8Linear.forward_rows(x, n0, n1)`**: 出力の行 `[n0, n1)` だけを、毎回 `self.weight` から切った連続ビューで計算する。呼び出し側がヘッドの境目で切るので、`n0` は結果として `head_dim`（128）の倍数になる。
- 割り当て器の上限と、モジュールを降ろす処理と、`tokens_box` は `pipeline_h3.py` の `_denoise`（`_vram16_begin`・`_vram16_finish`・`_evict_text_modules`）にある。ワーカーとアダプタの鍵は §8。

### 定数と理由

正本は `engine_h3/constants.py`（コメントに根拠の実測がある）。分割の単位と常駐数は**形状だけから決める決定的な規則**で、実行時の値から導いてよいのは割り当て器の上限だけである（裁定 51）。

| 定数 | 値 | 理由 |
|---|---|---|
| `VRAM16_HEAD_GROUP` | 8 | ヘッド群（56 ヘッド → 7 群）。28／14／8 の 3 択はどれも最速から +10% 以内で、割り当てが最小なのが 8（事前に決めた判定規則） |
| `VRAM16_ROW_CHUNK` | 4096 | FFN・AdaLN・最終層で共通の行の塊。8,192／4,096／2,048 は 4,096 と 2,048 が同点で、同点なら大きい塊を採る。塊は `ceil(S / 4096)` 個に**等分**する（S ≤ 4,096 は分割しない）。端の塊が小さくならないので、`int8_linear` の m ≤ 2（Turing は m ≤ 128）の別経路に入らない |
| `VRAM16_BLOCKS_ON_GPU` | 4 | on のときの常駐ブロック数の上限。4 と 8 は時間に差がなく、割り当てだけが 1,488MiB 違う。画角の長さによるしきい値は設けない |
| `VRAM16_CAP_MARGIN_MIB` | 1024 | 割り当て器の上限から引く余白 |

### 上限と OOM

- **上限**: `set_per_process_memory_fraction` に、`(このプロセスの予約 + mem_get_info の空き − 余白) / 総量` を渡す（`derive_memory_cap`。0〜1 に収める）。ノイズ除去の頭（`_place_dit` の前）で課し、`finally` の先頭で 1.0 に戻す。CUDA のデバイスは番号つきで渡す（番号無しの `cuda` を渡すと上限が課せない）。製品の条件での値は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §169.3 にある。
- **記録**: `done` の `h3.phases.denoise.vram16` に、上限（比と MiB）・常駐ブロック数・ヘッド群・行の塊・降ろした先（`text_modules`）・割り当て器の再試行と OOM の回数の差分・`inactive_split` のピーク・qkv の量子化の共有の可否（`qkv_quant_shared`。ロード時の検査〔§5 の例外〕の合否で、ブロックごとの判定ではない）を入れる。
- **OOM は失敗させる（裁定 47）**。on のとき `torch.OutOfMemoryError` を `VRAM16_OOM_MESSAGE`（「VRAM 16GB mode でも GPU メモリが足りません (CUDA out of memory)。解像度かフレーム数を下げるか、VRAM 16GB mode を切ってください」）の `RuntimeError` に包む。アプリ側は「out of memory」を含む文言を `GPU_OOM` に分類するので、ジョブは失敗し、`get_job` の `error` に案内が出る。黙って退避を許す経路は作らない。案内に「画角」と書かない。
- **カーネルが投げる `RuntimeError("CUDA error: out of memory")` は包まれない**。包むのは `torch.OutOfMemoryError` だけである（記録だけの小さな漏れ）。

### 降ろす規則

token_refiner と `condition_proj` は、`refine_text` の後に走らない。常駐するジョブ（`keep_resident`）は CPU へ移し（`_park_dit` が戻すのと同じ行き先）、常駐しないジョブは meta へ落として捨てる（`drop_to_meta`）。**降ろした後に `empty_cache` は呼ばない**。外した約 1.5GB は割り当て器のキャッシュに残る。重みの区画は 1 つあたり約 231MB 以下で、活性化（U＝約 408MiB）はそこに収まらないので、上限に当たったときに「キャッシュを返して再試行」が起き、`num_alloc_retries` に数えられうる（推測。割り当て器の内部は読んでいない）。再試行の回数を VRAM の逼迫の指標として読むときの注意として残す（製品の条件の実測では 0 回）。

### 常駐数

block swap の常駐ブロック数 `blocks_on_gpu`（block swap が GPU に置いておくブロックの数。モデルの保持〔`keep_resident`〕とは別）は、on でも off でも毎回、パイプラインが `install` の前に代入する（on のジョブで減らした数が次の off のジョブに残らない）。on のとき、`n_load` が 0 以下か全ブロック以上（DiT 全体を GPU に置く）ならそのまま、そうでなければ `min(n_load, 4)`。先読みの受け皿は常駐数 + 2 本なので、常駐 8 → 4 で受け皿が 10 → 6 本になり、固定費（受け皿）が減る。実測の割り当ての差は 1,488MiB（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §169.3）。時間は変わらない。

### 数値の約束

- **目標はビット一致（裁定 46）**。行ごと・ヘッドごとの演算だけを分割しているので、同じ関数を範囲ごとに呼べば一致する。
- 確かめた範囲（結果は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §169.3）: GPU テストで `forward_rows` の結合・行の塊の縦結合・`k.mean` のヘッド群比較が完全一致。端から端まで（640×384・124 フレーム・20 ステップ・sdpa）の指紋は off も on も `0da6111c…` に全桁一致。
- **製品の形（S＝39,764・実重み）の 50 ブロック比較では、sdpa は 50 ブロックともビット一致、sage は 50 ブロック中 2 ブロックで値が違う**（ブロック 22 とブロック 40。再現性あり）。ブロックごとの最大絶対差は 22 で 256・40 で 1,792、値が違う要素の割合は 22 で約 54%・40 で約 3.3%、出力全体の相対差は 22 で 6.6e-3・40 で 3.1e-3（正本は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §169.3）。ブロック 22 で切り分けたところ、この要因だけで説明できた。SageAttention の計算核が 1 回の呼び出しのヘッド数（off は 56、on は 8）で値を変える。q・k・v は全群で一致し、off の入力を 8 ヘッドずつで sage に渡すと on と完全一致する。ブロック 40 は切り分けていない（同じ仕組みと見られる。推測）。**この差を受け入れるかは裁定 46 に従い、ブロックごとの最大差がゆらぎ級であることと、オーナーの目視で品質差が無いことで決める**。B-G5 の目視（I2V 896×1152×124 フレーム・20 ステップ）で合格し、採用した（裁定 53）。

### 山の内訳

製品の条件（I2V 896×1152×124 フレーム、S＝39,764、sage）での**概算**。U は bf16 の `[S, 5376]` のテンソル 1 本（約 408MiB）で、bf16 の `[S, 7168]` は 1.33U、f32 の `[S, 5376]` は 2U。行の塊（4,096 行）とヘッド群（8 ヘッド）の一時テンソルは「+」で数える。ブロック 1 以降で、入口の `x` はブロックの最後まで生きている。

| 区間 | 生きているもの | on の概算（U） | off の概算（U） |
|---|---|---|---|
| 入口 | `x`（トークンはもともと bf16。`tokens_box` で呼び出し側に参照を残さず、ブロック 0 を抜けると解放される） | 1 | 2（トークンも保持） |
| norm1 と変調 | `x`・norm1 の出力・変調後の `h` + 塊の f32 の一時 | 約 3.4 | 7 |
| 注意（山） | `x`・量子化済みの入力（int8 で 0.5）・出力の受け皿 `o`（1.33）+ 群の q・k・v・RoPE の出力・sage の内部 | 約 4.5 | 18.33 |
| out_proj | `x`・`o`・int8 の写し・出力 | 約 4 | 約 12.7 |
| 注意の残差 | `x`・注意の出力・新しい `x2` + 塊の一時 | 約 3.4 | 約 6 |
| norm2 と変調 | `x`・`x2`・norm2 の出力・`h2` | 4 | 8 |
| FFN | `x`・`x2`・`h2`・`m` + 塊の fc1 出力（`[4096, 28672]`）と活性化 | 約 5.3 | 14.67 |
| FFN の残差 | `x2`・`m`・出力 + 塊の一時 | 約 3.5 | 約 7 |

- off の列は第 1 段の棚卸し（[`Outputs-archive/h3-vram-2026-10-18/reports/R1_vram_inventory.md`](Outputs-archive/h3-vram-2026-10-18/reports/R1_vram_inventory.md) §3.2）の値で、活性化の山は 18.33U ≈ 7,475MiB。on の山は約 5U ≈ 2.1GB。
- 実測との照合: on のノイズ除去の割り当てのピーク 4,411MiB から、先読みの受け皿 6 本（371.08 × 6 ≈ 2,226MiB）を引くと約 2,185MiB ≈ 5.4U で、概算の山（約 5U）と合う（qkv の量子化の共有の後の実測は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §177）。
- 山が下がるので、割り当て器の上限（14,033MiB）の下に収まり、返されない空きセグメントが共有メモリへの退避に化けない。

### 範囲と既知の限界

- **範囲**: on の q・k・v は群ごとに連続で、最大のオフセットは S × 群のヘッド数 × 128。群 8 で S ≈ 209 万行まで int32 の範囲に収まる。防御用の関数は作らない。
- **上限はこのプロセスの割り当てだけを縛る（裁定 47）**。ジョブ中に他のプロセスが VRAM を増やした場合の退避は防げない。
- **VRAM 16GB mode の実測は開発機（RTX 4070 Ti SUPER・Ada）だけである。** RTX 30 系（Ampere）は未確認（サブマシンで確かめたのは α版の T2V だけ。[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §167.8）。
- **off の経路の限界**: SDPA の mem-efficient 経路は、系列が約 10 万行を超えて v が view（行の刻みが詰まっていない）のとき、不正なメモリアクセスになる。実測は 98,304 行で正常・100,352 行で不正（v を連続にすれば正常。[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §168.3 の T6）。on は群ごとに連続な q・k・v を渡すので、この境界に近づかない。off の経路には防御を足していない。
- 上限のせいで先読みの受け皿が確保できないとき、同期の経路に黙って切り替わる（記録だけ。on の条件では起きていない）。
- Turing と、comfy-kitchen の内部が検査に合わないときは、qkv の量子化は従来どおり 1 ブロック 21 回になる（§5 の例外）。共有の経路は Ampere では確かめていない（オーナー裁定 2026-10-25 で門に入れなかった）。

## 6.6 LoRA（実行時の低ランク経路）

**結論**: LoRA（追加学習した低ランクの差分重み。Style・Motion・Turbo など）は、int8 の重みには触れず、各対象層の出力に FP32 で差分を足す経路として動く。利用者が `models/MiniMaxH3/LoRA/` に置いた `.safetensors` を、操作パネル・Gradio・MCP から使える。同時に使う本数に制限はなく、ステップ数と shift は自動では変えない（Turbo を使うときは利用者が下げる。オーナー裁定は研究ノート §10 の裁定 62〜73）。LoRA を使わないジョブには hook も buffer も無く、今日と同じ経路を通る（基準の指紋 `0da6111c…` が変わらないことで確かめた。実測は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §176）。

### 式

対象は本体 50 ブロックと token_refiner 2 ブロックの `attn.qkv_proj`・`attn.out_proj`・`mlp.fc1`・`mlp.fc2`（正規名は `blocks.{i}.…`・`token_refiner.blocks.{j}.…`）。1 層の出力は次の式で決まる。

`y = bf16( f32(base(x)) + Σ_k s_k · ( f32(x) @ A_kᵀ ) @ B_kᵀ )`、`s_k = 強度_k × alpha_k ÷ rank_k`

- ファイルに `.alpha` が無いときの倍率は 1.0（alpha ÷ rank を使わない）。
- LoRA が見る `x` は**回転前の生の入力**である（ConvRot の回転は int8 カーネルの内部の話）。
- A と B は CPU の主メモリに**ファイルの dtype のまま**（BF16・F16・F32）置き、使うときに f32 へ持ち上げる（可逆）。
- 丸めは 1 回だけ。f32 の差分を bf16 の出力へ `add_` で足すと、共通の dtype である f32 で計算して最後に 1 回だけ bf16 に丸める。

### 接続（hook と `forward_rows`）

- **forward hook**: `forward()` を通る呼び出し（off の経路の 4 層・token_refiner・VRAM 16GB mode の out_proj と `block.mlp`）はすべて `Module.__call__` を通るので、層ごとに hook を 1 本掛けて差分を足す。`dit.py` と `H3Int8Linear.forward` は変えない。
- **`H3Int8Linear.forward_rows(x, n0, n1, lora_xa=None)`**: VRAM 16GB mode の qkv は `__call__` を通らないので、`forward_rows` と、共有の経路の `forward_rows_q`（`x=None`・`lora_xa` で呼ぶ）が自分で差分を足す。B は出力の行 `[n0, n1)` で切る。`lowvram.block_forward` はヘッド群のループの前に `f32(h) @ Aᵀ` を 1 回だけ計算して `lora_xa` で渡す（群ごとの 21 回の計算を避ける）。LoRA が無いジョブでは `None` で、算術は増えない。
- **buffer**: A と B は層の**永続しない buffer**（`_lora_A_{k}`・`_lora_B_{k}`）として置く。block swap・先読みの受け皿・`_park_dit`・`drop_to_meta` がブロックと一緒に運び、state dict は変わらない。

### 塊の切り方（off と VRAM 16GB mode が一致する理由）

差分は、行を `VRAM16_ROW_CHUNK`（4096）、出力の列を `LORA_COL_CHUNK`（1024）の塊で回して足す。1024 は `VRAM16_HEAD_GROUP × head_dim`（8 × 128）で、VRAM 16GB mode が qkv を切る q・k・v の 1 切片と同じ幅である。fc1・fc2・out_proj も同じ規則で切るので、cuBLAS に渡る形は **off と on で全層一致**する。qkv だけの特別扱いは作らない。したがって「LoRA ありの off と VRAM 16GB mode の出力は**形によって**ビット一致する」（裁定 46 の基準の延長）。確認は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §176（off と on の mp4 の sha256 が全組で一致。先読みを切った同期の入れ替えも含む）。`LORA_COL_CHUNK` と `VRAM16_HEAD_GROUP × head_dim` の一致、および行の塊の幅が `VRAM16_ROW_CHUNK` と等しいことは CPU テストで固定する。

加算の形は「行の塊ごとに `xs = f32(x[行]) @ Aᵀ × s`、列の塊ごとに `delta = xs @ B[列]ᵀ`（2 本目以降は `addmm_`）を f32 の塊 `[行, 1024]`（約 16MB）へ作り、`out[行, 列].add_(delta)`」である。要素あたりの読み書きは 12 バイトで、`apply` に `except` は書かない（失敗は失敗）。

### 付け外しの位置（`pipeline_h3.py`）

1. **`validate_request`**: 各 LoRA の存在・ヘッダ・鍵の写像を調べ、パス空・強度が正でない・ファイルが無い・壊れている場合は**文章の符号化の前**に日本語で拒否する（常駐 DiT を失わない）。鍵が写らないだけでは拒否しない。
2. **`_denoise` の `try:` 先頭**（`_vram16_begin`・`_place_dit` の前）: ファイルを読み、CPU のまま `attach`。先読みの計画がその buffer を一緒に詰める。付けた後は読んだ辞書を捨てる。
3. **`finally`**: `teardown_prefetch` → `release_installed` → **`detach`（無条件）** → `_park_dit` の順。**順序の制約**: `teardown_prefetch` の `_release` は飛行中のブロックの buffer を `mod._buffers[name]` へ**名前で書き戻す**ので、`detach` が先だと A と B が戻ってしまう。`detach` は `delattr` で buffer と非永続集合を消し、hook を外す（冪等。meta・CPU・GPU のどれでも安全）。この順序は CPU テストで固定する。
4. **ジョブ間のキャッシュは作らない**。ファイルは毎ジョブ読み直す（Turbo の約 2GB で NVMe 上 1〜3 秒。見積もり）。常駐 DiT は次のジョブの前に付ける前と同一に戻る。

### 例外と注意

- **全ブロック常駐の例外**: `blocks_on_gpu` が 0 以下か全ブロック以上のときは、LoRA の buffer も全部 GPU に載る（Turbo で約 +1.9GB。見積もり）。ベースの重みも全部 GPU にある条件なので整合するが、「50 ブロック分を常駐させない」要件の例外としてここに明記する。
- **固定メモリの中継は育つ**: 先読みの固定メモリの中継は大きくなる方向にだけ変わる（縮まない）。Turbo の後は常駐サービスが約 2×39MB を持ち続ける。数値には関係しない。
- **形の合わない組**: `attach` は A が `[rank, in_features]`・B が `[out_features, rank]` であることを確かめ、合わない組・モデルに無い名前・dtype が BF16／F16／F32 以外の組は**飛ばして記録する**（実行は続く）。対象は `H3Int8Linear` と素の `nn.Linear` だけ。

### FP32 の保証

`H3Pipeline.load` が 1 回 `require_fp32_matmul()` を呼ぶ。次の 3 条件を確かめ、違えば `RuntimeError` で止める（`done` には記録しない）。(1) `allow_tf32` が False。(2) `torch.get_float32_matmul_precision()` が `"highest"`。(3) （属性があれば）`torch.backends.cuda.matmul.fp32_precision` が `"ieee"` か `"none"`。torch 2.13 の既定は `"none"`（親の設定を引き継ぐ）で、効いているのは (1)(2) の旧来の旗である。当初の計画の「`"ieee"` に等しい」は全ロードを拒否する誤りで、実測で訂正した。テストは、bf16 の行列積なら必ず違う値になる入力で f32 の明示的な参照と `torch.equal` で比べ、`mm`／`addmm_` を差し替えて全オペランドが f32 であることも確かめる。

### 非対応の判定

「LoRA が対応か」の判定の正本は**リポジトリ直下の `h3_lora_format.py`**（torch 非依存）で、アプリ（一覧の「非対応」表示）とワーカー（A／B を探す写像）が同じ関数 `map_lora_keys` を import する。写像の規則は 2 つの名前の流儀と 2 組の接尾辞で、詳細は同ファイルの冒頭に書いてある。

- 受ける名前: 点区切り（先頭の `diffusion_model.` は任意）と kohya の下線区切り（`lora_unet_blocks_0_attn_qkv_proj`）。接尾辞は `lora_A`／`lora_B` と `lora_down`／`lora_up`。`.alpha` は任意。
- **非対応**: 対のキーが 1 つも無い・DoRA／LoHa／LoKr のキーがある・H3 の対象に写らないキー（AdaLN・norm など）が 1 つでもある・A と B の rank が合わない・dtype が BF16／F16／F32 以外。**対象の一部が無いだけ**（token_refiner が無いなど）は対応である。
- **非対応でも選べて実行できる**（研究ノート §10 の裁定 63）。H3 では 422 `LORA_FORMAT_UNSUPPORTED` を返さない。操作パネルは一覧に「非対応」のバッジを出し、生成ボタンの下に黄色い注意文を出す（送信は止めない）。写らないキーは無視され、効果が出ない可能性がある。LTX は今日のまま 422 を返す。
- 記述子の `lora_dir` と系統→ディレクトリの対応は `services/engines/__init__.py::lora_scope_for` の 1 か所（[`MULTI_ENGINE_DESIGN.md`](MULTI_ENGINE_DESIGN.md) の LoRA の項）。H3 の一覧には LTX の IC-LoRA を出さない。

### 記録

LoRA を使ったジョブだけ、`done.h3.loras` に LoRA 1 本ごと `{name, strength, layout, dtype, pairs_applied, skipped[]}` を入れる（`name` はファイル名だけ。絶対パスは mp4 のコメントに埋まるので書かない）。`metadata.json` では `h3.loras` に入る。LoRA の無いジョブの `done` は変わらない。

### 費用

加算は FP32 で行うので、1 ステップごとに時間が増える。Style や Motion のような rank の小さい LoRA は 1 割強、rank の大きい Turbo は事前の見積もりを大きく上回った。それでも Turbo の少ないステップ数なら、通常の 20 ステップより短く済む。**実測の数値の正本は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §176**（VRAM・主メモリの増分も同じ）。ジョブ間の LoRA キャッシュは作らず、v1 はこの費用を受け入れた。高速化は台帳 §3-253。

### 範囲外

diffusers／PEFT の分離 QKV の LoRA・量子化 LoRA・LoHa／LoKr／DoRA・テキストエンコーダ用 LoRA・Ref2VA 用の重みとの互換（Ref2VA 自体が未実装）。LoRA を焼き込んだ配布物は普通の重みとして読む（既存どおり）。

## 7. ヘッダの判定と吸収する揺れ

- **判定はテンソル名の指紋**: H3 の DiT は `{接頭辞}video_patch_proj.weight` と `{接頭辞}audio_patch_proj.weight` の**同時存在**で判定する。GGUF の KV のようなメタデータには頼らない（コミュニティ配布物は KV が偽装・欠落しており、safetensors の `__metadata__` も枝刈り版では空である）。MULTI_ENGINE_DESIGN §2.2・§2.4 の判定とは別の経路で、H3 系統は safetensors にこの指紋を使う。
- **吸収する揺れ**:
  - 接頭辞 4 通り（無し／`model.diffusion_model.`／`model.model.`／`net.`）を剥がす。
  - 構成（層数・幅・ヘッド数・ffn・AdaLN 表の格子数 G とランク・枝刈りか否か）は、メタデータでなく**テンソルの形状**から導く。
  - `comfy_quant` は `format`・`convrot`・`convrot_groupsize` の 3 キーだけを読み、他のキーは無視する。
  - groupsize は 256 以外も通す。量子化されていない層は、読んだ後に島の外側を bf16、内側を f32 に揃える。
  - 知らないテンソルは警告ログを出して捨てる。
- **拒否するもの**: 非枝刈り版（`adaln_t_table` が無い）と、旧式の量子化記述（`_quantization_metadata`）、`int8_tensorwise` 以外の形式、VSA の追加テンソル、PDD ヘッドは、理由の文つきで拒否する（または警告して捨てる）。主に試すのは公式のファイルで、コミュニティ版への対応は後回しである。例外として、オーナーが PinkCherry Hybrid を置いて生成に成功した（実機の事実・2026-10-18）。構造が同じことの根拠は研究ノート §13.3（ComfyUI のコードの読解であり、実測ではない）。対応の保証は §12 のとおり後回し（§13）。
- **置き場**: 判定は torch に依存しない `h3_format.py`（リポジトリ直下。`sft_quant_format.py`・`chain_math.py` と同じ置き場）に書く。アプリ側（torch の無い仮想環境）の事前検査からも呼ぶためである。
- **アプリ側の事前検査**: `services/model_registry.py` の `precheck_model_file` が記述子の系統を見て、`h3` なら DiT を `inspect_h3_dit`、テキストエンコーダを `inspect_h3_te` にかける。VAE 2 本は汎用の safetensors 検査（長さと JSON）である。`h3_format.py` の `H3FormatError` は `MODEL_INCOMPATIBLE` に変換して返す。
- **FL2VA と Ref2VA はヘッダで区別できない**（テンソル名・形状が同じ）。記述子（`scripts/manifests/40-minimaxh3.json`）で配布ファイル名を固定して縛る。

### ワーカーのメッセージ

アダプタの `_build_load_payload` がそのまま写せるよう、キー名はここで固定する。

- **`load`**: `transformer_path`・`text_encoder_path`・`video_vae_path`・`audio_vae_path`・`tokenizer_dir`・`blocks_on_gpu`・`attention_backend`・`block_swap_prefetch`・`deterministic`（`attention_backend` と `block_swap_prefetch` は、ジョブごとの値が無いときの既定になる）
- **`generate`**: `prompt`・`seed`・`width`・`height`・`num_frames`・`frame_rate`・`num_inference_steps`・`shift_video`・`shift_audio`・`images`・`keep_resident`・`attention_backend`・`block_swap_prefetch`・`vram16_mode`・`source_audio`・`output_path`（ステップ数と shift は省略可。省略時は既定値。`source_audio` は A2V のときだけ）
  - `images`: `[{path, frame_idx}]`。無ければ T2V。アダプタは要求のキーフレームを全部（最大 10 枚。上限は API の検査）、サーバーが寄せた後の `frame_idx` で送る。ワーカーは並び順を問わず、`frame_idx` が 0〜F−1 の範囲・重複なし・パスが空でないことを確かめ、外れれば日本語の理由つきの `ValueError` でジョブを止める（プロセスは生き続ける）。要素の知らないキー（強度など）は無視してログに 1 回出す。アダプタは強度を送らない（H3 に強度の概念が無い。裁定 57）。
  - `keep_resident`: 真のときだけ保持する。無ければ偽（保持物を解放する）。アダプタは真のときだけ送る。
  - `attention_backend`・`block_swap_prefetch`: 無ければ `load` の値。アダプタは毎回送る。
  - `vram16_mode`: 真のときだけ VRAM 16GB mode の経路で回す（§6.5）。無ければ偽（ワーカーの既定は off。H3 の既定 on はアプリ側の規則表が書き戻す）。アダプタは毎回送る。
  - `source_audio`: `{path, strength}`。無いか `null` なら T2V／I2V（今までどおり）。あれば A2V（§3.1）。`strength` は 0〜1 で、省略は 0.5。中の知らないキーはログに 1 回出して無視する。アダプタは A2V のときだけ、`output_path` の前に置いて送る（アプリ側の既定を書き戻した値なので、`strength` は毎回入る）。
- **イベント**: `ready`（`sage_available`）／`progress`（`stage`・`index`・`total`）／`done`／`error`（`detail`）
- **進捗の段階名**: LTX の語彙を借りる。`encode`／`stage1_denoise`（単段のノイズ除去。H3 は 1 段なのでこの名前だけを使う）／`decode`。アダプタは進捗の割合計算に `_read_worker_events(one_stage=True)` を使う。`encode` の総数は、3 に、キーフレームが 1 枚以上あれば 1（画像の符号化）、元の音声を符号化するなら 1（音声の符号化。Strength 0 では符号化しないので足さない）を足した数である（`pipeline_h3.py` の `encode_steps` の 1 か所で決める）。画像読み取り部に入る画像の有無では決めない（中間だけのジョブも 4 になり、3 と数えたあとに 4/4 が出ることはない）。`audio_encode` は `done` の `h3.phases` の段の名前で、進捗の段ではない。アダプタは `encode` を常に同じ割合に写すので、A2V でないジョブの進捗は変わらない。
- **`done` のキー**: `seed_used`・`sampler`・`num_inference_steps`・`shift_video`・`shift_audio`・`peak_vram_mb`・`peak_vram_reserved_mb`・`rss_peak_gib`・`seconds`・`num_frames`・`frame_rate`・`width`・`height`・`size_bytes`・`attention_used`（ジョブごとの値）・`block_swap_prefetch_used`・`keep_resident_used`（`"on"`／`"off"`。このジョブの終わりに保持したか）・`vram16_mode_used`（`"on"`／`"off"`。VRAM 16GB mode で回したか）・`images_used`（要求のキーフレームの枚数。名前は変えない）・`commit_gib`・`commit_peak_gib`（コミット量）・`h3`（段ごとの秒数と RSS を `phases` に、使われた量子化経路を `quant_backends` に持つ。`phases.decode` には `audio_samples`〔切り揃え後〕と `audio_samples_decoded`〔復号した全量〕が入る〔`engine_h3/pipeline_h3.py` の `_decode`〕。I2V のときは `phases` に `image_encode` が入る〔`source_size` は画像ごとの元の大きさ `[w, h]` を昇順に並べたリスト、`vision_tokens` は画像読み取り部に入ったトークンの合計〕。`phases` の `denoise` には `dit_source`、`decode` には `vae_source` がいつも入る〔`"file"`／`"resident"`〕。VRAM 16GB mode のジョブは `phases.denoise.vram16` に上限・常駐数・分割の単位・割り当て器の再試行と OOM の回数の差分・`inactive_split` のピーク・退避の行き先〔`text_modules`〕が入る〔§6.5〕。A2V のジョブだけ、`phases` に `audio_encode`〔符号化した本数・サンプル数・潜在の形〕と `denoise.mask`、`decode` に `audio_output`〔`"original"`／`"decoded"`〕が入り、`h3` に `a2v`〔A2V の記録。アプリが `metadata.json` の最上位の `a2v` へ移す。キーの正本は仕様書 §6.6〕が加わる。A2V でないジョブの記録は変わらない）

### 映像 VAE の構成

符号化器と復号器に分け、別々にファイルから読む（裁定 33）。共通の部分（正規化の平均と標準偏差・空間タイルの分割・継ぎ目の混ぜ）は基底の型に置く。

- **`H3VideoEncoder`**（`encoder`＋`quant_conv`）: f32。精度の島は無い。I2V のジョブごとに 1 度だけ組んでキーフレームの画像を 1 枚ずつ符号化し、すぐ捨てる。T2V では組まない。戻り値は事後分布の平均を `latents_mean`／`std` で正規化した潜在である。
- **`H3VideoDecoder`**（`post_quant_conv`＋`decoder`）: bf16。精度の島（`post_quant_conv`・入力の埋め込み・出力の正規化・各ブロックの正規化とスケール）は f32。
- ファイルの名前の振り分けは `encoder_key_map`／`decoder_key_map` で行い、それぞれの型は自分のテンソルだけを持つので、読み残しは例外になる。

### 映像 VAE の特例

- 潜在フレームが 1 つ（T'=1）のときは、単独では復号が悪いので、5 つに複製して復号し、3 番目を取る。
- **復号は CPU 上の uint8 `[F, H, W, 3]` を返す**。窓ごとに確定した片（継ぎ目を混ぜた後）を、その場で正規化を戻し→clamp→×255→round→uint8 の順で変換して CPU へ移し、連結は CPU で行う（T'=1 の特例も同じ契約）。GPU に全フレームを置かないので、大きな画角でも復号の VRAM は窓の大きさで決まる。バッチは 1 だけを受ける。音声の復号は窓なしである。

### tokenizer の渡し方

テキストエンコーダの tokenizer は、記述子のカテゴリではなく**記述子の `assets.tokenizer_dir`** で渡す（LTX 2.3 の `gemma_root` と同じフォルダ方式）。アダプタが `load` の `tokenizer_dir` に写す。`<d>` などの追加特殊トークンは `tokenizer_config.json` にしか無いので、`tokenizer.json` だけでは足りず、ファイル一式を 1 つのフォルダとして扱う。I2V の画像プロセッサ（`preprocessor_config.json`）も同じフォルダから作る。追加特殊トークン 7 語が語彙の 151669〜151675 に入ることを、ロード時に検査する（入らなければ明示的に足す）。

### セルフテスト

`python -m engine_h3.worker --selftest-generate` が、`load`／`generate` を合成メッセージで直接呼んで全イベントを記録し、mp4 の SHA-256 と `done` を JSON で書く。`--image P`（先頭フレーム。`--keyframe 0=P` と同じ）と `--keyframe FRAME=PATH`（何度でも書ける。同じフレームを 2 度渡すと読み込みの前に断る）で I2V、`--keep-resident` で常駐を、`--vram16` で VRAM 16GB mode を、`--source-audio PATH` と `--audio-strength S` で A2V を試せる。回帰の基準の指紋 `0da6111c…` は、`--prompt` に第 1 弾の門 G5 のプロンプト（黄色いレインコートの女性の文。正確な文は `Docs/Outputs-archive/h3-gate3/g2_selftest_g5prompt.cmd`）を渡し、ほかはセルフテストの既定（640×384・124 フレーム・20 ステップ・seed 42・sdpa）で回したときのものである。既定のプロンプトのまま回すと別の指紋になり、一致しない（条件は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §167）。

## 10. 仮想環境

- **名前**: `.venv-engine-h3`。MULTI_ENGINE_DESIGN §5.3 の一覧に並ぶ、3 つ目のエンジン用仮想環境である。
- **torch を LTX に揃えない理由【オーナー裁定：裁定 11・16】**: comfy-kitchen の CUDA 拡張は CUDA 13 系の torch で効く。拡張自体は torch の DLL にリンクしていないので、CUDA 13 系でさえあれば torch の版は問わない。そのうえで、SageAttention・triton-windows などの周辺の実績がある版を選ぶ。既存の 2 系統の torch（CUDA 12.8 系）のままでは CUDA 拡張が使えない。
- **利用者側の条件**: NVIDIA ドライバ **R580 以上**（CUDA 13 系の下限）。GPU は **Turing（RTX 20 系）以降**（CUDA 13 で Pascal 以前が削除された）。動作を確かめたのは Ada（RTX 4070 Ti SUPER）と Ampere（RTX 3080 Laptop 16GB）で、Blackwell（RTX 50 系）は未確認、Turing は int8 が遅い経路になり SageAttention も使えず、動作も未確認である（裁定 38・43）。主メモリの推奨は 64GB で、32GB 機はページファイル（「システム管理」）を前提に短い生成を確認している。コミット量の山が 32GB を超えるのでページファイルに頼り、遅くなる場合がある（裁定 26・43。実測は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §167）。利用者向けの書き方（確かめた世代と未確認の世代の区別、主メモリと容量）は README の「ハードウェア要件の詳細」「対応する GPU 世代」と §7.6 にある。
- **作るのは導入バッチ**: `setup.bat` はこの仮想環境を作らない。`install-MiniMaxH3.bat` が `install_ltx.ps1` の `Ensure-EngineVenv`（H3 用の呼び出し）で作り（`-SkipVenv` を越える。物体追尾の `.venv-utils` と同じ形）、そのあと重みを取る。導入バッチの位置づけは MULTI_ENGINE_DESIGN §6.2。`setup.bat` の再実行では当て直されないので、freeze が変わったときは `install-MiniMaxH3.bat` を再実行する。
- **ライセンスの注意【オーナー裁定：裁定 36・41】**: `install_model.ps1` は、記述子の `id` が `MiniMaxH3` のときだけ、取得の前にライセンスの注意文（名称・利用できる地域・取得者の自己責任）と本文の URL を表示する。表示するだけで、同意の入力は求めない。記述子は `MiniMaxAI/MiniMax-H3` の `LICENSE` も取得して `models/MiniMaxH3/LICENSE` に置く（検査の行の鍵は `h3_license`。サーバーは読まないが、写しを手元に置くための行なので消さない）。NOTICE は作らない。利用者向けの文面は README の「ライセンス」節である。
- **容量が増える**: torch の版が既存の仮想環境と違うため、uv のハードリンク共有（MULTI_ENGINE_DESIGN §5.3「容量は心配しなくてよい」）が効かず、この仮想環境ぶんの数 GB がそのまま増える。実測値は freeze と記録簿を見る。必要空き容量の正本は README のハードウェア要件表である。
- **入れないもの**: torchaudio（CUDA 13 の Windows 版が torch の新しい版と組めず、H3 の経路は使わない）、diffsynth（部品は移植した）。
- **版の正本は `engine_h3/venv-engine-h3.freeze.txt`** である。手で作り直すときの仕様と、各版を選んだ理由は `engine_h3/engine_h3-venv-pyproject.toml` に書く。

- **性能**: 大きな画角でノイズ除去の段の VRAM が溢れる問題は、VRAM 16GB mode（§6.5）の on で消えた（開発機の機械の門。製品の条件で退避ゼロ。実測は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §169.3。1 ステップ約 20 秒〔同 §177〕）。配置後のオーナーの目視（B-G5）にも合格し、sage の 2 ブロックの値の差は採用した（裁定 53）。残るのは次の 2 点である。(1) 計測台の T1 で重い減速が出なかった理由は未解明のまま残している（オーナー裁定で追わない。同 §168.9）。(2) 快適上限の較正（台帳 §1-95）は、退避そのものの量で線を引く（同 §168.1）。LoRA（Turbo）は §6.6 で対応した。較正（§1-95）の計画では、LoRA の有無を条件に入れるかを確かめる。
- **LoRA の後続**: (1) 動画と音声に個別の強度を持たせる（台帳 §3-252。いまは `audio_strength` を送らず、1 本の強度が両方に効く）。(2) 加算の高速化（台帳 §3-253。費用は §6.6）。
- **PinkCherry Hybrid**: オーナーが PinkCherry Hybrid を置いて生成に成功した（実機の事実・2026-10-18）。構造が同じことの根拠は研究ノート §13.3（ComfyUI のコードの読解であり、実測ではない）。対応の保証は §12 のとおり後回し（Ref2VA の参照経路も後回し）。
- **m×n ≥ 2³¹ の CUDA 経路**: ソースの水準では限界が無いが、実測は台帳 §1-95（快適上限の較正）で行う。VRAM 16GB mode の on では行の塊で分割されるので届かず、off でだけ届きうる（算術による推測。扱いは §1-95 の計画で決める）。
- **中間のキーフレームの品質**: 実装は 0〜F−1 の任意の位置を受けるが、中間のフレームは ComfyUI だけの拡張で、比べられる正解データが無い。そこで品質はオーナーの目視で決め、go だった（第 2 弾の 2-G2。[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §170.10）。No-go のときの戻し方（規則表に「先頭と末尾だけ」の項目 `keyframe_ends_only` を足して位置を絞る）は要らなかった。
- **テキストエンコーダの int8 と bf16 の差**: 画像 2 枚のときに大きい件（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §170.7 (a)）は診断していない。台帳 §4-43。
- **快適上限の較正（台帳 §1-95）への含意**: 条件行はキーフレーム 1 枚につき grid 行増える（K 枚で K×grid 行）。系列が長くなるので、較正ではキーフレームの枚数も条件に入る。10 枚のときの VRAM の山は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §170.6 の 1-G4 に記録してある（条件行が 10 枚でも、ノイズ除去の山は 2 枚のときと同じ。山は復号で決まる）。
- **ヘッダの揺れのうち後回しにしたもの**: コミュニティ版の読み込み、非枝刈り版、groupsize の混在への対応範囲。
- **A2V の残り（§3.1）**: (1) 0 < m < 1 の品質には一次資料の評価が無く、目視でしか決められない（既定 0.5 はオーナーの目視で決めた。裁定 76）。(2) 映像のマスクの固定行に雑音増し 0.999 を掛けるか（ComfyUI）、clean のままにするか（DiffSynth）は、映像のマスクを使う台帳 §1-106 の計画で目視により決める。(3) 1 本の A2V ジョブで ffprobe が数回呼ばれる（前の検査・実行・mock。実装差分のレビュー R5 の M9。実害が小さいので後回し。[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §178）。(4) キーフレームの条件行は雑音増しが 0.999（`KEYFRAME_NOISE_AUG`。§3）に固定で、強度を変えられない（裁定 57）。これが先頭画像ありの A2V に硬さが残る一因かもしれない（推測。確かめていない）。
