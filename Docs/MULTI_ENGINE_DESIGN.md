## 1. 結論（この機能が何をするのか）

**ヘッダーのドロップダウンで、使う動画生成AIを切り替えられる。**

利用者から見た振る舞いはこうなる。

1. ヘッダーのドロップダウンに「LTX 2.3」「LTX 2.5」……とベースモデル名が並ぶ。導入済みかどうかも一緒に表示される。
2. 導入済みのものを選ぶと、**その場でモデルの読み込みが始まる**。押すボタンは無い。
3. 読み込みが終われば、そのベースモデルで生成できる。Settings のモデル選択欄（transformer＝動画モデル / text_encoder＝テキストエンコーダ / video_vae＝動画VAE / audio＝音声モデル）の中身も、選んだベースモデルのものへ入れ替わる。
4. 未導入のものを選ぶと「まず導入してください」と案内が出て、切り替えは行われない。ダウンロードはサーバーがやらない。

内部では、**利用者が選ぶ単位（ベースモデル）**と**推論実装の単位（エンジン系統）**を分けてある。この分離により、新しいモデルを足すときの重さが2通りに分かれる。

- **既存のエンジン系統でそのまま読める重みなら、記述ファイル（manifest）を1本足すだけで済む。**
- **既存の系統と依存関係やコードが同居できない世代・系統は、専用の推論エンジンと専用の Python 環境を新設する**（既存の系統には一切手を入れない）。**LTX 2.5 がこれに当たり**、将来の Wan なども同じ扱いになる。

## 2. 責任分界の大原則 — エンジン系統は記述子が決め、KVメタデータが照合する 【オーナー裁定】

### 2.1 何が何を決めるか

**どの推論エンジンで動かすかは、選択中のベースモデルの記述子（manifest）が決める。** 記述子の `engine_family` から Runner クラスを引き（`services/engines/__init__.py` の `runner_class_for`、呼び出しは `services/pipeline_manager.py`）、その系統の仮想環境とワーカーが起動する。

**重みファイルの中身（GGUFのKVメタデータ）は、その選択が正しいかを照合する材料である。** 読み込みの直前に、選ばれた transformer のKVから系統を導き、記述子が宣言する系統と突き合わせる。**食い違っていても自動では解決しない——422 で止めて、選び直しを案内する（fail loud）。**

> このtransformerはltxv 2.5.0（LTX 2.5）です。選択中のベースモデル「LTX 2.3」はLTX 2.3用のため読み込めません。ベースモデルに「LTX 2.5」を選んでください。

黙って別の系統に切り替えないのは、**「利用者が選んだつもりのもの」と「実際に動いたもの」が食い違う状態を作らない**ためである（§6.1 と同じ思想）。逆に照合を省くと、LTX 2.3 のワーカーへ LTX 2.5 の重みが渡り、意味の分からない場所で落ちる——あるいは落ちずに誤った数値が出る。**交差する組み合わせが「動いてしまわない」ことのほうが、正しい組み合わせが通ることよりも重要である。**

### 2.2 判別材料 — 自前GGUFのKVメタデータ

判別に使うのは、GGUF ファイル（このプロジェクトが配布する量子化済み重みの形式）が先頭に持っている **KVメタデータ**（キーと値の組。ファイルが自分自身を説明するための欄）である。**判別は2段の契約**で、1つのキーでは決めない。

| 段 | キー | 何を決めるか | 判定 |
|---|---|---|---|
| 1段目 | `general.architecture` | **系統**（どのモデル一族か）。LTX 系の重みは 2.3 も 2.5 も一律 `ltxv` | `ltxv` 以外は別系統の重みなので 422 |
| 2段目 | `model_version` | **世代**（同じ系統の中のバリアント）。`2.3.0` / `2.5.0` のように入っており、上位2桁で判定する | そのエンジンが動かせない世代なら 422 |

**2段そろって初めて判別が成立する。1段目だけでは 2.3 と 2.5 を区別できず、2段目だけでは Gemma のような別系統を弾けない**（実ファイル4本での検分は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §67.1・§68.2）。系統への対応表は `services/engines/__init__.py` の `FAMILY_BY_KV` で、`(ltxv, 2.3) → ltx` ／ `(ltxv, 2.5) → ltx25` の2行だけである。

**判定の対象は transformer カテゴリだけである。** 世代を名乗る刻印を持つのは transformer だけで、映像VAE・音声VAEは safetensors なのでKVを持たず、テキストエンコーダの GGUF は `general.architecture` を持つものの、**カテゴリ間の世代整合**（transformer が 2.5 なのに text_encoder が 2.3 用、という組み合わせの検出）は現時点のスコープ外である。

**キーが無いファイルは警告して通す。** 手元の正規の配布物・自家変換ファイルは2つのキーを必ず持つが、このプロジェクトの変換ツールを通していない持ち込みGGUFは持たないことがある。**キーが有って食い違うのは拒否、キーが無いのは WARNING を出して通す**——判別できない状態と、判別できて不一致な状態を、同じ扱いにしない。最終判断はエンジン自身のローダーに委ねる。

**記述子×KVの4組はすべて契約テストで固定してある**（LTX 2.3 の記述子×2.3のKV／LTX 2.5 の記述子×2.5のKV は通過、交差する2組は明示的な422）。

### 2.3 KVを読む経路

読み書きの分担は3つに分かれている。**読む・拾う・裁くを1本にまとめない**のがこの設計の要点である。

| モジュール | 役割 |
|---|---|
| `services/gguf_kv.py` | **読む**。GGUFヘッダを走査して、指定されたキーだけを文字列の辞書で返す。欲しいキーが揃った時点で読み止める。構造が壊れていれば `GgufParseError`。要求したキーがファイルに無いのは異常ではない（辞書に入らないだけ） |
| `services/model_registry.py` の `precheck_model_file` | **拾う**。軽量チェック（GGUFのマジックナンバー・safetensorsヘッダの妥当性）に加え、GGUFならKVの辞書も一緒に返す |
| `services/engines/__init__.py` の `check_kv` と、各アダプタの `check_kv` | **裁く**。前者が系統の照合（§2.1）、後者が系統内の判定（アーキテクチャ名・扱える世代）を行う。**裁きだけがエンジン固有の知識**なので、エンジン側に置いてある |

`gguf_kv.py` を独立モジュールにしてあるのは責務が別だからである——`model_registry.py` は「名前をパスへ解決する」役、`gguf_kv.py` は「ファイルの先頭を読んで辞書を返す」役で、後者はモデル管理の概念を一切知らない。おかげで単体テスト（`tests/test_gguf_kv.py`）が合成バイト列だけで完結し、実重みファイルを必要としない。

**パーサは自前である。** アプリ側の仮想環境（`.venv`）には GGUF パーサ用の `gguf` パッケージが入っておらず、入れると「アプリ venv は torch 無し」という前提（§5.3）が壊れる。読みたいのは文字列型のKVが2個だけなので、汎用パーサは要らない。なお `engine/gguf/loader_service.py` の `metadata()` は KV から埋め込みconfig JSON（`config` / `ltx.config` / `general.config`）を取り出すだけで、系統の判別には関与しない。

### 2.4 規約（契約）としての保証 【オーナー裁定】

**Nz-Videomni が扱うGGUFは、変換ツールも配布リポジトリも自前である。したがって「transformer のGGUFは `general.architecture` と `model_version` を必ず持つ」を規約として保証する。**

- 変換ツール `Nz-GGUF-Converter-LTX23` が両キーを書き出す（LTX 2.5 用プロファイルを含む）。**別リポジトリへの要求事項**なので、本書側で強制する手段は無い。
- 配布物（HuggingFace の `Rootport/Nz-LTX23-weights` ほか）も、利用者の自家変換ファイルも、同じツールの出力なので自動的に規約を満たす（実ファイルでの確認は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §67.1）。

将来 safetensors を直接読むエンジンを足すときは、GGUFのKVに相当するものが無い。その場合は **ComfyUI 方式のヘッダキー指紋**——safetensors ヘッダに並ぶテンソル名の特徴的な組み合わせを見てモデル種別を当てる方法——で対応できる。上流の LTX wheel（`ltx_pipelines/utils/constants.py` の `detect_params()`）には safetensors メタデータから `model_version` を読む前例もあり、そちらを流用してもよい。**安全に拡張できる余地があることだけ記録しておき、実装は必要になった時点でよい。**

### 2.5 フールプルーフは作らない。エラー品質で解決する 【オーナー裁定】

**「transformer に LTX 2.5 を選んだから VAE も自動で 2.5 に差し替える」といった自動選択・自動修正は作らない。組み合わせが不整合なら、エラーを出して止まる。**

理由は、自動修正が「利用者が意図してやった実験」まで勝手に書き換えてしまうためである。このプロジェクトは自家変換の重みを混ぜて使う利用者を想定しており、勝手な差し替えは害のほうが大きい。

ただし**エラーの質は上げる**。重みを実際に読み込む前——ワーカープロセスを起動する前——に、選ばれたファイルのKVを読んで整合を確かめ、食い違っていれば§2.1のような「次の一手を言う」文章で止める。これは自動修正ではなく**エラーメッセージの品質**の話であり、既存の `precheck_model_file`（数バイトだけ読む軽量チェック）と同じ位置に、同じ思想で足してある。

## 3. 概念モデル — 2つの軸を分ける

本設計の中核は、**「モデル」という1つの概念を、性質の違う2つの軸に分けること**である。

### 3.1 BaseModel（ベースモデル）— 利用者に見える単位

「LTX 2.3」「LTX 2.5」のような、**利用者が名前で認識し、ドロップダウンで選ぶ単位**。ベースモデル1つに対して、ドロップダウンの項目（「LTX 2.3」）・モデル置き場のディレクトリ（`models/LTX23/`）・記述ファイル（`scripts/manifests/10-ltx23.json`）が1対1で対応する。

「置き場所がそのまま所属の宣言になる」という現行の `models/` レイアウト（[`NEXT_SESSION_HANDOFF.md`](NEXT_SESSION_HANDOFF.md) §4）は、この軸にそのまま合致する。**現行レイアウトは変更しない。**

導入口はベースモデル別ではなく `setup.bat` の1本である（§6.2）。

### 3.2 EngineFamily（エンジン系統）— 推論実装の単位

「ltx」「ltx25」のような、**実際に計算を回す実装の単位**。エンジン系統ひとつが次の4つを所有する。

- 専用のワーカープロセス（`engine/worker.py`・`engine25/worker.py`）
- 専用の Python 仮想環境（`.venv-engine`・`.venv-engine-ltx25`）
- ワーカーへ送るペイロード（読み込み要求・生成要求の項目一覧）の形
- パラメータの制約と、扱える機能の範囲（§5.6）

### 3.3 2つの軸の関係 — ベースモデルからエンジン系統へは多対1

```text
BaseModel        EngineFamily
─────────        ────────────
LTX 2.3  ──────→ ltx        （engine/   + .venv-engine）
LTX 2.5  ──────→ ltx25      （engine25/ + .venv-engine-ltx25）

Wan 2.2  ──────→ wan        （将来）
```

写像は多対1である——同じエンジン系統に複数のベースモデルが載ることはありうる。**現在は2つのベースモデルがそれぞれ別の系統に載っており、1対1になっている。**

**LTX 2.5 が LTX 2.3 と同じ `ltx` 系統に載らなかった理由は2つある。どちらも「同居できない」という物理的な事実であり、設計の好みではない。**

1. **LTX 2.3 側の推論スタックには LTX 2.5 のコードが1行も入っていない。** `.venv-engine` が固定している公式パッケージ（`ltx-core` / `ltx-pipelines`）は2026年3月のコミット `00dc53d` で、LTX 2.5 に対応した公式 v1.2.0 の**5か月前**である。2.5 の読み込みに要るシンボルは1つも存在しない。「分岐を足す」のではなく「まだ書かれていないコードを持ち込む」話なので、既存の仮想環境の中では始まらない。
2. **テキストエンコーダの要求バージョンが同居できない。** LTX 2.3 は Gemma 3、LTX 2.5 は Gemma 4 を使い、Gemma 4 を扱えるのは `transformers` 5.8 以上である。1つのインタプリタに両方のバージョンを入れることはできない。

**別系統にしたことで守られたもの**: `engine/` と `.venv-engine`（LTX 2.3側）は**1バイトも変更していない**。同じシードでの LTX 2.3 の生成がビット単位まで従来どおりであることを実機で確認済みである（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §69.16）。**同居させていれば 2.3 の推論スタックを丸ごと上げることになり、既存の全機能を再検証する羽目になっていた。**

したがって新しいモデルを足すときの重さは、次の判断で決まる。

| 追加するもの | 必要な作業 |
|---|---|
| **既存のエンジン系統でそのまま読める重み** | 記述ファイルを1本足す。必要ならGGUF変換プロファイルを足す。**新しい仮想環境もワーカーも要らない** |
| **依存関係やコードが同居できない世代・系統**（LTX 2.5・将来の Wan 等） | 上記に加えて、専用ワーカー・専用仮想環境・専用アダプタを新設する。既存系統には手を入れない |

## 4. 記述子（SSOT）— ベースモデルの正体を宣言する

### 4.1 カテゴリ集合の正本は記述子である

**「このベースモデルがどのカテゴリのファイルでできているか」を宣言するのは記述ファイル（manifest）であり、コードの定数ではない。** コード側は「記述ファイルが言っているカテゴリ」を扱うだけの汎用処理になっている。

かつては同じ4カテゴリの定義がコードの6箇所（レジストリの定義本体・その順序タプル・API 2箇所・ワーカーペイロードの対応表・フロントエンドの定数）に散らばっており、カテゴリ構成が変わるたびに全部を直す必要があった。現在の残り方は次のとおりである。

- **カテゴリの定義本体は記述ファイルにある。** レジストリはそれを読んでスキャンする。
- `CATEGORIES`（モジュール定数のリテラル）だけは残してある。これを import している3ファイルを触らずに済ませるためである。
- フロントエンドの `MODEL_CATEGORIES`（`webui/src/shell/useModels.ts`）も**型の器として温存**している。撤去すると `ModelCategory` 型が `string` に退化し、カテゴリ名の打ち間違いをコンパイル時に検出できなくなるためである。**「何を何の順で表示するか」を決めるのはサーバー**（`GET /models` の応答）であり、この定数は綴りを固定しているだけで表示の決定権を持たない。

**カテゴリ集合そのものは4種のままで、可変にはしていない。** LTX 2.5 も transformer / text_encoder / video_vae / audio の同じ4種で、変わったのは中身（Gemma 4・2.5の畳み込みVAE）だけだった。**カテゴリ軸は製品の性質であってエンジン世代の性質ではない**——利用者から見て「動画モデル」「テキストエンコーダ」「動画VAE」「音声モデル」という4つの交換単位があるという事実は世代で変わらず、`state.json` もこの名前で選択を覚えている。4種を超えて増減させる一般化は、実際に必要になるまで行わない（§8.1）。

### 4.2 記述ファイルは2種類ある

置き場所は `scripts/manifests/` で、インストーラ `scripts/install_ltx.ps1` と同じものをサーバーも読む。インストーラはこの記述ファイルに完全に駆動されており（`Import-ModelManifests` が `scripts/manifests/*.json` を読み、スクリプト自体はモデル名を一切持たない）、スキーマ番号による版管理も形式検証（`Test-ManifestShape`。schema 1 と 2 の両方を受理する）も備わっている。

- **ベースモデル記述子**（`10-ltx23.json`・`20-ltx25.json`）— `engine_family` を持つ。**これだけがヘッダーのドロップダウン・ベースモデル一覧に出る。**
- **共有資産記述子**（`00-preprocessors.json` など）— `engine_family` を持たない。どのベースモデルからも参照される共有素材を記述する。`setup.bat` の「全部読んで全部入れる」経路には含まれるが、ベースモデル切替のUIには現れない。

### 4.3 記述子の形

```jsonc
{
  "schema": 2,
  "id": "LTX23",
  "display_name": "LTX 2.3",        // ドロップダウンに出す表示名
  "engine_family": "ltx",            // このベースモデルを動かすエンジン系統（§2.1）

  // このベースモデルが必要とするカテゴリの集合。
  // カテゴリごとに「どこを探すか」「どの拡張子を受け付けるか」「既定は何か」を宣言する。
  "categories": {
    "transformer": {
      "scan": ["LTX23/Weights"],
      "extensions": [".gguf"],
      "recursive": true,
      "default_file": "LTX23/Weights/LTX-2.3-22B-distilled-1.1-Q4_K_M.gguf"
    },
    "text_encoder": { "scan": ["LTX23/TextEncoder"], "extensions": [".gguf"],
                      "default_file": "LTX23/TextEncoder/gemma-3-12b-it-Q4_K_M.gguf" },
    "video_vae":   { "scan": ["LTX23/VAE"], "extensions": [".safetensors"], "name_hint": "video",
                      "default_file": "LTX23/VAE/LTX23_video_vae_bf16.safetensors" },
    "audio":       { "scan": ["LTX23/VAE"], "extensions": [".safetensors"], "name_hint": "audio",
                      "default_file": "LTX23/VAE/LTX23_audio_vae_bf16.safetensors" }
  },

  // 選び替えの対象ではないが読み込みに要るファイル（models/ 相対）。
  // カテゴリに混ぜるとドロップダウンに出てしまうので分けてある。
  "assets": {
    "gemma_root": "LTX23/TextEncoder/tokenizer",
    "spatial_upsampler_path": "LTX23/Upscaler/ltx-2.3-spatial-upscaler-x2-1.1.safetensors",
    "component_text_projection_path": "LTX23/TextEncoder/ltx-2.3_text_projection_bf16.safetensors",
    "component_video_vae_pruned_path": "LTX23/VAE/prunavaed/PrunaVAED-decoder-bf16.safetensors"
  },

  // 初回選択時の既定の組み合わせ（カテゴリ → 登録名）。
  "default_selection": {
    "transformer": "default", "text_encoder": "default",
    "video_vae": "default", "audio": "default"
  },

  "downloads": [ /* インストーラが読む */ ],
  "migrate":   [ /* インストーラが読む */ ]
}
```

補足が3点ある。

- **`default_selection` の値は、レジストリの登録名か予約センチネル `"default"` のいずれかでなければならない。** レジストリの走査は、既定パスと同一実体を指すファイルにスキャンで別名を作らない（既定パスと同じファイルは常に `"default"` という名前だけで参照する設計である）。ファイル名ベースで直接書くとその名前がレジストリに存在せず、`resolve()` が 404 を返す。ファイル名で指定したい場合は、config の明示登録map（`model.*_names` 相当）側にも同じ名前で登録しておく必要がある。
- **`assets` の内容は系統ごとに違う。** LTX 2.5 側の `assets` は空間アップスケーラ1つだけである——tokenizer とプロセッサのメタデータは**テキストエンコーダのGGUFの中**にあり、`engine25/assets_export.py` がそれをGGUFの隣へ書き出すためで、LTX 2.3 の `gemma_root` や text projection に相当するものは存在しない。**音声VAEはワーカーに必須だが `assets` へは入れない**（カテゴリ軸で届くので、二重に宣言すると整合先が2箇所になる）。
- 記述ファイルは既存のものにならって **UTF-8（BOM 付き）** で保存する。Python 側は `encoding="utf-8-sig"` で読む。

**この記述ファイルを、インストーラ（`downloads` / `migrate` を読む）・レジストリ（`categories` でスキャンする）・API（`categories` のキー集合でリクエストを検証する）・フロントエンド（`GET /models` の応答で受け取る）の4者が全員読む。** これが「散在の解消」の実体である。

### 4.4 ワーカーへ送る項目名はエンジンアダプタが持つ

**カテゴリ名からワーカーペイロードの項目名への対応表（`SELECTION_FIELDS`）は、記述ファイルではなくエンジンアダプタ側にある**（`services/engines/ltx/adapter.py`・`services/engines/ltx25/adapter.py`）。項目名はエンジン系統に属する知識であってベースモデルに属する知識ではないからである。**カテゴリ名（キー）は両系統とも同じ4種で、違うのは送る項目名（値）だけ**である。

置き場所そのものより大事なのは**二重定義を作らないこと**である。

- **`SELECTION_FIELDS` は写しではなく本体である。** ペイロードを組み立てる `_build_load_payload` がこの辞書を実際に読んで各項目を埋める。転記していないのでずれようがない。**参照されていない定義は作らない。**
- **記述子のカテゴリ集合との一致は契約テストで固定している**（`tests/test_base_model_contract.py`）。記述ファイルの `categories` のキー集合とアダプタの `SELECTION_FIELDS` のキー集合が一致しないとテストが落ちる。**記述ファイルに新しいカテゴリを足してアダプタ側を足し忘れると、そのカテゴリは黙って何もしない**——この「静かな失敗」だけを潰せばよく、そのためには定義を1本化するよりテストで縛るほうが確実である。

## 5. 層の構成

### 5.1 モデルレジストリと `GET /models`

**スキャンの根は記述ファイルの `categories[].scan`（配列）から取る。** ベースモデルごとに独立してスキャンし、結果もベースモデルごとに分ける。これにより LTX 2.3 と LTX 2.5 の transformer を同時に一覧できる（config の明示登録map経由なら、任意のパスを名前付きで登録して一覧に載せることも従来どおりできる）。

**`GET /models` の応答は、旧構造 `categories` を残したまま3層構造を並置する「加算」である。**

```jsonc
{
  "categories": { ... },            // 従来どおり。中身は「現在アクティブなベースモデル」のもの
  "active_base_model": "LTX23",
  "base_models": [                  // ベースモデル→カテゴリ→登録名 の3層はこちら
    {
      "id": "LTX23", "display_name": "LTX 2.3", "engine_family": "ltx",
      "active": true,
      "installed": true,            // 全カテゴリのファイルが実在する
      "present": true,              // 1つ以上のカテゴリのファイルが実在する
      "missing_categories": [],
      "category_order": ["transformer", "text_encoder", "video_vae", "audio"],
      "unsupported_features": [],   // §5.6
      "categories": { ... }
    },
    { "id": "LTX25", "installed": false, "present": true,
      "missing_categories": ["text_encoder", "video_vae", "audio"], ... }
  ]
}
```

置き換えではなく加算にしてあるのは、**`categories` を読んでいる既存の利用者が実在するから**である。Gradio 側のアダプタ（`gradio_ui/adapters.py`）がこの構造を直接読んでおり、置き換えれば同時に直す必要が出る。加算なら**その利用者は1文字も変えずに生き続ける**。

**`category_order` を配列で持つ理由**: カテゴリの表示順の正本は記述子のキー順（＝交換頻度順）であり、`categories` オブジェクトのキー順にも同じ並びが出ている。ところが**JSONオブジェクトのキー順は転送を越えて保たれるとは限らない**——サーバーもフロントエンドのコードも順序を保っているのに、AviUtl2 側のWebUIでは並びがアルファベット順になる現象が実際に起きた（疑いは唯一検証できていない AviUtl2 プラグインの WebView2 メッセージ経路に残る）。**配列の要素順にはこの曖昧さが無い**ので、順序は配列で運び、受け手はキー順に依存しない。

**`installed` と `present` を分けてあるのは、「未導入」と「一部だけ導入済み」を利用者に区別して見せるため**である。`present: false` なら「まだ導入されていません」と案内してAPIを叩かず、`present: true` かつ `installed: false` なら「一部未導入」と表示したうえで**サーバーに理由を言わせる**（§6.2）——フロントエンドが勝手に「たぶん無理だろう」と短絡しない、というのがこの2フィールドの目的である。

### 5.2 エンジンアダプタ

**エンジン系統ごとに1つのアダプタがある**（`services/engines/ltx/adapter.py`・`services/engines/ltx25/adapter.py`）。系統の対応表とディスパッチは `services/engines/__init__.py` が持つ。

- **対応表はアダプタのクラスではなく、モジュールパスを文字列で持つ**（`FAMILY_BY_ID`）。呼ばれた系統だけを `importlib` で解決するので、ベースモデルを列挙したいだけのプロセス（インストーラ・MCPサーバー・起動時の記述子検査）が、全アダプタを芋づるに読み込む代金を払わずに済む。
- **`ltx25` アダプタは `ltx` アダプタを継承している。** 共有しているのは `@@LTX@@` プロトコル・サブプロセスの起動と後始末・進捗の受け取り・mock バックエンドで、**エンジン世代で本当に違う事実だけ**を上書きする（どの仮想環境とワーカーか、どのワーカーログへ書くか、どのカテゴリがどのペイロード項目になるか、子プロセスに渡す環境変数、扱える機能の範囲）。
- **「汎用の EngineRunner」と「エンジン別アダプタ」への分割は行っていない。** 共有できたのはすでに1ファイルに固まっていた部分で、別ファイルへ切り出す実利が無かった。**分割の要否は3例目（Wan 等）が来たときに改めて判断する**（§8.1）。

**現行コードは書き直さない。** `_build_load_payload` は「ペイロードのキー集合と挿入順まで契約であり、`tests/test_model_swap_load.py` のゴールデンスナップショットで固定されている」と自身のドキュメント文字列に書いている。系統を足すときも、既存系統の振る舞いを変えないこと——変えていないことは、このゴールデンスナップショットが通り続けることで確認できる。

### 5.3 ワーカーと仮想環境 — エンジン系統ごとに1つ 【オーナー裁定】

**エンジン系統ごとに専用の Python 仮想環境を持つ。** アプリと推論の2プロセス・2仮想環境構成を、そのまま横に増やした形である。

```text
.venv                … アプリ（FastAPI）。torch 無し
.venv-engine         … ltx エンジン系統（LTX 2.3）。torch+cu128
.venv-engine-ltx25   … ltx25 エンジン系統（LTX 2.5）。torch+cu128
.venv-wan            … wan エンジン系統。torch+cu128（将来）
```

系統ごとに違うのは主に次の3点で、**これが「同じ仮想環境に同居できない」ことの実体**である（§3.3）。

| 項目 | ltx（LTX 2.3） | ltx25（LTX 2.5） |
|---|---|---|
| 公式パッケージ | `ltx-core` / `ltx-pipelines`（2026-03 の `00dc53d`） | 同（公式 **v1.2.0** = `d151147`） |
| `transformers` | Gemma 3 が動く版 | **5.14.1**（Gemma 4 には 5.8 以上が要る） |
| 高速化ライブラリ | `sageattention` あり | **無し**（`sage_available` は恒久的に false） |

`.venv-engine-ltx25` の確定記録は `engine25/venv-engine-ltx25.freeze.txt`（50パッケージ）。インストーラ側は、エンジン用仮想環境の構築を `Ensure-EngineVenv`（必須引数7つ）へ抽出して**2回呼ぶ**形にしてある。系統ごとにコピーを作らないのは、マーカー判定のロジックが2箇所へ分かれると最初の修正で食い違うためである。

**なぜアプリと推論で venv を分けるか**: (1) LTX 推論スタック（torch+cu128 と `ltx-core`・`ltx-pipelines` ほか）は PyPI ではなく PyTorch の cu128 wheel index から取る必要がある。(2) アプリ側スタックと推論側スタックは**両方ともトップレベルに `services` パッケージを持つため、同一インタプリタに同居できない**（import 時に衝突する）。この分離を新しいエンジン系統にもそのまま踏襲する。

#### 容量は心配しなくてよい

仮想環境を増やすと数GBずつ増える、という直感は**この構成では当たらない**。パッケージ管理ツール `uv` はダウンロードした実体を `.uv_cache/` に1つだけ置き、各仮想環境からはそこへ**ハードリンク**（同じファイル実体に別名を付けたもの）を張る。**実体は `.uv_cache` 側にあり、各仮想環境が示す容量はその別名を数え直した見かけの数字にすぎない。** したがって**同じバージョンの torch を使う限り、2つ目以降のエンジン用仮想環境を作っても物理的なディスク消費はほとんど増えない**（増えるのは、その系統にしか無い固有パッケージの分だけ）。実測値とハードリンク共有の確認手順は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §67.2 を参照。

> **この実測値は `.venv-engine-ltx25` を作る前のものである。** 追加後の再実測は [`PENDING_TASKS.md`](PENDING_TASKS.md) §3-107 で管理する（2系統とも torch 2.9.1+cu128 で揃っているため、増えたのは 2.5 にしか無いパッケージの分だけのはずだが、数字は取り直していない）。

**方針: 全エンジンで torch のバージョンを揃える 【オーナー裁定】。** 上の利点はバージョンが一致していて初めて成立する。揃えられない依存関係が出てきた場合は、容量が実際に増えることを承知のうえでオーナー判断を仰ぐこと。

**前提としてよい利用者像 【オーナー裁定】**: 「同時に導入するベースモデルは2〜3種類」を前提にしてよい。全ベースモデルを同時に置ける前提での容量最適化は不要である。

### 5.4 状態の3層憲章 【オーナー裁定】

**設定・実行時状態・端末の好みを、3つの置き場所へはっきり分ける。**

| 層 | 置き場所 | 誰が書くか | 何を持つか |
|---|---|---|---|
| **設定** | `config.yaml` | 人と、自動移行時のインストーラ。**サーバーは読むだけ** | **ユーザーの上書き・好みのみ**（明示登録map・プリセット・上限値・VRAMのつまみ）。**モデルの既定パスは持たない** |
| **実行時状態** | `state.json` | **サーバーだけ** | 最後に使ったベースモデル。ベースモデル別の「最後に使った組み合わせ」 |
| **端末のUIの好み** | ブラウザの localStorage | フロントエンドだけ | 表示言語・テーマ・高速化設定・NAGの文面・プリフィル方針（`nzvideomni.lang` / `.theme` / `.acceleration` / `.nagNegativeText` / `.prefillSizePolicy` / `.prefillFpsPolicy` の6キー） |

**モデルの既定パスの正本は記述子である。** インストーラも実行時のサーバーも同じ記述ファイルを読むので、「インストーラが認識するモデル構成」と「config が持つ既定パス」を同期し続けるコストは無い。config.yaml 側には**明示登録map（`model.*_names` 相当）だけを上書き手段として残してある**——利用者が自家変換ファイルを任意のパスで登録できる仕組みは、ベースモデル軸の有無と無関係に必要だからである。

**サーバーは `config.yaml` を書かない。** `config.py` は読み込み専用で、実行中に YAML を書き出す処理は無い。**この性質は維持する。**

#### `state.json`

ドロップダウンを切り替えたとき、Settings のモデル選択欄に何を初期値として出すかを決める必要がある（§6.3）。「前回このベースモデルで使った組み合わせ」を覚えておく場所がこれである。localStorage は端末の好みであってサーバーの状態ではないので、そこへ置くのは層の混同になる。

**置き場所はリポジトリのルート直下**（実装は `services/runtime_state.py`、設定上の位置は `AppConfig.state_file`。`.gitignore` に `/state.json` と `/state.json.bad` を登録済み）。`models/` 配下を選ばなかったのは、**`models/` は「重みファイルの置き場」という単一の意味を持つ場所**であり、そこにサーバーの実行時状態を混ぜると、利用者がモデルフォルダを丸ごと移動・削除したときに状態も道連れになるためである。[`STORAGE_POLICY.md`](STORAGE_POLICY.md) は Outputs（宝物）と Uploads（一時置き場）の設計正本だが、**`state.json` はそのどちらでもない**——生成物でも入力素材でもなく、消えても再生成される付箋にすぎない。

```jsonc
{
  "schema": 1,
  "active_base_model": "LTX23",
  "selections": {
    "LTX23": { "transformer": "Sulphur-2-base-distil-Q4_K_M",
               "text_encoder": "default", "video_vae": "default", "audio": "default" }
  }
}
```

- **読むのは起動時の1回だけ**。実行中に読み直さない（サーバーが唯一の書き手なので、読み直す理由が無い）。
- **書くのは読み込みが成功したときだけ**（§6.3の「失敗した組み合わせを覚えない」に対応）。一時ファイルへ書いてから差し替える原子的な方式なので、途中で電源が落ちても中途半端なファイルが残らない。
- **壊れていても止まらない**。JSONとして読めなければ WARNING を出し、`state.json.bad` へ退避して既定の組み合わせで起動する。未知のベースモデルidなら先頭のベースモデルへ落とす。書き込み失敗も WARNING を残して続行する。

#### LoRA はベースモデル軸を持たない

config.yaml の `lora_dir`（Style LoRA の置き場）と `ic_loras`（IC-LoRA アダプタの明示登録）は記述子へ移していない。したがって LoRA は現在ベースモデル軸を持たず、どのベースモデルを選んでいても同じ1本のディレクトリを見る。LoRA が**モデルの読み込み時ではなくジョブごとに適用される**別系統の資産であり、カテゴリとはライフサイクルが違うためである。**LTX 2.5 用の LoRA が実在するようになった時点で必要になる話**なので、[`PENDING_TASKS.md`](PENDING_TASKS.md) §3-102 が受け皿になっている。

### 5.5 API

**いずれも加算のみ**——既存フィールドの意味は変えない。契約の正本は [`../Videomni_Backend_Specification.md`](../Videomni_Backend_Specification.md) §6.9 で、本節は設計意図の記録である。

**(a) `POST /pipeline/load` の `base_model`**: リクエストに `base_model` を足した（省略時は現在のベースモデル）。現在のものと違えば、旧ワーカーを落としてから新しい系統のワーカーを起こす。`base_model` だけを送って `models` を省略した呼び出し（「ベースモデルだけ切り替えたい」という自然な呼び方）も効くようになっており、「同一選択なら作り直さない」という no-op 判定にも `base_model` を含めてある。

**ベースモデルを変えるときは、`"default"` のカテゴリも含めて全カテゴリを明示パスとして渡す。** ベースモデルが変われば `"default"` の指す先が別のファイルに変わるので、載せないままにすると**中身を一度も確かめないまま別世代の重みをワーカーへ渡す**ことになり、§2.1のKV照合が働くべき場所を素通りしてしまう。**代償**として、一度ベースモデルを切り替えた後のボディ無しロードのペイロードは「旧ペイロードとバイト同一」ではなく「値が同一」に格下げされる（同じファイルパスが、同じキーに、同じ順序で入る）。**ベースモデルを一度も切り替えていない限り、バイト同一の保証はそのまま生きる。** 登録名は `"default"` のままなので、画面の表示・no-op判定・`metadata.json` の `name` はいずれも変わらない。

**(b) `GET /status` の `state` と `base_model`**: サーバー内部には `unloaded` / `loading` / `ready` / `running` / `error` の5状態があるが、従来は `pipeline_loaded`（真偽値）しか外に出ておらず、**`loading`（読み込み中）が外部から観測できなかった**。フィールドを1つ足すだけで観測できるようになったのは、モデルの読み込みが呼び出し元をブロックする同期処理でも、**その間 `GET /status` は別のリクエストとして通る**（FastAPI が別スレッドで処理する）ためである。値の語彙は `POST /pipeline/load` の応答に既にある `state` と揃えてある。

### 5.6 エンジンごとの機能スコープ — `unsupported_features` と 422 `FEATURE_UNSUPPORTED`

**エンジン系統が2つあると、「このエンジンにはこの機能が無い」という状態が発生する。** §7が「エンジン別のUIパラメータ制約は作らない」と決めているのはパラメータの**刻みや倍数**の話であって、**機能そのものの有無**はそれとは別で、避けて通れない。LTX 2.5 の現行範囲は基本生成（テキストから動画／画像から動画 ＋ 畳み込みVAE ＋ 16GB運用）と、**クリップ連結（Chained）・V2V 継続・A2V〔Single・長尺・バッチ〕（いずれも 2026-08-23 に追加）**、**スタイルLoRA と IC-LoRA〔参照動画による制御。長尺＝クリップ別の参照窓を含む〕（2026-08-24 に追加）**、**高速化2つ＝fused GGUF逆量子化カーネルと先読み block swap〔いずれも既定 on。2026-08-24 に追加〕**、**モデル骨格の常駐＝`keep_resident`〔既定 off のオプトイン。2026-08-25 に追加〕**で、Retake・End source・Outpainting・NAG などは持っていない。

**LTX 2.5 が現在宣言している `unsupported_features` は7件である**（LTX 2.3 は0件＝空配列）。内訳は**連結生成に重ねる2つのモード**（`retake` / `end_source`）と、**単発生成の拒否表から自動的に作られる5件**（`two_stage_hq` / `outpaint` / `nag` / `prune_vaed` / `sage_attention`）である。**`chain` / `v2v` / `a2v` は 2026-08-23 に、`loras` / `reference_video` は 2026-08-24 にこの一覧から外れた**——素の連結生成・V2V 継続・A2V・LoRA・参照動画が動くようになったので、宣言を残すと動くタブやパネルを灰色にしてしまうためである（`a2v` は Chained タブの音声カードに加え、Single タブの A2V とバッチ A2V の灰色化にも使われている）。

> **高速化第2弾（2026-08-25）で、この配列が初めて動いた（8件 → 7件）。** モデル骨格の常駐（`keep_resident`）は**もともと 422 で断っていた機能**なので、開通させると3つの表（`REJECT_TABLE` / `CHAIN_REJECT_TABLE` / `unsupported_features`）から1行ずつ消える。**「断っていた機能を開ける」ときと「無視していた項目を効かせる」ときとで、動く表が違う**——前者では4分類の対応表に加えてこの配列も動き、**画面のグレーアウトが1つ解ける**。それでも**フロントエンド本体の変更は0行**だった（Settings 画面はこの配列を読んでいないため。触ったのはモックの2箇所だけである）。実測は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §76.4。

> **高速化第1弾（2026-08-24）では `unsupported_features` は動いていない。** fused GGUF逆量子化カーネル（`fused_gguf_dequant_kernel`）と先読み block swap（`block_swap_prefetch`）は、もともと**「無視＋ログ」の側にあった項目**であって、`unsupported_features` で断っていた機能ではない。動いたのは4分類の対応表だけ（**「無視＋ログ」から「動作」へ2件ずつ**）で、**422 の表・従属の表・`unsupported_features` はいずれも無変更**である。したがって**画面のグレーアウトも1つも変わらず、フロントエンドのコードは1行も触っていない**。実測は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §75.5。

**(1) 判断の主体はエンジンアダプタ1箇所。** 「何が使えないか」を宣言するのはアダプタ（`services/engines/ltx25/adapter.py`）だけで、API層は**系統名を渡して取り次ぐだけ**である。API層が系統ごとの機能表を持ち始めると、同じ表が2箇所に生まれて必ずずれる。宣言していない系統（`ltx`）は素通りするので、**LTX 2.3 から見た振る舞いは1バイトも変わらない**。

**(2) 強制するのは常にサーバー。エラーは 422 `FEATURE_UNSUPPORTED`。** ジョブを作る前に、他のどの検証よりも先に拒否する——素材の有無より前に「そのエンジンにその機能が無い」と答えないと、利用者は直しようのないものを直しに行くことになるためである。連結生成の一族（Chained・Retake・End source・V2V・A2V）はすべて `POST /generate/chain` から来るが、**「この一族を丸ごと扱えるか」ではなく「リクエストのどのフィールドが扱えないか」を答える**——2026-08-23 以降、LTX 2.5 は素のChained・V2V 継続・A2V を走らせ、その上に重ねる残り2つのモード（Retake・End source）だけを断るようになったためである。したがって取り次ぎの関数はリクエスト本体を受け取る（`engines.reject_chain(family, request)`）。

**(3) 先回りは `GET /models` の加算で行う。** `base_models[]` の各要素に `unsupported_features`（機能名の配列）がある。フロントエンドはこれを読み、選択中のベースモデルで**押しても必ず断られる操作**を押させないようにする（タブとパネルのグレーアウト）。**これはあくまで先回りであって強制ではない**——強制は常に(2)のサーバー側である。

> **省略は「制限なし」であって「全部だめ」ではない。** LTX 2.3 側は空配列を返すので、既存クライアントから見た応答は1バイトも変わらない。フィールドそのものを知らない古いバックエンドに対しても、フロントエンドは「制限なし」として扱う。

リクエストの各フィールドをどう扱うかは、**4分類の対応表として宣言してある**（`GenerateRequest` の全フィールドが必ずどれか1つに属することを機械検証するテスト付き。将来フィールドが増えたらそのテストが落ち、対応表の更新が強制される）。

| 分類 | 扱い |
|---|---|
| **422** | 既定値と違えば `FEATURE_UNSUPPORTED`。**判定は常に「既定と違うか」であって「有るか」ではない**——フロントエンドは毎回スキーマ全体を送るため、既定値のまま届いたフィールドは利用者が求めたものではない |
| **無視＋ログ** | 拒否すると敵対的になるもの。フロントエンドは毎回スキーマ全体を送るので、素のT2V要求にもこれらが必ず載ってくる。**2026-08-24以降ここに残っているのは1種類だけ**——蒸留版2.5にはCFG（プロンプトへの従い具合の制御）もステップ数の概念も無い、という理由の項目である（`negative_prompt`／`guidance_scale`／`num_inference_steps`／`neg_method`／`vsf_scale`）。**高速化2つ（`fused_gguf_dequant_kernel`／`block_swap_prefetch`）は同日この分類を抜けて「動作」へ移った**——LTX 2.5でも既定onで実際に効くようになったため、「無視」のまま置くと嘘になる（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §75） |
| **動作** | そのまま効く。`crop_output` は完成したmp4への後処理（ffmpeg）でエンジンに依存しないため、ここに入れて**黙って消さない** |
| **従属** | 上位のフィールドが既定のままなら意味を持たない従属パラメータ。上位が422側にあるので、これらが意味を持つリクエストは上位の時点で既に断られている |

**「無視」と「従属」を分けてある**のは、「無視」が「それでもジョブは走る」という約束を含むためである。従属パラメータはそもそも走るジョブに到達できないので、同じ箱に入れると嘘になる。

**この4分類の表はスキーマごとに1つある**——単発生成（`GenerateRequest`）用と連結生成（`GenerateChainRequest`）用の2つで、同じフィールド名でもスキーマが違えば答えが違うためである（`clips` や `stage2_window` は連結側にしか無く、`outpaint` は単発側にしか無い）。1つの表を両方に使い回すと「このスキーマのときだけ例外」という但し書きが要り、それは監査テストが防ごうとしているものそのものになる。

**どのフィールドがどの分類かの正本は [`../Videomni_Backend_Specification.md`](../Videomni_Backend_Specification.md) §6.10 である**（件数も含め、本書には転記しない。単発生成は同 (d)、連結生成は同 (f)）。実測記録は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §69.9（単発）・§72.4（連結）・§74.5（スタイルLoRAとIC-LoRAの開通で両方の分類が動いたときの実測）。

### 5.7 参考: 16GB対応のための改変は生成品質に影響しない（人間向けの注釈）

**結論から言うと、LTX 2.5エンジンの16GB対応は、公式コードの計算式そのものを1つも変えていない。**変えたのは「重みをどこに置くか」と「計算をどう分割するか」だけであり、品質への影響は**GPU内部の計算順序のゆらぎ**級にとどまる。

| 改変 | 数値への影響 | 根拠 |
|---|---|---|
| Q4量子化（4bitへ圧縮した）重みの常駐＋層単位の逆量子化（元の精度へ戻す処理） | ゼロ | 逆量子化は決定的な算術で、いつ展開しても同じ値になる |
| block swap（重みをCPUとGPUの間で移動させる仕組み） | ゼロ | 破棄→再構築を3周させても出力が最終桁まで一致（§69のG2） |
| テキストエンコーダーの層オフロード（GPUへ載せる層数の調整） | ゼロ | GPU常駐層数0／8／48の3構成で隠れ状態がビット一致（§69のG3） |
| aggregate射影（まとめて行う行列積）のチャンク化（小分けにする処理） | ゆらぎ級 | 数学的には等価だが、cuBLASが出力幅ごとにカーネルを選び直すためビット単位では一致しない。刻み幅を定数として固定してあるので決定性（同じ入力なら毎回同じ出力になる性質）は保たれる |
| cudnn.deterministic固定（計算順序を毎回同じにする設定） | ゆらぎ級 | 総和の順序を固定するだけの変更で、速度コストは実測誤差以下 |
| euler_ancestralサンプラー（ノイズ除去の手順）の強制ON | 公式挙動の復元 | GGUF経由だと公式の自動判定が壊れて別世代のサンプラーへ落ちてしまうのを、明示指定で直したもの |
| VAE・アップスケーラー・sigmas・サンプラー本体 | 無改変 | 公式コードのまま |

**比較の目安**: sdpa（通常の注意機構）からsage attention（近似計算を含む高速化）への切り替えや、通常VAEからPrunaVAED（圧縮率を上げたVAE）への切り替えのほうが、本件より大きな差を生む。

**注意——これはエンジンの差ではなく「重みと設定の選び方」による差である。**同じ重みをComfyUI公式ワークフローで動かした場合との違いは3点ある。(1) ComfyUIは拡散デコーダー版のVAEを使うが、本エンジンv1はConv版のまま（§3-103で保留）。(2) ComfyUIはプロンプト拡張（小型のGemma 4でプロンプトを自動で書き足す機能）が既定ONだが、本エンジンはOFF。(3) Stage-2の入口sigma（ノイズの強さの初期値）はComfyUIが0.85・公式Pythonが0.909375で、本エンジンは公式Python準拠。Stage-1の8ステップぶんのsigmasはバイト一致している。目視で差が出た場合は、まず(1)(2)を疑うとよい。

## 6. 利用者から見た振る舞い（UX仕様）【オーナー裁定】

### 6.1 切り替え＝即ロード

**ドロップダウンでベースモデルを選んだ瞬間に、モデルの読み込みが始まる。** 内部的には、Settings の「Load selected models」ボタンを1回押したのと同じ処理が自動で走る。

**「選択中とロード済みが食い違っている」という状態を作らない**のがこの仕様の目的である。ドロップダウンが「LTX 2.5」を指しているのに動いているのは LTX 2.3、という状況は、利用者にとって説明のしようがない。

### 6.2 4つのガード

| # | 状況 | 振る舞い |
|---|---|---|
| (1) | **生成ジョブの実行中** | 切り替えできない。既存の 409 `JOB_BUSY` をそのまま使う |
| (2) | **未導入のベースモデルを選んだ** | ドロップダウンの項目自体に導入済み／未導入を表示する。未導入を選んだ場合は導入を促す案内を出し、切り替えを中止して元の選択へ戻す。**案内の文面はいまのところバッチファイル名を出さない汎用のもの**（「まだ導入されていません。導入手順に従って重みファイルを配置してから、もう一度選び直してください」）。**ベースモデル別のバッチが実在するようになったら、この文面はバッチ名を名指しする形へ戻してよい**（[`PENDING_TASKS.md`](PENDING_TASKS.md) §3-111） |
| (3) | **ロード中の二重切替** | 409 `PIPELINE_LOADING` で断る（下記） |
| (4) | **失敗時のUI復帰** | 切り替えが409／503で失敗したとき、フロントエンドのドロップダウンは選択中の表示を**元の（切り替え前の）ベースモデルへ必ず戻す**。ただし**黙って戻すのではなく、理由を必ず伝える**——選んだ表示のまま止まると §6.1 が禁じる食い違い状態そのものになり、無言で戻ると利用者は自分の操作が届いたのか判断できない |

**ガード(3) の実装は2点が要点である。**

**(i) 判定はAPI層ではなく `PipelineManager` のロックの中で行う。** API層で `pm.state` を読んでから `pm.load()` を呼ぶまでの間に別のリクエストが割り込めば、2本とも「読み込み中ではない」と判断して通ってしまう。**状態を見る場所と状態を変える場所は同じロックの中でなければならない**ので、判定は `state = LOADING` を代入するのと同じ `with self._lock:` の中に置いてある。

**(ii) `POST /pipeline/unload` にはこのガードを置かない。** 一見「読み込み中なら unload も断るべき」に思えるが逆である。**`unload` は、読み込みが異常終了して状態が `loading` のまま張り付いたときの唯一の復帰路**だからである。ここに409を置くと、張り付いた状態から抜け出す手段がサーバー再起動しか無くなる。**「二重ロードを防ぐ」ことと「詰まりを解消する」ことは別の目的であり、後者を前者の巻き添えにしない。**

**自動ロード経由のときは 409 がそのまま出ない。** `auto_load_on_generate` が有効な状態で読み込み中に生成を投げると、409 は生成ジョブの中で起きるため `generation_failed`（ジョブの失敗）に包まれて返る。**利用者が読むのは包まれた側のメッセージ**なので、そこに「読み込み中である」と分かる文言が残ることをテストで固定してある。

**ダウンロードはサーバーの責務にしない 【オーナー裁定】。** サーバーが数十GBのダウンロードを開始する設計は、進捗表示・中断・再開・失敗時の後始末をすべてサーバー側に抱え込むことになる。導入はバッチファイル（`setup.bat` とその仲間）の役目である。

**導入口は「本体＋ベースモデル別」の2階建てである 【オーナー裁定】。** `setup.bat` は **Nz-Videomni 本体のインストーラ**であり、最初に試していただくAIとして **LTX 2.3 だけを一緒に導入する**（お試し用の1本という位置づけである）。**別のベースモデルは、そのモデル専用の導入バッチで足す**——ダブルクリックすると、ダウンロード → 配置 → ドロップダウンで選べる状態、までが一続きで走るものを想定している。

> **ベースモデル別の導入バッチそのものは別スコープで設計する**（[`PENDING_TASKS.md`](PENDING_TASKS.md) §3-111）。設計には「どの記述子をどのバッチが担当するか」のスイッチが要る——現行の `scripts/install_ltx.ps1` は `scripts/manifests/*.json` を一括で読むため、`20-ltx25.json` の `downloads[]` を埋めた瞬間に `setup.bat` が LTX 2.5 まで取りにいってしまう（本体を入れるだけで 60GB 超のダウンロードになる）。**そのスイッチができるまで `20-ltx25.json` の `downloads[]` は空のままにしておく**——`setup.bat` が LTX 2.5 を取りにいかないのは意図どおりの状態である。
>
> **未導入のベースモデルを選んだときの案内文は、いまは汎用の文面のままにしておく**（バッチ名を出さない。上のガード(2)）。**名指しへ戻すのは、そのバッチが実在するようになってからである**——存在しないファイルの実行を促す案内は出せないためである。

### 6.3 切り替えたとき、Settings のモデル選択欄に何が入るか

| 場面 | 初期値 |
|---|---|
| そのベースモデルを**初めて**選んだとき | 記述ファイルの `default_selection` |
| **2回目以降** | `state.json` が覚えている「そのベースモデルで最後に使った組み合わせ」 |

「最後に使った組み合わせ」は、**読み込みが成功したときに更新する**（失敗した組み合わせを覚えて次回も同じ失敗を繰り返す事態を避けるため）。

### 6.4 「デフォルトに戻す」ボタン（未実装）

Settings のモデル選択欄に、既定の組み合わせへ戻すボタンを置く。押したときの処理は、①`default_selection` が指すファイルが実際に揃っているかを確かめる、②揃っていれば適用する、③欠けていれば汎用の導入案内を出す（バッチファイル名は出さない。**サーバーはダウンロードしない**。名指しへ戻す条件は §6.2 と同じく[`PENDING_TASKS.md`](PENDING_TASKS.md) §3-111）の順である。**このボタン自体はまだ実装していない。**

### 6.5 ヘッダーの状態バッジ

ヘッダーの状態バッジは7種類ある——`checking`（確認中）/ `bridge-unavailable`（ブリッジ未接続）/ `offline`（サーバー停止）/ `online`（稼働中）/ `busy`（生成中）/ `loading-models`（モデル読み込み中）/ `error`（エラー）（`webui/src/modes/single/StatusHeader.tsx`）。

**`loading-models` は §5.5(b) の `state` フィールドとセットで意味を持つ。** これが無いと、モデルの読み込み中もヘッダーは `online`（稼働中）のまま数分間留まる——`GET /status` へのフェッチ自体は成功し続けるためで、利用者からは「切り替えが終わって使える状態になった」と読めてしまい、生成を試みて失敗する。バッジだけを足しても判定材料が無く、フィールドだけを足しても利用者には見えない。

## 7. スコープ外 — エンジン別のUIパラメータ制約 【オーナー裁定】

**エンジンごとに違うパラメータ制約（フレーム数の刻み・解像度の倍数など）をUIが切り替える機能は、まだ作らない。**

現在の2系統はどちらも LTX 系なので、フレーム数の `8n+1` 規約（LTXの映像VAEが時間方向を8分の1に圧縮し、因果的な先頭1フレームが加わることに由来する）を共有しており、必要になっていない。

**この対応が「定数を1つ差し替えれば済む」話ではないことは記録しておく。** 規約の出どころは `chain_math.py` の定数

```python
VIDEO_TIME_FACTOR = 8            # 映像VAEの時間圧縮率
AUDIO_LATENTS_PER_SEC = 25.0     # 16000 / 160 / 4
```

だが、実装は定数を共有しているのではなく**規約だけが伝播し、独立したリテラルとして複数箇所に散らばっている**。`api/models.py` だけでも `8` という数値が `chain_math` を参照せず5箇所（`:342`・`:377`・`:515`・`:582`・`:587`）に直書きされており、フロントエンド側にも独立実装がある（例: `webui/src/bridge/mockBridge.ts:1014` の `(numFrames - 1) % 8 !== 0`）。**エンジン別化に着手するときは、これらをすべて洗い出す必要がある。**


## 8. 段階分割と検証の戦略

### 8.1 抽象の正しさは2例目で実証する 【オーナー裁定】

**「将来いろいろなモデルを載せられる作り」を、1例しか無い状態で完成させようとしない。** 抽象化が正しかったかどうかは、2例目を載せてみるまで分からない。1例しか無いうちに凝った作りにすると、2例目が来たときに「想定と違った」という理由で作り直すことになる——**過剰抽象化は、抽象化しないのと同じくらい手戻りを生む。**

この原則は実際に効いた。2例目（LTX 2.5）を載せたとき、当初「LTX 2.5 は ltx 系統のまま載る」と見込んでいた点が外れたが、**先回りして作り込んでいなかったので、訂正は表の書き換えで済んだ**。ベースモデル軸とエンジン系統軸を分けた設計そのものは正しく、外れたのは「LTX 2.5 がどちらの軸に載るか」という当てはめだけだった。**同じ理由で、3例目が来るまで判断を保留している事項がいくつかある**——汎用 `EngineRunner` への分割（§5.2）、mock バックエンドの共通化（§9.1）、カテゴリ集合の可変化（§4.1）である。

### 8.2 土台整備と2例目は抱き合わせで行う

土台だけを先に作って寝かせない。**土台と2例目を1つのテーマとして進める**ことで、抽象が正しかったかどうかがその場で判明する。実際、第1段階（土台）と第2段階（LTX 2.5）は連続したテーマとして実施し、2例目でベースモデル軸とエンジン系統軸の両方を同時に実証した。

### 8.4 コミット分割とゲートの作法

両段階で共通の進め方であり、次に系統を足すときも踏襲する。

- **分割の基準は「何をしたコミットか一言で言えること」。** 特に**「引っ越しだけのコミット」と「振る舞いを変えるコミット」を混ぜない**——移動と変更が同じ差分に入ると、ゴールデンスナップショットが落ちたときに原因が引っ越しなのか変更なのか判別できなくなる。
- **フェーズごとに1つずつゲートを置き、前の段が合格しない限り次へ進まない。** ゲートは2種類ある——**機械ゲート**（エージェントが実行できるもの。自己診断・pytest・バイト一致）と、**実機ゲート**（実GPUで実際に動画を作るもの）である。
- **実機ゲートの実施中はコードを1行も変えない。** 作業ツリーが直前のコミットとバイト同一であることが、測った対象がそのコミットだと言える根拠になる。

#### 続き: スタイルLoRA と IC-LoRA（参照動画による制御・長尺を含む）（2026-08-24）

**§3-102 の第3段であり、必須級として残っていた最後の2件である。** スタイルLoRA（絵柄を寄せる追加学習ファイル）と IC-LoRA（参照動画から輪郭線・骨格・深度などの制御信号を作って生成を導く仕組み）は、LoRAを取り付ける経路と参照動画を条件として足す経路が同じ部品の上に乗るため、**1つの計画**として実装した。クリップごとに参照動画の担当区間を切り出す長尺IC-LoRAも同じ段に含めている。

**設計上の要点は4つある。**

1. **LoRAの取り付けは「付ける／外す」を必ず対で書く。** 取り付け位置は 2.3 と同じくモデルを組み立てた直後・ブロックをGPUへ配る直前で、**LoRAが無いときは明示的に外す**形にしてある。連結生成は1つのジョブでモデルを何度も組み直すため、「付ける」だけでは前のクリップのLoRAが残りうる。**毎回どちらかを必ず通るので、その芽が構造的に消える。** LoRAの状態はパイプラインの段（`Ltx25DiffusionStage`）が持ち、ジョブの開始時に必ずクリアされる。
2. **参照動画の条件付けは新しいモジュール（`engine25/reference25.py`）に閉じ込め、公式関数を一時的に差し替える方式で足す。** LTX 2.5 の公式パイプラインには参照を足す差し込み口が無いためで、差し替えと元通しは必ず対（例外が出ても戻す）にしてある。差し替え先の関数の在り処・引数・内部の式は照合検査（`verify()`）で固定してあり、公式パッケージ側が変わったら気づける。
3. **連結生成では、参照条件を全セグメントぶん最初に作り切る。** 2.5 の映像エンコーダは呼び出しの中でしか生きないので、2.3 のような遅延方式が取れない。**エンコーダを1回組み立てるその場で全クリップぶんを作り、以後は小さな潜在表現だけを持ち回る**（512×384・49フレームで1セグメントあたり約70KB）。
4. **前処理（canny／dwpose／depth）は LTX 2.3 と同じコードを共有する。** `engine/preprocess/` は公式パッケージに依存しないため、2.5 用の仮想環境に依存を2行足すだけで動く。**エンジンごとに前処理を二重に持たない**という判断で、その正しさは実機で裏づけが取れた——同じ素材から 2.3 と 2.5 が書いた制御動画の SHA-256 が完全に一致している（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §74.7(f)）。

**公式との差を2点、意図して作っている。** ①**LoRAを Stage-1・Stage-2 の両方へ適用する**（公式の IC-LoRA パイプラインは Stage-1 のみ。LTX 2.3 に揃えた）。②**参照アイテムのノイズ側の扱いが 2.3 と実装レベルで違う**（2.5 はゼロで埋め、2.3 は「ここは参照だ」という印を立てる）。②は公式部品の仕様なのでそのまま使い、照合検査で固定してある。

**既定の強度は動かしていない。** 前提実験では LTX 2.5 でLoRAがやや弱く効くことが分かっている（ぼけ取りの復元率が強度1.0で46%・1.3で136%）が、同等化のスコープでは既定を変えない。強めに効かせたい利用者は画面から強度を指定できる（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §74.9(1)）。

**この段で `unsupported_features` は8件になった**（`retake` / `end_source` / `two_stage_hq` / `outpaint` / `nag` / `prune_vaed` / `sage_attention` / `keep_resident`）。API 契約への反映は [`../Videomni_Backend_Specification.md`](../Videomni_Backend_Specification.md) §6.10(d)・(f)。**オーナーの目視は 2026-08-25 に合格した**——AviUtl2 の操作パネルからスタイルLoRAと IC-LoRA の両方を試し、いずれも効果があることを確認しての判定である（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §74.12）。

#### 続き: 高速化第1弾＝fusedカーネルと先読み block swap（2026-08-24）

**必須級（同等化）が出尽くしたあと、オーナー裁定の段階分けに従って高速化技術の前倒しに入った、その第1弾である。** 対象は高速化5つのうち**出力がビット単位で変わらない2つ**——**fused GGUF逆量子化カーネル**（圧縮された重みを計算に使える形へ展開する処理を、量子化形式ごとに1つのGPU処理へまとめる）と**先読み block swap**（CPU と GPU のあいだの重みの受け渡しを計算の裏で先回りさせる）——で、**どちらも既定 on** にした。残る3つ（SageAttention・`keep_resident`・PrunaVAED）は出力または品質が変わりうるので別の弾として扱う。

| 段 | コミット | 内容 | 通過したゲート |
|---|---|---|---|
| C0 | `d4311ca` | LTX 2.5 用の仮想環境へ `triton-windows` を導入。逆量子化の初回検算のキーを「型」から「**型＋ポインタの整列**」へ。自己診断を任意の GGUF へ向けられるように | G0 |
| C1 | `ae21067` | `engine25` 側の fusedカーネルの受け口（有効化・後始末とエコー2キー） | G1 |
| C2 | `0ed330b` | `engine25` 側の先読み block swap の受け口（ビルドごとの張り直し・量子化テンソルの型の持ち回り・自己診断C15） | G2 |
| C3 | `22aebf7` | アプリ側の配線（4分類の対応表を「無視＋ログ」から「動作」へ。**既定で両方 on**） | G3 |
| C2b | `6027180` | 先読みの受け皿（アリーナ）の**リング化**と `expandable_segments` の整理・自己診断C16 | C2b再ゲート |
| G5 | — | 実機ゲート（実GPU・45ジョブ・固定ベンチマークB系17本） | 全合格（記録は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §75） |

**設計上の要点は4つある。**

1. **fusedカーネルは、共有部品の上に「配線」しただけである。** Triton を使う逆量子化の分岐は、もともと両エンジンが共有する `engine/gguf/` の中に存在していた。したがって `engine25` 側の仕事は「ジョブの頭で有効にし、終わりで必ず戻す」という作法の写し取りだけで、**有効化は `try` の外・後始末は `finally`**、しかも2つの後始末を別々に囲って片方の失敗がもう片方を有効のまま残さないようにしてある。**エンジンごとにカーネルを二重に持たない**という判断は、前処理（canny 等）を共有した第3段と同じ形である。
2. **先読みは「1ジョブでモデルを何度も組み直す」ことへの対応が本体である。** 連結生成はクリップ数×タイル数だけ transformer を組み直すので、ビルドのたびに張り直す必要がある。**取り外しはビルドの1行目に固定**（組み立て処理が内蔵する防御的な取り外しに任せると、重みを読み込んだ後に前ビルドの CPU 正本が書き戻され、今回のビルドを静かに上書きする）、**forward の張り替えは今回の生きたモデルに対して明示的に剥がす**（同じ器が使い回されるため、剥がさないと1プロセスに1回しか効かない）。エコーの畳み込み方は LTX 2.3 と同型（全ビルドで効いたときだけ `"on"`）。
3. **アリーナリングは、`hold_arenas` による意図的な系統別の例外である。** Windows の PyTorch は `expandable_segments` を受け付けない（**一度も効いていなかった**）ため従来型のアロケータで動き、ブロックごとの確保・返却が予約プールを一方向に押し広げていた。固定本数の受け皿を使い回す「アリーナリング」でこれを解消したが、**リングが得になるかどうかはエンジンごとに違う**——LTX 2.5 は VRAM の天井が denoise の**中**にあるので得しかない（B4 で 15,292 → 14,840MB）のに対し、LTX 2.3 は天井が denoise の**外**（デコード段）にあるためリングぶんがそのまま上積みされる（Chain A で 13,264 → 15,550MB）。**「どちらのエンジンにも同じ挙動を」の例外を作るときは、違いを隠さずフラグの名前で表に出す**という形にしてある（`hold_arenas`。LTX 2.5 だけが on）。顛末は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §75.7。
4. **エンジンの範囲が広がっても、`unsupported_features` は動いていない。** この2つは 422 で断っていた機能ではなく「無視＋ログ」の側にあった項目なので、動いたのは4分類の対応表だけである（§5.6 の補足）。**フロントエンドのコードは1行も触っていない。**

**実測の要点（第1弾）**: 交互対比較で **fused 単独が生成時間の中央値 99.95秒 → 65.72秒**、**先読み単独が平均 25.3%短縮**、**併用が平均 102.86秒 → 39.28秒＝61.8%短縮**。**固定ベンチマークB系17本はすべて mp4 の SHA-256 が従来と一致**し、予約 VRAM も全本が基準比 +400MB 以内（最大 B4 の +282MB）である。**LTX 2.3 は Chain A の SHA・予約 VRAM とも完全に従来どおり**。API 契約への反映は [`../Videomni_Backend_Specification.md`](../Videomni_Backend_Specification.md) §6.10(d)・(f)（**4分類は単発が 6／5／14／3、連結が 7／5／19／3 になった**）。

#### 続き: 高速化第2弾＝モデル骨格の常駐（`keep_resident`）のテキストエンコーダ側（2026-08-25）

**高速化5つのうち、残っていた3つ（SageAttention・`keep_resident`・PrunaVAED）の先頭に着手した第2弾である。** LTX 2.5 の変換器（映像を作る本体）側の重みは以前からメインメモリに残る設計（ロードペイロードの `cache_weights`。既定 on）だったが、**Gemma 4 テキストエンコーダの重みだけは毎ジョブ GGUF から読み直していた**——そこが唯一の未回収分だった。**既定は off のオプトイン**で、他の2つの高速化とは向きが逆である（メインメモリと引き換えの機能のため）。

| 段 | コミット | 内容 | 通過したゲート |
|---|---|---|---|
| C0 | `f72c8e7` | 計測下地（機能変更ゼロ）。`10a_te_build` / `10b_ep_build` / `40_job_end` の3フェーズ新設と、chain の `seconds_total` からサブフェーズを除外する規約 | G0 |

| C2 | `69b58ec` | アプリ側の開通（**拒否表から受理表へ**・ペイロードの加算・エコーの中継。`unsupported_features` は 8件 → 7件） | G3 |
| G5 | — | 実機ゲート（実GPU・GPUジョブ11本） | 全合格（記録は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §76） |

**設計上の要点は4つある。**

1. **同じ名前でも、LTX 2.3 とは別の実装である。** 契約（キー欠落＝off＝明示的な解放指示・ジョブ末にリセットしない・エコー3値・`GET /status` にフラグを載せない・RAM の自動降格を作らない）は 2.3 から逐語で写したが、**コードは1行も共有していない**——2.3 が常駐させるのは全サブモデルの骨格（約20GB）、**2.5 が抱えるのは Gemma 4 テキストエンコーダの state dict ただ1つ（実測 7.68GiB）**である。**この区別は仕様書・README・MCP の説明文・コードの docstring の4箇所に1文ずつ入れてある**（同名別実装の誤読が最大のリスクだったため）。
2. **on は「フラグの書き換え」だけで済むが、off は `pop()` が要る。** 公式の登録簿（`ModelRegistry`）は `add()` のときしか `_cache_weights` を読まず、**`get()` はこのフラグを見ない**。したがってフラグを戻すだけでは、一度入った重みが永遠に配られ続ける。**「解放は次に off を要求したジョブの頭で起きる」という非対称**（ジョブ末では戻さない＝残ることが機能そのもの）も、2.3 の規律をそのまま写したものである。
3. **私的属性への依存は、署名検査では守れない。** 公式パッケージが `_cache_weights` を改名しても関数の形は変わらないので、検査は通ったまま**静かに 7.68GiB を取りこぼす**。そこで `verify()` に**使い捨ての登録簿で add / get / pop を実際に往復させる挙動ピン**を置いた（偽のホイール2種で `CompatError` になることを実証済み）。**同じ形の依存を足すときは、同じ手当てをすること。**
4. **RAM の自動降格は作らない、という判断は据え置いた。** 「常駐に十分なメモリがあるかどうかは利用者の選択であって、サーバーが判定すべき環境の能力ではない」（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §48.1-10）。同じ理由で `GET /status` にも能力フラグを載せていない（同 §48.7）。台帳 [`PENDING_TASKS.md`](PENDING_TASKS.md) §3-51 は先送りのまま生きている。

**実測の要点（第2弾）**: **2本目以降の生成が 27.6秒 → 20.5秒＝約25%短縮**（連結生成では 35.17秒 → 30.13秒＝約5秒短縮）。テキストエンコーダの構築は **6〜8秒 → 0.4秒**、常駐の増分は **7.68GiB**、**VRAM は on/off で完全に同値**（RAM と引き換えの機能なので、動かないことが期待どおりの結果である）。**出力は単発・連結とも凍結ベンチマークと SHA-256 が一致**する。API 契約への反映は [`../Videomni_Backend_Specification.md`](../Videomni_Backend_Specification.md) §6.10(d)・(f)（**4分類は単発が 5／5／15／3、連結が 6／5／20／3 になった**）。

> **副産物として、LTX 2.5 のメインメモリの見え方が変わった。** 計測の標本点を増やしたところ、**`keep_resident` が off のときでも2本目以降のジョブは 25.9GiB に達している**ことが分かった（変換器の常駐 14.7GB とテキストエンコーダの構築 9.2GB が同時に生きる瞬間を初めて捉えたもので、従来の報告値 18.3GiB は「山を越えたあとの谷」を読んでいた）。**LTX 2.5 の RAM を語るときは、この前提から始めること。** 詳細は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §76.2(3)。

**次の一手の材料も1つ出た**——埋め込み処理器（embeddings processor）の構築が毎ジョブ 3.3〜4.7秒かかっており、**費用はテキストエンコーダと同格**である。しかも `keep_resident` を on にしてもこの区間は縮まない（別の登録簿を使っているため）。台帳 [`PENDING_TASKS.md`](PENDING_TASKS.md) §3-114 へ起票した。

## 10. 未決事項

**本書に残っている未決事項は無い。** 今後の課題は台帳 [`PENDING_TASKS.md`](PENDING_TASKS.md) §3 側で管理する（**どの項目がいくつ生きているかは台帳 §3 を見ること**。件数と項目番号を本書に書かないのは、同じ数が文書ごとに食い違う事故を繰り返したためである）。

判断が必要になったとき参照する現状を1つだけ挙げておく。**LTX 2.5 の映像デコーダは畳み込み版（conv）を既定としている。** 拡散デコーダ版は反復的なノイズ除去を伴うため決定性が壊れる（同じシードでも同じ動画にならない）。ファイル自体は捨てずに `models/LTX25/VAE/diffvae/` へ退避してあり、カテゴリの走査は非再帰なので**自動認識の対象にならない**（置いてあるが選べない、という状態）。採用の可否は §3-103 で判断する。
