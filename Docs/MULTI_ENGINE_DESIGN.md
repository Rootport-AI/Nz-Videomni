## 1. 結論（この機能が何をするのか）

**ヘッダーのドロップダウンで、使う動画生成AIを切り替えられるようにする。**

利用者から見た振る舞いはこうなる。

1. ヘッダーのドロップダウンに「LTX 2.3」「LTX 2.5」「Wan 2.2」……とベースモデル名が並ぶ。導入済みかどうかも一緒に表示される。
2. 導入済みのものを選ぶと、**その場でモデルの読み込みが始まる**。押すボタンは無い。
3. 読み込みが終われば、そのベースモデルで生成できる。Settings のモデル選択欄（transformer / text_encoder / video_vae / audio）の中身も、選んだベースモデルのものへ入れ替わる。
4. 未導入のものを選ぶと「まず導入してください」と案内が出て、切り替えは行われない。ダウンロードはサーバーがやらない。

内部では、これは次の2つを同時に満たす設計になる。

- **LTX 2.5 を足すときは、モデルの記述ファイルを1つ足すだけで済む**（推論エンジンは LTX 2.3 と共用）。
- **Wan のような別系統を足すときは、専用の推論エンジンと専用の Python 環境を新設する**（既存の LTX 側には一切手を入れない）。

## 2. 責任分界の大原則 — 推論エンジンはサーバーがメタデータで決める 【確定・オーナー裁定】

### 2.1 UIの選択値は推論エンジンを決めない

**ドロップダウンの選択が変えるのは「Settings のモデル選択欄に何が並ぶか」だけである。どの推論エンジンで動かすかは、サーバーが重みファイルそのものの中身（メタデータ）を読んで決める。**

> **実行時のエンジン決定の優先順位（F-1・敵対的レビュー2026-08-20指摘）**: 実行時にどの推論エンジンで動かすかを決める材料は、**選ばれた重みファイルのKVメタデータのみ**である。§4.3で足す記述ファイル（manifest）の `engine_family` は、これとは別の目的——既定値の決定・未導入判定・インストーラでの分岐——のためのヒントであり、**実行時のエンジン選択には使わない**。記述子の `engine_family` と、実際に指定された重みファイルのKVが食い違う場合（例: `engine_family: "ltx"` の記述子経由で選ばれたはずの transformer が、実は別系統のGGUFだった）、サーバーは自動で解決せず、§2.5のとおり422で止まる（fail loud）。両者は別レイヤーの情報であり、優先順位で合成するような設計にはしない。

これは画像生成ツール Forge neo（Stable Diffusion 系の統合環境）が採っている方式と同じ考え方で、利点は次の一点に尽きる。

> **利用者が「LTX 2.3」を選んだまま LTX 2.5 の重みファイルを指定しても、サーバーは正しく LTX 2.5 として動く。**

UIの選択値を信じる設計にすると、この場合サーバーは LTX 2.3 のつもりで LTX 2.5 の重みを読み、意味の分からない場所でクラッシュする。メタデータを読む設計なら、そもそも食い違いが起きない。

### 2.2 判別材料 — 自前GGUFのKVメタデータ

判別に使うのは、GGUF ファイル（このプロジェクトが配布する量子化済み重みの形式）が先頭に持っている**KVメタデータ**（キーと値の組。ファイルが自分自身を説明するための欄）である。

**実ファイルで確認した事実（2026-08-20 実測・要約）**: `models/LTX23/Weights/` の3ファイル（公式重みから変換した `LTX-2.3-22B-distilled-1.1-Q4_K_M.gguf` と、利用者が自分で変換した `10Eros-v1.2-Q4_K_M.gguf`・`Sulphur-2-base-distil-Q4_K_M.gguf`）すべてに `general.architecture = ltxv` と `model_version = 2.3.0` が入っている。**自家変換のファイルも同じKVを持っている**——変換ツール（`Nz-GGUF-Converter-LTX23`）が付けるためで、これが後述の「規約として保証できる」根拠になる。テキストエンコーダの `gemma-3-12b-it-Q4_K_M.gguf` は `general.architecture = gemma3`（KV40個。LTX側は7個）で、**カテゴリが違えば architecture も違う**ので取り違えもこのキーで検出できる。KVの全項目・バイト数などの詳細は `Docs/VERIFICATION_LOG.md` §67 を参照（L-6・敵対的レビュー2026-08-20指摘: 詳細数値は追記専用記録簿側に寄せ、本書は結論の要約のみ持つ）。

### 2.3 現状は誰もこのKVを読んでいない

**現状のコードは `general.architecture` も `model_version` も一切参照していない。** `engine/gguf/loader_service.py:101-135` の `metadata()` は、KVフィールドの中から `config` / `ltx.config` / `general.config` という名前のものだけを探して埋め込みconfig JSONを取り出し、見つからなければ safetensors 側のconfigへフォールバックする。architecture を見て分岐する箇所は存在しない。

つまり本設計の第一歩は、**すでにファイルの中に入っているのに誰も読んでいない情報を読み始めること**である。ファイル形式の変更も再配布も要らない。

### 2.4 規約（契約）としての保証 【確定・オーナー裁定】（本書側がこれを前提とすることの確定。変換ツール側で実際にKVを書き出す実装作業は【提案】——別リポジトリへの依頼のため。下記参照）

**Nz-Videomni が扱うGGUFは、変換ツールも配布リポジトリも自前である。したがって「transformer のGGUFは `general.architecture` と `model_version` を必ず持つ」を規約として保証する。**

- 変換ツール `Nz-GGUF-Converter-LTX23` 側で、この2つのKVの書き出しを必須にする（LTX 2.5 用プロファイルを足すときに、あわせて検証規則として組み込む）。**この項目は `Nz-GGUF-Converter-LTX23` という別リポジトリへの要求事項であり、本書からの依頼にすぎない。** 本書側で強制する手段は無いため【提案】として扱う——実装はそちらのリポジトリの作業計画に委ねる。
- 参考: 上流の LTX wheel（`ltx_pipelines/utils/constants.py` の `detect_params()`）に、safetensors メタデータから `model_version` を読む前例が既にある（本プロジェクトでは未使用）。将来 safetensors 側の判別を実装するときに、KVの代わりにこの前例を流用できる（§2.4後段の「ヘッダキー指紋」方式の一案として記録しておく）。
- 配布物（HuggingFace の `Rootport/Nz-LTX23-weights` ほか）は変換ツールの出力なので、自動的に規約を満たす。
- 利用者の自家変換ファイルも同じツールを通るので満たす。**すでに手元の実ファイル3本で満たされていることを確認済み**（§2.2）。

将来 safetensors を直接読むエンジン（LTX 2.5 の非量子化重みを扱う場合など）を足すときは、GGUFのKVに相当するものが無い。その場合は **ComfyUI 方式のヘッダキー指紋**——safetensors ヘッダに並ぶテンソル名の特徴的な組み合わせを見てモデル種別を当てる方法——で対応できる。安全に拡張できる余地があることだけ記録しておき、実装は必要になった時点でよい。

### 2.5 フールプルーフは作らない。エラー品質で解決する 【確定・オーナー裁定】

**「transformer に LTX 2.5 を選んだから VAE も自動で 2.5 に差し替える」といった自動選択・自動修正は作らない。組み合わせが不整合なら、エラーを出して止まる（fail loud）。**

理由は、自動修正は「利用者が意図してやった実験」まで勝手に書き換えてしまうためである。このプロジェクトは自家変換の重みを混ぜて使う利用者を想定しており、勝手な差し替えは害のほうが大きい。

ただし**エラーの質は上げる**。重みを実際に読み込む前——ワーカープロセスを起動する前——に、選ばれた各ファイルのKVを読んで整合を確かめ、食い違っていれば次のような文章で止める。

> transformer は ltxv-2.5 ですが、テキストエンコーダは gemma3（LTX 2.3 用）が選ばれています。同じ世代の組み合わせを選んでください。

（S-1・敵対的レビュー2026-08-20指摘: 例文は transformer と text_encoder の組——両方とも GGUF で KV を持つ——に揃える。VAE は safetensors で、v1 の時点ではファイル自体に `general.architecture` 相当のKVが無いため、**VAE 側との整合チェックは v1 のスコープ外**とする。§2.4後段の「ヘッダキー指紋」方式を実装した時点で拡張の余地がある。）

これは自動修正ではなく、**エラーメッセージの品質**の話である。既存の `precheck_model_file`（`services/model_registry.py:132-186`。GGUFの先頭4バイトのマジックナンバーと safetensors ヘッダの妥当性だけを数バイト読んで確かめる軽量チェック）と同じ位置に、同じ思想で足す。

**実装方式の注記（S-1）**: アプリ側の仮想環境（`.venv`）には GGUF パーサ用の `gguf` パッケージが入っていない（requirements.txt に無く、依存追加もしない——アプリ venv は torch 無しという§5.3の前提を壊すため）。したがって KV ヘッダを読む処理は、既存の `gguf` ライブラリに頼らず、`services/model_registry.py` 側に最小限の自前パーサとして実装する。GGUF の KV ヘッダは、マジックナンバー・バージョン・テンソル数に続けて KV の個数と各KVの型付きエントリが並ぶ単純な二進形式で、本用途で読みたいのは文字列型のKVが2個（`general.architecture` と `model_version`）だけなので、汎用パーサは要らない。

## 3. 概念モデル — 2つの軸を分ける 【提案】（S-7・敵対的レビュー2026-08-20指摘によりラベル降格。概念の分割自体はオーナーディスカッションで合意しているが、実装計画の段階で見直してよい設計案として扱う）

本設計の中核は、**これまで1つだった「モデル」という概念を、性質の違う2つの軸に分けること**である。

### 3.1 BaseModel（ベースモデル）— 利用者に見える単位

「LTX 2.3」「LTX 2.5」「Wan 2.2」のような、**利用者が名前で認識し、ドロップダウンで選ぶ単位**。

ベースモデル1つに対して、次の4つが1対1で対応する。

| 対応するもの | 例（LTX 2.3 の場合） |
|---|---|
| ドロップダウンの項目 | 「LTX 2.3」 |
| モデル置き場のディレクトリ | `models/LTX23/` |
| 導入用のバッチファイル | `install-LTX23.bat`【提案・新設】 |
| 記述ファイル（manifest） | `scripts/manifests/10-ltx23.json` |

「置き場所がそのまま所属の宣言になる」という現行の `models/` レイアウト（[`NEXT_SESSION_HANDOFF.md`](NEXT_SESSION_HANDOFF.md) §4）は、この軸にそのまま合致する。**現行レイアウトは変更しない。**

### 3.2 EngineFamily（エンジン系統）— 推論実装の単位

「ltx」「wan」のような、**実際に計算を回す実装の単位**。エンジン系統ひとつが次の4つを所有する。

- 専用のワーカープロセス（`engine/worker.py` に相当するもの）
- 専用の Python 仮想環境（`.venv-engine` に相当するもの）
- ワーカーへ送るペイロード（読み込み要求・生成要求の項目一覧）の形
- パラメータの制約（フレーム数の刻み、解像度の倍数、対応する機能の有無）

### 3.3 2つの軸の関係 — ベースモデルからエンジン系統へは多対1

```text
BaseModel        EngineFamily
─────────        ────────────
LTX 2.3  ─┐
          ├───→  ltx      （worker + .venv-engine を共有）
LTX 2.5  ─┘

Wan 2.2  ──────→ wan      （worker + .venv-wan を新設）
```

> **注記（F-1）**: この写像は**インストール時・既定値決定の話**である（§4.3の `engine_family` フィールドがこの対応を記述子として持つ）。**実行時のエンジン選択はこの写像を見ず、§2.1のとおりKVメタデータのみで決まる。** 記述子の対応と実際に読み込まれる重みのKVが一致しているのが通常の状態だが、一致を強制するのはKV側であり、写像図はその既定値を人間が読みやすくするための参考図にすぎない。

この関係から、追加作業の重さが自動的に決まる。

| 追加するもの | 必要な作業 |
|---|---|
| **LTX 2.5**（同じエンジン系統の別ベースモデル） | 記述ファイルを1つ足す。GGUF変換プロファイルを足す。既存の ltx エンジンに 2.5 の読み込み分岐を足す。**新しい仮想環境もワーカーも要らない** |
| **Wan 2.2**（別のエンジン系統） | 上記に加えて、専用ワーカーと専用仮想環境とアダプタを新設する |

**LTX 2.5 対応が「重い改造」ではなく「ベースモデルの追加」で済むのは、この分離があるからである。** 逆に言えば、この分離を作らないまま LTX 2.5 を足すと、LTX 2.3 用のコードに 2.5 の分岐が全体に散らばることになる。

## 4. 記述子（SSOT）— 既存 manifest を拡張する 【提案】（S-7・敵対的レビュー2026-08-20指摘によりラベル降格）

### 4.1 何が問題か

**現状、「このシステムが扱うモデルのカテゴリは transformer / text_encoder / video_vae / audio の4種類である」という事実が、コードの定数として複数の場所に散らばっている。**

| 場所 | 現状 |
|---|---|
| `services/model_registry.py:73-98` | `CATEGORY_SPECS` — 4カテゴリの定義本体（既定パスのフィールド名・拡張子・スキャン方法） |
| `services/model_registry.py:101` | `CATEGORIES` — 上記から作る固定順のタプル |
| `api/pipeline.py:19` | `CATEGORIES` を import して、リクエストのカテゴリ名を検証 |
| `api/models_registry.py:21` | `CATEGORIES` を import して、`GET /models` の応答を組み立て |
| `services/ltx_runner.py:1242-1247` | `_SELECTION_FIELDS` — カテゴリ名からワーカーペイロードの項目名への対応表（同じ4カテゴリの二重定義） |
| フロントエンド `webui/src/shell/useModels.ts:10` | `MODEL_CATEGORIES` — 同じ4カテゴリをTypeScript側でも定義 |

LTX 2.5 が「テキストエンコーダは Gemma 4」「映像デコーダは Conv VAE または DiffVAE」という別のカテゴリ構成を持つ**可能性がある**（S-6・敵対的レビュー2026-08-20指摘: これは未検証であり、[`LTX25_RESEARCH_NOTES.md`](LTX25_RESEARCH_NOTES.md) の見立てにすぎない。同資料は「Gemma 4 も text_encoder・Conv VAE も video_vae のままカテゴリ名を変えずに済む可能性」も同時に記録しており、カテゴリ集合そのものが増減するとは決まっていない）。もしカテゴリ構成が実際に変わる場合、**この定数を増やす方向で対応すると、増えるたびに6箇所を直すことになる。**

**段階の切り方（S-6）**: 上記の不確実性を踏まえ、第1段階では「`CATEGORY_SPECS` を記述子（manifest）から生成できる形にする」ところまでで止める。**カテゴリ集合そのものを可変にする（4種を超えて増減させる）作業は、LTX 2.5 の実際のカテゴリ構成が判明してから着手するかどうかを判断する。** 第1段階の完了時点で LTX 2.3 の4カテゴリがそのまま記述子駆動になっていれば十分であり、まだ存在しない2.5の構成に合わせて先回りして一般化しすぎない（§8.1「抽象の正しさは2例目で実証する」と同じ考え方）。

### 4.2 解決 — カテゴリ集合をコードからデータへ降格させる

**カテゴリの集合は、ベースモデルごとの記述ファイル（manifest）が宣言する。コード側は「記述ファイルが言っているカテゴリ」を扱うだけの汎用処理になる。**

置き場所は既存の `scripts/manifests/<base>.json` を拡張する。新設しない理由は、**この記述ファイルがすでに「モデルの構成を知っている唯一の場所」として機能しているから**である。インストーラ `scripts/install_ltx.ps1` はこの記述ファイルに完全に駆動されており（`Import-ModelManifests` が `scripts/manifests/*.json` を読み、スクリプト自体はモデル名を一切持たない）、スキーマ番号による版管理（`schema: 1`）も形式検証（`Test-ManifestShape`）も既に備わっている。

**manifest は2種類ある（S-8）**: `scripts/manifests/` には、`engine_family` を持つ**ベースモデル記述子**（`10-ltx23.json` など）と、`engine_family` を持たない**共有資産記述子**（`00-preprocessors.json` など。Preprocessors のように、どのベースモデルからも参照される共有素材を記述する）の2種類が混在する。**`engine_family` を持つものだけが、ヘッダーのドロップダウン・ベースモデル一覧に出る。** 共有資産記述子はインストーラの「全部読んで全部入れる」経路（`setup.bat`）には引き続き含まれるが、ベースモデル切替のUIには現れない。

### 4.3 追加するフィールド 【提案】

現行の manifest（`scripts/manifests/10-ltx23.json`）は `schema` / `id` / `downloads` / `migrate` を持つ。ここへ次の3つを足す。スキーマ番号は `2` へ上げる。

> **S-2・敵対的レビュー2026-08-20指摘**: スキーマ番号を `2` へ上げても、それだけでは動かない。`scripts/install_ltx.ps1:286-288`（`Test-ManifestShape`）は `$Manifest.schema -ne 1` を検証しており、schema 1 以外を渡すと即座に例外で止まる**厳格一致**である。したがって**このインストーラの検証を「1または2を受理する」形へ先に改修することが、記述子の拡張と対になる必須作業**（第1段階の一部。§9.1・§10参照）——記述子側にフィールドを足すだけでは、既存インストーラがその記述子自体を拒否して止まる。

                                      // が指定された場合も自動解決せず422で止まる（fail loud）。

  // このベースモデルが必要とするカテゴリの集合。
  // カテゴリごとに「どこを探すか」「どの拡張子を受け付けるか」を宣言する。
  "categories": {
    "transformer": {
      "scan": ["LTX23/Weights"],
      "extensions": [".gguf"],

> **注記（F-2・敵対的レビュー2026-08-20指摘）**: `default_selection` の値は、レジストリの**登録名**または予約センチネル `"default"` のいずれかでなければならない。`services/model_registry.py:233-240` の走査ロジックは、config の既定パス（`known_paths`）と同一実体を指すファイルにはスキャンで別名の登録名を作らない——既定パスと同じファイルは常に `"default"` という名前だけで参照する設計だからである。したがって `"LTX-2.3-22B-distilled-1.1-Q4_K_M"` のようにファイル名ベースで直接指定すると、その名前がレジストリに存在せず `resolve()`（`services/model_registry.py:337-365`）が `model_not_found`（404）を返す。**上の例は `"default"` センチネルへ修正済み。** ファイル名ベースの登録名で `default_selection` を指定したい場合は、config の明示登録map（`model.*_names` 相当。§5.1のL-2参照）側にも同じ名前で登録しておく必要がある。**（2026-08-20裁定・§5.4参照）**: モデルの既定パスは config.yaml から manifest 側へ移管する裁定が確定した。したがって実装時には、上記の「config の既定パス（`known_paths`）」は「manifest が導く既定パス」に置き換わる——`"default"` センチネルが指す先が変わるだけで、`resolve()` の名前解決ロジックや「既定パスと同じ実体には `"default"` という名前を割り当てる」という仕組み自体は変わらない。

**この記述ファイルを、インストーラ・レジストリ・API・フロントエンドの4者が全員読む。** これが「散在の解消」の実体である。

- インストーラ（PowerShell）— `downloads` / `migrate` を読む（現行どおり）。
- レジストリ（Python）— `categories` を読んでスキャンする。
- API（Python）— `categories` のキー集合をリクエスト検証に使う。
- フロントエンド（TypeScript）— `GET /models` の応答からカテゴリを受け取る（TypeScript側の定数 `MODEL_CATEGORIES` は撤去し、サーバーが返すものに従う）。

### 4.4 `payload_field` について

`categories` の各要素に `payload_field`（ワーカーへ送る項目名）を持たせているのは、現状 `services/ltx_runner.py:1242-1247` の `_SELECTION_FIELDS` が同じ対応表を二重に持っているためである。記述ファイルへ寄せることで二重定義が消える。

ただし**この項目はエンジン系統に属する知識であってベースモデルに属する知識ではない**——LTX 2.3 と LTX 2.5 で `payload_field` は同じはずである。記述ファイルに書くか、エンジンアダプタ（§5.2）側に持たせるかは、実装時に決めてよい。本書は「二重定義を1箇所に寄せる」ことだけを確定とする。

## 5. 層の構成

### 5.1 モデルレジストリ — 記述子駆動・多ルートスキャンへ 【提案】（S-7・敵対的レビュー2026-08-20指摘によりラベル降格）

**現状**: `services/model_registry.py` の `_scan_category`（`:256-288`）は、**そのカテゴリの既定パスが置かれているディレクトリ1本だけ**をスキャン対象にしている。具体的には config の既定ファイルパスを取り、その親ディレクトリ（`parent_levels` 段だけ上）をスキャンの根にする。

```python
# services/model_registry.py:256-262 の要旨
base = self.config._abs(default_path)   # 例: models/LTX23/Weights/LTX-2.3-...gguf
for _ in range(spec.parent_levels):
    base = base.parent                   # → models/LTX23/Weights
```

この作りでは、**「自動発見」は既定パスの親ディレクトリ1本に限られる**——既定パスは1つしか無いので、自動でスキャンする根も1つしか決まらない（L-2・敵対的レビュー2026-08-20指摘: ただし config の明示登録map（`configured` = `model.*_names` 相当。`services/model_registry.py:218-231`）経由なら、任意のパスを名前付きで登録でき、そちらは複数本を同時に一覧できる。「同時に一覧できない」のは自動発見の話であり、config明示登録まで含めた話ではない）。したがって LTX 2.3 と LTX 2.5 の transformer を**自動発見だけで**同時に一覧することはできない。

**変更**: スキャンの根を記述ファイルの `categories[].scan`（配列）から取る。ベースモデルごとに独立してスキャンし、結果もベースモデルごとに分ける。

**API の階層も1段深くなる。**

| | 現状 | 変更後 |
|---|---|---|
| `GET /models` の構造 | カテゴリ → 登録名（2層。`api/models_registry.py:26-40`） | **ベースモデル → カテゴリ → 登録名**（3層） |

現行の応答は `{"categories": {"transformer": {"default": ..., "active": ..., "entries": [...]}, ...}}` という形である。ここへベースモデルの層を挟む。凍結API契約（[`../Videomni_Backend_Specification.md`](../Videomni_Backend_Specification.md) §6）に対しては、**旧構造を残したまま新構造を並置するか、`GET /models` は非凍結の加算エンドポイントとして扱えるかを実装計画時に確認すること**（`GET /models` はモデル管理機能で後から足した加算エンドポイントである。`api/models_registry.py:1-13` の冒頭注記を参照）。

### 5.2 EngineRunner（汎用）＋ エンジン別アダプタ 【提案】（S-7・敵対的レビュー2026-08-20指摘によりラベル降格）

**現状**: `services/ltx_runner.py` は10万バイト超の1ファイルで、次の2種類の責務が混ざっている。

| 責務の種類 | 中身 |

| **どのエンジンでも同じもの** | ワーカープロセスの起動・監視・終了。`@@LTX@@` 接頭辞による行フレーミング（`:1137`）。load / generate / shutdown の呼び出し順序。状態の管理。テスト用の mock バックエンド |

### 5.3 ワーカーと仮想環境 — エンジン系統ごとに1つ 【確定・オーナー裁定】

**エンジン系統ごとに専用の Python 仮想環境を持つ。** 現状の2プロセス・2仮想環境構成（アプリ側 `.venv` は torch 無し、推論側 `.venv-engine` は torch+cu128）を、そのまま横に増やす形になる。

```text
.venv          … アプリ（FastAPI）。torch 無し
.venv-engine   … ltx エンジン系統。torch+cu128
.venv-wan      … wan エンジン系統。torch+cu128（将来）
```

**なぜ venv を分けるか（L-7）**: `requirements.txt` 冒頭の注記にある理由をそのまま踏襲する。(1) LTX 推論スタック（torch 2.9.1+cu128 と `ltx-core`・`ltx-pipelines` ほか）は PyPI ではなく PyTorch の cu128 wheel index から取る必要がある。(2) アプリ側スタックと推論側スタックは**両方ともトップレベルに `services` パッケージを持つため、同一インタプリタに同居できない**（import 時に衝突する）。したがってアプリ用 `.venv`（torch 無し）と推論用 `.venv-engine`（torch+cu128）は物理的に別プロセス・別インタプリタとして分離されており、この分離を新しいエンジン系統にもそのまま踏襲する。

#### 容量は心配しなくてよい

仮想環境を増やすと数GBずつ増える、という直感は**この構成では当たらない**。

パッケージ管理ツール `uv` はダウンロードした実体を `.uv_cache/` に1つだけ置き、各仮想環境からはそこへ**ハードリンク**（同じファイル実体に別名を付けたもの）を張る。**実体は `.uv_cache` 側にあり、各仮想環境が示す容量はその別名を数え直したもの（見かけの数字）にすぎない。** したがって**同じバージョンの torch を使う限り、2つ目のエンジン用仮想環境を作っても物理的なディスク消費はほとんど増えない**（増えるのは、そのエンジンにしか無い固有パッケージの分だけ）。実測値（`.venv-engine` 5.1GiB・`.venv` 277MiB・`.uv_cache` 7.2GiB、ハードリンク共有の確認手順を含む）は `Docs/VERIFICATION_LOG.md` §67 を参照（L-6・敵対的レビュー2026-08-20指摘: 詳細数値は追記専用記録簿側に寄せ、本書は結論の要約のみ持つ）。

#### 方針: 全エンジンで torch のバージョンを揃える 【確定・オーナー裁定】

上の利点はバージョンが一致していて初めて成立する。したがって**新しいエンジン系統を足すときは、既存と同じ torch バージョンで動くことを条件とする。** 揃えられない依存関係が出てきた場合は、容量が実際に増えることを承知のうえでオーナー判断を仰ぐこと。

#### 前提としてよい利用者像 【確定・オーナー裁定】

**「同時に導入するベースモデルは2〜3種類」**を前提にしてよい。全ベースモデルを同時に置ける前提での容量最適化は不要である。

### 5.4 状態の3層憲章 【確定・オーナー裁定】

**設定・実行時状態・端末の好みを、3つの置き場所へはっきり分ける。**

| 層 | 置き場所 | 誰が書くか | 何を持つか |
|---|---|---|---|
| **設定** | `config.yaml` | **人と（自動移行時は）インストーラ**（L-1）。サーバーは読むだけ | **ユーザーの上書き・好みのみ**（named明示登録map・プリセット・上限値・VRAMのつまみ）。**モデルの既定パスは持たない**——2026-08-20裁定によりmanifest側へ移管した（下記参照） |
| **実行時状態** | `state.json`【新設・確定】（スキーマ・置き場所は【提案】。§10参照） | **サーバーだけ** | 最後に使ったベースモデル。ベースモデル別の「最後に使った組み合わせ」 |
| **端末のUIの好み** | ブラウザの localStorage | フロントエンドだけ | 表示言語・テーマ・高速化設定・NAGの文面・プリフィル方針 |

> **注記（L-1）**: 「人だけ」と書いていたが、正確には**人と自動移行時のインストーラ**が書く。`scripts/install_ltx.ps1` は既存の `models/` レイアウトを新レイアウトへ移行するとき、`config.yaml` のモデルパスを書き換え、旧ファイルの `.bak` を生成する（§9.1「記述ファイル基盤」参照）。**サーバー（実行中のFastAPIプロセス）は読むだけ**、という性質は変わらない。**この書き換え対象（モデルの既定パス）は下記裁定によりmanifest側へ移管するため、移行スクリプトのこの箇所も実装時にあわせて見直しの対象になる。**

#### モデルの既定パスの置き場所 — config.yamlからmanifestへ移管 【確定・2026-08-20裁定】

**config.yaml の `model:` ブロックが持っていた「モデルの既定パス」は、記述子（manifest）側へ移す。config.yaml からは撤去する。**（旧F-3・敵対的レビュー2026-08-20指摘の未決事項に対する裁定。提示した2択のうち **(a) 既定パスの決定をconfig.yamlから記述子側へ移し、`model:` ブロックの一部または全部をconfigから撤去する** で確定した。(b)の「`model:` をベースモデルごとに入れ子化する」案は不採用。）

- **manifest = そのベースモデルの正体と既定構成の正本**。§4.3の `categories[].scan` と `default_selection` が指す既定パス・既定構成が、そのベースモデルについて「何を読み込めばよいか」を一意に定める唯一の場所になる。**インストーラも実行時のサーバーも、同じmanifestを読む**という一系統に揃う。これまで「インストーラが認識するモデル構成」と「`config.yaml` が持つ既定パス」が別々の場所に存在し、両者を同期し続けるコストがあったが、この裁定により**二重記載は解消される**。
- **config.yaml = ユーザーの上書き・好みのみ**。モデルの既定パスというフィールドは撤去する。ただし**named明示登録map（`model.*_names` 相当。§5.1のL-2で触れた `configured` 経路）は上書き手段として温存する**——利用者が自家変換ファイル等を任意のパスで登録できる仕組み自体は、ベースモデル軸の有無と無関係に必要であり、撤去しない。
- **state.json = 最後に使った組み合わせ**（上表のとおり）。

**波及（§4.3への影響）**: §4.3の `default_selection` が指す `"default"` センチネルは、これまで「`config.yaml` の既定パス」を指すものだったが、この裁定により**「manifestの `categories[].scan` が導く既定構成」を指すもの**へ意味が変わる。§4.3のF-2注記が説明している「configの既定パス（`known_paths`）と同一実体のファイルには`"default"`という名前だけを付ける」という現状のレジストリの挙動自体は変えない——**既定パスの出処がconfigからmanifestへ移るだけ**で、「既定パスと同じ実体には`"default"`を割り当てる」という名前解決の仕組みそのものは踏襲する。

**現状の裏取り**

- `config.yaml` へのサーバーからの書き戻しは**存在しない**。`config.py` は読み込み専用で、実行中に YAML を書き出す処理は無い（`yaml.dump` 相当の呼び出しがコード全体に無いことを確認済み）。**この「サーバーは config.yaml を書かない」性質は維持する。**
- サーバーが永続化している実行時状態は**現在ゼロである**。最後に使ったモデルの組み合わせを持つ `PipelineManager.active_models`（`services/pipeline_manager.py:177`）はメモリ上だけで、サーバーを再起動すると全カテゴリが `default` へ戻る。
- localStorage は現在6キー（**変更しない**）。

  | キー | 定義場所 |

  | `nzvideomni.lang` | `webui/src/i18n/strings.ts:2786` |
  | `nzvideomni.theme` | `webui/src/shell/ThemeContext.tsx:9` |

  | `nzvideomni.prefillSizePolicy` | `webui/src/shell/PrefillPolicyContext.tsx:35` |
  | `nzvideomni.prefillFpsPolicy` | `webui/src/shell/PrefillPolicyContext.tsx:36` |

**なぜ `state.json` が要るのか**: ドロップダウンを切り替えたとき、Settings のモデル選択欄に何を初期値として出すかを決める必要がある（§6.3）。「前回このベースモデルで使った組み合わせ」を覚えておく場所が、現在どこにも無い。localStorage は端末の好みであってサーバーの状態ではないので、そこへ置くのは層の混同になる。

**`state.json` の性質**: 消えても機能は壊れない（既定の組み合わせへ戻るだけ）。したがって git 追跡外とし、書き込み失敗はログを残して続行する。**置き場所（プロジェクトルート直下か、`models/` 配下か等）は未決（L-5・§10参照）**——`Docs/STORAGE_POLICY.md`（Outputs/Uploads の置き場所設計の正本）との関係整理も含めて、実装計画時に決める。

### 5.5 API の変更点 【提案】

いずれも**加算のみ**——既存フィールドの意味は変えない。

#### (a) `POST /pipeline/load` に `base_model` の軸を足す

現状のリクエストは `{"models": {"transformer": "...", ...}}` というカテゴリ→名前の対応表だけを受け取る（`api/pipeline.py:24-32`）。ここへ `base_model` を足す。

```jsonc
{
  "base_model": "LTX23",              // 追加。省略時は現在のベースモデル
  "models": { "transformer": "..." }  // 現行どおり
}
```

`base_model` が現在のものと違えば、ワーカーを作り直す（現行の「選択が変われば unload → load で作り直す」経路がそのまま使える。`api/pipeline.py:84-87`）。

> **実装上の注記（S-4・敵対的レビュー2026-08-20指摘）**: `base_model` を素直に追加しただけでは2箇所が壊れる。
> - **早期return（`api/pipeline.py:41-46`）**: `requested = (body.models if body is not None else None) or {}` の直後、`requested` が空なら `models` を一切見ずにレガシー経路（現在のアクティブ選択のまま再ロード）へ入る。`base_model` だけを送って `models` を省略した呼び出し（「ベースモデルだけ切り替えたい」という自然な呼び方）は、この早期returnに飲まれて `base_model` が無視される。`base_model` の有無も判定条件に含めるよう、この分岐を変える必要がある。
> - **no-op判定（`api/pipeline.py:75-82`）**: `if pm.loaded and effective == pm.active_models:` は `effective`（カテゴリ→名前の対応表）だけを見ており、`base_model` を比較に含めていない。全カテゴリが `"default"` のまま `base_model` だけを LTX23→LTX25 のように切り替えると、`effective` は変化しないため、この判定が「同一選択」と誤判定してワーカーを作り直さずに黙って無視する。`effective` の比較に `base_model` を含めるよう修正が要る。

#### (b) `GET /status` に `state` フィールドを足す

**現状の問題**: `GET /status` が返すフィールドのうち、**パイプラインの状態そのものを表すのは `pipeline_loaded`（真偽値）だけ**である（L-3・敵対的レビュー2026-08-20指摘: 他に `pipeline_type` / `vram_optimization` / `acceleration` / `queue` も返るが、これらは状態遷移とは別種の情報——モデル種別・VRAM設定・高速化可否・キュー件数——であり、`unloaded`/`loading`/`ready`/`running`/`error` の5状態を区別する材料にはならない。`api/status.py:16-38`）。一方サーバー内部には5つの状態がある——`unloaded` / `loading` / `ready` / `running` / `error`（`services/pipeline_manager.py:143-147`）。**このうち `loading`（読み込み中）が外部から観測できない。** 読み込み中は `pipeline_loaded` が `false` のままなので、「まだ読み込んでいない」のか「今読み込んでいる最中」なのかを、フロントエンドが区別できない。

**確認済みの重要な事実**: モデルの読み込み（`pm.load`）は同期処理で呼び出し元をブロックするが、**その間も `GET /status` は別のリクエストとして通る**（FastAPI が別スレッドで処理するため）。つまり**フィールドを1つ足すだけで、読み込み中の観測が可能になる**——処理の非同期化のような大掛かりな改造は要らない。

```jsonc
{
  "pipeline_loaded": false,
  "state": "loading",          // 追加。unloaded | loading | ready | running | error
  "base_model": "LTX23",       // 追加。現在のベースモデル
  ...
}
```

`POST /pipeline/load` の応答にはすでに `state` が含まれている（`api/pipeline.py:46`）ので、フィールド名と値の語彙はそれに揃える。

## 6. 利用者から見た振る舞い（UX仕様）【確定・オーナー裁定】

### 6.1 切り替え＝即ロード

**ドロップダウンでベースモデルを選んだ瞬間に、モデルの読み込みが始まる。** 内部的には、現在 Settings にある「Load selected models」ボタン（`webui/src/i18n/strings.ts:1785`）を1回押したのと同じ処理を自動で走らせる。

**「選択中とロード済みが食い違っている」という状態を作らない**のがこの仕様の目的である。ドロップダウンが「LTX 2.5」を指しているのに動いているのは LTX 2.3、という状況は、利用者にとって説明のしようがない。

### 6.2 4つのガード（S-4・敵対的レビュー2026-08-20指摘によりガード数を訂正——当初「2つ」と書いていたが、実装が要る観点を数えると4つある）

| # | 状況 | 振る舞い |
|---|---|---|
| (1) | **生成ジョブの実行中** | 切り替えできない。既存の409 `JOB_BUSY` をそのまま使う（`api/pipeline.py:54-55` が既に「ジョブ実行中はモデルを入れ替えられない」を実装済み。フロントエンド側の受け皿も `webui/src/shell/useModels.ts:32-36` に `status: "busy"` として存在する） |
| (2) | **未導入のベースモデルを選んだ** | ドロップダウンの項目自体に導入済み／未導入を表示しておく。未導入を選んだ場合は「`install-LTX25.bat` を実行して導入してください」と案内し、切り替えを中止して元の選択へ戻す |
| (3) | **ロード中の二重切替**【新規・S-4】 | ドロップダウンの読み込み中（`pm.state == "loading"`）にもう一度別のベースモデルを選んだ場合。**現状これをブロックする仕組みが無い。** `services/pipeline_manager.py` の `load()`／`reload()` は `with self._lock:` の中で `state = LOADING` に設定した直後に**ロックを解放してから** `self.runner.load(...)` を呼ぶ（`:292-301` 相当）。つまりロード処理そのものはロックの外で進む。ロード中に2回目の `POST /pipeline/load` が来ても、この経路は409を返さず素通りしてしまう——**409を返す仕組みを新設する必要がある**（例: ロード開始時に `state` を見て `pm.state == "loading"` なら即座に409を返すガードをAPI層に足す） |
| (4) | **失敗時のUI復帰**【新規・S-4】 | 上記いずれかの理由で切り替えが409／503で失敗したとき、フロントエンドのドロップダウンは選択中の表示を**元の（切り替え前の）ベースモデルへ必ず戻す**。選んだ表示のまま止まると、§6.1が禁じている「選択中とロード済みが食い違っている」状態そのものになる |

**ダウンロードはサーバーの責務にしない 【確定・オーナー裁定】。** サーバーが数十GBのダウンロードを開始する設計は、進捗表示・中断・再開・失敗時の後始末をすべてサーバー側に抱え込むことになる。導入はこれまでどおりバッチファイル（ダブルクリックで動くもの）に任せる。

> **現状との差分**: 現在の導入口は `setup.bat` の1本だけで、これは `scripts/manifests/` にある記述ファイルを**全部**読んで全部を導入する。ベースモデル別の `install-XXX.bat` は本設計での新設提案である。**S-8・敵対的レビュー2026-08-20指摘**: 「記述ファイルを1つだけ指定してインストーラを呼ぶ薄いラッパー」と書いていたが、現行の `scripts/install_ltx.ps1` の `param()`（`:104-122`）には記述子を選ぶ引数が無く（`-ResolveLatest`・`-RunSmoke`・`-SkipModels`・`-SkipVenv`・`-DryRun`・`-SkipMigrate` の6スイッチのみ）、Preprocessors 等の共有資産（§4.2）は常に一緒に処理される前提で書かれている。したがって `install-XXX.bat` を作るには、**まずインストーラ本体に `-Manifest <id>` 相当の選択引数と、指定した記述子（＋共有資産）だけを処理する部分実行モードを新設する必要がある**——「薄いラッパー」はその新設が済んだ後で初めて成立する話であり、既存の `param()` に対する加算だけでは済まない。

### 6.3 切り替えたとき、Settings のモデル選択欄に何が入るか

| 場面 | 初期値 |
|---|---|
| そのベースモデルを**初めて**選んだとき | 記述ファイルの `default_selection` |
| **2回目以降** | `state.json` が覚えている「そのベースモデルで最後に使った組み合わせ」 |

「最後に使った組み合わせ」は、**読み込みが成功したときに更新する**（失敗した組み合わせを覚えて次回も同じ失敗を繰り返す、という事態を避けるため）。

### 6.4 「デフォルトに戻す」ボタン

Settings のモデル選択欄に、既定の組み合わせへ戻すボタンを置く。押したときの処理は次の順序。

1. `default_selection` が指すファイルが実際に揃っているかを確かめる。
2. 揃っていれば `default_selection` を適用する。
3. 欠けていれば「`install-XXX.bat` を実行してください」と案内する。**サーバーはダウンロードしない**（§6.2 と同じ原則）。

### 6.5 ヘッダーのバッジに「読み込み中」を足す 【提案】（§5.5(b)が確定するまでは提案のまま。S-7・敵対的レビュー2026-08-20指摘）

**現状**: ヘッダーの状態バッジは6種類——`checking`（確認中）/ `bridge-unavailable`（ブリッジ未接続）/ `offline`（サーバー停止）/ `online`（稼働中）/ `busy`（生成中）/ `error`（エラー）（`webui/src/modes/single/StatusHeader.tsx:4-36`）。このうち `busy` は「キューに実行中のジョブがある」ことだけを見ている。

**追加**: `loading models`（モデル読み込み中）の状態を足す。判定材料は §5.5(b) で `GET /status` に足す `state` フィールドの `"loading"`。

**根拠の訂正（S-3・敵対的レビュー2026-08-20指摘）**: 当初「読み込み中はヘッダーが `offline` に見えてしまう」と書いていたが、これは誤り。フロントエンドの `useServerStatus.ts` を確認すると、`offline` 状態になるのは `GET /status` へのフェッチ自体が失敗（例外）したときだけであり、`pipeline_loaded` フィールドの値は見ていない。読み込み中も `GET /status` は変わらず200を返す（§5.5(b)で確認済みの事実）ため、フェッチは成功し、実際には **`online`（稼働中）のバッジのまま数分間留まる**。つまり利用者からは「もうエラーではなく、切り替えが終わって使える状態になった」と読めてしまう——これは§5.5(b)が指摘している「読み込み中かどうかが外部から観測できない」問題と整合する正しい根拠であり、「サーバーが止まって見える」という当初の記述より実害が大きい（オフラインなら再試行するだけだが、online のまま生成を試みると失敗する）。**バッジの追加は、状態フィールドの追加とセットで意味を持つ。**

## 7. v1 のスコープ外 — エンジン別のUIパラメータ制約 【確定・オーナー裁定】

**エンジンごとに違うパラメータ制約（フレーム数の刻み・解像度の倍数など）をUIが切り替える機能は、v1では作らない。**

事実として、LTX の制約はUIの表示だけでなく**APIのバリデーションまで連動している**。たとえばフレーム数の `8n+1` 規約（LTXの映像VAEが時間方向を8分の1に圧縮し、因果的な先頭1フレームが加わることに由来する）は `chain_math.py:41-42` の定数

```python
VIDEO_TIME_FACTOR = 8            # 映像VAEの時間圧縮率
AUDIO_LATENTS_PER_SEC = 25.0     # 16000 / 160 / 4
```

に**由来する規約**である。ただし**S-5・敵対的レビュー2026-08-20指摘**: 当初「この定数を起点に貫いている」と書いていたが、実態は定数を共有しているのではなく**規約だけが伝播し、実装は複数箇所に独立リテラルとして散らばっている**。`api/models.py` だけでも `8` という数値リテラルが `chain_math` の定数を参照せず独立に5箇所（`:342`・`:377`・`:515`・`:582`・`:587`）に直書きされており、フロントエンド側にも独立実装がある（例: `webui/src/bridge/mockBridge.ts:1014` の `(numFrames - 1) % 8 !== 0`）。**つまり「エンジンごとに `8n+1` を差し替える」対応は、`chain_math.py` の定数を1箇所直すだけでは済まない**——`api/models.py` の5箇所とフロントエンドの独立実装をすべて洗い出して直す必要がある。**この事実は記録するが、v1では手を付けない。**

### 作業の順序 【確定・オーナー裁定】

```text
第1段階  推論エンジン切り替えの土台づくり
            ↓
第2段階  LTX 2.5 の実装と、切り替えの成功
            ↓
第3段階  UI調整（エンジン別のパラメータ制約など）
```

LTX 2.5 も LTX 系である以上、`8n+1` 規約は共有される見込みが高い（[`LTX25_RESEARCH_NOTES.md`](LTX25_RESEARCH_NOTES.md) が「`8n+1` フレーム規約は共通」と記録している）。したがって第2段階までは制約切り替えが無くても成立する。**別系統（Wan 等）を入れる段になって初めて、第3段階が必須になる。**

## 8. 段階分割と検証の戦略 【提案】（S-7・敵対的レビュー2026-08-20指摘によりラベル降格。ただし§8.1の原則自体はオーナー裁定であり別途【確定】を維持する——下記参照）

### 8.1 抽象の正しさは2例目で実証する 【確定・オーナー裁定】

**「将来いろいろなモデルを載せられる作り」を、1例しか無い状態で完成させようとしない。** 抽象化が正しかったかどうかは、2例目を載せてみるまで分からない。1例しか無いうちに凝った作りにすると、2例目が来たときに「想定と違った」という理由で作り直すことになる——**過剰抽象化は、抽象化しないのと同じくらい手戻りを生む。**

### 8.2 したがって、土台整備と LTX 2.5 対応は抱き合わせで行う

LTX 2.5 は、2例目として理想的な性質を持つ。

- **BaseModel の軸だけを実証できる**——エンジン系統は ltx のまま（仮想環境もワーカーも新設しない）ので、「ベースモデルという概念が正しく分離できているか」だけを検証できる。
- 一度に検証する軸が1つで済むので、失敗したときに原因が絞れる。

**エンジン系統の軸（別仮想環境・別ワーカー・別ペイロード）の実証は、Wan 等の別系統を入れるときに行う。** その時点で `EngineRunner` の汎用／固有の切り分けが正しかったかが判明する。土台をそこまで見越して先に作り込まないこと。

### 8.3 段階の目安 【提案】

| 段階 | 内容 | 完了の判定 |
|---|---|---|
| 第1段階 | 記述子の拡張、レジストリの多ルート化、`EngineRunner` と ltx アダプタの分離、`state.json` の新設、API の軸追加 | **既存の全テストが通り、LTX 2.3 の振る舞いが一切変わらない**（`_build_load_payload` のゴールデンスナップショットが通ることが最重要） |
| 第2段階 | LTX 2.5 用のGGUF変換プロファイル、ltx アダプタへの 2.5 読み込み分岐、記述ファイル `20-ltx25.json`、`install-LTX25.bat` | **ドロップダウンで LTX 2.3 ↔ 2.5 を往復でき、双方で生成が成功する** |
| 第3段階 | エンジン別のUIパラメータ制約、ヘッダーバッジの磨き込み | 別途 |
