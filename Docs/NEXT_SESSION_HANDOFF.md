## 1. このリポジトリの形

**`Nz-Videomni` はモノレポ（1つのリポジトリに複数の成果物を入れる方式）である。** バックエンドとフロントエンドが同じリポジトリに同居しており、片方だけを別リポジトリで開発することはもう無い。

| 場所 | 中身 |
|------|------|
| リポジトリ直下 | バックエンド（`main.py` / `api/` / `services/` / `engine/`〔LTX 2.3〕/ `engine25/`〔LTX 2.5〕/ `gradio_ui/` / `mcp_server/`）。REST API サーバー本体 |
| `AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/` | AviUtl2 拡張フロントエンドのソース（C++ プラグイン `native/` ＋ React/TypeScript の `webui/`） |
| `AviUtl2-Plugin/NzVideomni.aux2` | ビルド済みのプラグイン本体（配布物・git 追跡。利用者はこれを AviUtl2 へドラッグ＆ドロップする） |
| `Docs/` | プロジェクト全体の文書と課題台帳 |
| `AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/Docs/` | フロントエンド固有の文書（ブリッジ契約・API リファレンス・実装ログほか） |

**旧フロントエンドリポジトリ `Nz-LTX23-frontend-AviUtl2`（GitHub 上の名称は不変）は凍結してある。** ディスク上のローカルフォルダは `_frozen_Nz-LTX23-frontend-AviUtl2` へリネーム済み（旧相対リンクが本機でだけ解決してしまう事故を防ぐため）。以後の変更はすべて本リポジトリで行うこと。

**名前の使い分け**: 製品ブランドは **Nz-Videomni**（識別子は `NzVideomni` / `nz-videomni`）。**LTX 2.3・LTX23 はモデルの名前**であり、こちらは今後も残る（`models/LTX23/`・HuggingFace の `Rootport/Nz-LTX23-weights`・`Nz-GGUF-Converter-LTX23` など）。将来 LTX 2.5 や Wan 2.x といった別のモデルも載せられる基盤を目指しているため、製品名からモデル名を外してある。

## 3. 開発の基本操作

### バックエンド

- 導入は `setup.bat`（中身は `scripts/setup.ps1` → `scripts/install_ltx.ps1`）、起動は `run.bat`（中身は `run.ps1`）。どちらもリポジトリ直下固定。
- **アプリ1プロセス＋エンジン系統ごとのワーカー構成**。アプリは `./.venv`（torch 無し）、LTX 2.3 の worker は `./.venv-engine`（torch+cu128）と `engine/`、LTX 2.5 の worker は `./.venv-engine-ltx25` と `engine25/`。**エンジン系統ごとに仮想環境とワーカーが1つずつある**（同居できない依存を持つため。理由は[`MULTI_ENGINE_DESIGN.md`](MULTI_ENGINE_DESIGN.md) §3.3・§5.3）。ワーカーは同時に1つだけ生き、ベースモデルを切り替えると旧ワーカーを落としてから新ワーカーを起こす。
- テストは `.\.venv\Scripts\python.exe -m pytest -q`。
- `config.yaml` は **git 追跡外**。配布されるのは `config.yaml.example` で、`setup.bat` / `run.bat` が無いときだけ複製する。**両者は同期させること。**
- `config.yaml` を書き換えたときの反映は**バックエンド再起動後**である。

### フロントエンド

作業ディレクトリは `AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/`。

- ビルド: `powershell -ExecutionPolicy Bypass -File scripts\build.ps1 -Config Release`。Web UI（`webui/`）の `npm run build:single` を先に走らせ、その単一 HTML を `.aux2` へ埋め込む（**埋め込みが既定**）。出力は `build\ninja-release\NzVideomni.aux2`。
- デプロイ: `powershell -ExecutionPolicy Bypass -File scripts\deploy.ps1 -Config Release`。**2箇所へ配る**——実機の AviUtl2 インストール先（既定 `D:\For_Videos\AviUtl2\aviutl2_v2.0.54\data\Plugin` の `NzVideomni\NzVideomni.aux2`。`Language\*.NzVideomni.aul2` は同じAviUtl2インストールの`data\Language\`〔`Plugin\`の兄弟〕へ）と、**本リポジトリの配布用コピー `AviUtl2-Plugin\NzVideomni.aux2`**。後者を忘れると、利用者が受け取るプラグインだけが古いままになる。
- 機械検証は3点セット（いずれも `webui/` で実行）: 型検査 `npm run typecheck`（`npx tsc --noEmit` は偽の合格を出すので使わないこと）・テスト `npm run test -- --run`（vitest）・静的検査 `npm run lint`。
- `.aux2` はビルドスクリプト経由でのみ作る（ninja を直接叩くと Web UI の埋め込みが更新されない）。

### MCP サーバー

`setup.bat` を一度実行すると、リポジトリ直下に `.mcp.json` が自動生成される（サーバーキーは `nz-videomni`、ツール22個）。マシン固有の絶対パスを含むため git 追跡外。

## 4. `models/` の配置とインストーラ

**ベースモデル優先レイアウト**——「置き場所がそのまま所属の宣言になる」形にしてある。

```text
models/
├─ LTX23/                LTX 2.3 一式
│   ├─ Weights/          transformer の GGUF（利用者の自家変換 GGUF もここへ同居する）
│   ├─ TextEncoder/      Gemma GGUF ＋ text projection ＋ tokenizer/
│   ├─ VAE/              映像・音声 VAE ＋ prunavaed/（枝刈り版デコーダ）
│   ├─ Upscaler/         空間アップスケーラ
│   ├─ StyleLoRA/        利用者が持ち込む画風・キャラクター LoRA
│   └─ IC-LoRA/          deblur / in-outpainting / pixel-spatial-upscaler / union-control
├─ LTX25/                LTX 2.5 一式
│   ├─ Weights/          transformer の GGUF
│   ├─ TextEncoder/      Gemma 4 GGUF（tokenizer は GGUF の中。隣の *.assets.safetensors は自動生成物）
│   ├─ VAE/              映像 VAE（畳み込みデコーダ版）＋音声 VAE ＋ diffvae/（拡散デコーダ版・退避先）
│   └─ Upscaler/         空間アップスケーラ
└─ Preprocessors/        ベースモデルに依存しない前処理器: DWPose/ ・ VDA/
```

- 各フォルダの `put_*_here.txt`（**全18本**。`git ls-files` 実測）は git 追跡。空フォルダのプレースホルダと「そこへ置ける形式」の掲示を兼ねる。
- **LTX 2.5 の記述子（`scripts/manifests/20-ltx25.json`）は `downloads` が空**で、インストーラは LTX 2.5 のぶんを単に飛ばす（最後の検証テーブル 15 行にも LTX 2.5 は出ない）。**これは意図した状態である**——`setup.bat` は本体のインストーラで、最初に試すAIとして LTX 2.3 だけを導入し、**別のベースモデルは専用のバッチ（`install-LTX25.bat` 等）で導入する**という設計である（[`MULTI_ENGINE_DESIGN.md`](MULTI_ENGINE_DESIGN.md) §6.2）。バッチ群の整備までは `downloads` を空のまま置くこと（埋めると `setup.bat` が LTX 2.5 まで取りにいく）。整備は[`PENDING_TASKS.md`](PENDING_TASKS.md) §3-111。
- **LTX 2.5 の重みは HuggingFace で公開済みである**（Public・非 Gated）。[`Rootport/Nz-LTX25-weights`](https://huggingface.co/Rootport/Nz-LTX25-weights)（transformer GGUF・映像/音声 VAE・空間アップスケーラ）と[`Rootport/Nz-Gemma4-12B-LTX25`](https://huggingface.co/Rootport/Nz-Gemma4-12B-LTX25)（Gemma 4 テキストエンコーダ GGUF）の2本立てで、**ライセンス確認も完了している**。ダウンロードして `models/LTX25/<カテゴリ>/` へ記述子の期待名のまま置けば、そのまま認識される。ファイル一覧と SHA-256 の正本は[`LTX25_RESEARCH_NOTES.md`](LTX25_RESEARCH_NOTES.md) 10節。期待するファイル名 5 本は記述子と[`../README.md`](../README.md) §1「models フォルダの構成」にも書いてある。
- インストーラ（`scripts/install_ltx.ps1`）は **`scripts/manifests/*.json` に駆動される**。manifest が取得元リポジトリ・展開先・期待ファイルを宣言し、スクリプト自体はモデル名を持たない。新しいモデルを足すときは manifest を足す。
- **ガードは期待ファイル単位**である（ディレクトリ合計サイズではない）。`TextEncoder` が2つのリポジトリから供給されること、`Weights` に利用者の自家変換 GGUF が同居することの2点で、合計方式は破綻するため。
- **旧レイアウトからの自動移行を持つ。** 旧配置のファイルを新配置へ移動し、`config.yaml` 内のモデルパスも自動で書き換える（書き換え前に `config.yaml.bak` を作る）。移動は上書きしない方式で、実行前に安全性チェック（シンボリックリンク・衝突）を通る。
- 検証に失敗した場合は、**足りない1ファイルだけを消して再実行する**。`models\LTX23` ごと消してはいけない（`StyleLoRA` や自家変換 GGUF は再取得できない利用者資産のため）。

## 5. 直近の状況（2026-08-29 現在）

**LTX 2.5 で使えるのは、基本生成（テキストから動画・画像から動画）・クリップ連結（Chained）・V2V継続（素材（冒頭）に動画を使って続きを作る）・A2V（音声から動画。Single・長尺・バッチのいずれも）・撮り直し（Retake）・素材（末尾）（End source）・スタイル LoRA・IC-LoRA（参照動画による制御。クリップ別の参照窓＝長尺 IC-LoRA を含む）・高速化4つ（GGUF逆量子化の1カーネル化・先読み block swap〔いずれも既定 on〕・モデル骨格の常駐＝`keep_resident`〔既定 off のオプトイン〕・SageAttention＝`attention_backend`〔既定は `"sdpa"` のまま〕）・画角拡張（Outpainting）である。** まだ無いのは NAG／VSF・非蒸留モデル・残る高速化1つ（PrunaVAED）の3つで、要求すると 422 で断る（`unsupported_features` は**3件**）。**この3つはいずれも画面を灰色にしない**——フロントエンドが機能名を読んで灰色にしているのは `webui/src/shell/useBaseModels.ts` の3つの表だけで、そこに現れる語は `chain` / `retake` / `outpaint` / `v2v` / `a2v` / `end_source` / `reference_video` の**7語しかない**。`two_stage_hq`・`nag`・`prune_vaed` はどの表にも無く、**画面のどの部品とも結びついていない**（NAG のトグルや非蒸留の選択は `unsupported_features` を見ずに描かれ、押せば 422 が返る）。**2026-08-26 に撮り直しと素材（末尾）が、2026-08-29 に画角拡張が開通したことで、単発生成でも連結生成でも断られるモードは1つも無くなった**——`unsupported_features` はいまや単発生成の拒否表をそのまま並べた式で、そこに残る3件はすべて「エンジンが持たない機能」である。**したがって、いま画面で灰色になるタブ・サブタブ・カードは1つも無い**（Edit タブの2つのサブタブは両方とも生きている）。後続は台帳[`PENDING_TASKS.md`](PENDING_TASKS.md) §3-102。

**ここまでの機能は、高速化第3弾（SageAttention）を含めてすべてオーナーの確認に合格している**（第3弾の目視ゲート G8 は 2026-08-25 に合格した。同 §77.10。下記の「残っているオーナー作業」を参照）。 基本生成（v1）は 2026-08-22（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §69.21）、クリップ連結は 2026-08-23（同 §72.10）、V2V継続と A2V は 2026-08-24（同 §73.10）、**スタイル LoRA と IC-LoRA は 2026-08-25**（同 §74.12。AviUtl2 の操作パネルから両方を試し、いずれも効果があることを確認して合格）。**長尺A2V はオーナー裁定で合格扱い**（裁定の全文と理由は同 §73.10(2)）。**使うときの注意が2つある**——スタイル LoRA は**トリガー語（そのLoRAの合言葉）をプロンプトに入れないと効きが穏やか**で、輪郭線制御（canny）は**鮮明な参照素材でないとエッジがほとんど出ない**（同 §74.9）。16GB の回避策は 1 段も使っていない（1920×1088・169フレームの V2V まで確認済み）。実測の正本は同 §69（v1）・§72（連結生成＋固定ベンチマーク B1〜B4）・§73（V2V・A2V＋B5〜B8）・§74（LoRA・参照動画＋B9〜B13）、API 契約は[`../Videomni_Backend_Specification.md`](../Videomni_Backend_Specification.md) §6.10、設計正本は[`MULTI_ENGINE_DESIGN.md`](MULTI_ENGINE_DESIGN.md) §5.6・§8.5、方式の差分は[`CHAIN_STAGE2_RESEARCH_NOTES.md`](CHAIN_STAGE2_RESEARCH_NOTES.md) 12節である。

**高速化第3弾（2026-08-25 実装）は機械ゲート・実機ゲートに加えて、同日オーナーの目視ゲート（G8）にも全項目合格した＝全ゲート完了である。** SageAttention（`attention_backend`）を LTX 2.5 でも開通させた——**既定は `"sdpa"` のまま**で、利用者が設定画面で明示的に `sage` を選んだときだけ効く。**実測は 1280×768・2クリップ×121フレームの連結生成で 1.1017倍**（交互3組の平均。合格線 1.10倍に対してぎりぎりの合格）。**本弾だけは「選ぶと出来上がる絵の細部が変わる」種類の高速化なので、固定ベンチマークの SHA-256 一致では合否を出せない**——判定は、すでに実績のある LTX 2.3 の sage を先に較正して作った **PSNR（ピーク信号対雑音比。元の絵とどれだけ違うかを1つの数値にまとめた指標で、単位は dB。数値が大きいほど元の絵に近い）と SSIM（構造類似度。2つの映像がどれだけ同じ構造をしているかを 0〜1 で表す指標で、1 に近いほど同じ）の相対の帯**で行った（768p 単発で PSNR 29.082dB／SSIM 0.891、512×320 で PSNR 25.171dB／SSIM 0.863。いずれも合格）。**当初の絶対基準〔SSIM 0.98／0.96〕は較正で LTX 2.3 自身が割ることが判明したため、オーナー再裁定で相対の帯・幾何別へ作り直してある**（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §77.2(3)）。**第2弾と同じく 422 の側からの移動なので `unsupported_features` は 7件 → 6件になったが、設定画面のグレーアウトが解けた理由はこれとは独立である**——設定画面（`SettingsPanel`）は `unsupported_features` をそもそも参照しておらず、attention の選択が押せるかどうかは `GET /status` の `acceleration.sage_available` だけで決まる。C2（`cb97613`）で真理値表から LTX 2.5 の恒久 `false` 上書きを削除したため実探索になり、true が返るようになった——**これが設定画面のグレーアウトが解けた理由である**（正本は[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §77.9(5)）。**`sage` で 422 になっていた罠（2.3 で選んだ設定がブラウザに残り、2.5 に切り替えると全ジョブが 422）も消えたが、`vae_mode` 側には同型の罠が残っている**（同 §77.7(f)・台帳 §3-102 の判断材料(9)）。実測の正本は同 §77、**目視ゲート G8 の結果（絵4項目・音1項目とも合格）は同 §77.10** である。


**撮り直し（Retake）と素材（末尾）（End source）の LTX 2.5 開通（2026-08-26 実装）は、機械ゲート・実GPUゲート・実機ゲートに全項目合格したが、オーナーの目視ゲート（G8）が未了である＝本段はまだ完了していない。** **2026-08-26、オーナーから「外出中のため目視G8は後日行う・テーマは一旦閉じてよい・問題があれば改めて修正作業を行う」との指示があり、本段はこの指示により一旦クローズした。**クローズは作業を止める区切りであって合格の意味ではない——チェックリストと素材（`outputs/ltx25-rtes-gate/g8_material/`）は有効なまま残り、目視は後日実施する。不合格項目が出た場合はそこから修正作業を再開する。 これまで LTX 2.3 でしかできなかった2つの機能——撮り直し（すでにある動画の「真ん中だけ」を作り直し、前後の「のりしろ」を凍結したまま元の映像へ重ねて戻せる形で出す）と素材（末尾）（手持ちの動画や静止画をチェーンの終点として指定し、そこへ着地するように生成させる）——が LTX 2.5 でも走るようになった。**仕様層（幾何計算・受理範囲・`metadata.json` のブロック）は 2.3 から一字も変えていない**——`chain_math.py` の共有計算が両系統から答えを出すためで、これは第1段（連結生成）で「帯の凍結が 2.3 とビット単位で同一になった」ことの配当である。**コミットは5本**（`dc480f4` フロントエンドの下地／`c6de7fb` 尾側の帯〔不活性〕／`18a501e` 撮り直し／`a53d086` 素材（末尾）／本コミット＝文書）。

**本段で押さえておくべき事実が4つある。**

1. **撮り直しの窓の符号化が、このエンジンの新しい最大負荷である。** 他のどの経路も素材の**頭**しか読まないが、撮り直しは**窓全体を2回**（stage-1 用の半解像度と stage-2 用の全解像度）符号化する。**LTX 2.5 の自動タイル化はこれを想定していない**——畳み込みデコーダ版の映像 VAE では縦横比だけを見る分岐へ解決し、**空き VRAM を一度も読まない**ので、16 GiB のカードでは失敗ではなく**こぼれ**（共有システムメモリでの裏打ち）が起きる。**面積の予算〔448×384〕で大きいほうの軸だけを絞る**専用のタイル上限を置いて、予約 26.6 GiB を 13.6 GiB へ落としてある（実測は 27,190 MiB → 13,926 MiB。**MiB を GiB へ直すのは ÷1024 である**）。**時間軸を絞ってはならない**（映像 VAE の因果的な受容野を担っており、短い窓で4デシベル近く落ちる）。**この種の経路を後続で足すときは、この前提から始めること**（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §78.5、コードの正本は `engine25/chain25.py` の `RETAKE_ENCODE_TILE_AREA_BUDGET`）。
2. **敵対的レビューが理論から導いた述語が、実測で否定された（M8）。** 「先頭フレームのキーフレーム印が正しいのは**タイムライン位置0**のときだけ」という理論に基づく述語は、**2シードとも 1.5〜2.2 dB 負けた**。**監督裁定**で**キャリー基準**を採り（**オーナー追認待ち**——ゲートの定めどおりエスカレーションはしたが、オーナー本人の承認はまだ受けていない）、出荷構成での再判定は **A（キャリー）32.912 dB 対 B（位置）30.236 dB、差 +2.676 dB で合格**した（LTX 2.3 の同一依頼 31.333 dB も上回る）。**正順では2つの述語が同じ集合を選ぶので、既存のチェーンの SHA は1つも動かない。** **この判断の実測根拠の正本はコードのコメント**（`engine25/chain25.py` の `seg_clear_kf` の代入行の直前）で、経緯は同 §78.7 にある。**理論から導いた述語は、区別がつく場面を1つ見つけて A/B で測ること。**
3. **合否の判定に使う「天井」は、判定される側とまったく同じ処理鎖を通ったものでなければならない。** R-1（のりしろが保たれているか）は、C0-prep が公表した天井に対しては短い2本が判定線をわずかに外して WEAK になるが、**ジョブが実際に使うタイルで測り直した天井に対しては6本すべて PASS** する。**差の出どころは凍結ではなくエンコードのタイル**（VRAM に収めるために意識して払った 0.5 dB）である。**監督裁定で読みBを正とした**（同 §78.4。**オーナー追認待ち**）。
4. **既知の制限が3つ残っている。** ①**素材（末尾）をクリップ2本以上で使う逆順モードの音声の継ぎ目が、LTX 2.3 より劣化する**（2.3 は6か所とも連続で最悪の比 5.125、2.5 は 4/6 が不連続で最悪 31.489。映像側は 2.5 でも 6/6 連続）——**もともと 2026-08-18 のオーナー裁定で「推奨外」と位置づけられているモード**であり、推奨のクリップ1本には影響しない。②**73フレームの窓の撮り直しでは、真ん中を作り直す余地がほとんど無い**（LTX 2.3 から引き継いだ性質。実用上は121フレーム以上を推奨）。③**フロントエンドのモックのクリップ数の下限が実 API とずれており、クリップ1本の素材（末尾）チェーンがモックでだけ 422 になる**（C3 以前からのずれ）。**いずれも台帳へ起票済み**（[`PENDING_TASKS.md`](PENDING_TASKS.md) §3-115〜§3-117）。

**実測の正本は同 §78、生の数値は `outputs/ltx25-rtes-gate/summary.json`、証跡は同 `evidence/`、オーナー向けの素材は同 `g8_material/` である。**

**画角拡張（Outpainting）の LTX 2.5 開通（2026-08-29 実装）も、前段の関門・機械ゲート・実GPUゲート（8腕）・実機ゲート（7項目）に全項目合格したが、オーナーの目視ゲートが未了である＝本段はまだ完了していない。** これで **LTX 2.5 が断っていた「モード」は1つも無くなった**（`unsupported_features` は4件 → **3件**）。**コミットは5本**（`9997db1` フロントエンドの下地／`8f4c1c6` 二段ドライバ〔不活性〕／`780ad94` 開通／`22203cc` フロントエンドの追随／`98ff3e4`＋`0a5c511`＝文書）。

**そして同じ 2026-08-29、この画角拡張の出力にあった「新しく描かれた領域全体の淡い緑かぶり」を取り除いた（「脱緑ブレンド」）。** ブレンドへ渡すキャンバスの余白を、その同じコマの生成画素で先に置き換えるだけの**約25行**の修正で、**LTX 2.3 と LTX 2.5 の両方に同時に入れた**（`engine/` の凍結に対するオーナー承認済みの例外である）。**副作用は無かったどころか、残すはずだった元映像の再現もよくなった**（2.5 の基準腕で 36.59 → **38.11 dB**、2.3 の W2 で 33.32 → **37.81 dB**）。実GPUゲートは**両エンジンとも取り直して全項目合格**（2.5 の8腕・2.3 の機械4項目）、**回帰3本も基準と一致**（2.3 の Chain A が `430eff8d…`／予約 13,264MB、2.5 の単発 `17751b45…`、2.5 の連結 `89af0757…`）。**判定線は1つも動かしていない。** **ただし出力が全面的に変わったので、目視ゲートは取り直し（G8′）になり、素材も全面的に作り直した。** 正本は[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) **§79.10**、コミットは `a7dd474`（実装）と本コミット（文書）である。

**本段で押さえておくべき事実が4つある。**

1. **台帳が持っていた実装方針を、着手前に棄却している。** §3-102 の判断材料(10) は2026-08-25の棚卸しで「LTX 2.3 の作り方の移植は成り立たない・潜在空間のマスクで作り直す」と結論していたが、**Web の一次情報を当たり直したところ、公式の LTX 2.5 画角拡張ワークフローそのものが「2.5 の本体＋2.3 が配布している In/Outpainting IC-LoRA」という世代をまたぐ組み合わせ**で、**LoRA を使わない公式経路は存在しなかった**。**2.3 の作り方は「古いやり方」ではなく、いまも公式のやり方である。** 判断材料(10) は追記型で訂正してある。
2. **アプリ層も仕様層も1行も変えていない。** 緑のキャンバスを作る `pad_green_mp4` は元からエンジン非依存で、`OutpaintSpec` の7フィールドも5検査も128倍数も256画素下限も 2.3 のままである。**新しく書いたのは `engine25/outpaint25.py` の1本だけ**で、その中身も借用だけ（複製は1つも作っていない）。
3. **全解像度の再符号化には `set_conv3d_memory_format` が要る。** 素のまま通すと予約VRAMが 27,188 MB まで膨らんでこぼれるが、重みの並びを変えるだけで **6,174 MB**・**52.3秒 → 19.0秒**になり、往復の一致度は **0.002 dB** しか動かない。**2.3 が同じ場所で使っているタイル面積の予算は採っていない**（13,922 MB までしか落ちず、**0.378 dB** 劣化するため）。**この種の経路を足すときは、まず bf16 の3次元畳み込みの im2col 落ちを疑うこと。**
4. **進捗が 50% 付近で長く止まるのは、2.5 固有ではなく両エンジン共通である。** 計画は「2.5 の既知挙動」と想定していたが、**同じ本文を LTX 2.3 で走らせても同じ場所で 18.0秒止まる**（2.5 は 16.1秒）。**単発生成の進捗計算が復号を数えない**という共通の性質で、実測で想定のほうを訂正した。
