# 第1部 決まったこと

## 1. 利用者から見た操作の流れ

**プレビュー画面で枠を合わせて、右クリックで追尾させます。** 操作パネルの上で矩形を描くことはありません。

1. 追尾させたい動画の**下の段**に部分フィルタを置きます（AviUtl2では下の段のフィルタが上の映像に掛かります）。置き場所は**右クリック→メディアオブジェクトを追加→画面効果→部分フィルタ**です（2026-09-11にオーナーが実機で確認）。「フィルタオブジェクトの追加」の11のカテゴリの中にはありません。旧AviUtl1とは置き場所が違います。
2. AviUtl2のプレビュー画面を見ながら、部分フィルタの枠の位置と大きさを、追いかけたい被写体に合わせます。このとき効果はまだ何も付けなくて構いません。
3. タイムラインでその部分フィルタを右クリックし、「🎯 物体追尾（部分フィルタを使用）」を選びます。
4. 操作パネルがToolboxタブに切り替わり、追尾が始まります。進み具合と、見失った区間が画面に出ます。途中で止めることもできます。
5. 終わると、部分フィルタの先頭から末尾まで、枠の位置と大きさに中間点が打たれています。
6. あとは利用者が自由に効果を足します。モザイクでも、ぼかしでも、色調整でも構いません。**追尾は枠を動かすだけで、効果の種類には関与しません。**
7. 途中で枠が被写体からずれてきたら、利用者がAviUtl2で部分フィルタをその位置で分割し、後ろ側の枠を合わせ直して、もう一度追尾させます。

**追える向きは前向きだけです。** 部分フィルタの先頭フレームの枠を種として、末尾まで順に追います。1回の追尾は1つのオブジェクトが対象で、同時に走らせられるのは1本だけです。

## 2. 責務の分担

**どの層が何を持つかを固定します。** これを崩さないかぎり、設定項目が増えてもサーバーとの契約は変わりません。

| 層 | 持つもの |
|---|---|
| AviUtl2本体 | 合成結果の描画、オブジェクトの生成と削除、レイヤーの表示制御、元に戻す操作 |
| プラグイン | 右クリック項目、描画ループ、フレームの送出、後処理、矩形と部分フィルタの値の換算、エイリアスの差し替え、レイヤーの一時無効化、中止、進捗の通知 |
| 操作パネル | 設定の画面と保存、進み具合と見失い区間の表示、停止ボタン、導入済みかどうかの表示、右クリックからの行き先の振り分け |
| バックエンドAPI | セッション1本の受付、「フレーム1枚を受けて枠とスコアを返す」窓口、エラーの封筒、`/status` への露出 |
| ユーティリティワーカー | UETrackの常駐読み込み、初期化、追跡 |

それぞれが**持たないもの**も同じくらい重要です。

- プラグインは推論をしません。設定の既定値も持ちません。
- 操作パネルは座標計算をしません。エイリアスの文字列も組み立てません。
- バックエンドは**生の枠とスコアしか返しません。** 見失いの判定も、平滑化も、中間点の間引きも行いません。
- ユーティリティワーカーはジョブ管理も動画生成もGPUの利用もしません。

## 3. 操作パネル（Toolboxタブ）

これまで常時無効の枠だったToolboxタブを、実際に使えるタブに昇格させ、その中に「物体追尾 / Object tracking」の区画を置きます。

### 3.1 設定は7項目

保存先は操作パネル側のブラウザ保存領域（`localStorage`）です。サーバーの設定には送りません。

数値を持つ4項目は、スライダーと数値ボックスの対で操作します。数値ボックスは範囲の外の値を打ち込めてしまうため範囲の内側に丸め、中間点を打つ間隔だけはさらに整数に丸めます。

**ラジオボタンの2択はいずれも横並びに出します**（2026-09-11のオーナー実機ゲート）。見出しはその上の行です。

- **モデル** — ラジオボタン。「◎ UETrack」「◯ Other」の2択に見えますが、**操作できない灰色の見本**です。実体はUETrackだけで、選択内容は保存しません。将来ほかの追跡AIを足すときの席を見せておくためのものです。**補足文は置きません**（灰色の見本であること自体が説明になっているため）。
- **探索範囲の広さ** — スライダー。2.0〜6.0、刻み0.1、既定4.0。追跡AIが次のフレームで探す範囲を、いまの枠の何倍の広さにするかです。補足文は「広いほど速い動きの追従性が上がるが、処理時間も増える。」です。この2.0〜6.0は操作パネルが出す範囲で、サーバー側が受け付ける上限はもう少し広い8.0です（§4.1）。
- **見失いのしきい値** — スライダー。0〜1、刻み0.01、既定は**0.35**（2026-09-11の実測のスコア分布に基づく暫定値です。以後はユーザーの反応を見て調整します。実測の数値は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §104）。追跡AIが返すスコアがこれを下回ったフレームを「見失い」として扱います。補足文は「追跡中のフィルタ内に描かれたものが追跡開始時から変化しすぎると「見失い」として扱う。その閾値。」です。
- **見失ったときの扱い** — ラジオボタン。「直前の位置で止める」（既定）か「そのまま追い続ける」かの2択です。
- **動きの滑らかさ** — スライダー。0〜1、刻み0.05、既定0.3。0なら追跡AIが返した枠をそのまま使います。値を上げるほど、前のフレームの枠に引きずられて滑らかになります。
- **枠の大きさも追従させる** — チェックボックス。既定はオン。オフにすると、位置だけを追いかけ、枠の大きさは種のまま固定します。**補足文は置きません**（この動作は項目名から読み取れるため）。
- **中間点を打つ間隔** — スライダー。1〜10、刻み1、既定1。1なら全フレームに中間点を打ちます。2なら1フレームおきです。**先頭と末尾の中間点は、この設定にかかわらず必ず残します。** 補足文はその但し書き（「先頭と末尾は、この設定にかかわらず必ず打ちます。」）だけです。

### 3.2 進み具合・見失い区間・停止

- 進み具合は「`123 / 240 フレーム ・ 18.4 fps`」の形で出します。1秒あたりのフレーム数は、操作パネルが進捗の通知が届いた時刻から自分で計算します（プラグインは送りません）。
- 見失い区間は「`120–134`」のような行を並べます。フレーム番号はAviUtl2のものです。
- 停止ボタン（表示は「🚫停止」）は追尾中だけ押せます。押すと途中までの結果で打ち切り、**そこまでの中間点は書き戻します。**
- 終わったあとは「`240フレームを追尾し、中間点を120個打ちました（12.3秒）`」という1行を出します。停止で終わった場合も、頭に「停止しました。」と付けて、そこまでの数を同じように出します。
- エラーはこの区画の中に、符号に対応する文言を添えて出します。文言を用意していない符号は、符号をそのまま出します。見出し「追尾に失敗しました」は `TRACK_BUSY` のときだけ出しません——これは失敗ではなく断りだからです。
- **追尾中にもう一度右クリックしたときは、操作パネルを作り直しません。** 「追尾が進行中です。🚫停止で止めてからやり直してください。」という案内を出すだけで、走っている追尾には手を触れません（Toolboxタブへの切り替えだけは行い、進み具合が見えるようにします）。作り直すと、走っている追尾の進捗の購読と応答の待ち合わせが捨てられ、**追尾自体は完走しているのに操作パネルだけが止まって見える**ためです。プラグイン側の `TRACK_BUSY`（§5.2）は裏の安全網として残します。

### 3.3 導入していないとき

追尾の仕組みが入っていない環境では、設定を灰色にして「`install-UETrack.bat` を実行してください」と案内します。判定はサーバーの `/status` から受け取ります（§4.5）。

案内の文言は2通りで、追尾の仕組みが導入されていないときと、ワーカーが起動できなかったときを書き分けます。サーバーの状態が分からないあいだ（つながる前や、基本モデルを切り替えている最中）は、最後に分かっていた可否をそのまま保ちます。

## 4. API契約

名前空間は `/api/v1/utils/track/` で、動画生成の名前空間とは分けます。認証は既存のものをそのまま掛けます。

### 4.1 エンドポイントは3本

| 手続き | パス |
|---|---|
| セッションを開く | `POST /utils/track/sessions` |
| フレームを1枚送る | `POST /utils/track/sessions/{session_id}/frame?frame=<整数>` |
| セッションを閉じる | `DELETE /utils/track/sessions/{session_id}` |

- **開く**: 本文はJSONで `{width, height, box:{x,y,w,h}, search_factor}`。応答は201で `{session_id, width, height, frame_bytes}`。`frame_bytes` は1枚あたりのバイト数（幅×高さ×4）です。
- **送る**: 本文は生のバイト列（`application/octet-stream`）。応答は200で `{frame, box:{x,y,w,h}, score}`。
- **閉じる**: 本文なし。応答は200で `{closed: true}`。
- `search_factor` は省くことができ、省いたときは追跡AIのランタイムが持つ既定値（4.0）を使います。**サーバー側で受け付ける上限は8.0**で、これを超える値は断ります。

**幅と高さはセッション単位で決まり、プラグインが実際に描画した1枚目の実寸を渡します。** フレーム側では**バイト長が `frame_bytes` と一致するか**だけを検査します。1枚目も2枚目以降も同じエンドポイントで、未初期化のセッションへ来た最初のフレームが初期化を兼ねます。応答の形はどちらも同じです。

`frame=` の問い合わせ文字列はAviUtl2のフレーム番号をそのまま返すためだけのもので、サーバーは中身を解釈しません。

**「見失った」という状態はAPIにありません。** サーバーは `score` を生のまま返し、判定はプラグイン側の純粋な関数が行います。

### 4.2 フレームの載せ方

**生のRGBA**（1画素を赤・緑・青・不透明度の4バイトで表す並び）を、そのままバイト列として送ります。1080pで1枚あたり約8.3メガバイトです。理由は第2部 §14にあります。

### 4.3 エラーは5種類

| 状況 | 状態番号 | 符号 |
|---|---|---|
| すでにセッションが1本ある | 409 | `TRACK_BUSY` |
| 追尾の仕組みが導入されていない、またはワーカーが起動できない | 503 | `TRACK_UNAVAILABLE` |
| 知らないセッション番号 | 404 | `TRACK_SESSION_NOT_FOUND` |
| 本文のバイト長が合わない | 400 | `TRACK_FRAME_INVALID` |
| 追尾の途中でワーカーが落ちた | 503 | `TRACK_FAILED` |

**本文の形そのものが誤っているとき**（値の型が違う、必須の項目が無い、幅・高さ・枠の大きさが0以下、探索範囲が受け付ける範囲の外）は、この5つの符号に入らず422で返します。`TRACK_FAILED` は「追尾の途中でワーカーが落ちた」ときと、「ワーカーは生きたまま `error` を返した」ときの両方に使います。

封筒の形は既存のエラーと同じにし、生成用の `feature_unsupported`（422）は使いません。理由は第2部 §16にあります。

### 4.4 セッションの寿命

- **同時に開けるのは1本だけです。** 2本目は409で断ります。
- **放置されたセッションは60秒で追い出します。** この60秒はソースコード上の定数で、設定項目にはしません。タイマー用のスレッドは作らず、次に開く要求が来たときにその場で古いものを判定して閉じます。放置の判定は「60秒**以上**」で、ちょうど60秒は追い出す側に入ります。
- **同じセッションを2度閉じると404です。** 2度目の番号はもう存在しないので、穏やかに返すとプラグイン側の取り違えを隠してしまいます。
- **正常終了でも中止でも、プラグインは必ず閉じる要求を出します。**
- **ワーカーのプロセスはセッションをまたいで常駐します。** モデルの読み込みは最初の1回だけです。

### 4.5 `/status` への追加

`/status` の応答に、既存の項目とは別のブロックを1つ足します。

```
"tracking": { "available": true }
"tracking": { "available": false, "reason": "not installed" }
"tracking": { "available": false, "reason": "worker failed" }
```

`reason` は使えないときだけ付きます。値は「導入されていない」「ワーカーが起動できなかった」の2つだけです。待ち行列や状態を表す既存のブロックには手を入れません。

## 5. プラグイン側

### 5.1 右クリック項目

タイムラインの右クリックメニューに項目を1つ足します。表示名は日本語で「🎯 物体追尾（部分フィルタを使用）」、英語で "🎯 Object tracking (uses a partial filter)" です。文言は運用の中で調整して構いません。通し番号は [`RIGHTCLICK_REDESIGN_SPEC.md`](../AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/Docs/RIGHTCLICK_REDESIGN_SPEC.md) の #21 です。

この項目は**選択が部分フィルタのときだけ**有効です。判別は、選択中のオブジェクトのエイリアスの先頭の効果名が「部分フィルタ」かどうかで行います。既知の4種別に当てはまらない選択はこれまでどおり「不明」に落ちるので、既存の挙動は変わりません。

### 5.2 呼び出しは2本

- **`timeline.trackObject`**（非同期）— 引数は `{layer, frame, searchFactor, smoothing, followSize, lostScoreThreshold, lostBehavior, keyframeStride}`。戻り値は `{ok, frames, keyframes, lostRanges, elapsedMs, cancelled}` です。`frames` と `keyframes` は件数、`lostRanges` は `{start, end}` の並びで、**フレーム番号はAviUtl2の絶対番号**（進捗の通知と同じ規則。§5.3）です。
  - **不変条件: `frame` には必ず選択スナップショットの `frameStart`（対象オブジェクトの開始フレーム）を渡します。** 再生カーソルの位置ではありません。理由は §5.4 の手順1にあります。
- **`timeline.cancelTracking`**（同期）— 中止の合図を立てるだけです。追尾のループが先頭で協調的に確認します。

**二重起動は防ぎます。** 追尾中にもう一度呼ばれたら `TRACK_BUSY` で断り、解除は処理の出口で自動的に行われる形（RAII）にします。

### 5.3 進捗の通知

イベント名は `timeline.trackProgress`、中身は `{frame, index, total, score, lost}` です。**`frame` はAviUtl2の絶対フレーム番号で、`index` は1始まりです。** ネイティブ内部の後処理はオブジェクト相対で動きますが、通知に載せる前に対象の開始フレームを足します。1秒あたりのフレーム数はここに入れません（操作パネルが到着時刻から計算します）。

**間引きの規則**: 直前に送ってから200ミリ秒以上が経ったときだけ送ります。**ただし最初のフレームと最後のフレームは必ず送ります。**

### 5.4 処理の手順

追尾は通信用のワーカースレッドの上で、次の順に進みます。

1. **種の読み取り** — 指定されたレイヤーとフレームからオブジェクトを探し、エイリアス全文と開始・終了フレームを取ります。AviUtl2の検索関数は「そのフレーム以降で最初に見つかったもの」を返す仕様ですが、§5.2の不変条件により指定フレームは対象自身の開始フレームなので、最初に見つかるのは対象自身です。**それでも、見つかった範囲が指定フレームを含むことを検証し、外れていたら中断します**（表明として残します）。
2. **種の矩形化** — エイリアスから部分フィルタの値を読み、矩形に直します。
3. **レイヤーの一時無効化** — 対象の部分フィルタが載っているレイヤーを一時的に無効にします。出口では必ず元に戻します（早期の打ち切りでも中止でも）。すでに効果が付いている部分フィルタを追尾させたときに、その効果が絵に焼き込まれてしまわないようにするためです。
4. **1枚目の描画とセッション開設** — 開始フレームの合成結果を描画し、**その実寸**でセッションを開きます。座標換算に使う画面の大きさも、この実寸を正本とします。編集情報から取り直すことはしません（正本を2つにしないため）。描画したバイト列を1枚目として送ります。
5. **ループ** — 開始フレームの次から終了フレームまで、中止の確認 → 描画 → 送信 → 応答を控える → 200ミリ秒の間引きで進捗を通知、を繰り返します。
6. **セッションを閉じる** — 閉じたあと、レイヤーの無効化が自動的に戻ります。
7. **後処理** — §5.5の6段を、純粋な関数として順に適用します。
8. **書き戻し** — §5.6・§5.7のとおりです。
9. **結果を返す** — 呼び出し元へ戻り値を返します。

### 5.5 後処理の6段

**順序は固定です。** 入力は「フレーム番号・枠・スコア」の並び、出力は「中間点の並び」と「見失い区間の並び」です。

1. スコアがしきい値を下回ったフレームに「見失い」の印を付けます。
2. 「直前の位置で止める」なら、見失ったフレームを直前の良好な枠で埋めます。「追い続ける」なら生のまま通します。
3. 指数移動平均（前の値と今の値を一定の割合で混ぜる平滑化）を掛けます。混ぜる割合は「1 − 滑らかさ」で、滑らかさが0なら素通しです。
4. 「枠の大きさも追従させる」がオフなら、幅と高さを種の値に固定します。
5. 中間点を打つ間隔ごとに残します。**先頭と末尾は必ず残します。**
6. 連続した見失いを区間にまとめます。

### 5.6 矩形と部分フィルタの値の換算

部分フィルタは、枠を「画面中心からのずれ」「大きさ」「縦横比」で持っています。矩形 `(x, y, w, h)`（左上原点・画素）との対応は次のとおりです。

- `X = (x + w / 2) − 画面幅 / 2`
- `Y = (y + h / 2) − 画面高さ / 2`
- `サイズ = max(w, h)`
- `縦横比 = w ≥ h のとき −100 × (1 − h / w)、w < h のとき +100 × (1 − w / h)`

**縦横比は ±99.99 でクランプします。** 幅または高さが0の矩形は不正として扱います。画面幅・画面高さには §5.4 手順4で描画した1枚目の実寸を使います。

### 5.7 エイリアスの書き換え範囲

**書き換えるのは5行だけです。**

- 値の行4本 — `X` / `Y` / `サイズ` / `縦横比`
- `[Object]` 区画の `frame=` の行1本

**それ以外はバイト単位でそのまま残します。** 利用者が追尾の前に付けていた効果も、マスクの種類も温存されます。これにより「効果はユーザーが自由に足す」という §1 の流れが成り立ちます。オブジェクトの名前はエイリアスには含まれないので、削除の前に読み取っておき、作り直した直後に付け直します。

`frame=` の行は**0始まりの相対フレーム番号で、両端を含みます。** N フレームのオブジェクトなら末尾の値は必ず `N − 1` です。これはAviUtl2本体の挙動として実機で確定しています（[`SDK_REFERENCE.md`](../AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/Docs/SDK_REFERENCE.md) §16 (h)）。同じ節の実機記録により、**オブジェクトを作り直すときに渡す長さの引数はエイリアスのヘッダに勝てません**——つまり長さの引数は冗長な二重の留め具であって、実尺を決めているのはヘッダ側です。

日本語の効果名・項目名は、ソースコードの文字コードに依存しないよう、既存の流儀にならってバイト単位の定数として持ちます。

#### 中間点つきの実書式

**中間点を複数持つ部分フィルタのエイリアスの実書式は、実機採取により確定しています。** 採取物の原文・採取日・パス・保存操作は [`SDK_REFERENCE.md`](../AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/Docs/SDK_REFERENCE.md) §16 (j) を正本とし、ここでは追尾の書き戻しが従う規則だけを記します。

- **値の行** — `v0,v1,…,v(N−1),直線移動,0` の形にします。値の個数は境界の個数と同数にし、末尾に移動方法の名前「直線移動」と数値`0`を続けます。値の書式は`X`・`Y`・`サイズ`を整数、縦横比を小数2桁にします。
- **境界の並び** — 先頭が開始、末尾が終了で、間に中間点を昇順に並べます。末尾の境界は必ず`length−1`にします（0始まりで両端を含む規則は本節冒頭のとおりで、境界が複数でも変わりません）。
- **途中で終わったとき** — 停止や途中失敗で最後に得られた点が末尾より手前になる場合は、その値を末尾（`length−1`）まで保って埋めます。値そのものは変えず、境界だけを末尾まで伸ばします。
- **点が1つだけになるとき** — 後処理（§5.5の5.）を経て残る点が1つだけなら、その項目は単一の値の表記にします（`,直線移動,0`は付けません）。既定値のままの項目と同じ形です。
- **追尾が管理しない項目に中間点が残っているとき** — 種のエイリアスに、追尾が書き換えない項目（回転・ぼかし・マスクの種類など）の中間点が既に付いていた場合は、先頭の値1つに畳みます。境界の個数がずれると項目間の対応が崩れて整合しなくなるためです。効果は追尾のあとに利用者が足す想定なので、これは想定外の入力に対する安全側の措置です。
- **既定値のままの項目** — 触っていない項目の行は常に書き出されるため（採取で確認済み）、欠落したキーの扱いを別途定める必要はありません。値が読めない場合も、安全側の既定`0`のまま扱います。

#### 書き戻しの手順

**AviUtl2 v2.0.54のSDKには、既存オブジェクトの区間を増やす／減らすAPIがありません。** そのため、削除して作り直す経路が一択です（理由は第2部 §17）。

1. **先に新しいエイリアスを組み立てて検証します。** 組み立てに失敗して空になったら、そこで中断します。この時点ではタイムラインに一切触れていないので、無傷です。
2. 対象オブジェクトを見つけ、削除します。
3. 同じレイヤー・同じ開始フレーム・同じ長さで、新しいエイリアスから作り直します。**空きレイヤーへ逃がす代替経路は付けません**（元の位置にあることが要件です）。
4. 作り直しが失敗したら、**即座に元のエイリアスで復元します。** それも失敗したら `TRACK_WRITEBACK_FAILED` を返します。
5. 削除と作り直しは**同じ編集区間**で行い、「元に戻す」操作1回で戻るようにします。

## 6. バックエンド側

### 6.1 専用の仮想環境とワーカー

UETrackは動画生成とは別の依存関係（CPU版のPyTorchなど）で動くため、**専用のPython仮想環境 `.venv-utils` を1本足し、別プロセスで常駐させます。** これは「重量級のパイプラインの切り替えに巻き込まれない」という要件から来ています。仮想環境をエンジン系統ごとに1つ持つ方針は [`MULTI_ENGINE_DESIGN.md`](MULTI_ENGINE_DESIGN.md) §5.3 が正本で、本機能は**推論エンジンではない仮想環境を足す最初の例**にあたります。

構成は次のとおりです。`engine/` と同格の位置に `tracking/` を新設します。

- `tracking/protocol.py` — 通信の枠付けと合図の名前。PyTorchに依存しないので、アプリ側の仮想環境からも読み込めます。
- `tracking/geometry.py` — RGBAからRGBへの変換、枠の画面内への収め込み、矩形表現の相互変換。これもPyTorchに依存しません。
- `tracking/worker.py` — `.venv-utils` の上で動く受信ループ。
- `tracking/uetrack_runtime.py` — PyTorchを読み込む唯一の場所。
- `tracking/vendor/uetrack/` — UETrackの推論に要る部分だけを取り込んだもの。取り込み範囲と出典は同じ場所に置く注意書きに記します。

アプリ側には、このプロセスを監督しセッションを持つ層と、3本のエンドポイントを1枚だけ足します。

**プロセスは起動時には起こしません。** 最初のセッションが来たときに遅延して起動します。アプリの終了処理も足しません——標準入力が閉じたことで自分から終わる、既存のワーカーと同じ作法にします。

`.venv-utils` には、この仮想環境の上でしか動かせない自動テスト（§9）のために pytest を足して入れます。**依存関係の凍結ファイルには載せません。** LTX 2.3 の仮想環境で pytest を同じように扱っているのと揃えた措置で、配布物の中身を検査用の道具で膨らませないためです。

### 6.2 ワーカーとの通信の約束

1メッセージは、目印の文字列 `@@TRK@@` に続けてUTF-8のJSONを1行、最後に改行です。JSONが `"bytes": N` を持つときは、その直後に生のバイト列がNバイト続きます。入出力の両方をバイナリで開き、緩衝はしません。

| 合図 | 送るもの | 返るもの |
|---|---|---|
| `load` | モデルの置き場所 | `ready` |
| `init` | 枠・探索範囲・幅・高さ＋1枚目の画素 | `box`（スコアは1.0） |
| `track` | 画素 | `box`（スコアつき） |
| `shutdown` | なし | （プロセス終了） |
| 例外が起きたとき | — | `error` |

初期化をやり直す合図は置きません。新しいセッションの最初の `init` がその役目を果たします。

**送受信の対は鍵で直列化します。** APIの枠組みは同時に来た要求を別々のスレッドで走らせるので、鍵がないと「長さを前に置く」形の枠付けが壊れて復帰できなくなります。既存の生成用アダプタが同じ理由で同じ作法を採っているので、そこから構造を写します。

### 6.3 UETrackランタイムの範囲と改変

**取り込むのは推論に要る部分だけです。** モデル本体、推論のラッパー、前処理（対象周辺の切り出しと窓関数）、矩形演算の使う分だけを取ります。

**取り込まないもの**: 学習、評価、設定ファイルの仕組み（Base固定の値をPythonの辞書に畳みます）、テンプレートの自動更新に関する設定（実際には効かない死んだ設定です）、テキスト側の特徴抽出の経路。

**加える改変**:

- GPU固定の呼び出しを、装置を指定する形へ機械的に置き換えます。装置は常に `"cpu"` です。
- 画像側の多モーダル入力は公式の重みの前提なので、そのまま残します（同じ画像を複製して所定のチャンネル数にします）。
- 言語側の多モーダル入力は切ります。これにより読み込まれない重みが出ますが、**それが言語側の分だけであることは実測で確かめてあります**（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §104）。
- テンプレート112画素角、探索窓224画素角、テンプレート倍率2.0、窓関数は内部で固定します。**外へ出す設定は探索範囲の広さだけです。**
- 公式配布のチェックポイントを読むため、読み込みの厳格な既定を明示的に緩めます。

公開する面は3つだけです——モデルを読む関数、初期化、1フレームの追跡（矩形と最良スコアを返す）。

### 6.4 設定 `tracking:`

アプリの設定に区画を1つ足します。**項目は4つだけです。**

- `backend` — `"uetrack"`（既定）または `"mock"`。
- `utils_python` — `.venv-utils` のPython実行ファイルへの道筋。既定は `./.venv-utils/Scripts/python.exe`。
- `model_dir` — モデル置き場からの相対名。既定は `UETrack`。
- `checkpoint` — 重みのファイル名。既定は `uetrack_base.safetensors`。

1枚あたりのバイト数の上限（4Kで約33メガバイトなので64メガバイト）と、放置セッションの期限（60秒）は**ソースコード上の定数**で、設定にはしません。この上限は2か所で効きます——セッションを開くときの幅×高さ×4の計算と、フレームを送る要求の `Content-Length` の検査です。後者は本文を読み込む前に判定するので、大きすぎる本文を受け取ってから測ることにはなりません。設定ファイルの見本にもこの区画は書きません（既定で足りるためです）。

`backend: "mock"` を選ぶと、別プロセスを立てずにアプリの中で偽の追跡が動きます。種の枠を毎フレーム決まった量だけ右下へずらし、決まった区間だけスコアを低く返します。自動テストと、実機なしの疎通確認に使います。

### 6.5 ログ

ワーカーの標準エラー出力は `logs/utils_worker.log` へ落とします。アプリ側のログ名は `ltx.tracking` です。

## 7. 重みと導入

**追尾は任意導入です。** 基本の導入手順には同梱せず、必要な人だけが `install-UETrack.bat` をダブルクリックします。理由は第2部 §21にあります。

- **重みの正本**は、公式配布のチェックポイントから**追跡に実際に使う部分だけを抜き出した safetensors**（重みを安全に保存する形式）です。公式配布は約1.18ギガバイトありますが、大半は追跡に使わない部分（テキスト側の特徴抽出器と蒸留用の教師）で、追跡本体は約2,700万パラメータ・約107メガバイトです（2026-09-11のスパイクで実測。絞った重みは公式配布と同じ枠とスコアをビット単位で返します）。抜き出しは再現できるよう小さなスクリプトとして残します。
- **置き場所**は `models/UETrack/uetrack_base.safetensors` です。前処理器と同じ「ベースモデルに依らない共有フォルダ」の並びに置きます。
- **配布元**は、既存の配布リポジトリに混ぜず、独立した [`Rootport/Nz-UETrack`](https://huggingface.co/Rootport/Nz-UETrack) です。絞った重みとモデルカードは配置済みで、`install-UETrack.bat` はここから取得します。
- **記述ファイル**を1本足します（`scripts/manifests/30-uetrack.json`）。この記述ファイルは**エンジン系統を宣言しません**——バックエンドはこれをベースモデルとして読みません。代わりに「任意導入である」という印を持ち、基本の導入手順からは外れ、`install-UETrack.bat` からだけ計画に入ります。
- **`.venv-utils` の作成**は、この導入の対象にUETrackが含まれるときだけ行います。CPU版のPyTorchを使います。既存の仮想環境には触れません。
- **未導入のとき**は `/status` が「導入されていない」と答え、操作パネルが案内を出します（§3.3・§4.5）。

## 8. 保存物と他機能との関係

**追尾はサーバーに何も残しません。**

- 成果物はAviUtl2のタイムライン上のエイリアス1本の書き戻しだけです。
- アップロード置き場も出力置き場も使いません。一時ファイルも作りません。したがって [`STORAGE_POLICY.md`](STORAGE_POLICY.md) の適用対象外です。
- **動画生成のジョブとは完全に独立です。** 追尾は生成ボタンを止めませんし、サーバーが生成で忙しいかどうかを追尾は見ません。追尾はCPUだけを使い、生成はGPUを使うので、取り合いになりません。
- **MCPサーバーの道具にはしません。** AviUtl2のタイムラインの上でしか意味を持たない操作だからです。
- **マスク動画の作成は本機能の外です。** マスクはAviUtl2側のオブジェクトから作る話で、契約の正本は [`PENDING_TASKS.md`](PENDING_TASKS.md) §3-55、入口の接続は同書 §4-25 です。追尾で動かした部分フィルタも、手で作ったオブジェクトも、そちらから見れば同じ「AviUtl2側のオブジェクト」です。

## 9. 検証の関門

**オーナーの実機ゲート1〜8と再確認2点は実施済みです（結果と実測値は [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §104 が正本で、本節には書き写しません。手順と合格条件の形にしたものは、フロントエンドの [`REAL_BACKEND_CHECKLIST.md`](../AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/Docs/REAL_BACKEND_CHECKLIST.md) §4.15 にあります）。** 下の一覧はそれを含む「この機能に手を入れたときに再度たどる確認項目」で、**§4.15 に対応する項目が無いものは今回のゲートでは確かめていません。**

自動の検査（Pythonの単体テスト、C++の単体テスト、操作パネルの単体テスト、型検査）はいずれも既存の基準値との比較で行います。それに加えて、**実機でなければ確かめられない項目**が次のとおりあります。

**実機で見るもの**

- 部分フィルタを右クリックしたときに「🎯 物体追尾（部分フィルタを使用）」の項目が出ること。
- 削除して作り直した直後の選択状態が壊れないこと（**今回のゲートでは確かめていない、再確認時の観点です。** 壊れるなら、作り直しの直後に対象へ焦点を戻す処理を1つ足します）。
- 追尾のあとに「元に戻す」を1回押すと追尾前に戻ること（**確認済み**。削除と作り直しが同じ編集区間に入っているので、2回・3回押す必要はありません）。
- 停止ボタンで中断したときに、レイヤーの表示が元に戻ること。
- 中間点の境界の数を2個・3個・N個と増やしたときに、`frame=` の並びが壊れないこと。
- 追尾済みの部分フィルタを途中で分割し、後ろ側だけを再追尾したときに、前側の中間点が保たれること。
- 追尾で動かした枠にモザイクを足すと、被写体に追従すること。モザイクが絵に焼き込まれていないこと。
- 追尾の最中にAviUtl2を閉じても固まらないこと（終了時は中止の合図と「終了中」の印を立て、レイヤーの復元と書き戻しの編集区間を省きます。その瞬間に限りレイヤーが非表示のまま残ることは許容します）。
- 追尾の最中に対象を消して同じレイヤー・同じ位置に別のオブジェクトを置いても、そのオブジェクトが壊されないこと（書き戻しの直前にエイリアスを照合し、別物なら何もしません）。
- 縦横比を一度も触っていない正方形の部分フィルタで追尾できること（既定値のままの項目がエイリアスに無い場合の扱い。ただし既定値の行は常に書き出されることは採取で確認済みである）。
- 冷えた状態での最初のセッション開設が、ワーカーの起動予算（180秒）の内側で返ること。実測の所要は `logs/utils_worker.log` で見ます。
- 最初から非表示にしてあるレイヤーの部分フィルタを追尾しても、終了後に非表示のままであること。
- 停止ボタンを押してから実際に止まるまでの待ち時間が気にならない長さであること（確認は1フレームごとです）。
- 部分フィルタの中で効果の順序を入れ替えても、右クリックの項目が出ること。

**測るもの**（実測値はいずれも [`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §104 が正本です）

- **追跡AIの単体の速度** — 1080pの1フレームにかかる時間を開発機で測ります。論文の報告値は1秒あたり56〜83フレームですが、測定機が最上位級のCPUなので**開発機ではこれより落ちます。** 相談のラインは「実効で毎秒5フレームを割るようなら、探索窓だけを送る通信の軽量化か、小型バリアントの採用をオーナーに相談する」です。あわせてスコアの分布（静止した物体・動く物体・隠れた物体）を採ります——§3.1の見失いのしきい値の既定は、この分布に基づく暫定値です。
- **動作環境の適合** — UETrackの公式環境はPython 3.10とPyTorch 1.11ですが、**本プロジェクトは他の仮想環境と揃えてPython 3.12で作ります。** 3.12で動かなかったときだけ、導入手順にPythonの版を指定する仕組みを足して3.10へ落とします。あわせて、言語側を切ったときに読み込まれない重みが**言語側の分だけ**であることを確かめます。
- **絞った重みの同一性** — 公式配布のチェックポイントと、抜き出した safetensors が、同じフレーム列に対して同じ枠を返すことを確かめます。食い違えば抜き出しの取りこぼしです。
- **通しの実効速度** — 描画・送信・推論を合わせた1秒あたりのフレーム数を、操作パネルを開いた状態で測ります。進捗の通知が詰まらないかも同時に見ます。

- 追尾の待ち行列、複数セッションの同時実行

- 逆方向の追尾

# 第2部 なぜそう決めたか

ここから先は、**一度検討して否決した案を再提案しないための記録**です。実装に着手するだけなら第1部で足ります。

## 11. 操作の起点をプレビューにした理由

**操作パネルの上に矩形を描かせる案を否決しました。**

追尾の対象は、AviUtl2のプレビューに映っている絵です。操作パネルの上に別の矩形指定の画面を作ると、「プレビューで見えているもの」と「パネルで描いた矩形」という2つの座標系を利用者が頭の中で突き合わせることになります。しかも、指定した矩形を最終的に部分フィルタへ写し取る作業が別に要ります。

一方、**部分フィルタの枠合わせはAviUtl2が既に持っている操作**です。利用者はプレビューを見ながらつまみを動かすだけで、結果は最初から部分フィルタの値として入っています。追尾はその値を読んで、末尾まで増やすだけで済みます。新しい座標系も、新しい矩形描画の画面も要りません。

## 12. 合成結果を1枚ずつ送る形にした理由

**動画ファイルに書き出してアップロードする案を否決しました。**

追跡に必要なのは「そのフレームで画面に何が映っているか」です。AviUtl2は合成結果を1枚ずつ描き出せます。これをそのまま送れば、入力は常に利用者が見ているものと一致します。

動画に焼く案には次の難点があります。

- 書き出しと読み込みで、非可逆の圧縮による劣化が挟まります。
- アップロード置き場に一時ファイルが増え、掃除の責任が生まれます（[`STORAGE_POLICY.md`](STORAGE_POLICY.md) の「一時置き場」の議論を追尾にも持ち込むことになります）。
- 進み具合を利用者に見せられるのが、書き出しが終わってからになります。

1枚ずつ送る形なら、どれも起きません。**追尾は保存物を1つも作らない機能になり、既存の保存・ジョブ・アップロードの仕組みにまったく触れずに済みます。**

## 13. 追尾とマスク作成を切り離した理由

**追跡結果から直接マスク動画を作る案を否決しました。**

**UETrackは矩形しか返しません**（領域を画素単位で切り分ける機能は持っていません）。マスクを作るなら矩形を白く塗るだけになりますが、それは**AviUtl2側のオブジェクトから作れること**で（作り方は §3-55 で決めます）、サーバーが作る必然性がありません。しかも一度サーバーにマスクを作らせると、「どの形式で」「どこへ置いて」「誰が消すのか」という保存物の議論が追尾に流れ込みます。

矩形しか返さないこと自体は、部分再生成の用途では問題になりません。潜在空間の都合でマスクは32画素角のブロック精度に丸まるので、矩形で足ります（[`PENDING_TASKS.md`](PENDING_TASKS.md) §3-55）。

マスクの受け渡しは、追尾に限らず「AviUtl2側で作ったオブジェクトから白黒の動画を作って渡す」という共通の話です。したがって契約は §3-55 に一本化し、**追尾はその入力元の1つに過ぎない**という位置づけにしました。手で作ったマスクも、他者のプラグインが作ったマスクも、同じ入口を通ります。

## 14. 生のRGBAで送る理由

**PNGなどに圧縮してから送る案を否決しました。**

送り先は同じ機械の中（ループバック）です。ここの転送速度は毎秒ギガバイト級なので、1080pの1枚8.3メガバイトは1枚あたり数ミリ秒で渡ります。一方でPNGへの符号化と復号は、**送り手と受け手の両方に、推論と同じくらいの桁の計算を足します。** 減るのは詰まっていない経路の通行量だけで、増えるのは律速になりうるCPU時間です。

ただし、圧縮を挟む余地は残してあります。通信の枠付けは1つのファイルに閉じてあるので、必要になればそこだけを差し替えられます。

## 15. 既存の生成用アダプタを継承しない理由

既存の推論エンジンにも「別プロセスを立ててやり取りする」層があります。しかし**継承せず、作法だけを写します。** 理由は3つです。

1. 既存のアダプタは生成要求の型を直接読み込んでおり、生成の語彙に密に結びついています。
2. 選択項目の一覧・必須の資産・読み込み時の組み立ては、いずれも動画生成モデルの記述子の語彙です。追尾には対応するものがありません。
3. 追尾はバイナリを流すので、送信と受信の両方を上書きすることになります。**再利用できる面がゼロになります。**

写すのは、プロセスの起動と停止の作法（標準エラー出力の記録、終了合図を出してから待ち、駄目なら強制的に終わらせる段取り、見張りのタイマー）と、**送受信の対を鍵で直列化する作法**です。後者は敵対的レビューで抜けを指摘された箇所で、これがないとバイナリの枠付けが壊れて復帰できません。流用元は注記として残します。

## 16. 409と503の使い分け

- **409（`TRACK_BUSY`）は「いまは無理」です。** セッションが既に1本あるだけで、少し待てば通ります。
- **503（`TRACK_UNAVAILABLE`）は「この環境では無理」です。** 仮想環境か重みが無いか、ワーカーが起動できませんでした。操作パネルはこれを見て導入の案内を出します。

**生成用の422（`feature_unsupported`）は使いません。** あれは「いま選んでいるベースモデルがその機能を持たない」という語義で（[`MULTI_ENGINE_DESIGN.md`](MULTI_ENGINE_DESIGN.md) §5.6）、追尾の可否はベースモデルと無関係だからです。語義を借りると、ベースモデルを切り替えれば直るかのように読めてしまいます。

## 17. 削除して作り直す経路一択の理由

**AviUtl2 v2.0.54のSDKには、既にあるオブジェクトの中間点を増やす／減らすAPIがありません。** 値を書き換えるAPIはありますが、区間の構造そのものを変えることはできません。追尾は中間点を数百個打つので、区間の構造を変えずには済みません。

したがって「エイリアスを取る → 文字列として書き換える → 削除して同じ位置に作り直す」以外の道がありません。外部の処理結果をこの経路でタイムラインへ入れる方式には、他者のプラグインによる動作実績もあります（§22）。

危険なのは「削除したあと作り直しに失敗して、オブジェクトが消える」場合だけなので、次の3重で守ります——**書き換えの成功を確かめてから削除する**、**作り直しに失敗したら即座に元のエイリアスで復元する**、**削除と作り直しを同じ編集区間に入れて「元に戻す」1回で戻す**。

## 18. GPU競合のポリシーが消える理由

起票時には「生成ジョブの最中はCPUの追跡器だけに制限する」といった取り決めが要ると考えていました。**UETrackをCPU固定にしたことで、この取り決め自体が不要になりました。** 追尾はGPUを1バイトも使いません。

このため、操作パネル側でも「サーバーが忙しいか」を追尾の可否に持ち込みません。**生成中でも追尾でき、追尾中でも生成できます。** これは本プロジェクトの「同時に走る重いジョブは1つ」という思想と矛盾しません——追尾は重いジョブではなく、取り合う資源が違うからです。

## 19. 設定項目をこの7つにした理由

UETrackの実装を読んだうえで、**実際に効く設定だけを選びました。**

- **探索範囲の広さ**は、追跡AIが次に探す窓の大きさそのもので、速い動きへの追随と計算量を直接交換します。これは出す価値があります。
- **窓関数**（探索窓の中心を重く見る重み付け）は内部で固定します。利用者が調整して良くなる性質のものではありません。テンプレートの大きさや倍率も同様です。
- **テンプレートの自動更新**は出しません。UETrackの実装にはそれらしい設定が残っていますが、**推論の経路では読まれておらず、動かしても何も変わりません。** 死んだ設定を画面に出すと「操作できるのに効かない」状態になります。
- **再検出**（見失ったあとに画面全体から探し直す）は第1弾に入れません。UETrackは単一物体の連続追跡が前提で、再検出の仕組みを持っていません。自前で足すと、それ自体が別の設計課題になります。代わりに「直前の位置で止める／追い続ける」の2択を置き、**ずれたら分割して追い直す**という利用者の操作で解決します。

残る5項目（見失いのしきい値、見失ったときの扱い、動きの滑らかさ、枠の大きさの追従、中間点の間隔）は、いずれも**追跡AIの外側の後処理**の設定です。これらをプラグイン側の純粋な関数に置いたので、**設定が増えてもサーバーとの契約は変わりません。**

## 20. バリアントをBase1種にした理由

UETrackにはBase・Small・Tinyの3つの大きさがあります。**第1弾ではBaseだけを使い、選ぶ画面も出しません。**

小さいものを選べるようにすると、「どれを選べばいいのか」という判断を利用者に押しつけることになります。そして精度の違いは、追尾のずれという形でしか現れません——利用者にはどの設定が原因か分かりません。まずBaseで実用に足りるかを実測し、**足りなかったときに初めて**小さいものを検討します。

モデル選択のラジオボタンを灰色の見本として置いてあるのは、この判断とは別の話です。**将来ほかの追跡AIを足す余地がある**ことを画面上で示しておくためのもので、UETrackの内部のバリアントを選ぶためのものではありません。

## 21. 任意導入と新設リポジトリにした理由

**どちらも「止められるようにしておく」ためです。**

UETrackは**コード側にライセンスファイルが無く**（形式上は全権利留保）、**重み側にはApache-2.0の表示がある**という食い違いを抱えています。公開リポジトリは事実上更新が止まっており、リポジトリ上の問い合わせ（Issue）にも応答がありません。責任はオーナーが引き受けていますが、**あとで問題が起きたときに素早く止められる形**にしておく価値があります。

- **重みを既存の配布リポジトリに混ぜず、新しいリポジトリへ置きます。** 問題が起きたら、そのリポジトリを削除するか非公開にするだけで配布が止まります。既存の配布物は影響を受けません。
- **基本の導入手順に同梱しません。** 同梱したほうが利用者の手間は減りますが、そうすると全利用者の環境に自動的に入ります。`install-UETrack.bat` を必要な人が実行する形にすれば、**入れた人だけが持つ**状態になります。

**利便性より封じ込めを優先した判断です。** 記述ファイルは1本なので、差し替えも撤去も容易です。

## 22. 先行事例から採ったこと

AviUtl2の周辺には、近い形の実装が2つあります。どちらもMITライセンスで公開されており、**2026-09-11に実物のソースとREADMEを読んで確かめた事実**を以下に記します。

### MotionTracking MK-II Plus for AviUtl2

**本設計にもっとも近い先行事例です。** AviUtl1向けの `MaverickTse/MotionTracking_MKII` から `Mr-Ojii/MotionTracking_MK-II_Plus` を経てAviUtl2へ移植されたもので、AviUtl ExEdit2 の 2.0beta48 以降に対応し、2.1.0 で動作が確認されています。

作りはこうです。対象物はポップアップウィンドウの中で矩形をドラッグして指定します。追跡器はOpenCVが持つ6種（MIL・KCF・CSRT・DaSiamRPN・Nano・ViT）から選びます。**入力はAviUtl2本体の合成結果を `rendering_scene_video` で1フレームずつメモリ上で受け取る形で、一時ファイルは作りません**（`src/tracker/tracker.cpp`）。解析は別スレッドで走り、閉じられる進捗ダイアログが処理中の毎秒フレーム数を表示し、閉じると協調的に中止します。**出力は部分フィルタへ全フレームの中間点として書き込みます**（`src/insert/insert_object.cpp` の `make_alias_as_sub`）。1フレームだけの追跡失敗は前後の平均で補い、追跡が途切れた区間ではオブジェクトを分割します。

**採ったもの**

- **合成結果を1フレームずつメモリで受け取る方式**（§12）。一時ファイルを作らないという判断もここと同じです。
- **部分フィルタへ中間点として書き戻すという出力の形**（§5.7）。
- **換算式の形**——中心を原点へ移す変換（同実装の `fix_frame`）と、大きさは幅と高さの大きいほう・縦横比は符号つきの百分率という取り方（同 `make_alias_as_sub`）。本書 §5.6 はこれに一致させています。
- **操作を止めない進捗表示と、毎秒フレーム数の提示と、協調的な中止**（§3.2・§5.3）。

**採らなかったもの**

- **中間点を全フレームに打ち、値が変わらないフレームも間引かないこと。** 本設計では中間点の間隔を設定にしました（§3.1）。
- **追跡が途切れたときに自動でオブジェクトを分割すること。** 本設計では分割を利用者の操作に委ねます（§1の手順7）。自動で分割すると、削除と作り直しを1つの編集区間に収めて「元に戻す」1回で戻すという §5.7 の約束が保てなくなります。

### `clean262/sam3_bb_gb_generator`

SAM3という切り抜きAIを使うプラグインで、**外部のAI処理の結果を `create_object_from_alias` でタイムラインへ入れる動作実績**があります。本プロジェクトは仮オブジェクトの実装でも同じ方式を採っており、**オブジェクトの識別子を保持せず、毎回エイリアスと位置で探し直す**という安全な型もここから採っています（[`TIMELINE_ALPHA_REQUIREMENTS.md`](../AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/Docs/TIMELINE_ALPHA_REQUIREMENTS.md) 第0節C）。**別プロセスのPythonに重い処理を任せる構成**の前例としても参考になります。

**採らなかったもの**

- **素材ファイルをPython側が独立に読み直すこと。** この実装は `cv2.VideoCapture` で素材を直接開きますが、それでは「画面に映っているもの」ではなく「素材そのもの」が入力になります（§12）。
- **ファイルの監視で連携すること。** この実装はPythonとC++がファイルの出現を見張って受け渡します。本設計はHTTPで同期的にやり取りします。同実装では出力のmp4が自動で消えず、既定で120秒に切り詰められるという制約も付いています。
- **マスク動画を独自形式で合成する「透過」出力。** 同実装はマスク動画を独自の `.anm2` と `.mod2` で合成しており、READMEにマスクのずれという未解決の不具合が記載されています。

### 採らなかった第三者のフォーク

UETrackを推論の別形式（ONNX）へ変換して速くする改造は、あるコンペの参加チームのフォークに実例がありますが（末尾の「参照」）、**本機能の第1弾には入れません**（§10）。素のPyTorchのままで実用の速度に届くかを先に測り、届かなかったときの手札として残します。なお、**これらのフォークはいずれも自分のライセンスを明記しておらず、§21で述べたライセンスの食い違いを解いた事例にはなりません。**
