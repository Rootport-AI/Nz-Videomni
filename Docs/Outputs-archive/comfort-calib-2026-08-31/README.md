# 快適上限キャリブレーション計測台（2026-08-31）

このフォルダは、動画生成の「快適上限」を実機で測り直すための計測台です。
製品のコードや設定には一切手を触れません。書き込むのはこのフォルダの中だけです。

計測は必ず **製品の HTTP インターフェース経由** で行います。ワーカーを直接叩く
方式は取りません。実際に利用者が通る経路をそのまま測ることが目的だからです。

---

## 1. 結論から：何を測って、何を判定するか

1 本のジョブごとに、次の 3 つの計器を同時に走らせます。

| 計器 | 出力先 | 何が分かるか |
|---|---|---|
| Windows の GPU メモリ カウンター（`vram_sampler2.ps1`） | `runs/<ラベル>/wddm.csv` | 専有メモリと共有メモリの推移。約 1 秒間隔。**共有メモリの増加が、本体メモリへの追い出し（あふれ）の唯一の直接証拠** |
| `nvidia-smi dmon`（1 秒間隔） | `runs/<ラベル>/dmon.txt` | 演算器の使用率と、本体と GPU の間の転送量（受信・送信、毎秒メガバイト） |
| ワーカーの記録ファイルの追尾 | `runs/<ラベル>/worker_tail.csv` | ワーカーの記録には時刻が入っていないため、行が届いた時刻をこちらで打ちます |

加えて、時刻付きのサーバー記録（`logs/server.log`）をジョブごとに切り出して
`runs/<ラベル>/server_slice.log` に保存します。

判定は 4 つの軸で行います。

- **軸 1（共有メモリの高止まり）** — 第 2 段階のノイズ除去の区間で、共有メモリの
  中央値が「待機時の 95 パーセンタイル ＋ 300 メガバイト」を超えているか。
- **軸 2（転送量）** — 同じ区間の受信転送量の中央値が、待機時の 95 パーセンタイル
  を超えているか。中央値と最大値の両方を必ず記録します。
- **軸 2b（転送量・基準比）** — 軸 2 には、このマシン固有の落とし穴があります。
  ブロック入れ替えが有効な間、ノイズ除去の各段で変換器のブロックが本体から
  GPU へ流れ続けるため、**転送が出続けているのは健全な状態の姿**です。しかも
  待機時の 95 パーセンタイルは 0 でした。そこで「同じ解像度の最小構成と比べて
  転送が増えたか」も別に判定します。こちらが本来の問いです。
- **軸 3（第 2 段階の遅さ）** — 1 トークンあたりの秒数が、基準点の 1.20 倍を
  超えているか。
- **軸 4（復元処理の遅さ）** — 1 かたまりあたりの復元秒数が、基準点の 1.20 倍を
  超えているか。復元区間の共有メモリのピークも併せて記録します。

  - **有害なあふれ** = 軸 1 かつ 軸 2 かつ（軸 3 または 軸 4）
  - **無害なあふれ** = 共有メモリは高止まりしているが、軸 3 も軸 4 も立たない
  - **問題なし** = 軸 1 が立たない

判定結果に関係なく、生の数値は必ず全部記録します（専有メモリのピーク、共有
メモリのピーク、転送量の中央値と最大値、第 2 段階の秒数、トークンあたり秒数、
復元秒数、かたまりあたり秒数、`metadata.json` の各値、実際に効いた高速化設定、
ジョブ番号、出力先、開始と終了の実時刻）。

## 2. 使い方

Python は必ずバックエンドの仮想環境のものを使ってください。システムの Python
には触れません。

```
S:\OriginalApps\12_Nz-LTX23-AviUtl2\Nz-Videomni\.venv\Scripts\python.exe calib.py <副命令>
```

| 副命令 | 何をするか |
|---|---|
| `server start` | `run.ps1` を切り離して起動し、プロセス番号を `server.pid` に記録し、状態確認が通るまで待ちます |
| `server start --pid <番号>` | すでに外で起動済みのサーバーを登録するだけ（下の注意を参照） |
| `server status` | 状態確認の結果をそのまま表示します |
| `server stop` | ジョブが走っていないことを確かめてから、プロセス木ごと停止し、ポートが空くまで待ちます |
| `load --base-model LTX23\|LTX25` | 土台モデルを切り替え、準備完了になるまで待って所要時間を表示します |
| `idle-calib --minutes 3` | モデルを読み込んだまま何もしない状態を計測し、`calib/calibration.json` を作ります |
| `run --plan plan.json` | 計測点を 1 件ずつ順番に実行します |
| `reanalyse [--label ラベル]` | 保存済みの記録から `run.json` を作り直します。**解析の不具合を直したときに、GPU のジョブをやり直さずに済ませるための命令です** |
| `report` | `manifest.jsonl` から一覧表を出力します |
| `restore-state` | 計測全体の最後に、元の土台モデル（`original_state.json` に記録）へ戻します |

### 起動についての注意（重要）

`server start` の切り離し起動は、**保護された（サンドボックス化された）シェルから
呼ぶと子プロセスが即座に落ちます**。2026-08-31 の初回試行では
`server_console.log` が空のまま 5 分待って失敗しました。保護のかかっていない
PowerShell から次のように起動し、そのプロセス番号を `--pid` で登録してください。

```powershell
$p = Start-Process -FilePath "powershell.exe" `
  -ArgumentList "-NoProfile","-ExecutionPolicy","Bypass","-File","<バックエンド>\run.ps1" `
  -WorkingDirectory "<バックエンド>" `
  -RedirectStandardOutput "<ここ>\server_console.log" `
  -RedirectStandardError  "<ここ>\server_console_err.log" `
  -PassThru -WindowStyle Hidden
$p.Id
```

### 計測点の書き方（`plan.json`）

計測点の一覧（配列）です。1 件はこう書きます。

```json
{
  "label": "smoke_512x320_f57",
  "kind": "single",
  "base_model": "LTX23",
  "width": 512, "height": 320, "num_frames": 57,
  "seed": 12345,
  "prompt": "…（省略すると土台モデルに応じた既定の指示文が入ります）",
  "accel": {
    "attention_backend": "sdpa",
    "block_swap_prefetch": true,
    "keep_resident": false,
    "fused_gguf_dequant_kernel": true,
    "vae_mode": "default"
  },
  "baseline_label": null
}
```

- `kind` は `single` / `chain` / `a2v` のいずれか。`chain` と `a2v` では
  `num_frames` の代わりに `clips`（例 `[{"num_frames":25},{"num_frames":161}]`）と
  `stage2_window`、`chunked_upsample` を指定します。音声駆動（`a2v`）は
  `audio_id` を付け、`stage2_window` は `full_length`、クリップは 1 本です。
- 高速化の 5 項目は**毎回必ず明示的に送ります**。既定に任せません。
- `baseline_label` には、同じ解像度の基準となる計測点のラベルを書きます。
  軸 3・軸 4・軸 2b はこの基準との比で判定します。`null` なら判定は保留（空欄）です。
- 幅と高さは 64 の倍数、フレーム数は 8n+1 でなければサーバーに拒否されます。
- 土台モデルが計測点の指定と違う場合、その点は実行せず記録だけ残して次へ進みます。
  切り替えは `load` で明示的に行ってください（計測の途中で勝手に切り替えません）。

## 4. GPU の識別子の見つけ方

同じ GPU でも、Windows の性能カウンターに出る識別子は再起動などで変わることが
実際にありました。そのため識別子は**実行時に必ず探し直します**。手順は、
`GPU Adapter Memory` の全インスタンスの専有使用量を 1 回だけ採取し、
**最も専有使用量が大きいものを選ぶ**だけです。単体の GPU は待機中でも
1 ギガバイト前後を確保しており、内蔵や仮想のものはほぼ 0 なので、これで分かれます。
選んだ識別子と候補一覧は `luid.json` に残ります。

## 5. 時刻の取り方（ここが計測の要）

- **第 2 段階のノイズ除去** は `logs/server.log` の `ltx.runner` の行から取ります。
  形は `generate stage-2 denoise 3/3 steps (0.02 step/s, 99.1s elapsed)` です。
  この行は約 2 秒に 1 回に間引かれており、しかも `started` の行は
  **1 ステップ目が終わった時点**で出ます。したがって `99.1s elapsed` が表すのは
  `最後の完了数 − 1` ステップ分です。1 ステップあたりの秒数を出してから
  全ステップ数を掛け直すことで、段階全体の秒数にしています。
- **復元処理（2.3）** は `logs/ltx_worker.log` の進捗バーから取ります。この記録には
  時刻がないので、追尾スレッドが行の到着時刻を打ちます。復帰文字（`\r`）でも
  行を切るので、かたまりごとの到着時刻が取れます。
- **2.5 の各段階** は `logs/ltx25_worker.log` の `PHASE` 行（秒数と確保量・予約量の
  ピークを持つ）から取ります。`22_stage2_denoise…` と `30_decode_encode` が該当します。

### 復元処理の計測について、判明した 2 つの癖（重要）

過去の 1367 本の進捗バーを調べて確認した事実です。

1. **最初のかたまりはバーが出来る前に復元されています。**
   `ltx_pipelines/utils/media_io.py` は `first_chunk = next(video)` で 1 つ目を
   先に取り出してから進捗バーを作ります。そのため到着時刻から取れる区間には
   1 つ目が含まれません。これは解像度ごとにほぼ一定のずれなので、
   「同じ解像度の基準点との比」で判定する軸 4 では相殺されます。
2. **バーが 100 パーセントで終わらないことがよくあります。**
   バーの分母は予測値で、実際にはそれより 1 つ少ないところで終わることが多く
   （1367 本中 593 本）、その場合 100 パーセントの締めの行は書かれません。
   これは解析の失敗ではなく正常な姿なので、未完のバーもそのまま採用します。

### 復元区間が測れないときの代替（明記）

復元が数秒で終わる小さな条件では、進捗バーの全行が追尾スレッドの 1 回の読み取り
（0.2 秒）に収まってしまい、到着時刻に分解能がありません。この場合は
**「第 2 段階の最後の行 → 動画ファイルが書かれた時刻」** を復元区間として使い、
`run.json` の `decode.source` に `FALLBACK` と明記し、
`degenerate_arrival_window: true` を立てます。この区間には第 2 段階の後始末と
動画の組み立ても含まれるため、外側の上限値である点に注意してください。
本番の計測条件（高解像度・長尺）では復元が数十秒かかり、かたまりが数秒おきに
届くので、到着時刻による計測が働きます。

## 6. 高速化設定が実際に効いたかの確認

`metadata.json` の `attention_used` / `block_swap_prefetch_used` /
`keep_resident_used` / `fused_gguf_dequant_kernel_used` / `vae_mode_used` を

実行中の一行要約にも `!! acceleration DEGRADED/mismatched` として出ます。

## 7. 守っている決まり

- 同時に走らせる GPU のジョブは常に 1 本だけです。
- `outputs/` と `uploads/` の中身は一切消しません。
- 製品のコード、`config.yaml`、`state.json`、テスト、文書には触れません。
  土台モデルの切り替えは `state.json` の `active_base_model` を書き換えるため、
  計測開始前の値を `original_state.json` に残し、計測全体の最後に
  `restore-state` で戻します。
- `nvidia-smi` は計測台が持つ 1 秒間隔の 1 プロセス以外では回しません。

## 8. 判定規約 v2（2026-08-31、E1a の実測を受けて追加）

v1 の 4 軸はそのまま残し、`run.json` に `axes_v2` と `verdict_v2` を追加しました。
**v1 の 2 つの軸が実測で機能しないことが分かった**ためです。

- **v1 の軸 1 は全点で成立してしまいました。** 待機時の共有メモリは 144 メガバイト
  ですが、健全に動いているだけで常時 650 メガバイト前後を使います。
  「待機時の 95 パーセンタイル ＋ 300 メガバイト」＝ 444 メガバイトの線は、
  正常な仕事が普通に越えてしまいます。
- **v1 の軸 2 はほとんど成立しませんでした。** 1 秒間隔の採取では、ブロック入れ替えの
  転送の山が採取と採取の間に落ちてしまい、区間の**中央値が 0 のまま**になります。
  最大値は毎秒 14,000 メガバイトを超えているのにです。

### 軸 1b（相対プラトー）

各窓（第 2 段階の窓・復元の窓）の共有メモリの**中央値**が、**同じ解像度の基準点の
同じ窓の中央値 ＋ 300 メガバイト**を超えているか。待機時ではなく「同じ条件で
動いている基準点」と比べるのが要点です。基準点自身は比較対象がないので評価不能
（`null`）です。

### 軸 2 v2（転送量・記録のみ）

各窓について**非ゼロ標本の割合**と **75 パーセンタイル**を記録し、基準点の同じ値との
比も出します。**判定には一切使いません**（`axes_v2.axis2_v2_pcie` に補助証拠として
置くだけです）。中央値が 0 でも非ゼロ割合は 0.40〜0.51 あり、リンクが実際には
忙しいことが分かります。

### verdict_v2

- **harmful** = （軸 3 かつ 第 2 段階の窓の軸 1b）または（軸 4 かつ 復元の窓の軸 1b）
- **organic** = どちらかの窓で共有メモリが待機時のしきい値を超えているが harmful ではない
- **clean** = 共有メモリが待機時のしきい値以下
- **baseline** = 基準点そのもの（`baseline_label` が無い点）

### 軸 4 の基準点の薄さ

復元の窓は「第 2 段階の最後の行 → 動画ファイル書き出し」で統一済みなので、その
定義のまま 1 かたまりあたり秒数の比を使います。ただし**基準点のかたまり数が 2 以下**
のとき（1440p の 57 フレーム基準点がこれに当たります）、1 かたまりあたりの値は
1 回の割り算に乗っているだけで脆いので、`run.json` に `decode_baseline_thin: true`
を立てます。比の値は出しますが、そのまま信用しないでください。
