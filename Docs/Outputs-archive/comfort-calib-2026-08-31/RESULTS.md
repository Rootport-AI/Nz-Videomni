## 2. 判定規約

較正の途中で判定規約を 2 回改めた（v1 → v2 → 今回新設の v3）。3 つとも `run.json` に痕跡が
残っているか、本ファイルのために再計算した。

### v1（計測台の当初案、README §1）

共有メモリの高止まり（軸1）・PCIe 転送（軸2）・stage-2 の速度低下（軸3）・復元処理の速度低下
（軸4）の 4 軸。**実測で軸1・軸2の 2 つが機能しないことが判明した**（README §8）。

- 軸1（待機時 95%点＋300MB＝444.1MB を境に判定）は**全点で成立してしまう**。健全に動いている
  だけで共有メモリは常時 650MB 前後を使うため。
- 軸2（PCIe 中央値が待機時 95%点＝0 を超えるか）は**1 秒間隔の採取ではブロック入れ替えの転送の
  山を捉えられず**、区間の中央値がほぼ 0 のままになる。最大値は毎秒 14,000MB を超えているのに
  である。

### v2（README §8、E1a の実測を受けて改定）

- **軸1b（相対プラトー）**: 各窓（stage-2 窓・復元窓）の共有メモリ中央値が、**同じ解像度の
  基準点の同じ窓の中央値＋300MB** を超えているか。待機時ではなく「同じ条件で動いている基準点」
  との比較に変えた。
- **軸2 v2（PCIe・記録のみ）**: 非ゼロ標本の割合と75%点を記録し基準点との比も出すが、
  **判定には使わない**。
- **verdict_v2**: harmful ＝（軸3 かつ stage-2 窓の軸1b）または（軸4 かつ復元窓の軸1b）。
  organic ＝ どちらかの窓で共有メモリが待機時基準を超えているが harmful ではない。clean ＝
  超えていない。baseline ＝ 基準点自身。

### v3（今回、本ファイルのために新設。速度・PCIeを線引きに使わない版）

**快適（○）＝ 対象の 2 つの窓（stage-2 窓・復元窓）のどちらでも、共有メモリの中央値が
同じ解像度の基準点比＋300MB 未満（持続的な追加退避が観測されない）。それ以外は非快適（×）。**
速度（軸3・軸4）と PCIe は証拠として記録するが、線の決定には使わない。これは `run.json` の
`axes_v2.axis1b_stage2_shared_vs_baseline` と `axis1b_decode_shared_vs_baseline` がどちらも
`false` であることをそのまま「○」と読み替えたものであり、**v2 の `verdict_v2`
（harmful/organic/clean）とは別の軸で判定した値である**。両者が食い違う点（後述）があるため、
結果表では `v2判定` 列と `v3快適` 列を必ず併記した。

**なぜ速度・PCIeを外すか**: 720p の 289f・305f・321f の三つ組は、いずれも復元窓の共有メモリが
同程度（+1,250MB・+682MB・+1,208MB）持続的に高止まりしているにもかかわらず、PCIe 受信の
挙動が割れる。289f と 321f は復元窓の p90 が 25,897MB/s・21,637MB/s（frac>5000MB/s が
0.18 前後）と明確に張り付くが、305f は p90 がわずか 264MB/s（frac>5000MB/s は 0）で無症状の
ままだった（`runs/e1_720_289`・`e1_720_305`・`e1_720_321` の `dmon.txt` を stage-2/復元窓で
実測）。同量の共有メモリのあふれが起きていても、その先で実際にスラッシング（読み書きの奪い
合い）が起きるかどうかは確率的であり、速度や PCIe の値だけでは再現しない。したがって「線」を
引く基準には共有メモリの持続的上昇だけを使い、速度・PCIe は有害性の裏付け（何が起きているかの
説明）としてのみ扱う。

**計器の限界**:

- **PCIe は 1 秒間隔の中央値ではブロック入れ替えのバーストを捉えられない。** 中央値・75%点は
  ほぼ常に 1 桁 MB/s に張り付くため、本ファイルでは p90・最大値・`frac>5000MB/s`（5,000MB/s
  を超えた標本の割合）も併記する。
- **LTX 2.3 の復元区間の定義は「stage-2 の最後の行 → mp4 書き出し」。** `tqdm` の進捗バーは
  最初のかたまりを作る前に 1 つ目を取り出す（`media_io.py` の `first_chunk = next(video)`）ため
  バー自体には現れない。同一解像度の基準点との比では相殺されるが、絶対値としては先読み分を
  含む外側の上限値である点に注意。
- **LTX 2.5 の `metadata.json` には `vae_mode_used` が書かれない（`null`）。** 2.3 と異なり、
  適用確認の対象から外れている。
- **`e3`（LTX 2.5 Chained）は `seed 1234`、`e2`（LTX 2.5 単発）は `seed 12345`。** シードは
  系統間で統一されていない。
- **プロンプトが 2.3 系と 2.5 系で異なる。** 2.3 系（E1・E4）:「a cinematic tracking shot of
  a red sports car driving along a coastal road at sunset」。2.5 系（E2・E3）:「A red vintage
  sports car drives along a winding coastal road at golden hour, cinematic tracking shot,
  film grain」。
- **共有メモリはジョブ間で約 1〜2 分持ち越される。** 直前の `e1_720_305`（復元窓の共有メモリ
  1,342MB）が終わったわずか 5 秒後に始まった `e1_1080_161` は、開始直後の共有メモリが
  1,338.7MB→1,218MB台のまま約 85 秒続き、開始から約 75 秒後に 641MB台へ、約 135 秒後に自分の
  定常値（603〜632MB）へ落ち着いた（`runs/e1_1080_161/wddm.csv` 実測）。同一解像度の基準点との
  差分で見る限り最終的な中央値には影響しないが、ジョブ冒頭の瞬間値だけを見ると前のジョブの
  影響を拾ってしまう。

## 3. 結果表

以下は `runs/<label>/run.json` をバッチ（計測計画ファイル）ごとに集計したものである。
列の意味:

- **専有ピークMB** = 該当ジョブ全体（`vram.job`）での dedicated（専有）メモリのピーク。
- **共有中央値 s2窓／dec窓** = stage-2 窓・復元窓それぞれでの共有（shared）メモリの中央値。
- **比(基準)** = 同じ解像度の基準点に対する比（sec/token・sec/chunk それぞれ）。基準点自身は
  `-`。
- **rxpci p90(s2窓) / frac>5000(s2窓)** = stage-2 窓内の PCIe 受信転送量の 90%点と、
  5,000MB/s を超えた標本の割合。`dmon.txt` を `run.json` の `stage2.start_iso`〜`end_iso` で
  切り出して計算した（`run.json` 自体には p90 は保存されていないため今回新たに算出した）。
- **v2判定** = `run.json` に保存済みの `verdict_v2`（harmful / organic / baseline）。
- **v3快適** = 本ファイルのために新規算出した値。○＝両窓とも基準比+300MB未満（快適）、
  ×＝どちらかの窓で+300MB以上（非快適）、基準＝その解像度の基準点自身（比較対象がなく評価対象
  外）。
- **used_ok** = `used_matches_request.ok`。要求した高速化設定（`sdpa`・`block_swap_prefetch`・
  `keep_resident`・`fused_gguf_dequant_kernel`・`vae_mode`）がそのまま効いたか。全 37 本で
  ○（食い違いゼロ）。

## 5. 派生した値

以下は今回の実測から読み取れる値であり、製品の設定にどう反映するかの提案は含まない。

- **LTX 2.3 既定構成の解像度別「快適な最大フレーム数」**: 1280×768 で 273f、1920×1088 で
  161f、2560×1472 で 81f。いずれも v3（共有メモリの相対プラトー、+300MB未満）で 2 回以上
  快適が再現した値。1920×1088 の 169f(44,880tok) は初回快適・再走非快適だったため、この解像度
  では 161f が実測で再現した上限になる。
- **LTX 2.5 単発の「快適」と「退避の兆し」**: 1280×768 で 369f(45,120tok) までは共有メモリが
  平坦（v3 快適・sec/token比も1.2倍未満）。385f(47,040tok) は共有メモリの相対プラトーでは
  v3 の閾値を割っていない（+121.0MB）が、sec/token 比が 1.426 倍まで伸びており速度カーブに
  折れが生じている。401f(48,960tok) は共有・速度とも明確に非快適。
- **LTX 2.5 Chained（窓22）の「快適」と「退避の兆し」**: 1,920×1,088(44,880tok) は共有メモリ・
  PCIe とも基準点並みで明確に平坦。1,984×1,088(46,376tok) は共有メモリの相対プラトーでは
  v3 の閾値未満（+192.6MB）だが、PCIe 受信 p90 が基準の約 1,300 倍（11.2MB/s→14,664.8MB/s）
  まで跳ね上がっており、共有メモリだけでは捉えきれない退避の兆候が見える。1,984×1,120
  (想定47,740tok) は高さの検証エラーで未計測。
- **a2v と T2V の等価性**: 同一幾何（720p/361f・1080p/169f）で比較すると、peak_vram_mb・
  peak_vram_reserved_mb・stage-2/復元窓の共有メモリ中央値・sec/token のいずれも ±4% 以内で
  一致した。壁時計全体の generation_time_seconds は 720p のペアだけ 24.7% の差があったが、
  stage-2秒数・復元秒数は両者で一致しており原因は本計測台の内訳では特定できていない。
- **高速化設定の適用確認**: 37 本すべてで `used_matches_request.ok` が真であり、要求した
  5 項目（`attention_backend`・`block_swap_prefetch`・`keep_resident`・
  `fused_gguf_dequant_kernel`・`vae_mode`）とサーバー側が実際に使った値の食い違いは 0 件。
