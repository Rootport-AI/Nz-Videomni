## 2. 判定規則

### 2.1 v3（第1次から不変）

**快適（clean）＝ 対象の 2 つの窓（stage-2 窓・復元窓）のどちらでも、共有メモリの中央値が
同じ幾何の基準点の同じ窓の中央値＋300 MB 未満。** 速度と PCIe は証拠として記録するが、
線の決定には使わない。

### 2.2 v3′（今回新設・裁定 J1 の案B′）

v3 の 2 窓に次の窓を加え、**同じ物差し（基準比 +300 MB）**で見る。v3 列を置き換えるのではなく、
**両方を併記する**（J1 の指示）。

| 窓 | 系統・種類 | 基準の取り方 |
|---|---|---|
| 参照の符号化 `reference_encode` | 両系統（`single_ref` と `outpaint`） | 同幾何・低尺の**参照つき**点の同じ窓 |
| stage-1 `s23_stage1` | 2.3 | 同幾何・低尺の同種の点の同じ窓 |
| 中間の隙間 `s23_gap_mid` | 2.3 | 同上（stage-1 復元＋1 回目の合成＋画素拡大＋stage-2 符号化を含む**外側の上限値**） |
| 末尾の隙間 `s23_gap_tail` | 2.3 | 同上（stage-2 復元＋2 回目の合成＋動画の組み立てを含む**外側の上限値**） |
| 各 PHASE 窓 `p25_*` | 2.5 | 同上（`GENERATE_REPORT` の秒数から到着時刻を逆算した**厳密**な窓） |

**2.5 の画角拡張では復元窓を `28_stage2_decode` へ切り替えている**（README §3.3）。
`30_decode_encode` は画角拡張では動画の組み立てだけで 1.4〜2.0 秒しかなく、そこで判定すると
何も測っていない窓で判定することになるためである。**この切り替えの副作用として、2.5 の
画角拡張の復元窓（`28_stage2_decode`）と、対照に使う 2.5 の t2v 点の復元窓
（`30_decode_encode`）は同じ窓ではない**（§7 で再掲）。

### 2.3 10 標本未満の窓は判定不能

窓ごとに `wddm_samples` を併記し、**10 標本に満たない窓は `decidable: false` として結論から
外す**。総合判定は `plateau`（判定可能な窓のどれかが +300 MB 超）／`clean`（判定可能な窓が
あり、どれも超えない）／`undecidable`（判定可能な窓が 1 つも無い）／`baseline`（基準点自身）。

### 2.4 `metadata` の `peak_vram_*` を参照つき／無しで比較してはならない

`fast_video_pipeline.py:1275` が参照を通る経路ではジョブの途中で `reset_peak_memory_stats` を
呼ぶため、`peak_vram_mb` と `peak_vram_reserved_mb` は 2 本のジョブで数え始めた場所が違う。
`run.json` の `metadata.peak_vram_note` に同じ注意書きが埋め込まれている。本ファイルの表でも
これらの列は**参考値**として置き、比較には窓ごとの共有メモリ統計と専有ピークを使う。

## 5. 仮説の検証結果

### H1（§3-133）: 参照は v3 の 2 窓を動かさない → **支持**

同幾何・同フレーム数の t2v と参照つきの対で、v3 の 2 窓の共有メモリ中央値を直接引き算した。
（表の delta 列は各点の基準点との比なので、ここでは対どうしの直接差を算出し直している。）

| 系統 | 幾何 / フレーム | stage2窓 差（ref − t2v） | 復元窓 差（ref − t2v） |
|---|---|---:|---:|
| 2.3 | 1280×768 / 121f | 1,169.2 − 1,160.4 ＝ **+8.8 MB** | 1,169.0 − 1,159.7 ＝ **+9.3 MB** |
| 2.3 | 1280×768 / 361f | 1,213.2 − 1,132.9 ＝ **+80.3 MB** | 1,124.7 − 1,134.6 ＝ **−9.9 MB** |
| 2.5 | 1280×768 / 121f | 636.0 − 651.9 ＝ **−15.9 MB** | 636.0 − 652.0 ＝ **−16.0 MB** |
| 2.5 | 1280×768 / 361f | 628.0 − 628.3 ＝ **−0.3 MB** | 611.9 − 612.0 ＝ **−0.1 MB** |

**最大でも +80.3 MB（2.3 の 361f・stage-2 窓）で、反証条件の +300 MB には遠く及ばない。**
参照の上乗せは v3 の 2 窓の判定を動かさない。ただし**この検定は 121f と 361f の 2 対でのみ
成立している**（385f には対の t2v 点が無い＝計画上 Tier B）。反転が起きた 385f で参照が
2 窓を動かさないことは、今回の実測では確かめられていない。

### H2′（§3-133）: 参照エンコードの予約はトークン線形、境界は単発線のすぐ上 → **支持**

**2.3**: 予測（`1086 + 4.902 × 参照トークン`）に対する残差は 5 点すべてで **±2.9% 以内**
（最大 +2.87%＝`r_g1_121_ref_23`、最小 −0.94%＝`r_g2_089_ref_23`）。同じ 5 点だけで回帰し直すと
**傾き 4.9401・切片 1,098.6**（先験の法則 4.902・1,086 とほぼ同じ）で、法則そのものが再現した。
なおスモーク点（参照 168 トークン）だけは残差 **+15.21%** と大きく外れる。極端に小さい
トークン数では切片の効き方が合わないと読める（掃引の範囲外の点であり、法則の当てはめ対象から
外れる）。

**境界の予測**: 予測式は「予約 15,500 MB を超えると共有メモリへ逃げ始める」という観察から
参照 2,941 トークン（単発換算 47,050 トークン ＝ 線 44,880 の 1.048 倍）を反転位置と見込んでいた。
実測では `r_g1_385_ref_23`（参照 2,940 トークン・予測 15,497.9 MB・**実測 15,734 MB**）が
plateau に反転し、その直下の `r_g1_361_ref_23`（参照 2,760・実測 14,818 MB）は clean のままだった。
**予測した位置に、予測した向きで境界が現れた。**

（追記・Tier B 最小）反転点を再走した `r_g1_385_ref_23_r2` でも、参照エンコードの予約ピークは
**実測 15,650 MB・残差 +152.1 MB＝+0.98%** と予測の 1% 以内に収まり、判定も再び plateau だった
（§3.3 表II）。**予測式は境界そのものの点で 2 回とも当たっている。**

**2.5**: 同じ形（トークン線形）が成り立つ。同じ 5 点で回帰すると
**傾き 4.8797・切片 506.4**、その自前の直線に対する残差は **−2.59%〜+2.96%** に収まる
（2.3 の法則をそのまま当てた場合の残差は §3.2 表II のとおり −3.50%〜−9.91%）。

- **傾きはほぼ移植可能**（4.902 → 4.8797、差 0.5%）。
- **切片は約 580 MB 低い**（1,086 → 506.4、差 579.6 MB）。2.3 の法則をそのまま 2.5 に当てると
  実測は 5 点すべてで下振れする（−3.50%〜−9.91%。トークンが小さいほど乖離が大きい）。
- **ただしこれは 5 点回帰の値であり、法則として確定させるには点数が足りない（留保）。**
  傾きを 4.902 に固定したときの切片は 457.9 MB になる。

同じ 2,940 参照トークンで、2.3 は予約 15,734 MB で反転し、2.5 は 14,955.5 MB で反転しなかった。
2.5 が上まで持つ理由の一部は、この切片の低さで説明がつく（一次読み）。

## 6. 境界の一次読み（**予算の採用値はオーナー裁定待ち**）

## 7. 既知の計測台の注意（劣化ではない・§7.1 のみ修正済み、残りはオーナー判断待ち）

### 7.1 `vae_mode_used` の期待表が 2.3 語彙のままだった（**Tier B 最小の前に修正済み**）

計測台は要求した加速 5 項目とサーバーが実際に使った値を突き合わせ、`used_matches_request` に
入れる。ここで期待値の語彙が 2.3 のもの（`on` / `off`）のままであるのに対し、**LTX 2.5 は
`vae_mode_used` に `"conv"` を返す**ため、**Tier A の実行中は 2.5 の全点で突き合わせが外れていた**。

| 系統 | 本数 | Tier A 実行時の `used_matches_request.mismatches` |
|---|---:|---|
| LTX23 | 15 | `{}`（食い違いゼロ） |
| LTX25 | 13 | `{"vae_mode_used": {"requested": "off", "used": "conv"}}`（**13 本すべてで同一**） |

**これは加速設定の劣化ではなかった。** 不一致は `vae_mode_used` の 1 項目だけであり、
`attention_used` / `block_swap_prefetch_used` / `keep_resident_used` /
`fused_gguf_dequant_kernel_used` は Tier A の 28 本すべてで要求どおりである
（Tier B 最小の 3 本も 5 項目すべて要求どおりで `ok: true`）。README §11 は
「2.5 が報告しない項目は値が返らない限り黙って照合を飛ばす」と書いているが、**§3-131 の実装で
2.5 も `vae_mode_used` を返すようになった**ため、「返らないから飛ばす」経路に入らず、
2.3 語彙の期待値と比べられて落ちていた。実害は実行中の一行要約に
`!! acceleration DEGRADED/mismatched` が出続けたことだけである。

**手当てと再解析（2026-09-04・Tier B 最小の直前）**: 期待表を 2.5 の語彙（`conv`）に対応させ、
**LTX25 の 13 点だけを `reanalyse` し直した**。結果は次のとおりである。

| 項目 | 再解析の結果 |
|---|---|
| `used_matches_request.ok` | 13 点すべて `false` → **`true`** に変わった |
| `mismatches` | 13 点すべて上記の 1 項目 → **`{}`**（空）に変わった |
| `verdict` / `verdict_v2` / `verdict_v3prime` | **13 点すべて変化なし** |
| v3′ の全窓の `delta_mb` | **13 点すべて変化なし** |

**判定は 1 つも動いていない。** 期待表は照合専用の列であり、窓の統計にも判定にも入らないことが
実測で確かめられた形である。再解析した行は `manifest.jsonl` に追記されるため、この 13 ラベルだけ
2 行ずつ入っている（§1.4）。**最終状態は後ろの行**である。

**LTX23 の 15 点は意図的に再解析していない。** 理由は `calib/calibration.json` が上書きされて
いるからで（§7.6）、いま再解析すると Tier A の LTX23 点に **LTX25 の待機時較正値**（あるいは
Tier B の LTX23 値）が当たってしまい、**v1 の `axis2_pcie_above_idle` など待機時の床を使う列が
動いてしまう**。Tier A の LTX23 の 15 点は、**当時の床 437.2 MB のまま凍結してある**のが正しい。
2.3 側には `vae_mode_used` の食い違いがもともと無い（`{}`）ので、再解析する動機も無い。

### 7.2 2.5 の参照エンコード窓は短すぎて WDDM では判定できない

2.5 の参照つき単発では `11_reference_encode` の実測秒数が **0.65〜1.76 秒**であり、
1 秒間隔の GPU メモリ採取では 1 標本しか入らない（5 点すべて n=1）。画角拡張側でも
4.65〜7.32 秒で 5〜7 標本にしかならず、規約の 10 標本に届かない。

**したがって 2.5 の参照エンコードは、WDDM の共有メモリではなく `GENERATE_REPORT` の
`11_reference_encode.peak_reserved_gib`（エンジン自身が測った予約ピーク）で見る。**
§3.2 表II はその値で作ってある。これは計測台の設計上の帰結であり、解析の失敗ではない。

2.3 の**参照つき単発**（倍率 2）も同様に短く、0.41〜3.41 秒・n=1〜4 で全点判定不能である。
2.3 の**画角拡張**（倍率 1・タイル分割）は 4.02〜15.04 秒とやや長く、`o_c2_153_23`（n=13）・
`o_c2_169_23`（n=13）・`o_c2_185_23`（n=15）の 3 点だけは判定可能になった（いずれも clean、
基準比 −30.2〜−4.5 MB）。いずれの場合も 2.3 はワーカー記録の区間ピーク行
（`interval peak … reserved …`）が読めるため、予約ピークはそちらを使う。

### 7.3 `r_g1_121_ref_23` / `r_g1_121_ref_25` の参照符号化窓には基準が無い

この 2 点は H1 の主検定の対を作るため、基準点に**参照なし**の点（`r_g1_121_t2v_*`）を
指定してある（README §5.2 の例外）。参照なしの点には参照符号化窓が存在しないため、
この窓の `baseline_shared_median_mb` は `null` になり `delta` も出ない。設計どおりである。

### 7.4 2.3 では復元窓と末尾隙間窓が同一区間

どちらも `[stage-2 の最後の進捗行 → "Video saved to"]` で定義されるため、2.3 の全点で
`restore` と `s23_gap_tail` の数値は完全に一致する。列を 2 つ立てているのは v3 と v3′ を
併記する規約のためであり、独立した 2 つの証拠ではない。

### 7.5 2.5 の復元窓は種類によって別の段階を指す

画角拡張（`kind: outpaint`）は `28_stage2_decode`、単発・参照つき単発（`kind: single` /
`single_ref`）は `30_decode_encode`。**対照実験で「復元窓」列を横に並べて読むときは、
両者が別の段階であることを必ず意識する。** 実測での差は §4.2 に書いたとおり大きい
（画角拡張の `30_decode_encode` は 1.4〜2.0 秒・0.25〜0.42 GiB、t2v のそれは 15.76 秒・6.496 GiB）。

### 7.6 `calib/calibration.json` は 3 回上書きされている（残っているのは 3 回目）

キャンペーン中に `idle-calib` を **3 回**走らせた。ファイルは毎回同じ場所に書かれるため、
残っているのは最後の 1 回だけである。

| 回 | 時刻 | 土台モデル | 共有メモリ 95%点 | **窓の絶対閾値** | 掛かっている点 |
|---:|---|---|---:|---:|---|
| 1 | 12:25 ごろ | LTX23 | 137.2 MB | 437.2 MB | Tier A の LTX23 15 点 |
| 2 | 14:06:51.535 | LTX25 | 133.5 MB | 433.5 MB | Tier A の LTX25 13 点 |
| 3 | **16:18:45.480**（現存） | **LTX23** | **143.4 MB** | **443.4 MB** | **Tier B 最小の 3 点** |

3 回目は Tier B 最小に入る前、土台モデルを LTX23 へ戻した直後（16:15:31）に 3 分・182 標本で
取り直したものである。**新しい床 443.4 MB は再現走の 3 点だけに適用され、既存の 28 点は
一切動いていない**（LTX23 の 15 点は再解析していないため。§7.1）。1 回目・2 回目の値は

**1 回目・2 回目の待機時の生データは復元できない**（§8.2 の B-9 はこれを指す）。

### 7.7 画角拡張の `peak_vram_reserved_mb` は物理 VRAM を超える

2.3 の画角拡張 4 点で 18,638〜20,146 MB を記録している（物理は 16,376 MB）。これは本体メモリへの

異常値ではないが、**専有ピーク（WDDM 実測）と混同してはならない**。
