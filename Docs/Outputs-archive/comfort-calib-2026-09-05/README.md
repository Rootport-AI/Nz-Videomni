## 1. 目的（なぜもう一度測るのか）

台帳 §1-27 でオーナーが決めた2件のうちの2番目です。

1. Edit画面（画角拡張＝アウトペインティング／撮り直し＝リテイク）に、
   設定画面の「生成高速化」を載せる。**これまで Edit 発の生成だけが、
   利用者の加速設定を無視してサーバー既定の構成で走っていました。**
2. **その結果として画角拡張の負荷が変わるので、快適上限のトークン予算を
   「加速を全部オンにした構成」で実測し直し、その値を線に採る。**

第2次（2026-09-04）が測った画角拡張の点は、**サーバー既定の構成**でした。
当時のフロントエンドが加速の値を1つも送っていなかったからで、それは
そのとき正しい選択でした。§1-27 でその配線が入る以上、線の前提そのものが
変わります。だから測り直します。

### 1.1 この線が誰に当たるのかについての留保（朝の判断 J1）

**画角拡張の快適上限は、エンジン系統だけで決まる固定の線です。**
構成が違えば別の線に切り替える、という仕組みは画角拡張にはありません
（Create／Chained のマーカーが持っているレガシー表へのフォールバックに
あたるものが無い）。したがって全オンの実測値を線に採ると、
**加速を切っている利用者には楽観側に出ます。**

オーナーの裁定は「全オン値を線に採用」で確定しているのでそのとおり進めますが、
この帰結は朝の判断 J1 で最終確認します。覆った場合の差し戻しは定数2値の
書き換えと再配置だけで済みます。

## 2. 加速の腕（6鍵になりました）

第2次の表は5鍵でした。**`keep_resident_embeddings`（LTX 2.5 の埋め込み処理器の
ジョブ間常駐・§3-114）が6鍵目として加わります。**

| **2.5 全オン** | `sage` | on | on | on | `default` | **on** |

両端がそれぞれ相手側では 422 になります。取り違えないための表です。

  2.3 にはそもそも埋め込み処理器という部品が無いので、`metadata.json` の
  `keep_resident_embeddings_used` は**常に `null`** です

### 2.1 「2.3 全オン」には正本がある／「2.5 全オン」には無い

- **2.3 全オンの正本は `config.py:322-336` の `ltx` 行の `requires`** です。
  Create／Chained の快適上限が「全オンの行」を持っており、その行の条件が
  そのまま上の表の2.3側になります。
- **2.5 全オンには正本がありません。** `config.py` の 2.5 の行は
  `requires={}`（無条件）で、「2.5 の全オンとは何か」を定義した場所が
  製品のどこにも無いからです。**上の表の2.5側は、このキャンペーンが
  「2.5 で合法にとれる最大の加速」として初めて定義したものです。**
  `RESULTS_comfort-calib-2026-09-05.md` と `Docs/VERIFICATION_LOG.md` §98 にも
