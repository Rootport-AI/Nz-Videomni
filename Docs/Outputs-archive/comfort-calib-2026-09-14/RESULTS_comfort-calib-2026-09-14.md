## 3. 逸脱と、採否の規則

### 3.1 逸脱（標準の手順から外れているところ）

**D-1 — 連結の基準点は「同じ解像度のより短い点」ではありません。**
連結の第2段階の窓は 22 潜在フレームに固定なので、解像度を変えずにトークン数だけ動かす
ことが原理的にできません。**腕の中の最小解像度の点（1280×768）を基準点にします。**
第1次（2026-08-31）の E3 と同じ扱いです。

**D-2 — 冷却150秒は、計画ファイルの境目では機械が保証しません。**
`cmd_run` の冷却は1つの計画ファイルの中の2点目以降にだけ効きます。今回は打ち切りのために
腕を2ファイルに割っているので、**その境目は人が手で150秒空けます。** 空け忘れは
共有メモリの持ち越しとして次の点に効くので、実際に空けたことを第5節に記録します。

**D-3 — 過去の実測値との比較は、条件が揃っていません。**
次の3点は「参考」であって、同じ表に並べて差を読む対象ではありません。

1. **連結の腕は、2026-08-31 が seed 1234、今回が seed 12345 です。**
2. **896×1152 には過去の実測点がありません**（この幾何は今回が初回です）。
3. **公式 Q4_K の対照（第5節の表3）は、今日・同じサーバープロセスで測ります。**
   これは 2026-08-31 の値の再測ではありません。あいだにコードの世代差があるので、
   **2026-08-31 の値との比較はあくまで参考です。**

### 3.2 採否の規則（境界をどう採るか）

| 記号 | 起きたこと | 採り方 |
|---|---|---|
| **R-A** | 腕の中で反転が観測された | **境界区間の下端（快適側の最大）を採る** |
| **R-B** | 上端まで一度も反転しなかった | **上端の値を線に採らない。**「上端以上・境界は未把握」と書く |
| **R-C** | 逆行した（下の点が退避し、上の点が快適） | 再走する。それでも残るなら**非単調と宣言し、線を提示しない** |
| **R-D** | 3つの解像度の結果が 2,040 トークン以内に近接した | **最小値を代表値として採り**、3つの実測値も併記する |
| **R-E** | 結果が現行の 44,880 と一致した | 「Q6_K でも成り立つ」と書く |

### 3.3 結論の書き方（3択）

結論は次の3つのいずれかになります。**どれになっても配信値は変更しません。**

1. **単調で、解像度ごとの値も近接した** → 「約 N トークン。現行 44,880 との差は M。反映は別途検討」
2. **解像度ごとに割れた** → 「単一の線では表せない。解像度ごとの値を記録する。反映は別途検討」
3. **上端まで反転しなかった** → 「上端以上。境界は未把握」

**配信値を変えない理由は、実装の事実そのものです。** 快適上限の表はエンジンの系統
（`ltx` / `ltx25`）でしか引けず、**同じ系統の中で transformer 別の行を持つ仕組みがありません**
（`config.py` の `_default_comfort_budgets()`）。**この事実自体を結論に書きます。**

## 7. 結論

**結論は「解像度ごとに割れた」です**（第3.3節の3択の2番目）。**Q6_K transformer の快適上限は、1本のトークン線では表せません。**

実測した3つの解像度の快適側の最大は **44,160**（1280×768）・**42,840**（1920×1088）・**40,320**（896×1152）で、いちばん上といちばん下の幅は **3,840トークン**あります。**採否規則 R-D（3つが2,040トークン以内に近接していれば最小値を代表値に採る）は成立しません。** 連結生成（第2段階の窓が22潜在コマ固定）の快適側の最大は **43,648**（1984×1024）です。**したがって、解像度ごとの快適側の最大を記録として残し、反映は別途検討とします。**

**確かめられたこと**:

- **4つの腕すべてで反転を観測しました（規則 R-A）。** 上端まで反転しなかった腕（R-B）はなく、**逆行（下の点が退避して上の点が快適になる）はどの腕にもありません（R-C に当たらない）。** 台地はすべて第2段階の窓だけで立ち、**復元の窓は全48点で一度も台地になっていません。**
- **現行の配信値 44,880 は、Q6_K では成り立ちません（規則 R-E の否定）。** 1920×1088 の単発生成と、連結生成の 1920×1088 は、どちらも 44,880 ちょうどで、**2回とも台地**でした。
- **台地が出るか出ないかは、GGUFの違いだけで決まります。** 同じ日・同じサーバープロセス・同じコードで公式Q4_Kに載せ替えると、同じ2点（45,120 と 44,880）がどちらも快適になりました（第6節 表3）。
- **「この系統の線は加速設定によらない」という現行の前提は、Q6_K でもおおむね保たれます。** 全onで測った3点のうち2点は既定構成と同じ側に落ち、境界のすぐ内側の1点（44,160）だけがしきい値の上で割れました（第6節 表4）。
- **896×1152 の腕には、確定できなかった点が1つ残っています。** 44,352 は2回で判定が割れたため境界に採らず、この腕の確定値は1段下ではなく**4段下の 40,320** になっています。**つまり 896×1152 の真の境界は [40,320, 45,360] のどこかで、区間はほかの2腕より広いままです。**

**参考（決定ではありません）**: それでも1本の線を引くとすれば、**安全側は 40,320**（896×1152 の確定値）です。**896×1152 の割れた点（44,352）を線の上と読むなら、3腕の最小は 42,840**（1920×1088 の確定値）になります。**どちらを採るかは、この記録では決めません。**

**配信値（`config.py` の `_default_comfort_budgets()`）は変更していません。** 理由は実装の事実そのものです——快適上限の表は**エンジン系統（`ltx`／`ltx25`）を鍵にした辞書**で、系統の中の行は加速設定（`requires`）でしか選べません（`config.py:311` の定義と `config.py:507-509` の設定項目）。**同じ系統の中で変換器ごとに別の行を持つ仕組みが、製品のどこにもありません。** 本節の数値は**製品が配る値ではなく、別のGGUFを選んだときに何が起きるかの実測**です。**反映するかどうか、するとすればどう配るかは、別途検討です。**
