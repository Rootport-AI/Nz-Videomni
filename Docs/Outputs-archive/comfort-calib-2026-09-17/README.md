## 1. 何を測るのか

**LTX 2.3 の変換器（transformer）を Sulphur-2 の Q6_K に替えたとき、快適上限が
致命的に下がるかどうかを実測で確かめます。**

- 対象の変換器: `Sulphur-2-base-distil-Q6_K`（主役）と `Sulphur-2-base-distil-Q4_K_M`（対照）。
  どちらも `models/LTX23/Weights/` に配置済みで、`GET /models` に `exists: true` で出ます。
- 構成は**全 on**（すべての加速を入れた構成）に固定します。内訳は
  `attention_backend=sage`・`block_swap_prefetch=true`・`keep_resident=true`・
  `fused_gguf_dequant_kernel=true`・`vae_mode=prune_vaed`・`keep_resident_embeddings=false` の6項目です。
  前の5項目は `config.py` の `_default_comfort_budgets()` にある `ltx`（LTX 2.3）の行の
  `requires` そのもので、配信している単発 44,880 トークンの線は**この構成でのみ**成り立つと
  宣言されています。6項目目の `keep_resident_embeddings` は `requires` には入っていません。
  LTX 2.3 はこの項目を `true` にすると 422 で拒むので（`services/engines/ltx/adapter.py` の
  `REJECT_TABLE`）、`false` が全 on における唯一の値です。
- 判定は**規則 v3**です。同じ解像度・同じ変換器の基準点と比べて、除去（stage-2）の窓でも
  復元（VAE）の窓でも、共有 GPU メモリの中央値が **+300 メガバイト**以上上がらなければ快適とみなします。
  速度の低下は記録しますが、線の決定には使いません。
- **スコープは「測って結論を出す」までです。** 配信値（`config.py` の `_default_comfort_budgets()`）は
  変更しません。フロントエンドやユーザーインターフェースへの反映方法も設計しません。

計測の一次記録は `RESULTS_comfort-calib-2026-09-17.md` です（結果表は `make_results.py` の機械生成）。

## 4. LTX 2.3 での判定の読み方（ここが第4次といちばん違います）

**境界は `runs/<ラベル>/run.json` の `v3prime.windows.stage2` と `v3prime.windows.restore` の
2 つの窓だけで決めます。**

LTX 2.3 の点には、この 2 つに加えて `s23_stage1`・`s23_gap_mid`・`s23_gap_tail` の
3 つの窓が必ず付きます（`calib.py` の 1800〜1814 行）。そして `verdict_v3prime` は
**5 つの窓の複合**で、どれか 1 つでも +300 メガバイトを超えれば `plateau` になります
（同 1879〜1887 行）。規則 v3 が見るのは除去と復元の 2 窓なので、
**`verdict_v3prime` と規則 v3 の判定は食い違うことがあります。**

- **線の決定に使う**: `v3prime.windows.stage2` と `v3prime.windows.restore` の `delta_mb`。
- **証拠として記録する（決定には使わない）**: `s23_stage1`・`s23_gap_mid`・`s23_gap_tail` の値と、
  複合の `verdict_v3prime`。一次記録では両方を並べて載せ、どちらで決めたかを明記します。
- コードは変えません。読み方の約束としてここに書きます。

### 専有ピークについての注意

**LTX 2.3 のワーカーは PHASE 行を出しません**（`logs/ltx_worker.log` に 0 件）。
そのため第4次の第10.3節にあった「除去の専有ピーク（torch が確保した量）」は、
LTX 2.3 では取れません。取れるのは次の 2 つです。

- **WDDM の専有ピーク**: グラフィックスカード全体の値で、およそ 1 秒に 1 回の採取です。
  デスクトップぶんの約 1,044 メビバイトを含みます。
- **`logs/server.log` の `Job … peak_vram=…MB`**: ジョブ全体のピークです。

どちらも「torch が確保した量」ではないので、**第10.3節の数値と直接比べてはいけません。**

## 5. この計測台を使うときに踏みやすい落とし穴

1. **`server start` に `--pid` を付けないでください。** オーナーのサーバーはすでに 18620 番で
   待ち受けているので、`server start` は「already listening」の経路に入り、
   `original_state.json` を控えるだけで何も起動しません。`--pid` を付けると `server.pid` が
   書かれ、万一 `server stop` を打ったときにオーナーのサーバーへ届いてしまいます。
   `server.pid` を書かなければ `server stop` は「止める相手が分からない」と言って何もしません。
   ちなみに 27300 は `run.ps1` のシェルではなく、待ち受けている python 自身です。
2. **`server stop` は絶対に打ちません。** `taskkill` はこの副命令の中にしかありません。
3. **`mkplan.py` を呼ぶたびに `--base-model LTX23` を明示してください。** 既定値は `LTX25` のままです。
   忘れると LTX 2.5 用の全 on 辞書（`vae_mode=default`・`keep_resident_embeddings=true`）が
   書かれ、実行時に 422 になります。
4. **Q4_K_M の点は必ず自前の基準点を持たせてください（`--baseline-first`）。**
   基準点の参照は `manifest.jsonl` 全体から `baseline_label` の最終レコードを拾う仕組みで、
   **変換器を照合しません。** Q4_K_M の点が Q6_K のラベルを参照すると、
   別の変換器の中央値と比べた無意味な判定が静かに出来上がります。
5. **切り替えのあとに `reanalyse` を打たないでください。** `idle-calib` は
   `calib/calibration.json` を 1 本上書きします（生の採取は変換器ごとの別フォルダに分かれますが、
   `calibration.json` は「いま有効な待機時の床」1 本きりです）。
   なお v3′ の判定は基準点の窓中央値だけを使うので、上書き自体は確定済みの判定に影響しません。
   影響が出るのは、上書き後にやり直したときだけです。
6. **各 Tier を始める前に `GET /status` の行列が空であることを確認してください**
   （`queue.pending` と `queue.running` がともに 0）。オーナーが生成を始めていたら待ちます。
7. **計画ファイルの境目には冷却が入りません。** `cmd_run` の冷却 150 秒は 1 つのファイルの中の
   2 点目以降にだけ効きます。次の `run` を打つ前に、手で 150 秒空けてください。
8. **`preflight` に `--online` は付けません。** `--online` が確かめるのは制御アダプタ 2 種の
   有無で、今回の計測はそれを使いません。
9. **`selftest/parser_selftest.py` の節 H はキャンペーンごとに書き直す節です。**
   今回は T11 で今回の計画ファイルへ向け直してあり、`parser_selftest.py` は
   **94 項目・失敗 0**（節 A〜G の 72 項目＋節 H の 22 項目）、
   `analyse_selftest.py` は **43 項目・失敗 0** で通ります。
   Tier C（Q4_K_M の対照）の計画ファイルを作ったら、その点を節 H に足してください。
   **対照点が宣言するのは `"default"` ではなく `Sulphur-2-base-distil-Q4_K_M` という登録名です**
   （第4次の節 H は公式重みを使っていたので `"default"` を期待していました。そのまま真似ると誤ります）。
10. **節 H を書き直すときは、期待値を新しい入力に合わせて直すのではなく、
    その入力で本当に成り立つことだけを書いてください。** 前者をやると、見張りが見張らなくなります
    （第4次 README の同じ趣旨の注意を引き継いでいます）。
11. **計測担当のエージェントが計画ファイルを作れない場合があります。** 今回のキャンペーンでは、
    担当の側で計画ファイルを作る命令が道具の許可判定に繰り返し拒まれ、Tier A の 10 点を終えたところで
    先へ進めなくなりました。**そのときは監督役が Tier A の点の雛形から計画ファイルを起こし、
    `calib.py run` まで直接実行してください**（今回はそうしました。較正台・点の設計・判定の規則は
    変えていません）。実行の記録は `run_<段>.log` に残し、`progress.md` に誰が走らせたかを書きます。
