## 4. 判定の読み方（LTX 2.3 の2窓）

### 4.1 規則 v3 — 2つの窓だけで決める

**快適とは、同じ幾何・同じ変換器の基準点と比べて、第2段階（仕上げのノイズ除去）の窓でも復元（VAE でのデコード）の窓でも、共有 GPU メモリ（VRAM に入り切らない分をシステムメモリへ逃がす領域）の中央値が +300 メガバイト以上は上がらないことです。** 規則の正本は `Docs\COMFORT_LIMIT_TABLE.md` 第4.2節です。速度低下と PCIe の転送量は記録しますが、線の決定には使いません。

境界は `runs\<ラベル>\run.json` の `v3prime.windows.stage2` と `v3prime.windows.restore` の2つの窓だけで決めています。

### 4.2 5窓の複合判定は証拠として併記する

**LTX 2.3 の点には、上の2つに加えて `s23_stage1`・`s23_gap_mid`・`s23_gap_tail` の3つの窓が必ず付きます。** そして較正台が書き出す `verdict_v3prime` は**5つの窓の複合**で、どれか1つでも +300 メガバイトを超えれば `plateau` になります。規則 v3 が見るのは2窓なので、**複合の判定と規則 v3 の判定は食い違うことがあります。**

**37点のうち実際に食い違ったのは1点だけです**（第6節 表1の 1280×768・385コマの1回目。第2段階の窓が +275.7 で規則 v3 では快適、補助の `s23_gap_mid` が +318.7 で複合は台地）。**表には両方を並べ、どちらで決めたかを明記します。**

**また、LTX 2.3 では復元の窓と `s23_gap_tail` は同じ区間です**（どちらも「第2段階の最後の行から `Video saved to` まで」）。したがって両者の値は常に一致します。

### 4.3 専有ピークについての注意

**LTX 2.3 のワーカーは PHASE 行を出しません。** そのため第4次の記録（`Docs\COMFORT_LIMIT_TABLE.md` 第10.3節）にあった「第2段階の除去の専有ピーク（torch が確保した量）」は、LTX 2.3 では取れません。**本書に載る専有の値は2種類とも別物です。**

- **WDDM の専有**: グラフィックスカード全体の値で、およそ1秒に1回の採取です。デスクトップぶんの約1,044メビバイトを含みます。
- **ジョブ全体のピークと予約ピーク**: `metadata.json` が報告する、そのジョブを通しての値です。

**どちらも「第2段階で torch が確保した量」ではないので、第10.3節の数値と直接比べてはいけません。**

## 7. 結論と留保

### 7.1 結論 — 線は動かなかった

**Sulphur-2 を Q6_K で載せても、LTX 2.3 の快適上限の線は動きません。** 根拠は3つです。

1. **線そのものの点（1920×1088・169コマ・44,880）が2回とも快適です**（表1）。
2. **線より上の段が、残る2つの幾何でも2回とも快適です**——1280×768 と 768×1280 の 45,120、1280×768 の 46,080（表1）。
3. **連結生成も、配信している線 40,000 の直上（40,832）と、さらに上の 44,880 の両方で快適です**（表2）。

**したがって、`Docs\COMFORT_LIMIT_TABLE.md` 第1.1節の `ltx` の行（単発 44,880・連結 40,000）は、この GGUF でもそのまま成り立ちます。配信値は変更していません。反映は別途検討です。**

### 7.2 留保1 — Q6_K に固有の孤立した台地がある（この結論の唯一の穴）

**44,160 トークンという1点だけ、上の段が快適なのに台地になります**（表4）。2つの幾何で2回ずつ再現し、同じ点は同じプロセスの Q4_K_M では4回とも快適です。**つまり Q6_K の挙動はトークン数に対して単調ではなく、「線より内側なら Q6_K でも常に快適」とは言えません。**

**この台地は速度を伴いません**（表4）。したがって利用者に見える形での被害が出るかどうかは、この計測からは言えません。**判定の物差しは共有メモリの中央値だけで、そこから先に何が起きるかは規則 v3 の守備範囲の外です**（`Docs\COMFORT_LIMIT_TABLE.md` 第4.2節が速度と PCIe を線から外した理由と同じ構図です）。

### 7.3 留保2 — 線は Q4_K_M にとっても余裕が薄い

**線の点そのもの（44,880）は、Q4_K_M で規則 v3・全 on で測ると2回で割れました**（表3）。`Docs\COMFORT_LIMIT_TABLE.md` 第4.3節のアンカー M2 がこの点を快適としているのは旧規則 v2 での判定です。**線が Q6_K で動かないことと、線そのものに余裕があることは別の話です。**

### 7.4 留保3 — 測っていないこと

第1.4節に挙げたとおりです。要点だけ繰り返すと、**第2段階の除去について torch が確保した量は LTX 2.3 では取れず**（本書に載る専有の値は WDDM のカード全体の値とジョブ全体の値です。第4.3節）、**1280×768 の上端は 385コマの割れで、768×1280 の上端は 377コマの1回で止めてあり**、**連結生成は2点の判定で境界ではなく**、**別の量子化や別の派生モデルは測っていません。**

**手順の側にも1つ穴があります**——計画ファイルの境目3つで冷却150秒を置いていません（第2.6節）。該当する3点の結果は持ち越しで説明の付く向きになっていませんが、**置いていないこと自体は事実です。**

### 7.5 配信値を変えなかった理由

**線が動かなかったので、変える材料がありません。** 加えて、仮に動いていたとしても変えられない事情があります——快適上限の表は**エンジン系統（`ltx`／`ltx25`）を鍵にした辞書**で、系統の中の行は加速設定（`requires`）でしか選べず、**同じ系統の中で変換器ごとに別の行を持つ仕組みが製品のどこにもありません**（`config.py` の `_default_comfort_budgets()` と `comfort_budgets`）。この事情の説明の正本は `Docs\COMFORT_LIMIT_TABLE.md` 第10.4節の1項目目です。
