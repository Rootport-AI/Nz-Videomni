## 1. 何を測るのか

**連結生成（Chained）の第 2 段（Stage-2）の窓を 22 潜在フレームから w46・w61 に広げても、
快適上限の線（1 タイルあたりのトークン数）が成り立つかを確かめます。** 窓を広げたのは
`Docs/PENDING_TASKS.md` §3-165 の改修で、記録の正本は `Docs/VERIFICATION_LOG.md` §116 です。

- 線は、LTX 2.3 の全 on が 40,000、LTX 2.5 が 44,880 です（`Docs/COMFORT_LIMIT_TABLE.md` 第1.1節）。
- 対象の変換器（transformer）は、LTX 2.3 が `Sulphur-2-base-distil-Q6_K`（主役）と
  `Sulphur-2-base-distil-Q4_K_M`（計画外の対照）、LTX 2.5 が公式の `default` です。
  LTX 2.5 の REDGraft Q6_K は、線そのものが割れていることが分かっているので使いません
  （`Docs/COMFORT_LIMIT_TABLE.md` 第10節）。
- 構成は**全 on**（すべての加速を入れた構成）に固定します。LTX 2.3 は
  `attention_backend=sage`・`block_swap_prefetch=true`・`keep_resident=true`・
  `fused_gguf_dequant_kernel=true`・`vae_mode=prune_vaed`・`keep_resident_embeddings=false`、
  LTX 2.5 は `vae_mode` を既定のままにし、`keep_resident_embeddings=true` にします
  （定義の正本は `Docs/COMFORT_LIMIT_TABLE.md` 末尾の付記の1項目目）。
- 全点に共通の形: クリップ 361 フレーム×2 本（つなぐと 705 フレーム・潜在 89）・T2V・
  `chunked_upsample: false`・シード 12345・24 fps・指示文は較正台の既定（車のプロンプト）。
  タイルの枚数は、窓 22 で 5 枚、w46 で 3 枚、w61 で 2 枚です。
- 判定は**規則 v3**です。同じ解像度・同じ変換器・窓 22 の基準点と比べて、Stage-2 の窓でも
  復元（VAE でのデコード）の窓でも、共有 GPU メモリの中央値が **+300 メガバイト**以上上がらなければ快適とみなします。
  内側の点は 2 回走らせ、2 回とも退避なら線が破れたとみなし、割れたら保留します。
  線の外側の点は 1 回だけ走らせ、記録にとどめます。
- **スコープは「測って結論を出す」までです。** 配信値（`config.py` の `_default_comfort_budgets()`）は
  変更しません。

計測の一次記録は `RESULTS.md` です（結果表は `make_results.py` の機械生成）。

### 実行の順番と、変換器の切り替え（2 回）

**T1 → T1x → T3a → 切り替え 1 → T1q → 切り替え 2 → T2 → T3b → 2 段階の復元**の順です。

1. 切り替え 1: `load --base-model LTX23 --transformer Sulphur-2-base-distil-Q4_K_M` のあと `idle-calib`（3 分）。

   まず `restore-state --base-model LTX25`（REDGraft Q6_K へ）、次に引数なしの `restore-state`
   （LTX 2.3 の Sulphur-2 Q6_K へ）の 2 段で戻しました。記録と `state.json` の突き合わせは
   `restore_state_output.txt` にあります。

## 4. 判定の読み方

**境界は `runs/<ラベル>/run.json` の `v3prime.windows.stage2` と `v3prime.windows.restore` の
2 つの窓だけで決めます。**

- **LTX 2.3 の点**には、この 2 つに加えて `s23_stage1`・`s23_gap_mid`・`s23_gap_tail` の 3 つの窓が付きます。
  `verdict_v3prime` は**5 つの窓の複合**で、どれか 1 つでも +300 メガバイトを超えれば `plateau` になります。
  規則 v3 の判定と食い違うことがあるので、一次記録では両方を並べ、どちらで決めたかを書きます。
  LTX 2.3 では復元の窓と `s23_gap_tail` は同じ区間で、値は常に一致します。
- **LTX 2.5 の点**には、`stage2`・`restore`・`p25_30_decode_encode` の 3 つの窓が付きます。
- **LTX 2.3 のワーカーは PHASE 行を出しません。** 専有の値は WDDM のカード全体の値（約 1 秒に 1 回の採取）と、
  ジョブ全体のピークだけです。`Docs/COMFORT_LIMIT_TABLE.md` 第10.3節の「torch が確保した量」と直接比べてはいけません。
- **Stage-2 の速さは `sec/token` 列では比べません。** この列は Stage-2 の秒数を 1 タイルぶんのトークン数で割った値で、
  窓が違うとタイルの枚数も違うので、窓の違う点どうしでは意味が揃いません。
  比べるときは、同じ解像度の基準点の `stage2.seconds` と並べます。

## 5. この計測台を使うときに踏みやすい落とし穴

1. **`original_state.json` を前のキャンペーンから持ち込まないでください。** あると `server start` が控えを取り直さず、
   終了時の復元が前のキャンペーンの選択へ戻ります（第2節）。
2. **`server start --pid` は、較正のために自分で起動したサーバーにだけ付けます。** オーナーが起動したサーバーに付けると、
   万一 `server stop` を打ったときにオーナーのサーバーへ届きます。今回は監督役が起動したサーバーなので 8800 を登録しました。
3. **`server stop` は打ちません。** サーバーを止めるかどうかは監督役が決めます。
4. **`mkplan.py` を呼ぶたびに `--base-model` を明示してください**（LTX 2.3 の点は `LTX23`、LTX 2.5 の点は `LTX25`）。
   既定値は `LTX25` のままです。LTX 2.3 の点で忘れると LTX 2.5 用の全 on の辞書が書かれ、実行時に 422 になります。
5. **窓だけを変える点には `--label` を付けてください**（T14）。付けないとラベルが `<接頭辞>_<幅x高さ>` になり、
   同じ解像度の基準点と名前がぶつかります（`mkplan.py` は同じラベルの 2 度目を拒みます）。
6. **変換器を替えた点には、必ず自前の基準点を持たせてください。** 基準点の参照は `manifest.jsonl` 全体から
   `baseline_label` の最後のレコードを拾う仕組みで、**変換器を照合しません。** Q4_K_M の点が Q6_K の基準点を参照すると、
   別の変換器の中央値と比べた無意味な判定が静かに出来上がります（今回は `a4_b1216` を別に取りました）。
7. **切り替えのあとに `reanalyse` を打たないでください。** `idle-calib` は `calib/calibration.json` を 1 本上書きします。
   v3′ の判定は基準点の窓中央値だけを使うので、上書き自体は確定済みの判定に影響しません。
8. **`idle-calib` はモデルを読み込んでから取ってください。** 今回の最初の 1 回（LTX 2.3 Q6_K）は読み込み前に取ってしまい、
   `pipeline_loaded=False` の警告が出ています。判定は基準点との差だけで行うので結果には響きませんが、待機時の床としては低めに出ます。
9. **各計画ファイルを始める前に `GET /status` の行列が空であることを確認してください**
   （`queue.pending` と `queue.running` がともに 0）。
10. **計画ファイルの境目には冷却が入りません。** `cmd_run` の冷却 150 秒は 1 つのファイルの中の 2 点目以降にだけ効きます。
    次の `run` を打つ前に、手で 150 秒空けてください（今回は `sleep 150`）。
11. **`preflight.json` は最後に走らせた `preflight` の結果で上書きされます。** 計画外の T1x・T1q は 00:54 に机上検算を通しましたが、
    `preflight_output.txt` に残っているのは着手前の 4 計画・15 点の記録だけです（T1x・T1q の検算は `progress.md` に記録）。
12. **`preflight` に `--online` は付けません。** `--online` が確かめるのは制御アダプタ 2 種の有無で、今回の計測はそれを使いません。
13. **`selftest/parser_selftest.py` の節 H はキャンペーンごとに書き直す節です。** 今回は T13 で計画の 4 本（15 ラン）へ向け直してあり、
    `parser_selftest.py` は **156 項目・失敗 0**（節 A〜G の 72 項目＋節 H の 84 項目）、
    `analyse_selftest.py` は **43 項目・失敗 0** で通ります。計画外の T1x・T1q の点は節 H に入っていません。
14. **節 H を書き直すときは、期待値を新しい入力に合わせて直すのではなく、その入力で本当に成り立つことだけを書いてください。**
    前者をやると、見張りが見張らなくなります。
15. **計測担当のエージェントが計画ファイルを作れない場合があります**（第5次で、計画ファイルを作る命令が道具の許可判定に
    繰り返し拒まれました）。そのときは監督役が計画ファイルを起こし、`calib.py run` まで直接実行してください。
    実行の記録は `run_<段>_output.txt` に残し、`progress.md` に誰が走らせたかを書きます。
16. **出力をファイルへ流すときは、標準出力の文字コードを UTF-8 に指定してください**（`PYTHONIOENCODING=utf-8`）。
    既定の cp932 では、全角の文字のところで異常終了します。
