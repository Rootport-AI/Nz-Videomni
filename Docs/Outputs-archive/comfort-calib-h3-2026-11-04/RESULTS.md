## 用語（初出の略語の説明）

- **FL2VA**: 先頭・末尾のキーフレームを受け付ける H3 の重み（`minimax_h3_fl2va_pruned_int8_convrot`。計画ファイルの名前は `default`）。**Ref2VA**: 参照素材（画像・動画・音声）を受け付ける重み（`minimax_h3_ref2va_pruned_int8_convrot`）。2 つはブロックの形が同じ（11-03 の考察 §0.1）。
- **K**: キーフレームの枚数。FL2VA の腕は K=1、Ref2VA の腕は K=0。
- **DiT**: ノイズ除去の本体のネットワーク。入る行の並びは `[text | cond | ref_video | ref_audio | audio | video]`。
- **text**: プロンプトと、キーフレーム・参照をテキストエンコーダーが文章の列に埋め込んだ行。**cond**: キーフレームの条件行。**ref**（R）: 参照の行（ref_video＋ref_audio）。**video**（Nv）: 生成する映像の行。
- **S**: DiT に入る行の総数。**vc**: 映像＋条件行。**vcr**: 映像＋条件行＋参照の行。**eff**: S＋0.40×text（計画 §4 で結果を見る前に決めた予測の軸）。
- **c**: 快適の上端（梯子の段で、2 回快適）。**U**: c の 1 段上（梯子は 17 フレーム刻み）。表の「c／U」はこの意味。
- **OOM**: GPU のメモリ不足。**cap**（上限）: VRAM 16GB mode がノイズ除去の段だけに掛ける割り当て器の上限（MiB）。
- **割り当て**（allocated）: PyTorch が張量として使っている GPU メモリ。**予約**（reserved）: PyTorch が GPU から確保して手元に持っている量。**予約済みの空き**: 予約−割り当て（断片化の目安）。**セグメント**: 割り当て器が GPU から一度に確保する連続した領域。
- **1 本**: [S, 5376] の bf16（16 ビットの浮動小数点）の張量 1 本＝S×10,752 バイト（11-03 の考察の「U」と同じ量。本書では c／U の U と紛れないよう「1 本」と書く）。
- **TE**: テキストエンコーダー（Qwen3-VL）。**Δ**: 窓（工程の区間）の共有メモリの中央値 − 基準点の同じ窓の中央値（MB）。+300MB 以上で「退避」。
- **retries**（`num_alloc_retries`）: 割り当て器が上限に当たって手元の空きセグメントを GPU へ返し、確保をやり直した回数。**inactive_split**: 分割されたセグメントの中の使っていない部分の山（MiB）。
- **sage**: attention（注意機構）の計算方式 SageAttention（製品の既定。オーナー裁定）。

- 【コード】`engine_h3/lowvram.py:143` は `o = torch.empty((s, inner), dtype=torch.bfloat16, device=x.device)` で、`inner = heads × head_dim`（同 142 行）＝56×128＝7,168（ヘッド 56 は `engine_h3/constants.py:53`、`engine_h3/dit.py:244-253` の `H3Attention` に「inner＝7168 は hidden 5376 より大きい」と注記あり）。**注意の全ヘッドの出力を受ける [S, 7,168] の bf16（1.333 本）**で、ヘッド群のループ（同 152-166 行）が群ごとに `o[:, h0*d:h1*d]` へ書き、168 行の `out_proj` に渡す。
- 【実測】s＝223,604 なら 223,604×7,168×2＝3,205,627,904 バイト＝2.985GiB（2MiB への切り上げで 2.99GiB）。**s＝223,604 は S の実測と一致し、inner＝7,168 で文言の 2.99GiB になる。**
- 【コード】`dit.py:653` は `H3DiT.forward` の `for block in self.blocks: x = block(x, t_emb, adaln_index, rope_cos, rope_sin)` で、VRAM 16GB mode では `block_forward`（`lowvram.py:115`）へ渡る。
- 【コード】修正（記録簿 §195.3・設計正本 §6.5 の #9）で消したのは、ステップの境目で映像の行だけが持つ [Nv, 5376] の float32 の 2 本（埋め込みの映像の射影 `dit.py:551` と最終層の `buf`。各 2 本分）が作る 3,432MiB 級のセグメントの穴と、TE の段から返らないセグメントだった。いま埋め込みは受け皿へ直接書き（`lowvram.embed_rows_packed`）、その float32 の跡は埋め込みの直後の `empty_cache`（`pipeline_h3.py:1575`）で返る。
- 【推測】修正の後は、ステップの中で最も大きい確保がこの `o`（1.333 本）になった。ブロックの中のほかの確保（`n1`・`h`・`x2`・`n2`・`h2`・`m`・戻り値）はどれも 1 本で、1 本の穴に `o` は入らない。定常のブロックでは前のブロックの `o` の跡に入るが、ステップの境目の 2 回の `empty_cache` で丸ごと空いたセグメントが返されたあとは、`o` のための新しいセグメントが要る。そのとき手元に返せない空き（§6.2）が多いと上限を超える。修正前の s1080_362 は 178 行の `h2`（1 本・2.24GiB）でステップ 0 に落ちていた（11-03 の考察 §3.2(a)）ので、**落ちる確保が「境目の float32 の穴に入らない 1 本」から「ブロックの中で最大の 1.333 本」に移った**と読める。ステップ 0 が通りステップ 1 で落ちた理由（ステップ 1 の頭に何が返せずに残っていたか）は、確保の履歴を取っていないので決められない。記録簿 §195.5 の 8 の「境目に残る丸ごと空いたセグメント 4 つ・計 282MiB」は量が小さく、3.84GiB の空きの説明にはならない（その 4 つは再試行で返るはず。推測）。

### 6.5 num_alloc_retries の意味

- 【実測】retries は、基準点・煙の点で 0、s1080_277・s720_481 で 4、上限の近くの完走点（s1080_328・s1080_345・s1440_192・r1080_362）で 9（20 ステップの s1080_345_20 で 41）、参照つき 3 点で 8。修正前の完走点は 2〜3（11-01 の s1080_260・s1440_141・s720_481、11-03 の r1080_260・i1080_226_p9）。記録簿 §195.4 の修正後の r1080_277 は 4（各ステップ 1 回）。
- 【推測】（PyTorch の割り当て器の一般的な仕様。ソースは読んでいない）新しいセグメントが上限（`set_per_process_memory_fraction`）か GPU の空きを超えるとき、割り当て器は手元の丸ごと空いたセグメントをすべて GPU へ返してからやり直し、そのたびに `num_alloc_retries` を 1 増やす。やり直しで入れば OOM にはならない。今夜の 8〜9 回は「4 ステップの間に 2 回程度ずつ、上限に当たって手元の空きを返した」ことを意味し（20 ステップの s1080_345_20 は 41 回。§8）、**OOM の回数 `num_ooms` は全点 0、退避も 0**。上限の近くで動いている印であって、失敗や退避の印ではない（設計正本 §6.5「降ろす規則」の注記と同じ読み）。
- 【実測】やり直しの時間の代償は見えない。retries 8〜9 の点の 1 ステップ秒は時間モデルより +0.0〜+0.5%、retries 0〜4 の点は −0.4〜+0.5%（§6.7）で、違いは見えない。
