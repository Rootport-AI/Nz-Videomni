# TE（テキストエンコーダー）段の VRAM 溢れの調査報告（2026-11-04・読むだけの調査）

- 調査の対象: 再較正（本フォルダ RESULTS.md）の i1080_243_p9（1920×1088×243・Ref2VA・参照画像 9 枚・text 行 18,462）で観測された TE 段の VRAM 溢れ（WDDM の退避）。専用メモリ中央値 15,969MB、共有メモリが常時の約 1.2GB からさらに +1,165MB、PCIe 受信の 90 パーセンタイル 4,357MB/s、TE 段 150.9 秒（11-03 の i1080_226_p9 は 124.0 秒・共有 +81MB・TE 段の予約 15,248MiB。今回は 16,074MiB）。
- 方法: 製品コード（engine_h3）・記録簿 §181〜182・§194・§195・run.json を読むだけ。GPU・サーバー・編集なし。
- 事実（file:line か run.json の値を添える）と推測（「推測」と明記）を分けて書く。

## 結論

- **山の正体は、TE（Qwen3-VL-32B を 50 層で切り、int8 ConvRot で量子化した重み）の注意の一時領域。** 注意は「問い合わせを 512 行ずつに分け、math カーネル（スコア表を実際に作る素朴な実装）で fp32 で計算する」方式。重みは 1 層（約 465MiB）ずつしか GPU に載らない。TE 段の GPU には TE 以外の常駐がない（DiT〔ノイズ除去の本体〕、VAE〔映像の符号化と復号の部品〕、ブロック入れ替えの受け皿は、どれもこの時点で載っていない）。
- **割り当ての山は系列長 N（text の行）にほぼ比例する。** 式は「約 491MiB＋0.4966MiB×N」で、別の日・別の台本の点まで数 MiB の差で合う。**溢れを決めているのは予約の山。予約と割り当ての差（断片化）は、最後の塊が 512 行より高くなる N（端数の併合が起きる N）で大きく跳ねる。** i1080_243_p9 は N＝18,462＝512×36＋30 なので、最後の塊が 542 行に併合される（推測。根拠は記録簿 §182.7 の記述と run.json の並び）。
- **11-03 から 11-04 で予約が 826MiB 増えた理由は、記録からは決められない（TE 段のメモリ確保の履歴がない）。** 割り当ての山は 9,976 と 9,978MiB でほぼ同じなので、違いは置き方（断片化）だけ。溢れの量（共有メモリ +1,165MB）は「予約の増加 826MiB＋待機時の専用メモリの増加 約 209MB」とほぼ釣り合う（推測）。
- **VRAM 16GB mode の上限（cap）が TE 段に掛からないことに、設計上の理由は書かれていない。** 設計正本は上限を「ノイズ除去の頭で課す」とだけ書く（§6.5 の #1）。TE の対策（裁定 83）が 16GB に収まると確かめたのは N≦16,314 までで、N＝18,462 はその範囲の外。
- **影響は小さく局所的。** i1080_243_p9 で TE が約 27〜28 秒遅れ、ジョブ全体 1,324 秒の約 2%。参照画像 2 枚・動画の参照・音声・参照なしでは溢れていない。

## ① TE 段の山の正体（事実）

- **重み**
  - TE は Qwen3-VL-32B（テキスト 50 層、隠れ次元 5120、問い合わせ 64 頭、鍵と値 8 頭、MLP 25600）（`engine_h3/text_encoder.py:81-118`）。
  - ファイルは `qwen3vl_32b_minimax_h3_int8_convrot.safetensors` の 1 種だけ（run.json の `metadata.models_selection.text_encoder`、`models/MiniMaxH3/TextEncoder/`）。TE の精度を選ぶ手段はない。
  - 読み込む量は、視覚の塔なしで 24.17GiB、ありで 25.28GiB（metadata の `te_read.read_gib`。b1080r と i1080_243_p9）。
  - `load()` は meta（重みを持たない骨格）を作るだけ。`encode` のときに、各デコーダー層をフックで直前に GPU へ読み、直後に meta へ戻す（`text_encoder.py:530-552`・`796-810`。`sft_load.py:153-189`。CPU を経由する同期の `tensor.to(device)` で、先読みはない）。
  - 1 層の量は (24.17−1.45)/50 ≈ 0.45GiB（計算）。下の式の固定分 491MiB とほぼ同じ。
- **視覚の塔は TE の一部**（同じファイルの `visual.*`。BF16 で 1.11GiB。`text_encoder.py:124-142`）。
  - 画像はすべて 1 回の呼び出しで処理器に通す（`text_encoder.py:665-682`・`701-714`）。
  - 視覚トークンは 1 枚あたり「参照の大きさ÷1024」。参照の大きさは生成の面積に合わせ、元画像より大きくはしない（`reference.py:77-83` の `match_size`）。1920×1088 では 1 枚 2,040（run.json の `te_read_references`）。
  - 視覚の塔の注意は SDPA のままで、画像ごとに `torch.split` で分けて計算する（`text_encoder.py:249-252`、transformers の `modeling_qwen3_vl.py:245-247`）。
- **埋め込み表と視覚の塔の早期解放（J）**: それぞれの forward の直後に meta へ戻す（`text_encoder.py:555-566`・`807`）。
- **注意（G）**
  - `blocked_causal_attention` が、問い合わせ 512 行ずつ、全長の鍵と値に対して計算する。`sdpa_kernel([MATH])` で math に固定し、`enable_gqa=True`（GQA。問い合わせ 64 頭が鍵と値 8 頭を共有する形）で呼ぶ（`text_encoder.py:158-211`）。
  - 64 行未満の端数は前の塊へ併合するので、最後の塊は 64〜575 行になる（同 `:167`・`:188`）。
  - スコア表は fp32 で実体化される（`text_encoder.py:249-250` のコメント、記録簿 §181.1）。N×N は作らないが、塊ごとに「64 頭×(512〜575)×N」の fp32 を作る。
  - 大きさの計算（推測。fp32 を前提にした概算）: N＝18,462 で 512 行の塊のスコア表は 1 本約 2,308MiB。softmax の出力も同じ大きさ。
- **DeepStack（視覚の特徴を浅い層に足し込む仕組み）**: transformers の forward は `deepstack_visual_embeds`（3 本×視覚トークン数×5120 の bf16）を 50 層のループの終わりまで持ち続ける（`modeling_qwen3_vl.py:833-840`・`1188-1251`）。18,360 トークンで約 538MiB（計算）。
- **同じ時点の他の常駐: なし（コードから確定）**
  - DiT は TE の後で組む（`pipeline_h3.py:783-833`）。映像の符号化器も TE の後（同 `:791-813`）。
  - `keep_resident`（モデルの保持）は全部 CPU に置く（同 `:632-634`・`1378-1390`）。
  - ブロック入れ替えの GPU の受け皿は `_denoise` の `finally` で外す（同 `:1626-1636`）。
  - cuBLAS（行列積のライブラリ）の作業領域は `load()` で 20MiB の自分用セグメントに置く（同 `:356-365`・`:675`）。
  - 実測の裏づけ: 小さな N の TE 段の予約は 1,514MiB（11-04 の b1080r ほか）で、埋め込み表 1,484MiB＋cuBLAS の 20MiB にあたる。
- **山の場所**: 割り当ての山はデコーダー側。根拠は、下の式が N≧9,258 の全点で数 MiB まで合うこと（推測）。デコーダーに入る前の山は run.json に段として記録されていない（記録なし）。

## ③ 予約が 15,248→16,074MiB に増えた理由の切り分け

- **事実**
  - 割り当ての山は同じ（9,976／9,978）。N・最後の塊・視覚トークン（2,040×9）も同じ。
  - 11-03 では cuBLAS の作業領域が古いジョブの 1,484MiB のセグメントを固定し、TE 段の開始時に残っていた。そのため小さな N の予約は 2,978（1,484 の残り＋今回の 1,494）だった。11-04 では 1,514（記録簿 §194.11、§195.4 の 4c で 1,971→1,493）。
  - TE の戻り値を CPU へ移す変更（`pipeline_h3.py:935`）は forward が返った後なので、TE の山には効かない（コードから確定）。
  - 待機時の専用メモリは 11-03 が 933.7MB、11-04 が 1,142.3MB（RESULTS.md:230、progress.md:17）。
- **溢れの量の釣り合い（推測）**: encode の窓の「専用の中央値＋共有 Δ」は 11-03 が 16,093MB、11-04 が 17,135MB で差は 1,042MB。予約の増加 866MB（826MiB）と待機時の増加 209MB の和は 1,075MB。溢れの量は予約の増加と同居の増加でほぼ説明できる。
- **予約が増えた原因そのもの: 記録なし。** TE 段のメモリ確保の履歴を取っていない。encode の `num_alloc_retries` も記録していない。候補（推測）: cuBLAS の作業領域の移動で、11-03 にあった「再利用できる 1.48GB の空き」がなくなり置き方が変わった。ただしこれだけでは +826MiB の向きを説明できない（11-03 はその 1,484 を予約に含んでいる）。確かめるには TE 段だけを確保の履歴つきで 1 本流す必要がある。

## ④ 既にある仕組みの棚卸し

1. 重みの直接読み（1 層ずつ。CFG〔条件あり・なしの 2 回の計算〕なしの 1 回の forward）: `text_encoder.py:28-42`・`530-552`。
2. 埋め込み表と視覚の塔の早期解放（J）: `:555-566`・`:807`（裁定 83）。
3. 塊の注意（G）。512 行・math 固定・端数の併合は 64 行未満: `:158-211`（裁定 83。F0〔cuDNN の注意〕は数値が変わるので不採用。設定項目にしない）。
4. 視覚の塔は画像ごとの SDPA（分けて計算し、画像の枚数に比例）: `:249-252`。
5. TE の後片付け: `finally` で全層を meta へ、`release()`、`_free_cuda()`（`text_encoder.py:826-838`・`861-869`、`pipeline_h3.py:938-941`）。戻り値は CPU へ（`:935`。§195 の (4)）。
6. cuBLAS の作業領域の先取り: `pipeline_h3.py:356-365`・`675`（§195 の (3)）。
7. TE 段に他の常駐はない（①の最後の点）。したがって「TE の前に常駐を下ろす処理」は不要で、存在しない。
8. **TE を参照ごと・塊ごとに分けて符号化する仕組みはない**（1 回の forward。`text_encoder.py:820-821`）。**TE のブロックのオフロードは、この直接読みがそれにあたる**（1 層ずつで先読みはない）。精度と量子化の選択肢はなし（int8 ConvRot の 1 ファイル）。
9. **上限（cap）はノイズ除去の段だけ**: `_vram16_begin`／`_vram16_finish`（`pipeline_h3.py:1331-1376`・`1486`・`1628`）、式は `lowvram.py:96-105`。設計正本 §6.5 の #1 は「ノイズ除去の頭で…課し、終わりに外す」。TE に掛けない理由は書かれていない。記録簿 §194.8 は「コードどおり」と観察を書いているだけ。裁定 47 は「黙って退避を許す経路は作らない」で、TE の溢れは事実上この経路にあたる（裁定 47 は VRAM 16GB mode の OOM〔GPU メモリ不足〕についての裁定）。裁定 83 の合格条件は「画像 9 枚（N≈9,300）・動画 15 秒（N≈16,300）」（§181.2）。1080p の画像 9 枚（N＝18,462）は確かめた範囲の外。
10. 先読みの降格（同期の経路への黙った切り替え）は DiT のブロック入れ替えだけの仕組み。TE には先読みがないので関係しない。
11. 台帳 §1-118（UI/UX の方針）: 「マーカーは参照なしの条件で出し、参照が重い場合は Reference アコーディオン側に注意・警告を出す」と決まっている。「行数の上限や自動の縮小は足さない」。

## ⑤ 回避の候補（決定はしない）

- **(a) 参照を 1 枚ずつ TE に通して結合する**: 意味が変わる。注意は全系列にわたる因果の注意で、後ろの札・画像・プロンプトが前の画像を見る（`text_encoder.py:190`）。M-RoPE（3 軸の位置の回転埋め込み）の位置も全系列で通し番号。不採用相当。似た形の「KV キャッシュで塊ごとに前へ進める（チャンク化した前処理）」は数学的には同じだが、層ごとに直接読む方式と相性が悪く、重み 25GB を塊の数だけ読み直すことになる（推測）。
- **(b) TE 段にも上限を掛ける**（`_encode` を `derive_memory_cap` で包む）: 上限に当たると割り当て器は手元の空きセグメントを返してから再試行する（RESULTS.md:225 の読み）。割り当ての山 9,978 は上限約 14,000 より十分小さいので、OOM ではなく「再試行で退避を避ける」形になる見込みが高い（推測。§181.6 の上限つきの T3 は予約が上限の下だったので上限が効いていない）。欠点: 再試行のたびに同期が入り、速さは不明。割り当てが本当に上限を超える N（約 2.7 万以上。推測）では OOM で失敗する。VRAM 16GB mode が off なら掛からない。置き場所は `pipeline_h3.py:900-949`。Chained もここを通る（`chain_h3.py:271`）。
- **(c) TE の前に常駐を下ろす**: 下ろすものがない。効果はない。同居プロセス（待機時 約 1.1GB）はエンジンからは減らせない。
- **(d) 注意の実装を切り替える**: F0 または F1（F1 は鍵と値を複製して memory-efficient の注意に通す方式）は N＝16,314 で割り当て／予約が 4,789／7,678、時間は約 18 秒（G は 8,592／10,384、約 93 秒）。数値は sage〔SageAttention〕と同じ等級で変わる（§181.5〜181.6）。**裁定 83 で不採用**なのでオーナーの再裁定が要る。math の bf16 の削減を許す設定（PyTorch の `allow_fp16_bf16_reduction_math_sdp`）も数値が変わる（推測。測っていない）。
- **(d′) 塊を 256 行にする（定数 1 つ）**: T4／T4b の実測では高さ 64〜575 はすべて今の方式とビット一致（§182.6）。ただし測った N は 3,123・4,100・6,148 だけ。スコア表は約半分になる。N＝3,130 で山 1,248→793MB、時間 57→63 ミリ秒（§181.4）。N＝18,462 では約 2.3GB 減と見込む（推測）。
- **(f) 塊を等分にする**（`ceil(N/512)` 等分。VRAM16_ROW_CHUNK の「等分」と同じ発想。`constants.py:58-59`）: 最後だけ高い塊がなくなるので、②の「併合による予約の跳ね」の源を消せる見込み（推測）。高さはビット一致を実測した 64〜575 の範囲に入る。
- **(g) 数値を変えずに断片化を減らす候補**（どれも推測で未測定）: J で下ろした直後（層 0 の前）か層の境目で `empty_cache` を呼ぶ。DeepStack の 3 本（約 538MiB）を層 2 の後で手放す（forward は transformers のままなので、フックで行う必要がある）。
- **(e) 回避せず、注意・警告で知らせる**（§1-118 の方針に合う）: 割り当ては N の 1 本の線で書ける。予約は併合（N mod 512）で跳ねるので、きれいな 1 本の線にならない。実測で言えることは「N≦16,314 は安全、18,462 は際」まで。N の数え方: 画像 1 枚 ≈ 生成の面積÷1024（元画像の面積が上限）。動画は 1 組 1,008 以下で、15 秒で約 15,100。1080p では画像 8 枚以上で N が 16,300 を超える。1440p では約 5 枚で超える（計算。推測）。
