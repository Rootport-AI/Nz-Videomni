言葉: **S** ＝ DiT（映像と音声を生成する本体のネットワーク）に入る総行数。**cap** ＝ VRAM 16GB mode の割り当ての上限（約 14,000MiB）。**c** ＝ 快適の上端の点。**U** ＝ c の 1 段上で快適でなかった点。**予約の山** ＝ PyTorch が GPU から確保した領域（reserved）の最大。**割り当ての山** ＝ そのうち実際に使っていた量（allocated）の最大。**余裕** ＝ cap − ノイズ除去の段の予約の山。**retries** ＝ 上限に当たって、空いたセグメント（確保済みの区画）を返してから確保し直した回数。**Δ共有** ＝ 共有メモリ（GPU が主メモリへ退避した量）の中央値の、同じ形式の基準点との差。

- int8 の 2560×1472×175（弾 X）は快適でした（快適の回数 1）。Kijai との比較のための点で、int8 の線の判定には使いません。int8 の c・U は現行（1080 345／362、1440 192／209）のままです。

## 6. 仕組みの考察（要約。詳細は `analysis/mechanism_w4a8.md`）

**事実（コードと記録）**
- Kijai の 1440×192 は、out_proj（注意の出力 7,168 列を 5,376 列へ戻す線形層）の入力の量子化で OOM しました。要求 1.46GiB は S×7,168 の int8 と一致します（qkv の幅 5,376 なら 1.09GiB）。Eros の 1080×328 は同じ関数の qkv 側で、要求 1.02GiB は S×5,376 の int8 と一致します。
- comfy-kitchen の二重確保: `w4a8_int8_linear` は 2391 行で `xq`（M×K の int8）を無条件に確保します。`fast_act` 経路（M≥512・groupsize 256）では 2446 行で `quantize_int8_rowwise_convrot64` の戻り値に差し替えるため、元の `xq` は一度も使われません（死んだ確保）。ほかの経路は `xq` に直接書きます。
- この二重確保は上流（PyPI 0.2.41・GitHub main 2026-11-04）でも残っていて、issue・PR はありません（別の調査担当の確認）。int8 の `int8_linear` は置き場を 1 本だけ確保します。
- int8 との差（Kijai − int8）: 1080×328 は予約 +480・割り当て +71・retries 16 対 9（int8 は 11-04）。1440×175 は予約 +1138・割り当て +51・retries 13 対 9（int8 は弾 X）。
- 割り当ての読み（b＝−920MiB は置き場の環が小さい分、a は 1080×328 で当てた +5,116 バイト／行）は、1440×175 の差を +52.6MiB と予測し、実測は +51MiB でした（独立な 1 点で一致）。
- 予約の読み（a＝+7,228 バイト／行）は否定されました。1 行あたりの予約の超過は 1080×328 で 7,228、1440×175 で 10,830 で、S に比例しません。前回の「7,228 は out_proj の S×7,168 の 1 本と近い」は偶然でした。
- int8 の傾き: 割り当ては 1080（328→345）で約 51,120、1440（175→192）で約 51,020 バイト／行と揃います。予約は約 53,370 と約 60,450 で揃いません。
- OOM した 4 点のうち 3 点は、予約済みの空きが要求より大きいのに 1 塊で取れませんでした（断片化）。Kijai 345 は空き 1.42GiB に 418MiB、Kijai 192 は 2.23GiB に 1.46GiB、Eros 328 は 1.26GiB に 1.02GiB です。この 3 点では、落ちた瞬間の割り当てが int8 の同じ形の割り当ての山より小さくなっていました（Eros 328: 11.40GiB 対 12,169MiB）。
- Eros は置き場の予約が int8 と同じ値でした（煙 3,848・基準点 5,866MiB）。Eros 345 は 1 ステップ目の sage の中で落ち、落ちた瞬間の割り当て（12.83GiB）が int8 345 の割り当ての山 12,669MiB を超えていました。
- fp8 は qkv の入力を 1 回だけ量子化して共有し、out_proj も 1 本確保するだけです。w4a8 の上乗せは無く、実測も int8 と同じでした。

**読み（推測）**
- Kijai の「使っている量」の上乗せは、bf16 の入力 h を注意の段の間持ち続ける分（+5,376 バイト／行）と、置き場の環が小さい分（−920MiB）で説明できます。
- 線を下げているのは予約の側の超過、つまり caching allocator（PyTorch のメモリの再利用の仕組み）の断片化だと読んでいます。呼び出しごとに S×7,168・S×5,376 の int8 の一時テンソルが 2 本並ぶため、予約の中に使えない穴が残ります。ただし量は形（解像度・一時テンソルの大きさ）で変わり、1 本の式にはなりません。
- Eros は置き場の環が小さくならない（b＝0）ので、w4a8 の層の上乗せがそのまま効きます（345 は使っている量の側、328 は断片化の側で落ちた）。
- 1 ステップの秒（int8 との比）:
  - fp8: 1080×345 が 1.089 倍、1440×192 が 1.088 倍。
  - Kijai: 基準点で 1.080 倍（1080）・1.060 倍（1440）、1080×328 で 1.026 倍、1440×175 で 1.029 倍（int8 は弾 X）。
  - Kijai は大きな S ほど比が 1 に近づきます。大きな S ではステップ時間の多くを注意の項が占め、注意の項は形式によらないためと読んでいます（推測）。
