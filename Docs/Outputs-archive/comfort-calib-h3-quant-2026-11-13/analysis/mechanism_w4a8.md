# Kijai w4a8 の快適上限 ― 仕組みの考察（2026-11-13。弾 X〔int8 1440×175・Eros 328〕の後に改訂）

GPU は使っていない。材料はコード読みと既存の記録（`runs/*/run.json`・`server_slice.log`、11-04 の `runs/`）だけ。
各節で **事実**（コードの行・記録の値・算数）と **推測** を分けて書く。
数の表記: S は DiT に入る総行数。MiB は 2²⁰ バイト、GiB は 2³⁰ バイト。

## 0. 結論（先に）

- **1440×192 の OOM は out_proj（注意の出力を 5,376 列へ戻す線形層）の入力の量子化で起きた**（事実・消去法で確定）。要求 1.46GiB は S×7,168 バイト（int8）で、7,168 は out_proj の入力の幅（heads×head_dim＝56×128）。qkv の入力の幅 5,376 なら 1.09GiB で、合わない。Eros の 1080×328 は同じ関数の qkv 側で落ちた（要求 1.02GiB＝S×5,376 の int8）。
- comfy-kitchen の `w4a8_int8_linear` は入力の int8 の置き場 `xq`（M×K）を先に確保し、そのあと `quantize_int8_rowwise_convrot64` が**別の** `q_2d`（M×K）を確保して `xq` を差し替える（事実・コード）。このため **呼び出しごとに M×K の int8 が一瞬 2 本**並ぶ。int8 の `int8_linear` は置き場を 1 本だけ確保し、そこへ直接書き込む。
- **割り当ての読みは 2 点で合う**（事実）: b＝−920MiB（置き場の環が小さい分）・a≈+5,116 バイト／行（1080×328 で当てた値。計画の +5,372＝bf16 の h を持ち続ける分に近い）は、弾 X で測った int8 1440×175 との差を +52.6MiB と予測し、実測は +51MiB だった。
- **予約の読み（a≈+7,228 バイト／行）は否定された**（事実）: 予約の超過は 1080×328 で +480MiB、1440×175 で +1,138MiB。b＝−920 を除いた 1 行あたりは 7,228 と 10,830 で、S に比例しない。前回書いた「7,228 は out_proj の S×7,168 の 1 本と近い」は偶然だった。
- 推測（残る読み）: 線を下げているのは予約の側の超過、つまり caching allocator（PyTorch のメモリの再利用の仕組み）の断片化。w4a8 は呼び出しごとに S×5,376・S×7,168 の大きな使い捨ての int8 を 2 本並べては返すので、予約の中に使えない穴が残る。OOM した 4 点（Kijai 345・192、Eros 328・345）は、Eros 345 を除き、要求より大きな予約済みの空きがあるのに取れなかった型。ただし量は形（解像度と一時テンソルの大きさ）で変わり、1 本の式にならない。
- Eros は 345・328 とも OOM → **線は S 203,092 より下・量は未定**（オーナー裁定で打ち止め。311 は打っていない）。計画の予測（328 −6 の境目・345 −580）はどちらも OOM 側で一致した。割り当ての読みは 328 を +44（快適）と外した。
- fp8 には関係しない。fp8 の out_proj は `quantize_per_tensor_fp8` が結果を 1 本確保するだけで、qkv は入力を共有する（事実・コード）。

## 2. 問 1: `q_2d` の dtype と形、どの線形層か

**事実（コード）**
- `quantize_int8_rowwise_convrot64`（cuda `__init__.py:1588-1623`）: `q_2d = torch.empty((rows, K // _input_act_width(input_act)), dtype=torch.int8)`。活性化を通さない呼び方では幅は K のまま。つまり **int8・[M, K]**。列にも行にも padding は無く、回転の中間テンソルも Python 側では確保しない（回転はカーネルの共有メモリの中で行う。`:1625-1629` の注記）。
- この Python 関数を呼ぶのは comfy-kitchen の中の 3 箇所だけ。`w4a8_int8_linear` の fast_act 経路（`:2446`）、W4A4 の線形（`:1322`）、重みの量子化（`:1721`）。製品側では `quant_linear.py:344`（int8 の入力共有。w4a8 では `shares_input` が偽なので通らない。`w4a8_linear.py:92-94`）。Kijai は 200 層すべてが `asym_w4a8_int8` なので、**呼び出し元は `w4a8_int8_linear` の `:2446`**（消去法）。
- H3 の層の幅（`engine_h3/dit.py:249,261-265,293-294`）: qkv_proj は 5,376→3×7,168、out_proj は **7,168→5,376**（`inner = heads × head_dim = 7168`）、fc1 は 5,376→2×ffn、fc2 は ffn→5,376。VRAM 16GB mode の呼び方（`lowvram.py`）は、qkv が S 行まるごとで 21 回、out_proj が S 行まるごとで 1 回（`:176`）、fc1・fc2 が 4,096 行の塊（`:192`）。

**事実（算数）**
- S×7,168 = 217,798×7,168 = 1,561,176,064 バイト = 1.4540GiB。大きな確保は 2MiB 単位に切り上がるので 1.4551GiB で、表示は **1.46GiB** になる。
- S×5,376 = 1.0905GiB で、表示は 1.09。fc1・fc2 は M=4,096 なので、1.46GiB になるには K が約 38 万要り、ありえない。
- → **out_proj の入力（`o`、S×7,168 の bf16）の量子化**。traceback の途中が切られていても、要求の大きさだけで決まる。
- 検算（同じ式で過去の点も合う）: int8 1080×362 の `o = torch.empty` は S×7,168×2 = 2.985GiB（表示 2.99）。w4a8 345 の sage の要求は 8×128×213,376（行を 64 の倍数へ揃えた数）×2 バイト = 416.75MiB → 418MiB。

## 3. 問 2: 注意の段の棚卸し（1 行あたりのバイト）

**事実（コード）: 1 回の呼び出しの中で確保されるもの**

| 呼び出し | int8（`H3Int8Linear`） | w4a8（`H3W4A8Linear` → `w4a8_int8_linear`） |
|---|---|---|
| qkv の前 | h（bf16 S×5,376）を 1 回だけ量子化して `xq` に（int8 S×5,376）。h は解放（`lowvram.py:150-155`） | 何もしない。h は `proj` の partial が持ち続ける（`:155` の注記） |
| qkv の 21 回それぞれ | 出力 S×1,024 の bf16（`_int8_gemm_prequantized` の `out`。CUTLASS 経路で int32 の一時は無い。8.9 では `_prefer_cublas_int8_fallback` が常に偽） | `xq` 置き場（int8 S×5,376）→ `xs` → `out`（bf16 S×1,024）→ `workspace`（列の塊×K、小さい）→ **`q_2d`（int8 S×5,376）** の順に確保（`:2391-2446`）。`q_2d` を確保する瞬間は置き場の `xq` も生きている |
| sage の中 | q・k・v（各 bf16 S×1,024）＋ sage の内部（v の転置 bf16・fp8 など）。int8 と w4a8 で同じ | 同じ。**加えて h（bf16 S×5,376）が残る** |
| out_proj | `int8_linear` が `x_qdata`（int8 S×7,168）を 1 本確保して直接書き込み、そのあと `out`（bf16 S×5,376） | `xq` 置き場（int8 S×7,168）・`out`（bf16 S×5,376）・workspace を確保したあとで、**`q_2d`（int8 S×7,168）をもう 1 本** ← 192 はここで OOM |

1 行あたりの差（w4a8 − int8。同じ瞬間どうし）:
- sage の段: h の 10,752 − 共有の `xq` 5,376 = **+5,376**（計画の a。式が 4 バイト違うのは丸め）
- out_proj の瞬間: 置き場の `xq` 1 本ぶん = **+7,168**
- qkv の呼び出しの瞬間: h 10,752 ＋ 置き場 5,376 ＋ `q_2d` 5,376 − 共有の `xq` 5,376 = +16,128（ただし int8 の山は別の瞬間なので、山どうしの差はこれより小さい）

**事実（記録）**
- 割り当ての山の差: 1080×328 は +71MiB。1440×175 は +51MiB（弾 X の実測の int8 12,007 に対し。弾 X の前は内挿 12,006 で +52 としていた）。b＝−920 とすると a は **5,116／5,108 バイト／行**（§5）。
- 予約の山の差: 1080×328 は +480MiB → (480+920)÷S = **7,228 バイト／行**。
- retries は w4a8 が 16／13、int8 は 9。inactive_split（分割されて使われていない塊の山）は w4a8 の方がわずかに少ない（4,230 対 4,566）。

**推測（読み）**
- 割り当ての山が +5,116 しか増えないので、山を決める瞬間は「sage の段（h を持ち続ける分だけ多い）」と読める。qkv の呼び出しや out_proj の一時的な置き場の重なりは、割り当ての山を決めていない。ただし、私の棚卸しの合計は int8 の割り当ての傾き 51,100 バイト／行（b1440→s1440_192、b1080→s1080_328、277→345 の 3 通りで 50,000〜51,100）より約 8,000 バイト少なく、山の瞬間をコードから決め切れてはいない（rope の f32 の一時などを数えていない）。
- （改訂）前回は「予約の超過 7,228 ≒ 7,168 は out_proj の S×7,168 の 1 本が予約に残るため」と読んだが、弾 X の 1440×175 で 1 行あたり 10,830 になり、この読みは否定された（§5）。192 の要求が S×7,168 なのは事実のまま。

## 4. 問 3: 345 の OOM の型

**事実**
- 割り当て 11.88GiB ＋ 予約済みの空き 1.42GiB ＝ 予約 13.30GiB（13,619MiB）。これに要求 418MiB を足すと 14,037MiB で、許可 13.67GiB（約 13,998MiB）を超える。
- 予約済みの空きは 1.42GiB（1,454MiB）あるのに、418MiB の要求は通らなかった。caching allocator（PyTorch のメモリの再利用の仕組み）は、要求以上の空きの塊があれば分割して使う。したがって**空きは 418MiB 未満の穴に分かれていた**（断片化）。新しい区画を取ると予約が cap を超える。
- 落ちた瞬間の割り当て 12,165MiB ＋ 418 ＝ 12,583MiB は、int8 345 が完走したときの割り当ての山 12,669MiB より**小さい**。
- 1・2 ステップ目は同じ S で完走し、3 ステップ目で落ちた（`h3_spans.denoise.last_done = 2`）。

**読み**
- 「割り当てが上限に届く型」（int8 1440×209: 12.80＋0.54＋0.45GiB）ではない。**断片化で予約が膨らみ、cap が予約に掛かる型**。int8 1080×362（予約済みの空き 3.84GiB に 2.99GiB が入らない）と同じ系統で、要求が小さい分だけ穴が細かい。
- int8 345 と並べると、使っている量は int8 より少ないのに予約の空き（推測: 1,454MiB。int8 345 の山の時点の予約 − 割り当ては 817MiB）が倍近い。w4a8 の「呼び出しごとに大きな int8 を 2 本確保して返す」動きと矛盾しない（推測）。
- ステップを重ねてから落ちるのは、予約の中の穴の並びが履歴で決まるため（推測）。

## 5. 問 4: Kijai の a・b の当て直し（弾 X の後に書き直し）

**事実（記録）**: int8 と Kijai の同じ形の差（Kijai − int8）

| 形 | S | int8 の予約／割り当て／retries | Kijai の予約／割り当て／retries | 予約の差 | 割り当ての差 | 予約 − 割り当て（int8 → Kijai） |
|---|---|---|---|---|---|---|
| 1920×1088×328 | 203,092 | 12,964／12,169／9（11-04） | 13,444／12,240／16 | +480 | +71 | 795 → 1,204（+409） |
| 2560×1472×175 | 199,342 | 12,700／12,007／9（弾 X・cap 14,001） | 13,838／12,058／13 | **+1,138** | **+51** | 693 → 1,780（+1,087） |

- 割り当ての読み（b＝−920 固定）: 1080×328 から a＝(71＋920)×2²⁰÷203,092 ＝ 5,116 バイト／行。これで 1440×175 を予測すると 5,116×199,342÷2²⁰ − 920 ＝ **+52.6MiB**、実測 **+51MiB**（独立な 1 点で一致）。前回の「1440×175 は内挿で +52」は、内挿値 12,006 に対し実測の int8 が 12,007 で、内挿も合っていた。
- 予約の読み（b＝−920 固定）: 1 行あたりは 1080×328 が (480＋920)÷S ＝ 7,228、1440×175 が (1,138＋920)÷S ＝ **10,830**。前回、7,228 の読みが成り立つための int8 1440×175 の予約は約 13,384 と書いたが、実測は 12,700 で、**否定**。
- int8 の傾き（事実の算数）:
  - 1440 の 175→192: 予約 12,700→13,764（+1,064MiB／18,456 行＝約 60,450 バイト／行）、割り当て 12,007→12,905（+898／18,456＝約 51,020）。175 は今回（cap 14,001）、192 は 11-04（cap 13,999）の値。
  - 1080 の 328→345: 予約 12,964→13,486（+522／10,256＝約 53,370）、割り当て 12,169→12,669（+500／10,256＝約 51,120）。どちらも 11-04 の値。
  - 割り当ての傾きは 2 つの解像度で約 51,000 に揃い、予約の傾きは揃わない。

**読み（推測）**
- Kijai の「使っている量」の上乗せは、bf16 の入力 h を注意の段の間持ち続ける分（+5,376 バイト／行。コード）と、置き場の環が小さい分（−920MiB）で説明できる。実測 5,116 との差（約 −260 バイト／行）の内訳は分かっていない。
- 予約の側の超過は形によって 2 倍以上違う（+409／+1,087MiB の「予約 − 割り当て」の増え）。1440 は 1 行あたりの一時テンソルの並び（qkv の S×5,376、out_proj の S×7,168、出力の S×5,376 の bf16 など）が 1080 と同じでも、映像・音声の行の比などの組み合わせで穴の残り方が変わる、と読むしかない。量を 1 本の式にはできない。
- OOM の 3 点（Kijai 345: 予約済みの空き 1.42GiB に 418MiB が入らない、Kijai 192: 2.23GiB に 1.46GiB が入らない、Eros 328: 1.26GiB に 1.02GiB が入らない）は、どれも「空きは要求より大きいのに 1 塊では取れない」断片化の型で、この読みと矛盾しない。

| 読み | a（バイト／行） | b（MiB） | 状態 |
|---|---|---|---|
| 計画（§4.2） | +5,372 | −920 | Kijai の 345・192 を快適と外した |
| 割り当て | +5,116 | −920 | 割り当ての山は 2 点で一致。ただし予約で決まる OOM は予測できない（345 を余裕 +392、192 を +92 と外す） |
| 予約 | +7,228 | −920 | **否定**（1440×175 で 10,830） |

基準点（S 3.9 万〜7 万）では割り当ての差が −875／−612MiB で、直線の式（−730／−578）からずれる。小さな S では山の瞬間が注意の段でないため（推測）、直線の式は大きな S にしか使わない。

## 6. 問 5: Eros（弾 E・弾 X の実測）

**事実（記録）**
- 置き場の予約は int8 と同じ値だった。煙の予約の山 3,848MiB（int8 3,848・Kijai 2,888）、基準点 b1080_eros は 5,866MiB（int8 5,866・Kijai 5,052）。b1080_eros の割り当ての山は 4,436MiB（int8 4,340）。

| 点 | 落ちたステップ | 場所 | 要求 | 割り当て | 予約済みの空き | 予約（割り当て＋空き） | 予約＋要求 | int8 の同じ形の割り当ての山（11-04） |

## 7. 問 6: fp8 への影響

- 関係しない（事実・コード）。fp8 `scaled` の qkv は入力を 1 回だけ量子化して共有する（`fp8_linear.py` の `shares_input`・`quantize_input`）。out_proj は `forward` → `quantize_per_tensor_fp8`（結果の uint8 [M, K] を 1 本確保するだけ。cuda `__init__.py:570` の `result_uint8 = torch.empty(x.shape)`）→ `scaled_mm_v2`。w4a8 の「置き場を確保してから別の `q_2d` で差し替える」2 本の確保も、h を持ち続けることも無い。したがって fp8 の予測（int8 と同じ）は変わらない。
