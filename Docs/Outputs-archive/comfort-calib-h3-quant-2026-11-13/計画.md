## 4. 仮説と予測（コード読みの裏取り結果。すべて推測。実測で確かめる）

### 4.1 仕組み（`engine_h3/lowvram.py`・`quant_linear.py`・`fp8_linear.py`・`w4a8_linear.py`・comfy-kitchen cuda）

- VRAM 16GB mode の線形層の呼び方: **qkv は出力 1,024 列の片ごとに 21 回呼ぶが、入力は毎回 S 行まるごと**（`lowvram.py:156-161`）。out_proj は全体呼び（`:176`）。fc1・fc2 だけが 4,096 行の塊（`:134`・`:191-192`）。
- int8 と fp8 `scaled` は `shares_input` が真で、入力を 1 回だけ量子化し元の bf16 入力 h を解放する（`:150-155`）。**w4a8 は入力を共有しないので、注意の段の間ずっと bf16 の h（S×5,376×2 バイト）を持ち続ける**（`w4a8_linear.py:92-94`）。これが w4a8 の 1 行あたり +5,372 バイト。
- 先読みの置き場（block swap の環）は「最大ブロック × (blocks_on_gpu＋2)」個（大きさ `engine/transformer/block_swap_prefetch.py:392`、個数 `:403-409`。VRAM 16GB mode は `constants.py:66` の 4 → 6 個）。int8・fp8 2,123MiB、Kijai 1,203MiB（−920）、Eros は int8 ブロック混在で 2,123。
- fp8 の fc2 の bf16 復元 cache（147MiB）は MLP の塊ループの間だけ。大きな S での山は注意の段で、MLP の段はそれより約 960MiB 低い計算 → cache は山に乗らないと読む。
- cap は予約（reserved）に掛かる（OOM の文言「割り当て＋予約済みの空き＋要求 ＞ 許可」が 2 点で成り立つ。torch の C++ の判定式は未確認）。
- **int8 の U の OOM の場所は 2 種**（11-04 の `server_slice.log`）: 1080×362 は注意の段の頭の **`o = torch.empty`**（`lowvram.py:147`。要求 2.99GiB・予約済みの空き 3.84GiB＝断片化の型）。この時点は入力量子化（`:150-155`）より前なので、生きているテンソルは int8 も w4a8 も同じ → ここでは Kijai の環の −920MiB だけが効く。1440×209 は **sage の中**（割り当てが上限に届く型）→ ここでは w4a8 の +5,372 バイト／行が効く。

- **仮説が外れたら分かること**: fp8 の 345 で予約が int8（13,486MiB）より 150MiB 以上高ければ「fc2 cache のセグメントが予約に残る」（1280×768×73 の +148 の正体）。Kijai の 345 が OOM なら a が +5,372 より大きい（xq 2 本の瞬間が山に乗る）。Eros の 345 が快適なら「山を決めるのは w4a8 のブロック」という読みが誤り。

## 5. 判定規則（快適上限表 §17.2 v3″ を継承。結果を見る前に固定）

- 快適 ＝ `completed` で、① OOM（`job.error` が `GPU_OOM:`）② 退避（denoise／decode の窓で共有メモリの中央値が **同じ重みの**基準点より +300MB 以上）③ 先読みの降格、のどれでもない。
- c（快適の上端）は 2 回快適。U（c の 1 段上）は cap での OOM なら 1 回で決定。退避か降格なら 2 回。**c の 2 回目（`_r2`）は弾 Z**。打てなかったときは結果の表の「快適の回数」の列に 1 と書き、11-04 の `_r2` が 1 回目と予約・割り当て・retries まで一致した事実（1080 13,486／12,669／9、1440 13,764／12,905／9）を根拠に添える。
- ノイズ除去より前の段（TE・符号化）の OOM は線から外す。
- 軸は S（総行数）。1080 と 1440 の帯が S で重なれば「解像度によらない」。
- **「余裕」の定義**: cap − 予約の山（MiB）。retries（上限に当たって丸ごと空いたセグメントを返した回数）が 0 でない点では、余裕は OOM までの距離そのものではない。考察では OOM の文の 4 つの数（要求・割り当て・予約済みの空き・許可）と retries を使う。
- 各点で cap・予約の山・割り当ての山・retries・OOM の場所（traceback の行。`o` の確保か sage の中か MLP か）・快適の回数・shift を表の列にする。cap が帯 13,999〜14,025MiB から 50MiB 以上外れた点、余裕 50MiB 未満の境目の点は留保に書く。
- **形式の記録**: 各 load の直後に `logs/h3_worker.log` の `LOAD_OK` 行の `quant_layers_by_format` と `fp8_mode` が期待どおりか確かめる（門 G1〜G4 の記録と同じ値: int8 `{"int8_tensorwise": 200}`、fp8 `{"float8_e4m3fn": 200}`・`fp8_mode "scaled"`、Kijai `{"asym_w4a8_int8": 200}`、Eros `{"asym_w4a8_int8": 180, "int8_tensorwise": 20}`）。§6 の差分 1 で run.json にも残す。
- **対照点（弾 I）の合否**: s1080_362_int8 が OOM で、OOM の文の 4 つの数（要求 2.99GiB・割り当て 6.94・予約済みの空き 3.84・許可 13.67）が 11-04 の 3 回の記録（`logs/server.log`）と一致 → 環境は同じ。OOM だが数が違う → 記録して進む（cap の差として考察）。快適 → 止めて監督へ。
- **Eros（1 点）の読み方を先に決める**: 345 が OOM → 「Eros の線は 213,348 より下。量は未定（1 点の裁定）」。快適 → §4.1 の「山を決めるのは w4a8 のブロック」の読みが誤り、と書く。
