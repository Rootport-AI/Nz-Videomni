## 記号と用語

- **U**: [行, 5376] の bf16（16 ビットの浮動小数点）の張量の 1 行ぶん＝10,752 バイト。DiT の 1 ブロックの中の主な張量はこの形なので、「S·U」は S 行ぶんの 1 本を表す（r1080_277 で 1.68GiB）。
- **S**: DiT に入る行の総数。**Nv**: 生成する映像の行（video）。**L**: text の行。**R**: 参照の行（ref_video＋ref_audio）。**C**: 条件行（cond。キーフレームの行）。**Na**: 生成する音声の行。
- **割り当て**（allocated）: PyTorch が張量として使っている GPU メモリ。**予約**（reserved）: PyTorch が GPU から確保して手元に持っている量（割り当て＋予約済みの空き）。**予約済みの空き**: 予約のうち使っていない分。本書では**断片化**の量と同じ意味で使う。
- **セグメント**: 割り当て器（PyTorch の CUDA メモリの割り当ての仕組み）が GPU から一度に確保する連続した領域。張量はセグメントを切り分けて置かれる。
- **上限（cap）**: VRAM 16GB mode がノイズ除去の段の間だけ課す、このプロセスの予約の上限。
- DiT＝ノイズ除去の本体。TE＝テキストエンコーダー（Qwen3-VL）。OOM＝GPU のメモリ不足。RoPE＝位置の回転埋め込み。AdaLN＝時刻で変える正規化。MLP＝ブロックの中の 2 層の全結合。CFG＝条件つきと無条件の 2 本を同時に流す方式。int8＝8 ビット整数。f32＝32 ビットの浮動小数点。ステップ 0・1＝0 から数えたノイズ除去のステップ（ステップ 1 は 2 つ目）。

## 0. 結論（問い 10 の答え）

**参照の行が軽く見えるのは、仮説 A（行の種類ごとに常駐する量が違う）でも仮説 B（前の段がキャッシュを整える）でも説明できない。** 仮説 A は参照の行を軽くする向きには働かない（常駐の差は text の行にしかなく、しかも重い側）。仮説 B はコードで否定される（段の境目でキャッシュを空にし、上限もノイズ除去の頭で計算し直している）。**軽さは「予約済みの空き」（断片化）の側にあり、その量は総行数よりも映像の行の数に沿って増えている（観測）。コードには、映像の行だけが持つ大きな一時張量がステップの境目に 2 本ある。** これを本書では**仮説 C** と呼ぶ。仮説 C は 2 回の較正の全点を 1 本のしきい値で分け、問い 8 の 3 つの検算も通す。ただし結果を見てから 1 つの値を合わせた記述にとどまる。空きがどの確保で作られたセグメントに閉じ込められているかはコードを読むだけでは決まらなかったが、OOM の時点の確保の履歴の測定で r1080_277 について決まり、**仮説 C は支持された**（6・§5）。

1. **仮説 A は参照の行については否定される**（【コード】【実測】）。ブロックの中の張量はすべて S 行全体を覆い、参照の行も映像の行と同じく問い合わせ（クエリ）・残差・MLP を通る（§2.1）。常駐の差を見ると、映像の行の状態（f32 [Nv,96]）と参照の行（f32 [R,96]）はどちらも 1 行 384 バイトで同じ。違うのは text の行だけで、`text_hidden`＋`text_refined` の 1 行約 21,000 バイトが**上乗せ**になる（§2.2）。既存の記録もこれと合う。ノイズ除去の割り当ての山は、2 回の較正の 15 点で「2,251MiB＋51,106 バイト×S＋20,423 バイト×L＋29 バイト×（参照＋条件行）」に残差 6MiB 以内で乗り、参照と条件行の上乗せは 0 とみなせる。OOM の時点の割り当ても、ブロックの中で起きた 10 件（2 回の較正の全部）で「固定分 2.19〜2.20GiB＋3·S·U＋行ごとの常駐」に ±0.005GiB で一致する（§3.2）。**割り当てだけで線を引くと、参照の行は映像の行と同じ重さ（1.0）、text の行は約 1.47 倍で、実測の重み 0.54〜0.77 とは向きが逆になる**（§3.3）。
2. **仮説 B はコードで否定される**（§1.5）。TE の段の終わり（`text_encoder.py:867-869`・`pipeline_h3.py:917`）と参照の符号化の段の終わり（`pipeline_h3.py:794`）で `gc.collect()`＋`torch.cuda.empty_cache()` を呼び、使い終わったセグメントはノイズ除去の前に GPU へ返している。上限はノイズ除去の頭で「その時点の予約＋空き−1,024MiB」から計算する（`pipeline_h3.py:1330-1333`）ので、前の段が予約を残しても上限の中で使える量は増えない。ただし、前の段のセグメントは全部は返っていなかった（測定で判明。§1.5 の訂正）。TE の段の埋め込みの表を読んだ 1,484MiB のセグメントは、先頭に残る 8,519,680 バイト（cuBLAS の作業領域と推定）のために GPU に返らず、r1080_277 の OOM の時点で予約済みの空きの 27.8% を占めた。これは使える量を増やすのではなく、S·U の入らない空きを増やす向き（仮説 B と逆）に効く。実測でも、TE の段と参照の符号化の段がまったく同じ i1080_226_p9（完走）と i1080_243_p9（OOM）が分かれており、前の段では決まっていない。
3. **境界を決めているのは断片化**（【実測】§3.4）。OOM の時点では、予約済みの空きが 2.26〜4.83GiB 残っているのに、S·U の大きさの連続した空きが無い。この量を Nv·U で割ると、ステップ 1 で落ちた 6 件（2 回の較正）で 2.56〜2.82 に揃う。S·U で割ると 2.16〜2.81 と広がり、参照・条件行の多い点ほど S·U あたりの断片化が小さい。
4. **落ちるのは、ステップの境目の直後のブロック 0**（【実測】ログの時刻から【推定】。§4.2）。ステップ 1 で落ちた 7 件は、すべて「ステップ 1 のブロック 0 の頭」で出るログ行から 4.0〜5.0 秒後（ブロック 1 本ぶんの平均時間より短い）に失敗している。ステップ 0 で落ちた 3 件も、DiT を置き終えてから 7〜8 秒後。境目の直前には、映像の行だけが持つ [Nv,5376] の f32 の一時張量が 2 本ある。最終層の `buf`（`lowvram.py:203`）と、次のステップの埋め込みの映像の射影（`dit.py:551`）で、どちらも 1 行 21,504 バイト（2U）。r1080_277 では 1 本 3.35GiB で、そのステップの中でいちばん大きい確保になる。参照・条件行の射影は別の小さな張量（`dit.py:545-549`）で、text の行には境目の一時張量が無い（§2.5）。【推定】映像の行の大きさで作られたセグメントに、ブロック 0 の S·U の張量がうまく収まらず空きが閉じ込められる、というのが仮説 C。
5. **仮説 C で問い 8 の 3 つの検算が通る**（【当てはめ】。§3.5）。断片化を「φ×Nv·U」と置き、φ を OOM の実測値に近い範囲（2.72〜2.88）にとると、(i) 参照なしの境界は映像 163,450〜167,260 行（実測は 157,080 で完走・167,280 で OOM。上端は OOM の点の 22 行下）、(ii) 参照＋text の重みは 0.62〜0.74（監督の計算 0.54〜0.77）、(iii) text を参照に含めた「参照だけの重み」は画像 9 枚で約 1.46〜1.49、動画で約 0.72〜0.77 と食い違う（監督の計算 画像 0.72〜1.66・動画 0.61〜0.91 で、1 つの値では両方を満たせない）。2 回の較正の全点（OOM 11 件・完走 28 点。小さい基準点を除く）が、φ の 1 つのしきい値（2.72 と 2.88 の間）で分かれる。**ただし、これは結果を見てから 1 つの値を合わせた記述で、仕組みの証明ではない。** しきい値の両側の差は 6% しかない。
6. **測定の判定 — 仮説 C を支持する**（【実測】`mem_history/MEM_HISTORY_REPORT.md` §0・§2・§3。2026-11-03 12:09〜、オーナー了承済み）。r1080_277 を確保の履歴つきで流し、較正と同じ要求 1.69・割り当て 7.43・予約済みの空き 4.73GiB・同じ場所（ステップ 1 のブロック 0 の `lowvram.py:178`）で OOM した。
   - OOM の時点の予約済みの空き 4.734GiB の内訳は、**70.4%（3.334GiB）が `dit.py:551`（ステップ 0 の埋め込みの映像の射影）と `lowvram.py:203`（ステップ 0 の最終層の `buf`）の [Nv,5376] f32 が作った 3,432MiB のセグメント 2 つの穴**、**ブロックの中の確保が作ったセグメントの空きは 0**、**27.8%（1.318GiB）は TE の段のセグメント**（§1.5 の訂正）、残り 1.7% はノイズ除去の前処理。
   - 2 つのセグメントにはそれぞれ S·U が 1 本（ブロック 0 の入力 x と、注意の残差の後の x2）入り、残りの穴は 1 つ 1,706.9MiB で S·U（1,725.1MiB）より 18.1MiB 小さい。そのため `h2` が入らず、新しいセグメントを足すと上限を超えた。

### 1.3 上限（cap）（問い 3 の前半）

【コード】
- **いつ**: `_denoise` の中で、DiT を CPU に読み終えた後、ブロック以外を GPU に置く前（`pipeline_h3.py:1461-1462`→`_vram16_begin` 1307-1337）。外すのは `finally` の先頭（`1599-1600`→`_vram16_finish` 1339-1352 の `set_per_process_memory_fraction(1.0)`、1344）。TE・参照の符号化・復号の段には上限が無い。
- **何から**: `torch.cuda.mem_get_info` の空きと総量、`torch.cuda.memory_reserved`（このプロセスの予約）から `(予約＋空き−1,024MiB)÷総量`（`lowvram.py:96-105`、余白は `constants.py:68`）。予約を足し戻しているので、上限は「このプロセスが使える GPU の量−1,024MiB」であり、直前にキャッシュが残っていても変わらない。今回の値は 13,999〜14,025MiB。
- **上限の効き方**（【推定】PyTorch の一般的な仕様）: 新しいセグメントを取ると予約の合計が上限を超えるとき、まず「丸ごと空いているセグメント」を全部 GPU へ返して再試行し（`num_alloc_retries` に数えられる）、それでも超えれば OOM にする。一部でも使われているセグメントは返せず、その中の空きが「予約済みの空き」として残る。

### 4.3 同じ大きさの確保が繰り返されるときの効き方（問い 9 の後半）

【推定】（PyTorch の割り当て器の一般的な仕様。本リポジトリでは読んでいない）

- 大きな確保は、手元の空きのうち要求以上で最も小さいもの（同じ流れ〔stream〕・同じ大きさの区分）に置かれ、余りが 1MiB を超えれば同じセグメントの中の空きとして残る。10MiB を超える要求で新しいセグメントを取るときは、大きさを 2MiB 単位に切り上げる（§3.2 の要求の値と合う）。
- ブロック 1〜49 は同じ大きさの確保を同じ順に繰り返すので、前のブロックが空けた穴にそのまま収まり、予約は増えない（毎ブロックの 1.7〜2.2GiB の確保そのものは危なくない）。
- 並びの形が変わるのは、ステップ 0 の頭（前処理の後）とステップの境目（最終層の 2·Nv·U、埋め込みの 2·Nv·U と Nv·U、連結の S·U）。直後のブロック 0 では、S·U の要求が「映像の行の大きさで作られた穴」と出会う。穴が S·U より少しでも小さければ使えず、その分が予約済みの空きとして閉じ込められる。上限の中で新しいセグメントを取れなくなれば、丸ごと空いたセグメントを返して再試行し（今回の大きい点の多くで `num_alloc_retries` が 2）、それでも足りなければ OOM になる。
- 仮説 C は、この「境目の穴の大きさが Nv で決まる」ことが、断片化が Nv に沿う理由だという推測。例えば参照なしでは 2·Nv·U の穴が 2·S·U よりわずかに小さく、S·U を 1 本入れた残りが S·U に届かない。参照や text が多いと穴が S·U に比べて小さくなり、閉じ込められる量が減る。ただし実際の並びは、注意の一時分・塊の一時分・常駐の小さな張量がどの穴に入るかで変わり、コードからは数値を出せない。
- **測定で確かめた**（r1080_277。【実測】`mem_history/MEM_HISTORY_REPORT.md` §0・§2.3・§3）。
  - ステップ 0 の最終層の `buf` を置くために、割り当て器は、ステップ 0 のブロックが使っていた S 行の大きさのセグメント 3 つ（1,726＋1,726＋2,302MiB）を返して、3,432MiB のセグメントを作った。
  - ステップ 1 では、ステップ 0 の埋め込みで作られた 3,432MiB と合わせた 2 つに、S·U が 1 本ずつ入った。残りの穴 1,706.9MiB は S·U より 18.1MiB 小さかった。
  - ステップ 0 で 2,302MiB のセグメントが担っていた役を、3,432MiB のセグメントが担うことになった。その差 1,130MiB だけ、ブロック 0 の `h2` の時点の予約（新しいセグメントを足して 14,186MiB）がステップ 0 の山（13,056MiB）より大きくなり、上限 14,025MiB を超えた。

## 5. まだ決まらないことと、実施した測定

初版で未決にしていた項目のうち、「予約済みの空きがどのセグメントに閉じ込められているか」「断片化が Nv に沿う理由」「どのブロックで落ちたか」は r1080_277 について、「`text_hidden` が TE の段のどの大きさのセグメントに載ったか」は参考の i1080_243_p9 の 1 本について、測定で決まった（§0 の 6、§1.5 の訂正、§4.3）。残るのは次の項目。

### 5.1 まだ決まらないこと

1. **上限が数十 MiB 動くと並びが変わる**。上限は他のプロセスの使い方で決まる GPU の空きから計算するので、数十 MiB 動く。予約が上限の近くを通る点では、その差で再試行の有無が変わり、OOM の場所や値が変わる。i1080_243_p9 は、測定のときの上限が較正より 16MiB 高かった。ステップ 0 の予約がその間（14,002MiB）に来て並びが分かれ、落ちた場所が out_proj から `lowvram.py:178` に変わって再現しなかった（【推定】の原因。`mem_history/MEM_HISTORY_REPORT.md` §4）。境界の近くの点の完走と OOM は、この揺れに左右されうる。r1080_277 は上限の近くを通らなかったので影響を受けていない。
2. **較正のときの i1080_243_p9 の並び**（out_proj で落ちた並び）は確かめていない。参照つきの内訳（Nv f32 の 2 つで 54.6%・TE の段で 42.3%・ブロックの中は 0）は、再現しなかった 1 本の参考値。
3. **穴の式が他の点でも成り立つか**。2·(2·Nv − S)·U は r1080_277 の内訳を言い直した式（と参考の 1 本）で、境界の式としては検証していない。2·Nv が S より小さい点（例えば 720 の動画 15 秒の点）では、S·U が Nv f32 のセグメントに入らず、別の並びになるはず（【推定】）。
4. **cuBLAS の作業領域という同定**は【推定】（大きさが既定の作業領域とバイト単位で一致すること、TE の最初の行列積で確保されたこと、解放されないことが根拠）。製品のワーカーは同じプロセスで複数のジョブを流すので、較正のときに作業領域がどこにあったかは分からない（割り当て器の値が一致したので、同じ並びだったと推定）。
5. **ステップ 2 以降の並び**は、ステップ 1 と同じ形を繰り返すと推定しているが、確かめていない。
6. **割り当ての山の位置**（注意の部分と推定。sage と sdpa の差 0.40U は核の中の分の推定に頼る）。測定の範囲外。
7. **§3.5 のしきい値は当てはめのまま**。測定は仕組みを確かめたが、φ の値を決める式は検証していない。
