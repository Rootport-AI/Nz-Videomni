## 用語（初出の略語の説明）

- **Ref2VA**: 参照素材（画像・動画・音声）を受け付ける H3 の重み（`minimax_h3_ref2va_pruned_int8_convrot`）。**FL2VA** は前回測った、先頭・末尾のキーフレームを受け付ける重み。
- **K**: キーフレームの枚数。今回は全点 K=0（キーフレームなし。オーナー裁定 3）。
- **DiT**: ノイズ除去の本体のネットワーク。ここに入る列（行の並び）は `[text | cond | ref_video | ref_audio | audio | video]`。
- **text**: プロンプトと、参照をテキストエンコーダーが文章の列に埋め込んだ行。**cond**: キーフレームの条件行（今回は 0）。**ref_video**: 参照の画像・動画の行（画像も ref_video に入る）。**ref_audio**: 参照の音声の行。**audio**・**video**: 生成する音声・映像の行。
- **S**: DiT に入る行の総数（`sequence.total`。上の 6 つの合計）。
- **vc**: 映像＋条件行（video＋cond）。前回の線の軸。**vcr**: 映像＋条件行＋参照の行（video＋cond＋ref_video＋ref_audio）。今回の軸の候補（計画 §1）。
- **S_source**: S の出どころ。`metadata` は完走した点の `metadata.json` の実数。`worker_log` は OOM の点で、ワーカーのログ（`encode: N text tokens` の行）の text の実数に、ほかの行を式で足した値（計画 §2.5-5）。
- **TE**: テキストエンコーダー（Qwen3-VL）。**TE の段**＝`encode`、**参照の符号化の段**＝`reference_encode`（参照の画像・動画・音声を DiT の行にする段）。
- **OOM**: GPU のメモリ不足（out of memory）。**cap**（`cap_mib`）: VRAM 16GB mode がノイズ除去の頭で掛ける割り当ての上限（MiB）。
- **Δ（デルタ）**: その窓（server.log の行で区切った工程の区間）の WDDM（Windows の GPU メモリ管理）の共有メモリの中央値 − 基準点の同じ窓の中央値（MB）。+300MB 以上で「退避」。
- **基準点**: 腕（解像度 × attention）ごとの 56 フレームの点（b1080・b720・b1080x）。**煙の点**: 動作確認の点（warm）。**復帰の捨てラン**: OOM のあとに較正台が読み込み直して流す小さな点（warm_rec…）。
- **sage**／**sdpa**: attention（注意機構）の計算方式。sage が製品の既定（オーナー裁定 1）、sdpa は照合用。
- **予約済みの空き**: PyTorch が GPU から予約したが、いまは使っていないメモリ（断片化の目安）。
- **predict**: 較正台が点を作るときに計算した行数の予測（`run.json` の `predict`）。

## 1. 結論

**S（総行数）でも vcr（映像＋参照の行）でも、1 本の線では完走と OOM が分かれない（計画 §2.4 の (c)）。** 「参照の行も text の行も同じ 1 行として合計に効く」という台帳の仮説は、どちらの形でも成り立たなかった。

根拠は 1920×1088・sage の腕の、矛盾する点の組（§4 の表）:

- **S で分かれない**: 参照なしの r1080_277（S 168,234）が OOM し、同じ条件の取り直し r1080_277b でも同じ場所・同じ数値で OOM した（§5）。一方、S がそれより大きい v1080_243_3s（S 173,966）と i1080_226_p9（S 174,256）は完走した。重なりは 6,022 行。落ちたのは text の少ない点（30 行）で、完走したのが text の多い点なので、計画 §2.4 の注記（「text の多い点が S の線より下で落ちただけでは (c) としない」）には当たらない。

## 8′. なぜ参照の行が軽く見えるか（仕組みの考察）

出典: 本フォルダの `MECHANISM_ANALYSIS.md`（調査担当。2026-11-03 10:30〜。コードと既存の記録〔今回と前回の較正の run.json・ワーカーのログ〕だけを読んだ考察で、GPU を使った新しい計測はしていない）。本節はその §0 の要約で、式の導き方・コードの行・点ごとの値（φ_max の全点の表を含む）は MECHANISM_ANALYSIS.md が正本（ここには写さない）。記号: U は [1 行, 5376] の bf16 の 1 行ぶん（10,752 バイト）、Nv は生成する映像の行。

### 8′.1 判定 — 仮説 C を支持（メモリ確保の履歴の測定）

- **参照の行が軽く見える理由**: 映像以外の行（参照・text・音声）は、S を増やして 2 つの穴を小さくする（閉じ込められる空きを 1 行あたり 2U 減らす）一方、S 行の作業用の張量は映像の行と同じだけ大きくするので、差し引きで映像の行より軽い。r1080_277 の OOM の時点の「予約＋要求」14,186MiB の内訳（TE の段と前処理のセグメント 3,870MiB＋Nv f32 のセグメント 3,432MiB×2＋ブロックの中のセグメント 1,726MiB＋要求 1,726MiB。報告書 §3）で数え直すと、予約を増やす量は映像の行 1 行で 6U（Nv f32 のセグメント 2 つで 4U＋ブロックの中のセグメントと要求で 2U）、映像以外の行 1 行で 2U（Nv f32 のセグメントの中の x・x2 の伸びは穴を埋めるだけ）になる（本担当の計算）。ただし TE の段の残りは参照と text が多いほど大きく（任意の i1080_243_p9 では予約済みの空きのうち 1.70GiB・42%）、参照の行の実効の重さを押し上げる。§8′ の φ の当てはめ（参照の行 0.59〜0.60）は、この 2 つ（穴を小さくする効果と、TE の段の残り）を合わせて 1 つの値で表したもの、と読める。
- **i1080_243_p9 は再現しなかった**（任意の 1 本。判定には使わない）。要求・割り当て・予約済みの空きは較正と ±0.02GiB だったが、落ちた場所が `out_proj`（comfy-kitchen の `int8_linear`）ではなく `lowvram.py:178` になった。上限が 14,015MiB で較正の 1080 の完走点の上限（13,999〜14,001MiB）より 14〜16MiB 高く、ステップ 0 のブロック 0 の `o`（[S, 7168] bf16 2,524MiB）のための新しいセグメントで予約がちょうど 14,002MiB になって上限の下に収まり、較正では起きたとみられる再試行が起きずに並びが分かれた、と報告書 §4 は推定している（§9 の 8）。
