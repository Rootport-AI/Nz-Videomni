## 用語（初出の略語の説明）

- **OOM**: GPU のメモリ不足の例外。**TE**: テキストエンコーダー（Qwen3-VL）。**DiT**: ノイズ除去の本体。
- **割り当て器**: PyTorch が GPU メモリを貸し出す仕組み（CUDA のキャッシュつき割り当て器）。**セグメント**: 割り当て器が GPU から一度に取る連続した領域（`cudaMalloc` 1 回ぶん）。張量はセグメントを切り分けて置かれ、セグメントどうしはつながらない。
- **予約**: 割り当て器が手元に持っているセグメントの合計。**予約済みの空き**: 予約のうち張量が使っていない分（OOM の文言の「reserved but unallocated」）。本書では断片化と同じ意味。
- **上限**: VRAM 16GB mode がノイズ除去の段の間だけ課す、このプロセスの予約の上限（OOM の文言の「allowed」）。
- **スナップショット**: `torch.cuda.memory._snapshot()` が返す、その時点のセグメントとブロックの一覧に、記録を始めてからの確保・解放の履歴（`device_traces`）を添えたもの。
- **S**: DiT に入る行の総数（168,234）。**Nv**: 映像の行（167,280）。**U**: [行, 5376] の bf16 の 1 行＝10,752 バイト。**S·U**: S 行の bf16 張量 1 本（1,725.1MiB）。**Nv f32**: [Nv, 5376] の f32 張量（3,430.5MiB＝3.35GiB）。
- **cuBLAS**: NVIDIA の行列積のライブラリ。PyTorch は最初の行列積のときに作業領域を割り当て器から借り、プロセスが終わるまで返さない。

1. Nv f32 の 2 本は、それぞれ 3,432MiB のセグメントを新しく作る（ステップ 0 の埋め込みで 1 つ、ステップ 0 の最終層で 1 つ）。最終層の 1 本を置くために、割り当て器はステップ 0 のブロックが使っていた S 行の大きさのセグメント 3 つ（1,726＋1,726＋2,302MiB）を GPU へ返している。
2. ステップ 1 では、2 つの 3,432MiB のセグメントに S·U の張量が 1 本ずつ入る（ブロック 0 の入力 x と、注意の残差の後の x2）。残りの穴は 1,706.9MiB で、S·U（1,725.1MiB）より **18.1MiB 小さい**ため、もう 1 本の S·U は入らない。
3. ブロック 0 の `h2`（`lowvram.py:178`）が S·U を要求したとき、入る穴がどこにも無く、新しいセグメント 1,726MiB を取ると予約が 12,460＋1,726＝14,186MiB になり、上限 14,025MiB を超えた。丸ごと空いたセグメントも無く、OOM になった。
4. ステップ 0 のブロック 0 でも `h2` は新しいセグメント 1,726MiB を取っているが、そのときの予約は 13,056MiB で上限の下に収まった。ステップ 0 のブロック 0 で `o`（[S,7168]）と x2 を置いた 2,302MiB のセグメントは最終層で返され、ステップ 1 ではその役を 3,432MiB のセグメント B が担った。S 行の張量の置き場の数は同じだが、B は 1,130MiB 大きく、その分が S·U に使えない穴になる。ステップ 0 の山と上限の間の余裕は 969MiB で、この 1,130MiB を吸収できなかった（【計算】14,186 − 13,056＝1,130＝3,432 − 2,302）。

**【計算】穴が S·U に届かない理由は行の内訳そのもの。** 3,432MiB のセグメント（2·Nv·U を 2MiB 単位に切り上げ）に S·U が 2 本入るのは S が 167,350 行以下のときだけで、映像以外の行が約 70 行を超えると入らない。r1080_277 の映像以外の行は 954 行（text 30・音声 924）。つまり 2 つの Nv f32 のセグメントに閉じ込められる空きはおよそ 2·(2·Nv − S)·U で、映像の行が増えれば増え、映像以外の行が増えれば減る。`MECHANISM_ANALYSIS.md` §3.4 の「断片化は映像の行に沿う」と同じ向き。ただし、この式が他の点でも成り立つかは今回の 1 点（と §4）でしか見ていない（【推定】）。

**驚いた点（事実の記録。変更の提案ではない）**: 残りの 27.8% は、TE の段で埋め込みの表（1,483.8MiB）を読み込んだセグメントにある。表は TE の前向きの途中で捨てられるが、その直後の最初の行列積で cuBLAS の作業領域と見られる 8.1MiB（8,519,680 バイト。PyTorch の既定の作業領域の大きさ 4,096KiB×2＋16KiB×8 とちょうど同じ）がセグメントの先頭に置かれ、解放されないまま残る。そのため TE の段の終わりの `empty_cache` でもこのセグメントは GPU に返らず、ノイズ除去の間も RoPE の表（61.6MiB）や映像の状態（61.3MiB）の置き場になっている。`MECHANISM_ANALYSIS.md` §1.5 の「前の段から GPU に残るのは `text_hidden`・`text_tags` だけで、2MiB の小さなセグメントに収まる」とは違う。このセグメントの大きさ（1,484MiB）は S·U より小さいので、OOM の時点の S·U の要求には使えない。

**再現**: 割り当て器が決める値（要求・割り当て・予約済みの空き）と場所は較正と一致した。GPU 全体の空きと上限（他のプロセスの使い方で決まる値）は少し違ったが、確保の並びを変えていないことを履歴で確かめた（§1.4）。

## 5. 注意

- **履歴の記録の影響**: 割り当て器が決める値（要求・割り当て・予約済みの空き）と場所が較正と同じだったので、記録は確保の並びを変えていない（【実測】）。ステップ 0 の秒も 212.1 秒で、較正（211.0／215.0 秒）と同じ程度。スナップショットの書き出しは 0.3〜0.4 秒で、ステップの境目（index 1）と OOM の瞬間の 2 回。
- **計測台の `snapshot_error.pickle` は OOM の瞬間ではない**（§1.2 の 3）。今回の判定には `snapshot_oom.pickle` だけを使った。`snapshot_error.pickle` は記録として残した（割り当て 5.38GiB・予約 10.23GiB。片付けの後の状態）。
- **読めなかった・無かったキー**: スナップショットのキーは、セグメントが `active_size`・`address`・`allocated_size`・`blocks`・`device`・`frames`・`is_expandable`・`requested_size`・`segment_pool_id`・`segment_type`・`stream`・`total_size`、ブロックが `address`・`frames`・`requested_size`・`size`・`state`、履歴が `action`・`addr`・`compile_context`・`frames`・`pool_id`・`size`・`stream`・`time_us`・`user_metadata`（OOM の項目は `addr` が無く `device_free` がある）。すべて読めた。ただし、
  - セグメントの `frames` は 14 個のうち 8 個で空だった（受け皿の 6 個だけ中身があり、履歴の `segment_alloc` と 6 個とも一致）。そのためセグメントの起点は履歴の `segment_alloc` から決めた。
  - 空きのブロック（`inactive`）は `frames` が空で `requested_size` が 0。空きの穴に「直前まで何が置かれていたか」は、履歴でその位置から始まった最後の確保を手がかりとして書いた（§2.3 の括弧）。
- **cuBLAS の作業領域という同定は【推定】**。根拠は、大きさが PyTorch の既定の作業領域（`:4096:2:16:8`）とバイト単位で同じこと、TE の最初の行列積で確保されたこと、プロセスの間ずっと解放されないこと。製品のワーカーは複数のジョブで同じプロセスを使うので、作業領域はそのワーカーの最初のジョブで置かれた場所に残り続ける。較正のときにどこにあったかは分からないが、割り当て器の値が一致したので、OOM の時点の並びは同じだったと【推定】する。
- **上限が並びを変えうる**（§4 で起きた）: 上限は GPU 全体の空きから計算するので、他のプロセスの使い方で数十 MiB 動く。予約が上限の近くを通る点では、その差で再試行の有無が変わり、OOM の場所や値が変わる。r1080_277 はその近くを通らなかったので影響を受けていない。
- **終了時の確認**（`postconditions.txt`）: 12:30:06 に GPU の使用 660MiB・計算のプロセスに python なし・python のプロセスはサーバーの 2 つだけ・`git status --short` は空・サーバーは `pipeline_loaded: false` のまま。
- **範囲**: 1920×1088・sage・ステップ 1 のブロック 0 の 1 点（と §4）。720・1440・sdpa・他の行の内訳に広げない。§0 の「2·(2·Nv − S)·U」は今回の点の内訳を言い直した式で、境界の式として検証したものではない。境界の決め方・受け皿の設計は範囲外。
