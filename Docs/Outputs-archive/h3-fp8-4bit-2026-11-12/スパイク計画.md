# MiniMax H3 の fp8／w4a8 スパイク計画（台帳 §1-283・第 0 段）

- 作成: 2026-11-12（監督）。状態: 承認待ち。設計の確認（Plan 役）と独立の事実確認（15 件の指摘。重大 1 件＝`forward_rows` の `lora_xa` 引数の欠落、要修正 3 件＝仕様型の属性・S1 ⑥の条件・差し替えの範囲。すべて反映済み。棄却なし）を通した版
- 位置づけ: 製品実装の前に、GPU で 1 度だけ行う試作と計測。**製品コードは触らない**。

## 1. 背景と目的

台帳 §1-283 の目的は、CivitAI などで配布される MiniMax H3 の fp8 と w4a8（重み 4 ビット・活性化 8 ビット）の safetensors を、`models\MiniMaxH3\Weights\` に置くだけで動かせるようにすることです。

オーナー裁定（2026-11-12）で、fp8 対応の目的は「利用者が ComfyUI などで使っている fp8 のチェックポイントを、できるだけ忠実に再現すること」と定まりました。fp8 を int8 ConvRot へ再量子化する案は採りません。fp8 専用の計算経路を設計し、既存のローダー・block swap・VRAM 16GB mode と可能な限り共通化します。速度より ComfyUI との数値的な整合性を優先し、本製品固有の不要な数値差を増やさないことを原則とします（完全な一致の保証は不要）。w4a8 も同じ原則で、ComfyUI が呼ぶ comfy-kitchen の関数を同じ引数で呼びます。

このスパイクで確かめるのは次の 3 点です。「ComfyUI と同じ関数を同じ引数で呼ぶ試作の層が、ComfyUI の計算経路とビット単位で一致するか」「既存の仕組み（ローダー・block swap・VRAM 16GB mode）がそのまま運べるか」「速度と VRAM が実用の範囲か」。

## 2. 確かめる仮説

- **H1（一致）**: comfy-kitchen の公開 API（`quantize_per_tensor_fp8`・`scaled_mm_v2`・`dequantize_per_tensor_fp8`・`w4a8_int8_linear`）を ComfyUI と同じ引数で呼ぶ試作の層は、同じ GPU・同じ入力で、comfy-kitchen の `QuantizedTensor` 経路（ComfyUI が実際に呼ぶ経路）とビット単位で一致する。
- **H2（行の切り出し）**: VRAM 16GB mode が qkv をヘッド群（1,024 行）で切って計算する `forward_rows` は、fp8 では数学的に等価で最下位の桁だけが揺れうる。w4a8 ではカーネル自身が同じ切り方をするのでビット単位で一致する。
- **H3（既存の仕組み）**: meta で組む→量子化層の差し替え→`load_streaming(assign=True)`→`normalize_dtypes`→block swap の arena、という既存の流れは、fp8（F8 の重み＋0 次元 F32 の倍率）と w4a8（I8 `[N,K/2]`＋F8 `[N,K/G]`＋F32 `[N]`＋F32 `[16]`）の平らなテンソルをそのまま運べる。
- **H4（速度と VRAM）**: RTX 4070 Ti SUPER で、fp8（`scaled_mm`）の 1 ステップは int8 と同程度から 1 割遅い程度、w4a8（CUDA カーネル）は int8 と同程度。fc2 の bf16 への復元は 1 ステップの数%。VRAM の峰は int8 と同程度。Kijai の w4a8 は重みが小さいぶん下がりうるが、h3ErosMax は block swap の環がいちばん大きいブロック（int8 のブロック 0・1・47〜49）の大きさで作られる（`block_swap_prefetch.py:392`）ので int8 と同程度と見込む。
- **H5（遅い経路）**: comfy-kitchen の w4a8 の CUDA カーネルは、この GPU と 2 本のファイル（Kijai G=16、h3ErosMax G=16・8・4 の混在と符号帳）で eager の経路に落ちない。
- **H6（検出）**: LTX 側の判定器 `sft_quant_format.layer_schemes` は、メタデータ式の印を受けるが、G=8・4 と符号帳なしの w4a8 を拒否する（CPU だけで確認。製品の検出の設計の入力）。

## 3. スコープ外

製品コードの変更、RTX 30 系の実機（bf16 へ戻す経路は RTX 40 系で強制して動かす）、LoRA、テキストエンコーダ、快適上限の較正、操作パネルと Gradio、comfy-kitchen の版上げ（0.2.37 のままで数値は 0.2.41 と同じ。調査 F）。

## 4. 方法

### 4.1 台本と差し替え

`outputs/h3-fp8-w4a8-spike-2026-11-12/h3_quant_spike.py`（git 無視の `outputs/` 配下。`.venv-engine-h3` の python でリポジトリ直下からプロセス内で動かす。Inpainting のスパイク台本 `Docs/Outputs-archive/h3-inpaint-2026-11-11/h3_inpaint_spike.py` の `Log`・`PATHS`・`build_request`・`run_generation` を写す）。引数は `--dry-run`（GPU なし）・`--s1`・`--s2`・`--s3 <条件>`・`--s3-all`（条件ごとに子プロセス。VRAM の峰と差し替えを条件間で混ぜない）・`--s4`。

製品コードはいっさい触らず、**モジュール属性への代入（monkeypatch）**で差し替えます。`H3Pipeline.load`（`engine_h3/pipeline_h3.py:775`）と `_build_dit`（`:1538-1568`。`generate` がジョブごとに呼ぶ `:1796`）は次の名前を呼び出し時に解決するので、差し替えは **`pipe.load()` から `generate` の終わりまで**（子プロセスの実行全体）を context manager で包み、`finally` で必ず戻します。

1. `h3_format.inspect_h3_dit` → 試作の検査 `inspect_h3_dit_spike`。現行は fp8 を「I8 でない層に `weight_scale` がある」（`h3_format.py:249-259`）で、w4a8 を形の表（`:359-379`。packed の `[N,K/2]` が `[N,K]` と合わない）で拒否します。**w4a8 の重みも dtype は I8 なので、層の種類は重みの dtype ではなく量子化の印で分けます**。印はメタデータ式（`__metadata__._quantization_metadata`。Kijai はこれのみ）と層ごとの `comfy_quant` の両方を読み、両方あれば一致を確かめます（`full_precision_matrix_mult` は層ごとの印からだけ読む）。形式ごとにテンソルの dtype と形を厳密に検査し、形の表は w4a8 の重みを論理形 `[N,K]` に直した表で通し、int8 の層は元の `_quant_layers` に（fp8／w4a8 の層のテンソルを除いた表で）任せて従来の検査を変えません。fp8／w4a8 の層の仕様は試作専用の型（`SpikeSpec`）に持ちますが、`load()` が `quant` の全要素から `format`・`convrot`・`convrot_groupsize` を読む（`pipeline_h3.py:812-813`）ので、この 3 つの属性は必ず持たせます（fp8 は `convrot=False`・groupsize 0。w4a8 は True・256）。補助テンソル名（fp8: `input_scale`、w4a8: `weight_s_rel`・`weight_s_channel`・`weight_codebook`）は `unknown` に入れません（入ると `dit_key_map_for`〔`pipeline_h3.py:561-574`〕が読み飛ばす）。h3ErosMax の `adaln_basis`・`adaln_mean` は従来どおり `unknown` で捨てられ、警告に残ります（想定どおり。記録する）。`h3_format._shape`・`_DIT_KNOWN` は全体で差し替えません（`inspect_h3_te` も使うため）。
2. `engine_h3.quant_linear.swap_in_int8_linears`（`:497`）→ 包み。int8 の層は元の関数に任せ、fp8 の層は `H3Fp8Linear`、w4a8 の層は `H3W4A8Linear` を meta の上で組んで `setattr(parent, leaf, new)` します（元の関数と同じ手順・同じ検査）。テキストエンコーダは `text_encoder.py:76` が import 時に名前を束縛しているので影響しません。
3. `normalize_dtypes`（`engine_h3/dit.py:474-510`）は `isinstance(mod, H3Int8Linear)`（`:499`）だけを飛ばし、float8 は浮動小数点なので試作の層の重みと倍率を bf16 に潰します。試作の層は **`H3Int8Linear` を継承**（`__init__` は `nn.Module.__init__` を直接呼び、int8 の重みを作らない）して、この検査と `lora.attach` の検査（`lora.py:193`）を自然に通します。`normalize_dtypes` の後に dtype の監査を記録します。
4. `engine_h3.lowvram.block_forward` → 包み（fc2 の復元の cache の有効期間＝1 ブロックの前向き 1 回。`dit.py:372-374` が呼び出し時に名前を解決する）。
5. `comfy_kitchen.backends.cuda` の `eager_w4a8_int8_linear` と `_dequant_int4_grouped_to_int8` → 呼び出しを数える包み（遅い経路に落ちたかの検出。registry を通らない内側の直呼びなので、ここで数えるしかない）。
6. `load_streaming`（`engine_h3/sft_load.py:58`）は差し替えません。ファイルの dtype を保って `assign=True` で入れる（F8_E4M3→float8_e4m3fn、0 次元も可、buffer も対象）ので、試作の層が宣言する形と一致していれば届きます。`.comfy_quant` は既定で読み飛ばします。映像・音声 VAE も同じ関数を使うので触りません。

block swap の arena（`engine/transformer/block_swap_prefetch.py:284-301`・`:434-479`・`:644-653`）は `mod._parameters` と `mod._buffers` を列挙し、`reshape(-1).view(uint8)` で詰めて `dtype`・`shape` で戻します。平らなテンソルなら dtype を問わず、0 次元も可。試作の層の重みと倍率は `nn.Parameter(requires_grad=False)` か buffer で登録し、テンソルのサブクラスは使いません。

`require_cuda_int8()`（`quant_linear.py:322-360`）は comfy-kitchen の eager と triton を**全体で**切ります（`:357-358`）。fp8 の量子化・復元と w4a8 の関数も CUDA 版しか選べません。これは ComfyUI（cu130 では CUDA 版）と同じ条件です。

### 4.2 試作の層（ComfyUI の手順を写す。出典: 調査 F）

**`H3Fp8Linear`**（重み F8 `[N,K]` の Parameter、`weight_scale` F32 0 次元の buffer、`input_scale` F32 0 次元の buffer または無し、`full_precision` 真偽）

- 経路の選び方: `full_precision` の層、強制スイッチ（`fp8_force_dequant`）、または GPU の計算能力が 8.9 未満なら `dequant`。それ以外は `scaled`。`scaled` で `input_scale` が無い層は、**スパイクでは理由を出して止める**（この 3 本のファイルには無い。製品では ComfyUI の規則〔倍率 1.0〕に従うかを製品の計画で決める）。
- `scaled`: `xq = ck.quantize_per_tensor_fp8(x_2d_bf16, input_scale)` → `scaled_mm_v2(xq, w.t(), scale_a=input_scale, scale_b=weight_scale, bias=None, out_dtype=bf16)`。
- `dequant`: `w_bf16 = ck.dequantize_per_tensor_fp8(w, weight_scale, bf16)` → `F.linear(x, w_bf16)`。`input_scale` は読まない。
- `forward_rows(x, n0, n1, lora_xa=None)`: 既存の層と同じ署名（lowvram は `lora_xa=` を必ず渡す。`lowvram.py:150`・`:152`）。`lora_xa` が `None` でなければ止める。`n0` と `n1−n0` が 16 の倍数であることを確かめ、重みの行 `[n0, n1)` を切って同じ呼び方。`dequant` では切った行だけを復元する（cache しない。21 片の合計は全体 1 回ぶん）。
- `shares_input` は `scaled` のときだけ真。`quantize_input(x)` は `(fp8 の x, input_scale)` を返し、`forward_rows_q(xq, xs, n0, n1, lora_xa=None)` は `scale_a=xs` で同じ行列積（静的な倍率なので `forward_rows` とビット単位で同じ）。
- 継承元の `__init__` を呼ばないので、継承元の method が読む属性（`spec`・`bias`・`_lora_specs`）が無いまま呼ばれないように、`forward`・`forward_rows`・`forward_rows_q`・`shares_input`・`quantize_input`・`extra_repr` をすべて自前にし、`bias` は `None` で登録し、`spec` も持たせる。
- fc2 の復元の cache: `block_forward` の包みが有効にする辞書に `id(self)` で持ち、`data_ptr` が変わっていないことを確かめて再利用。VRAM 16GB mode ではトークンの塊ごとに fc2 が呼ばれるので、cache が無いと 1 ステップに約 500 回の復元（見積りで 0.3〜0.5 秒。情報）。切替可能にして S2 で実測する。cache の VRAM は fc2 で 147MiB、強制 `dequant` のときは fc1 も入って 441MiB。
- LoRA が付いていれば `NotImplementedError`（スパイクでは使わない）。

**`H3W4A8Linear`**（重み I8 `[N,K/2]` の Parameter、`weight_s_rel` F8 `[N,K/G]`・`weight_s_channel` F32 `[N]`・`weight_codebook` F32 `[16]` または無し、の buffer。`group_size` G、`convrot_groupsize` 256）

- `ck.w4a8_int8_linear(x_2d_bf16, weight, s_rel, s_channel, codebook, None, None, G, 256, bf16)` を 1 回。入力の量子化はカーネルの内側（ComfyUI と同じ）。
- `forward_rows(x, n0, n1, lora_xa=None)`: 3 つのテンソルを `[n0:n1]` で切って同じ呼び方（`n0` は 16 の倍数。`lora_xa` が `None` でなければ止める）。
- `shares_input` は偽（lowvram は `forward_rows` の枝に入る。入力の量子化は 1 ブロックで 21 回になるが数値は同じ。費用は S2 で測る）。`quantize_input`・`forward_rows_q` は呼ばれたら止める。`bias` は `None`、`spec` も持たせる（fp8 と同じ理由）。
- fc2 の SwiGLU は従来どおり bf16 の `silu(gate) * up` を先に作って渡す（0.2.41 の融合版とビット単位で同じ。調査 F）。

共通: `in_features`・`out_features`（int）。VRAM 16GB mode（`lowvram.py:147-187`）は qkv に `shares_input(h)` を無条件に呼び、真なら `quantize_input` と `forward_rows_q`、偽なら `forward_rows` を 1,024 行ずつ呼ぶ。out_proj は全体を 1 回、fc1・fc2 は `block.mlp(h2[r0:r1])`（トークンの塊 4,096 行以下）。

## 6. 危険と備え

- `F.scaled_mm`（torch 2.13）に 0 次元の倍率と列優先の重みの片を渡せるかは未確認。S1 で決まる（通らなければ理由を記録して止める）。
- `scaled_mm` の制約（K と切り出し行数が 16 の倍数・連続した 2 次元入力）: H3 の形は満たす。満たさなければ台本が理由を出して止まる。
- VRAM 16GB mode の上限と、⑤の cache 441MiB の併存で VRAM が足りなくなる可能性。足りなければ fc1 の cache を切って再実行。
- h3ErosMax の 20 層の int8（`per_row`）と BF16 の `adaln_t_table`: 既存の int8 の層と `normalize_dtypes` の F32 化で受かる見込み。受からなければ理由を記録して止める。
- S1 の入力は乱数で実際の活性化ではない。VRAM 16GB mode off の通し生成は行わない（層単位の S1 のみ）。いずれも限界として記録する。
- 試作の層は LoRA の対象外。スパイクでは LoRA を使わない。
