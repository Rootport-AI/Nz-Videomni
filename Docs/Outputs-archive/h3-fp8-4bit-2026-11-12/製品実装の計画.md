# MiniMax H3 の fp8・w4a8 対応 — 製品実装の計画（台帳 §1-283・第 1 段）

- 作成: 2026-11-12（監督）。状態: 承認待ち。独立の事実確認（19 件。重大 0・要修正 9・注記 10）を「過剰設計やスパゲッティ化の危険は無いか」「裏付けを得られるか」の 2 点で選別し、14 件を反映・1 件を棄却（サーバー側の WARNING ログ。H3 だけの例外になるため）・残りは確認済みの注記として扱った版
- 前の段: スパイク（記録簿 §210。dev `5516958`）。裁定は設計正本 裁定 101。

## 1. 背景と目的（Context）

CivitAI などで配布される MiniMax H3 の fp8（ComfyUI の `float8_e4m3fn`）と w4a8（`asym_w4a8_int8`）の safetensors を、`models\MiniMaxH3\Weights\` に置くだけで選んで生成できるようにします。目的は速度ではなく、**利用者が ComfyUI で使っているチェックポイントの忠実な再現**です（裁定 101 ②③）。ComfyUI が呼ぶ comfy-kitchen の関数を同じ引数で呼び、本製品だけに生じる不要な数値差を増やしません。

スパイクで確かめたこと（記録簿 §210）: 試作の層は ComfyUI の計算経路とビット単位で一致し、既存のローダー・block swap・VRAM 16GB mode は新しい 2 形式を手直しなしで運びました。この計画は、その試作を製品のコードに載せ、検出・テスト・操作パネルの不具合・文書を揃えるものです。

あわせて直すもの: 旧式の量子化の印（`__metadata__._quantization_metadata`）を読む（裁定 101 ⑤）。Settings のモデル読み込み欄がサーバーの返す具体的な理由（`detail`）を捨てている不具合（裁定 101 ⑥）。

## 2. 範囲

- **対象**: 枝刈り版の DiT。形式は int8 ConvRot（従来）・fp8（`float8_e4m3fn`。テンソルごとの `weight_scale`、任意の `input_scale`、`full_precision_matrix_mult` の印）・w4a8（`asym_w4a8_int8`。組の大きさ G は 4・8・16 など、`weight_codebook` は任意、ConvRot 256）。1 つのファイルに 3 形式が混在してよい（h3ErosMax は int8 と w4a8 が混在）。印は層ごとの `comfy_quant` とメタデータ式の両方を読む。
- **対象外**（裁定 101 ①）: 非枝刈り版、テキストエンコーダ（int8 ConvRot のまま。検査も int8 だけを受けるまま）、nvfp4・w4a4・w6a8、GGUF と BF16／FP16 のフルモデル、快適上限の線と較正、Gradio（モデル一覧は `GET /models` から取るので変更不要）、MCP（同上）、comfy-kitchen の版上げ。
- **RTX 20 系（Turing）**: fp8 は bf16 に戻す経路で動く。w4a8 は読み込みを理由つきで断る（カーネルが計算能力 8.0 以上を要る。裁定 101 ⑧）。

## 3. 設計（決めたこと）

### 3.1 検出（`h3_format.py`。torch 非依存。アプリ側の事前検査とエンジンの両方が使う）

- 量子化層の種類は**重みの dtype ではなく量子化の印で決める**（w4a8 の重みも I8 なので）。印は 2 つの置き場所から読み、**メタデータ式（`__metadata__._quantization_metadata` の `layers`。鍵はテンソル名そのまま）があればそれを採り、無い層だけ層ごとの `<層>.comfy_quant` を読む**（ComfyUI の `convert_old_quants` がメタデータで層ごとの印を上書きするのと同じ優先順位。LTX の判定器 `sft_quant_format._resolve_markers` も同じ）。両者の一致検査はしない（ComfyUI にも無い）。`full_precision_matrix_mult` は採った側の印から読む。`per_row` など知らない鍵は無視する。メタデータの JSON の読み出しは `sft_quant_format` の既存の関数（`_metadata_layers`）を公開名にして共用する（振る舞いは変えない）。印の無い I8・F8 の重みは断る（従来の「`comfy_quant` 無し」の規則を F8 にも広げる）。浮動小数点の重みに `weight_scale` だけがある層を断る従来の検査は残す。
- 順序: 印を先に読み、その結果で w4a8 の重みを論理形 `[N,K]` に直してから形の表を通す（形の表は現状 `_quant_layers` より前に走るので、順序を入れ替える）。
- `QuantSpec` を広げる（frozen のまま。既存の 3 欄 `format`・`convrot`・`convrot_groupsize` は位置も名前も変えない）: `group_size: int | None = None`、`full_precision: bool = False`、`has_input_scale: bool = False`、`has_codebook: bool = False`。`pipeline_h3.py:812-813` の要約と既存テスト `QuantSpec("int8_tensorwise", False, 256)` はそのまま通る。
- 形式ごとのテンソルの検査（dtype と形を厳密に）: int8 は従来どおり（I8 `[N,K]`・F32 `[N,1]` の `weight_scale`）。fp8 は F8_E4M3 `[N,K]`・F32 0 次元の `weight_scale`・任意の F32 0 次元 `input_scale`。w4a8 は I8 `[N,K/2]`・F8_E4M3 `[N,K/G]` の `weight_s_rel`・F32 `[N]` の `weight_s_channel`・任意の F32 `[16]` の `weight_codebook`。`*_correction` がある層は断る（非対称の変種は対象外）。`convrot` が偽か `convrot_groupsize` が 256 以外の w4a8 は断る。組の大きさの条件は comfy-kitchen の `AsymW4A8Int8Layout.Params`（`tensor/w4a8_int8.py:160-171`）を**そのまま写す**: `G >= 4`、`K % G == 0`、`K % 16 == 0`、`K % 256 == 0`、（`16 % G == 0` または `G % 16 == 0`）。
- 形の表（`h3_format.py:359-379`）は、w4a8 の重みを論理形 `[N,K]` に直して通す。`parse_comfy_quant` の形式の検査（現状 int8 だけ）には呼び出し側の「受ける形式」を渡す。
- 補助テンソル名（`input_scale`・`weight_s_rel`・`weight_s_channel`・`weight_codebook`）を既知の名前に入れ、`unknown` に落とさない。
- 受ける形式は呼び出し側が指定する: `inspect_h3_dit` は 3 形式、`inspect_h3_te` は int8 だけ（テキストエンコーダは対象外のまま）。
- `sft_quant_format.py` の判定の規則は変えない（上のメタデータ読み出しの関数を公開名にするだけ）。理由: LTX の判定器は LTX の実行部（G=16 と符号帳を前提にした復元。`engine/sft_quant/dequant.py:43-45`・`:111-123`）と対で、G≠16 や符号帳なしを受けるよう広げると LTX 側で実行時に壊れる。H3 の検出は `h3_format` の中で閉じる（`read_header` は従来どおり共用）。
- `services/weight_class.py`（快適上限の種別）は変えない（H3 は None のまま。裁定 101 ①）。

### 3.2 層（`engine_h3/`）

- 共通の土台 `H3QuantLinear`（`nn.Module`）を `quant_linear.py` に置き、`H3Int8Linear` はこれを継承する。土台は**最小限**にする: 中身は no-op の `dequant_cache()` 文脈だけで、抽象の「契約」の method は置かない（3 つのクラスが同じ名前の method を持つことは、VRAM 16GB mode と LoRA が duck typing で使う事実とテストで押さえる）。土台を置く理由は、`dit.normalize_dtypes`（`dit.py:499`）と `lora.attach`（`lora.py:193`）の `isinstance` を 1 つの名前で書くため（3 クラスのタプルにすると、新しい 2 つの module が `quant_linear` を import する以上、循環 import になる）。層が持つ名前: `in_features`・`out_features`・`spec`・`bias`（H3 の量子化層は常に `None`。差し替え先の `nn.Linear` にバイアスがあれば断る）、`forward(x)`、`forward_rows(x, n0, n1, lora_xa=None)`、`shares_input(x)`、`quantize_input(x)`、`forward_rows_q(xq, xs, n0, n1, lora_xa=None)`、`extra_repr`。VRAM 16GB mode（`lowvram.py:147-187`）は変えない。新しい module は comfy-kitchen を `quant_linear._ck()` の module 属性経由で呼ぶ（既存テストの偽カーネルがそこを差し替えるため）。
- `H3Fp8Linear`（新規 `engine_h3/fp8_linear.py`）: 重み F8 `[N,K]` の Parameter、`weight_scale` F32 0 次元の buffer、`input_scale` F32 0 次元の buffer または `None`。
  - 経路は読み込み時に 1 回決める（`fp8_mode`。3.3）。`scaled`: `ck.quantize_per_tensor_fp8(x_2d, input_scale)` → `comfy_kitchen.scaled_mm_v2.scaled_mm_v2(xq, w.t(), scale_a=input_scale, scale_b=weight_scale, bias=None, out_dtype=bf16)`。`dequant`: `ck.dequantize_per_tensor_fp8(w, weight_scale, bf16)` → `F.linear`。`full_precision_matrix_mult` の層は常に `dequant`。
  - `input_scale` の無い層を `scaled` で計算するとき: **ComfyUI と同じく倍率 1.0** を使う（裁定 101 ⑩ の決定。忠実さの原則）。ComfyUI と同じく `torch.ones((), dtype=float32, device=x.device)` を呼び出しのたびに作る（buffer にはしない。CUDA の制約は fp32 の倍率が同じデバイスにあること）。読み込み時に該当する層の数を 1 回だけ警告に出す。
  - `forward_rows`: `n0` と `n1−n0` が 16 の倍数であることを確かめる（`F.scaled_mm` の制約。ヘッド群 1,024 行は満たす）。`shares_input` は `scaled` のときだけ真で、`quantize_input` は `(fp8 の x, input_scale)` を返す。LoRA は int8 と同じく `lora.apply` を自分で足す（`forward_rows`・`forward_rows_q`）。`forward` は hook（`lora.attach` が掛ける）。
  - bf16 に戻した重みの cache: **`lowvram.block_forward` の MLP のトークンの塊のループを `with mlp.fc1.dequant_cache(), mlp.fc2.dequant_cache():` 相当の文脈で包む**（土台に no-op の既定を持たせ、fp8 の層だけ実装する）。文脈の外では cache を持たない（block swap が同じ番地を別のブロックに使い回すため、`data_ptr` で持ち越す設計は採らない）。通常経路（VRAM 16GB mode off）は fc2 が 1 ブロック 1 回なので cache 不要。
- `H3W4A8Linear`（新規 `engine_h3/w4a8_linear.py`）: 重み I8 `[N,K/2]` の Parameter、`weight_s_rel` F8・`weight_s_channel` F32・`weight_codebook` F32 または `None` の buffer、`group_size`。`forward`／`forward_rows` は `ck.w4a8_int8_linear(x_2d, weight[n0:n1], s_rel[n0:n1], s_channel[n0:n1], codebook, None, None, G, 256, bf16)`。`shares_input` は偽（入力の量子化はカーネルの中。VRAM 16GB mode では qkv の片ごとに量子化し直すぶん約 1 割遅い。受け入れ、改善は台帳 §3 へ）。LoRA は同上。
- `swap_in_int8_linears`（名前はそのまま。`text_encoder.py:76` が import 時に束縛する）は `spec.format` で 3 クラスを選ぶ。キーワード引数 `fp8_mode`（既定あり。テキストエンコーダの呼び出し `text_encoder.py:644` は無変更）を足し、`_build_dit` が読み込み時に決めた値を渡す。
- `normalize_dtypes` は `H3QuantLinear` を飛ばす（fp8 の重み・F8 の `weight_s_rel`・F32 の倍率が bf16 に潰れない）。`adaln_t_table` の BF16 → F32 は従来の動きで正しい。
- 読み込み（`sft_load.load_streaming`）は変えない。鍵の写像 `dit_key_map_for` も変えない（`unknown` の扱いが変わるだけ）。

### 3.3 読み込み時の判定（`pipeline_h3.py` と `quant_linear.py`）

- `require_cuda_int8()` を `require_cuda_quant(formats)` に広げる: **`int8_linear` は常に要る**（テキストエンコーダが int8 のため）。加えて fp8 なら `quantize_per_tensor_fp8`・`dequantize_per_tensor_fp8`（`scaled` のときは `has_scaled_mm_v2()`）、w4a8 なら `w4a8_int8_linear` が CUDA backend の能力に含まれることを確かめ、満たさなければ理由を出して断る（従来どおり eager と triton は切る）。注: `list_backends` の能力は GPU の世代に関係なく登録名を返すので、世代の検査は別に行う（次項）。w4a8 の CUDA カーネルは内部で eager の実装に黙って落ちることがある（ComfyUI も同じ）。これは忠実さの範囲内で、速度の危険として設計正本 §5 に書く（検出の仕組みは作らない）。
- `fp8_mode`: `torch.cuda.get_device_capability(self.device) >= (8, 9)` なら `scaled`、未満なら `dequant`（ComfyUI の `supports_fp8_compute` と同じ）。w4a8 の層があり計算能力が 8.0 未満なら断る。結果は**読み込みの記録**（`build_report["dit"]`。`int8_layers` を `quant_layers` に改名し、形式ごとの層の数と `fp8_mode` を足す。消費者は自己検査 `worker.py:1212` と仕様書）に残す。`done` の `h3.quant_backends` は backend ごとの能力の表なので、そこには能力の旗（`w4a8_int8_linear`・`quantize_per_tensor_fp8`）だけを足す（加算のみ。`chain_h3.py:746` も同じ関数を使うので自動で揃う）。
- `_build_dit` の流れ（meta で組む → 差し替え → `load_streaming` → `normalize_dtypes` → block swap）は変えない。

### 3.4 Settings の理由文（操作パネル。`AviUtl2-Plugin/Nz-Videomni-frontend-AviUtl2/webui/src/`）

- `shell/useModels.ts:172-177`: 失敗の状態に `detail` と `httpStatus` を持たせる（`BackendApiError`）。
- `shell/ModelsPanel.tsx:111-115`: **422 のときだけ** `detail`（無ければ従来の定型文）を `loadFailed(...)` に渡す。ヘッダーのベースモデル欄 `useBaseModels.ts:229` と同じ条件（他の失敗は技術的な英文を含みうるので従来どおり定型文）。文言の資源は変えない。
- サーバー側のログは足さない（レビューの指摘を採用: H3 だけの例外になり、裁定 101 ⑥ は Settings の表示だけを求めている）。

### 3.5 変えないもの

VRAM 16GB mode の定数と予算の決め方（上限は実測から決まる。w4a8 の一時メモリは大きいがスパイクの山は int8 以下で収まった。§6.5 に注記だけ）、block swap、Gradio・MCP、マニフェスト、快適上限、LoRA の方式（出力側の差分。裁定 101 ⑨）。

## 7. 危険と備え

- `H3QuantLinear` の導入で `H3Int8Linear` の `isinstance` に依存する箇所（`dit.py:499`・`lora.py:193`・テストの `spec` 比較）を見落とすと int8 の回帰になる。機械の門 G1 と既存テストで押さえる。
- `swap_in_int8_linears` の名前を変えないのは `text_encoder.py` の import 時の束縛のため。振り分けだけ足す。
- `F.scaled_mm` の制約（16 の倍数）はヘッド群 1,024 行で満たすが、将来 `VRAM16_HEAD_GROUP` を変えるときの罠。`forward_rows` の検査で止まる。
- cache の有効期間を `lowvram.block_forward` の MLP ループに限るのは、block swap が番地を使い回すため。`data_ptr` だけで持ち越さない。
- `input_scale` 無しの層の倍率 1.0 は ComfyUI と同じ動きだが、入力が 448 を超えると飽和する。公式の fp8 には該当する層が無い（fc2 は常に `dequant`）。警告で数を出す。
- エンジン venv の pytest は GPU を起こしうる（`H3_GPU_TESTS` 既定 off を守る。GPU の空きを先に確かめる）。
- 印の中の知らない鍵（h3ErosMax の w4a8 ファイルの int8 層にある `per_row: true` など）は無視でよい（comfy-kitchen も ComfyUI も読まない）。旧式の印の 2 本（beta5 int8）の印は `format`・`convrot`・`convrot_groupsize` だけ。
