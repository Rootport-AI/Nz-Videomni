## A. §1-270

### A-1 形と `_linear_f32`

- 【コード】`_linear_f32` は `F.linear(x.to(float32), layer.weight.to(float32), b)` です。bias があれば `layer.bias.to(float32)` を渡します（`engine_h3/dit.py:418-421`）。matmul ではなく F.linear で、bias つきの 2 次元の入力です。重みは `normalize_dtypes` で f32 にそろえてあるので、`.to` は何もしません（`dit.py:471-483`）。
- 【コード】`video_patch_proj = nn.Linear(video_patch_dim, hidden, bias=True, dtype=float32)`（`dit.py:448`）。`video_patch_dim = latents_dim·1·2·2`（`dit.py:442`）、`latents_dim`＝24（`h3_format.py:154`）なので、**K＝96・N＝5376**・bias ありです。
- 【コード】`final_layer.video_out = nn.Linear(5376, 96, bias=True, f32)`、`audio_out = nn.Linear(5376, 32, bias=True, f32)` です（`dit.py:406-407`、`audio_latents_dim`＝32 は `h3_format.py:155`）。最終層は **K＝5376・N＝96／32** です。
- 【コード】vram16 の最終層は、`buf = torch.empty((n, 5376), f32)` に行の塊ごとに `copy_` し、`_linear_f32(buf, out)` を 1 回呼びます（`engine_h3/lowvram.py:199-206`）。off の経路も同じ `_linear_f32` を M＝Nv で 1 回呼びます（`dit.py:589-594`）。つまり on と off で、行列積の形は今も同じです。
- 【コード】埋め込みは `parts` に f32 の射影→bf16 を並べ、`torch.cat` で [S,5376] を作ります（`dit.py:543-552`）。映像の射影 `_linear_f32(video_rows, video_patch_proj)`（[Nv,5376] f32）、その bf16（[Nv,5376]）、cat の出力（[S,5376]）の 3 本が同時に生きる瞬間があります。

### A-2 「最終層の行列積を行の方向には分けない」とした理由

- 【記録】設計正本 §6.5 #6 は理由を書いていません（`Docs/MINIMAX_H3_DESIGN.md` 724 行付近）。
- 【記録】計画（`Docs/Outputs-archive/h3-vram16-2026-10-18/PLAN_vram16.md` 32 行）の表は「`_linear_f32` を 1 回（行列積は分割しない）」で、等価性の見込みの列は「ビット一致」です。**分けてビットが変わったという実測は、§169.3・計画・E1 の報告・レビューのどこにも見つかりませんでした。** 計画の段階で「形を変えないから一致する」側を選んだ、保守的な判断と読めます【推定】。
- 【記録】同じ考え方は LoRA にもあります。「ビット一致は、測って合わせるより、形を揃える設計で作る」（`Docs/VERIFICATION_LOG.md` §176 の教訓、18400 行）。off と on の両方で f32 の行列積を 4096 行 × 1024 列の塊にそろえています（`engine_h3/lora.py:30-35`、`MINIMAX_H3_DESIGN.md` 827 行）。
- 【記録】形が変わるとビットが変わった実例は 2 つあります。
  - LTX のテキストエンコーダーの集約射影: 出力の幅を刻むと、cuBLAS〔NVIDIA の行列積のライブラリ〕が実装を選び直してビットが変わった（§69.19 の 2、6156 行）。これは N の方向の話です。
  - H3 のテキストエンコーダーの注意（bf16 の bmm）: 塊の高さ M が 16 行以下では不一致、17 行以上では一致した（§182.6 の T4・T4b、19122〜19138 行）。
- 【記録】int8 の行列積は、行で分けても一致しています（GPU テスト `test_gpu_forward_of_row_chunks_equals_forward`、`tests/test_h3_engine.py:2280-2291`）。ただし int8 は整数で足すので、足す順序に依存しません。**f32 の行列積を行で分けて一致を確かめた記録はありません。**
- 【コード】git の履歴は、作業ツリーを変えない範囲で十分に追えませんでした（`git log -S` は流していません）。docstring の「the matmul is not split」（`lowvram.py:192-194`）は弾 A の `69e62a9` のときからあると見られます【推定】。

### A-3 cuBLAS の f32 GEMM〔行列同士の掛け算〕は、M だけを変えてもビット一致するか

- 【Web】cuBLAS の文書の保証は「同じツールキットの版・同じアーキテクチャ・同じ SM 数なら、毎回同じビット」までです。問題の大きさが違うときの一致には触れていません。split-K を選んだときも、部分和は「決定的に」足すと書かれています。https://docs.nvidia.com/cuda/cublas/index.html （§2.1.4 Results reproducibility、§2.1.10）
- 【Web】PyTorch の数値精度の注記にも「切り出した張量への演算が、結果の切り出しと同じになる保証はない」とあります。https://docs.pytorch.org/docs/2.13/notes/numerical_accuracy.html （Batched computations or slice computations）
- 【Web】TF32: torch 1.12 以降、行列積の `allow_tf32` の既定は False です。https://docs.pytorch.org/docs/2.13/notes/cuda.html
- 【コード】この venv の値は `allow_tf32=False`・`float32_matmul_precision='highest'`・`fp32_precision='none'`・`are_deterministic_algorithms_enabled()=False` でした（印字のみ）。製品はロードで `require_fp32_matmul()` を呼び、TF32 なら止めます（`engine_h3/pipeline_h3.py:335-355`・`655`）。
- 【コード】製品の `deterministic` が設定するのは cuDNN の `deterministic=True`・`benchmark=False` だけです（`pipeline_h3.py:657-659`、docstring 154-160）。`torch.use_deterministic_algorithms` も `CUBLAS_WORKSPACE_CONFIG` も、リポジトリのどこでも設定していません（grep で 0 件）。決定論の設定は「同じ形なら毎回同じ」を強めるもので、形が違うときの一致は約束しません。
- 【推定】埋め込みの射影（K＝96）は K が小さいので split-K は選ばれにくいと見られます。それでも M によって別のタイルの核が選ばれ、内積の足し方が変わる可能性は残ります。最終層（K＝5376・N＝96）は、M＝4096 だと出力のタイルが少なく（例えば 128×128 の核なら 32 枚、4070 Ti SUPER の SM は 66 基）、split-K が選ばれる可能性が高いと見られます。どちらも実測でしか決まりません（未決 1）。

### A-4 候補の評価

前提の事実（【記録】`MEM_HISTORY_REPORT.md` §3 の時系列）:
- ステップ 0 の最終層の `buf` が入らず、上限に当たって再試行し、丸ごと空いた 1,726・1,726・2,302MiB を返して B（3,432MiB）を作った（#173487〜#173491）。
- `buf` を解放すると B は丸ごと空く（#174109）。**ステップの境目（#174159）では A も B も丸ごと空き**で、予約は 10,734MiB だった。
- ステップ 1 では A と B の両方に S·U が 1 本ずつ入り、穴が 1,706.9MiB ずつ残り、ブロック 0 の `h2` で OOM になった。

#### (a) 埋め込みの射影を行の塊ごとに計算し、[S,5376] bf16 の受け皿へ直接書く

- f32 の山: [Nv,5376] f32 が消え、塊の [4096,5376] f32（84MiB）になります。穴: A の起点が消えます。`torch.cat` の写しも消えます。
- 数値: `video_patch_proj`（cond・ref_video も同じ重み）の f32 の行列積が M＝Nv から M≤4096 に変わります。off の経路は変えられない（裁定 45）ので、on と off の一致は cuBLAS が M に依存しないことに頼ります。音声の射影（K＝32）も分けるなら同じです。危険は中くらいで、実測が要ります。
- メモリと時間: 境目の山が「f32 2·Nv·U＋bf16 Nv·U＋cat S·U」から「受け皿 S·U＋84MiB」に下がります。行列積は 41 回になりますが、K＝96 なので時間の差は誤差と見られます【推定】。
- 相互作用: 受け皿をそのまま `tokens_box` に入れればよく、ブロック 0 の後に解放される性質は変わりません。block swap の受け皿・keep_resident・連結は、埋め込みに関わりません（連結はクリップごとに `_denoise` を呼ぶだけ。`engine_h3/chain_h3.py:312`）。
- 規模: `lowvram.py` に関数を 1 つ、`dit.embed_rows` の先頭に vram16 の分岐（`embed_rows` は今は vram16 を受け取らないので、引数か、`_denoise` 側の呼び分けが要ります）。約 20 行です。

#### (b) ステップの境目で `torch.cuda.empty_cache()` を 1 回呼ぶ

- 置き場所の案: `_denoise` のステップのループの終わり（`del v_video_rows, …` の後。`pipeline_h3.py:1572-1573`）、または次のステップの `embed_rows` の直前。vram16 のときだけ呼びます。
- 追跡: 境目では A も B も丸ごと空きなので、`empty_cache` で両方 GPU に返ります。予約は 10,734 から約 3,870MiB に下がります。次のステップの埋め込みは、ステップ 0 と同じ手順で A' を新しく作ります（#16683 と同じ）。ブロック 0 もステップ 0 と同じ確保をし（`o` が入らないところで再試行が起きるのも同じ）、山はステップ 0 と同じ 13,056MiB になる見込みです。最終層では再試行して B を作り直し、また境目で返します。つまり**毎ステップがステップ 0 の並びを繰り返す**と【推定】します。
- 効果の限界: ステップ 0 の並びにも A の穴（x の後ろの 1,707MiB）と TE の段のセグメントの空き（1,349MiB）があります。(b) は「ステップ 1 で B が 2,302MiB の役を奪う」1,130MiB の差を消すだけです。境界は「ステップ 0 の山が上限に収まるか」に移ります。
- 危うさ: 境目で A と B が丸ごと空くのは、小さな長命の張量（映像の状態 [1,24,T',H,W] f32＝61MiB、`euler_step` が毎ステップ新しく作る。`v_video_rows` など）が、たまたま TE の段のセグメントの穴に入ったからです（MEM_HISTORY §2.3 では映像の状態は TE のセグメントの中）。§1-271 を直して TE のセグメントが無くなると、これらが B の先頭に入って B が丸ごと空かなくなり、(b) が効かなくなる恐れがあります【推定】。(b) と §1-271 の修正は、組み合わせて測る必要があります（未決 3）。
- 数値: なし（割り当てだけの操作）。
- 時間: `empty_cache` は中で同期し、`cudaFree` と次の `cudaMalloc` を数回（合わせて数 GB）行います。1 ステップ 200 秒級に対して誤差と見られますが【推定】、小さい画角（1 ステップ数秒）で測る価値はあります。
- 相互作用: block swap の受け皿は確保済みのまま（`hold_arenas`）なので返りません（【コード】`engine/transformer/block_swap_prefetch.py:43-48`。`release_blocks` は、分割されていないブロック＝丸ごと空いたセグメントだけを返す）。転送の流れ〔stream〕の解放待ちは、`empty_cache` が `synchronize_and_free_events` で待ちます（【Web】下の A-5）。tokens_box・keep_resident・連結との関わりはありません。
- 文書: 設計正本 §6.5 の「降ろした後に `empty_cache` は呼ばない」（token_refiner の退避の規則）と、`num_alloc_retries` の読み方の注記を書き直す必要があります。境目の `empty_cache` で token_refiner の跡のキャッシュも返るためです。
- 規模: 2〜3 行です。

#### (c) 最終層の行列積も行の塊ごとに計算する

- f32 の山: `buf` が塊の 84MiB になり、B の起点が消えます。
- 数値: `video_out`（K＝5376・N＝96）と `audio_out`（N＝32）の M が Nv から 4096 前後に変わります。A-3 のとおり split-K に入る可能性が高く、危険は高いです【推定】。出力は [Nv,96] f32 で小さいので、メモリの得は `buf` の分だけです。
- 規模: `final_rows_chunked` の `head` を書き換える約 10 行です。設計正本 §6.5 #6 の変更になります。

#### (d) f32 の受け皿を [S,5376]（2 本の S·U が入る大きさ）で確保し、先頭 Nv 行だけを使う

- `buf`: `torch.empty((S,5376), f32)[:Nv]` は連続したビューなので、`_linear_f32` の M は Nv のまま、ビットは変わらない見込みです【推定】。セグメントが 2·S·U（2MiB 単位に切り上げ）になり、S·U がちょうど 2 本入ります。
- 埋め込みの f32: F.linear には `out=` がありません。2 次元の入力で bias があると、ATen の linear は `addmm(bias, x, W.t())` と同じ計算に入るので、`torch.addmm(..., out=ビュー)` で同じ値になるはずですが【推定】、「同じ関数を呼ぶ」という §6.5 の置き方から外れます。
- 危うさ: 合わせ込みです。2MiB の切り上げ、best-fit〔要求以上で最も小さい空きを選ぶ規則〕、ほかの張量（`o` 1.333·S·U、量子化した入力 0.667·S·U）がそのセグメントにどう入るかに頼ります。参照や text の行が多い（S−Nv が大きい）と、境目の山が (S−Nv)·2U 増えます（i1080_243_p9 の形なら約 770MiB）。割り当て器の版が変わると前提が崩れます。
- 規模: 約 10 行です。

#### (e1) 埋め込みで受け皿を先に確保し、f32 は全行のまま書き、終わったら `empty_cache`

- 手順: `out = torch.empty((S,5376), bf16)` を先に取り、各部分を `out[r0:r1].copy_(_linear_f32(rows, proj))` で書きます（cat の写しが消えます）。f32 の一時張量は out と別のセグメントに入り、埋め込みの後には丸ごと空きになります。そこで `empty_cache` を呼んで返すと、x がちょうどの大きさのセグメントに収まり、A の穴が消える見込みです【推定】。
- 数値: 行列積の形（M＝Nv）は変わりません。違いは f32→bf16 の丸めが `.to(bf16)` から `copy_` に変わる点だけです。`.to` も中で `_to_copy`→`copy_` を通るので、同じ変換の核になるはずですが【推定】、`torch.equal` のテストで固定すべきです（CPU でも GPU でも安く書けます）。
- メモリと時間: 境目の山は「S·U＋2·Nv·U」に下がります（今は 2·Nv·U＋Nv·U＋S·U）。`empty_cache` が 1 ステップに 1 回増えます（(b) と合わせると 2 回）。
- 相互作用: (a) と同じです。(b) と組むと、境目で返し → 受け皿（新しい 1,726MiB）→ f32（新しい 3,432MiB）→ 返す、の順になる見込みです【推定】。
- 規模: `lowvram.py` に関数を 1 つ、分岐が 1 つで、約 15 行です。

#### (e2) f32 の 2 本を専用の MemPool に置き、使い終わったら置き場ごと返す

- 【コード】この venv の torch には `torch.cuda.MemPool`・`use_mem_pool` があります（`.venv-engine-h3/Lib/site-packages/torch/cuda/memory.py:63-64`）。【Web】文書には「どの張量もプールを参照しなくなると、プールの削除時に中で `empty_cache` が呼ばれ、全メモリが返る」とあります。https://docs.pytorch.org/docs/2.13/notes/cuda.html
- 期待: 既定のプールの張量が f32 の跡の穴に入らなくなります。
- 不明点: Windows での動作、上限（`allowed_memory_maximum`）との関係、block swap の受け皿との関係はどれも確かめていません。仕組みが (b)・(e1) より重いです。

#### 各候補の後に境界を決めるもの（概算）

### B-1 cuBLAS の作業領域の扱い（torch 2.13）

### B-2 TE の段の最初の行列積

- 【コード】`modeling_qwen3_vl.py:367` は `.venv-engine-h3/Lib/site-packages/transformers/models/qwen3_vl/modeling_qwen3_vl.py`（transformers 5.14.1）の `Qwen3VLTextRotaryEmbedding.forward` の `freqs = (inv_freq_expanded.float() @ position_ids_expanded.float())` です。f32 の小さな bmm で、int8 ConvRot の経路ではありません（autocast は切ってあります）。

- 【コード】ワーカーは 1 本の主スレッドで命令を順に処理します（`engine_h3/worker.py:695-740`。`_do_load`／`_do_generate` を同じループで呼ぶ）。ロードで行う GPU の検査は comfy-kitchen のバックエンドの確認で（`quant_linear.py:322-` の `require_cuda_int8`）、行列積は走らせていないと読めます【推定】。履歴でも最初の行列積は TE の段の #16 でした（【記録】MEM_HISTORY §2.3）。
- 【コード】block swap の別の流れ（`torch.cuda.stream(self._xfer)`、`engine/transformer/block_swap_prefetch.py:601`）は写しだけで、行列積はしません。作業領域は「主スレッドのハンドル×既定の流れ」の 1 組だけと見られます【推定】。
- 【推定】製品のワーカーは同じプロセスで複数のジョブを流すので、作業領域は最初のジョブの TE の段の表のセグメントに置かれ、プロセスが終わるまでそこに残ります。2 本目以降のジョブでは、表は新しいセグメントに入り（古いセグメントの空き 1,475.9MiB は表の 1,483.8MiB より小さい）、古い 1,484MiB は空きのまま予約に残り続けます。

### B-4 候補の評価

#### (a) `release()` で `_cuda_clearCublasWorkspaces()` を呼んでから `empty_cache`

- 効果: 作業領域が割り当て器へ戻り、表のセグメントは丸ごと空いて返ります。
- 落とし穴: 次の行列積（参照つきなら参照の符号化の VAE の中、無ければノイズ除去の `refine_text`）で、作業領域が best-fit で取り直されます。そのとき空いている大きな穴（VAE のセグメント、DiT のブロック以外の 148MiB のセグメントなど）のどれかに入り、そのセグメントが返らなくなります【推定】。問題が別の場所に移るだけになりうるので、単独では勧めにくいです。
- 数値: なし。規模: 1 行です。

#### (b) ワーカーの読み込みの最初（GPU に何も無いうち）に小さな行列積を 1 回行う

- 効果: 作業領域（8.1MiB。1〜10MiB の範囲）は、空の割り当て器から新しい 20MiB のセグメントの先頭を取ります（A-5 の `get_allocation_size`）。以後プロセスが終わるまでそこに残り、TE の段の表のセグメントは段の終わりに丸ごと返ります。
- 代償: 20MiB が予約に常に残ります（うち約 11.9MiB は、1〜10MiB の確保の置き場として使えます）。
- 数値: なし。作業領域の場所は計算の値に効かず、大きさは変わりません【推定】。
- 条件: 後の行列積と同じスレッド・同じ流れで行うこと（主スレッド・既定の流れ。B-2）。(ハンドル, 流れ) の新しい組ができると、そのときに別の作業領域が取られます。
- 相互作用: 連結・keep_resident・複数のジョブのどれでも同じ場所に残ります。
- 規模: `_do_load` か `H3Pipeline.load` の先頭に 3〜5 行です。

#### (c) `_encode` で `hidden` を CPU へ移してから `te.release()`（`_denoise` の `.to(dev)` はそのまま）

- 効果: TE の段のセグメントに `text_hidden` が残らなくなります。`refine_text` の直前の GPU の写しは、`refine_text` を抜けると捨てられる一時張量です。ノイズ除去の間の割り当ても 1 行 10,240 バイト減ります（【記録】§194.12 の 4）。
- 数値: なし（bf16 の CPU との往復は厳密に同じ値）。
- 代償: 最大で約 190MB の往復（画像 9 枚の 18,462 行で 180MiB）。数十ミリ秒の見込みです【推定】。
- 相互作用: 連結も `_encode` を通るので同じように効きます。`text_tags` も CPU にしてよいです（`.to(dev)` で使われている）。CPU テストで `_encode` の戻り値の device を確かめているものは、grep では見つかりませんでした。
- 規模: `pipeline_h3.py` の `_encode` の `try` の中に 1〜2 行です（`te.release()` より前に移すのが要点）。

#### (d) TE の段の終わりに CPU へ移し、`empty_cache` の後に GPU へ戻す

- 効果: ② は消えますが、戻した張量は新しい小さなセグメント（または別の穴）でノイズ除去の終わりまで残ります。(c) より得が小さく、行も多いです。

#### (e) TE の段の終わりに「作業領域を消す → `empty_cache` → 小さな行列積」

- 効果: (b) と同じ置き方を、ジョブごとに作り直します。前のジョブの履歴に左右されません。
- 注意: その瞬間に大きな空きが残っていると、作業領域がそこに入ります。(c) で `text_hidden` を先に CPU へ移しておく必要があります。(b) で足りるなら不要です。

1. **f32 の行列積を行で分けたときのビット一致**: `video_patch_proj`（K＝96・N＝5376）を M＝Nv と M≤4096 で計算した結果、`video_out`（K＝5376・N＝96）・`audio_out`（N＝32）を同じく分けた結果が `torch.equal` になるか。4070 Ti SUPER で、製品の Nv（167,280・8,880 など）と端数の塊の高さで測る必要があります。(a)・(c) を選ぶときだけ要ります。
2. **f32→bf16 を `copy_` で書いても `.to(bf16)` と同じビットになるか**（(e1)）。同じ核を通るはずですが、`torch.equal` で 1 本確かめる必要があります。
3. **(b) の後の並び**: 境目で A と B が丸ごと空くのは、映像の状態（61MiB）などの小さな長命の張量が TE の段のセグメントの穴に入っていたからです。§1-271 を直すとそれらの入り先が変わり、B の先頭に入れば (b) が効かなくなります。(b) 単独・§1-271 単独・両方で、ステップの境目のスナップショットを取る必要があります。
4. **`empty_cache` の時間の代償**: 1 ステップ 1〜2 回の `cudaFree`／`cudaMalloc`（数 GB）と同期が、小さい画角（1 ステップ数秒）でどれだけ効くか。
5. **(b)（作業領域の先取り）の後に、TE の段の表のセグメントが本当に返るか**。表の跡にほかの何か（rotary の表、TE の途中の小さな張量）が残っていないかは、履歴でしか分かりません。
6. **ジョブの合間の割り当て 8,650,752 バイト**（§166.6）が 8,519,680 より 128KiB 多い理由。cuBLAS の作業領域が 2 つあるのか、別の小さな常駐があるのか。
7. **Windows の torch 2.13 で expandable segments が本当に使えないか**（警告が出るか）。§3-272 の範囲です。
8. **MemPool（(e2)）が Windows・上限つきで期待どおり動くか**。
9. **直した後の境界の量**: 穴を消すと境界がどこまで上がるか。A-4 の約 24 万行は断片化 0 の上限の割り算で、実際の値は再較正でしか決まりません（Single の §17 と参照つきの §18、マーカー §1-119 に響きます）。

## 設計で決める必要があること（監督とオーナーへ）

- (b) は §6.5 の「降ろした後に `empty_cache` は呼ばない」の規則と、`num_alloc_retries` の読み方の注記を書き換えることになります。規則の意図（退避の後に呼ばない理由）は §169.7 の 2 にも書かれておらず、理由が無いのか、書き漏らしなのかは記録から決まりませんでした。

- §1-271 の (b) は H3 のワーカー全体（VRAM 16GB mode の off も）の割り当てに効きます。off の経路を変えない約束（裁定 45）は数値についての約束と読めますが、割り当ての並びも含むかは確かめていません。
