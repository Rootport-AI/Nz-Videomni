## 1. 既存の較正の模型（int8 ConvRot の重み）

### 1.1 上限（cap）
- cap は固定の 0.857 ではない。`derive_memory_cap` が「このプロセスの予約＋空き − 1,024MiB」を総量で割った比を、ノイズ除去の頭（`_place_dit` の前）で課す（`engine_h3/lowvram.py:100-109`、`engine_h3/pipeline_h3.py:1710-1718`、`engine_h3/constants.py:68`、設計正本 §6.5「上限と OOM」）。
- 実測の cap は 13,999〜14,025MiB（快適上限表 §17.1、記録簿 §196.1・§212.1）。16GB（16,376MiB 前後）に対して約 0.855 なので、「0.857」は結果としての比（推測ではなく、値からの割り算）。
- 先読みの環（下の 2）は `_place_dit` の中で確保されるので、cap の内側に入る。

### 1.2 VRAM の内訳の模型

| うち先読みの環 | 371.08MiB × 6 本 ≈ 2,226MiB（固定分のほぼ全部） | 設計正本 §6.5「山の内訳」の照合、記録簿 §212.6 の 4 |

- **§212 の係数の意味**（記録簿 §212.6 の 4・推測の段）: b＝−920MiB は「先読みの環（最大のブロック × 6 本）が int8 より小さい分」。Kijai の w4a8 のブロックが int8 より約 153MiB 小さく、×6 で −920MiB。a＝+5,116 B/行は、w4a8 では qkv の入力を共有しない経路（`forward_rows`）なので bf16 の入力 `h`（5,376 B/行）を注意の段の間持ち続ける分、と読まれた（差 −260 B/行の内訳は不明）。Eros（w4a8 と int8 の混在・端の 5 ブロックが int8）は最大のブロックが int8 と同じなので b＝0 で、置き場の予約が int8 と同じ値だった（§212.6 の 7）。**この「環＝最大のブロック×6」の読みは、実測で 1 点独立に確かめられている**（2560×1472×175 の割り当ての差の予測 +52.6MiB に対し実測 +51MiB）。

### 1.4 行の式（快適上限表 §17.3・§18.2）
- gh＝高さ÷32、gw＝幅÷32、F＝フレーム数（17n＋5 の梯子）。

## 2. block swap の置き場の大きさ（コードの事実）

| 事実 | 出典 |
|---|---|
| VRAM 16GB mode の常駐ブロック数は `min(n_load, 4)`（`VRAM16_BLOCKS_ON_GPU = 4`） | `engine_h3/lowvram.py:86-97`、`engine_h3/constants.py:66` |
| H3 は `BlockSwapService(..., hold_arenas=True)` で環を使う | `engine_h3/pipeline_h3.py:1662` |
| 環の本数は `min(ブロック数, blocks_on_gpu + 2)` ＝ 6 本 | `engine/transformer/block_swap_prefetch.py:403-409` |
| **環の各枠は「最大のブロックの大きさ」で一律に確保**（`max_bytes = max(lay.total_bytes ...)`、`torch.empty(max_bytes, ...)`）。使うときは各ブロックの実寸に切り詰めたビュー（確保は増えない） | 同 :392、:406-408、:585-593 |
| 定常の常駐は `blocks_on_gpu + 1` 個（窓 4＋解放待ち 1）。環はその 1 つ上の 6 本 | 同 :107-117 |
| 固定メモリ（pinned）側は 2 枠、各枠は最大のブロックの大きさ。プロセスの間持ち続け、大きくなる方向だけに育つ | 同 :144-147、:236-281、:392-393 |
| 先読みの準備のとき、ブロック 0 の実寸の仮の置き場を 1 回確保して捨てる（`_validate`） | 同 :394、:481-492 |
| テンソルは dtype を問わず `("plain", dtype, shape)` として uint8 の置き場へ 512 バイト揃えで詰める。量子化層（int8 の重み＋F32 の倍率）と素の `nn.Linear`（bf16 の重み）で運び方に差は無い。違うのはバイト数だけ | 同 :454-460、:139-142、:477 |
| 環が確保できないとき（準備で OOM）は、そのビルドだけ同期の経路へ降格する。同期の経路は `blk.to(device)` でブロックの実寸を運ぶ | 同 :396-402、`engine/transformer/block_swap_service.py:256-268` |
| ノイズ除去の終わり（`finally`）で環を返す。復号の段には残らない | `block_swap_prefetch.py:93-96`、`pipeline_h3.py:1635-1639` |

- 結論（事実）: 先読み on（製品の既定）では、**BF16 のブロックが 1 個でもあれば、環の 6 本すべてが BF16 のブロックの大きさになる**。BF16 のブロックが何個あるか、どれが隣り合うかは、VRAM の固定分に効かない。
- 同期の経路（降格したとき）だけは実寸なので、同時に載る BF16 のブロックの数が効く。

## 3. BF16 のブロック 1 個の大きさと、固定分の増加

計算の台本: 同じフォルダの `fermi.py`・`fermi2.py`（電卓として使っただけ）。

### 3.1 大きさ（形から計算。512 バイト揃えを含む）
| 部分 | int8 のブロック | BF16 のブロック |
|---|---|---|
| qkv [21504,5376] | 115,605,504 B（I8） | 231,211,008 B |
| out_proj [5376,7168] | 38,535,168 B | 77,070,336 B |
| fc1 [28672,5376] | 154,140,672 B | 308,281,344 B |
| fc2 [5376,14336] | 77,070,336 B | 154,140,672 B |
| 行ごとの倍率 F32 | 243,712 B | なし |
| adaln_proj（精度の島なので読み込み後 f32。重み [96768,8]＋bias） | 約 3.48MB | 約 3.48MB |
| norm・q/k_norm | 約 22KB | 約 22KB |
| **合計** | **371.08MiB** | **738.35MiB** |

- int8 の 371.08MiB は設計正本 §6.5 の実測値（371.08）と一致するので、数え方は正しい。
- Y のブロック 2〜48 の adaln は I8（[96768,8]＋倍率）で約 1.2MB 小さいが、環は最大のブロックで決まるので影響しない。
- 差は 1 ブロックあたり +367.27MiB。

### 3.2 GPU に同時に載る BF16 のブロック
- 先読み on（既定）: 環 6 本が全部 738.35MiB になる（2 の事実）。**Y でも Z でも、BF16 のブロックの数や位置によらず、固定分は +6×367.27 ＝ +2,204MiB**。楽観・中央・悲観の差は無い（コードで決まる）。
- 参考（同期の経路に降格したとき。推測を含む）: 窓 4＋前の周回の残り 1 の実寸なので、Y はブロック 0・1（＋前の周回の 49）で最大 3 個、Z は 47・48・49 で 3 個。+734〜1,102MiB。降格は判定規則 v3″ で非快適なので、線の材料にはしない。
- 固定メモリ（主メモリ側）: 2 枠 × 738.35MiB ＝ 1,477MiB（int8 は 742MiB）。+735MiB の主メモリ。VRAM には効かない。

## 4. 計算時の一時メモリの差

前提: いまのコードでは、VRAM 16GB mode で qkv が素の `nn.Linear` だと `lowvram.py:150` で落ちる（先行報告 A）。以下は「qkv が素の Linear のとき、int8 の `forward_rows` と同じく、重みの行（ヘッド群 8 個＝1,024 行ずつ）を切り出して `F.linear(h, W[n0:n1])` で計算する」と仮定した見積もり（推測）。

| 段 | int8（共有の経路） | BF16 の素の Linear | 差（1 行あたり） |
|---|---|---|---|
| 注意（ブロックの山。設計正本 §6.5 で約 4.5U） | `x`＋量子化済みの入力（int8 5,376＋倍率 4 B/行）＋`o`＋群の一時 | `x`＋`h`（bf16 10,752 B/行）を最後の群まで保持＋`o`＋群の一時。群の出力は同じ [S,1024] bf16 | **約 +5,372 B/行**（w4a8 で実測した割り当ての上乗せ +5,116 B/行と同じ仕組み） |
| out_proj | `x`＋`o`＋入力の int8 の写し（7,172 B/行）＋出力 | `x`＋`o`＋出力だけ | −7,172 B/行（ただし山ではない段） |
| FFN（4,096 行の塊ごと） | 塊の入力の int8（約 21MiB・56MiB）＋fc1 出力 [4096,28672] bf16（224MiB）など | 入力の int8 が無い | 塊あたり約 −77MiB（山ではない段） |
| qkv を一括で計算した場合（参考） | — | `x`＋`h`＋`o`＋[S,21504] bf16（43,008 B/行）が同時に生きる | 約 +30,400 B/行 |

- 割り当ての当てはめの傾き 51,102 B/行 ≒ 4.75U で、注意の段が山であることと合う（設計正本 §6.5 の表と同じ読み。推測）。山は全ブロックの最大なので、BF16 のブロックが 1 個でもあれば +5,372 B/行が山に乗る。
- 素の `F.linear` は cuBLAS の作業領域を使うが、読み込みで先取り済み（設計正本 §6.5 #9 の注）なので増えない（推測）。

## 5. フレーム数への換算

### 5.1 式
予約の山の予測 ＝ 2,252.1MiB ＋ 51,102 B×S ＋ 10,287 B×text（割り当て。記録簿 §196.6 の 1）＋ 断片化の余裕 g ＋ 固定の増加 ΔF ＋ Δa×S ≦ cap

- int8（ΔF＝0、Δa＝0、g＝900MiB、cap 13,999MiB）で既知の点を再現する: 1920×1088・K=1 は 345 快適／362 OOM、K=0 は 362 快適、2560×1472・K=1 は 192／209。割り当ての予測は r1080_362 で 12,950MiB（実測 12,949）、s720_481 で 9,079MiB（実測 9,080）。
- 注意: 小さな S の点の予約の山（例 1280×768×481 の 11,352MiB）は上限から遠く、割り当て器が空きを抱えたままなので、そこへ足し算すると過大になる。上限の近くでは返せる空きを返して確保し直す（retries）ので、「割り当て＋g」で見る（記録簿 §196.6 の 2・5、§212.7 の Z-③ と同じ扱い）。

| 想定 | Δa | g | cap | ΔF |
|---|---|---|---|---|
| 楽観 | +5,116 B/行（w4a8 の実測の上乗せ） | 795MiB | 14,025MiB | +2,204MiB |
| 中央 | +5,376 B/行（`h` 1 本分の半分の差。コードから） | 900MiB | 13,999MiB | +2,204MiB |
| 悲観 | +7,228 B/行（w4a8 の予約の側の読み。否定済みの値を上限の目安に流用） | 939MiB | 13,999MiB | +2,204MiB |

- 固定分だけで失う行: 2,204MiB ÷ 51,102 B/行 ≒ 45,200 行。
- S の予算（text 30 の形）: 楽観 163,657 行・中央 160,472 行・悲観 154,676 行（int8 の線 219,516 から −56,000〜−65,000 行、約 26〜30% 減）。

## 6. 結論と不確かさ

- **「3 秒までしか作れない」恐れは小さい（推測）。** 1920×1088 で約 10 秒（243〜260 フレーム）、1280×768 は 481 フレーム（20 秒）まで快適の見込み。
- ただし int8 の線 219,516 のままでは、1920×1088 の 260〜345 フレームあたりで印の内側の OOM が起きる見込み（w4a8 の時と同じ形）。
- **最も効く未知数**: (1) BF16 の qkv をどう計算するか（行の切り出しなら +5,400 B/行、一括なら +30,400 B/行で 1 段どころか 4 段変わる）。(2) 上限の近くの予約の断片化（w4a8 では予測より +360〜+1,037MiB 高く、1〜2 段ずれた。BF16 の素の Linear には w4a8 のような二重の一時確保は無いので小さいと見るが、未測）。(3) 固定分の +2,204MiB はコードで決まるので確度が高い（Kijai の −920MiB が同じ式で実測と合った）。
- 実機で 1 点だけ確かめるなら（提案。実行しない）: qkv の修正の後、Y で 1920×1088×243・K=1 を 1 本回し、ログの「ring of 6 x 738.3 MB」と、ノイズ除去の割り当ての山が予測の約 12,650MiB（予約は約 13,550MiB）に入るかを見る。
