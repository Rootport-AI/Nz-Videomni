# MiniMax H3: Sulphur-3 の int8 版と、一部のブロックを BF16 で残した重みへの対応

## Context（なぜ直すのか）

MiniMax H3 エンジンで、次の 3 本の重みが動きません。

| 重み | 症状 | 原因 |
|---|---|---|
| `s3_raw_int8`（以下 X） | 完走するがブロック状のノイズ | 原因 1 |
| `Sulphur-3_Ref2VA-hybrid_mid_int8_convrot_keepB0-1-49`（以下 Y） | `shares_input` のエラーで停止 | 原因 2。直した先に原因 1 も控える |
| 10Eros 8stepTURBO int8HQ（以下 Z） | Y と同じ場所で停止 | 原因 2 |

- **原因 1（`adaln_proj` の倍率）**: X と Y は、時刻による変調の層 `adaln_proj` まで int8 にしています（公式の重みは F16）。製品はこの層の重みを直接読んで計算するので、int8 の生の値がそのまま掛かり、倍率が使われません。CPU の数値照合で、変調量が 8〜26 倍に膨らむことを確認済みです。
- **原因 2（VRAM 16GB mode の qkv）**: qkv の処理が量子化層だけを想定していて、BF16 のまま残った素の線形層が来ると落ちます。落ちるのは製品全体でこの 1 か所だけです。
- **回転（ConvRot）なしの int8** は、印の旗をそのまま計算の核に渡す作りなので、コードの変更は不要の見込みです。ただし実機の実績が無いので、修正後の実機確認で確かめます。

ゴールは「3 本とも置くだけで動き、意味のある動画として収束すること」です。ComfyUI とのビット一致は求めません。快適上限の較正と操作パネルの修正は範囲外です。

## 方針: 既存の経路は 1 行も変えない

切り替えは、重みのヘッダの印から**層ごとに**自動で決まります（エンジン全体を重みの種類で分岐させません）。公式の int8 ConvRot・fp8・w4a8 の重みは、今と同じ行を通ります。

## コードの変更（2 か所・合計 約 20 行）

### 変更 1: `engine_h3/dit.py` の `H3AdaLNProj.forward`（316〜319 行）

層が int8 の量子化層のときだけ、重みに行ごとの倍率を掛けてから計算します。

```python
lin = self.linear
w = lin.weight.to(torch.float32)
if isinstance(lin, H3Int8Linear):   # int8 の値 × 行ごとの倍率
    w = w * lin.weight_scale
b = lin.bias.to(torch.float32)
```

- 公式の重み（この層が F16 の素の線形層）は分岐が偽になり、計算は今とまったく同じです。
- 数値照合では、この方法が量子化前の値に最も近い結果でした（相対誤差 約 0.12%。ComfyUI と同じ手順は約 0.15%）。
- 最終層の変調も同じ関数を通るので、一緒に直ります。
- import に `H3Int8Linear` を足します（循環 import にはなりません）。

採らなかった案:
- 読み込みの段で float に戻して素の線形層に入れる案 → 倍率の置き場が無く、読み込みの手順に新しい例外の規則が増えます。
- ComfyUI と同じく int8 の核を通す案 → 量子化層の入出力が bf16 固定なので、公式の重みも通る関数を変えることになります。精度も上の方法に劣ります。

### 変更 2: `engine_h3/lowvram.py` の qkv の分岐（148〜155 行）

素の線形層のときの分岐を先頭に足します。既存の行は `if` が `elif` になるだけです。

```python
xa = _lora.xa_for(qkv, h)
if isinstance(qkv, nn.Linear):          # 一部のブロックを BF16 で残した重み
    proj = functools.partial(_linear_rows, qkv, h, lora_xa=xa)
elif qkv.shares_input(h):               # 以下は今と同じ
    ...
else:
    ...

def _linear_rows(layer, x, n0, n1, lora_xa=None):
    out = F.linear(x, layer.weight[n0:n1])   # 重みの行は呼ぶたびに切り出す
    if lora_xa is not None:                  # 層を直接呼ばないので LoRA の仕掛けは働かない
        out = _lora.apply(layer, None, out, n0, n1, xa=lora_xa)
    return out
```

- qkv をヘッド群ごとに分けて計算する省 VRAM の設計を維持します（全体の一括計算はしません）。
- 量子化層は `nn.Linear` の子ではないので、必ず既存の行に落ちます。
- LoRA は、既存の部品（`lora.xa_for`・`lora.apply`）をそのまま使います。量子化層の `forward_rows` と同じ呼び方で、VRAM 16GB mode を切ったときと同じ数値になります。二重に足されることもありません。
- out_proj・fc1・fc2 は、素の線形層でも今のコードのままで正しく動きます（LoRA つきでも）。

### 触らないファイル

検査器（`h3_format.py`）・`quant_linear.py`・`fp8_linear.py`・`w4a8_linear.py`・`lora.py`・`pipeline_h3.py`・アプリ側・操作パネル。

### 対応を広げない点

`adaln_proj` が fp8 や w4a8 のファイルは、今も修正後も読み込みの段で断られます（そうした配布物は見つかっていません）。

## 自動テスト（追加 7 件・GPU を使わない）

`tests/test_h3_engine.py` に 6 件、`tests/test_h3_format.py` に 1 件。

1. 素の線形層の qkv で、VRAM 16GB mode の on と off が一致する（ブロック単体）。
2. BF16 のブロックと int8 のブロックが混在する DiT 全体で、on と off が一致する。
3. 上の混在の DiT に LoRA を当てて、on と off が一致し、LoRA なしとは値が違う。
4. int8 の `adaln_proj` が倍率つきで計算される。F16 の `adaln_proj`（公式の形）は今と同じ値のまま。
5. int8 の層が、印の回転の旗（あり・なし）をそのまま計算の核に渡す。
6. 混在のファイルを組み立てると、BF16 の層は素の線形層、int8 の層は量子化層になる。
7. 検査器が「一部のブロックが BF16・`adaln_proj` が int8」のファイルを受理する。

既存のテスト（量子化層・VRAM 16GB mode・LoRA・fp8・w4a8）は、変更せずに通ることを確かめます。

実行のしかた:
```
.venv-engine-h3/Scripts/python.exe scripts/run_h3_pytest.py tests/test_h3_engine.py
.venv/Scripts/python.exe -m pytest tests/test_h3_format.py tests/test_h3_quant_class.py tests/test_engine_h3_adapter.py
```
テストの前に、オーナーのサーバー（127.0.0.1:18620）が動いていないかを確かめます。GPU のテストは、明示して有効にしないかぎり走りません。

## 実機（GPU）の確認

過去の門の台本 `outputs/h3-fp8-w4a8-gate-2026-11-12/h3_quant_gate_api.py` を新しいフォルダ `outputs/h3-mixed-int8-gate-2026-11-22/` に写して使います（MCP 経由）。共通の条件は過去の門と同じです（T2V・1280×768×73 フレーム・seed 1234・VRAM 16GB mode on）。

| 条件 | 重み | 目的 |
|---|---|---|
| R0 | 公式の int8 ConvRot | **コードを変える前**に採る基準 |
| R1 | 同じ | 修正後。映像と音声のストリームが R0 と一致すれば「既存の経路を壊していない」 |
| X | `s3_raw_int8`（製品の既定: 20 ステップ・shift 12/3） | **最初の関門**。まだノイズなら、ここで止めて原因究明に戻る |
| Y | Sulphur-3 keepB0-1-49（製品の既定: 20 ステップ・shift 12/3） | 素の qkv と int8 の `adaln_proj` |
| Z | 10Eros int8HQ（8 ステップ） | 素の qkv だけ |
| YL | Y に Turbo LoRA（4 ステップ） | 素の qkv に LoRA を当てる経路 |

- R1 が R0 と一致しなかったときは、R1 をもう 1 本回して、実行ごとの揺れかどうかを切り分けます。
- 台本の自己検査（完走・寸法・フレーム数・音声・層の数がヘッダと一致）に、ノイズの客観的な指標（1 フレームあたりのバイト数・輪郭の強さ・フレーム間の差を R1 と比べる）を足します。値は記録し、最終の合否はオーナーの目視で決めます。
- ログから、block swap の置き場の大きさ（Y・Z は 1 枠 約 738MB の見込み）とノイズ除去の VRAM の山を読み、フェルミ推定と照らします。較正はしません。
- 所要は合計 約 30 分の見込みです。
- **GPU を使う前に、毎回オーナーの了承を取ります。** サーバーの起動と、修正後の再起動はオーナーにお願いします。
- 生成した動画は上の outputs のフォルダに置き、場所を報告します（外部へのアップロードはしません）。

## VRAM の見込み（フェルミ推定・参考）

BF16 のブロックが 1 個でもあると、block swap の置き場（最大のブロック × 6 枠）が約 2,200MiB 増えます。

| 解像度 | int8 だけ | BF16 混在の見込み |
|---|---|---|
| 1280×768 | 481 フレーム（20 秒） | 481 フレームのまま |
| 1920×1088 | 345 フレーム（14.4 秒） | 243〜260 フレーム（約 10 秒） |

「3 秒までしか作れない」恐れは小さく、今回は打ち手を入れません。

## 残る不確かさ

- X が修正後も収束しない場合の候補は、回転なしの int8 の核の実機での動きです。そのときは、既存の GPU テスト（回転なしの int8 の層を、float に戻した参照と比べるもの）で切り分けます。
- BF16 の qkv を行ごとに切り出した結果が、GPU で一括の結果とビット単位まで一致するかは測りません（CPU のテストでは一致）。品質に影響しない階級の差です。
