# MiniMax H3: BF16 のブロックを含む重みに、概算による暫定の快適上限の線を出す

（前の計画「Sulphur-3 の int8 版と BF16 のブロックを残した重みへの対応」は完了し、dev `54f0724f` に入っています。写しは保管庫 `Docs/Outputs-archive/h3-mixed-int8-2026-11-22/計画.md`。本書はその続きの別件です。）

## Context（なぜやるのか）

今日の修正で、一部のブロックを BF16 のまま残した int8 の重み（Sulphur-3 keepB0-1-49・10Eros int8HQ）が動くようになりました。この種の重みは block swap の置き場が約 2,200MiB 大きくなるのに、重みの種類が「int8」と判定されるので、int8 の線の快適上限の印が出ます。そのため、1920×1088 の 260〜345 フレームのあたりでは、印の内側なのに VRAM が溢れる見込みです。

正確な較正は後（台帳 1-291）に回し、**いまの段階で、概算（フェルミ推定）の数字を暫定の線として印に載せます**（オーナーの方針 2026-11-22。「目安は、不正確でも無いよりある方がよい」という以前の裁定と同じ考え方です）。

## 決まったこと（オーナー裁定 2026-11-22）

- 線は概算の**中央の値 160,472 行**にする。
- 操作パネルは今回触らない（バックエンドの修正と再起動だけで印が出る）。

印の位置の見込み（キーフレーム 0 枚／1 枚）:

| 解像度 | いま（int8 の線） | 暫定の線 |
|---|---|---|
| 1920×1088 | 362／345 フレーム | 260／243 フレーム |
| 2560×1472 | 209／192 フレーム | 141／124 フレーム |
| 1280×768 | 481 フレーム | 481 フレーム（変わらない） |

## 仕組み（既存のものに 1 種類足すだけ）

いまは、重みの種類（`int8`・`fp8`・`w4a8`）を読み込みのたびにヘッダから決め、`GET /models` の `transformer_quant_class` で配り、操作パネルがマニフェストの `comfort.single_rows_budget_by_quant_class` を種類の名前で引いて線を選びます。操作パネルは値を「辞書を引く鍵」として使うだけなので、バックエンドに新しい種類を足せば、配置済みの操作パネルのまま新しい線が出ます。印を出す場所（Single・Chained・Outpainting・Inpainting・右クリックの種）はすべて同じ関数を通るので、同時に切り替わります。

## コードの変更（バックエンドだけ）

### 1. `h3_format.py` の `quant_class`（619〜633 行）

新しい種類 `"bf16_blocks"` を足し、**最初に**判定します。

- 規則: **ブロックの大きな線形層（qkv・out_proj・fc1・fc2）に、量子化の印が無いものが 1 つでもあれば `"bf16_blocks"`**。それ以外は今と同じ（w4a8 → fp8 → int8）。
- `adaln_proj` と token_refiner は数えません（公式の重みでも量子化されていないため。数えると公式の重みが誤って新しい線に入ります）。
- 最初に判定する理由: 新しい線がいちばん低いので、w4a8 や fp8 の層と BF16 のブロックの両方を含む重みが来ても、低い方の線に寄ります（そうした重みは手元にも配布物にも見つかっていません）。
- 量子化の層が 1 つも無い重み（全層が BF16）は、今は `"int8"` ですが、新しい規則では `"bf16_blocks"` になります。置き場の大きさからいって、こちらが実態に合います。
- `H3_QUANT_CLASSES`（616 行）に名前を足します（起動時にマニフェストの鍵と照合しているため、足さないと起動が止まります）。

### 2. `scripts/manifests/40-minimaxh3.json`（46 行）

```json
"comfort": { "single_rows_budget": 219516,
             "single_rows_budget_by_quant_class": { "w4a8": 203092, "bf16_blocks": 160472 } },
```
同じファイルの `_note` に、この値が概算による暫定の値であることを 1 文足します。

### 3. 値の一覧を書いている説明文

`services/model_registry.py`・`services/pipeline_manager.py`・設定の説明・MCP の説明文（`mcp_server` の `system.py`）で、種類の値を列挙している箇所に `bf16_blocks` を足します（文言だけ。動作は変わりません）。

### 触らないもの

操作パネル（型の定義 `types.ts` に新しい値が載っていない状態になりますが、動作には影響しません。台帳の「軽微なデバッグ」の受け皿 3-280 に 1 行残し、次に操作パネルを直す機会に足します）、エンジン（`engine_h3/`）、Gradio（種類を読みません）。

## 自動テスト（GPU を使わない）

- 追加: `tests/test_h3_quant_class.py` に、次の場合の判定を足します。
  - ブロックの 1 つで qkv・out_proj・fc1・fc2 に印が無い → `bf16_blocks`
  - `adaln_proj` だけ印が無い（公式の形）→ `int8` のまま
  - w4a8 の層と印の無いブロックの両方 → `bf16_blocks`
- 更新（値を完全一致で固定しているもの）: `tests/test_h3_quant_class.py` の「量子化の層が無い重み → int8」を `bf16_blocks` に。`tests/test_comfort_budgets.py`・`tests/test_model_swap_load.py` の、マニフェストの辞書や種類の一覧を固定している箇所。
- 実ファイルでの確認（ヘッダだけを読む・GPU なし）: `models\MiniMaxH3` 配下の重みすべてに判定を掛け、`bf16_blocks` になるのが Sulphur-3 keepB0-1-49 と 10Eros int8HQ の 2 本だけで、公式・PinkCherry・h3ErosMax・`s3_raw_int8`・w4a8 の各重みは今までと同じ種類のままであることを確かめます。
- テストの前に、オーナーのサーバー（127.0.0.1:18620）が動いていないか、対象のテストがモックのフィクスチャであることを確かめます。

## 実機での確認（オーナーにお願いする分）

GPU を使う生成の確認はしません（線の値は概算で、実測の裏付けは台帳 1-291 の較正で取ります）。バックエンドを再起動したうえで、印の位置だけを見ていただきます。台帳のチェックリストにします。

- Sulphur-3 keepB0-1-49 を読み込み、Single タブで解像度を 1920×1088 にする → 快適上限の印が 260 フレームに出る（今までは 362）。
- 10Eros int8HQ を読み込む → 同じ位置に出る。
- 公式の int8 の重みを読み込む → 今までどおり 362 フレームに出る。
- `s3_raw_int8` を読み込む → 今までどおり 362 フレームに出る（BF16 のブロックを含まないため）。

## 残る不確かさ

- 線の値は概算です。w4a8 のときは概算より実測が厳しく出たので、印の内側で失敗する可能性は残ります（とくにキーフレーム 0 枚の 260 フレーム）。README と快適上限表に「未較正」と明記し、台帳 1-291 の較正で置き換えます。
- Chained・Outpainting・Inpainting・参照つきも同じ線を使います。BF16 のブロックを含む重みで参照つきの場合は、概算もしていません。
