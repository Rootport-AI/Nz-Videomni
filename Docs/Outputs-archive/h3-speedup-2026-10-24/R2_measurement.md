# R2 台帳 §1-105 の計測（MiniMax H3 の 1 ステップの高速化・第 1 弾。M0・腕 N・腕 E・腕 P）

計測日 2026-10-25（01:19〜01:40）。対象はブランチ dev の作業ツリー。製品のコードは変えていない（差し替えは計測台の中だけ）。GPU は RTX 4070 Ti SUPER 16GB（ドライバー 610.88）、torch 2.13.0+cu130、comfy-kitchen 0.2.37。設計の正本は `R1_investigation.md`。

## 結論

1. **① QKV の量子化の共有の短縮の上限は、1 ステップあたり 1.45 秒（実測）。** 2 ステップ目の qkv の量子化の核は 1,050 回・合計 1,519.7 ms で、その 20/21 が 1,447 ms。見積もり 0.95〜1.6 秒の中に入る。単体のマイクロベンチ（M0）の 1 回 1.442 ms × 1,000＝1.442 秒とも 0.4% で一致した。20 ステップで約 29 秒、Turbo の 4 ステップで約 5.8 秒（上限の換算）。R1 の判定の使い方に従えば **① は進める側**。
2. **② のステップの境目の GPU の空きは 1 ステップあたり約 60 ms（実測。見積もり 45 ms）。** 20 ステップで約 1.1 秒（19 回 × 59.7 ms）。見積もりより 3 割ほど大きいが、「1〜2 秒は原則として見送る」の範囲に収まる。
3. **③ のブロック切り替えの GPU の空きの合計は 1 ステップあたり 0.06〜0.07 ms（実測。見積もり ほぼ 0）。** ステップの途中で GPU がメモリコピーを待つことは無い。CPU は GPU より先を走り、起動の呼び出しの中で止まっている（腕 P で確認）。②・③ の見送りの前提は実測で裏付けられた。
4. **量子化の核は決定的。** 同じ入力に 2 回かけた int8 の結果とスケールはビット一致した（S＝39,764 と 89,388 の両方。`torch.equal`）。① の数値等価の残っていた前提が実測で埋まった。
5. **計測の負担は検出できない大きさ。** 腕 E（イベントと包み）の 2・3 ステップ目 21.633／21.685 秒に対し、外部の負荷が無いときの腕 N（N3）は 21.641／21.684 秒。前回の A-G5（h8_r4096_b4）の 21.74 秒とも 0.5% 以内。生成物の mp4 は 5 回すべてで同じ（md5 `eb2a53ae…`）。
6. **注意: 計測の途中で、別のプロセスの GPU の負荷（SM 約 35%・PCIe の受信 約 950 MB/s の定常の流れ）が断続的にあり、その間のステップは約 1.5 秒（約 7%）遅くなった。** 最初の腕 N（N・N2）はこれに当たって 23.2 秒前後だった。腕 N を取り直し（N3。負荷なし）、比較には負荷の無いステップだけを使った。負荷の出どころのプロセスは**未確認**。今後の A/B（R1 の M2）では dmon の受信の列で負荷の有無を確かめる必要がある。

### 2.4 外部の GPU の負荷について（計測の途中で見つけたこと）

- 最初の腕 N は 2 ステップ目 23.19 秒で、続く腕 E（21.63 秒）より 1.5 秒遅かった。計測を足した腕のほうが速いのは不自然なので、腕 N を取り直した（N2）が、やはり 23.18 秒だった。
- dmon（1 秒刻み）を見ると、遅いステップでは毎秒 約 470 か 約 950 MB/s の PCIe の受信が途切れずに続いている。速いステップでは受信はほぼ 0 で、ときどき 4,000〜22,000 MB/s の瞬間値が出るだけ。block swap の転送（1 本 371 MB を 約 16 ms で送る。1 ステップで 50 本）は 1 秒刻みの瞬間値ではこの「ほぼ 0 とときどきの山」に見えるので、定常の 950 MB/s は block swap ではない。モデルを読む前の待機の窓（`idle_window`。計測台のプロセスはまだ GPU で何もしていない）にも、E・P・N2 では SM 約 35%・受信 約 900 MB/s が出ており、N3 と前回の A-G5 では 0 だった。計測台の動きは毎回同じなので、別のプロセスのものと判断した（判断。プロセスの特定はしていない）。
- 3 回の N（N・N2・N3）と E・P の 15 ステップすべてで、「定常の受信がある＝22.4〜24.0 秒」「ない＝21.6〜21.9 秒」がきれいに分かれた（`step_rx.jsonl`）。腕 P の 2 ステップ目（22.28 秒）は負荷が途中まであった。
- N3（負荷なし）は 21.641／21.684 秒で、腕 E と 0.01 秒以内で一致した。前回の A-G5 も同じ方法で見ると負荷なしだった。
- 負荷のプロセスは**未確認**。計測の前後の `nvidia-smi --query-compute-apps` には Python のプロセスは無く、グラフィックスのプロセス（ブラウザー・Steam・Discord・NVIDIA Overlay など）だけだった。`nvidia-smi pmon` で同時に記録しようとしたが、何も出力されないまま残ったので止めた（下の 6）。

## 4. 見積もりとのずれとその理由

- **(a) の 1 回の時間 1.44 ms は、R1 の範囲（0.95〜1.6 ms）の上寄り。** 実効帯域が公称の約 67%（445 GB/s）にとどまるため（実測）。R1 が A-G5 のヘッド群 8／14／28 から逆算した 1.6〜1.67 ms との差（約 0.2 ms）は、ヘッド群を変えると sage の呼び出しの大きさや行列積の N も変わるため、と R1 自身が書いていたとおりと見られる（推測）。
- **(b) が 45 ms ではなく 60 ms になった理由（実測の内訳からの説明）**:
  1. CPU 側のコピー 1 本が 15.1〜18.9 ms（中央値 15.9 ms）で、R1 の前提 14.4 ms（LTX のブロックでの 27.1 GB/s）より遅い。ここで測ったのはビュー作りを含む値なので、コピーそのものの速さは未確認。
  2. ブロック 2 の発行で区画の空きを 7.1 ms 待った（R1 の時間線にもある待ちだが、ブロック 0 の H2D〔ホストから GPU への転送〕が R1 の前提 16.6 ms より長くかかったと見られる。推測）。
  3. head から pre[0] までに 6.3 ms（`time_rows`・埋め込み・時間の埋め込みなど。R1 の「前処理の数 ms」）。
- **(c) はほぼ 0 で見積もりどおり。** CPU は 1 ステップの 7 割を起動の呼び出しの中で待っており、GPU より十分先を走っている。

## 6. 計測中に気づいたこと

**R1 と食い違う点・R1 に足す事実**

1. `g5a.sh` は **2 ステップ**で、プロンプトは **`f0_prompt.txt`**。R1 の「共通の計測の設計」の条件（3 ステップ・「画像とプロンプトは `g5a.sh` と同じ」）のうち、ステップ数は `g5a.sh` と違う。今回は 3 ステップで回した（0 節の注 1）。
2. 包む対象の関数の名前と署名は R1 のとおりだった: `PrefetchEngine.on_block_forward(self, idx: int) -> None`・`_issue(self, idx: int) -> None`・`_acquire_slot(self) -> int`（`engine/transformer/block_swap_prefetch.py`）、`pipeline_h3.time_rows(layout, t_video, t_audio, device=None)`、`lowvram.block_forward(block, x, t_emb, adaln_index, rope_cos, rope_sin)`、`H3Int8Linear.forward_rows(self, x, n0, n1, lora_xa=None)`。`time_rows` は `pipeline_h3.py:1008` の 1 か所だけから呼ばれる。
3. 量子化の核は 3 種類（テンプレートの引数 256・512・1,024）あり、qkv と fc1 が 256、fc2 が 1,024、out_proj が 512 と見られる（回数から推定）。R1 は 1 種類を前提にしていたが、① が消すのは 256 の核の qkv の分だけなので、判定には影響しない。
4. R1 の推測「量子化の核は決定的（状況証拠）」は、M0 でビット一致を実測した。
5. R1 の推測「CPU が先行しすぎないのは起動の列が満杯で止まるから」は、腕 P で確認した（1 ms を超える起動の呼び出しが 3,880 回・合計 15.7 秒）。
6. R1 の (b) の見積もりの前提（CPU 側のコピー 14.4 ms／本）は、H3 のブロックでは 15〜19 ms（ビュー作りを含む）だった。境目の空きは約 60 ms。
7. block swap の 1 パスの区画の待ち（stdout の「≈265 ms waiting on pinned slots」）のほぼ全部が、ブロック 2 の forward でブロック 5 を発行するときの 1 回（約 258 ms）に集まっている。そのあいだ GPU は計算中で、GPU の待ちにはなっていない。

**計測の運用で気づいたこと**

8. **外部の GPU の負荷**（SM 約 35%・PCIe 受信 約 950 MB/s）が断続的にあり、1 ステップを約 1.5 秒（約 7%）遅くする（2.4）。プロセスは未確認。① の実装後の A/B（R1 の M2）は差が 1.45 秒（約 7%）の見込みで、この負荷と同じ大きさなので、**各ステップの dmon の受信の中央値で負荷の有無を確かめ、負荷のあるステップを比較から外す**必要がある（`step_rx.py` がそのまま使える）。
9. `nvidia-smi pmon` をバックグラウンドで `timeout 400` を付けて起動したが、出力が 0 バイトのまま、時間が過ぎてもプロセスが残っていた（Git Bash の `timeout` が Windows の子プロセスを止めなかった）。最後に `Stop-Process` で止めた。GPU の計算のプロセスではない。計測の各回の前の `nvidia-smi --query-compute-apps` には、毎回 Python のプロセスは無かった（孤児なし）。
10. 腕 E の包み（イベントの記録・`time_rows` の入口の `synchronize`・`query()`）は、壁時計にも出力（mp4）にも影響しなかった。製品に計測の口を常設するなら、この形は負担が無い（参考。提案ではない）。
