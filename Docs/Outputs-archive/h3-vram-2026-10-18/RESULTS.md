# 結果: MiniMax H3 の VRAM 溢れの犯人（台帳 §1-101 第 1 段・計測）

計測 2026-10-18（開発機 RTX 4070 Ti SUPER 16GB・主メモリ 64GB・ドライバ 610.88・torch 2.13.0+cu130・dev `709a2fe`）。計画は `PLAN_measure.md`、条件と再実行の手順は同じフォルダの `README.md`。機械可読の要約は `summary.json`（敵対的レビュー `REVIEW_results.md` の指摘を全件取り込んだ版）。

**用語と単位**: 数値の単位は MiB。「2 ステップ目」の時間＝進捗の知らせ（progress）のノイズ除去の番号（index）2 が届いた時刻 − 番号 1 の割り込み（採取）を終えた時刻（どちらも `torch.cuda.synchronize()` の後）。「ノイズ除去の窓」＝`stage1_denoise` の index 0 から index 2 までの壁時計の区間。U＝bf16 の [系列長, 5376] 1 本（画角 A で約 414MiB）。「上限」＝`torch.cuda.set_per_process_memory_fraction` で割り当て器に課した上限（0.85＝13,919MiB）。

## 結論

- **H1 支持（ただし留保つき）**: 溢れの主因は、割り当て器（torch の CUDA メモリの割り当ての仕組み）が返さずに抱えたままの空きセグメント（cudaMalloc で取った塊）だった。
  - 直接の証拠: T1 の割り当てがピークの瞬間、未使用の予約 4,075 のうち 3,316 は、使用中のブロックが 1 つも無い丸ごと空いたセグメント 2 つ（2,210 と 1,106）だった。計画 §1 の定義で「返せる」分にあたる。
  - 上限 0.85 の T3 では、割り当ては同じ 12,908 のまま予約が 16,970→13,652 に下がった。窓の共有メモリは基準並み（−27）に戻り、OOM（メモリ不足）は出ず、2 ステップ目は 32.6→20.8 秒に速くなった。
  - 不利な事実: 上限の下では、返せない断片（`inactive_split`＝使用中のブロックと同じセグメントにある空き）がかえって増えた。ピークは T1 1,937 に対し T3 2,774・T5b 4,283。今回の画角では上限の下で OOM なく返せたが、返せない断片は増えており、もっと大きい画角でも足りるかは確かめていない。
- **H2 支持**: sage と sdpa の割り当てのピークの差は 1,524（T1 12,907／T2 11,383。予測 約 1,520＝3.67U）。
- **H3 不支持**: 溢れの無い条件で sage 20.76 秒・sdpa 52.69 秒（T3／T4。sdpa は 2.5 倍遅い）。sdpa の遅さは溢れとは関係ない。溢れの判定の閾値（+300）の下にある T2 も 54.06 秒だった。原因は mem-efficient 経路そのものの速度と見る（この Windows 版 torch には flash attention が無い。推測を含む）。
- **H4 支持（割り当ての側）**: 常駐ブロック数 8→4→2 で、割り当ては −1,489／−2,233（予測 −1,484／−2,226）。2 ステップ目は 20.76／20.71／20.80 秒で横ばい。予約の側の予測（予約も同じ量だけ下がる）は外れた。上限の下では、予約は削減量を表さない（後述）。
- **H5 支持**: SDPA の mem-efficient 経路は、S=100,352 で v の view（行の刻み 21,504）を渡すと不正なメモリアクセス（CUDA エラー）になった。v を連続にすると正常だった（別プロセスで切り分け）。S=98,304 では view と連続が完全に一致した。実測で言える境界は 98,304〜100,352 の間。
- **§166.9 の「1 ステップ約 210 秒」は、計測台 T1（T2V・履歴あり）では出なかったが、製品の条件を揃えた対照の腕 F0 で再現した**（2 ステップ目 202.9 秒・3 ステップ目 205.2 秒）。
  - 条件: §166.9 と F0 は I2V 896×1152×124（系列 39,764 行）。T1 は T2V 960×1152×124 の 2 ステップ目だけ。
  - 事実: F0 の割り当て／予約のピーク 12,807／16,828 は、オーナーの 1 回目と完全に一致した。オーナーの操作パネルからの 2 回目（job `c14379b2`）でも 2 ステップ目以降 168.5〜205.0 秒で再現し、条件が揃えば毎回出る（F0 と操作パネルの 2 回）。
  - 未解明の例外: T1 は窓の共有が 3,631（生の値。§166.9 の 3.7GB と同じ物差し）、基準との差 +2,394 と、F0（+2,032）より多く退避したのに 32.6 秒だった。溢れの軽い側の症状として、上限ありの T3 より 11.8 秒遅かった。T1 で重い症状が出なかった理由は、オーナーの裁定で追わない（後述の「計測台の検証」）。
  - 重い症状の特徴（F0）: PCIe の受信が中央値 27GB/s で飽和し、先読みが転送待ちで止まる（pass 2 で 160 秒）。
  - 監督の裁定 3（維持）: 今後の較正（台帳 §1-95。この計画では線は引かない）では、線を速度ではなく「退避そのもの（窓の共有メモリの中央値）」で引く。COMFORT_LIMIT_TABLE §4.2 の v3 が速度を線に使わないのと同じ理由。

### 時間の比較の扱い（監督の裁定 1。事前登録の規則からの逸脱）

計画 §2 の事前登録の規則では、index 1→2 の確保・解放の回数が腕の間で 2 倍以上違えば、時間の比較は「参考」になる。T3（+5／+5）対 T4（0／0）、T1（0／+1／0）対 T3 はどちらもこれに当たる。監督は、この 2 つの比較を**結論に使う**と裁定した。これは事前登録の規則から外れる判断である。

理由:
- 回数の絶対量が小さく、費用は数ミリ秒の見込み（推測）。
- 上限が時間に効かないことは、sdpa の T2（54.06 秒）対 T4（52.69 秒）で確かめた。
- 履歴が時間に効かないことは、T3（履歴あり・20.76 秒）対 T5a（履歴なし・20.71 秒）で見た。ただしこの比較には常駐 8 と 4 の違いが混ざり、常駐数が時間に効かないという H4 の結果に頼っている。
- T1 対 T3 は履歴の有無が同じで、回数が多い T3 のほうが速い。比べる向きとしては控えめな側にあたる。

### 判定

計測台は、製品の条件を揃えれば症状を再現する。今後の門として使える。重い症状の採取上の特徴は次の 2 つ。
- PCIe の受信が中央値 27GB/s で飽和する。
- 先読みが転送待ちで止まる（pass 2 で 160 秒）。T1 の受信は 451MB/s だった。
