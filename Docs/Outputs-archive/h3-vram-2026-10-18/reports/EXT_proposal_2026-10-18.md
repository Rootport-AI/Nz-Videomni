# Nz-Videomni / MiniMax H3：VRAM 16GB最適化のアイディア

GitHubの `main` ブランチから、指定の `PENDING_TASKS.md` §1-101、設計書、推論エンジンの実装を確認した。

最初に結論を述べると、量子化精度を下げたり、Attentionを近似したりしなくても、かなり大きなVRAM削減の余地があると思う。

特に有望なのは、次の3系統だ。

1. MLP（FFN）のトークン方向チャンク化：巨大な中間テンソルを一度に生成しない。
2. AdaLNのメモリ効率改善：少数の変調パラメータを、数万トークンに展開して保持する処理を減らす。
3. Block SwapのGPU常駐ブロック数を調整：現在の8ブロック＋先読み用領域によるVRAM消費を抑える。

このうち1と2は、数学的には同じ計算を実行する方式にできる。3は重みの置き場所を変えるだけなので、推論結果自体に影響しない。

## 1. まず、何がVRAMを大量消費しているのか

現在の実装では、MiniMax H3のDiTに次の特徴がある。

- Hidden size：5,376
- FFN hidden size：14,336
- Attention：56 heads × 128
- DiT：50ブロック
- Block Swap：既定で8ブロック
- 演算精度：主にBF16、AdaLNなど一部FP32

896×1152・124フレームのI2Vでは、映像だけで37,296トークン。条件画像、音声、テキストを含めると約3.9万トークンになる。

この約3.9万トークンを一括処理したときの、主要な中間テンソルの理論サイズは以下のとおり。

計算上の目安。テキスト150トークンを仮定。単一テンソルのサイズであり、同時に存在するメモリ量ではない。

| テンソル | 推定サイズ |
| --- | --- |
| Hidden state `[S, 5376]` BF16 | 約399 MiB |
| AdaLN展開 `[S, 5376]` FP32 | 約797 MiB |
| Attention QKV `[S, 21504]` BF16 | 約1,594 MiB |
| FFN fc1出力 `[S, 28672]` BF16 | 約2,126 MiB |
| FFN中間 `[S, 14336]` BF16 | 約1,063 MiB |

しかもFFNでは、`fc1` の出力に加えてSiLUや乗算結果も生成される。

現在の `H3MLP.forward()` は、実質的に次の処理を一括実行している。

```
gate, value = self.fc1(x).chunk(2, dim=-1)
return self.fc2(F.silu(gate) * value)
```

これはチャンク化による節約余地が非常に大きい箇所だ。

一方、すでにVAEデコードは窓化され、テキストエンコーダも層ごとの直接読み込みに変更されている。今回、真っ先に取り組むべきはその部分ではない。

## 2. 有望な改善策の詳しい検討

### A. FFNのチャンク化（最優先候補）

FFNはAttentionと違い、トークン同士の相互作用がない。つまり、入力系列を分割して計算し、結果を元の順番に戻しても、数学的には同じ出力になる。

FFNを4,096トークン単位で処理するイメージ: 一括実行のFC1出力 2,126 MiB → 4,096行チャンクのFC1出力 224 MiB。単一のFC1中間テンソルで約90%減。モデル全体のVRAMが90%減るという意味ではない。

実装は比較的簡単だ。`H3MLP.forward()` にチャンクループを追加し、最終出力の領域だけを確保して、チャンクごとの計算結果を書き込んでいく。

重要なのは、現在の `comfy_kitchen.int8_linear` のConvRotが特徴量方向に適用され、活性値の量子化も行単位であることだ。トークン方向で分割しても、量子化グループを切断するわけではない。

そのため、チャンク化によって量子化精度をさらに落とす必要はない。ただし、GEMMの分割形状が変わることで浮動小数点の丸め結果が多少変わる可能性はあり、ビット単位の一致は実測で判定する必要がある。

### B. AdaLNの展開を減らす（最優先候補）

`dit.py` の `_modulate()` と `_gate()` では、次のような処理がある。

```
out = scale.index_select(0, idx)
out.add_(1.0)
out.mul_(x)
out.add_(shift.index_select(0, idx))
```

`scale` と `shift` は少数の時刻とモダリティから求められる。しかし、`index_select` によって約3.9万行のFP32テンソルへ展開される。

映像トークンの大部分が同じ変調パラメータを使う。映像系列がすべて同じ時刻・モダリティの組み合わせを使うなら、対応する5,376要素のベクトルをブロードキャストすればよい。行ごとに変調ベクトルを複製する必要はない。さらに映像行をチャンクで処理すれば、巨大なFP32の一時領域まで縮小できる。`_gate()` にも同じ考え方を適用できる。

実装の難易度を抑えるなら、まずは大きな映像領域だけにこの方式を適用し、テキストや条件行には既存の処理を残すのが安全だと思う。

### C. Block Swapを画角に応じて調節する

現在の `block_swap_prefetch.py` は、先読み時に原則として `blocks_on_gpu + 2` 個のGPU側arenaを確保する。H3では既定値が8なので、合計10個だ。

| 常駐ブロック数 | Arena数 | 概算GPU領域 |
| --- | --- | --- |
| 8（現行） | 10 | 約3.69GB |
| 6 | 8 | 約2.95GB |
| 4 | 6 | 約2.21GB |
| 2 | 4 | 約1.48GB |

解像度やフレーム数が大きくなるほど、GPUが1ブロックを計算する時間も長くなる。すると、CPUから次のブロックを転送する時間を隠すために必要な先読みブロック数は、むしろ少なくて済む可能性がある。小さな動画には8ブロック、大きな動画には2〜4ブロック、という調整が合理的かもしれない。転送する重みの総量は変わらない。

注意点として、現在の `_place_dit()` はBlockSwapServiceを再利用している。自動調節を導入するには、サービス側の常駐数をジョブごとに安全に変更できるようにする必要がある。最初は自動調節を実装せず、固定値を変えた実験だけで効果を測るのがよいと思う。

### D. AttentionのQKV生成とRoPEを省メモリ化する

優先順位はA〜Cより低いが、長尺動画への対応では重要になりそうだ。QKV本体と変換後のQ・Kが同時に存在することでVRAMピークが上がりうる。考えられる改善は、QKVをチャンクで生成すること、QとKの変換に必要な一時バッファを減らすこと、あるいはQの系列を分割してAttentionを実行することだ。

H3は映像・音声・テキストの全系列をFull Attentionで処理するため、時間方向に分割して独立にAttentionを計算する方法は不可だ。KとVを全系列ぶん用意し、Qだけを分割するなら、全トークンへの参照を維持したまま計算できる。現在のQKV一括投影をそのまま残してQだけ分割しても、投影時のピークは改善しない。投影自体の分割や重みの行方向スライスまで踏み込む必要がある。第2段階の改善候補だろう。

### E. FlashAttention系の実行確認

`F.scaled_dot_product_attention()` を呼んだだけでは、実際にどのCUDAバックエンドが使われたかは確定しない。`torch.nn.attention.sdpa_kernel(SDPBackend.FLASH_ATTENTION)` で診断する。SageAttentionは内部で低精度量子化を利用する実装を含む。今回の「精度を落とさない」という条件では、新たな最適化手段としては選ばず、比較試験の基準をSDPAに統一したい。

### F. VRAMの断片化と実使用量を計測する

VRAM 16GBなのに、専用VRAM使用量12.8GBの時点で共有GPUメモリ3.7GBを使用したのはなぜか？ 実際に確保された領域と、PyTorchのキャッシュとして予約された領域、GPUドライバから見える利用量は区別する必要がある。`max_memory_allocated()`・`max_memory_reserved()`・`memory_stats()`・`mem_get_info()`・Windows の共有GPUメモリ・CUDAメモリスナップショット。Block Swapのarena ringは理にかなっているので、安易に撤去するべきではない。断片化が主犯なのか、生存テンソルのピークが主犯なのかを最初に切り分けたい。

## 3. 改善策の優先順位

| 改善策 | VRAM削減の期待 | 実装負担 | 精度 |
| --- | --- | --- | --- |
| FFNのチャンク化 | 非常に大 | 小〜中 | 数学的に維持 |
| AdaLNの分割・ブロードキャスト | 大 | 中 | 数学的に維持 |
| Block Swapの常駐数調整 | 中〜大 | 小〜中 | 維持 |
| QKV生成・RoPEのメモリ削減 | 中〜大 | 大 | 数学的に維持可能 |
| Flash SDPA経路の確認 | 状況次第 | 小 | 近似量子化なし |
| アロケータの調整 | 状況次第 | 小〜中 | 維持 |

## 4. 目標解像度まで拡張するとどうなるか

| 動画条件 | 系列長の概算 | FC1出力だけの容量 |
| --- | --- | --- |
| 896×1152・124f | 3.9万 | 2.1GiB |
| 1280×768・260f | 7.6万 | 4.1GiB |
| 1920×1088・124f | 7.8万 | 4.2GiB |
| 1920×1088・141f | 8.8万 | 4.7GiB |

チャンク化してしまえば、FC1のピークが全系列長に比例しなくなる。Attentionは全系列を参照するので計算量が系列長の2乗に比例する。VRAM溢れを解決できても、MiniMax H3がLTX系と同じ生成速度になるとは限らない。

## 5. 私ならこう実験する

1. 現状のメモリピークを分解計測（896×1152・124f、1〜2ステップ）。
2. FFNを4,096行単位でチャンク化（2,048・8,192も比較）。
3. AdaLNの巨大な展開を縮小（まず映像領域から）。
4. Block Swapの常駐数を実測で決定（8・6・4・2）。
5. 長尺・大画角の検証（1280×768・260f、1920×1088・124f）。

精度の検証については、保存済みの生成動画のハッシュだけでなく、各ブロックやDiT最終出力を比較できる仕組みがあると便利だ。ビット一致・数値誤差・最終動画の変化を区別して判断するのがよい。

## 6. もう一つの発想：VRAM最適化をH3だけで終わらせない

利用可能VRAMと系列長を入力にして、FFNチャンクサイズとBlock Swapの常駐数を決定する「メモリ予算管理」の仕組みを設ける。最適化の実装そのものは各エンジンに残す。共通化するのはVRAMの計測、予算判定、設定値の選択という部分だ。

## 結論

FFNのチャンク化＋AdaLNの省メモリ化＋Block Swap常駐数の調整という組み合わせを、§1-101の中心的な改善方針として提案したい。
