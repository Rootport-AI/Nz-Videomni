# R1 MiniMax H3 のノイズ除去の段の VRAM の棚卸し（2026-10-18・読み取り専用の調査）

## 1. 結論

1. **割り当て量（`max_memory_allocated`）は、コードから作った式でほぼ全部説明できる。** 式による見積もりと実測の差は P1 で −3〜−26MiB、P2 で +19MiB しかない（どちらも 0.4% 以内）。内訳は次の 3 つ。
   - 重み 5,239MiB。画角によらず一定。
   - 1 ブロックの前向き計算の活性化（途中で作られる一時テンソル）の山。系列長に比例する。
   - その他 数十 MiB。
2. **P2 の溢れの直接の原因は「予約と割り当ての差」4,021MiB である。** P2 の割り当てのピークは 12,807MiB で、物理 VRAM（16,376MiB）に約 3.5GB の余裕があった。ところが予約（割り当て器が抱えている量）のピークは **16,828MiB で、物理 VRAM を越えている**（`outputs/dc9491a2-…/metadata.json` の `h3.phases.denoise.peak_vram_reserved_mb`）。依頼文の「12,807MB（専用）＋共有 3.7GB」の 12,807 は割り当ての値で、予約の値ではない（`engine_h3/pipeline_h3.py:330-333`）。
3. **予約と割り当ての差は、系列長にきれいに比例している。** P1 は 913〜944MiB、P2 は 4,021MiB。どちらも「bf16 の [S, 5376] のテンソル 1 本」の約 9.6〜9.9 本ぶんで、活性化の山に対する比はどちらも約 0.54（sage の場合）である。したがってこの差は重みではなく、**活性化の大きさの違う一時テンソルが割り当て器の中で生む隙間（断片化）**とみるのが自然である。ただし仕組みそのものは推測で、メモリのスナップショットでの確認はしていない。
4. **活性化の山は、sage（SageAttention）の呼び出しの瞬間にある。** 「bf16 の [S, 5376] のテンソル 1 本」（以下 U と書く）の 18.33 本ぶんで、P2 では 7,475MiB になる。このうち約 2,174MiB は同じ内容の重複である。
   - q・k・v を連結した元のテンソル `qkv` が呼び出しの間ずっと生きている。
   - sage へ渡すために `.contiguous()` で q・k・v を写し直している（`engine_h3/dit.py:196`）。
5. **画角によらない固定費が 2 つある。**
   - 先読みのアリーナリング（GPU 上の重みの受け皿を固定本数で使い回す仕組み）: 10 本×371MiB＝3,711MiB。
   - token_refiner（テキストだけを整える 2 ブロック。**bf16 のまま**で量子化されていない）: 1,470MiB。ループの前に 1 回使うだけなのに、ノイズ除去の段のあいだ GPU に残る。

### 説明できなかった残り

- **割り当て量**: P1 は −3〜−26MiB（式がわずかに多い）、P2 は +19MiB。実質 0 である。
- **予約と割り当ての差**: P1 は 913〜944MiB、P2 は 4,021MiB。量は実測だが、内訳（どの大きさの空き領域がいくつあるか）はコードからは出せない。

## 4. 問いへの答え

### 問い 1. FFN（各ブロックの前向き全結合層）の構造と幅

- **事実**: SwiGLU（ゲート付きの活性化関数）。ただし層は 2 本で、`fc1` が [gate; value] を連結して出す（`dit.py:239-249`、`h3_format.py:152`）。中間幅は ffn＝14,336。G2 の門で使った [28672, 5376] は fc1（2×14,336 行）にあたる。
- 1 ブロックで同時に生きているテンソルは §3.2 の表のとおり。fc1 の出力 bf16 [S, 28672]（2·S·28672 バイト＝5.33U）は、`gate`・`value` が view として参照しているので、fc2 が終わるまで解放されない（事実）。

### 問い 2. AdaLN の変調の適用

- **事実**: 行ごとに `[S, d]` へ展開（gather）している。shift／scale／gate のどれも `index_select(0, idx)` で f32 の [S, 5376] を作る（`dit.py:276-296`）。区間ごとの適用はしていない。
- dtype は f32。変調そのものは f32 で計算し、最後に bf16 へ戻す。1 回あたり、展開した scale と shift の 2 本（2U×2）が同時に生きる。P2 では 1 本 815MiB、同時に 1,631MiB。
- 1 ブロックで 4 回（変調 2 回・ゲート 2 回）起き、最終層でも映像の行の分だけ起きる（`dit.py:528`）。§3.2 のとおり、これはブロックの山そのものではない。

### 問い 3. attention（注意計算）の経路

- **事実（`dit.py:190-199`・`224-236`）**:
  - SDPA（PyTorch 標準の注意計算）は `F.scaled_dot_product_attention(qh, kh, vh)` で呼ぶ。マスクなし・`is_causal` は既定の偽・`scale` は既定（D^-0.5）・dropout なし。
  - 入力は bf16・head_dim 128・形 [1, 56, S, 128]。
  - 入力は `[S, H, D]` を `transpose(0,1)` した view で、連続ではない。v は `qkv` の view で、行の間隔は 21,504 要素である。最後の次元は連続。
- **RoPE 後の q・k は f32 の写しにならない（事実）**: `cos`／`sin` を先に x の dtype（bf16）へ変換し、bf16 で計算する（`rope.py:391-394`）。cos／sin の表そのものは f32 [S, 96] で、ノイズ除去の段のあいだ GPU に置かれる（`pipeline_h3.py:723-724`）。
- マスクもバイアスも実体化していない（事実）。系列全体を区切りなしで 1 回の呼び出しにしている。
- **sage の経路（事実）**:
  - q・k・v に `.contiguous()` を掛けて HND の並び（[バッチ, ヘッド, 系列, 次元]）で渡すので、3 本の写し（各 1.33U）ができる。
  - SageAttention 2.2.0 の sm89（RTX 40 系）の経路は `sageattn_qk_int8_pv_fp8_cuda` で、CUDA 12.8 以上なので `pv_accum_dtype="fp32+fp16"` になる（`sageattention/core.py:162-168`）。
  - この経路は int8 の q・k、出力 `o` を作り、さらに v を bf16 で転置・パディングした一時テンソル（1.33U）と fp8 の v（0.67U）を作る（`core.py:745-760`、`quant.py:276-283`）。
  - sage は `tensor_layout="NHD"` も受け付ける（`core.py`）。H3 は HND で呼んでいる。
- **SDPA が落ちるカーネルについてコードから言えること**: 次の条件はすべてフラッシュ注意（flash）の要件を満たす。bf16・head_dim 128・マスクなし・dropout なし・勾配なし・sm89・最後の次元が連続。
  - 計算をそのまま行列にする経路（math）でないことは、実測から言える。math なら注意の得点 [56, S, S] を作るので、P1 でも bf16 で 9.1GiB になり、実測の 6.6GiB の山に収まらない。
  - flash と mem-efficient（省メモリ版）のどちらかは確認できなかった（Windows 版の torch 2.13 の wheel に flash が入っているか未確認）。どちらでも、余分なメモリは系列長に比例する程度で、P1 の一致から見て山には効いていない。

### 問い 4. `H3Int8Linear.forward`

- **渡しているもの（事実。`quant_linear.py:101-121`）**:
  - 活性化は `x.reshape(-1, K)` を bf16 にして `.contiguous()` した 2 次元のテンソル。
  - 重みは int8 [N, K]、スケールは f32 [N, 1]、バイアスはなし（本体の 4 層は bias なし）。
  - `out_dtype=bf16`、`convrot=True`、`convrot_groupsize` はファイルの記述どおり（公式ファイルでは 256。`quant_specs` が報告される）。
- **呼び出し側でのチャンク化（行を分けて少しずつ計算すること）はない（事実）**。行全体を 1 回で渡している。
- **comfy-kitchen 0.2.37 の CUDA 経路の中（事実。`comfy_kitchen/backends/cuda/__init__.py:2035-2290`）**:
  - K＝5,376／7,168／14,336 はどれも 256 の倍数かつ 16,384 以下で、共有メモリの条件（K＝14,336 で 90,112 バイト）も sm89 の上限の内である。したがって活性化の回転と量子化を 1 つのカーネルで行う経路に乗る。
  - そこで作られるのは、int8 の活性化 [m, K]（m×K バイト）と f32 の行ごとのスケールだけ。
  - 行列積は CUTLASS（NVIDIA の行列積の部品集）の逆量子化つきカーネル（major≥8）で、bf16 の出力 [m, N] へ直接書く。int32 の中間結果は cuBLAS へ落ちたときにしかできない（`_prefer_cublas_int8_fallback` は常に偽）。
- 出力は bf16。

### 問い 5. block swap（ブロックの出し入れ）

- **`blocks_on_gpu` の決まり方（事実）**: 画角では変わらない。
  - `config.yaml:89` の `block_swap_blocks_on_gpu: 8`
  - → `services/engines/h3/adapter.py:372`（`... or DEFAULT_BLOCKS_ON_GPU`。既定 8、`adapter.py:97`）
  - → ワーカーのロード（`engine_h3/worker.py:235`）
  - → `H3LoadOptions.blocks_on_gpu`（`pipeline_h3.py:118`）
  - → `BlockSwapService(blocks_on_gpu=n, hold_arenas=True)`（`pipeline_h3.py:657-658`。プロセスに 1 回だけ作る）
- **先読みの受け皿（事実）**: `hold_arenas=True` なので、`prepare()` で最大ブロックの大きさの領域を min(50, 8+2)＝**10 本**、GPU に確保し、`teardown()` まで持つ（`block_swap_prefetch.py:401-407`）。定常状態で同時に GPU にあるブロックは 9 本（窓 8＋解放待ち 1。同ファイルの説明文 113-115 行）で、1 本は予備である。

### 問い 7. アロケータ（GPU メモリの割り当て器）

- **`PYTORCH_CUDA_ALLOC_CONF`／`PYTORCH_ALLOC_CONF` は H3 のどこでも設定していない（事実）**。ワーカーが設定する環境変数は `TORCH_COMPILE_DISABLE=1` だけ（`engine_h3/worker.py:87`）。LTX 2.5 のアダプタは意図して設定しない（`services/engines/ltx25/adapter.py:662-667`）。
- **`hold_arenas` 相当の手当ては、H3 に既にある（事実。`pipeline_h3.py:658`）**。重みの出し入れによる断片化は、これで抑えられているはずである。
- **予約と割り当ての差（P1 で約 0.9GB）を説明できる要因**:
  - 差は実測で、系列長に比例している（P1・P2 とも約 9.9U。§3.3）。重みは画角によらず一定なので、**重みでは説明できない**（実測からの推論）。
  - 活性化の大きさは種類が多い（0.5U・0.67U・1U・1.33U・2U・2.67U・4U・5.33U）。segmented（従来型）の割り当て器の中で、これらが互いに切り分けられて隙間が残り、予約が膨らむ、とみる（**推測**。メモリのスナップショットは未取得）。
  - 隙間が物理 VRAM を越えても解放されない理由は、Windows の共有メモリへの退避（sysmem fallback）にあるとみる（**推測**）。退避があると確保の失敗が起きない。通常、割り当て器は確保の失敗をきっかけにキャッシュを返して再試行するので、そのきっかけが無いことになる。LTX 2.5 の連結生成でも、「チャンクごとの `empty_cache` が無いと予約が断片化して共有メモリへ溢れる」という同種の観察がある（`engine25/chain25.py:755-759`）。

## 5. 確認できなかった点

1. 予約と割り当ての差 4,021MiB の内訳。どの大きさの空き領域が残っているかは、`torch.cuda.memory_snapshot()` などの実測が要る。
2. SDPA が flash と mem-efficient のどちらに落ちているか。Windows 版の torch 2.13＋cu130 の wheel に flash が入っているかを確かめていない。
3. torch 2.13 の `nn.RMSNorm` が bf16 で融合カーネル（`_fused_rms_norm`。ヘッダは wheel にある）を使い、f32 の一時テンソルを作らないこと。式はこの前提で書いた。また、`q_norm`／`k_norm` へ連続でない view を渡したとき、内部で写しを作るかどうか。
4. CUTLASS のカーネルが実際に選ばれ、cuBLAS（int32 の中間結果）へ落ちていないこと。条件はコードで満たしているが、実行時に確かめていない。
5. 実行時の最大ブロックの大きさ（ログ「pinned staging pool = 2 x … MB」の値）。式では 371.1MiB、コメントでは 369MB。
6. 共有 GPU メモリの 3.7GB のうち、このプロセスの分と他のプロセスの分の比率。タスクマネージャーの数え方（ページ固定の主メモリを含むか）も確かめていない。
7. 1 ステップ約 200 秒への減速が、共有メモリへ退避した領域のうち生きた活性化の分によるのか、使われていないキャッシュの分なのか。WDDM がどの確保を VRAM に残すかはコードからは分からない。
8. engine25（ltx_core）の DiT の中の活性化の扱い（FFN の分割の有無など）。
