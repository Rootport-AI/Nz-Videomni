# 敵対的レビュー: MiniMax H3 の VRAM 溢れの犯人を確定する計測計画（playful-juggling-reef.md）

レビュー 2026-10-18。読み取りのみ（torch は import していない。ソースと既存の記録を読んだ）。
注意: この報告は、依頼された置き場（scratchpad\h3vram\REVIEW_plan_measure.md）ではなく、プランモードで書くことを許された唯一のファイル（本ファイル）に書いた。監督が scratchpad へ写してほしい。

## 結論

- **Critical 0・Major 8・minor 13。**
- 総評: 仮説の立て方と腕の構成は筋がよく、数値の大半（系列長 ≈ 40,415・U ≈ 414MiB・T1／T2／T3／T4 の割り当ての予測・H2 の差 1.5GB・受け皿 n+2 本）は R1／R2 の式から正しく出ている。上限の設定（割り当て器の上限）を「Linux なら起きる確保の失敗とキャッシュの解放」の再現として使う発想も妥当。
- ただし、**H1 の判定の中心にある 2 つの読み方に穴がある**。(1) 1 ステップ目の終わりのスナップショットは「ピークの瞬間の隙間」を写さない（予測の「未使用 約 4GB」は、その時点では約 11.7GB になる）。(2) 共有メモリの「基準」が何か決まっていない。さらに、**採取器の LUID が古いと共有メモリが黙って 0 になる**ため、溢れが「消えた」と誤読しうる。
- 時間の比較（H3・H4）は、履歴の採取を入れた T3 を時間の比較に使う矛盾と、上限の下で起きるキャッシュの解放と再確保の費用が混ざる点を直せば使える。
- 製品コードを変えない約束は守れる作りだが、「1 腕 1 プロセス」を明記しないと設定が黙って無視される（ワーカーとパイプラインがプロセスに 1 回しか作らない部品を持つため）。

## Major

### M1. H1(a) の予測と、スナップショットを取る時点が合っていない
- **どこ**: §1 の H1 の予測 (a)、§2「1 ステップ目の終わりに割り込む方法」、§4 `snapshot_report.py`
- **何が問題か**: progress の index 1 は、1 ステップ目の 50 ブロックが終わり、`del tokens`・`del v_video_rows…` の**後**に呼ばれる（`engine_h3/pipeline_h3.py:767`・`772`・`773`）。この瞬間には活性化はすべて解放済みで、割り当て中に残るのは重み 5,239MiB と小物だけ。一方、予約はステップの間に `empty_cache` が無いので約 17,000MiB のまま（R1 §4 問い 6）。したがって、その時点のスナップショットの「未使用の予約」は **約 17,000−5,300 ≈ 11,700MiB** になり、予測の「約 4GB」とは一致しない。予測が外れて「仮説を疑う」方向へ誤読される。また、その時点の空き領域は全部が活性化の大きさなので、「大半が活性化の等級の隙間」は自明に当たってしまい、判定の役に立たない。
- **根拠**: `pipeline_h3.py:756-773`（ステップの中の生存と progress の位置）、`pipeline_h3.py:795`（`empty_cache` はループの外の `finally` だけ）、R1 §3.3（ピーク時の予約−割り当て 4,021MiB）。
- **直し方の案**:
  - 予測 (a) を「**割り当てがピークだった瞬間**の未使用の予約が約 4,085MiB（9.86U）」と書き直す。
  - `snapshot_report.py` は、スナップショットの `device_traces`（確保と解放の履歴）を逆にたどって、割り当てが最大になった瞬間のセグメントの状態を復元する（pytorch の `_memory_viz` と同じ考え方）。その瞬間の空きブロックの大きさの分布と、「新しいセグメントの確保（`segment_alloc`）のうち、要求より小さい空きブロックの合計は足りていたのに、要求を入れられる 1 個の空きが無かったもの」の件数と量を出す。後者が断片化の直接の証拠になる。
  - `memory_stats()` の `inactive_split_bytes`（分割されて返せない空き）と `num_alloc_retries`・`num_ooms` も、index 1・2 で記録する（存在は `torch/cuda/memory.py:251-285` で確認）。
  - 履歴の件数の上限（`max_entries`）は、ノイズ除去の 1 ステップ目のピークまでの履歴が切れない大きさにする（エンコードの段から履歴が始まるため）。

### M2. T3 は履歴あり（時間に影響しうる）なのに、H3 の時間の比較（T4 との対比）に使っている
- **どこ**: §2「メモリスナップショット…時間の比較に使う腕では切る」と §3 の T3（履歴あり）・T4（T3 と比較）
- **何が問題か**: 方針と腕の表が食い違う。さらに、index 1 で `_dump_snapshot` を呼ぶと、そのぶん index 1→2 の間隔（2 ステップ目の時間）が伸びる。index 0→1（1 ステップ目）は DiT の最初の先読みの立ち上がりを含むので、時間の代表に使いにくい。結果として、T3 からは**きれいな 1 ステップの時間が 1 本も取れない**。
- **根拠**: `pipeline_h3.py:748`（index 0 はループの前）・`773`。
- **直し方の案**（腕は増やさない）:
  - progress を包む関数の中で、入ったときの時刻と、スナップショットを書き終えた時刻の両方を記録する。2 ステップ目の時間は「index 2 の時刻 − index 1 で書き終えた時刻」とする。
  - 履歴の採取そのものの負担は、1 ステップ数千回の確保に Python の呼び出し元を付ける程度で、数十秒のステップに対して小さい（推測）。T3 の履歴はあえて残す（理由は M7 と minor m9: OOM〔メモリ不足で止まること〕が起きたときに、その瞬間の状態を履歴から復元できる唯一の手段になる）。
  - 時間の代表は「2 ステップ目」と計画に明記する。

### M3. 「1 腕 1 プロセス」が明記されていない。同じプロセスで腕を回すと設定が黙って無視される
- **どこ**: §2「経路」、§4 `measure_h3_vram.py`
- **何が問題か**: 2 か所で、最初の設定がプロセスに残る。
  - `_do_load` は `_PIPE` があると読み込みをせずに `ready` を返し直すだけ（`engine_h3/worker.py:208-213`）。attention・常駐の数・先読みの読み込み時の設定は変わらない。
  - `BlockSwapService` はプロセスに 1 回だけ作られ、`blocks_on_gpu` は作ったときの値に固定される（`pipeline_h3.py:657-658`）。T5a／T5b を T4 と同じプロセスで回すと、受け皿は 10 本のまま。
  - `set_per_process_memory_fraction` も、そのプロセスの後の全部の確保に効き続ける。
- **直し方の案**: 「1 腕 1 プロセス（台本を腕ごとに起動し直す）」を §2 に明記する。`run.json` に、実際に効いた値の証拠を書く。具体的には、`_PIPE.build_report` の `blocks_on_gpu`・`attention_backend`（`pipeline_h3.py:436-437`）、`done` の `attention_used`・`block_swap_prefetch_used`、受け皿の本数（`_PIPE._swap_service` の受け皿の一覧の長さ、またはログ「arenas …」の行。`block_swap_prefetch.py:403-413`）、`torch.cuda.get_per_process_memory_fraction()` の値。台本はこれらが引数と合わなければ失敗にする。

### M4. 共有メモリの判定の「基準」が決まっていない
- **どこ**: §1 の H1 (b) の予測「共有メモリの中央値が基準（小さい画角）と同程度に戻り」、§2「判定は COMFORT_LIMIT_TABLE §4.2 の v3 に合わせ」
- **何が問題か**: 判定規則 v3 の基準点は「**同じ解像度**の基準点」（`Docs/COMFORT_LIMIT_TABLE.md:202`）。この計画の B（640×384）は解像度が違うので、v3 の文面には当てはまらない。何と比べて +300MB を見るのか（T0 の窓か、その腕自身の読み込み前か、絶対値か）が書かれていない。さらに、採取器のカウンタはアダプタ全体の値で（`vram_sampler2.ps1:31`）、他のプロセスの増減も入る。ページ固定の主メモリ（先読みの 2×371MiB）が共有の側に数えられる可能性もある（推測。R1 §1「説明できなかった残り」と同じ論点）。
- **直し方の案**: §2 に次の 2 行を足す。
  - 「基準＝T0 のノイズ除去の窓の共有メモリの中央値（先読みの受け皿と固定のプールは画角によらず同じなので、固定の分が相殺される）。判定は v3 の閾値（+300MB）を借りるが、v3 そのものではない（基準の画角が違う）と RESULTS に明記する」。
  - 「各腕で、読み込み前の約 10 秒の待機の共有メモリも記録し、他のプロセスの変化を補正する」。採取器はすでに読み込み前から動かせる形（`calib.py:642-673` の `Monitors`）。

### M5. 採取器の LUID が古いと、専有も共有も黙って 0 になる
- **どこ**: §4「LUID の取得も同ファイルの方法に倣う」、§5 G-M1・G-M2
- **何が問題か**: 採取器は、カウンタのパスに LUID（アダプタの識別子）が含まれる行だけを拾う。一致しなければ 0 を書き続け、例外にならない（`vram_sampler2.ps1:32-40`）。LUID は起動のたびに変わりうる（推測。`calib.py` が `luid.json` を保存し、`--refresh-luid` を持つのはそのため。`calib.py:570-586`・`2638`）。10-04 の `luid.json` を写して使うと「共有 0MB＝溢れなし」と誤読し、H1(b) を誤って「支持」にしうる。G-M2 は「行がある」ことしか見ない。
- **直し方の案**: 台本は毎回 LUID を取り直す（キャッシュを使わない）。G-M1 の dry-run（試運転）と G-M2 に「`wddm.csv` の専有の値が 0 でなく、読み込み前の待機で数百 MB 以上ある」を足す。

### M6. T5b（常駐 2）の予測値が誤っている
- **どこ**: §3 の T5b「割り当て −2,968」
- **何が問題か**: 計画自身の式は −371MiB×(8−n)。n＝2 なら 8−2＝6 本減って **−2,226MiB**（受け皿 10 本→4 本）。−2,968 は 8 本分で、式と合わない。事前に登録した予測が誤っていると「外れたら仮説を疑う」の判断を誤る。
- **根拠**: `block_swap_prefetch.py:403`（`min(len(blocks), blocks_on_gpu + 2)`）、R1 §3.1（1 本 371.08MiB）。T5a の −1,484（4 本分）は正しい。
- **直し方の案**: T5b を「割り当て −2,226（受け皿 4 本）」に直す。予約も同じ量だけ下がるはず、と書き添える。

### M7. 上限の下での時間（H3・H4）に、キャッシュの解放と再確保の費用が混ざる
- **どこ**: §1 の H3・H4、§3 の T3〜T5b
- **何が問題か**: 上限を超える確保があると、割り当て器はキャッシュを解放して確保し直す（この振る舞いの説明は minor m1）。そのたびに全ストリームの同期と `cudaFree`／`cudaMalloc` が起きる。WDDM ではこれが遅い（推測）。
  - sage（T3）と sdpa（T4）では、上限にぶつかる回数が違う。T4 の予約の予測は約 15,300 で上限 13,920 を超えるので、T4 もぶつかる。常駐 2（T5b）では受け皿が 2.2GB 減って、ほとんどぶつからなくなりうる。
  - そのため、「sdpa が速い」「常駐を減らしても遅くならない」が、計算そのものの差でなく「解放と再確保の回数の差」で出てしまう恐れがある。
- **直し方の案**（腕は増やさない）: 各腕で、index 1・2 の時点の `num_alloc_retries`・`num_device_alloc`・`num_device_free` を記録し、RESULTS の時間の表に並べる。回数が腕の間で大きく違うときは、時間の比較を「判定不能」か「参考」にする規則を、計画の時点で決めておく。補足: T2 が溢れなかった場合は、T2 と T4 の差が sdpa の「上限の費用」そのものになる。これは追加の費用なしで得られる情報なので、RESULTS に書く。

### M8. T6 の合成試験が、製品の q・k の並びを写していない
- **どこ**: §4 `sdpa_int32_probe.py`「`[S,3,56,128]` から `unbind` した view の v と `.contiguous()` の v」
- **何が問題か**: 製品では、q と k は RoPE の後の新しい連続テンソル（行の刻み 7,168）で、v だけが `qkv` の view（刻み 21,504）（R2 §5-3、`dit.py:229-230`、`rope.py:175-184`）。試験で q と k も同じ `[S,3,56,128]` の view にすると、q の側の位置の掛け算（`(q_start+query_start)*q_strideM`、R2 §5-3）も S≈99,968 で溢れる。すると「v を連続にすれば起きない」の腕でも q 側の溢れで不一致かエラーになり、H5 の後半を誤って「不支持」にする。
- **直し方の案**: q・k は連続の `[S,56,128]` を `transpose` した view（製品と同じ）にして、変えるのは v だけ、と明記する。正解は「v を連続にした版」とする（刻み 7,168 では S≈299,593 まで溢れない）。

## minor

- **m1（2(a) の確認）**: `set_per_process_memory_fraction` の docstring は「上限を超える確保は割り当て器の中で OOM を出す」としか書いていない（`torch/cuda/memory.py:173-197`）。キャッシュを解放して確保し直す動きは C++ の割り当て器の中にあり、wheel には C++ のソースが無いので、ここでは上流の実装の知識による（推測）。上流では「上限を超える `cudaMalloc` を失敗とみなす → 使っていないキャッシュのブロックを解放して再試行 → 全部のキャッシュを解放して再試行 → それでも駄目なら OOM」の順で、Linux で本物の確保の失敗が起きたときと同じ道を通る。ただし解放できるのは「**中に使用中のブロックが 1 つも無いセグメント**」だけで、分割されて一部が使用中のセグメントは返せない。この区別が「返せる断片化」と「返せない断片化」の境目なので、H1 の説明に 1 行足すとよい。`num_alloc_retries` が増えていれば、この解放の道を通った証拠になる（M1・M7）。
- **m2（2(c) の確認・問題なし）**: `_Phases.phase("denoise")` が段の頭でピークの記録を戻すのは、DiT の読み込みより前（`pipeline_h3.py:315`・`476`）。index 1・2 の時点の `memory_stats` の peak は、ノイズ除去の段の頭からの値になる。`finally` の `empty_cache`（`pipeline_h3.py:795`）は index 2 の後なので、index 2 の採取はそれより前で正しい。ただし、OOM のときは例外が `finally` を通ってから台本へ届くので、その時点で `empty_cache` 済みになり、状態は消えている。これが T3 に履歴を残す理由になる（M2）。
- **m3**: `engine_h3.worker` を import すると `os.chdir(ROOT)` でリポジトリのルートへ移る（`worker.py:91`）。台本の `runs/<label>/` などの相対パスは、リポジトリのルートに書かれる。出力先は import の前に `Path(__file__).resolve()` から絶対パスで決めておく。
- **m4**: progress を包む関数は `time.time()`（壁時計）も記録する。採取器は壁時計（`vram_sampler2.ps1:41-44`）、dmon は `-o DT` なので、窓を切るのに必要。時刻を取る前に `torch.cuda.synchronize()` を入れる（メモリの状態は変えない。ステップの境目が GPU の実際の終わりと揃う）。
- **m5**: 「他のプロセスの VRAM」の切り分けには、`mem_get_info` だけでなく、Windows のプロセスごとのカウンタ `\GPU Process Memory(*)\Dedicated Usage`・`Shared Usage` を、読み込みの前と index 1 の時点で 1 回ずつ取るとよい。どのプロセスがいくら持っているかが出るので、R1 の「説明できない 3.2GB」に直接効く。腕は増えない。あわせて、このプロセスの torch 以外の持ち分（CUDA の文脈・カーネルの像・CUTLASS の作業領域）の算出式を RESULTS に書く。式は「(total−free)@index1 − reserved@index1 − 他プロセス@読み込み前」。
- **m6**: 履歴の採取は `stacks="python"` にする。C++ の呼び出し元まで採ると、Windows では書き出しが非常に遅くなるおそれがある（推測）。引数は `_record_memory_history(enabled="all", context="all", stacks=..., max_entries=...)`（`torch/cuda/memory.py:985-995`）。G-M1 の試運転で、小さな確保 1 回と `_dump_snapshot` が通ることも確かめる（モデルは読まない）。
- **m7**: 文章のトークン数。セルフテストの既定のプロンプトは 41 トークン（R1 §2 の P1）で、計画の「32」とずれている。系列長への影響は 0.02% で結論には効かないが、§2 の数字は直す（系列長 ≈ 40,415）。
- **m8**: 主メモリ。オーナーの I2V の実測では、コミット量の山が **44.61GiB** だった（`outputs/dc9491a2-…/metadata.json` の `h3.commit_peak_gib`）。計画の「35〜43GB」より上。数字を直し、腕の間で待ち時間（クールダウン）を置き、次の腕の前に共有メモリとコミット量が待機の水準へ戻ったことを確かめる手順を足す（`calib.py` に同じ作法がある）。
- **m9**: T3 が OOM で止まった場合の扱い。G-M3 で「完走扱い」にするのはよいが、そのときは H3（溢れの無い sage の時間）が判定不能になる。上限を上げてもう 1 本走らせるかどうかは監督の提案とオーナーの了承で決める、と書いておく（計画の §3 末尾の原則のとおり。いま腕を足す必要は無い）。
- **m10**: 上限の値 0.85 の決め方。物理の 16,376MiB でなく、読み込み前の `mem_get_info` の free から「torch 以外の持ち分の見込み（約 0.5〜0.8GB。推測）」を引いた値の下に置く、という条件を足す。オーナーの機械の他のプロセスが 1.5GB を超えると、0.85 でもアダプタ全体では溢れうる。
- **m11**: sdpa の経路の確認を `run.json` に入れる。`torch.backends.cuda.is_flash_attention_available()` と `mem_efficient_sdp_enabled()` を記録する（R2 の「確認できなかった点」の 1 つが無料で埋まる）。T6 では、既定の選択のほかに `sdpa_kernel(SDPBackend.EFFICIENT_ATTENTION)` で強制した版も 1 回呼び、既定が mem-efficient であることを確かめる。
- **m12**: T6 の時間と負荷。S≈100,352・56 ヘッドの注意計算 1 回は数秒かかる（推測）。溢れるかどうかは行の刻みとキーの位置だけで決まり、ヘッド数には依らない。そこで `qkv` を `[S,3,56,128]` で作ったまま、ヘッドを 8 本ほどに切り出した view で試せば（刻み 21,504 は保たれる）、時間と VRAM を減らせる。画面表示の GPU で長いカーネルが走る心配（Windows の応答停止の検出と回復〔TDR〕）も下がる。
- **m13**: 文書。`Docs/VERIFICATION_LOG.md` の最後の節は §167（17,285 行目）で、**§168 は空いている**（§164 の 16,965 行目にも「次の番号 … 本書 §168」とある）。ただし慣例では、新しい節の末尾に「次の番号」の行を置き、台帳 `PENDING_TASKS.md` の 3 行目「最終更新」も直す。「文書の編集はこの 3 点だけ」と書くなら、この 2 つが含まれることを明記する。台帳 §1-101 の追記は「第 1 段（計測）済み・記録は VERIFICATION_LOG §168」とすれば、4 段のうちどこまで済んだかが分かり、結論は正本 1 か所（§168）に置ける。

## 観点ごとの答え（要約）

1. **仮説と予測の整合**: 系列長 37×(36×30)＋414＋41＝40,415（≈40,400・I2V 39,764 との差 +1.6%）、U＝2×40,415×5,376 B≈414MiB、T1 の 12,900／17,000、T2 の 11,380／15,300、H2 の差 3.67U≈1,520MiB、受け皿 n+2 本は正しい。誤りは T5b（M6）と H1(a) の時点（M1）。
2. **計測の妥当性**: (a) 上限の振る舞いは上流の実装どおりなら計画の想定どおり（m1。返せるのは丸ごと空いたセグメントだけ）。H1 の判定には使えるが、時間には M7 の混ざりがある。(b) 時間への影響は「書き出し時間を差し引く」で足りる（M2）。(c) 予約のピークの数値は取れるが、ピークの瞬間の形は履歴の復元が要る（M1・m2）。(d) 基準が曖昧（M4）。LUID の罠（M5）。(e) T2V で I2V を代えるのは妥当。系列長が 2% 以内、エンコードと符号化器は段の間の `empty_cache` で切れている（`pipeline_h3.py:547`・`568`）、オーナーの I2V でもエンコード 4.2GB・復号 7.6GB の予約は上限 13.9GB の内側。違いは他のプロセス（オーナーの I2V は AviUtl2 と操作パネルが動いていた）の分で、T1 が 3.7GB まで再現しなくても H1 は崩れない、と RESULTS に書く。
3. **腕の過不足**: 8 本で H1〜H5 は判定できる。追加の腕は不要。履歴の on／off の対照は要らない（履歴は確保の決定を変えないので、割り当てと予約の数値は比べられる）。先読み off の対照は目的の外。足すのは採取項目だけ（M1・M3・M7・m5・m11）。
4. **実行の危険**: 1 腕 1 プロセス（M3）、OOM は例外で返り、プロセスは生きる（台本で受けて `run.json` に書く）、不正なメモリアクセスは T6 だけで別プロセス（計画どおり）。主メモリは 44.6GiB の山を前提にする（m8）。自動許可については、python から PowerShell の採取器と `nvidia-smi dmon` を起こす形は較正台で通ってきた型なので、止められる可能性は低いと見る（推測）。止められたら迂回しない（計画 §5 のとおり）。
5. **成果物と文書**: §168 は空き（m13）。製品コードを変えない作りは守れる（台本はワーカーの関数とインスタンスの属性を包むだけ）。m3 の相対パスだけが、作業ツリーを汚すおそれ。
6. **過剰設計・逸脱**: 大きな逸脱は無い。上限を「診断の道具」と明記している点、mode の設計を範囲外にしている点はよい。T6 は犯人の確定そのものではないが、数分で済む事実の確認で、設計の先取りではない（そのままでよい）。
