# LTX 2.5 Outpainting — C0-prep（G0 = GO/NO-GO 関門）実測結果

実施日: 2026-08-26 / 実施環境: RTX 4070 Ti SUPER（16376 MiB）、`.venv-engine-ltx25`
**製品コードの変更は0行。git コミットなし。バックエンドHTTP不使用（`.venv-engine-ltx25`
から engine25 の部品を直接駆動）。GPUジョブは全件直列（各実行前に `nvidia-smi` で空きを確認）。**

数値の正本は同ディレクトリの `summary.json`。本書はその読み方と判定です。

## 結論

### **GO**（実装フェーズ C1 へ進んでよい）

2.3配布の In/Outpainting IC-LoRA は、**2.5のGGUF量子化 transformer 上でも緑センチネルを
完全に塗り潰しました**。しかも「LoRAを外すと塗り潰さない」という対照実験が
極めてきれいに出たため、これは偶然や別要因ではなく LoRA そのものの働きだと断定できます。

| 判定項目 | 結果 |
|---|---|
| G0-a（最重要）: 2.3 LoRA が 2.5 で緑を塗り潰すか | **GO**。緑残存率 0.000000（全73フレーム・pad帯全域）。対照腕（LoRAなし・参照あり）は 0.999817 |
| G0-b: LoRA強度 1.0 で足りるか | **足りる**。1.0 と 1.3 は緑残存率とも 0.0、keep領域PSNRは 1.0 のほうがわずかに良い（30.02 dB 対 29.50 dB）。**FE固定値の変更は不要**（別テーマ化も不要） |
| G0-c: VAE往復天井 | 実写素材 1280×768 で **43.77 dB**（2.3のC0-prep実測 42.81 dB と同等以上）。合格 |
| G0-d: VRAM | **要対処だが解決済み**。既定のまま全解像度 tiled_encode を通すと 16GB を大きく超える（下記）。ただし**タイル予算ではなく既存の `set_conv3d_memory_format` 一発で解決**する |
| G0-e: VAE空間ストライド / 128倍数キャンバス | ストライドは **32**（2.3の想定64ではない）。128倍数キャンバスは端数を一切落とさない。全16形状で実測一致 |

**想定外の発見が2件あります**（後述の「C1設計への申し送り」§1 と §2）。どちらも
C1 の設計に影響しますが、いずれも実装量を**増やしません**（片方はむしろ引き算です）。

## G0-a / G0-b — 2.3 LoRA は 2.5 で緑を塗り潰すか

### 実測条件

* キャンバス: 1280×768、4辺パディング（左右320 / 上下192）、内側640×384、73フレーム @ 24 fps
* 素材: `uploads/_outpaint_verify/w2_src_640x384_73f.mp4`（W2ゲートの実写クリップ）
* キャンバス生成: `services.video_io.pad_green_mp4`（アプリ層の製品コードをそのまま import）。
  センチネル純度は実測で確認済み（pad帯の緑一致率 1.000000 / keep領域 0.000000）
* 実行: **stage-1 のみ**。半解像度 640×384、8ステップ、ancestral（`DISTILLED_SIGMAS`）、
  `chain25` の stage-1 ループの作法をそのまま踏襲。参照は
  `reference25.reference_conditioning_from_pixels`（緑キャンバス半解像度・
  **デコード用に解決済みの tiling_config を直渡し**）、strength 1.0 / attention_strength 1.0
* ブレンド・アップスケール・stage-2 は一切行っていません（LoRAの効きだけを見るため）
* 全腕で同一シード（20260826）・同一プロンプト
* `reference_downscale_factor` は LoRAヘッダから 1 と解決され、参照は 640×384 で
  latent (1,128,10,12,20) にエンコードされました。LoRAは **480 Linear すべてに適合**

### 実測値

| 腕 | LoRA | 緑キャンバス参照 | pad帯 緑残存率(最悪) | pad帯 平坦度 | keep領域 PSNR(平均) | stage-1 |
|---|---|---|---|---|---|---|
| **lora10（製品経路）** | あり 1.0 | あり | **0.000000** | 41.59 | **30.02 dB** | 81.3 s |
| **lora13** | あり 1.3 | あり | **0.000000** | 41.36 | 29.50 dB | 68.7 s |
| **refnolora（対照A）** | **なし** | あり | **0.999817** | **2.04** | 28.74 dB | 57.8 s |
| **nolora（対照B）** | なし | **なし** | 0.000000 | 28.12 | **9.91 dB** | 48.7 s |

4辺別の緑残存率（平均）も同じ結論です。lora10 / lora13 は左右上下すべて 0.000000、
refnolora は左 0.9997 / 右 0.9999 / 上 1.0000 / 下 0.9997。

### 読み方

**対照Aが決定的です。** 同じ緑キャンバスを同じ強度で参照させ、LoRAだけを外すと、
2.5のベースtransformerは**緑をそのまま複写します**（残存率 99.98%、平坦度 2.04 =
無地のセンチネルそのもの）。LoRAを付けた瞬間に残存率が 0 になり、平坦度が 41.59 =
質感のある画に変わります。**塗り潰しているのは LoRA です。**

**対照Bは「緑残存率 0 だけでは合格にできない」ことの担保です。** 参照を外せば
入力に緑がないので残存率は当然 0 になりますが、keep領域PSNRは 9.91 dB —
元素材と無関係な画です。つまり「緑残存率 0」と「keep領域が元素材である」の
2つが揃って初めて意味を持ちます。製品経路は両方を満たしています
（0.000000 と 30.02 dB）。

代表フレーム（`g0a_*_f036.png` 等）を見れば一目です。lora10 は台所の情景が
四方に自然に伸びた1枚の画になっており、refnolora は中央の元映像の周りが
真緑のままです。

### G0-b の判定

強度 1.3 は 1.0 と同じく緑を完全に消しますが、keep領域PSNRが 30.02 → 29.50 dB と
わずかに劣化します（元素材からの逸脱がやや大きい）。目視でも構図が少し変わるだけで
質の向上は認められません。**1.0 で十分**であり、FE が固定送信している 1.0 を
変更する必要はありません（＝アプリ層改修の別テーマ化は**不要**）。

## G0-c — 2.5 VAE 往復天井

### 素材についての重要な注意

`uploads/_outpaint_verify/w2_src_1920x1080_73f.mp4`（W2ゲートのFHD素材）は
**実写ではなく合成のカラーバー＋細かい市松模様のテストパターン**でした
（`g0c_material_pattern_1280x768_orig_f000.png`）。彩度が振り切れた硬いエッジは
どのVAEにとっても最悪ケースで、同じ形状の実写素材より **13 dB 以上** 低く出ます。
そのため天井は2種類の素材で測り、両方を載せます。

* `real` = W2の640×384実写クリップ。640×384超の行は拡大されているため、
  **楽観側のブラケット**であって「その解像度の実写を測った値」ではありません
* `pattern` = 上記テストパターン。**悲観側のブラケット**

### 実測値（すべて 1行1プロセス）

| 素材 | 形状 | 往復PSNR（平均） | 最悪フレーム |
|---|---|---|---|
| real | 640×384 × 73f | 37.68 dB | 33.42 |
| real | 640×384 × 241f | 36.78 dB | 30.31 |
| **real** | **1280×768 × 73f** | **43.77 dB** | 39.79 |
| real | 1280×768 × 121f | 43.69 dB | 38.87 |
| real | 1280×768 × 241f | 43.13 dB | 37.26 |
| pattern | 1280×768 × 73f | 28.47 dB | 27.38 |
| pattern | 1280×768 × 121f | 28.48 dB | 27.62 |
| pattern | 1280×768 × 241f | 28.43 dB | 27.56 |
| pattern | 1920×1088 × 73f | 29.76 dB | 28.81 |
| pattern | 1920×1088 × 121f | 29.80 dB | 28.65 |
| pattern | 1920×1088 × 241f | 29.73 dB | 28.65 |
| pattern | 960×544 × 241f | 25.54 dB | 24.63 |

**天井そのものは合格です。** 実写 1280×768 で 43.77 dB は、2.3 の C0-prep が
同じ場所で測った 42.81 dB と同等以上です。フレーム数を 73 → 241 に伸ばしても
0.6 dB しか落ちません（VAEのタイル分割が効いている証拠）。

色ずれ（ドメイン取り違え）は起きていません。チャンネル別のDC成分を除去しても
PSNRはほとんど変わらず（例: 28.427 → 28.435）、損失は純粋に質感側です。
つまり計画の C-1（float[0,1] ↔ u8 境界）は本スクリプトの経路で正しく守られています。

### G2 への申し送り

計画の G2 判定は「keepコアPSNR ≥ 30」ですが、この閾値は**素材によって意味が変わります**。
FHD素材（テストパターン）では往復天井そのものが 29.8 dB しかないため、
**同じ素材で 30 dB を要求すると原理的に不合格になります**。G2 では
必ず「その素材・その形状の G0-c 天井」との相対で読んでください。本表がその天井です。
（なお実際の配信物では keep 領域はラプラシアンブレンドで元キャンバス画素に
戻されるため、VAE往復天井は keep 領域の上限にはなりません。効いてくるのは
pad帯と継ぎ目の評価です。）

## G0-d — VRAM 実測

### (i)(ii) エンコードのVRAMピーク

計画（H-5）の方針は「参照encode・再encode とも**デコード用に解決済みの
tiling_config を直渡し**、G0-d で不足が出たときだけ専用予算を導入」でした。
**不足が出ました。** ただし原因はタイルの大きさではなく、
**bf16 Conv3d の im2col フォールバック**でした。

解決済みの tiling_config は形状によらず一定です
（`frames 80/24, height 448/64, width 768/64` — 2.5の CONV VAE では
`AUTO_TILING` がアスペクト専用の分岐に落ちるため）。したがってピークは
「解像度」ではなく「タイルが満杯かどうか」で決まります。

| 形状 | エンコード経路 | alloc(MB) | **reserved(MB)** | 秒 | 往復PSNR |
|---|---|---|---|---|---|
| 1280×768 × 73f | 素の `tiled_encode`（直渡し） | 13054 | **15686** | 6.4 | 28.465 |
| 1280×768 × 73f | + `set_conv3d_memory_format` | 3094 | **3568** | 4.8 | 28.462 |
| 1920×1088 × 73f | 素の `tiled_encode`（直渡し） | 13055 | **15694** | 13.4 | 29.762 |
| **1280×768 × 241f** | **素の `tiled_encode`（直渡し）** | 14417 | **27188（スピル）** | **52.3** | 28.429 |
| 1280×768 × 241f | + `_retake_encode_tiling` 予算(448×384) | 7524 | **13922** | 24.2 | 28.051 |
| **1280×768 × 241f** | **+ `set_conv3d_memory_format`** | **3366** | **6174** | **19.0** | **28.427** |
| 1920×1088 × 241f | + `set_conv3d_memory_format` | 3374 | 6164 | 41.5 | 29.727 |
| 640×384 × 241f（半解像度） | + `set_conv3d_memory_format` | 2577 | 4588 | 4.7 | 36.781 |
| 960×544 × 241f（半解像度） | + `set_conv3d_memory_format` | 3362 | 6162 | 10.6 | 25.541 |

カード総量は 16376 MiB。**reserved が 15500 MB を超えた行は WDDM の共有システム
メモリに逃げています（スピル）** — 落ちはしませんが激遅になります。
1280×768 × 241f の素の直渡しは 27188 MB / 52.3 秒で、これは `chain25` の
`RETAKE_ENCODE_TILE_AREA_BUDGET` の docstring が retake で記録した
「27190 MB」とぴたり一致します。同じ罠です。

**境界: 素の直渡しは最小形状（1280×768 × 73f）ですでに 15686 MB で、
16GB の縁に張り付いています。** つまり「どの形状から超えるか」ではなく
**「実用上どの形状でも危ない」**が答えです。

### (iii) `image_conditioner` 2回目の重み再読込コスト

計画の 27（stage-2 再encode）は `image_conditioner` の2回目呼び出しになります。
全16行で計測した再読込オーバーヘッドは **0.34〜0.47 秒**（241フレームの素の
直渡しだけ 1.32 秒 — スピル中のため）。1回目と2回目の出力は**全行でビット一致**
（`call1_call2_bit_identical: true`）。

**懸念は不要です。** 半秒未満のコストのために `ImageConditioner` の
ライフサイクルを触る価値はありません。計画どおり2回呼んでください。

### デコード側（参考・本テーマの対象外）

デコードは既存の出荷経路そのものですが、長尺・高解像度で reserved が伸びます:
1920×1088 × 241f のデコードは **19818 MB（スピル）**、1920×1088 × 121f で 13818 MB。
これは outpaint が持ち込む問題ではなく 2.5 の既存の性質です。
Outpainting が FHD 級 × 241f を許すなら、**その組み合わせは outpaint 固有の
問題ではないと明記したうえで**台帳に別件として起票するのが筋です。

## G0-e — VAE空間ストライドと 128倍数キャンバス

`tiling_scale_factors_for_vae` が返す実測値:

```
SpatioTemporalScaleFactors(time=8, height=32, width=32)
```

**空間ストライドは 32 です。** 2.3 の `engine/outpaint/canvas.py` は
`CANVAS_MULTIPLE = 128` を「64px VAEストライド × 2」と説明していますが、
2.5 のストライドはその半分です。したがって **128 は 2.5 にとって
必要量（64 = 32×2）のちょうど2倍**であり、計画のリスク R-3
「128 ⊂ 64」は成立します。**`CANVAS_MULTIPLE` を変える必要はありません。**

`VideoLatentShape.from_pixel_shape` は 9形状すべてで端数を落としませんでした
（実測のエンコード結果も 16行すべて `latent_shape_matches_expected: true`）:

| 画素 | latent | 割り切れ |
|---|---|---|
| 1280×768 × 73f | (1,128,10,24,40) | 1280/32=40, 768/32=24 |
| 1280×768 × 241f | (1,128,31,24,40) | 同上 |
| 1920×1088 × 241f | (1,128,31,34,60) | 1920/32=60, 1088/32=34 |
| 640×384 × 73f（stage-1半解像度） | (1,128,10,12,20) | 640/32=20, 384/32=12 |
| 960×544 × 73f（同・FHD級） | (1,128,10,17,30) | 960/32=30, 544/32=17 |
| 896×512 × 73f（2.3 W2キャンバス） | (1,128,10,16,28) | — |

半解像度側（キャンバス÷2 = 64の倍数）もストライド32でちょうど割り切れます。
**キャンバス倍数128なら stage-1・stage-2 のどちらでも端数は発生しません。**

**注意点が1つ**: `1920×1088` は **128の倍数ではありません**（1088 % 128 = 64）。
G0-c/G0-d では課題の指示どおり測りましたが、Outpainting の正当なキャンバスには
なりません。FHD級の正当なキャンバス高は **1024 または 1152** です。

## C1設計への申し送り

### 1.（最重要・引き算）全解像度 encode には `set_conv3d_memory_format` を掛ける

計画の「H-5採用・引き算」— *タイル予算は先回りせず、G0-d で不足が出たときだけ導入* —
の条件は成立しました。ただし**導入すべきものはタイル予算ではありません**。

`reference25.set_conv3d_memory_format(encoder, torch.channels_last_3d)` で
エンコーダの Conv3d 重みを囲むだけで、1280×768 × 241f の reserved が
**27188 MB → 6174 MB**、時間が **52.3 s → 19.0 s** になり、
往復PSNRは **28.429 → 28.427（差 0.002 dB）** で変わりません。

タイル予算（`_retake_encode_tiling`）と比べても全項目で優ります:

| | reserved | 秒 | PSNR差 |
|---|---|---|---|
| タイル予算 448×384 | 13922 MB | 24.2 | **−0.378 dB** |
| **channels_last_3d 再レイアウト** | **6174 MB** | **19.0** | **−0.002 dB** |

しかもこれは**新しい仕組みではありません**。`reference25` が factor-1 の参照encode で
すでに使っている出荷済みの関数で、`reference_conditioning_from_pixels` の docstring が
理由まで書いています（torch 2.9 の bf16 Conv3d が contiguous 重みに対して im2col
フォールバックを取り、`in_ch*27 × 出力体積` の bf16 行列を畳み込みごとに実体化する）。
2.3 では 6265 → 1198 MiB と記録されており、今回の 13054 → 3094 MB は同じ現象です。

**C1への具体的な指示:**

* 手順27（stage-2 全解像度再encode）は `enc.tiled_encode(pixels, tiling_config)` を
  `set_conv3d_memory_format` の try/finally で囲む。**`finally` での contiguous 復帰は
  必須**（`reference25` の docstring が言うとおり、これは衛生ではなく正しさの要件）
* tiling_config は計画どおり**デコード用解決済みを直渡し**のまま。変える必要はない
* `_retake_encode_tiling` 予算は**採らない**（計画の「先回りしない」方針を維持できる）
* 手順11（半解像度参照encode）は `reference_conditioning_from_pixels` を呼ぶだけで
  すでにこの再レイアウトを通ります（factor=1 のため）。**追加対応不要**。
  実測 2384〜3362 MB で余裕あり
* この差分は「意図的差分」として記録する価値があります（2.3側は同じ場所で
  タイル予算を使っているため）

### 2. G2 の PSNR 閾値は素材ごとの天井と相対で読む

計画の G2 は「keepコアPSNR ≥ 30」を絶対閾値として持っています。W2ゲートの
**FHD素材はテストパターンで、VAE往復天井が 29.8 dB しかありません**。
FHD腕をその素材で回すと、実装が完璧でも 30 を割ります。上の G0-c 表を
天井として相対で判定してください。1280×768 の実写腕なら 43.77 dB が天井なので
30 は十分に余裕のある閾値です。

### 3. 1920×1088 はキャンバスとして不正

O8（最大幾何）の腕を組むときは 1088 を使わないでください。128の倍数ではありません。
FHD級なら **1920×1152** か **1920×1024**。

### 4. G0スクリプトが C-1 の境界を先行実証しました（R-15）

デコード出力は実測で `torch.bfloat16` の float[0,1]（min 0.0 / max 1.0）、
形状は **(F, H, W, C)** でした（(B,C,F,H,W) ではありません）。
`.mul(255).round().clamp(0,255).to(uint8)` で u8 化し、
VAE入力側は `/127.5 - 1.0`（`normalize_images`）で戻す往復を全行で通しており、
DC成分の残留は 0.03〜1.45/255 と無視できる範囲です。C1 の dtype・レンジ検査テストは
この形状（F,H,W,C）を前提に書いてください。

### 5. 強度の既定は 1.0 のまま（分岐は発生せず）

G0-b の分岐（「1.0不足ならFE固定値＝アプリ層＝別テーマ」）は**発生しません**。
