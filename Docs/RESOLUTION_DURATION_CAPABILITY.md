# 16GB VRAM 解像度×尺 能力リファレンス（実測）

作成: 2026-06-30 / 性格: **16GB(RTX 4070 Ti SUPER)で LTX-2.3 がどの解像度・どの尺まで動画を生成できるかの実測結果と推定式**。AviUtl2 拡張の UI（解像度/尺の選択肢・所要時間の目安）設計、および将来の尺・解像度見積りの一次根拠。
関連: [VERIFICATION_LOG.md](VERIFICATION_LOG.md) §10.6（生データ・経緯）、[LTX23_REFERENCE.md](LTX23_REFERENCE.md)（トークン理論）、memory `[[720p-16gb-verified]]`。

## 0. TL;DR — 能力表

| 表示解像度 | 生成サイズ(÷64) | 5秒(121f) | **実用最長** | 5秒の生成時間 |
|---|---|---|---|---|
| 720p | 1280×768 | ✅ | （5秒で検証・余裕大） | ~2.8分 |
| **1080p** | 1920×1088 | ✅ | **≥11秒（速度律速・さらに先も可）** | 4.3分 |
| **1440p** | 2560×1472 | ✅（限界点） | **~5秒** | 11分 |
| **4K(2160p)** | 3840×2176 | ❌ | **~2秒** | — |

- **生成サイズは必ず ÷64**（two-stage distilled の契約）。**表示解像度へは中央 crop**（例 1088→1080、1472→1440、2176→2160）。crop は既定 OFF＝既定で生成サイズのまま配信（[api/models.py] `crop_output`）。
- **音声は joint で自動生成**（AAC/48kHz/stereo）。発話・効果音・音楽はプロンプト依存（ベストエフォート）。
- 設定: **use_component_files=true（Path B）/ LTX_KEEP_RESIDENT=0 / block_swap_blocks_on_gpu=8 / vae_spatial_tile_size=512 / vae_temporal_tile_size=64**（＝本番デフォルト）。

## 1. 核心の発見 — ボトルネックは「生成」でなく「ロード」

- **VRAM 天井 ＝ ロード時の Gemma text-encode ピーク `max_alloc 15,098 MB`（解像度にも尺にも完全に非依存の固定費）**。物理 dedicated は 16,376 MB で、ここに ~2.3GB の shared 溢れを伴いつつ毎回これを通過する。
- **生成（denoise/upsampler/VAE decode）は、小〜中サイズではこの天井に対し大きな余裕がある。** よって「より大きい/長い動画」を阻むのはロード固定費であって、生成そのものではない。
- 唯一スケールするのは **denoise stage2**（フル解像度の再デノイズ）。これが尺・解像度（＝トークン数）に比例して増える。

## 2. VRAM 推定式（フェルミ）

### トークン数
```
N = (W/32) × (H/32) × (1 + (F-1)/8)
```
（W,H＝生成解像度、F＝フレーム数。VAE 32×空間圧縮・8×時間圧縮の帰結。）

### denoise stage2 の max_alloc（実測フィット）
```
低〜中トークン(N ≲ 32,000):   den2 ≈ 5,085 MB + 0.175 × N
高トークン(天井付近, N ≳ 32,000): den2 ≈ 10,796 MB + 0.194 × (N − 32,640)
```
- 常駐ベースライン ~5GB（block-swap 8ブロック等）＋ 活性 ~0.175–0.194 MB/token。
- 高トークン側で傾きがやや急になる（アテンションの N² 項・周辺オーバーヘッドが効き始める）。
- **実測との一致は ±1%**（下記検証）。

### VAE decode は横ばい
- `vae_spatial_tile_size=512 / vae_temporal_tile_size=64` のタイル化により、**VAE decode は解像度・尺に依存せず ~1.9GB 固定**。末端スパイクの心配は無い。

### 使い方（任意の解像度×尺の見積り）
1. N を計算。
2. den2 を式で推定。
3. 判定: **den2 < ~15,100MB なら天井（ロード）内で快適**。**15,100〜18,000MB なら shared へ溢れて完走するが遅い**。それ以上は更に遅く、いずれ非実用。
   - 例: 1080p/241f(10s) → N=2,040×31=63,240 → den2≈10,796+0.194×30,600=16,733MB → 溢れるが完走（実測 16,815・11.3分）。

| 尺 | F | **den2** | shared | commit% | 時間 | 結果 |
|---|---|---|---|---|---|---|

## 4. メカニズム — 上限は「OOM」でなく「速度」

- dedicated 物理 16,376MB は **ロード時に既に飽和**（den2 が小さくても enc が天井）。
- 尺を伸ばすと den2 が増え、**物理を超えた分は shared へページング**。commit（物理RAM＋ページファイル）に余裕がある限り**生成は完走する**。
- 代償は**速度**: shared は system RAM 経由のため、溢れた GB 分だけ遅くなる。1080p では概ね **+3〜4分/秒**（9s=9分 → 11s=15分）。
- したがって 16GB での実用上限は**「どこまで待てるか」**で決まる。1080p は 11秒まで実測で確実、12秒以降は1本20分超で実用性が落ちる。1440p/4K は早い段階で den2 が天井を超えるため尺が短い。

## 6. AviUtl2 UI への含意
- **解像度選択肢**: 720p / 1080p / 1440p / 4K（いずれも生成÷64→crop）。
- **尺の上限を解像度に応じて可変に**（実測根拠）: 1080p≤~11秒、1440p≤~5秒、4K≤~2秒。UI 側で上限を提示し、超過時は警告（「生成が大幅に遅くなります」）。
- **所要時間の見積り表示**: §5 を内蔵すれば、ユーザーが生成前に待ち時間を把握できる。
- 生成サイズと表示解像度の差（÷64→crop）は UI で吸収（生成1088→表示1080 等）。

## 7. 再現方法・アーティファクト
- ハーネス: `scratchpad/gen_one.py`（本番同等設定で直接 `LTXFastVideoPipeline.create()/generate()` を叩き、API の÷64/解像度制限をバイパス）＋ `sampler_all.ps1`（GPU dedicated/shared ＋ system commit 同時サンプリング）＋ 昇順 orchestration（OOMで打ち切り）。※これらは scratchpad（リポジトリ外）の使い捨て。
- 計測物: `outputs/bigres_*`（解像度スイープ）/ `outputs/verify_*`（5秒検証）/ `outputs/long_1080p_*`（1080p長尺・音声付き）。各 mp4 ＋ sampler CSV ＋ 段境界 phase_timeline JSON。
- 計測の要諦: worker の `peak_vram_mb`（torch max_allocated）は dedicated/shared を区別できないため、**必ず perf-counter で dedicated/shared/commit を別取り**する（VERIFICATION_LOG §5）。

## 付記（前提・限界）
- 本表は **comp=1 / keep=0 / bs=8 / vae512-64** 構成・このマシン（RAM64GB＋pagefile、commit上限~113GB）での実測。RAM/pagefile が小さい環境では commit 上限が下がり、長尺で先に commit 枯渇しうる（[[no-large-pagefile-disk-requirement]]）。
- 音声の発話内容は生成物（ベストエフォート）。正確なセリフ再現は保証されない。
- den2 式は 720p〜4K・1〜11秒の範囲で検証。範囲外は外挿のため誤差が増えうる。
