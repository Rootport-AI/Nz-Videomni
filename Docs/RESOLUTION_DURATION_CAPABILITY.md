## 0. TL;DR — 能力表

| 表示解像度 | 生成サイズ(÷64) | 5秒(121f) | **実用最長** | 5秒の生成時間 |
|---|---|---|---|---|
| 720p | 1280×768 | ✅ | （5秒で検証・余裕大） | ~2.8分 |
| **1080p** | 1920×1088 | ✅ | **≥11秒（速度律速・さらに先も可）** | 4.3分 |
| **1440p** | 2560×1472 | ✅（限界点） | **~5秒** | 11分 |
| **4K(2160p)** | 3840×2176 | ❌ | **~2秒** | — |

- **生成サイズは必ず ÷64**（two-stage distilled の契約）。**表示解像度へは中央 crop**（例 1088→1080、1472→1440、2176→2160）。crop は既定 OFF＝既定で生成サイズのまま配信（[api/models.py] `crop_output`）。
- **音声は joint で自動生成**（AAC/48kHz/stereo）。発話・効果音・音楽はプロンプト依存（ベストエフォート）。
- 設定: **use_component_files=true（Path B）/ LTX_KEEP_RESIDENT=0 / block_swap_blocks_on_gpu=8 / vae_spatial_tile_size=512 / vae_temporal_tile_size=64**（＝本番デフォルト）。
  - ※`LTX_KEEP_RESIDENT` は当時の手順。2026-08-02 に環境変数の経路は撤去され、現在は API の `keep_resident` フィールド（`POST /generate`・`POST /generate/chain`。既定 `false`＝上記の keep=0 と同じ状態）で指定する（[`VERIFICATION_LOG.md`](VERIFICATION_LOG.md) §48）。
- **▶ 「実用最長」と「溢れない尺」は別軸（2026-07-01 実測で明確化）**: 上表の「実用最長」は *溢れても待てる速度上限*（spill 容認・低速化を許容）。一方 **VRAM が溢れ始めない最長尺（快適域）** は別で、直接実測 = **720p 257f=10.67秒（API上限で clean・物理境界は<321f＝321f は追試で溢れ）・1080p ~6.3秒(153f)・1440p ~3.3秒(81f)**。生成時間は各解像度の天井で ~340秒に収束（§8.6）。正本は **§8.4／§8.6**（旧 doc の外挿値 720p~18.5s/1080p~8.5s は実測で下方修正・退行ではない）。

## 1. 核心の発見 — ボトルネックは「生成」でなく「ロード」

- **VRAM 天井 ＝ ロード時の Gemma text-encode ピーク `max_alloc 15,098 MB`（解像度にも尺にも完全に非依存の固定費）**。物理 dedicated は 16,376 MB で、ここに ~2.3GB の shared 溢れを伴いつつ毎回これを通過する。
- **生成（denoise/upsampler/VAE decode）は、小〜中サイズではこの天井に対し大きな余裕がある。** よって「より大きい/長い動画」を阻むのはロード固定費であって、生成そのものではない。
- 唯一スケールするのは **denoise stage2**（フル解像度の再デノイズ）。これが尺・解像度（＝トークン数）に比例して増える。

> **★追記（2026-07-01）：`--te-offload`（既定 ON）が Gemma text-encode ピークを ~10.5GB に低減。** 逐次 per-layer ストリーミング（GGUF Gemma 48 層を CPU 常駐→2層ずつ GPU へ）で、この **Gemma text-encode ピーク（peak ①）を 15,839→10,540 MB（−33%）に下げ、encode 時の shared 溢れも消去**（512×320/49f A/B 実測。VERIFICATION_LOG §11）。**ただし本表の能力上限は不変**：ジョブ全体の天井は **denoise stage2（peak ②）** で決まり、te-offload は peak ① のみを下げる（全体 `peak_vram_mb` は両モードとも 16,944 で不変）。よって §2 の den2 推定式・§3 の実測値・§8.4 の「溢れない尺上限」はすべて**そのまま有効**（den2 は te-offload の影響を受けない）。本書の測定値は変更しない。
>
> **★追記（2026-07-01）：`--dit-cpu-load`（既定 ON）が transformer ロード時の一過性 GPU スパイク（~16.9GB）を除去。** 従来は block-swap が GGUF transformer の 48 ブロックを一旦 full-GPU に materialize（~16.9GB）してから CPU 退避していた＝これが「ロード固定費」の主要因。本機能は transformer を**直接 CPU 構築**し block 以外のみ GPU へ移すことで、この **LOAD 時 materialization スパイクを除去**（transformer-load Dedicated 15,815→1,444 MB＝−14.4GB・512×320/49f A/B 実測。compute は GPU・出力バイト一致。VERIFICATION_LOG §12）。これにより**小〜中サイズでは全体ジョブ天井がもはや transformer-load スパイクで決まらなくなる**（512×320 で whole-job ceiling が torch `max_memory_allocated` 16,944→~9.2GB）。**ただし §0 の能力表・§2 の den2 推定式・§3 の実測値はすべて不変**：dit-cpu-load が消すのは固定 LOAD スパイクのみで、**解像度・尺にスケールする denoise stage2（den2）の活性成長には影響しない**（den2 こそが大解像度・長尺での真の制約軸）。本書の測定値は変更しない。

## 2. VRAM 推定式（フェルミ）

### トークン数
```
N = (W/32) × (H/32) × (1 + (F-1)/8)
```
（W,H＝生成解像度、F＝フレーム数。VAE 32×空間圧縮・8×時間圧縮の帰結。）

### denoise stage2 の max_alloc（実測フィット）
```
低〜中トークン(N ≲ 32,000):   den2 ≈ 5,085 MB + 0.175 × N
高トークン(天井付近, N ≳ 32,000): den2 ≈ 10,796 MB + 0.194 × (N − 32,640)
```
- 常駐ベースライン ~5GB（block-swap 8ブロック等）＋ 活性 ~0.175–0.194 MB/token。
- 高トークン側で傾きがやや急になる（アテンションの N² 項・周辺オーバーヘッドが効き始める）。
- **実測との一致は ±1%**（下記検証）。
- ⚠️ **式は 1080p 中心に較正**（較正点＝1080p/1440p/4K の 25f＋720p の 5s）。**較正域外の高トークン外挿（特に 720p 長尺）は直接実測より楽観的**（式は 720p「溢れない尺」を ~18.5s と出すが、実測 §8.6 は ~13s）。**「溢れない尺」の正本は §8.4 の実測 caps**（式は傾向把握用に温存）。

### VAE decode は横ばい
- `vae_spatial_tile_size=512 / vae_temporal_tile_size=64` のタイル化により、**VAE decode は解像度・尺に依存せず ~1.9GB 固定**。末端スパイクの心配は無い。

### 使い方（任意の解像度×尺の見積り）
1. N を計算。
2. den2 を式で推定。
3. 判定: **den2 < ~15,100MB なら天井（ロード）内で快適**。**15,100〜18,000MB なら shared へ溢れて完走するが遅い**。それ以上は更に遅く、いずれ非実用。
   - 例: 1080p/241f(10s) → N=2,040×31=63,240 → den2≈10,796+0.194×30,600=16,733MB → 溢れるが完走（実測 16,815・11.3分）。

## 4. メカニズム — 上限は「OOM」でなく「速度」

- dedicated 物理 16,376MB は **ロード時に既に飽和**（den2 が小さくても enc が天井）。※ 2026-07-01 以降は `--te-offload`（既定 ON）で enc（Gemma text-encode）ピークが ~10.5GB に下がり、**この「ロード時飽和」は緩和**された（encode 時 shared 溢れ消失・VERIFICATION_LOG §11）。**だが実用上限は den2（peak ②）が依然律速**なので本節の結論（上限は OOM でなく速度）は不変。
- 尺を伸ばすと den2 が増え、**物理を超えた分は shared へページング**。commit（物理RAM＋ページファイル）に余裕がある限り**生成は完走する**。
- 代償は**速度**: shared は system RAM 経由のため、溢れた GB 分だけ遅くなる。1080p では概ね **+3〜4分/秒**（9s=9分 → 11s=15分）。
- したがって 16GB での実用上限は**「どこまで待てるか」**で決まる。1080p は 11秒まで実測で確実、12秒以降は1本20分超で実用性が落ちる。1440p/4K は早い段階で den2 が天井を超えるため尺が短い。

## 6. AviUtl2 UI への含意
- **解像度選択肢**: 720p / 1080p / 1440p / 4K（いずれも生成÷64→crop）。
- **尺の上限を解像度に応じて可変に**（実測根拠）: 1080p≤~11秒、1440p≤~5秒、4K≤~2秒。UI 側で上限を提示し、超過時は警告（「生成が大幅に遅くなります」）。

- 生成サイズと表示解像度の差（÷64→crop）は UI で吸収（生成1088→表示1080 等）。

## 8. 追補（2026-06-30 後半）: denoise窓のshared再算出・溢れ起因の時間肥大化・溢れない尺上限

> 本節は §3 の元アーティファクト（sampler CSV × phase_timeline JSON）を **denoise stage2(den2)窓に限定して** 取り直した再分析。§0–§7 の "shared" はグローバル（全工程）ピークを含むため、**「VRAM溢れ」を論じる指標としては本節を正とする**。

### 8.1 重要な訂正 — §3 の "shared" 列はロード時(Gemma encode)ピーク
§3.2/§3.3 の "shared" 値の多くは、**モデルロード時(Gemma text-encode・解像度非依存 ~2.0–2.6GB)のグローバルピーク**であり、denoise 過程の実消費ではない。den2窓で取り直すと食い違う:

| run | §3表 shared | ロード時ピーク | **den2窓 shared(真値)** |
|---|---|---|---|
| 1080p/5s | 2,348 | 2,348 | **351** |
| 1080p/9s | 2,462 | 2,462 | **2,122** |
| 4K/2s | 3,513 | 3,513 | **1,906** |
| 1080p/10s | 3,892 | 3,892 | 3,892（一致）|
| 1080p/11s | 5,506 | 5,506 | 5,506（一致）|

短〜中尺では denoise の shared 消費はロード時より小さく、長尺(1080p 10s〜)で初めて den2 溢れがロード時を上回る。**「溢れ」を測るときは den2窓の値を使うこと。**

縦=解像度 / 横=尺。全セル CSV×den2窓から再算出した正確値。

**表A（denoise shared ピーク MB）**

|---|---|---|---|---|---|

- **オーガニック(非溢れ)ベースライン ≈ 1GB**（block-swap の CPU 側ステージング/pinned 転送等）。720p列は尺によらず ~1GB フラット＝**溢れなし**。よって実効 **spill ≈ shared − 1GB**。

- サンプリング間隔は実測 ~5秒（§7記載の0.5秒ではない）。短尺(2s)は5–8サンプルで粗く±数百MBの取りこぼし可能性。長尺(9–11s)は60–120サンプルで高信頼。
- アーティファクト所在: 720p各尺=`outputs/fill_720p_*`・`outputs/run720p`、1080p各尺=`outputs/fill_1080p_2s`・`outputs/verify_1080p_5s`・`outputs/long_1080p_{9,10,11}s`、1440p=`outputs/fill_1440p_2s`・`outputs/verify_1440p_5s`、4K=`outputs/verify_4k_2s`。各 `sampler*.csv` ＋ `phase_timeline_*.json`。

### 8.3 溢れ起因の時間肥大化の実証（計算量の伸びだけでは説明不可）
各尺列はフレーム数が同一なので、純計算（FLOPs律速）なら 1080p/720p の時間比は空間トークン比 ≈2.1倍で**尺によらず一定**のはず。実際は:

| 尺 | 720p | 1080p | 1080p/720p比 |
|---|---|---|---|
| 2s | 136 | 166 | 1.22 |
| 5s | 172 | 262 | 1.52 |
| 9s | 238 | 549 | **2.31** |
| 10s | 262 | 678 | **2.59** |
| 11s | 280 | 896 | **3.20** |

比が 1.22→3.20 と右肩上がりに膨張し、これは 1080p の spill 立ち上がり(§8.2)と同期。720p(溢れなし)では同じフレーム増加でこの爆発が起きない。**→ 1080p長尺の超線形の時間伸長は spill(VRAM↔system RAM の PCIe 帯域律速ページング)起因であると実証**。§4 の「+3〜4分/秒は spill 起因」という帰属推定を、解像度間比較で裏付けた形。

### 8.4 溢れない尺の上限（16GB・本番直結）★2026-07-01 直接実測で更新

> **▶ 更新（2026-07-01）**: 本節の値は当初 den2 推定式からの**外挿**だったが、**§8.6 の直接実測スイープ**で各解像度の溢れ境界を実測し、下表を実測値へ置換した。**旧・式外挿値（720p ~18.5s / 1080p ~8.5s）は実測で下方修正**（下表「旧（式外挿）」欄に温存）。**これは退行ではない**——denoise VRAM（torch max_alloc）は QAT/text-only リファクタ前後で **2MB 差以内一致**（§8.6・1080p 5s/10s）＝旧 caps は最初からこの実 VRAM 挙動で、今回**外挿でなく直接測っただけ**。

溢れ開始の実効天井: **dedicated が物理 16,376MB（16GB）に飽和した瞬間**、full-res の upsampler stage2＋den2 窓で shared へ spill（§8.6 機序）。torch 換算の den2 max_alloc ≈ **15,100MB**（物理 − 非torch OH ~1,300）。

| 表示解像度 | 生成サイズ | **溢れない最長（実測）** | 旧（式外挿・supersede） | 備考 |
|---|---|---|---|---|
| **720p** | 1280×768 | **257f=10.67秒（API上限・実測 clean）** | ~18.5秒（外挿・720p実測アンカー無し） | 物理溢れ境界は **257<x<321f**（321f は追試で溢れ・旧推定 ~326f は楽観、§8.6）。API `num_frames≤257` が実効上限＝**257f が実運用の溢れない最長** |
| **1080p** | 1920×1088 | **~6.3秒 / 153f** | ~8.5秒（式逆算） | 物理 spill が律速（API 257f に届く前に溢れる） |
| **1440p** | 2560×1472 | **~3.3秒 / 81f** | （§8.4本表に無し） | 物理 spill が律速 |

- **実測ブラケット（§8.6）**: 720p 10s(241f)溢れなし→20s(481f)溢れ／1080p 5s(121f)溢れなし→10s(241f)溢れ／1440p 2s(49f)溢れなし→5s(121f)溢れ。上表はこのブラケット内を直接内挿した値（外挿でなく実測境界内）。
- **旧 N_max ≈ 54,800（den2=15,100 を §2 高N式で逆算）**は 1080p 中心に較正した式の外挿値で、720p は較正域外＝楽観的だった（実測 §8.6 で確定）。
- **API含意**: 解像度別に「溢れない尺」を内部しきい値に持つ。**720p は API 257f(10.67s)が先に効く**（物理溢れ ~13s には届かず快適）。**1080p ~6.3s・1440p ~3.3s を超えると spill で大幅低速化**（§6 UI 含意の数値根拠）。

### 8.5 （参考・将来課題）8GB VRAM での capability フェルミ推定 → 台帳へ移設済み

> ⚠️ **8GB対応は現プロジェクトの当面の対象外。** 本節にあったフェルミ推定表（480p ~177f／720p ~73–81f／1080p ~33f／1440p ~9f／4Kは静止画1枚のみ。実測ではなく §8.4 の枠組みを 8GB へ外挿した**楽観的上限**）は、2026-07-27の整理で[`PENDING_TASKS.md`](../../Nz-LTX23-frontend-AviUtl2/Docs/PENDING_TASKS.md) §4-4へ移設した。**以後の管理は同書で行う。** 16GB の実測正本は本書§8.4・§8.6（本節の外挿元）。8GB での有効な調整軸（`block_swap_blocks_on_gpu` を 8 から減らす）も同書 §4-4 へ収録済み。

### 8.6 直接実測スイープ（2026-07-01・16GB本番設定・dedicated/shared 実測）
QAT/text-only リファクタ後、本番 production path で 480p–4K × 2–20秒の **11本を生成**し、**専用(dedicated)・共有(shared) GPU メモリを perf-counter で実測**（RTX 4070 Ti SUPER の LUID にロック・全11本成功/OOMゼロ）。これが §8.4 の「溢れない尺」を式外挿でなく直接確定した根拠。データ＝`outputs/vram_sweep/sweep_manifest.json`。

| 480p 2s | 896×512 | 2 | 49 | 11,231 | 151（無） | 8,440 | 108 |

| 720p 5s | 1280×768 | 5 | 121 | 15,014 | 187（無） | 8,535 | 157 |

- **溢れ機序**: 溢れ4本（4K2s・1440p5s・1080p10s・720p20s）は **dedicated が ~15.9–16.0GB（16GB天井）に飽和した瞬間**に shared へ spill。spill は低解像度の den1 でなく **full-res の upsampler stage2＋den2 窓**で発生（両者は同じ full-res・full-length latent を扱う）。溢れると WDDM ページングで **wall-clock 2–3倍**・ただし全11本 **OOM せず完走**（天井は「溢れて遅くなる」であって「落ちる」ではない）。
- **画素数が支配的**: 溢れの重さは 4K(4,522) > 1080p10s(3,660) > 1440p5s(3,185) > 720p20s(2,381)。フレーム数より解像度（画素数）が dedicated を押し上げる。
- **★退行なしの対照（QAT リファクタ前 vs 後）**: リファクタ前の実測 den2 max_alloc（VERIFICATION_LOG §10.6）と今回の worker peak_vram_mb（＝これらの尺では den2 が全工程ピーク）が **2MB 差以内で一致**——1080p 5s: 旧 10,798 / 新 10,800、1080p 10s: 旧 16,815 / 新 16,817。**＝溢れ律速の denoise VRAM は不変**。§8.4 の「値が変わった」のは退行でなく **旧＝式外挿／新＝直接実測** の測定手法の差。
- 20s(481f) は API `num_frames≤257` を harness 内でのみ回避して物理計測（engine/config 不変）。**API 経路の実運用上限は 257f=10.67秒**。
- **▶ 溢れない最長尺の生成時間（2026-07-01 追試・`outputs/max_spillfree/`）**: 各解像度の溢れ天井で生成時間を実測。**720p 257f(10.67s)=270秒（clean・shared 185MB）／1080p 153f(6.3s)=343秒／1440p 81f(3.3s)=334秒**。**天井では解像度に依らず ~334–344秒（~5.7分）にほぼ収束**（総 denoise 仕事量が同程度＝空間ディテールと尺長を交換しているだけ）。720p 257f だけ 270秒と速いのは、API 257f 上限が 720p の物理天井より手前で頭打ち＝天井に余裕があるため。**720p 境界の較正**: **321f(13.3s)は追試で溢れた**（shared 1,148MB・344秒）→ 真の 720p 溢れ境界は **257<x<321f**（§8.4 の旧推定 ~326f はわずかに楽観的）。1080p 153f・1440p 81f は推定どおり溢れず（実測妥当）。
